**[학생]테이블**

# 1. 위 '학생' 테이블은 (  ) 무결성 제약조건을 위반했다. 괄호에 들어갈 단어를 쓰시오.

### 💡 답변 (Assistant)

---

## ✅ 문제 분석

제시된 테이블의 핵심 포인트를 보면:

- **기본키: 학번**
- 데이터 중 **학번이 NULL인 행 존재**

→ 핵심 키워드:
**기본키, NULL 값, 식별자**

---

## 🎯 정답  
👉 **개체 무결성 (Entity Integrity)**

---

## 📌 정답인 이유

**개체 무결성(Entity Integrity)**의 정의는 다음과 같습니다.

| 구분 | 설명 |
|------|------|
| 대상 | 기본키(Primary Key) |
| 조건 | NULL 값 허용 ❌ |
| 목적 | 각 행을 유일하게 식별 |

---

문제에서:

> 학번 = 기본키  
> 그런데 학번이 NULL인 데이터 존재

→ 기본키는 **절대 NULL이 될 수 없음**

따라서  
👉 **개체 무결성 위반**

---

## 🔎 헷갈릴 수 있는 오답

### ❌ 참조 무결성 (Referential Integrity)

- 외래키(Foreign Key) 관련
- 다른 테이블과의 관계에서 발생
- 현재 문제는 **단일 테이블 + 기본키 문제** → 해당 없음

---

### ❌ 도메인 무결성 (Domain Integrity)

- 속성 값의 범위, 형식, 타입 제한
- 예: 학번은 숫자만, 전공은 특정 값만 등

→ NULL 문제는 **도메인보다 기본키 규칙 문제**

---

## 📚 추가로 공부해야 할 것 (핵심 정리)

### 1️⃣ 무결성 제약조건 3대장 (시험 핵심)

| 종류 | 설명 |
|------|------|
| 개체 무결성 | 기본키는 NULL ❌, 중복 ❌ |
| 참조 무결성 | 외래키는 참조 대상 존재 |
| 도메인 무결성 | 속성 값의 범위/형식 제한 |

---

### 2️⃣ 개체 무결성에서 꼭 기억할 것

✔ 기본키 특징  
- 유일성 (Unique)  
- 최소성 (Minimal)  
- **NULL 불가 (시험 핵심)**  

---

## 🧠 실기시험 포인트 정리

✔ "기본키 + NULL" → 무조건 **개체 무결성 위반**  
✔ "외래키 + 존재하지 않는 값" → **참조 무결성 위반**  
✔ "값의 범위/형식 문제" → **도메인 무결성 위반**

---

필요하면 **무결성 제약조건 + 이상(Anomaly) + 정규화**까지 한 번에 연결해서 정리해줄게. 지금 이 부분은 실기에서 세트로 묶여서 자주 출제되는 영역이야.

① 모든 명령문을 적어도 한 번 실행되도록 조합하는 커버리지
② 각 결정문의 결과가 참/거짓을 각각 한 번 이상 갖도록 테스트하는 커버리지
③ 각 결정문 내 각 조건식의 결과가 참/거짓을 각각 한 번 이상 갖도록 테스트하는 커버리지

**Statement Condition/Decision Branch Condition Modified Condition/Decision**

### 💡 답변 (Assistant)
좋습니다. 이 문제는 **코드 커버리지 유형 4가지**를 정확히 구분할 수 있는지를 묻는 전형적인 실기 문제입니다.

## ✅ 문제 분석

각 문장을 키워드로 정리해보면:

### ①  
- **모든 명령문 실행**
→ 키워드: *명령문 실행*

### ②  
- **결정문의 결과 (참/거짓)**
→ 키워드: *결정 결과*

### ③  
- **결정문 내부의 조건식 각각 (참/거짓)**
→ 키워드: *조건식 단위*

---

## 🎯 정답

① 👉 **Statement Coverage**  
② 👉 **Branch Coverage** (Decision Coverage)  
③ 👉 **Condition Coverage**

---

## 📌 정답인 이유

### ① Statement Coverage

| 구분 | 설명 |
|------|------|
| 기준 | 모든 명령문 실행 |
| 특징 | 가장 기본적인 커버리지 |
| 포인트 | "한 번이라도 실행" |

→ 문제의 "모든 명령문 실행"과 정확히 일치

---

### ② Branch Coverage (Decision Coverage)

| 구분 | 설명 |
|------|------|
| 기준 | 각 결정문의 결과 (True/False) |
| 대상 | if, while 등의 분기 |
| 포인트 | 결과 기준 |

→ "결정문의 결과가 참/거짓" → Branch/Decision

---

### ③ Condition Coverage

| 구분 | 설명 |
|------|------|
| 기준 | 조건식 각각의 True/False |
| 대상 | 복합 조건식 (A && B 등) |
| 포인트 | 조건 단위 |

→ "각 조건식의 결과" → Condition

---

## 🔎 헷갈릴 수 있는 오답

### ❌ Modified Condition/Decision Coverage (MC/DC)

- 각 조건이 **독립적으로 결과에 영향을 주는지**까지 확인
- 항공/안전 시스템에서 사용
- 문제에서 “독립적 영향” 언급 없음 → 오답

---

### ❌ Statement Condition Coverage

- 시험에서 잘 안 쓰는 표현 (혼합형)
- 일반적으로 **Statement + Condition**은 따로 구분함

---

## 📚 추가로 공부해야 할 것 (중요)

### 커버리지 포함 관계 (시험 핵심)

```
Statement ⊂ Branch(Decision) ⊂ Condition ⊂ MC/DC
```

→ 뒤로 갈수록 **강한 테스트**

---

### 예시로 이해 (매우 중요)

```c
if (A && B)
```

| 커버리지 | 만족 조건 |
|----------|----------|
| Statement | if문 한 번 실행 |
| Branch | True / False 각각 |
| Condition | A, B 각각 True/False |
| MC/DC | A, B 각각 결과에 영향 |

---

## 🧠 실기시험 포인트 정리

✔ "명령문 실행" → Statement  
✔ "결정 결과" → Branch (Decision)  
✔ "조건식 각각" → Condition  
✔ "독립적 영향" 나오면 → MC/DC  

---

이 문제는 **화이트 박스 테스트 핵심 중 핵심**이라서  
👉 “문장 vs 분기 vs 조건 vs MC/DC” 구분은 반드시 완벽히 암기해야 합니다.

원하면 **기출에서 어떻게 변형되어 나오는지**까지 같이 정리해줄게.

- ( 4 ) : 튜플을 구별하는데 기준이 되는 키로 유일성과 최소성을 만족하는 키.

## ✅ 문제 분석

각 보기의 핵심 키워드를 정리하면:

### (1)  
- 다른 릴레이션의 기본키 사용  
→ **참조 관계**

### (2)  
- 유일성 O, 최소성 X  
→ **불필요한 속성 포함**

### (3)  
- 기본키로 선택되지 않음  
→ **후보키 중 탈락**

### (4)  
- 유일성 + 최소성 만족

4️⃣ 👉 **후보키**

## 📌 정답인 이유

### ① 외래키 (Foreign Key)

| 구분 | 설명 |
|------|------|
| 의미 | 다른 릴레이션의 기본키 참조 |
| 목적 | 테이블 간 관계 설정 |

→ "다른 릴레이션의 기본키로 이용" → 외래키

---

### ② 슈퍼키 (Super Key)

| 구분 | 설명 |
|------|------|
| 특징 | 유일성 O |
| 단점 | 최소성 X (불필요 속성 포함 가능) |

→ 예: (학번), (학번+이름) 둘 다 슈퍼키

---

### ③ 대체키 (Alternate Key)

| 구분 | 설명 |
|------|------|
| 정의 | 후보키 중 기본키 제외 나머지 |
| 특징 | 기본키 대체 가능 |

→ "기본키로 선택되지 않은 후보키"

---

### ④ 후보키 (Candidate Key)

| 구분 | 설명 |
|------|------|
| 조건 | 유일성 + 최소성 |
| 역할 | 기본키가 될 수 있는 후보 |

→ 문제의 정의 그대로 일치

---

## 🔎 헷갈릴 수 있는 오답 포인트

### ❌ 후보키 vs 기본키

- 후보키: **가능한 키들**
- 기본키: **선택된 1개**

---

### ❌ 슈퍼키 vs 후보키

| 구분 | 차이 |
|------|------|
| 슈퍼키 | 유일성만 만족 |
| 후보키 | 유일성 + 최소성 |

→ **최소성 여부가 핵심 차이**

---

## 📚 추가로 공부해야 할 것 (핵심 정리)

### 키의 포함 관계 (시험 필수)

```
슈퍼키 ⊃ 후보키 ⊃ 기본키
```

---

### 전체 키 구조 한눈에 정리

| 키 종류 | 특징 |
|--------|------|
| 슈퍼키 | 유일성만 만족 |
| 후보키 | 유일성 + 최소성 |
| 기본키 | 후보키 중 선택 |
| 대체키 | 후보키 - 기본키 |
| 외래키 | 다른 테이블 참조 |

---

## 🧠 실기시험 포인트 정리

✔ "다른 릴레이션 참조" → 외래키  
✔ "유일성 O, 최소성 X" → 슈퍼키  
✔ "기본키 탈락 후보키" → 대체키  
✔ "유일성 + 최소성" → 후보키  

---

이 파트는  
👉 **정규화 + 무결성 + 키 구조**까지 연결해서 출제됩니다.

원하면 다음 단계로  
**“이상(Anomaly) + 정규화 + 함수적 종속”까지 한 번에 정리**해줄게.

## ✅ 문제 분석

문장에서 반복되는 핵심 키워드를 뽑으면:

- **오류 검출 코드**
- **체크섬 기반 무결성 확인**
- **특정 다항식 적용**
- **나머지 계산 후 전송**
- **수신 측 동일 다항식 검증**

→ 핵심 키워드:  
👉 *다항식, 나머지, 검증*

---

## 🎯 정답  
👉 **CRC (Cyclic Redundancy Check)**

---

## 📌 정답인 이유

### CRC의 핵심 개념

| 구분 | 설명 |
|------|------|
| 방식 | 다항식 기반 나눗셈 |
| 송신 | 데이터 ÷ 생성 다항식 → **나머지(Remainder)** 전송 |
| 수신 | 동일 다항식으로 나눠 **오류 여부 확인** |
| 목적 | 전송 중 오류 검출 |

---

문제에서:

> "특정 다항식을 적용한 나머지를 함께 전송"

→ 이것이 바로 **CRC의 정의 그 자체**

---

## 🔎 헷갈릴 수 있는 오답

### ❌ Parity Check

- 1비트 추가
- 단순 오류 검출
- 다항식 사용 ❌

---

### ❌ Checksum

- 단순 합 계산
- 다항식 ❌
- CRC보다 정확도 낮음

---

### ❌ Hamming Code

- 오류 **검출 + 수정**
- 재전송 없이 복구 가능 (FEC)
- CRC는 **검출만**

---

## 📚 추가로 공부해야 할 것 (핵심 정리)

### 1️⃣ 오류 제어 방식 2가지

| 구분 | 설명 |
|------|------|
| FEC (Forward Error Correction) | 수신 측에서 직접 수정 |
| ARQ (Automatic Repeat reQuest) | 오류 시 재전송 요청 |

---

### 2️⃣ 오류 검출 vs 오류 수정

| 구분 | 대표 기법 |
|------|----------|
| 오류 검출 | Parity, Checksum, **CRC** |
| 오류 수정 | Hamming Code |

---

### 3️⃣ CRC 특징 (시험 포인트)

## 🎯 정답

---

## 📌 정답인 이유

### 공통 결합도 (Common Coupling)

| 구분 | 설명 |
|------|------|
| 특징 | 여러 모듈이 **전역 변수 공유** |
| 방식 | 외부(공통 영역) 데이터 사용 |
| 문제점 | 하나 변경 시 전체 영향 |

---

문제에서:

> "모듈 밖에 선언된 전역 변수"  
> "참조하고 갱신"

→ 여러 모듈이 **같은 전역 데이터를 공유**

👉 이것이 바로 **공통 결합도**

---

## 🔎 헷갈릴 수 있는 오답

### ❌ 내용 결합도 (Content Coupling)

- 다른 모듈의 **내부 코드 직접 접근**
- 가장 강한 결합도

→ 전역 변수는 내부 코드 접근이 아님

---

### ❌ 제어 결합도 (Control Coupling)

- 제어 정보(flag, switch 등) 전달
- 흐름 제어 목적

→ 데이터 공유가 아니라 **제어 전달**

---

### ❌ 자료 결합도 (Data Coupling)

- 파라미터로 데이터 전달
- 가장 바람직한 결합도

→ 문제는 "파라미터가 아닌 전역 변수"

---

## 📚 추가로 공부해야 할 것 (핵심 정리)

### 결합도 강도 순서 (매우 중요)

``` id="m88sk1"
내용 > 공통 > 외부 > 제어 > 스탬프 > 자료
```

👉 왼쪽일수록 **나쁨 (강함)**  
👉 오른쪽일수록 **좋음 (약함)**

---

### 결합도 유형 정리

| 결합도 | 설명 |
|--------|------|
| 내용 결합도 | 내부 코드 직접 접근 |
| 공통 결합도 | 전역 변수 공유 |
| 외부 결합도 | 외부 장치/파일 공유 |
| 제어 결합도 | 제어 정보 전달 |
| 스탬프 결합도 | 구조체 전체 전달 |
| 자료 결합도 | 필요한 데이터만 전달 |

# 📚 여기서 반드시 확장해서 공부해야 할 것 (중요)

---

## 1️⃣ Session Hijacking vs Session Fixation (핵심 비교)

| 구분 | Session Hijacking | Session Fixation |
|------|------------------|------------------|
| 시점 | 로그인 후 탈취 | 로그인 전에 세션 고정 |
| 방식 | 세션 가로채기 | 세션 ID 강제 설정 |
| 특징 | TCP/쿠키 탈취 | 사용자 속이기 |

👉 시험에서 **같이 묶어서 출제됨**

---

## 2️⃣ TCP 공격 유형 정리 (매우 중요)

### ✔ TCP 관련 공격 3대장

| 공격 | 특징 |
|------|------|
| Session Hijacking | 세션 탈취 |
| SYN Flooding | 서버 자원 고갈 |
| TCP Reset Attack | 연결 강제 종료 |

---

### ✔ 문제에서 나온 RST 패킷

👉 TCP Reset Attack 요소 포함

→ 시험 포인트:
- RST → 연결 끊기
- 이후 → Hijacking

---

## 3️⃣ 네트워크 공격 흐름 이해 (실기 핵심)

``` id="n92xk1"
1. 정상 연결 (3-way handshake)
2. 공격자가 패킷 스니핑
3. RST로 연결 종료
4. 공격자가 세션 탈취
```

👉 이 흐름 자체가 시험에 그대로 나옵니다

---

## 4️⃣ 관련 공격 같이 암기 (세트로 나옴)

| 공격 | 핵심 키워드 |
|------|-------------|
| Session Hijacking | 세션 탈취 |
| Session Fixation | 세션 고정 |
| Sniffing | 패킷 도청 |
| Spoofing | IP 위조 |
| MITM (Man-in-the-Middle) | 중간자 공격 |

## 🎯 실무 예시 (가장 대표적인 사례)

### 💡 결제 시스템 연동 (강력 추천 예시)

### 상황

우리 시스템은 아래 인터페이스를 사용한다고 가정:

```java
interface Payment {
    void pay(int amount);
}
```

---

### 문제

외부 결제 API는 이렇게 되어 있음:

```java
class KakaoPayAPI {
    void kakaoPay(int money) {
        System.out.println("카카오페이 결제: " + money);
    }
}
```

👉 인터페이스 불일치  
- 우리: `pay()`  
- 외부: `kakaoPay()`

---

## 🔧 Adapter 적용

```java
class KakaoPayAdapter implements Payment {
    private KakaoPayAPI kakao;

    public KakaoPayAdapter(KakaoPayAPI kakao) {
        this.kakao = kakao;
    }

    @Override
    public void pay(int amount) {
        kakao.kakaoPay(amount);  // 변환!
    }
}
```

---

## 🧠 사용

```java
Payment payment = new KakaoPayAdapter(new KakaoPayAPI());
payment.pay(10000);
```

``` id="adapter-flow"
Client → Payment (인터페이스) → Adapter → KakaoPayAPI
```
