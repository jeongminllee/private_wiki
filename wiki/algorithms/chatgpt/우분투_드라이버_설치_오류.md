### 💡 답변 (Assistant)
네. 그 메시지는 보통 **`apt --fix-broken install`** 또는 예전 표기인 **`apt-get -f install`** 을 뜻합니다. 여기서 “broken”은 “APT가 고장났다”는 뜻이 아니라, **패키지 의존성 관계가 현재 만족되지 않는 상태**를 말합니다. Ubuntu의 APT 문서도 `--fix-broken`을 “broken dependencies를 바로잡으려는 시도”라고 설명합니다. citeturn376132search1turn633352search4

우분투에서 NVIDIA 드라이버나 CUDA Toolkit 설치 중 이 메시지가 자주 뜨는 핵심 이유는 대체로 이겁니다.

1. **패키지 버전 조합이 서로 안 맞을 때**  
   예를 들어 드라이버는 535 계열 일부 패키지, 다른 라이브러리는 또 다른 535 마이너 버전으로 잡히면 서로 `Breaks`나 `Depends` 충돌이 납니다. NVIDIA 포럼에도 Ubuntu 저장소 패키지와 NVIDIA 제공 패키지가 충돌해서 설치가 깨진 사례가 올라와 있습니다. citeturn633352search1turn413282search0

2. **설치 방법을 섞었을 때**  
   가장 흔한 원인 중 하나입니다.  
   - Ubuntu 기본 저장소/`ubuntu-drivers`
   - NVIDIA CUDA network repo
   - `.run` 설치 파일  
   이 셋을 섞으면 같은 이름의 구성요소를 서로 다른 출처가 관리하게 되어 꼬이기 쉽습니다. NVIDIA의 CUDA 설치 가이드는 설치 전 **conflicting installation methods를 처리하라**고 명시합니다. citeturn398003search0turn398003search3

3. **커널 헤더 / DKMS / 현재 커널 버전이 안 맞을 때**  
   NVIDIA 드라이버는 커널 모듈을 빌드하거나 맞는 prebuilt 모듈을 가져와야 하는데, 현재 실행 중인 커널에 맞는 헤더가 없거나 커널 업데이트 직후 패키지 구성이 어긋나면 설치가 실패할 수 있습니다. NVIDIA 문서도 드라이버 설치 시 **현재 커널 버전에 맞는 kernel headers/development packages가 필요하다**고 설명합니다. citeturn398003search3turn398003search5

4. **이전 설치 찌꺼기나 보류(held) 패키지**  
   과거에 설치하다 만 CUDA/NVIDIA 패키지, i386 멀티아치 패키지, PPA 잔재, 미완료 dpkg 상태가 남아 있으면 새 설치가 막힙니다. Ask Ubuntu/Stack Overflow 쪽 사례들에서도 `held broken packages`, `i386`, `but it is not going to be installed` 같은 메시지가 반복됩니다. citeturn413282search5turn413282search6turn413282search10

5. **업그레이드 도중 중단되었을 때**  
   전원 차단, 설치 중 강제 종료, 배포판 업그레이드 중 끊김 때문에 `dpkg --configure -a` 와 `apt --fix-broken install` 순서가 필요해지는 경우도 Ubuntu 문서에 나옵니다. citeturn633352search4turn376132search12

## 그럼 이 오류가 원래 빈번한가?

정확히 말하면:

- **우분투 전체에서 늘 흔한 일반 오류**라고 보긴 어렵습니다.
- 하지만 **NVIDIA 드라이버 + CUDA 조합에서는 꽤 자주 보는 편**입니다.  

이건 단순히 “엔비디아가 형편없다” 수준의 얘기가 아니라, 드라이버·커널 모듈·커널 버전·저장소 출처·CUDA 버전이 동시에 맞아야 해서 **의존성 그래프가 복잡하기 때문**입니다. NVIDIA 공식 가이드도 설치 방법을 나눠 설명하고, 충돌 설치 방식과 커널 헤더를 별도로 주의사항으로 강조합니다. 동시에 Ask Ubuntu, Stack Overflow, NVIDIA 포럼에는 같은 유형의 질문이 다수 반복됩니다. 그래서 **빈번하진 않지만, 이 조합에서는 충분히 흔한 문제**라고 보는 게 맞습니다. citeturn398003search0turn398003search3turn633352search3turn633352search6turn633352search5

## `apt --fix-broken install`이 정확히 하는 일

이 명령은 대충 “문제난 패키지를 자동으로 적당히 맞춰라”에 가깝습니다.  
APT man page에 따르면, 이 옵션은 **깨진 의존성 상태를 수정하려고 시도**하며, 필요하면 일부 패키지를 설치/제거하지 않는 방식으로 APT가 해결책을 추론하게 합니다. 즉, 이 명령은 **원인 자체를 진단하는 명령**이라기보다 **꼬인 의존성 상태를 정리하는 응급 복구 명령**입니다. citeturn376132search1

그래서 이 메시지가 떴다는 건 보통 아래 중 하나라는 뜻입니다.

- “지금 설치하려는 패키지 자체가 잘못됐다”
- “이미 시스템에 남아 있는 패키지 상태가 꼬여 있다”
- “저장소가 섞여서 버전 해석이 불가능하다”
- “필수 의존 패키지를 가져올 수 없는 상태다”

## 커뮤니티에서 많이 나오는 해결 패턴 요약

스택오버플로우, Ask Ubuntu, NVIDIA 포럼 쪽을 보면 해결책은 대체로 같은 흐름으로 수렴합니다.

### 1) 먼저 패키지 상태 복구
가장 먼저 많이 시도하는 순서는 이겁니다.

```bash
sudo dpkg --configure -a
sudo apt --fix-broken install
sudo apt update
```

이 순서는 Ubuntu 문서와 커뮤니티 답변 양쪽에서 반복됩니다. citeturn633352search4turn376132search8

### 2) 설치 출처를 하나로 통일
커뮤니티에서 가장 많이 강조되는 포인트입니다.

- Ubuntu의 `ubuntu-drivers`로 갈 거면 **그 방식만 사용**
- NVIDIA CUDA repo를 쓸 거면 **그 repo 기준으로 정리**
- `.run`으로 설치했다면 apt 패키지와 혼용하지 않기

특히 Ubuntu 패키지와 NVIDIA 제공 패키지가 섞이면 충돌 사례가 실제로 보고되어 있습니다. citeturn633352search1turn413282search0

### 3) 꼬였으면 NVIDIA/CUDA 패키지 정리 후 재설치
Ask Ubuntu나 Ubuntu 커뮤니티 글들에서 자주 보이는 방법이 **기존 NVIDIA/CUDA 관련 패키지를 purge하고 다시 깔기**입니다. 예를 들어 `nvidia-*`, `cuda*`를 정리한 뒤 `ubuntu-drivers autoinstall`로 다시 맞추는 패턴이 반복됩니다. 다만 이건 현재 설치 상태를 크게 바꾸므로, 실행 전 제거 대상 목록을 꼭 확인해야 합니다. citeturn633352search3turn398003search7turn413282search4

### 4) 드라이버와 툴킷을 분리해서 생각
커뮤니티에서는 “CUDA Toolkit만 필요하면 드라이버까지 같이 설치하려 하지 말고, **드라이버는 우분투 쪽에서 안정적으로 맞춘 뒤 Toolkit만 별도로** 설치”하는 조언이 자주 보입니다. 실제 Ask Ubuntu 사례에도 로컬 설치기에서 **드라이버 설치를 제외하고 Toolkit만 설치**해서 해결한 경우가 있습니다. citeturn413282search1turn398003search5

### 5) 커널 헤더와 Secure Boot 점검
드라이버는 단순 라이브러리가 아니라 커널 모듈이 포함되므로,
- `linux-headers-$(uname -r)` 존재 여부
- Secure Boot 활성화 여부
- DKMS 빌드 실패 여부  
를 확인하라는 조언이 많습니다. Ubuntu 커뮤니티 문서도 Secure Boot 환경에서 모듈 서명 경로를 별도로 설명합니다. citeturn398003search3turn398003search5

### 6) i386 패키지 꼬임 확인
질문 사례들에서 `libnvidia-gl-xxx:i386` 같은 32비트 패키지가 같이 딸려와 충돌하는 경우가 적지 않습니다. 특히 Steam/Wine 같은 걸 쓰는 환경에서 멀티아치가 켜져 있으면 버전 맞춤이 더 복잡해질 수 있습니다. citeturn633352search1turn413282search6turn633352search11

## 실전에서 가장 안전한 해석

당장 메시지만 보고 해석하면:

> “`apt --fix-broken install`을 치라”  
= “현재 시스템 패키지 상태가 완전히 일관되지 않아서, 새 패키지 설치 전에 의존성 복구부터 하라”

입니다.

즉, **엔비디아 드라이버 설치 명령 자체가 틀렸다**기보다,  
대부분은 **이미 시스템 안에 있는 패키지 상태가 꼬인 채로 다음 설치를 시도하고 있어서 APT가 중단시키는 것**입니다. citeturn376132search1turn633352search4

## 추천하는 대응 원칙

지금 같은 상황에서는 보통 이 원칙이 가장 중요합니다.

1. **무조건 섞지 않기**  
   Ubuntu 드라이버 방식 / NVIDIA repo 방식 / `.run` 방식 중 하나만 유지.

2. **드라이버 먼저 안정화**
   `nvidia-smi`가 정상 동작하는지 먼저 확인.

3. **그 다음 CUDA Toolkit**
   ML/DL 용도라면 사실 시스템 전체 CUDA보다, 프레임워크가 제공하는 런타임으로 충분한 경우도 많음.

4. **에러 원문을 봐야 정확히 판단 가능**
   특히 아래 문자열이 중요합니다.
   - `held broken packages`
   - `but it is not going to be installed`
   - `Depends: ...`
   - `Breaks: ...`
   - `dkms`
   - `linux-modules-nvidia`
   - `:i386`

# 1️⃣ 전체 제거 (완전 초기화 단계)

## (1) CUDA + NVIDIA 패키지 전부 제거
```bash
sudo apt-get --purge remove "*cuda*" "*cublas*" "*cufft*" "*curand*" \
"*cusolver*" "*cusparse*" "*npp*" "*nvjpeg*" "nsight*" "*nvidia*"
```

👉 목적  
- CUDA Toolkit + 드라이버 + 관련 라이브러리까지 전부 제거  
- 의존성 꼬임 제거

📌 근거  
- entity["organization","NVIDIA Documentation","CUDA Installation Guide Linux"]  
  → 기존 CUDA/NVIDIA 패키지 제거 후 재설치 권장

---

## (2) 자동 설치된 의존성 정리
```bash
sudo apt-get autoremove
sudo apt-get autoclean
```

👉 목적  
- 남은 찌꺼기 패키지 제거

---

## (3) 남아있는 설정/디렉토리 제거
```bash
sudo rm -rf /usr/local/cuda*
sudo rm -rf /etc/apt/sources.list.d/cuda*
```

👉 목적  
- CUDA 경로 및 repo 흔적 제거  
- 이전 버전과 충돌 방지

📌 CUDA는 `/usr/local/cuda` 심볼릭 링크를 쓰기 때문에 이게 남아있으면 버전 꼬임 발생

---

## (4) dpkg 상태 복구 (중요)
```bash
sudo dpkg --configure -a
sudo apt --fix-broken install
```

👉 목적  
- 현재 패키지 상태를 “정상 상태”로 리셋

📌 근거  
- entity["organization","Ubuntu Documentation","package management guide"]  
  → broken dependency 복구 표준 절차

## (2) Toolkit만 설치 (중요)
```bash
sudo apt-get install cuda-toolkit
```

- `cuda` = 드라이버 + toolkit 같이 설치

- “Toolkit only install”이 충돌 회피 핵심

4. CUDA는 toolkit만 설치
