# 에이전트 사용량 계산

> **카테고리**: `Algorithms (알고리즘 & 자료구조)`  
> **원천**: ChatGPT 대화 아카이브 (`raw/notes/Chatgpt_2026-08-02-23-14-23`)  
> **작성일**: 2026-07-23

## 💬 대화 내용 및 Q&A

### ❓ 질문 (User)
에이전트를 개발하려고 하는데 사용하는 양을 예상 사용량 (RPM/TPM) 이걸로 표현이 가능한가?

### 💡 답변 (Assistant)
가능합니다. **에이전트의 API 사용량과 필요한 처리 용량을 추정할 때 RPM과 TPM은 핵심 지표**입니다. 다만 에이전트는 한 번의 사용자 요청이 여러 번의 모델 호출로 증폭되므로, 단순히 “사용자 요청 수 = API 요청 수”로 계산하면 크게 빗나갈 수 있습니다.

## 기본 개념

- **RPM, Requests Per Minute**  
  1분 동안 모델 API를 몇 번 호출하는지
- **TPM, Tokens Per Minute**  
  1분 동안 입력과 출력 토큰을 얼마나 처리하는지

일반적으로:

\[
TPM = Input\ TPM + Output\ TPM
\]

예를 들어 1분 동안 API를 30번 호출하고, 호출당 평균 입력 4,000토큰과 출력 1,000토큰을 사용한다면:

\[
RPM = 30
\]

\[
TPM = 30 \times (4,000 + 1,000) = 150,000
\]

---

## 에이전트에서는 이렇게 계산해야 합니다

사용자 요청 1건당 모델 호출 횟수를 먼저 추정해야 합니다.

예를 들어 한 번의 에이전트 실행에서:

1. 사용자 요청 분석: 1회
2. 도구 선택: 1회
3. 검색 결과 해석: 1회
4. 추가 도구 호출 판단: 1회
5. 최종 답변 생성: 1회

평균 5번의 LLM 호출이 발생한다고 가정하겠습니다.

사용자 요청이 분당 20건이면:

\[
Agent\ RPM = 20
\]

하지만 실제 모델 API RPM은:

\[
Model\ RPM = 20 \times 5 = 100
\]

즉, 에이전트 시스템에서 RPM을 말할 때는 다음 둘을 구분하는 것이 좋습니다.

- **User RPM**: 사용자가 에이전트를 호출하는 빈도
- **LLM RPM**: 내부적으로 모델 API가 호출되는 빈도

---

## 에이전트 TPM 계산식

다음과 같이 계산할 수 있습니다.

\[
TPM =
User\ RPM
\times
평균\ LLM\ 호출\ 횟수
\times
호출당\ 평균\ 토큰
\]

좀 더 정확히 쓰면:

\[
TPM =
U_{rpm}
\times
\sum_{i=1}^{N}
(InputTokens_i + OutputTokens_i)
\]

예를 들어:

- 사용자 요청: 20 RPM
- 요청당 평균 모델 호출: 5회
- 호출당 평균 입력: 3,000토큰
- 호출당 평균 출력: 700토큰

이라면:

\[
LLM\ RPM = 20 \times 5 = 100
\]

\[
TPM = 20 \times 5 \times (3,000 + 700)
\]

\[
TPM = 370,000
\]

따라서 예상 사용량은 대략:

- **User RPM:** 20
- **LLM RPM:** 100
- **TPM:** 370K

로 표현할 수 있습니다.

## 다만 RPM/TPM만으로는 부족합니다

에이전트는 호출 패턴의 변동성이 커서 다음 지표도 함께 봐야 합니다.

### 1. 평균 호출 수와 최대 호출 수

예:

- 평균 LLM 호출 수: 4회
- P95 호출 수: 9회
- 최대 호출 수: 15회

일부 요청이 반복 탐색이나 재시도를 일으키면 순간 RPM이 크게 증가할 수 있습니다.

### 2. 평균 토큰과 P95 토큰

평균값만 사용하면 긴 문서나 긴 대화 때문에 발생하는 부하를 놓칠 수 있습니다.

예:

- 평균 입력: 3K tokens
- P95 입력: 18K tokens
- 최대 입력: 80K tokens

실제 용량 설계에서는 평균보다 **P95 또는 P99 TPM**이 더 중요합니다.

### 3. 동시 요청 수

같은 RPM이라도 요청이 고르게 들어오는지, 한꺼번에 몰리는지에 따라 필요한 처리 능력이 달라집니다.

대략적으로:

\[
Concurrency \approx RPS \times Average\ Latency
\]

예를 들어:

- 60 RPM = 1 RPS
- 평균 에이전트 실행 시간 20초

이면:

\[
Concurrency \approx 1 \times 20 = 20
\]

즉 평균적으로 약 20개의 에이전트 실행이 동시에 진행될 수 있습니다.

### 4. 도구 호출량

LLM 외에 다음 사용량도 별도로 계산하는 것이 좋습니다.

- 검색 API 요청 수
- 데이터베이스 쿼리 수
- 임베딩 API 사용량
- 벡터 검색 횟수
- 코드 실행 횟수
- 외부 SaaS API 호출량
- 재시도 횟수

## 비용 추정도 가능합니다

모델 가격이 입력 토큰당 \(P_{in}\), 출력 토큰당 \(P_{out}\)일 때:

\[
Cost/min =
InputTPM \times P_{in}
+
OutputTPM \times P_{out}
\]

단, 모델 가격은 보통 백만 토큰 단위이므로:

\[
Cost/min =
\frac{InputTPM}{1,000,000} \times Price_{in}
+
\frac{OutputTPM}{1,000,000} \times Price_{out}
\]

월간 사용량은:

\[
MonthlyTokens =
TPM \times 일일사용분 \times 월사용일
\]

예를 들어 하루 8시간, 월 22일 운영한다면:

\[
MonthlyTokens = TPM \times 60 \times 8 \times 22
\]

## 결론

**RPM과 TPM으로 에이전트의 예상 사용량을 표현하는 것은 충분히 가능하고, API 모델 선정과 rate limit 협의에도 적합합니다.**

다만 정확한 설계를 위해서는 최소한 다음 구조로 보는 것이 좋습니다.

\[
사용자\ 요청량
\rightarrow
요청당\ 에이전트\ 단계
\rightarrow
요청당\ LLM\ 호출\ 수
\rightarrow
호출당\ 입력/출력\ 토큰
\rightarrow
LLM\ RPM/TPM
\]

핵심은 **사용자 RPM이 아니라 내부 호출 증폭까지 반영한 LLM RPM과 TPM을 산출하는 것**입니다. 에이전트 사용량 산정에서는 평균값과 함께 피크, P95, 최대 반복 횟수를 반드시 분리해야 합니다.

## 권장 표기

### 예상 평균 사용량

| 지표 | 예상값 |
|---|---:|
| 사용자 요청량 | 평균 2~3 User RPM |
| 사용자 피크 요청량 | 5~10 User RPM |
| 요청당 LLM 호출 | 평균 5~7회 |
| 모델 API 요청량 | 평균 15~25 RPM |

| 평균 입력 토큰 | 요청당 25K~50K |
| 평균 출력 토큰 | 요청당 3K~8K |
| 평균 TPM | 150K~300K TPM |
| 피크 TPM | 600K~900K TPM |

따라서 API 제공 업체나 인프라 담당자에게 제출할 값은 다음처럼 정리하는 것이 좋습니다.

> **요청 Rate Limit: 60 RPM / 1M TPM**

이 정도면 초기 금융 보안 분석 에이전트를 개발하고, 여러 사용자가 테스트하는 파일럿 단계에서도 지나치게 빡빡하지 않습니다.

## 산정 근거

금융 보안 분석 요청 1건이 다음과 같이 실행된다고 가정하겠습니다.

1. 요청 분류 및 분석 계획 생성
2. 코드·문서·로그 청크 분석
3. 보안 정책 및 금융 규정 RAG 검색
4. 취약점·이상 징후 판단
5. 근거 검증
6. 최종 보안 보고서 생성

평균적으로 요청당 LLM을 6번 호출하고, 각 호출의 평균 사용량을 다음처럼 잡을 수 있습니다.

- 평균 입력: 7,000 tokens
- 평균 출력: 1,000 tokens
- 호출당 총 8,000 tokens
- 요청당 LLM 호출: 6회

따라서 사용자 요청 1건당:

\[
6 \times 8,000 = 48,000\ tokens
\]

사용자 요청이 평균 3 RPM이면:

\[
LLM\ RPM = 3 \times 6 = 18\ RPM
\]

\[
TPM = 3 \times 48,000 = 144,000\ TPM
\]

재시도, 긴 문서, 복수 RAG 검색, 보고서 재생성 등을 고려하면 평균 사용량을 약 150K~300K TPM으로 보는 것이 적절합니다.

피크 시간에 사용자 요청이 10 RPM까지 올라간다면:

\[
LLM\ RPM = 10 \times 6 = 60\ RPM
\]

\[
TPM = 10 \times 48,000 = 480,000\ TPM
\]

여기에 다음 여유분을 적용해야 합니다.

- 긴 금융 규정 문서
- 대규모 소스코드 또는 로그
- 도구 호출 실패 및 재시도
- 여러 검색 결과의 재검증
- 상세 보안 보고서 생성
- 순간적인 요청 집중

그래서 피크 TPM을 **600K~900K**, 신청 또는 설계 한도를 **1M TPM**으로 잡는 것이 안전합니다.

## 배치 분석은 별도 표기

금융 보안 에이전트에서 파일, 소스코드 저장소, 감사 로그 등을 일괄 분석한다면 RPM/TPM만으로는 설명이 부족합니다. 다음 지표도 같이 적는 것이 좋습니다.

```text
배치 분석 워크로드

- 파일당 예상 사용량: 50K~300K tokens
- 저장소당 예상 사용량: 500K~5M tokens
- 시간당 분석 작업: 5~20 jobs
- 최대 동시 분석 작업: 3~5 jobs
- 최대 단일 작업 처리 시간: 별도 측정
```

특히 소스코드 저장소 전체를 분석하면 하나의 사용자 요청이 수십 번의 LLM 호출로 분할될 수 있습니다. 따라서 다음 두 트래픽을 구분해야 합니다.

- **Interactive workload:** 채팅, 취약점 질의, 규정 검색
- **Batch workload:** 저장소, 로그, 문서 전체 분석

## 개발 단계별 권장값

| 단계 | 권장 RPM | 권장 TPM |
|---|---:|---:|
| 개인 개발·기능 검증 | 20 RPM | 300K TPM |
| 초기 PoC | 60 RPM | 1M TPM |
| 사내 파일럿 | 100 RPM | 2M TPM |
| 소규모 운영 | 200~300 RPM | 5M TPM 이상 |

현재 단계에서는 **“평균 20 RPM / 300K TPM, 피크 60 RPM / 1M TPM”**으로 명시하는 것이 가장 설득력 있습니다. API 한도를 신청하는 문서라면 평균값이 아니라 **피크 기준인 60 RPM / 1M TPM**을 요청값으로 제출하는 편이 좋습니다.

### 💡 답변 (Assistant)
그 판단이 맞습니다. **초기 PoC는 기능 검증뿐 아니라 실제 사용 패턴을 계측하는 단계**이므로, 너무 작게 잡기보다 약간의 여유를 둔 한도로 시작하는 편이 좋습니다.

초기 표기는 다음 정도가 적절합니다.

### 금융 보안 특화 에이전트 초기 PoC 기준

| 항목 | 예상 사용량 |
|---|---:|
| 평균 사용자 요청량 | 2~3 User RPM |
| 피크 사용자 요청량 | 5~10 User RPM |
| 요청당 LLM 호출 | 평균 5~7회 |
| 평균 LLM API 요청량 | 15~25 RPM |
| 피크 LLM API 요청량 | 최대 60 RPM |
| 평균 토큰 사용량 | 150K~300K TPM |
| 피크 토큰 사용량 | 최대 1M TPM |
| 권장 API 한도 | **60 RPM / 1M TPM** |

문서에는 이렇게 한 줄로 요약하면 명확합니다.

> **초기 PoC 단계에서는 평균 20 RPM / 300K TPM, 피크 기준 최대 60 RPM / 1M TPM의 사용량을 예상한다.**

다만 여기서 **20 RPM은 사용자 요청 수가 아니라 내부 LLM API 호출량**이라고 명시해야 합니다. 사용자 요청 기준으로는 평균 2~3 RPM 정도입니다.

또한 PoC 단계에서는 추정치를 확정값처럼 쓰기보다 다음 문구를 붙이는 것이 좋습니다.

> 실제 사용량은 요청당 문서 크기, RAG 검색 횟수, 보안 검증 단계 수, 재시도 발생률에 따라 변동될 수 있으며, PoC 운영 로그를 기반으로 P50·P95·최대 사용량을 재산정한다.

PoC에서 반드시 수집해야 할 지표는 다음입니다.

- 요청당 LLM 호출 횟수
- 입력·출력 토큰 수
- 요청당 총 토큰
- P50·P95 응답 시간
- 도구 호출 및 재시도 횟수
- 동시 실행 수
- 요청 유형별 사용량

결국 **60 RPM / 1M TPM은 PoC의 목표 사용량이라기보다, 피크와 실험 여유를 포함한 용량 상한선**으로 이해하면 됩니다. 실제 평균 사용량은 그보다 상당히 낮을 가능성이 큽니다.
