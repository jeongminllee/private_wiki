## 1. 백트래킹의 작동 원리 및 상태 공간 트리

### 작동 원리
- **점진적 구축(Incremental Construction)**  
  해를 구성하는 각 단계(step)마다 가능한 선택지를 하나씩 붙여 나가며(→),  
- **유망성 검사(Feasibility Check)**  
  부분 해(partial solution)가 문제 조건(제약)에 어긋나는지 검사  
- **되돌아가기(Backtrack)**  
  어긋나면 그 선택을 취소하고(prev 선택) 다음 선택지로 넘어감  

### 상태 공간 트리(State Space Tree)
- **노드**: partial solution (지금까지 선택된 결정들)
- **간선**: 다음 단계에서의 선택(branch)
- **루트**: 빈 해(아직 아무 것도 선택되지 않음)
- **리프(Leaf)**: 모든 단계가 채워져 완전 해가 된 상태 또는 더 이상 전진할 수 없는 상태  
- **탐색**: 트리의 깊이 우선(DFS) 또는 너비 우선(BFS)으로 가능하지만, 주로 깊이 우선 탐색을 재귀로 구현

```
         [ ]                 ← 루트 (아직 선택 없음)
        /   \
     [A]     [B]            ← 1단계에서 선택 A 또는 B
    /  \       \
 [A1] [A2]    [B1]          ← 2단계 선택…
   ⋱      ⋱
```

### 재귀를 주로 쓰는 이유
1. **스택 자동 관리**  
   함수 호출 스택이 자연스럽게 ‘선택→검사→되돌아감’을 관리  
2. **코드 간결성**  
   분기마다 거의 동일한 로직(‘선택 → 검사 → 재귀 호출 → 되돌아오기’) 반복  
3. **직관적 구조**  
   상태 공간 트리의 깊이 우선(DFS) 순회와 1:1 대응

## 2. 백트래킹 vs 완전 탐색(Brute‑force)

| 구분         | 완전 탐색 (Brute‑force)               | 백트래킹                           |
|--------------|---------------------------------------|------------------------------------|
| 탐색 방식    | 모든 가능한 해(모든 조합·순열 등)를 생성 | 부분 해가 유망하지 않으면 가지치기 |
| 효율성       | 최악의 경우 모든 해를 확인 → 지수 시간 | 가지치기로 많은 분기 탈락 → 실전 속도 ↑ |
| 구현 복잡도  | 로직 단순(중첩 루프 or 재귀로 전체 탐색) | 유망성 검사 로직 추가 필요         |

### 백트래킹이 효율적인 이유
- **불필요한 분기 제거**  
  문제 조건을 위반하는 순간 더 깊이 들어가지 않고 가지치기  
- **근본 해 공간 감소**  
  전체 해 공간(완전 탐색) 대비 실제로 방문하는 노드 수 대폭 축소

### 유용한 문제 유형 예시
1. **n-Queens 문제**  
   격자 위 퀸 배치 시, 서로 공격하지 않도록 배치 → 퀸 개수 늘어날수록 완전 탐색 불가능  
2. **부분집합 합(Subset Sum)**  
   원소 선택 여부 2ⁿ 경우의 수 → 중간 합이 목표치 초과 시 즉시 가지치기  
3. **그래프 색칠(Graph Coloring)**  
   인접 정점 색이 같지 않도록 칠하기 → 색 지정 후 충돌 검사하여 백트랙

## 3. 시간 복잡도, 영향 요소, 가지치기의 효과

### 시간 복잡도 표현
- 보통 해 공간 크기가 **\(b\)^\(d\)** 형태로 주어짐  
  - \(b\): 각 단계별 분기(branch) 수(평균 선택지 개수)  
  - \(d\): 깊이(max 단계 수)  
- 최악: \(O(b^d)\) (완전 탐색과 동일)

### 실제 수행 시간에 영향 미치는 요소
1. **분기 수 \(b\)**  
   - 문제 정의에 따라 달라짐(예: n-Queens에서 한 행에 놓을 수 있는 열 수)
2. **유망성 검사 비용**  
   - 매 단계마다 검사 로직이 복잡하면 오버헤드 증가
3. **가지치기 강도**  
   - **얼마나 일찍** 비유망 분기를 걸러내는가에 따라 실행 노드 수가 크게 줄어듦

### 가지치기(pruning)의 효과
- **의미**: 상태 공간 트리에서 더 이상 해를 확장할 필요가 없는 부분 트리를 통째로 잘라내기
- **효율 개선**:  
  - 불필요한 하위 트리 전체를 무시 → 탐색 노드 수, 재귀 호출 횟수 급감  
  - 실제로는 \(b^d\) 중 일부분만 방문

#### 예: 부분집합 합 문제
> **문제**: 크기 \(n\)의 집합 \(S=\{s_1,…,s_n\}\)에서 합이 \(T\)가 되는 부분집합 찾기  

1. **완전 탐색**: \(2^n\)개의 부분집합 모두 검사  
2. **백트래킹 + 가지치기**  
   - 재귀 탐색 중 부분합 \(current\_sum\) 유지  
   - **Prune**: \(current\_sum > T\)인 순간 더 이상 진행 X  
   - 큰 수가 앞에 위치하면 더 빨리 자르기 가능  

```pseudo
function dfs(i, current_sum):
    if current_sum == T:
        record solution
        return
    if current_sum > T or i > n:
        return                // 가지치기
    // s_i를 포함하는 경우
    dfs(i+1, current_sum + s_i)
    // s_i를 포함하지 않는 경우
    dfs(i+1, current_sum)
```

- **효과**: 많은 부분집합(특히 중간 합이 이미 초과된 것)에서 하위 호출을 억제 → 실제 호출 횟수 크게 감소

---

### 정리
1. 백트래킹은 **재귀** 기반 DFS로 상태 공간 트리를 탐색하면서 부분 해의 유망성 검사를 통해 되돌아가며 해를 구성  
2. 완전 탐색과 달리 **비유망 분기**를 조기에 제거하여 탐색 비용을 절감  
3. 시간 복잡도는 최악 \(O(b^d)\)이나, **가지치기**로 실제 수행 시간은 훨씬 짧아질 수 있음  

이러한 특성 덕분에 백트래킹은 n-Queens, 그래프 색칠, 부분집합 합, 해밀턴 경로 등의 조합 폭발(combinatorial explosion) 문제를 푸는 데 특히 유용합니다.

### 💡 답변 (Assistant)
백트래킹은 “가능한 해를 하나씩 만들어 가다가, 더 이상 해가 될 수 없다고 판단되면 되돌아가 다음 후보를 시도”하는 기법으로, 다음과 같은 단계로 동작합니다.

---

## 1. 부분 해의 점진적 구성 (Incremental Construction)

1. **초기 상태**  
   - 아직 아무것도 선택되지 않은 빈 해(Partial Solution)에서 시작  
2. **선택(Branching)**  
   - 현재 단계에서 “가능한 후보들(candidate choices)”을 나열  
   - 예: n-Queens라면 “현재 행에 놓을 수 있는 모든 열 위치”  
3. **추가 및 검사**  
   - 한 후보를 해에 추가한다(탐색 트리에서 아래로 한 칸 이동)  
   - 이 순간 **유망성 검사(feasibility check)** 를 통해 “지금까지의 선택이 제약을 위반하는가?”를 판단  
4. **되돌아가기(Backtrack)**  
   - 만약 제약 위반이면, 그 후보를 제거(undo)하고 다른 후보로 넘어감  
   - 위반이 없다면, 다음 단계(더 깊은 레벨)로 재귀 호출  

이 과정을 반복해 “완전 해(complete solution)”에 도달하면 답으로 저장하거나 출력하고, 다시 되돌아가 다른 해를 탐색합니다.

---

## 2. 상태 공간 트리(State Space Tree)

- **노드(Node)**  
  - 현재까지 선택된 partial solution  
- **간선(Edge)**  
  - 후보 하나를 택해 부분 해에 추가하는 행위  
- **루트(Root)**  
  - 아직 아무것도 선택되지 않은 상태  
- **리프(Leaf)**  
  - 해의 길이가 목표 깊이(문제 크기)에 도달했거나, 더 이상 전진할 수 없어 탐색 종료된 상태  

```
          Level 0 (루트: [])
         /         \
    Level 1: [A]   [B]
      /    \        \
Level 2: [A,X] [A,Y] [B,X]
   … 각 노드에서 다시 분기 …
```

DFS 방식으로 이 트리를 순회하며, 제약 위반 노드를 만나는 즉시 그 분기(subtree)를 “가지치기(prune)” 합니다.

---

## 3. 재귀(DFS) 기반 구현

```python
def backtrack(level, partial):
    # 1) 종료 조건: 완전 해에 도달했을 때
    if level == MAX_LEVEL:
        process_solution(partial)
        return

    # 2) 후보군 생성
    for candidate in generate_candidates(level, partial):
        # 3) 유망성 검사
        if is_promising(candidate, partial):
            # 4) 선택
            partial.append(candidate)
            # 5) 재귀 호출 (다음 레벨로 한 걸음)
            backtrack(level + 1, partial)
            # 6) 되돌아오기: 선택 취소
            partial.pop()
```

- **level**: 현재 탐색 깊이 (혹은 단계 번호)  
- **partial**: 지금까지 선택된 값들의 리스트  
- **generate_candidates**: 현재 단계에서 고려할 모든 가능한 선택지  
- **is_promising**: 부분 해가 여전히 유망한지(제약을 만족하는지) 검사  
- `partial.append()` 후 `backtrack()` → return 시점에 자동으로 “가장 최근에 선택한” 상태로 돌아가 pop()

### 왜 재귀인가?
- **함수 호출 스택**이 탐색 트리의 경로를 그대로 관리  
- “선택→재귀 호출→되돌아오기” 구조가 직관적으로 코드에 반영  
- 별도의 스택 자료구조를 명시적으로 만들 필요 없이, 언어가 제공하는 콜 스택 활용

## 4. 예시: 부분집합 합 문제

> **문제**: 집합 \(\{s_1, s_2, \dots, s_n\}\)에서 합이 \(T\)가 되는 부분집합 찾기

```python
def subset_sum(i, current_sum, partial):
    # 1) 목표 합 달성
    if current_sum == T:
        print("해 찾음:", partial)
        return
    # 2) 인덱스 초과 혹은 초과 합일 때 가지치기
    if i == n or current_sum > T:
        return

    # 3) s_i 선택
    partial.append(s[i])
    subset_sum(i + 1, current_sum + s[i], partial)
    partial.pop()

    # 4) s_i 비선택
    subset_sum(i + 1, current_sum, partial)
```

- `i`: 현재 검사 중인 원소 인덱스  
- `current_sum`: 지금까지 부분집합의 합  
- **Pruning**: `current_sum > T`인 순간, 더 깊이 들어갈 필요 없이 탐색 중단  

이처럼 백트래킹은 “가능성 없는 경우를 빨리 자르고” 나머지 유망한 경로만 깊이 우선으로 탐색하므로, 완전 탐색에 비해 훨씬 효율적으로 조합·순열·부분집합·그래프 색칠 등의 문제를 해결할 수 있습니다.

### 💡 답변 (Assistant)
네, 본질적으로 맞는 요약입니다. 다만 좀 더 엄밀히 짚어 보면 다음과 같은 차이가 있습니다:

1. **탐색 대상**  
   - DFS는 일반적으로 그래프나 트리의 “노드”를 단순히 방문하는 알고리즘인 반면,  
   - 백트래킹은 문제의 **해를 구성하는 단계별 결정(부분 해)** 을 노드로 간주하는 “암시적 상태 공간 트리(State Space Tree)”를 탐색합니다.

2. **후보 생성(Candidate Generation)**  
   - DFS는 인접 리스트나 간선 정보에서 다음 방문 노드를 그대로 가져오지만,  
   - 백트래킹은 `generate_candidates()` 같은 함수를 통해 “현재 partial solution에 붙일 수 있는 모든 후보”를 **매 단계마다 동적으로 생성**합니다.

3. **유망성 검사(Promising Function)**  
   - 요약하신 대로, **`is_promising()`** 으로 “이 후보를 선택해도 여전히 해가 될 가능성이 있는가?”를 검사해 **불필요한 분기(subtree)를 가지치기(prune)** 합니다.  
   - 이 검사 덕분에 이론상 완전 탐색(\(O(b^d)\))과 같아 보이는 탐색 공간도 실제로는 훨씬 줄어듭니다.

4. **백트래킹의 핵심 동작 흐름**  
   ```text
   1) 후보 생성 → 2) 유망성 검사 → 3) 선택(재귀 진입) → 4) 되돌아오기(undo)
   ```  
   이 흐름이 DFS의 “방문 → 재귀 → 돌아오기” 구조와 동일해 보이지만, 백트래킹은 각 단계마다 **문제 제약을 반영한 검사**와 **partial solution 관리**가 추가된 형태라고 보면 됩니다.

## 1. 백트래킹에 재귀를 주로 쓰는 이유

1. **함수 호출 스택의 활용**  
   - 백트래킹은 “선택 → 다음 단계 재귀 호출 → 되돌아오기”의 흐름을 반복합니다.  
   - 이때 언어가 제공하는 **콜 스택(call stack)** 이 마치 상태 공간 트리를 따라 내려갔다 올라오면서(`push`/`pop`) 자동으로 경로를 기록하고 복원해 주기 때문에, 별도의 자료구조 관리 없이도 간단히 구현할 수 있습니다.

2. **코드의 간결성·직관성**  
   - 재귀를 쓰면 “깊이 우선 탐색(DFS)”와 백트래킹의 논리가 1:1로 대응되어,  
     ```python
     partial.append(choice)
     backtrack(level+1, partial)
     partial.pop()
     ```
     와 같은 매우 직관적인 형태로 작성할 수 있습니다.  
   - 반대로 반복문과 스택을 직접 다루면, 이 과정을 하나하나 수작업으로 구현해야 해서 코드가 훨씬 장황해집니다.

3. **부분 해 관리의 용이성**  
   - `partial`(혹은 `path`) 리스트에 대한 추가·삭제가 재귀 호출 시점에 맞춰 자연스럽게 이뤄집니다.  
   - 재귀를 빠져나올 때마다 이전 상태로 **자동 복원**되므로, “되돌아가기(backtrack)” 코드를 명시적으로 여러 군데에 쓰지 않아도 됩니다.

---

## 2. 비(非)재귀적 구현 방법

재귀 대신 **명시적 스택(explicit stack)** 을 이용해 백트래킹을 구현할 수도 있습니다. 핵심 아이디어는 “콜 스택이 하던 일을 내가 직접 구현”하는 것이죠.

### (1) 스택을 사용한 DFS 형태

```python
def backtrack_iterative():
    # 스택 원소: (level, partial, next_candidate_index)
    stack = [(0, [], 0)]

    while stack:
        level, partial, idx = stack.pop()

        # 완료된 해라면 처리
        if level == MAX_LEVEL:
            process_solution(partial)
            continue

        # 현재 단계의 후보 리스트
        candidates = generate_candidates(level, partial)

        # 아직 처리 안 한 후보가 남아 있으면
        if idx < len(candidates):
            # 1) “다음 후보”를 다시 스택에 넣어두고
            stack.append((level, partial.copy(), idx + 1))
            # 2) 이번 후보로 내려간 상태를 스택에 추가
            choice = candidates[idx]
            if is_promising(choice, partial):
                new_partial = partial.copy()
                new_partial.append(choice)
                stack.append((level + 1, new_partial, 0))
        # idx == len(candidates) 이면 이 레벨의 모든 후보를 다 시도해 봤으므로
        # 그냥 continue → 자동으로 되돌아간 것과 동일
```

- **구조**  
  - `(level, partial, idx)`를 스택에 담고, `while`문으로 반복  
  - 재귀 때처럼 “append → 재귀 → pop” 흐름을, “스택에 상태를 push → while 루프 내에서 pop”으로 흉내 냈습니다.

- **장단점**  
  - **장점**: 재귀 호출에 따른 스택 오버플로우 걱정이 줄고, 호출 깊이를 더 세밀히 제어 가능  
  - **단점**: `partial.copy()` 등으로 상태 복사가 잦아지고, 코드가 훨씬 길어짐

### (2) 비트마스크(bitmask)나 순열·조합 생성 기법

- n-Queens, 부분집합 합 등에서는 **비트마스크를 이용해 상태를 숫자 하나로 압축**하고,  
- 다음 후보를 “다음 비트 위치”를 기준으로 순회함으로써, 스택도 최소화하거나 아예 없이 “for mask in range(1<<n):” 같은 루프만으로 완전 탐색을 하면서, 내부에서 유망성 검사(pruning)를 적용하는 기법도 있습니다.

```python
for mask in range(1 << n):
    if promising_bitmask(mask):
        process_solution(mask)
```

- 이 방식은 전형적인 백트래킹보다는 “비트마스크 완전 탐색 + 빠른 검증” 조합에 가깝지만, 비슷한 효과(가지치기)로 사용할 수 있습니다.

---

## 3. 정리

- **재귀**를 쓰면  
  - 콜 스택이 “경로 저장·복원”을 자동으로 해 주고,  
  - 코드가 짧고 읽기 쉬워서 백트래킹의 핵심 로직에 집중할 수 있습니다.

- **비재귀(반복문 + 스택)** 방식도 가능하지만  
  - 상태 복사·관리 코드가 늘어나고,  
  - 구현 복잡도가 올라가므로  
  - 특별히 “재귀 깊이 제한” 문제를 피하거나 “더 세밀한 스택 관리”가 필요할 때 주로 선택합니다.

백트래킹 알고리즘의 시간 복잡도는 기본적으로 문제의 해 공간 크기와 각 단계에서의 가지치기 정도에 의해 결정됩니다. 아래에서 일반적인 표현법과 함께, 가지치기(pruning)가 실제 수행 시간에 미치는 영향을 자세히 살펴보겠습니다.

---

## 1. 기본적인 복잡도 표현

백트래킹이 탐색하는 상태 공간 트리(State Space Tree)의 크기를 \(b^d\)라고 가정하면,

- \(b\): 각 레벨(level)에서 평균적으로 생성되는 **분기(branch)** 수  
- \(d\): 탐색의 **깊이(depth)** 또는 단계 수  

이때, 백트래킹의 **최악 시간 복잡도**는  
\[
O\bigl(b^d\bigr)
\]
로 표현됩니다.  
이는 “완전 탐색(Brute‑force)”과 동일한 형태이지만, 실제로는 **가지치기**로 많이 줄어들게 됩니다.

---

## 2. 분기 수 \(b\)와 깊이 \(d\)의 의미

1. **분기 수 \(b\)**  
   - 예: n-Queens 문제에서 한 행(row)에 놓을 수 있는 **유망한** 열 위치 개수  
   - 예: 부분집합 합 문제에서 아직 고려하지 않은 원소 각각을 “선택/비선택” 두 가지로 분기 → 최대 2

2. **깊이 \(d\)**  
   - 문제 크기와 동일한 경우가 많음  
     - n-Queens: \(d = n\) (퀸을 \(n\)개 모두 배치해야 하므로)  
     - 부분집합: \(d = n\) (각 원소마다 선택 여부 결정)

---

## 3. 가지치기(pruning)에 따른 실제 수행 시간

### 3.1. 유망성 검사 비용  
각 노드(부분 해)에서 **is_promising()** 같은 함수를 호출해 제약 위반 여부를 검사하는데, 이 비용이 복잡도에 영향을 줍니다.  
- 제약 검사 비용이 \(O(p)\)라면, 전체 시간 복잡도는 \(O(p \times \text{방문 노드 수})\)가 됩니다.

### 3.2. 효과적인 분기 수 \(b'\)  
- 가지치기를 통해 “실제로” 탐색되는 분기 수는 \(b\)보다 작아집니다.  
- 보통 \(b' < b\)라 가정하면,  
  \[
    \text{실제 복잡도} \;=\; O\bigl({b'}^d\bigr)
  \]  
- 문제에 따라 \(b'\)가 크게 줄어들면, 지수 복잡도가 사실상 훨씬 낮아지는 효과가 있습니다.

---

## 4. 예시로 보는 복잡도 변화

### 4.1. n‑Queens 문제

- **파라미터**: 퀸 수 \(n\)  
- **분기 수**: 처음에 \(n\), 그다음에는 “이미 놓인 퀸과 충돌하지 않는 열 개수”로 점점 줄어듦  
- **깊이**: \(d = n\)  
- **최악 복잡도**:  
  \[
    O(n^n)
  \]  
  (실제로는 가지치기로 \(n!\) 정도로 줄어들기도 함)

### 4.2. 부분집합 합(Subset Sum)

- **파라미터**: 집합 원소 수 \(n\), 목표합 \(T\)  
- **분기 수**: 각 원소마다 선택/비선택 → \(b = 2\)  
- **깊이**: \(d = n\)  
- **최악 복잡도**(가지치기 없이):  
  \[
    O(2^n)
  \]  
- **Pruning**: 중간 합이 \(T\)를 초과하면 더 이상 내려가지 않음 → 평균적으로 훨씬 적은 노드 방문

---

## 5. 평균·최선 시간 복잡도

- **최선(best‑case)**: 초기에 강력한 가지치기가 적용되어 \(O(d)\) 또는 \(O(d \times p)\) 정도로 끝날 수도 있습니다.  
- **평균(average‑case)**: 분포에 따라 다르지만, 유망성 검사를 통해 방문 노드 수가 크게 줄어들어 \(O({b'}^d)\) 형태로 수렴합니다.

---

## 6. 요약

1. **최악 복잡도**: \(O(b^d)\)  
2. **실제 복잡도**:  
   - 제약 검사 비용 \(p\)를 고려하면 \(O\bigl(p \times \text{방문 노드 수}\bigr)\)  
   - 가지치기로 인한 효과적인 분기 수 \(b' \ll b\) → \(O(p \times {b'}^d)\)  
3. **영향 요소**:  
   - 분기 수 \(b\)  
   - 깊이 \(d\)  
   - 유망성 검사 비용 \(p\)  
   - 얼마나 일찍·강력하게 가지치기를 적용하느냐

따라서, 백트래킹의 시간 복잡도 분석에서는 “이론적 최악”과 “실제 성능”을 구분하고, **가지치기의 강도**가 성능을 결정짓는 핵심 요소임을 항상 염두에 두어야 합니다.

## ✅ 1. **가지치기의 효과성 (Pruning Effectiveness)**

> **가장 중요한 요소입니다.**

- 백트래킹은 상태 공간 트리에서 모든 노드를 탐색하지 않고, **유망하지 않은 가지를 조기에 잘라내는 것**이 핵심입니다.
- **얼마나 빨리** 그리고 **얼마나 많이** 잘라내느냐에 따라 탐색 노드 수가 급격히 줄어들 수 있습니다.

예시:  
- n-Queens 문제에서 열·대각선 충돌 여부를 빨리 검사해서 유망하지 않으면 더 깊이 안 내려감  
- Subset Sum 문제에서 현재 합이 목표를 초과하면 더 이상 진행하지 않음

💡 가지치기를 잘하면 `O(b^d)` → `O(k)` (k는 실제 유망 노드 수)로 수행 시간이 **극적으로 감소**함.

---

## ✅ 2. **문제 크기 (문제의 입력 크기 또는 탐색 깊이)**

- **깊이 \(d\)**: 상태 공간 트리의 깊이 = 보통 입력 데이터의 크기 (`n`)와 관련  
- 깊이가 깊어질수록 이론적 분기 수 \(b^d\)는 기하급수적으로 증가  
- 입력 크기가 조금만 커져도 수행 시간은 폭발적으로 늘어날 수 있음

예시:  
- n이 10 → 최대 탐색 10^10  
- n이 15 → 최대 탐색 15^15

---

## ✅ 3. **분기 수 (각 단계의 후보 개수)**

- 각 단계에서 시도해볼 수 있는 **후보의 수** (branching factor)가 크면, 전체 탐색 공간이 커짐  
- 유효한 후보 수를 제한할 수 있는 조건이 많을수록 성능이 좋아짐

예시:  
- 순열 만들기 → 후보가 남은 원소의 수 만큼 (n, n-1, ..., 1)  
- 조합 만들기 → 선택된 개수와 조건에 따라 분기 수가 확 줄어듦

---

## ✅ 4. **유망성 판단 함수의 시간 복잡도**

- `is_promising()` 함수가 빠르면 빠를수록 전체 탐색 속도에 긍정적인 영향  
- 이 함수가 복잡하거나 무거우면 매 노드마다 큰 비용이 추가됨

예시:  
- 단순 배열 검색 vs 고급 조건 체크 (예: 수식 계산, 정렬 필요 등)

---

## ✅ 5. **문제의 특성: 해가 얼마나 자주 나오는가**

- 해가 자주 나오는 문제일수록 “해를 찾고 종료”할 수 있어 탐색량이 줄어듦 (특히 최초 해만 찾는 경우)  
- 반면 해가 적거나 없으면 끝까지 탐색해야 하므로 느려짐

---

## ✅ 6. **데이터 구조 최적화**

- 충돌 검사나 후보 생성에 적절한 자료구조(예: 비트마스크, HashSet 등)를 쓰면 많은 시간 절약 가능

예시:  
- n-Queens에서 열/대각선 충돌 여부를 HashSet 또는 비트로 관리하면 검사 시간이 O(1)

## ✅ 요약: 실제 시간에 가장 큰 영향을 주는 3가지 핵심

| 순위 | 요소 | 설명 |
|------|------|------|
| 🥇 1 | **가지치기의 강도** | 유망하지 않은 경로를 얼마나 빨리 잘라내는지 |
| 🥈 2 | **입력 크기(깊이)** | 상태 트리의 깊이에 따라 지수적으로 증가 |
| 🥉 3 | **분기 수** | 각 노드에서 후보 수가 많을수록 느려짐 |

필요하다면 각 요소가 어떻게 코드로 구현되고, 실제로 얼마나 성능에 영향을 미치는지도 예제를 통해 보여줄 수 있어요!
