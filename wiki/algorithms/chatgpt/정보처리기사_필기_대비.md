   - 반드시 정리해야 할 이론 키워드
   - 기출에서 어떻게 변형되어 나오는지

## 문제
다음 중 **자료결합도(Data Coupling)** 에 대한 설명과 **가장 거리가 먼 것**은?

### 보기
1. call by value 의 방식으로 함수를 호출  
2. 모듈 간의 인터페이스로 전달되는 인수와 전달받는 매개변수를 통해서만 상호작용이 일어나는 경우  
3. 두 모듈이 동일한 자료구조를 부분적으로 공유하는 경우  
4. 가장 낮은 결합도를 가지며 모듈의 품질을 향상  

---

## 정답  
👉 **3번**

---

## 1️⃣ 문제 해설 (출제 의도 & 접근 전략)

이 문제는 **모듈 간 결합도(Coupling)** 중  
👉 **자료결합도(Data Coupling)** 와  
👉 **스탬프 결합도(Stamp Coupling)** 를 **구분할 수 있는지**를 묻는 문제입니다.

시험에서는 다음처럼 출제됩니다:

- “가장 낮은 결합도는?”
- “자료결합도에 해당하지 않는 것은?”
- “구조체를 넘기는 경우는 어떤 결합도인가?”

👉 **‘자료만 넘긴다’ vs ‘자료구조를 넘긴다’**  
이 차이를 정확히 알아야 합니다.

---

## 2️⃣ 정답인 이유 (3번)

### ❌ 3번:  
> 두 모듈이 동일한 자료구조를 부분적으로 공유하는 경우

이 설명은 **자료결합도(Data Coupling)** 가 아니라  
👉 **스탬프 결합도(Stamp Coupling)** 에 해당합니다.

### 핵심 이유
- 자료결합도:  
  - **필요한 데이터만** 매개변수로 전달
- 스탬프 결합도:  
  - **구조체, 레코드, 배열 등 자료구조 전체를 전달**
  - 그 중 일부만 사용하는 경우

📌 “자료구조를 공유 / 부분적으로 사용”  
→ **스탬프 결합도 키워드**입니다.

---

## 3️⃣ 나머지 선지 분석 (왜 정답이 아닌가)

### 1번. call by value 의 방식으로 함수를 호출  
✔ **자료결합도에 해당**

- 값에 의한 호출(call by value)
- 필요한 데이터만 전달
- 가장 이상적인 결합 형태

👉 시험에서는  
**“call by value = 자료결합도”**  
거의 공식처럼 나옵니다.

---

### 2번. 매개변수로만 상호작용  
✔ **자료결합도의 정의 그 자체**

- 전역변수 사용 ❌  
- 공통 영역 접근 ❌  
- 오직 매개변수만 사용 ⭕  

👉 **교과서 정의 그대로**라서 자주 정답 보기에 나옵니다.

---

### 4번. 가장 낮은 결합도  
✔ 맞는 설명

결합도 낮은 순서(중요 암기):

> **자료결합도 → 스탬프 → 제어 → 외부 → 공통 → 내용결합도**

👉 **자료결합도 = 가장 낮음 = 가장 바람직**

---

## 4️⃣ 틀렸다면 무엇을 더 공부해야 하나?

이 문제를 틀렸다면 아래 개념이 정리되지 않은 상태입니다.

### 반드시 정리할 것 (출제 빈도 매우 높음)

#### 📌 결합도 종류별 핵심 키워드

| 결합도 | 핵심 키워드 |
|------|------------|
| 자료결합도 | 필요한 데이터만, 매개변수, call by value |
| 스탬프 결합도 | 구조체, 레코드, 배열 전달 |
| 제어결합도 | 제어 플래그 |
| 공통결합도 | 전역변수, 공용 메모리 |
| 내용결합도 | 다른 모듈 내부 직접 참조 |

👉 시험에서는 **자료결합도 vs 스탬프 결합도**를  
**가장 많이 헷갈리게 냅니다.**

---

## 5️⃣ 시험장에서 바로 써먹는 요령

- **“부분적으로 공유”**, **“자료구조”**  
  → 무조건 **스탬프 결합도**
- **“매개변수만”**, **“값 전달”**  
  → 무조건 **자료결합도**
- “가장 낮은 결합도”  
  → 고민 없이 **자료결합도**

---

## 문제

## 정답  
👉 **1번**

---

## 1️⃣ 문제 해설 (출제 의도 & 접근 전략)

이 문제의 출제 의도는 단순 암기가 아닙니다.  
👉 **각 패턴 유형의 ‘핵심 관점’** 을 구분할 수 있는지를 봅니다.

### 디자인 패턴 3대 분류 (무조건 암기)

| 분류 | 핵심 관점 |
|---|---|
| 생성 패턴 | 객체 생성 방법 |
| 구조 패턴 | 객체 **구성 / 구조화** |
| 행위 패턴 | 객체 **상호작용 / 책임 분배** |

👉 문제에서 **“상호작용”** 이 나오면 구조패턴이 아닐 가능성이 큽니다.

---

## 2️⃣ 정답인 이유 (1번)

### ❌ 1번  
> 반복적으로 사용하는 객체들의 **상호작용**을 패턴화

이 설명은 **행위 패턴(Behavioral Pattern)** 의 개념입니다.

### 행위 패턴의 핵심
- 객체 간 **책임 분배**
- 객체 간 **상호작용**
- 알고리즘과 통신 구조 정의

📌 대표 예시  
- Observer  
- Strategy  
- Command  
- Iterator  

👉 따라서 1번은 **구조패턴과 가장 거리가 멈** → 정답

---

## 3️⃣ 나머지 선지 분석 (왜 구조패턴에 해당하는가)

### 2번  
> 객체들의 협력에 의해 어떤 역할을 수행할 때 객체를 조직화시키는 방식

✔ 구조패턴 설명에 해당

- 여러 객체를 **조합**하여 기능 수행
- 객체 간 **관계 구성**이 핵심

📌 Adapter, Bridge, Composite 등의 공통 개념

---

### 3번  
> 객체에 접근할 수 있는 인터페이스와 새로운 기능 제공

✔ 구조패턴 (특히 **Proxy, Decorator**)

- 기존 객체 수정 없이 기능 확장
- 접근 제어 + 인터페이스 제공

👉 **Decorator / Proxy 단골 키워드**

---

### 4번  
> 여러 객체를 모아 구조화시키는 패턴

✔ 구조패턴의 가장 교과서적인 정의

- 객체 간 관계를 구조적으로 조직
- 클래스 또는 객체의 구성 방식 정의

---

## 4️⃣ 틀렸다면 무엇을 추가로 공부해야 하나?

이 문제를 틀렸다면 **디자인 패턴 분류 기준이 흐릿한 상태**입니다.

### 반드시 정리할 것 (출제 빈도 매우 높음)

#### 📌 패턴 유형별 핵심 단어 매칭

| 키워드 | 패턴 유형 |
|---|---|
| 생성, 인스턴스화 | 생성 패턴 |
| 구조, 구성, 조합, 래핑 | 구조 패턴 |
| 상호작용, 책임, 행위 | 행위 패턴 |

👉 시험에서는 **용어 하나로 분류를 물어봅니다.**

---

## 5️⃣ 시험장에서 바로 쓰는 판별 요령

- **“상호작용” “책임 분배”**  
  → 행위 패턴
- **“구조화” “조합” “인터페이스 제공”**  
  → 구조 패턴
- **“객체 생성” “인스턴스화”**  
  → 생성 패턴

---

현행 시스템 중 아래에서 설명한 것은?

## 정답  
👉 **2. 시스템 인터페이스 파악**

---

## 1️⃣ 문제 해설 (출제 의도 & 풀이 전략)

이 문제는 **현행 시스템 파악 항목 4가지** 중  
👉 **각 항목의 역할을 정확히 구분하는지**를 묻는 문제입니다.

### 현행 시스템 파악 4대 요소 (무조건 암기)

| 구분 | 파악 대상 |
|---|---|
| 소프트웨어 구성 파악 | 응용 SW, DB, 미들웨어 |
| 하드웨어 구성 파악 | 서버, 네트워크 장비 |
| **시스템 인터페이스 파악** | **데이터 교환** |
| 개발팀 구성 파악 | 인력, 조직 |

👉 문제에서 **“데이터 / 전송 / 프로토콜”** 이 나오면  
**무조건 인터페이스**를 떠올려야 합니다.

---

## 2️⃣ 정답인 이유 (2번)

### ✔ 2번. 시스템 인터페이스 파악

시스템 인터페이스 파악이란:

- 시스템 간 **데이터 송수신 구조** 분석
- 파악 대상:
  - 데이터 종류
  - 데이터 형식
  - 통신 프로토콜
  - 전송 주기
  - 연계 방식(API, Batch 등)

- 입력(Input) / 출력(Output) 개념 혼동

  - 화면, 스피커, 알림 등

👉 “조작 = 출력”으로 설명한 것이 결정적인 오류  
👉 **입·출력 개념이 뒤바뀐 전형적인 함정 보기**

- **“순차 / 선택 / 반복”**  
  → 구조적 **프로그래밍**
- **“분석 / 설계 / 모듈화 / 데이터 중심”**  
  → 구조적 **방법론**

  👉 구현 단계 문장을 먼저 제거

## 문제
UML의 구성 요소가 **아닌 것**은?

## 정답  
👉 **4. 보안**

---

## 1️⃣ 문제 해설 (출제 의도 & 풀이 전략)

이 문제는 UML을 **“무엇으로 구성되어 있는가”**라는 관점에서 묻습니다.  
즉, UML의 **3대 구성 요소**를 정확히 알고 있으면 **바로 푸는 문제**입니다.

### UML 구성 요소 3가지 (무조건 암기)

> **사물(Things) + 관계(Relationships) + 다이어그램(Diagrams)**

👉 보기에서 이 3가지에 **해당하지 않는 개념**을 찾는 것이 핵심입니다.

---

## 2️⃣ 정답인 이유 (4번)

### ❌ 4번. 보안

- **보안(Security)** 은:
  - 시스템의 **비기능 요구사항**
  - 품질 속성(Quality Attribute)
- UML의 구성 요소가 아님

👉 UML은 **모델링 언어**이지  
👉 보안과 같은 품질 특성을 **구성 요소로 포함하지 않습니다.**

---

## 3️⃣ 나머지 선지 분석 (왜 UML 구성 요소인가)

### 1번. 다이어그램 ✔
- UML은 **다이어그램 중심의 모델링 언어**
- 예:
  - 클래스 다이어그램
  - 유스케이스 다이어그램
  - 시퀀스 다이어그램 등

👉 UML 구성 요소 중 하나

---

### 2번. 사물 ✔
UML에서 사물(Things)은 모델의 기본 구성 단위

- 구조적 사물 (클래스, 인터페이스)
- 행위적 사물 (상호작용)
- 그룹 사물 (패키지)
- 주해 사물 (노트)

👉 UML의 핵심 구성 요소

---

### 3번. 관계 ✔
사물과 사물 간의 연결 관계

- 연관
- 의존
- 일반화
- 실체화

👉 UML 모델의 의미를 완성하는 요소

---

## 4️⃣ 틀렸다면 무엇을 추가로 공부해야 하나?

이 문제를 틀렸다면 **UML 구성 요소를 단순 암기로 정리하지 않은 상태**입니다.

### 반드시 정리할 것 (기출 반복)

#### 📌 UML 구성 요소 공식 정리

| 구분 | 내용 |
|---|---|
| 사물 | 모델의 대상 |
| 관계 | 사물 간 연결 |
| 다이어그램 | 표현 도구 |

👉 시험에서는  
- “UML의 구성 요소는?”  
- “다음 중 UML 구성 요소가 아닌 것은?”  
형태로 반복 출제됩니다.

---

## 5️⃣ 시험장에서 바로 쓰는 판별 요령

- **추상적인 품질 속성**  
  (보안, 성능, 신뢰성 등)  
  → UML 구성 요소 ❌
- **모델링 단위 / 표현 요소**  
  → UML 구성 요소 ⭕

이 문제는 **정보처리기사 필기 – 애자일 방법론(XP: eXtreme Programming)** 에서 **XP의 핵심 가치(Value)를 정확히 암기하고 있는지**를 묻는 **빈출 개념 문제**입니다.

## 문제  
XP의 가치(Value)에 **해당하지 않는 것**은?

---

## 정답  
👉 **2. 정형 분석**

---

## 1️⃣ 문제 해설 (출제 의도 & 풀이 전략)

이 문제는 XP를 구성하는 요소 중  
- **가치(Value)** 와  
- **기법 또는 전통적 방법론 용어**  

를 구분할 수 있는지를 묻습니다.

👉 XP 문제의 핵심 전략은  
**“XP 가치 5가지”를 정확히 외워두는 것**입니다.

---

## 2️⃣ 정답인 이유 (2번)

### ❌ 2번. 정형 분석

- **정형 분석**은:
  - 전통적인 구조적 방법론
  - 문서 중심, 계획 중심 개발 방식
- XP의 가치와는 **개념적으로 완전히 반대 방향**

👉 XP는 **문서 최소화, 변화 수용, 반복적 개발**을 지향  
👉 따라서 **XP의 가치가 아님** → 정답

---

## 3️⃣ 나머지 선지 분석 (왜 XP의 가치인가)

### 1번. 피드백 ✔
- XP의 핵심 가치 중 하나
- 빠른 반복 개발을 통해 **즉각적인 피드백** 중시
- 테스트, 고객 피드백 강조

---

### 3번. 단순 ✔
- “지금 필요한 것만 만든다”
- 가장 단순한 설계 유지
- 불필요한 기능 배제

👉 시험에서는 **“단순한 설계(Simple Design)”** 자주 출제

---

### 4번. 존중 ✔
- 팀원 간 상호 존중
- 개발자, 고객 모두 존중 대상

👉 최근 개정 교재에서 강조되는 가치

---

## 4️⃣ 틀렸다면 무엇을 추가로 공부해야 하나?

이 문제를 틀렸다면 **XP의 가치와 원칙·기법이 섞여 있는 상태**입니다.

### 반드시 정리할 것 (기출 최다)

#### 📌 XP의 가치 5가지 (무조건 암기)

> **의사소통(Communication)**  
> **단순(Simple)**  
> **피드백(Feedback)**  
> **용기(Courage)**  
> **존중(Respect)**

👉 보기에서 이 5개에 없는 단어는 거의 정답 후보입니다.

---

## 5️⃣ 시험장에서 바로 쓰는 판별 요령

- **추상적이고 인간 중심적 단어**  
  → XP 가치 가능성 높음  
- **분석, 설계, 문서, 정형**  
  → 전통적 방법론 용어 → XP 아님
- XP 가치 문제는  
  👉 **암기 여부로 5초 컷 가능**

**스크럼과 비교 문제** 나오면 시험에서 매우 강해집니다.

### ❓ 질문 (User)
자료 추상화에 대한 설명으로 옳은 것은?
1. 데이터의 세부적인 속성 및 표현 방법 없이 대표적인 표현으로 대체
2. 상세 제어 매커니즘이 아닌 포괄적인 표현으로 대체
3. 상세 수행 과정이 아닌 전반적인 흐름만 파악하도록 표현
4. 공통 속성을 가지는 데이터를 통합

### 💡 답변 (Assistant)
좋습니다.  
이 문제는 **정보처리기사 필기 – 추상화(Abstraction)** 단원에서 **자료 추상화(Data Abstraction)와 다른 추상화 개념을 구분할 수 있는지**를 묻는 **개념 판별형 문제**입니다.

## 문제  
자료 추상화에 대한 설명으로 **옳은 것**은?

---

## 정답  
👉 **1번**

---

## 1️⃣ 문제 해설 (출제 의도 & 풀이 전략)

출제 의도는 다음 3가지를 **구분해서 알고 있는지**입니다.

- 자료 추상화 (Data Abstraction)
- 제어 추상화 (Control Abstraction)
- 과정/기능 추상화 (Procedural Abstraction)

👉 핵심 전략  
**“데이터의 표현·속성을 감춘다” → 자료 추상화**  
**“흐름·제어·과정” → 자료 추상화 아님**

---

## 2️⃣ 정답인 이유 (1번)

### ✔ 1번  
> 데이터의 세부적인 속성 및 표현 방법 없이 대표적인 표현으로 대체

이 설명은 **자료 추상화의 정확한 정의**입니다.

### 자료 추상화란?
- 데이터의 **내부 구현**(저장 구조, 표현 방식)은 숨기고
- **필요한 인터페이스만 제공**
- “무엇(What)”에 집중하고 “어떻게(How)”는 감춤

📌 예시  
- 스택(Stack): 내부 구현은 몰라도 push/pop만 알면 됨  
- 클래스의 private 멤버 숨김

👉 시험 기준으로 **가장 교과서적인 표현** → 정답

---

## 3️⃣ 오답 선지 분석 (왜 아닌가)

### ❌ 2번  
> 상세 제어 메커니즘이 아닌 포괄적인 표현

이 설명은 **제어 추상화(Control Abstraction)** 에 해당합니다.

- 조건문, 반복문 등 제어 구조를 단순화
- 데이터와 직접적인 관련 없음

---

### ❌ 3번  
> 상세 수행 과정이 아닌 전반적인 흐름만 파악

이 설명은 **과정(절차) 추상화 / 기능 추상화** 입니다.

- 함수, 프로시저 단위 추상화
- “어떤 일을 하는가”에 초점

👉 데이터 중심 ❌

---

### ❌ 4번  
> 공통 속성을 가지는 데이터를 통합

이 설명은:
- 일반화(Generalization)
- 데이터 통합
- 혹은 객체지향의 개념에 가깝습니다.

👉 **자료 추상화의 정의가 아님**

---

## 4️⃣ 틀렸다면 무엇을 추가로 공부해야 하나?

이 문제를 틀렸다면 **추상화의 종류별 키워드 정리가 안 된 상태**입니다.

### 반드시 정리할 것 (기출 반복 영역)

#### 📌 추상화 유형 비교

| 추상화 종류 | 핵심 키워드 |
|---|---|
| 자료 추상화 | 데이터 표현 은닉 |
| 제어 추상화 | 제어 구조 단순화 |
| 과정(기능) 추상화 | 수행 과정 은닉 |

👉 시험에서는 **문장 하나로 구분**하게 만듭니다.

---

## 5️⃣ 시험장에서 바로 쓰는 판별 요령

- **“데이터, 속성, 표현 방식”**  
  → 자료 추상화
- **“흐름, 제어, 반복, 조건”**  
  → 제어 추상화
- **“수행 과정, 기능”**  
  → 과정 추상화

이제 이어서 **추상화 vs 캡슐화 vs 정보은닉** 섞어 놓은 문제 나오면  
실전 대비에 아주 좋습니다.

## 문제
화이트박스 테스트의 제어 구조 검사 중  
다음 설명에 해당하는 것은?

- 소스 코드의 **변수 정의(definition)**, **사용(use)** 을 중점적으로 테스트

---

## 정답  
👉 **2. 데이터 흐름 검사**

---

## 1️⃣ 문제 해설 (출제 의도 & 풀이 전략)

화이트박스 테스트에서는 **소스 코드 내부 구조**를 기준으로 테스트합니다.  
그중 **제어 구조 검사**는 다시 여러 유형으로 나뉘며, 이 문제는 다음을 구분할 수 있는지 묻습니다.

- 루프 검사
- 조건 검사
- **데이터 흐름 검사**
- 오류 예측 검사

👉 핵심 키워드  
**“변수의 정의와 사용”** 이 나오면  
→ 고민 없이 **데이터 흐름 검사**

---

## 2️⃣ 정답인 이유 (2번)

### ✔ 2번. 데이터 흐름 검사

**데이터 흐름 검사(Data Flow Testing)** 는 다음을 중점으로 합니다.

- 변수의 **정의(def)**
- 변수의 **사용(use)**
- 정의된 변수가 사용되기까지의 경로
- 정의되었으나 사용되지 않는 변수 탐지

📌 주요 목적
- 초기화되지 않은 변수 사용
- 불필요한 변수 정의
- 잘못된 데이터 사용 오류 발견

👉 문제 설명과 **정확히 일치** → 정답

---

## 3️⃣ 오답 선지 분석 (왜 아닌가)

### 1번. 루프 검사 ❌
- 반복문의:
  - 시작 조건
  - 종료 조건
  - 반복 횟수
- 무한 루프 여부 확인

👉 변수 정의/사용과는 무관

---

### 3번. 조건 검사 ❌
- 분기 조건(참/거짓)
- 복합 조건의 논리 검증

👉 조건식 중심, 데이터 흐름 아님

---

### 4번. 오류 예측 검사 ❌  
(※ 오탈자 있어도 시험에서는 **오류-예측 검사(Error Guessing)** 로 판단)

- 경험에 기반한 오류 추정
- 개발자 직관 활용
- **블랙박스/화이트박스 모두 가능**

👉 제어 구조 검사도 아니고  
👉 변수 정의·사용과 직접적 관련 없음

---

### 💡 답변 (Assistant)
아래 C 코드를 **한 줄씩, 포인터·배열 관점에서 정확히** 설명하겠습니다.  
핵심은 **2차원 배열과 배열 포인터(`int (*p)[3]`)의 관계**, 그리고 **포인터 연산 결과**입니다.

---

## 1. 헤더와 main 함수

```c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[]){
```

- 표준 입출력 및 일반 유틸리티 라이브러리 포함
- `argc`, `argv`는 이 코드에서 사용되지 않음

---

## 2. 2차원 배열 선언 및 초기화

```c
int arr[2][3] = {1, 2, 3, 4, 5, 6};
```

- `arr`은 **2행 3열**의 2차원 정수 배열
- 메모리 구조 (행 우선, row-major):

```
arr[0][0] = 1   arr[0][1] = 2   arr[0][2] = 3
arr[1][0] = 4   arr[1][1] = 5   arr[1][2] = 6
```

- 내부적으로는 다음과 같이 연속 배치됨:

```
[ 1 ][ 2 ][ 3 ][ 4 ][ 5 ][ 6 ]
```

---

## 3. 배열 포인터 선언

```c
int (*p)[3] = NULL;
```

- `p`는 **“int 3개짜리 배열을 가리키는 포인터”**
- 즉, 타입은:

```
p → int[3]
```

⚠️ 주의  
`int *p[3]` ❌ (포인터 배열)  
`int (*p)[3]` ⭕ (배열 포인터)

---

## 4. 배열 포인터에 배열 대입

```c
p = arr;
```

- `arr`은 표현식에서 **`int (*)[3]` 타입**으로 decay
- 즉:

```
p == &arr[0]
```

- 따라서:

```
p[0] → arr[0]
p[1] → arr[1]
```

---

## 5. 첫 번째 printf

```c
printf("%d, ", *(p[0]) + 1 + *(p[1] + 2));
```

### 5-1. `p[0]`

```c
p[0] == *(p + 0) == arr[0]
```

- 타입: `int[3]`
- `*(p[0])` → `arr[0][0]` → **1**

---

### 5-2. `p[1] + 2`

```c
p[1] == arr[1]
p[1] + 2 == &arr[1][2]
```

- `*(p[1] + 2)` → `arr[1][2]` → **6**

---

### 5-3. 계산

```
*(p[0]) + 1 + *(p[1] + 2)
= 1 + 1 + 6
= 8
```

➡️ 출력:
```
8,
```

## 8. 핵심 정리 (시험·면접 포인트)

### ✅ 타입 관계
```c
arr        → int [2][3]
arr        → int (*)[3]
p          → int (*)[3]
p[i][j]    → arr[i][j]
```

### ✅ 포인터 이동 단위
- `p + 1` → **int 3개 크기만큼 이동**
- 2차원 배열에서는 **행 단위 이동**
