# 코드베이스 이해 방법

> **카테고리**: `Algorithms (알고리즘 & 자료구조)`  
> **원천**: ChatGPT 대화 아카이브 (`raw/notes/Chatgpt_2026-08-02-23-14-23`)  
> **작성일**: 2026-07-31

## 💬 대화 내용 및 Q&A

### ❓ 질문 (User)
내가 Codex로 프로젝트를 잔뜩 진행시켜서 4만줄이 넘는 코드를 봐야되는 상황이 되었어. 현직자들은 이 모든 코드를 읽고 이해하는거야?

### 💡 답변 (Assistant)
아니. **현직자도 4만 줄을 처음부터 끝까지 읽고 전부 기억하지 않는다.** 실제로는 코드 전체를 외우는 게 아니라, 필요한 순간에 원하는 부분을 빠르게 찾아갈 수 있는 **코드베이스의 지도**를 만든다.

4만 줄은 개인 프로젝트 기준으로는 상당히 크지만, 회사 프로젝트에서는 오히려 작은 편일 수 있다. 수십만~수백만 줄인 코드베이스도 흔하다. 그런 환경에서 모든 코드를 완전히 이해하려고 하면 개발 자체를 할 수 없다.

현직자가 주로 파악하는 것은 다음 정도다.

- 프로그램이 어디서 시작되는지
- 주요 기능이 어떤 모듈로 나뉘는지
- 데이터가 어디에서 들어와 어디로 나가는지
- 핵심 객체와 함수가 무엇인지
- 수정하려는 기능이 어떤 코드 경로를 거치는지
- 테스트와 설정 파일이 어디에 있는지

예를 들어 API 서버라면 모든 코드를 읽는 것이 아니라 대략 다음 경로를 추적한다.

```text
HTTP 요청
→ Router
→ Controller / Endpoint
→ Service
→ Repository
→ Database
→ Response
```

특정 기능을 수정할 때만 그 경로 주변을 자세히 읽는다.

## 코드 이해에는 단계가 있다

현업에서는 대략 세 가지 수준으로 이해한다.

### 1. 구조적 이해

```text
src/
├── api/
├── services/
├── models/
├── repositories/
├── utils/
└── tests/
```

각 디렉터리가 어떤 책임을 갖는지 파악하는 단계다. 이때는 함수 내부 구현까지 읽지 않는다.

### 2. 흐름 이해

예를 들어 “이미지 생성 요청”이 들어왔을 때 다음 흐름만 따라간다.

```text
generate_image()
→ validate_prompt()
→ load_model()
→ run_inference()
→ save_result()
```

관련 없는 인증, 로깅, 관리자 기능은 일단 보지 않는다.

### 3. 세부 구현 이해

버그를 수정하거나 성능을 개선할 때 필요한 함수 몇 개만 깊게 읽는다.

즉, **전체 4만 줄을 동일한 깊이로 읽지 않는다.**

## 다만 Codex가 만든 4만 줄은 조금 다르게 봐야 한다

사람이 설계하면서 점진적으로 만든 4만 줄과, 에이전트가 빠르게 생성한 4만 줄은 위험성이 다르다.

Codex가 많은 코드를 생성했다면 이런 문제가 있을 수 있다.

- 같은 기능을 여러 곳에서 중복 구현
- 사용되지 않는 코드가 계속 남아 있음
- 파일마다 설계 방식이 다름
- 불필요한 추상화와 클래스가 많음
- 테스트 없이 기능만 확장됨
- 이름은 그럴듯하지만 실제 동작은 불일치
- 서로 다른 시점에 생성된 코드 사이의 규칙 충돌

따라서 지금 필요한 것은 **4만 줄을 읽는 것보다 코드베이스를 정리하고 신뢰 경계를 만드는 것**이다.

## 지금부터는 이렇게 보는 게 좋다

### 1. 실행 진입점부터 찾기

Python 프로젝트라면 보통 다음 파일부터 확인한다.

```text
main.py
app.py
run.py
cli.py
__main__.py
```

웹 프로젝트라면 FastAPI의 `FastAPI()`, Flask의 `Flask()`, Django의 `urls.py` 같은 진입점을 찾는다.

### 2. 파일별 역할을 한 줄로 적기

```text
api/routes.py          API 요청 라우팅
services/generation.py 이미지 생성 비즈니스 로직
models/request.py      입력 데이터 구조
infra/database.py      DB 연결
utils/image.py         이미지 처리 유틸리티
```

내용을 완벽히 이해하지 못해도 괜찮다. 우선 “무슨 책임을 가진 파일인지”만 정리한다.

### 3. 핵심 기능 하나씩 추적하기

프로젝트에서 가장 중요한 사용자 시나리오를 3~5개 고른다.

```text
1. 사용자가 요청을 보낸다.
2. 요청이 검증된다.
3. 모델이 실행된다.
4. 결과가 저장된다.
5. 사용자에게 응답한다.
```

각 단계에서 호출되는 함수와 파일만 따라간다.

### 4. 테스트를 먼저 확인하기

테스트는 작성자가 생각한 사용법을 가장 압축해서 보여준다.

```text
tests/
├── test_api.py
├── test_generation.py
└── test_database.py
```

테스트가 없다면 상당히 위험한 상태다. 적어도 핵심 경로에는 smoke test나 integration test가 필요하다.

### 5. 사용되지 않는 코드 제거하기

다음 항목을 정리하면 4만 줄이 실제로는 훨씬 줄어들 가능성이 크다.

- 호출되지 않는 함수
- import되지 않는 모듈
- 중복 구현
- 이전 버전 파일
- 임시 스크립트
- 사용하지 않는 설정
- 주석 처리된 대형 코드 블록

에이전트 기반 개발에서는 코드가 늘어나는 속도보다 **죽은 코드가 쌓이는 속도**가 더 큰 문제가 되기도 한다.

## 중요한 기준

프로젝트를 이해했다는 것은 모든 줄을 설명할 수 있다는 뜻이 아니다. 다음 질문에 답할 수 있으면 상당 부분 이해한 것이다.

1. 이 프로그램의 시작점은 어디인가?
2. 핵심 기능은 어떤 모듈들이 담당하는가?
3. 요청이나 데이터는 어떤 경로로 이동하는가?
4. 외부 시스템과 연결되는 지점은 어디인가?
5. 핵심 상태는 어디에 저장되는가?
6. 문제가 생기면 어느 로그와 테스트를 확인해야 하는가?
7. 특정 기능을 바꾸려면 어느 파일들을 수정해야 하는가?

이 질문에 답할 수 있다면, 4만 줄을 외우지 않아도 프로젝트를 관리할 수 있다.

그리고 솔직히 말하면, 지금 상황은 나쁜 경험만은 아니다. **에이전트에게 코드를 생성시키는 능력 다음 단계는, 생성된 코드의 구조와 품질을 통제하는 능력**이다. 현업에서도 훨씬 가치 있는 역량은 코드를 많이 타이핑하는 능력보다, 큰 코드베이스에서 변경 범위를 정확히 잡고 안전하게 수정하는 능력이다.

### ❓ 질문 (User)
200줄 정도 되는 파이썬 파일 하나도 분석 잘 안될때는 어떻게 해야할까

### 💡 답변 (Assistant)
그럴 수 있어. **200줄이라고 쉬운 코드가 아니다.** 콜백, 상속, 데코레이터, 전역 상태, 외부 모듈 호출이 섞이면 200줄도 충분히 어렵다. 반대로 단순한 데이터 처리 코드는 2,000줄이어도 비교적 쉽게 읽힌다.

핵심은 **위에서 아래로 전부 이해하려 하지 않는 것**이다.

## 1. 먼저 파일의 목적을 한 문장으로 추정한다

파일을 열고 처음에는 구현을 읽지 말고 다음만 본다.

```python
import ...
from ... import ...

CONSTANT = ...

class ...
def ...

if __name__ == "__main__":
    ...
```

그리고 임시로 한 문장을 적는다.

```text
이 파일은 이미지 생성 요청을 받아 모델을 실행하고 결과를 저장하는 파일 같다.
```

정확하지 않아도 된다. 나중에 수정하면 된다.

## 2. 실행 시작점을 찾는다

Python 파일에서는 보통 다음 중 하나가 시작점이다.

```python
if __name__ == "__main__":
    main()
```

또는 다른 파일에서 호출되는 대표 함수다.

```python
def run(...)
def main(...)
def predict(...)
def train(...)
def create_app(...)
```

클래스라면 외부에서 생성될 가능성이 높은 클래스를 찾는다.

```python
controller = AttentionStore()
```

그다음 시작점 안에서 호출되는 함수만 따라간다.

```text
main()
→ load_config()
→ load_model()
→ run_inference()
→ save_result()
```

일단 이 호출 흐름만 확보하면 된다.

## 3. 함수마다 세 가지만 적는다

각 함수의 모든 줄을 이해하려 하지 말고 다음만 적는다.

```text
함수 이름:
입력:
출력:
부작용:
```

예를 들면:

```text
run_inference
입력: prompt, model, generator
출력: 생성된 이미지 tensor
부작용: GPU 메모리 사용, 로그 출력
```

여기서 **부작용**은 특히 중요하다.

- 파일 저장
- 전역 변수 수정
- GPU 사용
- 데이터베이스 변경
- 네트워크 요청
- 객체 내부 상태 변경

이것만 정리해도 코드의 절반 이상이 보인다.

## 4. 실제 값 하나를 넣어서 따라간다

추상적으로 읽으면 어렵다. 구체적인 값으로 바꿔서 본다.

```python
prompt = "a red car"
seed = 14291
indices_to_alter = [2, 3]
```

그리고 머릿속이나 메모에 기록한다.

```text
prompt
→ tokenize
→ token_indices
→ model inference
→ image tensor
→ PIL image
→ output.png
```

조건문도 실제 값 기준으로 판단한다.

```python
if run_standard_sd:
```

현재 값이 `False`라면 첫 분석에서는 해당 블록을 건너뛴다. 모든 분기를 동시에 이해하려 하면 훨씬 어렵다.

## 5. 모르는 함수 내부로 바로 들어가지 않는다

예를 들어 이런 코드가 있다고 하자.

```python
image, latent = run_and_display(...)
```

처음부터 `run_and_display()` 내부 100줄을 읽지 말고 먼저 다음만 확인한다.

```text
입력으로 무엇을 받는가?
무엇을 반환하는가?
호출 전후 어떤 값이 달라지는가?
```

내부 구현은 실제로 문제가 발생하거나 수정해야 할 때 들어간다.

이 방식은 IDE의 함수 접기 기능과 함께 쓰면 좋다.

## 6. 실행하면서 확인한다

코드를 읽는 것만으로 이해하려 하지 않아도 된다.

```python
print(type(prompt), prompt)
print(type(token_indices), token_indices)
print(image.shape)
print(image.dtype)
print(image.device)
```

조금 더 체계적으로 하려면:

```python
import logging

logging.basicConfig(level=logging.DEBUG)
logger = logging.getLogger(__name__)

logger.debug("prompt=%r", prompt)
logger.debug("token_indices=%s", token_indices)
```

PyTorch 코드라면 특히 다음을 확인한다.

```python
print(tensor.shape)
print(tensor.dtype)
print(tensor.device)
print(tensor.requires_grad)
```

머릿속으로 추측하는 것보다 실제 실행 결과를 보는 편이 훨씬 빠르다.

## 7. 디버거로 한 줄씩 따라간다

VS Code라면 함수 시작 부분에 breakpoint를 걸고 다음을 사용한다.

- `Step Over`: 현재 줄 실행
- `Step Into`: 호출한 함수 내부로 이동
- `Step Out`: 현재 함수에서 빠져나오기
- `Variables`: 현재 변수 값 확인
- `Call Stack`: 어떤 함수들을 거쳐 왔는지 확인

특히 **Call Stack**을 보면 프로젝트의 실행 흐름을 이해하기 좋다.

200줄을 눈으로 읽는 것보다, 정상 입력 한 번을 디버거로 따라가는 것이 더 효과적일 때가 많다.

## 8. 코드를 네 구역으로 분류한다

파일의 각 부분을 다음처럼 분류해 본다.

```text
1. 설정과 상수
2. 데이터 준비
3. 핵심 로직
4. 입출력과 저장
```

예를 들면:

```python
# 설정
DEVICE = "cuda"

# 데이터 준비
def load_image(...):
    ...

# 핵심 로직
def generate(...):
    ...

# 입출력
def save_image(...):
    ...
```

이 구분이 되지 않는다면, 코드 자체가 여러 책임을 한 파일에 섞어 놓았을 가능성도 있다. 즉, 이해가 안 되는 원인이 실력 부족만은 아닐 수 있다.

## 9. 분석 메모를 남긴다

다음 템플릿이면 충분하다.

```text
파일 목적:
실행 시작점:
핵심 함수:
주요 입력:
주요 출력:
변경되는 상태:
외부 의존성:
아직 모르는 부분:
```

예:

```text
파일 목적:
Attention 기반 이미지 생성 실행

실행 시작점:
notebook에서 run_and_display() 호출

핵심 함수:
get_indices_to_alter_new
run_and_display
AttentionStore

주요 입력:
prompt, image_guidance, mask_image_path

주요 출력:
image, image_latent

외부 의존성:
torch, diffusers pipeline, CUDA

아직 모르는 부분:
AttentionStore가 어느 시점에 attention map을 저장하는지
```

“모르는 부분”을 명시하면 막연한 불안이 구체적인 질문으로 바뀐다.

## 10. AI에게는 파일 전체 설명보다 좁게 질문한다

이렇게 질문하면 답변이 피상적일 수 있다.

```text
이 코드 전체 설명해줘.
```

대신 다음처럼 질문하는 것이 좋다.

```text
이 파일의 실행 진입점과 핵심 호출 흐름만 정리해줘.
```

```text
run_and_display 함수에서 GPU 메모리를 가장 많이 사용할 가능성이 높은 부분을 찾아줘.
```

```text
이 함수의 입력, 출력, 부작용을 구분해서 설명해줘.
```

```text
normal_prompt가 최종 이미지 생성까지 전달되는 경로를 추적해줘.
```

```text
이 코드에서 제거해도 될 가능성이 있는 분기와 중복 로직을 찾아줘.
```

## 추천 분석 순서

200줄짜리 Python 파일이라면 다음 순서로 보면 된다.

```text
1. import 확인
2. 전역 변수 확인
3. 함수와 클래스 목록 작성
4. 실행 시작점 찾기
5. 핵심 호출 흐름 작성
6. 정상 입력 하나만 추적
7. 변수 shape/type 확인
8. 모르는 함수만 내부 분석
9. 테스트 또는 디버거로 검증
```

가장 중요한 것은 **한 번에 완전히 이해하려 하지 않는 것**이다.

첫 번째 읽기에서는 구조만, 두 번째 읽기에서는 실행 흐름만, 세 번째 읽기에서 필요한 구현만 본다. 200줄을 읽고도 이해가 안 되는 것은 드문 일이 아니고, 실제 현업에서도 코드를 실행하고 로그와 테스트를 보면서 이해한다.
