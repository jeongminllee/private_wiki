### 💡 답변 (Assistant)
네, **코딩 없이도 AI 에이전트 개발은 가능합니다.** 다만 정확히는 **“어느 수준까지 에이전트라고 부를 것인가”**에 따라 달라집니다.

### 코딩 없이 가능한 범위

노코드 에이전트 빌더를 사용하면 다음 정도는 충분히 구현할 수 있습니다.

- 시스템 프롬프트와 역할 설정
- PDF·문서·사내 지식 기반 질의응답
- 여러 단계의 업무 흐름 구성
- 웹 검색, 이메일, 캘린더, Notion 같은 외부 서비스 연결
- 조건에 따른 분기
- 담당자 승인 후 다음 단계 실행
- 정해진 형식의 보고서 생성
- 간단한 멀티 에이전트 협업

예를 들어 금융 보안 에이전트라면:

> 보안 문서 입력  
> → 위험 요소 추출  
> → 관련 규정 검색  
> → 위험도 분류  
> → 대응 방안 작성  
> → 담당자 승인 요청

이 정도 흐름은 노코드 또는 아주 적은 설정만으로도 만들 수 있습니다.

### 코딩이 필요해지는 지점

다음 요구사항이 들어가면 순수 노코드는 빠르게 한계에 도달합니다.

- 금융 데이터나 사내 시스템의 복잡한 API 연동
- 사용자별 접근 권한과 인증
- 민감정보 마스킹
- 정교한 RAG 검색 및 재정렬
- 여러 번의 재시도와 예외 처리
- 에이전트 상태의 장기 저장
- 모델 호출량·비용·지연시간 최적화
- 감사 로그와 의사결정 근거 저장
- 자동 평가와 품질 테스트
- 온프레미스 또는 폐쇄망 배포
- 에이전트가 실행할 수 있는 작업을 정책적으로 제한하는 기능

특히 **금융·보안 분야는 “답변이 그럴듯한가”보다 “왜 그렇게 판단했는지, 어떤 자료를 사용했는지, 무엇을 실행했는지”가 중요**합니다. 그래서 실제 운영 단계에서는 코드가 거의 반드시 필요합니다.

### 당신의 금융 보안 특화 에이전트 기준

이전에 잡았던 **초기 PoC 단계**라면 가장 현실적인 방식은 **노코드 70% + 코드 30%의 로우코드 방식**입니다.

| 영역 | 권장 구현 |
|---|---|
| 화면과 대화 인터페이스 | 노코드 |
| 프롬프트·업무 흐름 | 노코드 |
| 문서 업로드와 기본 검색 | 노코드 |
| 외부 서비스 연결 | 기존 커넥터 우선 |
| 보안 규칙·권한 검사 | 코드 |
| 민감정보 제거 | 코드 |
| 검색 품질 개선 | 필요 시 코드 |
| 평가·감사 로그 | 코드 또는 별도 저장소 |
| 운영 배포 | 코드 기반 권장 |

처음부터 모든 것을 Python으로 직접 만들 필요는 없습니다. 노코드로 업무 흐름과 사용자 반응을 먼저 검증한 뒤, 문제가 생기는 부분만 코드로 교체하는 방식이 효율적입니다.

### 권장 개발 순서

1. **노코드 프로토타입**  
   문서 입력 → 분석 → 보고서 출력 흐름을 검증합니다.

2. **로우코드 PoC**  
   Python API를 추가해 보안 규칙, 로그, 검색, 검증 단계를 구현합니다.

3. **코드 기반 운영 버전**  
   인증, 권한, 관측성, 평가, 비용 관리, 장애 복구까지 포함합니다.

결론적으로, **에이전트의 아이디어와 업무 흐름을 검증하는 데는 코딩이 없어도 충분하지만, 금융 보안 에이전트를 신뢰할 수 있는 서비스로 운영하려면 최소한의 코딩은 필요합니다.** 당신처럼 Python과 ML 도구를 이미 다룰 수 있다면, 순수 노코드보다 **노코드로 빠르게 시작하고 중요한 부분만 직접 구현하는 방식**이 가장 적합합니다.

## 먼저 잡아야 할 수상 전략

상세 심사 배점은 현재 페이지에 공개되어 있지 않습니다. 다만 대회 설명으로부터 다음 요소가 중요할 가능성이 높다고 판단됩니다.

1. 문제가 한 문장으로 설명될 것
2. 사용 전후 효과가 명확할 것
3. 단순 챗봇이 아니라 일정한 결과물을 만들 것
4. 특정 사용자 집단에 실제 도움이 될 것
5. 예선 단일 기능이 결선 서비스로 자연스럽게 확장될 것

특히 공식 설명에서 반복해서 강조하는 것은 거대한 기술적 난제가 아니라 **“반복되는 작은 불편”과 “다른 사람에게도 이로운 결과”**입니다. citeturn489165view0

따라서 “무엇이든 물어보세요” 형태의 범용 에이전트는 피하고, 다음처럼 구성해야 합니다.

> 특정 사용자가 특정 자료를 넣으면  
> 에이전트가 특정 판단 절차를 거쳐  
> 바로 사용할 수 있는 특정 결과물을 제공한다.

# 가장 추천하는 1순위

## 1. 수입식품 위해정보 판독 에이전트

### 한 문장 설명

> 복잡한 해외 식품 리콜·위해정보를 입력하면, 국내 소비자와 수입업자가 이해할 수 있는 위험 요약과 확인 체크리스트로 변환해 주는 에이전트

이 아이디어가 당신에게 가장 강합니다.

당신은 목재·농산물 계열 연구 배경이 있고, 과거에도 **수입 농산물 농약 검사와 수입식품 안전 위해도 예측**에 관심을 보였습니다. 단순한 아이디어가 아니라 문제의 맥락을 이해하고 설명할 수 있다는 점이 발표에서 상당한 차별점이 됩니다.

### 사용자가 겪는 문제

해외 리콜이나 식품안전기관의 공지는 다음과 같은 문제가 있습니다.

- 외국어로 작성됨
- 전문용어가 많음
- 실제로 어떤 제품이 위험한지 찾기 어려움
- 소비자와 수입업자가 해야 할 행동이 다름
- 긴 문서에서 제품명, 원산지, 위해물질, 조치 내용을 직접 찾아야 함

### 예선용 단일 기능

사용자가 해외 리콜 공지나 위해정보 본문을 붙여 넣으면 다음 형식으로 변환합니다.

```text
[위해정보 요약]

위험 제품:
원산지:
제조사:
위해요인:
영향 대상:
발표 기관:
발표 날짜:

[위험 수준]
주의 / 확인 필요 / 긴급 확인

[소비자 행동]
1.
2.
3.

[수입·판매업자 확인사항]
1.
2.
3.

[확인되지 않은 정보]
-
```

핵심은 단순 요약이 아니라 **정보 추출 → 위험 해석 → 사용자별 행동 체크리스트 생성**입니다.

### 결선 MVP 확장

결선에서는 다음 서비스로 발전시킬 수 있습니다.

- 국가별 리콜 공지 입력
- 한국어 표준 형식으로 통합
- 동일 제품명·제조사·원산지 기준 중복 이슈 묶기
- 소비자용, 수입업자용, 검사기관용 보고서 분리
- 관심 제품 등록
- 위험정보 이력 관리
- 원문과 AI 해석을 나란히 제시
- AI가 확인하지 못한 항목을 별도 표시

### 강점

- 사회적 편익이 명확함
- 흔한 일정관리·요약 에이전트와 차별화됨
- 문서 이해에 강한 Solar LLM과 잘 맞음
- 노코드로 예선 기능을 만들기 쉬움
- 결선에서 데이터 서비스로 확장 가능
- 당신의 연구 배경과 서사가 연결됨

### 주의점

“안전하다” 또는 “위험하다”라고 최종 판정하는 서비스로 만들면 안 됩니다.

다음처럼 포지셔닝하는 것이 안전합니다.

> 공식 위해정보를 쉽게 이해하고, 사용자가 확인해야 할 사항을 빠뜨리지 않도록 돕는 정보 정리 에이전트

# 2순위

## 2. 보안사고 초동대응 에이전트

### 한 문장 설명

> 의심스러운 이메일, 문자 또는 보안 상황을 입력하면 위험 신호와 즉시 해야 할 행동을 순서대로 알려주는 에이전트

당신이 구상해온 **금융보안 특화 에이전트**를 공모전 수준으로 축소한 아이디어입니다.

“금융보안 전반을 분석하는 에이전트”는 너무 큽니다. 대신 **보안사고 발생 직후 사용자가 무엇을 해야 하는지 모르는 문제** 하나에 집중합니다.

### 대상 사용자

- 피싱 문자를 받은 일반인
- 의심스러운 송금 요청을 받은 직원
- 계정 탈취가 의심되는 소규모 사업자
- 보안 담당자가 없는 비영리단체·소기업

### 예선용 단일 기능

사용자가 상황을 설명하거나 메시지 내용을 붙여 넣으면 다음을 생성합니다.

```text
[현재 상황 요약]

[발견된 위험 신호]
1.
2.
3.

[지금 즉시 할 일]
1.
2.
3.

[하지 말아야 할 행동]
1.
2.

[증거 보존 항목]
- 문자 캡처
- 발신 번호
- 송금 기록
- 접속 시각

[연락해야 할 기관 또는 담당자]
-
```

### 좋은 차별화 포인트

대부분의 보안 챗봇은 “피싱으로 보입니다”에서 끝납니다. 이 에이전트는 **행동 순서와 증거 보존 절차**를 제공합니다.

예를 들면:

> 링크를 클릭했지만 로그인하지 않음

과

> 링크를 클릭하고 아이디·비밀번호를 입력함

은 대응 순서가 달라야 합니다.

### 결선 MVP 확장

- 상황별 단계형 문답
- 피싱, 계정탈취, 악성앱, 송금사기 유형 분류
- 개인용·회사 직원용 대응 절차 분리
- 사고 타임라인 자동 작성
- 신고용 사건 요약서 생성
- 조직별 보안 담당자 연락 절차 연결
- 대응 완료 여부 체크
- 민감정보 자동 마스킹

### 장점

- 누구나 이해할 수 있는 문제
- 발표 시 시연이 매우 쉬움
- 사회적 가치가 강함
- 금융보안 진로와 연결 가능
- 실제 서비스를 상상하기 쉬움

### 위험 요소

법적·금융적 확정 판단을 제공하지 말고, 반드시 다음 역할로 제한해야 합니다.

> 위험 가능성을 정리하고 공식 대응 절차를 안내하는 초동대응 지원 도구

# 3순위

## 3. AI·ML 실험 인수인계 기록 에이전트

### 한 문장 설명

> 흩어진 실험 메모와 로그를 입력하면, 다른 사람이 그대로 이어서 작업할 수 있는 재현 가능한 인수인계 문서로 변환하는 에이전트

이 아이디어는 당신의 실제 경험과 가장 강하게 연결됩니다.

GPU 환경이 바뀌거나, 작업물이 삭제되거나, 실험 담당자가 달라지면 다음과 같은 정보가 자주 사라집니다.

- 어떤 모델을 사용했는가
- 어떤 데이터 버전이었는가
- 어떤 명령으로 실행했는가
- 무엇이 실패했는가
- 어떤 설정이 가장 좋았는가
- 다음 실험은 무엇인가

당신도 컴퓨팅 환경이 축소되거나 변경되는 경험을 통해 기록의 중요성을 체감했다고 했습니다. 이 이야기는 발표 서사로 좋습니다.

### 예선용 단일 기능

실험 로그, 메모, 오류 메시지를 붙여 넣으면 다음 문서를 생성합니다.

```text
# 실험 인수인계서

## 1. 실험 목적

## 2. 실행 환경
- OS:
- GPU:
```

# 추천안: 공지 행동 전환 서비스

단순히 공지를 요약하는 서비스가 아닙니다.

> **읽어야 할 공지를, 완료해야 할 행동으로 바꿔주는 서비스**

가 핵심입니다.

## 예선: 단일 기능

### 입력

공지문, 안내 문자, 이메일 본문, 알림장 내용을 붙여 넣습니다.

### 출력

```text
[이 공지가 나에게 해당하는가]
해당 대상: 교육 참가자 전원

[해야 할 일]
□ 8월 12일까지 참가 신청
□ 신청 후 이메일 확인
□ 행사 당일 신분증 지참

[중요 일정]
- 신청 마감: 8월 12일 18:00
- 행사 일시: 8월 20일 14:00

[준비물]
- 신분증
- 개인 노트북

[주의사항]
- 현장 주차 지원 없음

[확인이 필요한 내용]
- 점심 제공 여부가 공지에 없음

[문의 메시지 초안]
안녕하세요. 행사 당일 점심이 제공되는지 문의드립니다.
```

여기서 중요한 차별점은 다음입니다.

- 요약이 아니라 **행동 추출**
- 마감일과 준비물의 **구조화**
- 정보가 없는 부분을 추측하지 않고 **불명확 항목으로 분리**
- 사용자가 바로 보낼 수 있는 **문의 문구 생성**
- 가능하면 각 결과가 공지의 어느 문장에서 나온 것인지 표시

“AI가 공지를 읽어줍니다”보다 “공지 때문에 해야 하는 일을 놓치지 않게 합니다”가 훨씬 강합니다.

# 결선: 실제 MVP

결선에서는 기능을 무작정 늘리지 말고, 예선 결과물을 저장하고 관리할 수 있는 서비스로 만듭니다.

## 화면 1. 공지함

사용자가 공지를 붙여 넣거나 문서를 등록합니다.

```text
오늘 등록한 공지
- 건강검진 안내
- 아파트 단수 안내
- 교육 참가 안내
```

## 화면 2. 내 실행 보드

공지 여러 개에서 나온 행동을 하나로 모읍니다.

```text
오늘
□ 관리사무소에 차량번호 제출

이번 주
□ 건강검진 문진표 작성
□ 교육 참가 신청

준비할 것
□ 신분증
□ 개인 노트북
□ 복용약 목록
```

이 화면이 있어야 단발성 프롬프트가 아니라 **서비스 MVP**가 됩니다.

## 화면 3. 변경 공지 추적

수정된 공지를 넣으면 기존 실행 카드와 비교합니다.

```text
변경된 내용

행사 장소
기존: 본관 3층
변경: 별관 1층

준비물
새롭게 추가됨: 신분증 사본

내 할 일 변경
□ 캘린더 장소 수정
□ 신분증 사본 준비
```

이 기능이 결선 데모의 하이라이트가 됩니다.

## 가능할 경우 추가할 기능

플랫폼에서 지원되는 범위가 확인되면 다음 중 하나만 추가하는 것이 좋습니다.

- 캘린더 등록
- 마감 전 알림
- 가족이나 동료와 실행 카드 공유

세 가지를 모두 넣기보다 **가장 안정적으로 작동하는 하나**를 선택하는 편이 낫습니다.

```text
공지 등록
   ↓

   ↓

   ↓

   ↓

   ↓

```

여기서 가장 중요한 차별점은 **수정 공지가 와도 기존 행동카드와 연결된다는 것**입니다.

일반적인 AI 요약 서비스는 새 공지를 다시 요약할 뿐이지만, 이 서비스는 다음처럼 동작합니다.

> → 기존 행동카드의 마감일 자동 변경  
> → 긴급도 ‘여유 있음’에서 ‘곧 마감’으로 변경  
> → 사용자에게 변경 사실 알림

# 2. 행동카드 구조

공지 하나에서 행동카드가 여러 개 만들어질 수 있습니다.

예를 들어 다음 공지가 있다고 가정하겠습니다.

> 교육 참가자는 8월 15일까지 신청서를 제출하고, 행사 당일 신분증과 노트북을 지참해 주세요.

생성되는 행동카드는 다음과 같습니다.

### 카드 1

```text
교육 참가 신청서 제출

상태: 해야 할 일
중요도: 중요
긴급도: 곧 마감
마감일: 8월 15일
예상 소요시간: 15분

해야 하는 이유:
교육 참가를 위해 필수로 제출해야 함

근거:
“교육 참가자는 8월 15일까지 신청서를 제출하고”

체크리스트:
□ 신청서 작성
□ 제출
□ 제출 완료 여부 확인
```

### 카드 2

```text
행사 준비물 챙기기

상태: 해야 할 일
중요도: 중간
긴급도: 여유 있음
실행일: 행사 전날

준비물:
□ 신분증
□ 노트북

근거:
“행사 당일 신분증과 노트북을 지참해 주세요.”
```

공지 전체를 하나의 카드로 만드는 것이 아니라, **독립적으로 완료할 수 있는 행동 단위로 분리**해야 합니다.

# 3. 상태는 3단계로 유지

사용자가 제안한 상태 구분이 적절합니다.

## 해야 할 일

아직 시작하지 않은 카드입니다.

- AI가 공지에서 자동 생성
- 기본 상태
- 중요도와 긴급도에 따라 정렬
- 시작 버튼을 누르면 ‘하는 중’으로 이동

## 하는 중

사용자가 현재 처리하고 있는 카드입니다.

- 진행 체크리스트 표시
- 필요한 서류나 준비물 확인
- 중간 진행 상태 저장
- 관련 문의 메시지 작성 가능

## 완료

행동이 끝난 카드입니다.

- 완료 일시 기록
- 완료 근거를 선택적으로 첨부
- 이후 수정 공지가 발생하면 재검토 가능

상태를 더 세분화해 `보류`, `대기 중`, `취소` 등을 넣고 싶을 수 있지만, 초기 MVP에서는 복잡해집니다.

대신 `취소됨`은 사용자 작업 상태가 아니라 **시스템 상태**로 별도 관리하는 것이 좋습니다.

```text
사용자 작업 상태:
해야 할 일 / 하는 중 / 완료

시스템 상태:
정상 / 변경됨 / 취소됨
```

---

# 4. 중요도와 긴급도는 분리해야 한다

이 부분이 핵심입니다.

중요도와 긴급도를 하나의 ‘우선순위’로 합치면 사용자가 이유를 이해하기 어렵습니다.

예를 들어:

- 세금 신고: 중요하지만 아직 마감까지 20일 남음
- 오늘까지 설문 참여: 긴급하지만 중요도는 낮음

둘은 성격이 다릅니다.

따라서 행동카드에 두 개의 축을 별도로 표시해야 합니다.

## 중요도

행동을 하지 않았을 때의 영향을 기준으로 판단합니다.

### 중요

다음 중 하나에 해당할 때입니다.

- 의무적으로 해야 함
- 미이행 시 불이익이 있음
- 금전·계약·안전과 관련됨
- 다른 일정이나 업무의 선행 조건임
- 기한을 놓치면 다시 처리하기 어려움

예:

- 등록금 납부
- 계약서 제출
- 건강검진 예약
- 시험 원서 접수
- 필수 교육 이수

### 중간

완료하는 것이 필요하거나 권장되지만, 즉각적인 큰 불이익은 없는 경우입니다.

- 참석 여부 회신
- 행사 준비물 챙기기
- 문서 검토
- 일정 조율
- 사전 설문 작성

### 사소

선택적이거나 영향이 작은 행동입니다.

- 만족도 조사
- 참고자료 읽기
- 선택 행사 신청
- 프로필 사진 등록
- 알림 설정

중요도는 AI가 자동 추천하되, 사용자가 언제든 수정할 수 있어야 합니다.

---

## 긴급도

긴급도는 마감일까지 남은 시간을 기준으로 **자동으로 계속 변경**됩니다.

예를 들어 기본 규칙을 다음처럼 정할 수 있습니다.

| 긴급도 | 기준 |
|---|---|
| 곧 마감 | 2일 이내 |
| 중간 | 3~7일 |
| 여유 있음 | 8일 이상 |
| 기한 초과 | 마감일 경과 |

하지만 모든 행동에 같은 기준을 적용하면 문제가 생길 수 있습니다.

예를 들어 해외여행 준비는 일주일 전이어도 긴급할 수 있고, 간단한 설문은 하루 전에도 충분할 수 있습니다. 따라서 MVP에서는 기본 규칙을 사용하고, 이후 예상 소요시간까지 반영할 수 있습니다.

```text
실질적 여유시간
= 마감일까지 남은 시간
- 예상 소요시간
- 준비에 필요한 선행시간
```

예:

```text
마감까지 5일 남음
필요 서류 발급에 4일 소요
→ 실제로는 ‘곧 마감’
```

이 기능은 상당히 강력한 차별점이 될 수 있습니다.

---

# 5. 최종 우선순위 계산

사용자 화면에서는 중요도와 긴급도를 각각 보여주되, 카드 정렬을 위해 내부적으로 종합 점수를 사용할 수 있습니다.

예를 들어:

```text
중요도
중요 = 3
중간 = 2
사소 = 1

긴급도
곧 마감 = 3
중간 = 2
여유 있음 = 1
```

기본 우선순위 점수는 다음처럼 구성할 수 있습니다.

```text
우선순위 점수
= 중요도 점수 × 2
+ 긴급도 점수
```

중요도를 조금 더 강하게 반영하는 방식입니다.

| 중요도 | 긴급도 | 점수 |
|---|---|---:|
| 중요 | 곧 마감 | 9 |
| 중요 | 중간 | 8 |
| 중요 | 여유 있음 | 7 |
| 중간 | 곧 마감 | 7 |
| 중간 | 중간 | 6 |
| 사소 | 곧 마감 | 5 |

다만 사용자에게 숫자 점수까지 보여줄 필요는 없습니다.

화면에서는 다음 정도가 좋습니다.

```text
🔥 지금 처리
중요 + 곧 마감

⭐ 미리 처리
중요 + 여유 있음

⏰ 빠르게 처리
중간/사소 + 곧 마감

📌 여유 있을 때
중간/사소 + 여유 있음
```

이렇게 하면 일반 사용자도 즉시 이해할 수 있습니다.

# 6. 보드 화면 설계

기본 화면은 칸반 보드 형태가 적합합니다.

| 해야 할 일 | 하는 중 | 완료 |
|---|---|---|
| 참가 신청서 제출 | 건강검진 문진표 작성 | 행사 참석 여부 회신 |
| 신분증 사본 준비 |  | 주차 등록 |
| 노트북 챙기기 |  |  |

각 카드에는 최소한 다음 정보가 표시됩니다.

```text
[중요] [곧 마감]

교육 참가 신청서 제출
8월 15일 마감 · 2일 남음
교육 안내 공지에서 생성됨
```

카드 상세 화면을 열면 다음을 보여줍니다.

- 해야 할 일
- 마감일
- 중요도
- 긴급도
- 예상 소요시간
- 체크리스트
- 원문 근거
- 관련 공지
- 변경 이력
- 문의 문구
- 일정 등록

# 7. 변경 공지는 어떻게 반영할 것인가

변경 공지는 서비스의 핵심 기능이므로 명확한 규칙이 필요합니다.

AI가 기존 공지와 새 공지를 비교해 변경사항을 다음 네 가지로 분류합니다.

## ① 기존 카드 수정

```text
신청 마감일
기존: 8월 20일
변경: 8월 15일
```

처리:

- 기존 카드 마감일 변경
- 긴급도 재계산
- 카드에 ‘변경됨’ 표시
- 사용자에게 알림

---

## ② 새로운 카드 추가

```text
변경 공지:
신분증 사본을 추가로 제출해야 합니다.
```

처리:

```text
새 행동카드 생성
→ 신분증 사본 제출
```

---

## ③ 기존 카드 취소

```text
변경 공지:
참가 신청서 제출은 필요하지 않습니다.
```

처리:

- 카드를 삭제하지 않음
- `취소됨` 상태로 변경
- 왜 취소됐는지 기록
- 사용자의 기존 작업 이력 보존

---

## ④ 완료한 카드 재활성화

이 경우가 중요합니다.

사용자가 이미 신청서를 제출했는데 새로운 공지에서 양식이 변경됐다고 가정하겠습니다.

```text
기존 카드: 완료
변경 사항: 새 양식으로 다시 제출 필요
```

서비스는 기존 카드를 조용히 수정하면 안 됩니다.

```text
완료한 작업에 변경사항이 발생했습니다.

기존:
이전 양식 제출 완료

변경:
새 양식으로 재제출 필요

새 행동:
□ 새 양식 다운로드
□ 다시 작성
□ 재제출
```

새 카드를 생성하거나 기존 카드를 `해야 할 일`로 다시 열어야 합니다.

---

# 8. 변경 내용을 자동 반영하되, 몰래 바꾸면 안 된다

AI가 사용자의 할 일을 자동으로 변경하면 신뢰 문제가 생길 수 있습니다.

따라서 변경 공지를 감지한 뒤 다음처럼 보여주는 것이 좋습니다.

```text
3개의 변경사항이 발견되었습니다.

✓ 마감일 변경
8월 20일 → 8월 15일

✓ 장소 변경
본관 3층 → 별관 1층

✓ 준비물 추가
신분증 사본

[변경사항 반영]
[하나씩 검토]
```

사소한 변경은 자동 반영할 수 있지만, 중요한 변경은 사용자 확인을 받는 구조가 안전합니다.

예:

- 문구 수정 → 자동 반영
- 장소 변경 → 확인 필요
- 마감일 변경 → 확인 필요
- 기존 카드 취소 → 확인 필요
- 완료한 카드 재활성화 → 확인 필요

---

# 9. AI가 우선순위를 정하는 근거를 보여줘야 한다

AI가 단순히 `중요`라고 표시하면 사용자는 믿기 어렵습니다.

따라서 각 분류에 이유를 붙여야 합니다.

```text
중요도로 분류한 이유:
공지에서 ‘필수 제출’이라고 명시되어 있으며,
미제출 시 참가가 불가능하기 때문입니다.

긴급도로 분류한 이유:
마감일까지 2일 남았습니다.
```

또한 원문 근거를 함께 표시하면 환각 문제도 줄어듭니다.

```text
원문 근거:
“신청서를 제출하지 않은 경우 교육에 참여할 수 없습니다.”
```

이 기능은 심사 발표에서도 강점이 됩니다.

> AI가 임의로 할 일을 만들어내는 것이 아니라, 공지 원문을 근거로 행동과 우선순위를 제안한다.

# 10. 예선과 결선의 기능 범위

## 예선 에이전트

예선에서는 욕심을 줄이고 다음 기능에 집중하는 것이 좋습니다.

```text
공지 입력
→ 독립된 행동카드 생성
→ 중요도·긴급도 분류
→ 원문 근거 표시
```

예선 출력 예시:

```text
총 4개의 행동카드가 생성되었습니다.

1. 참가 신청서 제출
상태: 해야 할 일
중요도: 중요
긴급도: 곧 마감
마감: 8월 15일
근거: “8월 15일까지 반드시 제출”

2. 신분증 준비
상태: 해야 할 일
중요도: 중간
긴급도: 여유 있음
실행 권장일: 행사 전날
```

상태 변경은 예선에서 대화로 표현할 수도 있습니다.

```text
사용자: 참가 신청서 제출을 완료했어.
에이전트: 해당 행동카드를 ‘완료’로 변경했습니다.
```

---

## 결선 MVP

결선에서는 예선 기능을 서비스로 확장합니다.

### 필수 기능

1. 공지 등록
2. 행동카드 자동 생성
3. 해야 할 일 / 하는 중 / 완료 보드
4. 중요도·긴급도 분류
5. 마감일에 따른 긴급도 자동 변경
6. 수정 공지 비교
7. 기존 행동카드 업데이트
8. 변경 이력 표시

### 선택 기능

- 알림
- 캘린더 연동
- 공지 이미지 또는 PDF 입력
- 가족·팀원과 공유
- 반복 공지 관리
- 문의 메시지 생성

결선 MVP에서 가장 중요한 것은 기능 개수가 아니라 다음 시나리오가 끊김 없이 작동하는 것입니다.

```text
공지 입력
→ 행동카드 생성
→ 사용자가 작업 시작
→ 상태를 ‘하는 중’으로 이동
→ 수정 공지 입력
→ 기존 카드의 마감일 변경
→ 우선순위 상승
→ 작업 완료
```

이 흐름 하나가 제대로 동작하면 서비스로서 설득력이 큽니다.

---

# 11. 이 아이디어의 진짜 차별점

단순 태스크 관리 앱과 비교하면:

> 사용자가 할 일을 직접 입력하지 않는다.  
> AI가 공지에서 해야 할 일을 발견한다.

공지 요약기와 비교하면:

> 내용을 이해하는 데서 끝나지 않고 완료까지 관리한다.

문서 비교 서비스와 비교하면:

> 변경된 문장을 알려주는 데서 끝나지 않고 기존 행동을 수정한다.

캘린더 앱과 비교하면:

> 일정뿐 아니라 제출·준비·문의·확인 같은 비일정 행동도 관리한다.

따라서 제품 포지셔닝은 다음과 같습니다.

> **공지 기반 AI 실행 관리 서비스**

또는 좀 더 대중적으로:

> **읽은 공지를 끝낸 일로 바꿔주는 AI**

---

## 현재 정리된 핵심 기능

```text
1. 공지를 행동카드로 변환한다.
2. 행동카드는 해야 할 일·하는 중·완료로 관리한다.
3. 중요도와 긴급도를 각각 분류한다.
4. 마감일이 다가오면 긴급도를 자동 조정한다.
5. 수정 공지가 오면 기존 행동카드를 업데이트한다.
6. 모든 판단에 공지 원문 근거를 표시한다.
7. 완료한 행동에 변경이 생기면 다시 알려준다.
```

이 정도면 예선의 단일 기능과 결선 MVP 사이의 연결이 매우 자연스럽습니다. 다음 단계에서는 **행동카드 데이터 구조와 예선 시연용 공지 3종**을 먼저 확정하는 것이 좋습니다.

---

### 💡 답변 (Assistant)
좋습니다. 이 방향이면 단순 공지 요약기가 아니라 **“공지 기반 실행 관리 서비스”**로 한 단계 올라갑니다. 다만 우선순위 체계를 너무 복잡하게 만들지 않도록, 상태·중요도·긴급도를 분리해서 설계하는 게 핵심입니다.

---

### ❓ 질문 (User)
이거를 노코드 에이전트 로 할 수가 있나??

### 💡 답변 (Assistant)
핵심 기능별로 나눠서 보겠습니다. **예선에서 가능한 범위**와 **결선 MVP에서 노코드만으로 버티기 어려운 부분**을 분리해 판단하겠습니다.

---

### 💡 답변 (Assistant)
가능합니다. 다만 **현재 설계 전체를 “에이전트 프롬프트 하나”로 만드는 것은 어렵고**, 예선과 결선의 구현 방식을 다르게 잡아야 합니다.

공식 안내는 예선에서 타임리 AI의 **노코드 에이전트 구현 환경**을 제공하고, 결선에서는 별도의 **온라인 서비스 빌더 교육**을 통해 실제 구동 가능한 MVP로 확장한다고 명시합니다. 코딩 지식 없이 자연어와 마우스 조작만으로 제작할 수 있다고도 안내합니다. citeturn552769view0

## 결론

### 예선

**완전히 노코드로 가능**합니다.

```text
공지 입력
→ 행동카드 분리
→ 중요도 판정
→ 긴급도 판정
→ 이전 공지가 있으면 변경사항 비교
→ 정해진 형식으로 출력
```

이 부분은 사실상 Solar LLM에 명확한 출력 규칙과 판단 기준을 주는 **단일 에이전트 스킬**입니다.

### 결선

**노코드 MVP로도 가능할 가능성이 높지만**, 일부 기능은 타임리 서비스 빌더의 실제 기능을 확인해야 합니다.

특히 다음 기능이 필요합니다.

- 행동카드 영구 저장
- 카드별 고유 ID
- `해야 할 일 → 하는 중 → 완료` 상태 변경
- 카드 수정과 삭제
- 이전 공지와 새 공지 연결
- 마감일 기준 긴급도 재계산
- 변경 이력 저장

공식 페이지에는 결선용 서비스 빌더와 교육이 제공된다고 나와 있지만, 데이터베이스·예약 실행·상태 변수 등 세부 기능은 공개 페이지에서 확인되지 않습니다. 따라서 **기획은 가능하지만 자동화 수준은 빌더 기능에 맞춰 조정해야 합니다.** citeturn552769view0

## 예선 핵심 기능

> 공지문을 사용자가 바로 실행할 수 있는 우선순위 행동카드로 변환하고, 수정 공지가 들어오면 기존 행동에 미치는 변경사항을 알려주는 에이전트

입력은 두 가지 모드를 두면 됩니다.

### 신규 공지 모드

```text
[신규 공지]

8월 15일까지 참가 신청서를 제출하고,
행사 당일 신분증과 노트북을 지참해 주세요.
```

출력:

```text
행동카드 1

제목: 참가 신청서 제출
상태: 해야 할 일
중요도: 중요
긴급도: 곧 마감
마감일: 2026-08-15
판단 이유: 미제출 시 행사 참가가 어려울 수 있음
원문 근거: “8월 15일까지 참가 신청서를 제출”

행동카드 2

제목: 신분증과 노트북 준비
상태: 해야 할 일
중요도: 중간
긴급도: 여유 있음
권장 실행일: 행사 전날
원문 근거: “행사 당일 신분증과 노트북을 지참”
```

### 변경 공지 모드

사용자가 기존 공지와 새 공지를 함께 입력합니다.

```text
[기존 공지]
8월 20일까지 신청서를 제출하세요.

[변경 공지]
제출 마감일이 8월 15일로 변경되었습니다.
신분증 사본도 함께 제출해야 합니다.
```

출력:

```text
변경 영향

1. 기존 카드 수정
- 신청서 제출 마감일
- 8월 20일 → 8월 15일
- 긴급도: 여유 있음 → 곧 마감

2. 새 카드 생성
- 신분증 사본 제출
- 중요도: 중요
- 마감일: 8월 15일

권장 조치
- 위 두 변경사항을 행동보드에 반영하세요.
```

이 정도는 **프롬프트와 출력 템플릿만으로 충분히 구현 가능**합니다.

# 결선 MVP는 이렇게 구성하면 됩니다

## 1. 공지 등록 화면

사용자가 새 공지 또는 변경 공지를 등록합니다.

```text
공지 제목
공지 내용
공지 유형: 신규 / 변경
관련 기존 공지
```

## 2. AI 분석 단계

에이전트가 구조화된 형태로 결과를 만듭니다.

```json
{
  "actions": [
    {
      "title": "참가 신청서 제출",
      "importance": "중요",
      "urgency": "곧 마감",
      "deadline": "2026-08-15",
      "status": "해야 할 일",
      "evidence": "8월 15일까지 참가 신청서를 제출"
    }
  ]
}
```

실제 코드 작성 여부와 관계없이, **출력 형식은 이렇게 구조화해야 서비스 빌더가 필드를 분리해 저장하기 쉽습니다.**

## 3. 행동보드

```text
해야 할 일        하는 중          완료
──────────       ──────────       ──────────
신청서 제출       문진표 작성       참석 회신
신분증 준비
노트북 준비
```

각 카드에는 최소 정보만 표시합니다.

```text
[중요] [곧 마감]

참가 신청서 제출
8월 15일 마감 · 2일 남음
```

## 4. 변경사항 검토 화면

변경 공지가 들어오면 기존 카드를 즉시 덮어쓰지 않고 다음처럼 보여줍니다.

```text
발견된 변경사항 2건

마감일 변경
8월 20일 → 8월 15일

새 준비물
신분증 사본 추가

[전체 반영]
[개별 검토]
```

이 방식이 노코드에서 더 쉽고, AI가 사용자의 완료 기록을 임의로 바꾸는 문제도 줄여줍니다.

# 자동화 수준을 낮추면 노코드 성공률이 올라갑니다

초기에는 다음 기능을 빼는 것이 좋습니다.

### 빼야 할 기능

- 매일 자정에 모든 카드의 긴급도 자동 계산
- 사용자의 이메일이나 메신저에서 공지 자동 수집
- 변경 공지 자동 감지
- 캘린더와 양방향 동기화
- 여러 사용자 실시간 협업
- AI가 검토 없이 완료 카드를 자동 재활성화

이 기능들은 에이전트보다 **백엔드 자동화·인증·외부 API 연동** 문제가 됩니다.

### MVP에서 대체하는 방법

| 고도화 기능 | 노코드 MVP 방식 |
|---|---|
| 매일 긴급도 자동 갱신 | 보드를 열거나 분석할 때 재계산 |
| 변경 공지 자동 탐지 | 사용자가 변경 공지 직접 등록 |
| 기존 카드 자동 덮어쓰기 | 변경 제안 후 사용자가 반영 |
| 캘린더 자동 동기화 | 캘린더 등록용 문구 또는 파일 생성 |
| 메신저 자동 수집 | 공지 복사·붙여넣기 |
| 완료 카드 자동 재활성화 | 재처리 필요 카드 제안 |

이렇게 하면 사용자 경험은 유지하면서 구현 위험은 크게 줄어듭니다.

다만 제품 정의를 다음처럼 제한해야 합니다.

> **공지에서 행동을 추출하고, 우선순위를 제안하며, 사용자가 진행 상태와 변경사항을 관리하는 서비스**

반대로 아래처럼 정의하면 순수 노코드 난도가 급격히 높아집니다.

> 모든 채널의 공지를 자동 수집하고, 변경을 실시간 감지하며, 행동카드와 알림을 자동 갱신하는 완전 자율 에이전트

따라서 **예선은 확실히 가능하고, 결선도 “사용자 확인 기반 반자동 MVP”로 설계하면 노코드로 승부할 수 있습니다.**

# 타임 트래커의 장점

타임 트래커는 사용자 풀이 확실히 넓습니다.

- 직장인
- 학생
- 프리랜서
- 개발자
- 시험 준비생
- 육아와 일을 함께 관리하는 사람

게다가 매일 사용할 수 있어 **서비스 지속성**은 행동카드보다 강합니다. 시간이 누적되면 주간·월간 분석도 가능하므로, 결선 MVP 이후의 성장 그림도 좋습니다.

```text
오늘 무엇을 했는지 기록
→ 업무별 시간 분류
→ 계획 대비 실제 시간 분석
→ 낭비 시간 발견
→ 내일 계획 추천
```

문제는 이미 타임 트래킹 서비스가 너무 많다는 점입니다.

- Toggl Track
- Clockify
- RescueTime
- Timely
- Notion 템플릿
- 각종 집중 타이머 및 포모도로 앱

단순히 다음 기능만 제공하면 공모전에서 약합니다.

```text
작업 시작 버튼
→ 시간 측정
→ 종료
→ 일일 통계
```

이건 AI 에이전트라기보다 기존 생산성 앱에 가깝습니다. 심사위원 입장에서 **“왜 Solar LLM이 필요한가?”**라는 질문이 바로 나올 수 있습니다.

# 공지 → 행동카드의 장점

공지 행동카드는 LLM이 수행해야 하는 인지 작업이 분명합니다.

```text
비정형 공지 이해
→ 사용자 행동 추출
→ 마감일·준비물 구조화
→ 중요도 판단
→ 수정 공지와 기존 카드 비교
→ 기존 행동에 미치는 영향 계산
```

즉, AI를 제거하면 서비스의 핵심 기능 자체가 사라집니다.

반면 타임 트래커는 AI를 제거해도 시간 측정 기능 대부분이 남습니다. 이 차이가 공모전에서는 중요합니다.

또 시연도 행동카드 쪽이 훨씬 선명합니다.

### 행동카드 데모

1. 복잡한 공지를 입력한다.
2. 세 개의 행동카드가 생성된다.
3. 중요도와 마감일이 정리된다.
4. 수정 공지를 입력한다.
5. 기존 카드의 마감일과 우선순위가 바뀐다.

짧은 시연에서도 **입력 전후의 변화가 극적**입니다.

### 타임 트래커 데모

1. 작업을 시작한다.
2. 시간이 흐른다.
3. 작업을 종료한다.
4. 통계를 본다.

실제 사용 가치는 있지만, 발표 현장에서 극적인 변화가 나오기 어렵습니다.

# 노코드 측면에서는

## 예선

둘 다 노코드로 가능합니다.

다만 타임 트래커의 핵심인 실제 시간 측정은 플랫폼이 다음 기능을 제공해야 합니다.

- 현재 시각 읽기
- 작업 시작 시각 저장
- 종료 시각 저장
- 경과 시간 계산
- 여러 기록 누적
- 일별 통계 계산

이 기능이 없으면 사용자가 다음처럼 직접 입력해야 합니다.

```text
10:00부터 11:20까지 알고리즘 공부했어.
```

그러면 에이전트가 80분으로 계산하고 분류하는 구조가 됩니다. 가능하지만 우리가 흔히 생각하는 자동 타이머와는 다릅니다.

공지 행동카드는 LLM 입력과 출력만으로도 예선의 핵심 가치가 완성됩니다. 그래서 **순수 노코드 예선에는 행동카드가 더 안정적**입니다.

## 결선

타임 트래커는 결선에서 다음 기능이 필요합니다.

- 타이머 상태 저장
- 백그라운드 시간 측정
- 기록 데이터베이스
- 일·주·월 통계
- 차트
- 작업 분류
- 중단·재시작 처리

공지 행동카드는 다음이 필요합니다.

- 공지 저장
- 행동카드 저장
- 상태 변경
- 마감일 정렬
- 변경 공지 비교
- 기존 카드 업데이트

둘 다 데이터 저장이 필요하지만, **타이머는 실시간 상태와 시간 계산이 필요해 노코드 구현 리스크가 조금 더 큽니다.**

# 타임 트래커가 경쟁력을 가지려면

일반적인 타임 트래커로는 부족하고, 기존 서비스가 잘 해결하지 못하는 문제를 잡아야 합니다.

예를 들어 다음 정도는 되어야 합니다.

## 1. 계획과 실제의 차이를 학습하는 에이전트

> 사용자가 예상한 작업시간과 실제 소요시간을 비교해, 다음 계획을 현실적으로 보정해 주는 에이전트

```text
예상: 보고서 작성 1시간
실제: 2시간 30분

AI 분석:
- 자료 검색에서 예상보다 50분 더 사용
- 초안 수정이 세 차례 발생
- 다음 유사 작업에는 2시간 20분 배정 권장
```

이건 단순 기록보다 훨씬 낫습니다.

## 2. 자연어 활동 기록 에이전트

> 하루 동안 한 일을 대화하듯 말하면 자동으로 활동·프로젝트·집중시간을 복원하는 에이전트

```text
오늘 오전에는 모델 오류를 잡다가 점심 먹었고,
오후 두 시부터 네 시까지 논문을 읽었어.
그 뒤에 30분 정도 영어 공부했어.
```

이를 자동으로 다음처럼 구조화합니다.

| 활동 | 분류 | 시간 | 프로젝트 |
|---|---|---:|---|
| 모델 오류 해결 | 개발 | 오전 | LLM 프로젝트 |
| 논문 읽기 | 학습 | 2시간 | ML 연구 |
| 영어 공부 | 자기계발 | 30분 | 영어 |

하지만 사용자가 정확한 시간을 말하지 않으면 추측 문제가 생깁니다.

## 3. 현실적인 하루 계획 재배치 에이전트

> 남은 시간과 작업 진행률을 보고 오늘 할 일을 자동으로 재배치하는 에이전트

```text
현재 16:00
남은 가용시간: 3시간
미완료 작업: 5개

추천:
1. 오늘 마감인 지원서 검토
2. 30분짜리 영어 학습
3. 논문 정리는 내일로 이동
```

이 역시 좋은 아이디어지만 캘린더·시간·상태 연동이 필요해서 구현 난도가 높아집니다.

# 둘을 합치는 것은 어떨까

완전히 합치면 범위가 커지므로 추천하지 않습니다. 다만 행동카드 안에 **시간 관련 필드만 제한적으로 넣는 것**은 좋습니다.

```text
행동카드
- 예상 소요시간: 20분
- 권장 시작일: 8월 12일
- 실제 소요시간: 35분
```

결선 이후에는 누적 데이터를 활용해 다음 기능으로 확장할 수 있습니다.

> 과거 완료 기록을 바탕으로 비슷한 행동의 예상 소요시간을 자동 추천

예를 들어 사용자가 과거 신청서 작성에 평균 40분이 걸렸다면:

```text
마감까지 1일 남음
예상 소요시간 40분
첨부서류 발급 예상 1일

판정: 지금 시작 필요
```

이렇게 하면 시간 관리가 행동카드의 **우선순위 판단을 강화하는 요소**가 됩니다. 별도의 타임 트래커 제품을 만드는 것보다 훨씬 자연스럽습니다.

# 최종 판단

### 공모전 주제로 하나만 고른다면

**공지 → 행동카드가 더 낫습니다.**

이유는 명확합니다.

1. AI가 필요한 이유가 분명합니다.
2. 기존 서비스와의 차별화가 쉽습니다.
3. 예선에서 결과를 바로 보여줄 수 있습니다.
4. 수정 공지 반영이라는 강한 데모 포인트가 있습니다.
5. 순수 노코드 예선 구현이 안정적입니다.
6. 결선에서 칸반형 MVP로 확장하기 자연스럽습니다.

### 서비스의 장기 사용성과 데이터 축적만 본다면

**타임 트래커가 더 좋습니다.**

하지만 수많은 기존 서비스와 경쟁하려면 단순 기록이 아니라 **계획 오차 학습, 일정 재배치, 자연어 활동 복원** 같은 강한 차별점이 반드시 필요합니다.

따라서 가장 좋은 조합은 다음입니다.

> **주력:** 공지 기반 행동관리 에이전트  
> **결선 부가기능:** 행동별 예상 소요시간과 실제 소요시간 기록  
> **향후 확장:** 사용자별 소요시간 학습과 우선순위 보정

타임 트래커를 별도 아이디어로 경쟁시키기보다, 행동카드가 **“무엇을 해야 하는가”**를 정하고 시간 정보가 **“언제 시작해야 하는가”**를 보정하도록 만드는 편이 제품 논리가 더 강합니다.

# 1. 예선 에이전트의 정확한 범위

예선 에이전트 이름을 가칭 **Notice2Action**이라고 하겠습니다.

이 에이전트는 세 가지 명령을 처리합니다.

### 신규 공지 분석

```text
이 공지를 행동카드로 바꿔줘.

[공지]
교육 참가자는 8월 15일까지 신청서를 제출하고,
행사 당일 신분증과 노트북을 지참해 주세요.
```

### 변경 공지 반영

```text
기존 행동카드에 다음 변경 공지를 반영해줘.

[변경 공지]
신청 마감이 8월 12일로 변경되었고,
신분증 사본도 함께 제출해야 합니다.
```

### 상태 변경

```text
A-001 신청서 제출 카드를 하는 중으로 바꿔줘.
```

즉, 프롬프트 하나로 모든 것을 처리하는 범용 챗봇이 아니라, **공지와 행동카드만 다루는 전문 스킬**로 제한합니다.

# 2. 에이전트 내부 구조

타임리 화면에서 실제 노드 명칭은 다를 수 있지만, 논리적으로는 다음 여섯 단계입니다.

```text
사용자 입력
   ↓
① 요청 유형 판별
   ↓
② 공지 내용 구조화
   ↓
③ 행동 단위 분리
   ↓
④ 중요도·긴급도 판정
   ↓
⑤ 기존 카드와 비교·수정
   ↓
⑥ 행동보드와 상태 데이터 출력
```

## ① 요청 유형 판별

사용자의 요청을 세 종류로 분류합니다.

```text
NEW_NOTICE
UPDATE_NOTICE
STATUS_CHANGE
```

사용자가 명확히 말하지 않아도 문맥으로 판별하되, 판별할 수 없을 때만 질문합니다.

예:

- 공지문만 입력됨 → `NEW_NOTICE`
- “수정”, “변경”, “기존 공지” 포함 → `UPDATE_NOTICE`
- “완료했어”, “시작했어”, “하는 중” → `STATUS_CHANGE`

---

## ② 공지 내용 구조화

에이전트가 먼저 다음 정보를 추출합니다.

```text
공지 제목
공지 대상
행사·업무 일시
신청·제출 마감일
장소
필수 행동
선택 행동
준비물
금지·주의사항
미확인 정보
```

중요한 규칙은 **공지에 없는 내용을 추측하지 않는 것**입니다.

예를 들어 공지에 행사 날짜가 없다면:

```text
행사 날짜: 확인되지 않음
```

이라고 출력해야 합니다.

---

## ③ 행동 단위 분리

공지 한 개가 카드 한 개가 되어서는 안 됩니다.

다음 공지에서:

```text
8월 15일까지 신청서를 제출하고,
신분증 사본을 첨부한 뒤,
행사 당일 노트북을 지참하세요.
```

세 개의 독립 카드가 생성되어야 합니다.

```text
A-001 신청서 제출
A-002 신분증 사본 첨부
A-003 노트북 준비
```

좋은 행동카드의 기준은 다음과 같습니다.

- 하나의 구체적인 동사로 표현됨
- 사용자가 독립적으로 완료할 수 있음
- 완료 여부를 판단할 수 있음
- 마감일 또는 실행 권장일을 연결할 수 있음

`교육 준비하기`처럼 모호한 카드는 피합니다.

# 3. 행동카드 데이터 구조

노코드라고 해도 내부 출력 구조는 엄격하게 정해야 합니다.

```yaml
card_id: A-001
title: 교육 참가 신청서 제출
status: 해야 할 일

importance: 중요
urgency: 곧 마감

deadline: 2026-08-15
recommended_start_date: 2026-08-12
estimated_duration: 20분

reason: 미제출 시 교육 참가가 제한될 수 있음
evidence: "8월 15일까지 신청서를 제출해 주세요."

notice_id: N-001
system_state: 정상
needs_review: false
```

각 필드의 역할은 다음과 같습니다.

| 필드 | 의미 |
|---|---|
| `card_id` | 카드 식별자 |
| `status` | 해야 할 일 / 하는 중 / 완료 |
| `importance` | 중요 / 중간 / 사소 |
| `urgency` | 곧 마감 / 중간 / 여유 있음 / 기한 초과 |
| `deadline` | 명시된 마감일 |
| `reason` | 우선순위 판단 이유 |
| `evidence` | 공지 원문 근거 |
| `system_state` | 정상 / 변경됨 / 취소됨 |
| `needs_review` | 사용자 확인이 필요한지 |

결선에서는 이 필드들을 그대로 데이터베이스 열로 사용하면 됩니다.

# 4. 중요도와 긴급도 규칙

LLM이 마음대로 판단하지 않도록 프롬프트에 규칙을 명시합니다.

## 중요도

### 중요

다음 중 하나라도 해당하면 `중요`입니다.

- 필수, 의무, 반드시 등의 표현이 있음
- 미이행 시 불이익이 명시됨
- 참가·신청·지원 자격과 관련됨
- 금전, 계약, 안전과 관련됨
- 다른 행동을 시작하기 위한 선행 조건임
- 기회를 다시 얻기 어려움

### 중간

- 해야 하지만 미이행 결과가 치명적이지 않음
- 참석 회신, 준비물 준비, 정보 확인
- 다시 처리하거나 보완할 수 있음

### 사소

- 선택 참여
- 참고자료 확인
- 만족도 조사
- 개인 편의를 위한 선택 행동

## 긴급도

기준일이 `2026-08-10`일 때:

| 남은 기간 | 긴급도 |
|---:|---|
| 0~2일 | 곧 마감 |
| 3~7일 | 중간 |
| 8일 이상 | 여유 있음 |
| 마감일 경과 | 기한 초과 |
| 마감일 없음 | 마감일 없음 |

단, 서류 발급처럼 준비 시간이 필요한 경우에는 남은 날짜가 많더라도 `곧 마감`으로 올릴 수 있습니다. 이때 반드시 이유를 표시합니다.

```text
긴급도: 곧 마감

판단 이유:
마감일까지 5일 남았지만, 제출 서류 발급에 최대 4일이 필요합니다.
```

플랫폼이 현재 날짜를 자동으로 제공하는지는 공개 페이지에서 확인되지 않으므로, 예선 버전에는 입력 필드나 대화 정보로 **기준일을 명시적으로 받는 방식**이 안전합니다. 공식 공개 페이지는 노코드 환경 제공까지 설명하지만, 변수·저장소·예약 실행 같은 세부 빌더 기능은 공개하지 않고 있습니다. citeturn166532view0turn303605view0

# 5. 데이터베이스 없이 상태를 기억하는 방법

예선에서 가장 중요한 설계입니다.

노코드 에이전트에 영구 저장소가 없다면, 매 응답 마지막에 **상태 스냅샷**을 생성합니다.

## 사용자에게 보이는 영역

```text
## 해야 할 일

🔥 A-001 교육 참가 신청서 제출
- 중요 · 곧 마감
- 8월 15일 마감

📌 A-002 신분증 사본 준비
- 중간 · 곧 마감
- 8월 15일 마감

## 하는 중

현재 진행 중인 카드가 없습니다.

## 완료

현재 완료한 카드가 없습니다.
```

## 에이전트가 다음 요청에서 재사용할 상태

```yaml
STATE_VERSION: 1
NOTICE_ID: N-001

CARDS:
  - id: A-001
    title: 교육 참가 신청서 제출
    status: TODO
    importance: HIGH
    urgency: SOON
    deadline: 2026-08-15
    system_state: ACTIVE

  - id: A-002
    title: 신분증 사본 준비
    status: TODO
    importance: MEDIUM
    urgency: SOON
    deadline: 2026-08-15
    system_state: ACTIVE
```

동일 대화에서는 에이전트가 이전 출력을 참조합니다.

새로운 대화나 세션에서도 이어가야 한다면 사용자가 상태 블록을 함께 붙여 넣습니다.

```text
이 상태에 변경 공지를 반영해줘.

[현재 상태]
...

[변경 공지]
...
```

이는 예선에서는 충분한 방식입니다. 결선에서는 이 상태 블록을 실제 테이블 저장으로 교체합니다.

# 6. 상태 변경 구현

사용자가 다음처럼 말합니다.

```text
신청서 제출을 시작했어.
```

에이전트는 기존 카드 중 가장 가까운 카드를 찾습니다.

```text
A-001 교육 참가 신청서 제출
해야 할 일 → 하는 중
```

완료 요청도 같습니다.

```text
신청서 제출 완료했어.
```

출력:

```text
✅ A-001 교육 참가 신청서 제출

상태가 ‘하는 중’에서 ‘완료’로 변경되었습니다.
완료일: 2026-08-12
```

동일한 이름의 카드가 여러 개라면 임의로 변경하지 않습니다.

```text
‘신청서 제출’ 카드가 두 개 있습니다.

A-001 교육 참가 신청서 제출
A-014 건강검진 신청서 제출

어느 카드를 변경할까요?
```

# 7. 변경 공지 반영 구현

변경 공지는 기존 카드와 새 공지를 비교해 다섯 종류의 수정 명령으로 변환합니다.

```text
CREATE
UPDATE
CANCEL
REOPEN
NO_CHANGE
```

## 마감일 변경

```text
기존: 신청 마감 8월 15일
변경: 신청 마감 8월 12일
```

결과:

```text
UPDATE A-001
deadline: 2026-08-15 → 2026-08-12
urgency: 중간 → 곧 마감
```

## 새로운 요구사항 추가

```text
신분증 사본도 함께 제출하세요.
```

결과:

```text
CREATE A-004
제목: 신분증 사본 제출
상태: 해야 할 일
```

## 기존 요구사항 취소

```text
노트북은 지참하지 않아도 됩니다.
```

결과:

```text
CANCEL A-003
system_state: 정상 → 취소됨
```

카드를 삭제하지 않는 것이 중요합니다. 그래야 변경 이력을 보여줄 수 있습니다.

## 완료 카드에 변경 발생

```text
기존 신청서를 제출했지만,
변경된 양식으로 다시 제출해야 합니다.
```

결과:

```text
A-001 기존 신청서 제출
상태: 완료 유지

A-005 변경 양식으로 재제출
상태: 해야 할 일
```

기존 완료 기록을 되돌리기보다 새 카드를 만드는 것이 더 명확합니다.

# 8. 변경사항은 바로 덮어쓰지 않는다

변경 공지를 분석한 뒤에는 먼저 제안 형태로 출력합니다.

```text
## 발견된 변경사항

1. 마감일 변경
   - 8월 15일 → 8월 12일
   - 긴급도: 중간 → 곧 마감

2. 새 제출물 추가
   - 신분증 사본

3. 준비물 취소
   - 노트북 지참 불필요

[전체 반영]이라고 입력하면 세 변경사항을 적용합니다.
[1, 2만 반영]처럼 선택할 수도 있습니다.
```

사용자가:

```text
전체 반영
```

이라고 입력해야 최종 상태를 갱신합니다.

이 방식은 노코드로 구현하기 쉽고, AI가 사용자의 할 일을 잘못 바꾸는 문제도 방지합니다.

# 9. 타임리 스킬에 넣을 핵심 지침

다음 구조를 시스템 지침으로 넣습니다.

```text
너는 공지사항을 실행 가능한 행동카드로 변환하고 관리하는
공지 기반 실행관리 에이전트다.

목표:
1. 공지에서 사용자가 직접 수행해야 할 행동을 추출한다.
2. 행동을 독립적으로 완료 가능한 최소 단위로 분리한다.
3. 각 행동에 상태, 중요도, 긴급도, 마감일을 부여한다.
4. 모든 판단에 원문 근거와 이유를 제시한다.
5. 변경 공지가 들어오면 기존 행동카드를 생성, 수정, 취소 또는
   재처리 카드 생성 방식으로 갱신한다.
6. 공지에 없는 사실은 절대로 추측하지 않는다.

지원 요청 유형:
- NEW_NOTICE: 신규 공지를 행동카드로 변환
- UPDATE_NOTICE: 기존 상태와 변경 공지를 비교
- STATUS_CHANGE: 카드 상태 변경

작업 상태:
- 해야 할 일
- 하는 중
- 완료

중요도:
- 중요
- 중간
- 사소

긴급도:
- 곧 마감: 마감일까지 2일 이하
- 중간: 3일 이상 7일 이하
- 여유 있음: 8일 이상
- 기한 초과: 마감일이 지남
- 마감일 없음: 공지에 마감일이 없음

행동 추출 규칙:
- 행동 하나에는 핵심 동사 하나만 포함한다.
- 사용자 스스로 완료 여부를 판단할 수 있어야 한다.
- 단순 정보는 행동카드로 만들지 않는다.
- 준비물은 하나의 준비 카드 또는 필요에 따라 독립 카드로 만든다.
- 선택 사항과 필수 사항을 구분한다.
- 날짜가 상대적이면 기준일을 사용해 절대 날짜로 변환한다.
- 기준일이 없으면 날짜를 추측하지 말고 사용자에게 확인한다.

변경 처리 규칙:
- 기존 카드 수정: UPDATE
- 새로운 행동: CREATE
- 더 이상 필요 없는 행동: CANCEL
- 완료 후 다시 해야 하는 행동: 새로운 재처리 카드 CREATE
- 확실하지 않은 변경: NEEDS_REVIEW
- 사용자의 확인 전에는 중요 변경을 최종 적용하지 않는다.

출력 순서:
1. 공지 핵심 정보
2. 발견된 변경사항 또는 생성된 카드
3. 해야 할 일 / 하는 중 / 완료 보드
4. 확인이 필요한 정보
5. 상태 스냅샷

항상 카드 ID를 표시한다.
항상 판단 근거가 되는 공지 원문을 표시한다.
```

여기에 **좋은 입력·출력 예시 3~5개**를 추가해야 결과가 안정됩니다.

# 10. 예선 데모 시나리오

세 가지 입력만 준비하면 됩니다.

## 데모 1: 신규 공지

긴 공지를 입력하고 여러 행동카드가 생성되는 모습을 보여줍니다.

검증 포인트:

- 필수 행동과 단순 정보를 구분하는가
- 마감일을 정확히 찾는가
- 중요도·긴급도가 타당한가

## 데모 2: 상태 변경

```text
A-001을 하는 중으로 변경해줘.
```

검증 포인트:

- 기존 카드 ID를 유지하는가
- 다른 카드가 변하지 않는가
- 보드 위치가 이동하는가

## 데모 3: 변경 공지

마감일 단축, 준비물 추가, 기존 항목 취소가 모두 포함된 공지를 입력합니다.

검증 포인트:

- 기존 카드와 연결하는가
- 새 카드만 별도로 만드는가
- 완료 기록을 훼손하지 않는가
- 우선순위를 재계산하는가

이 세 장면이면 예선 기능과 결선 확장성을 모두 보여줄 수 있습니다.

# 11. 결선에서는 무엇이 바뀌는가

예선의 상태 스냅샷을 실제 데이터 저장소로 옮깁니다.

```text
예선
대화 기록 + 상태 스냅샷
        ↓
결선
Notice 테이블 + ActionCard 테이블 + ChangeLog 테이블
```

결선 화면은 네 개면 충분합니다.

1. **공지 등록 화면**
2. **해야 할 일 / 하는 중 / 완료 보드**
3. **변경사항 검토 화면**
4. **카드 상세·원문 근거 화면**

예선에서 만든 프롬프트는 그대로 AI 분석 엔진으로 사용합니다. 결선에서는 그 출력 결과를 카드 UI와 저장소에 연결하는 것입니다.

## 가장 현실적인 구현 범위

### 예선 필수

- 공지 입력
- 원자적 행동카드 생성
- 중요도·긴급도 판정
- 원문 근거 표시
