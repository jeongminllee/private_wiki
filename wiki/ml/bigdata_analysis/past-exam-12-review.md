## 📌 [01번] 분산 데이터 처리 MapReduce 디자인 패턴 - 조인 패턴(Join Pattern)

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 빅데이터 저장 및 처리 $\rightarrow$ MapReduce 디자인 패턴
- **핵심 의도**: 서로 다른 위치에 저장된 두 데이터 세트(회원 마스터 + 주문 로그)를 공통 식별자인 `회원ID`를 키(Key)로 결합하는 분산 처리 디자인 패턴(**조인 패턴, Join Pattern**) 식별.

### 🎯 정답
**② 조인 패턴 (Join Pattern)**

### 📌 정답인 이유: [분산 환경에서의 데이터 결합 원리]
- **조인 패턴(Join Pattern)**:
  - RDBMS의 `JOIN` 연산을 하둡/맵리듀스 분산 환경에서 구현한 대표적인 디자인 패턴.
  - **Map 단계**: 서로 다른 데이터셋에서 공통 조인 키(`회원ID`)를 Key로 설정하여 `(회원ID, Value)` 쌍을 방출함.
  - **Shuffle/Sort 단계**: 동일한 `회원ID`를 가진 레코드들이 단일 Reducer 노드로 자동 그룹화되어 모임.
  - **Reduce 단계**: 모인 서로 다른 데이터셋의 레코드들을 하나의 확장된 레코드로 결합함.
- 문제에서 요구하는 작업은 “두 데이터 세트를 회원ID 키로 하나로 결합하는 것”이므로 **조인 패턴(Join Pattern)**이 정확한 정답임.

### 🔎 선지 정밀 분석: [MapReduce 4대 디자인 패턴]
1. **① 필터링 패턴 (Filtering Pattern)**: 특정 조건(예: 결제금액 $\ge 100$만원)을 만족하는 데이터만 선별/추출하거나 레코드를 제거하는 패턴 (❌).
2. **② 조인 패턴 (Join Pattern)**: 공통 Key를 기준으로 복수의 이종 데이터셋을 하나로 결합하는 패턴 (⭕ 정답).
3. **③ 요약 패턴 (Summarization Pattern)**: 수치 집계(평균, 합계, 개수, 최댓값 등)를 산출하는 통계 요약 패턴 (❌ 연령대별 평균 계산은 결합 이후의 후속 작업임).
4. **④ 메타 패턴 (Meta Pattern)**: 복합적인 비즈니스 로직 처리를 위해 여러 MapReduce 잡(Job)을 파이프라인으로 체이닝하는 상위 패턴 (❌).

### 📚 출제위원 시크릿 족보: [MapReduce 3대 핵심 디자인 패턴 비교]
| 디자인 패턴 | 대표 동작 (동사) | 주요 작업 예시 | SQL 연계 |
| :--- | :--- | :--- | :--- |
| **조인 패턴 (Join Pattern)** | **결합한다 (Merge)** | **회원 테이블 + 주문 로그 테이블 결합** | `JOIN ... ON` |
| **필터링 패턴 (Filtering)** | **거른다 (Filter/Select)** | 상위 10% VIP 추출, 불량 로그 제거 | `WHERE ...` |
| **요약 패턴 (Summarization)** | **집계한다 (Aggregate)** | 연령대별 평균 결제액, 총 매출 합계 | `GROUP BY`, `SUM()`, `AVG()` |

### 🧠 빅분기 암기 팁
- **“두 데이터셋 + 공통 Key로 붙인다 $\rightarrow$ 무조건 조인 패턴(Join Pattern)!”**
- **“필터(Filter) = 거른다 / 서머리(Summary) = 집계한다 / 조인(Join) = 붙인다!”**
- **“'연령대별 평균' 낚시어에 속지 말고 본질인 '데이터 결합 작업'을 볼 것!”** 1초 컷!

## 📌 [02번] 데이터 품질 4대 핵심 요소 - 완전성(Completeness) vs 정확성/정합성/적시성

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 데이터 거버넌스 및 품질 관리 $\rightarrow$ 데이터 품질 4대 평가 요소
- **핵심 의도**: 회원 데이터 중 '가입 연령', '요금제 코드' 등 필수 컬럼의 값이 비어 있거나 미입력된 **결측치(Missing Value, NULL, 누락)** 상태를 검증하는 데이터 품질 속성(**완전성, Completeness**) 식별.

### 🎯 정답
**③ 완전성 (Completeness)**

### 📌 정답인 이유: [데이터 품질의 4대 핵심 질문]
- **완전성 (Completeness)**:
  - 데이터베이스의 필수 입력 항목이나 레코드에 누락(결측값, NULL, 빈칸)이 없이 **"있어야 할 필수 데이터가 빠짐없이 채워져 있는가?"**를 평가하는 품질 척도.
  - 문제 지문의 "가입 연령 항목이 비어 있음(9만 건)", "요금제 코드가 아예 입력되지 않음(3만 건)"은 명백한 결측값/누락 현상이므로 **완전성(Completeness)**에 해당함.

### 🔎 선지 정밀 분석: [데이터 품질 4대 요소 완벽 대조]
1. **① 적시성 (Timeliness)**: 데이터가 요구되는 적절한 시점에 최신 상태로 제공/갱신되었는가? (❌ 시간/갱신 지연 문제).
2. **② 정합성 (Consistency)**: 서로 다른 테이블이나 시스템 간에 데이터가 모순 없이 논리적으로 일치하는가? (❌ 시스템 간 불일치 문제).
3. **③ 완전성 (Completeness)**: 필수 데이터가 누락 없이 빠짐없이 존재하는가? (⭕ 결측/NULL 검증 $\rightarrow$ 정답).
4. **④ 정확성 (Accuracy)**: 저장된 값이 실제 사실(현실 세계의 참값)과 일치하는가? (❌ 값은 있으나 틀린 오기입 문제).

### 📚 출제위원 시크릿 족보: [데이터 품질 4총사 1초 판별 질문 공식]
| 품질 요소 | 1타 강사 판별 질문 | 실제 발생 오류 사례 |
| :--- | :--- | :--- |
| **완전성 (Completeness)** | **“값이 빠짐없이 [있는가]?”** | `나이 = NULL` (미입력, 결측치 발생) |
| **정확성 (Accuracy)** | **“저장된 값이 실제와 [맞는가]?”** | 30세인데 `나이 = 300` (오기입, 왜곡된 값) |
| **정합성 (Consistency)** | **“데이터 간 내용이 서로 [같은가]?”** | 고객DB 성별='남' vs CRM 성별='여' (모순, 불일치) |
| **적시성 (Timeliness)** | **“데이터가 제때 갱신되어 [최신인가]?”** | 6개월 전 과거 주소가 여전히 남아있음 (갱신 지연) |

### 🧠 빅분기 암기 팁
- **“있나 $\rightarrow$ 완전성 / 맞나 $\rightarrow$ 정확성 / 같나 $\rightarrow$ 정합성 / 제때인가 $\rightarrow$ 적시성!”**
- **“결측치 / NULL / 빈칸 / 누락 $\rightarrow$ 1초 만에 완전성(Completeness)!”**
- **“값 없음 = 완전성 / 값 틀림 = 정확성!”**

## 📌 [03번] 프라이버시 보호 모델의 진화 - $k$-익명성, $l$-다양성, $t$-근접성, $m$-유일성

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 데이터 비식별화 및 법·제도 $\rightarrow$ 프라이버시 보호 모델 4총사
- **핵심 의도**: 개인 식별 방어 기법 중 **$m$-유일성(m-Uniqueness)**의 명칭에 담긴 함정(유일성 $\neq$ 유일하게 존재시킴)을 간파하고, $k$-익명성, $l$-다양성, $t$-근접성의 방어 메커니즘을 정확히 구별하는지 평가.

### 🎯 정답
**① $m$-유일성(m-Uniqueness) ❌ (틀린 설명)**
*(설명: 특정 속성 값이 데이터 집합 내에 유일하게 존재하도록 보장하여 개인정보를 보호한다 $\rightarrow$ 정반대 왜곡)*

### 📌 정답인 이유: [개인정보 보호의 역발상과 $m$-유일성]
- **개인정보 비식별화의 기본 철학**: 데이터 내에서 특정 개인이나 레코드가 **"단 1개로 유일하게 특정(Unique)"될 수 있다면 재식별(Re-identification) 공격에 매우 취약**해짐.
- **$m$-유일성(m-Uniqueness)의 진짜 정의**:
  - 원본 데이터의 특정 속성 조합이 비식별 데이터셋 내에서 **최소 $m$개 이상의 후보군으로 존재**하도록 보장함으로써, 공격자가 외부 지식을 결합하더라도 특정 개인 1명으로 확정할 수 없도록 방어하는 기법.
  - 따라서 ①번의 "특정 속성 값이 유일하게 존재하도록 보장한다"는 개인정보를 노출시키는 정반대의 설명이므로 오답임.

### 🔎 선지 정밀 분석: [프라이버시 4대 모델 핵심 검증]
1. **① $m$-유일성 (m-Uniqueness)**: 재식별 후보군을 최소 $m$개 이상 확보하여 유일 식별을 차단하는 모델임 (❌ 유일하게 1개만 존재시킨다는 설명은 틀림 $\rightarrow$ 정답).
2. **② $t$-근접성 (t-Closeness)**: 동질 집단 내 민감정보의 확률분포가 전체 데이터의 민감정보 분포와 거리 **$t$ 이하로 유사**하도록 유지하여 쏠림/유사성 공격을 방어 (⭕ 옳은 설명).
3. **③ $k$-익명성 (k-Anonymity)**: 동일한 준식별자(QI: 나이, 성별, 지역 등) 조합을 갖는 레코드가 **최소 $k$개 이상** 존재하도록 하여 연결 공격(Linkage)을 방어 (⭕ 옳은 설명).
4. **④ $l$-다양성 (l-Diversity)**: $k$-익명성을 만족하는 동질 집단 내에서 민감정보(질병, 소득 등)의 고유값이 **최소 $l$개 이상의 서로 다른 다양성**을 갖도록 하여 동질성/배경지식 공격을 방어 (⭕ 옳은 설명).

### 📚 출제위원 시크릿 족보: [프라이버시 모델의 3단계 계층적 진화와 취약점 방어]
$$\boxed{k\text{-익명성 (사람 수 } k\text{명)} \xrightarrow{\text{동질성 공격 방어}} l\text{-다양성 (민감값 } l\text{종류)} \xrightarrow{\text{쏠림/유사성 방어}} t\text{-근접성 (분포차 } t\text{ 이하)}}$$

| 보호 모델 | 핵심 제약 조건 | 방어하는 주 공격 유형 | 한계점 / 취약 공격 |
| :--- | :--- | :--- | :--- |
| **$k$-익명성** | 동일 준식별자 조합 **최소 $k$명** | **연결 공격 (Linkage Attack)** | **동질성 공격(전원 동일 질병), 배경지식 공격** |
| **$l$-다양성** | 그룹 내 민감정보 **최소 $l$가지** | **동질성 공격, 배경지식 공격** | **쏠림 공격(Skewness), 유사성 공격(비슷한 질병)** |
| **$t$-근접성** | 그룹 분포 ↔ 전체 분포 차이 **$t$ 이하** | **쏠림 공격, 유사성 공격** | 데이터 유용성(Utility) 손실 큼 |
| **$m$-유일성** | 재식별 후보군 **최소 $m$개 보장** | **재식별 공격 (Re-identification)** | - |

### 🧠 빅분기 암기 팁
- **“$k$ = 사람 수 $k$명 / $l$ = 민감정보 $l$종류 / $t$ = 분포 거리 $t$ 이하!”**
- **“$m$-유일성 = '유일하게 만들자(X)'가 아니라 '유일하게 1명으로 못 찍게 하자(O)'!”**
- **“동질성 공격 방어 $\rightarrow l$-다양성 / 쏠림·유사성 공격 방어 $\rightarrow t$-근접성!”** 1초 컷!

## 📌 [04번] 웹 데이터 수집 및 구조 해석 - 파싱(Parsing)과 DOM 트리

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 데이터 수집 및 비정형 전처리 $\rightarrow$ 웹 데이터 스크래핑 및 파싱
- **핵심 의도**: 비정형/반정형 HTML 문자열 문서를 태그 단위 구성 요소로 분해하고 문서 객체 모델(DOM) 계층 구조를 문법적으로 해석하는 과정(**파싱, Parsing**) 식별.

### 🎯 정답
**④ 파싱 (Parsing)**

### 📌 정답인 이유: [문자열에서 계층 구조를 만드는 과정]
- **파싱(Parsing / 구문 분석)**:
  - 컴퓨터 과학에서 일련의 문자열이나 소스코드를 정해진 **문법(Grammar) 규칙에 따라 토큰화하고 계층적인 구문 트리(Syntax Tree 또는 DOM Tree)로 변환**하는 핵심 처리 과정.
  - 웹 크롤러가 수집한 원시 HTML 코드는 단순한 문자열에 불과하지만, **HTML Parser**를 통과하면 부모-자식 간의 계층적 **DOM(Document Object Model)** 구조로 재해석되어 원하는 태그의 텍스트(상품명, 가격 등)를 정확하게 추출할 수 있게 됨.

### 🔎 선지 정밀 분석: [웹 데이터 수집/처리 관련 용어 검증]
1. **① 정형 언어 (Formal Language)**: 엄격한 문법 규칙으로 정의된 언어 체계 그 자체를 의미하며, 처리 과정/작업 명칭이 아님 (❌).

## 📌 [07번] 문서 지향 NoSQL 데이터베이스 - MongoDB의 특징(BSON, Auto-Sharding)

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 빅데이터 저장 및 관리 $\rightarrow$ NoSQL 데이터베이스 유형 및 특징
- **핵심 의도**: 오픈소스 기반으로 **BSON(Binary JSON)** 포맷의 문서(Document)를 저장하며, 유연한 스키마와 수평 확장(Scale-out)을 위한 **Auto-Sharding**을 지원하는 대표 NoSQL 제품(**MongoDB**) 식별.

### 🎯 정답
**④ MongoDB**

### 📌 정답인 이유: [MongoDB의 3대 핵심 시그니처]
- **MongoDB (몽고DB)**:
  - 대표적인 **문서 지향(Document-oriented) NoSQL 데이터베이스**.
  - **BSON(Binary JSON) 포맷**: JSON 형태의 유연한 비정형/반정형 문서를 바이너리 형태로 직렬화하여 고속 저장 및 인덱싱.
  - **유연한 스키마(Schema-less)**: 사전 고정 스키마 없이 Collection 내 Document마다 서로 다른 필드 구조 허용.
  - **Auto-Sharding**: 대용량 데이터를 다수의 노드/서버에 자동으로 수평 분산 분할(Scale-out)하여 처리 성능 확장.

### 🔎 선지 정밀 분석: [NoSQL 대표 제품군 완벽 대조]
1. **① Redis**: **Key-Value Store** 기반의 초고속 **인메모리(In-Memory)** 데이터베이스 (캐시, 세션 관리, ❌).
2. **② DynamoDB**: AWS가 제공하는 **완전관리형(Managed)** NoSQL 데이터베이스 (Key-Value/Document, ❌).
3. **③ CouchDB**: 문서 지향 NoSQL이나, BSON이 아닌 **표준 JSON 문서 및 HTTP/REST API**를 핵심 아키텍처로 사용함 (❌).
4. **④ MongoDB**: BSON, 유연한 스키마, Auto-Sharding을 갖춘 오픈소스 Document NoSQL (⭕ 정답).

### 📚 출제위원 시크릿 족보: [NoSQL 4대 데이터 모델 및 대표 제품 총정리표]
| NoSQL 데이터 모델 | 데이터 저장 구조 | 대표 제품군 | 핵심 특징 및 시험 키워드 |
| :--- | :--- | :--- | :--- |
| **Document Store** | **JSON / BSON 문서** | **MongoDB**, CouchDB | **BSON, 유연한 스키마, Sharding (MongoDB)** / **JSON+REST (CouchDB)** |
| **Key-Value Store** | **Key $\rightarrow$ Value** | **Redis**, Memcached, DynamoDB | **In-Memory 초고속 캐시/세션 (Redis)** |
| **Column Family** | **Row Key + Column Family** | **HBase**, Cassandra | **HDFS 기반 빅데이터 분산 저장 (HBase)**, 대규모 쓰기 최적화 |
| **Graph Store** | **Node + Edge (관계)** | **Neo4j**, OrientDB | 소셜 네트워크, 추천 시스템, 경로 탐색 |

### 🧠 빅분기 암기 팁
- **“BSON + Document + Sharding $\rightarrow$ 1초 만에 MongoDB!”**
- **“JSON + REST API $\rightarrow$ CouchDB!”**
- **“In-Memory + Key-Value $\rightarrow$ Redis!”**
- **“Hadoop HDFS 연계 컬럼 DB $\rightarrow$ HBase / Node+Edge $\rightarrow$ Neo4j!”**

## 📌 [08번] 하둡 분산 파일 시스템(HDFS) 아키텍처와 네임 노드(NameNode)의 단일 장애점(SPOF)

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 빅데이터 저장 기술 $\rightarrow$ HDFS(Hadoop Distributed File System) 아키텍처
- **핵심 의도**: HDFS의 핵심 구성 요소인 마스터 노드(**NameNode**)와 워커 노드(**DataNode**)의 역할 분담, 블록(Block) 분할 및 3중 복제 원리, NameNode의 **단일 장애점(SPOF, Single Point of Failure)** 특성을 정확히 이해하고 있는지 평가.

### 🎯 정답
**③ 메타데이터를 관리하는 네임 노드에 장애가 발생하면 전체 시스템이 정상적으로 동작하지 못한다 ⭕ (옳은 설명)**

### 📌 정답인 이유: [도서관 대출 목록과 서가 배치도 비유]
- **네임 노드 (NameNode = 마스터 / 도서관 검색대 & 배치도)**:
  - 파일 시스템의 네임스페이스(디렉터리 구조, 파일명)와 각 파일이 어떤 블록으로 쪼개져 어느 DataNode에 위치하는지에 대한 **메타데이터(Metadata)를 전담 관리**함.
  - DataNode에 실제 물리 데이터 블록이 온전히 보관되어 있더라도, **NameNode가 다운되면 블록의 위치와 조합 정보를 전혀 알 수 없어 클러스터 전체의 읽기/쓰기가 전면 마비**됨 $\rightarrow$ 전통적 HDFS의 대표적인 **단일 장애점(SPOF)**.

### 🔎 선지 정밀 분석: [오답 원인 정밀 파쇄]
1. **① 블록 하나의 크기를 10MB 이하로 제한한다**: HDFS는 대용량 스트리밍 처리를 위해 일반 OS보다 훨씬 큰 **기본 128MB(구버전 64MB)** 단위의 대형 블록을 사용함 (❌ 10MB 제한은 오답).
   - 💡 **큰 블록 사용 이유**: 블록 크기가 클수록 블록 개수가 줄어들어 **NameNode의 메모리 메타데이터 관리 부담과 탐색 시간(Seek Time)이 대폭 절감**됨.
2. **② 파일을 분할하지 않고 하나의 DataNode에 통째로 저장한다**: 대용량 파일을 수십~수백 개의 **블록(Block)으로 균등 분할하여 여러 DataNode에 분산 저장**함 (❌).
3. **③ NameNode 장애 시 전체 시스템 정상 동작 불가**: NameNode가 독점하는 메타데이터 없이는 파일 복원이 불가능하므로 SPOF에 해당 (⭕ 정답).
4. **④ 블록 단위 중복 저장 때문에 장애 시 복구 불가**: 노드 고장에 대비하여 동일 블록을 기본 3개 노드에 **3중 복제(Replication Factor=3)**하므로, 노드가 죽어도 다른 복제본에서 **자동 무중단 복구**됨 (❌).

### 📚 출제위원 시크릿 족보: [HDFS 3대 핵심 노드 역할 및 아키텍처 비교]
$$\boxed{\text{NameNode (지도/목록 관리, SPOF)} \longleftrightarrow \text{DataNode (실제 블록 보관, 3중 복제)} \longleftrightarrow \text{Secondary NameNode (체크포인트 병합)}}$$

| HDFS 구성 노드 | 비유 | 핵심 역할 및 특징 | 시험 빈출 함정 |
| :--- | :--- | :--- | :--- |
| **네임 노드 (NameNode)** | **도서관 검색대 (배치도)** | 파일명, 디렉터리, 블록 위치 **메타데이터 관리 (SPOF)** | 메모리(RAM)에 메타데이터 상주 |
| **데이터 노드 (DataNode)** | **실제 서가 (책 보관 창고)** | **실제 데이터 블록 물리 저장**, NameNode에 하트비트 보고 | 기본 3중 복제(Rack 인지 복제) |
| **보조 네임 노드 (Secondary NN)**| **배치도 복사 보조원** | `FsImage`와 `EditLog`를 주기적으로 병합(체크포인트) | **🚨 NameNode의 즉시 대체 백업 서버가 아님!** |

### 🧠 빅분기 암기 팁
- **“네임 노드는 지도(메타데이터, SPOF), 데이터 노드는 창고(실제 데이터 3중 복제)!”**
- **“HDFS 블록 크기는 대용량 128MB (10MB 같은 쪼잔한 크기 X)!”**
- **“보조 네임 노드는 로그 병합 비서일 뿐, 예비 반장이 아니다!”** 1초 컷!

## 📌 [09번] 하둡(Hadoop) 에코시스템과 대규모 분산 로그 수집 시스템 - Chukwa(척와)

### ✅ 문제 분석

- **핵심 의도**: 다수의 분산 웹 서버로부터 발생하는 대규모 비정형 **로그 데이터를 실시간/배치로 수집하여 HDFS에 적재**하는 데이터 수집 프레임워크인 **Chukwa(척와)** 식별.

### 🎯 정답
**② Chukwa (척와)**

### 📌 정답인 이유: [하둡 기반 분산 로그 수집 파이프라인]

  - 대규모 분산 서버 클러스터에서 발생하는 시스템 로그, 웹 서버 로그(Access/Error log) 및 모니터링 메트릭을 중앙 집중식으로 수집하여 **HDFS 및 HBase에 저장하고 MapReduce로 분석**할 수 있도록 지원하는 하둡 에코시스템의 대표적 데이터 수집 시스템.

### 📚 출제위원 시크릿 족보: [하둡 에코시스템(Hadoop Ecosystem) 핵심 도구 매칭 총정리]

## 📌 [10번] 분석 과제 발굴의 4가지 유형 - What(대상) vs How(방법) 매트릭스

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 분석 과제 발굴 $\rightarrow$ 분석 대상(What)과 분석 방법(How)의 Known/Unknown 조합
- **핵심 의도**: 분석 대상(What)과 분석 방법(How)의 인지 여부에 따라 도출되는 4대 분석 과제 유형(**최적화 Optimization, 솔루션 Solution, 통찰 Insight, 발견 Discovery**)을 정확히 매핑하는지 평가.

### 🎯 정답
**① ㄱ Optimization / ㄴ Insight / ㄷ Solution / ㄹ Discovery**

### 📌 정답인 이유: [What vs How의 4분면 매트릭스 원리]
- **분석 대상(What)**과 **분석 방법(How)**의 인지 상태에 따른 분류:
  1. **ㄱ. What(Known) + How(Known) $\rightarrow$ 최적화 (Optimization)**: 문제와 해결 방법을 모두 이미 알고 있으므로, 프로세스 효율 극대화 및 성능 튜닝에 집중.
  2. **ㄴ. What(Unknown) + How(Known) $\rightarrow$ 통찰 (Insight)**: 분석 기법(예: 연관분석, 군집분석)은 알고 있으나 어떤 패턴이 나올지 모르므로 데이터로부터 새로운 시사점 발굴.
  3. **ㄷ. What(Known) + How(Unknown) $\rightarrow$ 솔루션 (Solution)**: 해결해야 할 비즈니스 문제(예: 고객 이탈 방지)는 명확하지만 구체적 알고리즘/방법을 모르므로 해결책 모색.
  4. **ㄹ. What(Unknown) + How(Unknown) $\rightarrow$ 발견 (Discovery)**: 대상과 방법 모두 모호한 상태에서 혁신적 기회나 미지의 가치를 탐색적으로 발견.

### 📚 출제위원 시크릿 족보: [분석 과제 4대 유형 매트릭스 완벽 정리]
$$\begin{array}{|c|c|c|}
\hline
\text{분석 방법(How) } \backslash \text{ 분석 대상(What)} & \textbf{Known (기존 대상)} & \textbf{Unknown (신규 대상)} \\
\hline
\textbf{Known (기존 방법)} & \textbf{ㄱ. Optimization (최적화)} & \textbf{ㄴ. Insight (통찰)} \\
\hline
\textbf{Unknown (신규 방법)} & \textbf{ㄷ. Solution (솔루션)} & \textbf{ㄹ. Discovery (발견)} \\
\hline
\end{array}$$

### 🔎 선지 정밀 분석: [Insight vs Solution 헷갈림 방지 비법]
- **Solution (What 알고, How 모름)**: **"문제(What)는 명확하니 해결책(Solution)을 찾자!"**
- **Insight (What 모르고, How 알고)**: **"방법(How)을 돌려보니 새로운 통찰(Insight)이 나왔네!"**

### 🧠 빅분기 암기 팁
- **“둘 다 안다(아·아) $\rightarrow$ 최적화 (Optimization)!”**
- **“문제만 안다(아·몰) $\rightarrow$ 솔루션 (Solution)!”**
- **“방법만 안다(몰·아) $\rightarrow$ 통찰 (Insight)!”**
- **“둘 다 모른다(몰·몰) $\rightarrow$ 발견 (Discovery)!”** 1초 컷!

## 📌 [11번] 데이터 분석 방법론 비교 - KDD 5단계 vs CRISP-DM 6단계 및 평가(Evaluation)의 본질

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 데이터 분석 방법론 $\rightarrow$ KDD vs CRISP-DM 비교 분석
- **핵심 의도**: KDD(5단계)와 CRISP-DM(6단계)의 프로세스 진행 특성(순차적 vs 반복·순환적) 및 CRISP-DM **평가(Evaluation)** 단계가 단순 모델 성능 측정을 넘어 **비즈니스 목적 달성 여부까지 포괄**함을 파악하고 있는지 평가.

### 🎯 정답
**③ ㄱ, ㄴ**

### 📌 정답인 이유: [KDD vs CRISP-DM 핵심 비교]
- **ㄱ. KDD 5단계 (⭕ 옳음)**: `Selection(선택) → Preprocessing(전처리) → Transformation(변환) → Data Mining(마이닝) → Interpretation/Evaluation(해석/평가)`.
- **ㄴ. 프로세스 진행 방식 (⭕ 옳음)**: KDD는 비교적 순차적·단계적 파이프라인 형태인 반면, CRISP-DM은 각 단계 간 피드백 루프를 통해 전 단계로 되돌아가는 **반복적·순환적(Iterative) 프로세스**임.
- **ㄷ. CRISP-DM 평가(Evaluation) 단계의 범위 (❌ 틀림)**: 정확도·재현율 등 알고리즘의 기술적 성능뿐만 아니라, **"비즈니스 목표를 실제로 달성했는가?", "프로젝트 프로세스 전반에 누락은 없는가?"**를 종합 평가함 (`기술적 성능만 평가` $\rightarrow$ 오답 함정).
- **ㄹ. 적용 범위 (❌ 틀림)**: CRISP-DM은 **Cross-Industry**(산업 범용) 표준 방법론으로 특정 DB 환경에 한정되지 않음.

### 🔎 선지 정밀 분석: [출제위원의 낚시 키워드 분쇄]
1. **ㄱ. KDD 5단계 순서**: `선 → 전 → 변 → 마 → 평` (⭕ 옳은 설명).
2. **ㄴ. KDD(순차적) vs CRISP-DM(반복·순환적)**: CRISP-DM의 핵심 철학인 피드백 루프 반영 (⭕ 옳은 설명).
3. **ㄷ. 평가 단계는 기술적 성능만 측정한다**: 객관식 단골 오답 한정어(`~만`) 등장, 비즈니스 평가 누락 (❌ 틀린 설명).
4. **ㄹ. CRISP-DM은 특정 DB에 한정된다**: Cross-Industry(범산업) 표준에 위배 (❌ 틀린 설명).

### 📚 출제위원 시크릿 족보: [KDD vs CRISP-DM 2대 분석 방법론 총정리표]
$$\boxed{\text{KDD (5단계): 선} \rightarrow \text{전} \rightarrow \text{변} \rightarrow \text{마} \rightarrow \text{평} \quad \text{vs} \quad \text{CRISP-DM (6단계): 업} \rightarrow \text{데} \rightarrow \text{준} \rightarrow \text{모} \rightarrow \text{평} \rightarrow \text{전}}$$

| 비교 항목 | KDD (Knowledge Discovery in Databases) | CRISP-DM (Cross-Industry Standard Process) |
| :--- | :--- | :--- |
| **추진 목적** | 데이터베이스 내 숨겨진 지식/패턴 발견 | **실제 비즈니스 데이터마이닝 프로젝트 완수** |
| **전체 단계** | **5단계** | **6단계** |
| **시작 단계** | 데이터 선택 (Selection) | **업무 이해 (Business Understanding)** |
| **전처리/준비** | Preprocessing(정제) $\rightarrow$ Transformation(변환) | Data Understanding(이해) $\rightarrow$ Data Preparation(준비) |
| **핵심 모델링** | 데이터 마이닝 (Data Mining) | 모델링 (Modeling) |
| **평가 (Evaluation)** | 패턴 해석 및 평가 (Interpretation/Evaluation) | **모델 성능 평가 + 비즈니스 목표 달성도 종합 평가** |
| **최종 단계** | 평가/해석 단계에서 종료 | **전개 / 실무 배포 (Deployment)** |
| **프로세스 성격** | 비교적 순차적·단계적 파이프라인 | **단계 간 피드백 루프가 활발한 반복적·순환적 구조** |

### 🧠 빅분기 암기 팁
- **“KDD = 선 · 전 · 변 · 마 · 평 (선택 $\rightarrow$ 전처리 $\rightarrow$ 변환 $\rightarrow$ 마이닝 $\rightarrow$ 평가)!”**
- **“CRISP-DM = 업 · 데 · 준 · 모 · 평 · 전 (업무 $\rightarrow$ 데이터 $\rightarrow$ 준비 $\rightarrow$ 모델 $\rightarrow$ 평가 $\rightarrow$ 전개)!”**
- **“CRISP-DM의 평가는 '비즈니스 목표 달성'까지 본다! (~만 나온 선지는 즉시 탈락!)”** 1초 컷!

## 📌 [12번] 빅데이터 분석 기획 프로세스 - 도메인 이슈 도출과 빅데이터 요건 정의서

### 📌 정답인 이유: [문제를 찾는 단계 vs 일정을 짜는 단계]
- **도메인 이슈 도출**:
  - 분석 프로젝트 착수 전, 해당 도메인(업무 현장)의 비즈니스 프로세스와 현황을 분석하여 **"현업에서 해결해야 할 본질적인 문제가 무엇인가?"**를 명확히 정의하고, 빅데이터 분석을 통해 해결할 수 있는 **개선 방향과 기능 요건(빅데이터 요건 정의서)**을 도출하는 첫 단추 단계.
- **선택 오답 분석 (① 프로젝트 계획 수립)**:
  - '분석 수행에 앞서'라는 시점 표현만 보고 프로젝트 계획으로 오인하기 쉬우나, 프로젝트 계획 수립은 도출된 요건을 바탕으로 **일정(WBS), 투입 인력, 예산, 역할 분담(R&R)**을 수립하는 활동임.

### 🔎 선지 정밀 분석: [분석 기획 4단계 핵심 활동 대조]
1. **① 프로젝트 계획 수립**: WBS 작성, 프로젝트 범위·일정·인력·비용 배분 및 리스크 관리 계획 (❌).
2. **② 분석 목표 수립**: 발견된 이슈를 해결하기 위해 구체적인 데이터 분석 목표 및 비즈니스 KPI 설정 (❌).
3. **③ 모델 개발**: 선정된 알고리즘을 바탕으로 학습 데이터를 투입하여 실제 머신러닝/통계 모델을 구현·튜닝 (❌).
4. **④ 도메인 이슈 도출**: 업무 현황 파악 $\rightarrow$ 문제 정의 $\rightarrow$ 개선방향 도출 $\rightarrow$ **빅데이터 요건 정의서 산출** (⭕ 정답).

### 📚 출제위원 시크릿 족보: [분석 기획 4단계 프로세스 및 핵심 산출물]
$$\boxed{\text{1. 도메인 이슈 도출 (요건 정의서)} \longrightarrow \text{2. 분석 목표 수립 (목표/KPI)} \longrightarrow \text{3. 프로젝트 계획 수립 (WBS/일정)} \longrightarrow \text{4. 모델 개발 (분석 모델)}}$$

| 기획 단계 | 핵심 활동 (무엇을 하는가?) | 결정적 출제 키워드 / 대표 산출물 |
| :--- | :--- | :--- |
| **1. 도메인 이슈 도출** | **현업 업무 현황 분석, 해결 문제 정의, 개선사항 발굴** | **업무 현황, 문제 정의, [빅데이터 요건 정의서]** |
| **2. 분석 목표 수립** | 비즈니스 문제를 해결하기 위한 분석 방향 구체화 | 분석 목적, 정량적 KPI, 데이터 요구사항 |
| **3. 프로젝트 계획 수립** | 프로젝트 수행 일정, 투입 리소스 및 위험 관리 | **WBS(작업분할구조도), 일정, 인력, 예산, R&R** |
| **4. 모델 개발** | 데이터 수집/전처리 후 실제 알고리즘 모델링 | 알고리즘 선정, 하이퍼파라미터 튜닝, 검증 |

### 🧠 빅분기 암기 팁
- **“현황 파악 + 문제 정의 + 개선사항 + 요건 정의서 $\rightarrow$ 도메인 이슈 도출!”**
- **“문제를 찾는 건 '도메인 이슈', 일정을 짜는 건 '프로젝트 계획'!”**
- **“도메인 이슈(문제 발견) $\rightarrow$ 목표 수립(KPI) $\rightarrow$ 계획 수립(일정/인력) $\rightarrow$ 모델 개발(알고리즘)!”** 1초 컷!

## 📌 [13번] 빅데이터 분석 과제 우선순위 평가 - ROI 관점의 4V 분할 (3V 투자비용 vs 1V 비즈니스 효과)

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 분석 마스터플랜 $\rightarrow$ 분석 과제 우선순위 평가 및 ROI 관점
- **핵심 의도**: 빅데이터의 4V(Volume, Variety, Velocity, Value)를 투자수익률(**ROI, Return on Investment**) 관점에서 **투자비용 요소(3V)**와 **비즈니스 효과 요소(Value)**로 명확히 분리하여 이해하고 있는지 평가.

### 🎯 정답
**② 투자비용 요소에는 크기(Volume)·다양성(Variety)·속도(Velocity)와 더불어 가치(Value)가 함께 포함된다 ❌ (틀린 설명)**

### 📌 정답인 이유: [투입 비용(Cost) vs 산출 효과(Benefit)]
- **$\text{ROI} \approx \frac{\text{비즈니스 효과(Benefit)}}{\text{투자비용(Cost)}}$ 관점의 4V 분할**:
  - **투자비용 요소 (Cost / 난이도 요인)**: 데이터의 크기(**Volume**), 다양성(**Variety**), 처리 속도(**Velocity**) $\rightarrow$ 데이터 인프라, 전처리, 스트리밍 구축 등으로 인해 **비용과 난이도가 상승**하는 요인 (**3V**).
  - **비즈니스 효과 요소 (Value / 수익 요인)**: 분석을 통해 얻게 되는 매출 증대, 비용 절감, 리스크 감소 등 **기업이 창출하는 실질적 가치 (**Value**)**.
- 따라서 ②번에서 "가치(Value)까지 투자비용 요소에 포함된다"고 설명한 것은 투입과 산출을 뒤섞은 명백한 왜곡 오답임.

### 🔎 선지 정밀 분석: [오답 원인 완벽 파쇄]
1. **① 투자비용 요소는 3V로 설명할 수 있다**: Volume, Variety, Velocity는 인프라 및 구축 비용 상승 요인이므로 참 (⭕ 옳은 설명).
   - 🚨 **수험생 착각**: "빅데이터는 4V인데 왜 3V만 비용이지?"라고 오해하기 쉬우나, ROI 관점에서는 3V(비용) + 1V(효과)로 분리됨.
2. **② 투자비용 요소에 Value가 함께 포함된다**: Value는 산출되는 이익(효과)이므로 비용이 아님 (❌ 틀린 설명 $\rightarrow$ 정답).
3. **③ 비즈니스 효과 요소는 Value로 설명할 수 있다**: 분석 모델의 최종적인 비즈니스 효용을 의미함 (⭕ 옳은 설명).
4. **④ 과제 우선순위를 ROI(비용 대비 효과) 관점에서 비교한다**: 시급성(전략적 중요도)과 난이도(비용/기술)를 종합 고려하여 우선순위 도출 (⭕ 옳은 설명).

### 📚 출제위원 시크릿 족보: [빅데이터 4V의 ROI 2대 축 매핑표]
$$\boxed{\text{투자비용 (Cost) } = \textbf{3V (Volume, Variety, Velocity)} \quad \longleftrightarrow \quad \text{비즈니스 효과 (Return) } = \textbf{Value}}$$

| ROI 평가 축 | 해당 4V 요소 | 세부 의미 및 영향 |
| :--- | :--- | :--- |
| **투자비용 (Cost)** | **1. Volume (크기)** | 대용량 저장소, 분산 스토리지(HDFS), 서버 증설 비용 |
| **투자비용 (Cost)** | **2. Variety (다양성)** | 정형/비정형/반정형 데이터 통합 및 복잡한 전처리 비용 |
| **투자비용 (Cost)** | **3. Velocity (속도)** | 실시간 스트리밍(Kafka, Flink), 고성능 인프라 구축 비용 |
| **비즈니스 효과 (Return)** | **4. Value (가치)** | **수익 증대, 고객 이탈 방지, 비용 절감, 신사업 창출** |

### 🧠 빅분기 암기 팁
- **“3V(크기·다양성·속도)에는 돈이 들고(비용), Value(가치)로 돈을 번다(효과)!”**
- **“기본 특성은 4V, ROI 관점 분할은 3V(비용) + 1V(효과)!”**
- **“Value를 비용이라고 우기면 0.1초 만에 오답 탈락!”** 1초 컷!

## 📌 [15번] 빅데이터 분석 마스터플랜(Analysis Master Plan) 수립 - 우선순위 평가와 단계적 구현 로드맵

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 분석 마스터플랜 $\rightarrow$ 분석 마스터플랜의 개념, 평가 기준 및 로드맵
- **핵심 의도**: 분석 마스터플랜이 단순한 단기 과제 계획이 아니라, 전사적 관점에서 과제의 **우선순위(전략적 중요도, ROI, 실행 용이성)**를 평가하고 중장기적인 **단계적 이행 로드맵(업무, 데이터, 기술 수준 고려)**을 수립하는 활동임을 식별.

### 🎯 정답
**④ 중장기적 관점에서 분석 과제를 도출하고, 전략적 중요도·비즈니스 성과·실행 용이성 등을 고려해 우선순위를 평가한 뒤 단계적 이행 계획을 수립한다 ⭕ (가장 올바른 설명)**

### 📌 정답인 이유: [마스터플랜의 2대 핵심 축: 우선순위 평가 + 구현 로드맵]
- **분석 마스터플랜 (Analysis Master Plan)**:
  - 전사 차원의 중장기 비전과 목표 달성을 위해 도출된 다수의 분석 과제를 대상으로 **우선순위를 평가**하고, 이를 바탕으로 실행 가능한 **단계별 구현 로드맵을 체계적으로 수립**하는 종합 실행 계획.
  - **1단계 (우선순위 평가)**: 전략적 중요도(시급성), 비즈니스 성과(ROI), 실행 용이성(기술 난이도)을 종합 평가.
  - **2단계 (단계적 로드맵 수립)**: 업무 내재화 수준, 분석 데이터 범위, 분석 기술 도입 수준을 3차원으로 고려하여 단계별(1단계 $\rightarrow$ 2단계 $\rightarrow$ 3단계) 이행 계획 확정.

### 🔎 선지 정밀 분석: [오답 선지의 함정 키워드 분쇄]
1. **① 투자비용 요소인 3V만으로 우선순위를 결정한다**: 3V(비용) 외에 Value(효과), 전략적 중요도, 실행 용이성을 다각도로 검토함 (`~만` 한정 왜곡, ❌).
2. **② 단기 실행 계획만 의미하고 중장기 로드맵은 포함하지 않는다**: 마스터플랜의 본질인 전사적 중장기 로드맵을 배제하여 틀림 (❌).
3. **③ 단계적 구현 로드맵에서 업무·데이터·기술 적용 수준을 고려하지 않는다**: 업무 영역, 데이터 확보 범위, 기술 성숙도의 3대 축을 필수적으로 고려해야 함 (❌).
4. **④ 중장기 관점 + 우선순위 평가 + 단계적 이행 계획 수립**: 마스터플랜의 표준 정의 (⭕ 정답).

### 📚 출제위원 시크릿 족보: [분석 기획 3총사의 계층적 연계 파이프라인]

## 📌 [16번] AI 모델 자체 설계 시 고려사항 vs 서비스 배포/인프라 환경 구분

### ✅ 문제 분석

### 🎯 정답
**② 사용자에게 결과를 전달하는 네트워크 전송 속도 ❌ (모델 자체 설계 요소 아님)**

### 📌 정답인 이유: [모델(Model)과 시스템 인프라(Infra)의 경계]

  1. **학습 데이터의 양(규모)**: 과소적합을 방지하고 복잡한 패턴을 학습하기 위한 표본 크기.
  2. **학습 데이터의 품질(Quality)**: GIGO(Garbage In, Garbage Out) 원리에 따른 정확성, 완전성, 일관성 확보.

- **네트워크 전송 속도 (Network Latency)**:
  - 모델의 내부 학습 알고리즘이나 예측 정확도와는 무관하며, 완성된 모델을 서빙(Serving)하고 API로 결과를 표출할 때 발생하는 **서비스 배포 및 네트워크 인프라 영역의 고려사항**임.

### 🔎 선지 정밀 분석: [4대 선지 영역별 분류]
1. **① 학습에 사용할 데이터의 양(규모)**: 모델 파라미터 학습 및 일반화 성능에 직결 (⭕ 모델 설계 요소).
2. **② 사용자에게 결과를 전달하는 네트워크 전송 속도**: 서비스 배포 및 통신 인프라 요소 (❌ 모델 설계 요소 아님 $\rightarrow$ 정답).
3. **③ 학습 데이터의 품질 (정확성·완전성 등)**: 모델의 예측 신뢰성을 결정하는 최우선 요소 (⭕ 모델 설계 요소).
4. **④ 문제 유형에 적합한 알고리즘의 성능**: 분류/회귀/군집 등 태스크별 최적 모델 선정 기준 (⭕ 모델 설계 요소).

### 📚 출제위원 시크릿 족보: [AI 모델 라이프사이클 4단계 및 단계별 고려사항]
$$\boxed{\text{1. 데이터 준비 (양/품질)} \longrightarrow \text{2. 모델 설계/학습 (알고리즘)} \longrightarrow \text{3. 모델 평가 (지표)} \longrightarrow \text{4. 서비스 배포 (네트워크/서버)}}$$

| **서비스 운영 및 배포** (4단계) | **모델 서빙, API 연동, 실시간 추론 파이프라인** | **네트워크 전송 속도, 서버 CPU/GPU 인프라, 처리 지연시간(Latency)** |

### 🧠 빅분기 암기 팁
- **“모델 설계 = 데이터(양+품질) + 알고리즘(유형+성능)!”**
- **“네트워크 전송 속도는 모델 설계가 아니라 배포/인프라 환경!”**

## 📌 [17번] 빅데이터 성공적 활용의 3대 구성요소 - 자원(데이터), 기술, 인력 vs 3V 특성

## 📌 [18번] 분석 과제 우선순위 평가 기준 - 난이도(Difficulty) vs 시급성(Urgency) 2대 축

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 분석 마스터플랜 $\rightarrow$ 분석 과제 우선순위 평가 기준 (시급성 $\times$ 난이도)
- **핵심 의도**: 분석 과제를 평가하는 2대 축인 **난이도(얼마나 구현하기 어려운가?)**와 **시급성(얼마나 빨리 수행해야 하는가?)**의 세부 평가 항목을 명확히 구분할 수 있는지 평가.

### 🎯 정답
**④ 전략적 중요도와 목표 가치(KPI) 측면에서 해당 과제를 얼마나 빨리 수행해야 하는지의 정도 ❌ (난이도가 아니라 시급성 기준)**

### 📌 정답인 이유: [어려움(난이도) vs 급함(시급성)]
- **난이도 (Difficulty / 기술적·비용적 구현 제약)**:
  - 분석에 필요한 **데이터의 확보 난이도 및 비용**(①번), 데이터 정제/변환 등 **가공 노력 및 전처리 비용**(②번), 기존 업무 시스템과의 연동 및 **기술 수준과 투자 규모**(③번) 등 과제를 실제로 구현하고 운영하는 데 드는 어려움과 복잡도를 의미함.
- **시급성 (Urgency / 전략적 가치 및 시간적 긴급성)**:
  - 비즈니스 전략적 중요도, 경영 목표 가치(KPI) 달성 및 조기 성과 창출 측면에서 **"해당 과제를 얼마나 서둘러 빨리 착수·수행해야 하는가?"**(④번)를 판단하는 기준임.
- 따라서 ④번은 난이도가 아닌 **시급성**의 대표적인 정의이므로 정답임.

### 🔎 선지 정밀 분석: [오답 원인 정밀 파쇄]
1. **① 분석에 필요한 데이터의 입수 난이도와 확보 비용**: 데이터 확보 관점의 난이도 (⭕ 난이도 기준).
2. **② 데이터를 적합한 형태로 가공하는 노력과 비용**: 데이터 전처리 및 변환 관점의 난이도 (⭕ 난이도 기준).
3. **③ 업무 시스템에 적용·운영하기 위한 기술 수준과 투자 규모**: IT 시스템 연동 및 인프라 구축의 어려움 (⭕ 난이도 기준).
   - 🚨 **수험생 오답 원인**: '투자 규모'라는 표현만 보고 비즈니스 효과로 착각하기 쉬우나, '시스템 구현을 위해 얼마나 많은 기술과 투자가 드는가'라는 구축 난이도 관점임.
4. **④ 전략적 중요도와 목표 가치(KPI) 측면에서 얼마나 빨리 수행해야 하는지**: 시간적 긴급성과 전략적 가치를 나타내는 대표적 시급성 지표 (❌ 시급성 기준 $\rightarrow$ 정답).

### 📚 출제위원 시크릿 족보: [분석 과제 우선순위 2대 평가 축 매핑 총정리]
$$\boxed{\text{분석 과제 우선순위} = \textbf{시급성 (얼마나 빨리?)} \quad \times \quad \textbf{난이도 (얼마나 어렵게?)}}$$

| 평가 축 | 핵심 질문 | 세부 평가 항목 및 출제 키워드 |
| :--- | :--- | :--- |
| **시급성 (Urgency)** | **“얼마나 빨리 해야 하는가?”** | **전략적 중요도, 목표 가치(KPI), 비즈니스 긴급성, 조기 성과 창출** |
| **난이도 (Difficulty)** | **“얼마나 구현하기 어려운가?”** | **데이터 확보 난이도, 데이터 가공 노력/비용, 분석 기술 수준, 시스템 적용/투자 규모** |

### 🧠 빅분기 암기 팁
- **“어려우면 난이도(데이터 확보·가공·기술수준), 급하면 시급성(전략·KPI·빨리수행)!”**
- **“'얼마나 빨리'가 보이면 0.1초 만에 시급성 확정!”** 1초 컷!

## 📌 [19번] 빅데이터 분석 조직 체계 - 집중형 vs 기능형 vs 분산형 3대 조직 구조

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 데이터 거버넌스 $\rightarrow$ 분석 조직 및 인력 구성 3대 구조
- **핵심 의도**: 전사 차원의 **별도 분석 전담 조직**을 신설하여 분석 업무를 총괄함으로써 **전문성 축적과 표준화**에는 유리하나, 현업 부서와의 분리로 인해 **업무 우선순위 충돌 및 이원화** 위험이 있는 조직 구조(**집중형 조직 구조**) 식별.

### 🎯 정답
**① 집중형 조직 구조**

### 📌 정답인 이유: [분석 인력을 중앙에 모으는 조직 구조]
- **집중형 조직 구조 (Centralized Organization)**:
  - 전사 분석 업무를 총괄하는 **독립적인 중앙 분석 전담 조직(데이터사이언스 센터, AI연구소 등)**을 두고, 각 현업 부서로부터 분석 과제를 요청받아 전담팀이 직접 수행하는 방식.
  - **장점**: 분석 전문 인력의 집중화로 지식·노하우 축적, 분석 프로세스 및 모델의 전사 표준화, 중복 투자 방지.
  - **단점**: 현업 부서와의 물리적·조직적 분리로 인해 현업 비즈니스 이슈에 대한 신속 대응 곤란, 현업과의 우선순위 마찰 및 업무 이원화 발생.

### 🔎 선지 정밀 분석: [분석 조직 3대 구조 비교]
1. **① 집중형 조직 구조**: 중앙 전담 조직 운영, 전문성/표준화 $\uparrow$, 현업과 충돌/괴리 $\uparrow$ (⭕ 정답).
2. **② 기능형 조직 구조**: 별도 전담 조직 없이 **각 현업 부서가 자체적으로 분석 수행** (업무 이해도 $\uparrow$, 전사 관점/전문성 $\downarrow$, ❌).
3. **③ 분산형 조직 구조**: 전문 분석 인력을 **각 현업 부서에 직접 배치/파견**하여 현업 밀착형 분석 수행 (신속한 현업 대응 $\uparrow$, ❌).
4. **④ 매트릭스형 조직 구조**: 기능 관리자와 프로젝트 관리자 간의 이중 보고 체계를 갖는 일반 조직론 구조 (❌).

### 📚 출제위원 시크릿 족보: [빅데이터 분석 조직 3대 구조 완벽 비교 총정리표]
$$\boxed{\text{집중형 (중앙에 모은다)} \quad \longleftrightarrow \quad \text{기능형 (현업이 직접 한다)} \quad \longleftrightarrow \quad \text{분산형 (전문가를 현업에 배치한다)}}$$

| 분석 조직 구조 | 분석 업무 수행 주체 | 핵심 장점 (출제 시그니처) | 핵심 단점 및 한계점 |
| :--- | :--- | :--- | :--- |
| **집중형 조직 (Centralized)** | **중앙의 별도 분석 전담 조직** | **전문성 축적, 분석 프로세스 표준화, 전사 통합 관리** | **현업 부서와의 괴리, 업무 우선순위 충돌, 이원화** |
| **기능형 조직 (Functional)** | **각 현업 부서 자체 수행** | **현업 업무 이해도 최고, 즉각적 실무 반영** | **전사 관점 부재, 부서 간 중복 투자, 전문 역량 미흡** |
| **분산형 조직 (Distributed)** | **현업 부서에 파견된 분석 인력** | **현업 밀착형 분석, 신속한 현장 피드백 반영** | 전사적 분석 통제 곤란, 인력 관리 복잡 |

### 🧠 빅분기 암기 팁
- **“별도 전담 조직 + 표준화 + 현업과 충돌 $\rightarrow$ 1초 만에 집중형!”**
- **“현업이 알아서 각자 한다 $\rightarrow$ 기능형!”**
- **“전문가를 현업에 파견/배치한다 $\rightarrow$ 분산형!”**
- **“집중=중앙 집중, 기능=현업 자체, 분산=현업 파견!”** 1초 컷!

## 📌 [20번] 빅데이터 저장소 아키텍처 - 데이터 레이크(Data Lake)와 Schema-on-Read

### ✅ 문제 분석
- **출제 파트**: 제1과목 빅데이터 분석 기획 $\rightarrow$ 데이터 저장 및 인프라 $\rightarrow$ 데이터 저장소 4대 아키텍처(Data Lake, DW, DM, ODS)
- **핵심 의도**: 정형/비정형 원천 데이터를 가공 없이 **Raw 상태로 대규모 저장**하고, 읽기 시점에 스키마를 정의하는 **Schema-on-Read** 방식을 사용하며, 거버넌스 부재 시 **데이터 늪(Data Swamp)**으로 변질될 위험이 있는 저장소(**데이터 레이크, Data Lake**) 식별.

### 🎯 정답
**② 데이터 레이크 (Data Lake)**

### 📌 정답인 이유: [데이터 레이크의 3대 핵심 시그니처]
- **데이터 레이크 (Data Lake)**:
  - 정형(RDB 테이블), 반정형(JSON, XML, 로그), 비정형(이미지, 영상, 텍스트) 등 모든 형태의 방대한 데이터를 사전 가공 없이 **원천(Raw) 상태 그대로 대용량 저장**하는 중앙 저장소.
  - **Schema-on-Read**: 데이터를 적재(Write)할 때 고정 스키마를 강제하지 않고, 향후 분석가가 데이터를 조회·분석(Read)하는 시점에 비로소 스키마 구조를 동적으로 적용함.
  - **데이터 늪 (Data Swamp)**: 데이터 카탈로그 및 메타데이터 관리, 거버넌스가 부실할 경우 어떤 데이터가 어디에 존재하는지 알 수 없게 오염되는 데이터 레이크 고유의 관리 실패 위험.

### 🔎 선지 정밀 분석: [4대 데이터 저장소 비교 대조]
1. **① 데이터 웨어하우스 (Data Warehouse)**: 전사 분석 및 의사결정을 위해 정제·통합된 데이터를 사전에 정의된 구조로 저장 (**Schema-on-Write**, ❌).
2. **② 데이터 레이크 (Data Lake)**: 원천 Raw 데이터, 정형/비정형 수용, Schema-on-Read, Data Swamp 위험 (⭕ 정답).
3. **③ 데이터 마트 (Data Mart)**: 데이터 웨어하우스(DW)로부터 **특정 부서나 특정 비즈니스 주제 영역**에 맞게 구축한 소규모 맞춤형 저장소 (❌).
4. **④ 운영 데이터 저장소 (ODS)**: 여러 트랜잭션 시스템의 데이터를 통합하여 **현재/최신의 운영 업무 지원 및 실시간 질의**를 수행하는 저장소 (❌).

### 📚 출제위원 시크릿 족보: [4대 엔터프라이즈 데이터 저장소 완벽 비교표]
$$\boxed{\text{ODS (운영 최신 데이터)} \longrightarrow \text{DW (정제·통합/Schema-on-Write)} \longrightarrow \text{DM (부서별 요약)} \quad \text{vs} \quad \text{Data Lake (Raw/Schema-on-Read)}}$$

| 데이터 저장소 | 주요 저장 형태 | 스키마 적용 시점 | 주요 목적 및 특징 | 1타 강사 시험 키워드 |
| :--- | :--- | :--- | :--- | :--- |
| **데이터 레이크 (Data Lake)** | **정형 + 반정형 + 비정형 (Raw)** | **Schema-on-Read** | 탐색적 빅데이터/ML 분석, 유연한 저장 | **Raw, Schema-on-Read, Data Swamp** |
| **데이터 웨어하우스 (DW)** | 주로 정형 (정제·구조화) | **Schema-on-Write** | 전사적 BI, 정기 보고서, 의사결정 | **주·통·시·비 (주제/통합/시계열/비휘발)** |
| **데이터 마트 (DM)** | 정형 (부서별 주제 중심) | Schema-on-Write | 특정 부서(마케팅/영업) 분석 지원 | **특정 부서, 소규모 DW** |
| **운영 데이터 저장소 (ODS)** | 정형 트랜잭션 데이터 | Schema-on-Write | 운영 시스템 간 최신 데이터 통합 조회 | **현재/최신 운영 업무 지원** |

### 🧠 빅분기 암기 팁
- **“Raw 데이터 + Schema-on-Read + 데이터 늪(Data Swamp) $\rightarrow$ 무조건 데이터 레이크(Data Lake)!”**
- **“정제·통합 + Schema-on-Write + 4대 특성(주·통·시·비) $\rightarrow$ 데이터 웨어하우스(DW)!”**
- **“특정 부서 맞춤형 $\rightarrow$ 데이터 마트(DM) / 최신 운영 업무 $\rightarrow$ ODS!”** 1초 컷!
