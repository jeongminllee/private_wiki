### 💡 답변 (Assistant)
먼저 결론부터 말하면, **내용은 되게 단단하고 “실무에서 한 번이라도 맞아본 사람” 느낌이 확 나요.** 다만, 살짝만 다듬으면 훨씬 더 설득력 있고 공유하기 좋은 글이 될 것 같아요.

## 1. 당신이 적어둔 기준으로 평가해보기

### 1) Conciseness (간결성)

- ✅ 좋은 점  
  - 각 섹션이 1, 2, 3, 4로 잘 나뉘어 있고, 메시지가 분명해요.
  - 문단 길이도 크게 부담스럽지 않고, 불필요한 수다스러운 표현은 거의 없어요.
- 🔧 아쉬운 점 / 개선 포인트  
  - 서두가 약간 길게 느껴질 수 있어요.  
    > “AI Agent 만들 때 LLM API 만 연결하면 된다고요? 한 번도 evaluation을 안 해본 분일겁니다..”  
    이 부분은 임팩트는 있는데, 독자에 따라 살짝 공격적으로 느낄 수도 있어요.  
  - 같은 포인트가 살짝 반복되는 부분이 있어요. 예를 들어:
    - “ML에서의 학습과 유사하다”는 설명이 여러 표현으로 다시 등장.
    - “도메인 전문가와 함께 이터레이션”도 3번, 4번에서 비슷한 뉘앙스로 반복.

👉 **제안**  
- 인트로를 1~2문장만 더 타이트하게 정리하면 좋겠어요.
- “ML과 유사하다”, “도메인 전문가와의 이터레이션” 같은 핵심 문장은 한 번 강하게 치고, 뒤에서는 예시나 관점 추가로 보완하는 식으로 중복을 줄이면 더 날렵해질 것 같아요.

---

### 2) Relevance (관련성)

- ✅ 아주 좋음  
  - AI Agent, LLM, Vertical Domain, Evaluation — 전부 같은 축 안에서 이야기하고 있어서 주제 이탈이 없어요.
  - 실제 에이전트 만들고 있는 엔지니어에게 딱 필요한 포인트만 모아둔 느낌.
- ✅ 특히 좋았던 부분  
  - “Agent도 과적합된다”는 비유는 ML 경험자에게 강하게 와닿는 문장이고, 이 글의 핵심 메시지 중 하나로 보입니다.
  - “모든 질문에 답하려고 하지 마세요.” → 실제 프로덕트에서 겪는 문제(스코프 크리프)를 잘 찌른 문장.

---

### 3) Correctness (정확성)

- ✅ 개념적으로 자연스럽고 타당해요.
  - LLM as a Judge 메트릭들: Conciseness, Relevance, Correctness, Coherence, Harmfulness, Criminality → 실무에서 흔히 쓰이는 축과 잘 맞음.
  - Training/Test 셋 개념을 프롬프트/에이전트 튜닝에 가져오는 관점도 요즘 실무에서 많이 이야기하는 방식과 일치.
  - Garbage In, Garbage Out + 도메인 QA 셋 중요성, Vertical Domain에서의 평가 기준 명확성 등도 논리적으로 맞고 설득력 있음.
- 🔧 더 튼튼하게 만들 수 있는 부분  
  - “LLM as a Judge를 쓸 때 어떤 식으로 프롬프트를 만들었는지, 혹은 샘플 스코어 예시”가 하나라도 있으면 “아 이 사람 진짜 해봤네”가 더 강하게 느껴져요.
    - 예: 1~5점 Likert scale로 평가한다든지  
    - “Relevance가 3점인데 Correctness가 5점인 경우” 같은 사례 한 줄

---

### 4) Coherence (일관성 / 논리 구조)

- ✅ 구조 면에서 강점
  - “이 글이 하고 싶은 말” → “1~4번 포인트로 나누어 전개” → “엔지니어들에게 응원 메시지”로 마무리  
    흐름이 자연스럽고 읽기 편합니다.
  - 2, 3, 4번은 서로 잘 물려 있어요:
    - (2) Overfitting & Train/Test 개념  
    - (3) 좋은 데이터셋이 중요  
    - (4) 결국 도메인 이해도  
    이런 식으로, 모델 평가 → 데이터 → 도메인으로 점점 근본 원인 쪽으로 내려가는 구조라 좋습니다.
- 🔧 살짝 애매한 부분
  - “Vertical Domain Agent”라는 표현이 초반에 갑자기 등장하는데, Vertical에 익숙하지 않은 독자는 “도메인 특화 에이전트” 정도의 한글 설명이 바로 뒤에 붙어 있으면 좋겠어요.

---

### 5) Harmfulness / Criminality

- ✅ 전혀 문제 없음  
  - 공격적이거나 혐오 표현 X
  - 범죄 조장이나 위험한 조언 X
  - 오히려 “안전한/적절한 Agent 개발 관점”을 강조하는 글에 가깝습니다.

## 2. 글의 강점 정리

1. **실무 감각이 드러나는 포인트들**
   - “Agent도 과적합된다”
   - “평가는 결국 데이터”
   - “모든 질문에 답하려고 하지 마라”
   - “도메인 전문가도 초기엔 뭘 평가해야 할지 모른다”
   → 이 네 줄만 모아도 이 글의 신뢰도가 꽤 올라갑니다.

2. **ML 경험자에게 직관적으로 와닿는 비유**
   - 프롬프트/시스템 메세지 튜닝을 “과적합”과 연결한 것
   - Train/Test 분리 전략을 ML과 동일한 프레임으로 설명한 것

3. **톤 & 마무리**
   - “에이전트 만들고 있는 수많은 엔지니어들 화이팅입니다!”  
     이런 마무리는 LinkedIn/브런치/블로그 어디에 올려도 독자 입장에서 기분이 좋아요.

## 3. 개선하면 더 좋아질 부분 (구체 제안)

### (1) 도입부 톤/구조 살짝 다듬기

현재:
> AI Agent 만들 때 LLM API 만 연결하면 된다고요? 한 번도 evaluation을 안 해본 분일겁니다..

이렇게도 바꿀 수 있어요:

> “LLM API만 연결하면 Agent가 완성된다”고 생각하면, 거의 항상 실전에서 발목이 잡힙니다.  
> 진짜로 쓰이는 Agent를 만들려면, 결국 **ML 모델 평가하듯이 접근**해야 합니다.

→ 공격성은 줄이고, “실전에서 부딪히는 문제를 아는 사람” 느낌은 그대로 살릴 수 있어요.

---

### (2) Vertical Domain Agent 정의 한 줄 추가

> 특히 **Vertical Domain Agent(특정 산업/도메인에 특화된 에이전트)**의 평가는 이렇게 접근하는 것이 좋습니다.

이렇게 괄호 안에 짧은 설명 넣어두면, 도메인 밖 독자도 따라오기 편합니다.

---

### (3) 2번 파트에 “간단한 플로우” 추가하면 좋음

2번은 글의 핵심이라, 짧은 프로세스를 그림처럼 써주면 더 직관적입니다:

> 제가 보통 하는 방식은 이렇습니다.  
> 1️⃣ **Training 셋에 과감하게 오버피팅**시킨다.  
> 2️⃣ **Test 셋 성능을 보며**,  
>  - 시스템 프롬프트  
>  - Few-shot 예제  
>  - Tool/RAG 사용 방식  
>    중 하나씩만 수정하며 **격차를 줄여간다.**  
>   
> 이 과정은 전형적인 “ML 모델 튜닝”과 매우 비슷한 역학을 가집니다.

이렇게 정리하면, “아 이게 하나의 정형화된 워크플로우구나” 하고 읽히죠.

---

### (4) 3번 파트: Q-A 예시 한 줄만 더

지금도 메시지는 명확한데, 예시가 살짝만 들어가면 더 실감납니다.

예를 들어:

> “우리 Agent는 **보험 설계사 보조**가 목적이다”라고 하면,  
> - “실제 상담에서 자주 나오는 질문들”  
> - “절대 잘못 안내하면 안 되는 질문들(약관, 보장 범위, 면책조건 등)”  
> 을 중심으로 Q-A 셋을 구성해야 합니다.

이런 식의 1줄짜리 예시.

## 4. 한 줄 총평

- **내용**: 실무 감각 + ML 비유 + 도메인 협업 강조 → 되게 잘 잡힌 글입니다.  
- **구조**: 1–4번 나눔, 흐름 자연스럽고 논리 일관.  
- **개선 여지**: 인트로 톤 다듬기, Vertical Domain 한 줄 정의, 각 섹션에 작은 예시/플로우 추가하면 “공유해서 북마크 해두고 싶은 글”로 올라갈 것 같아요.

원하시면, 이 글을 **LinkedIn/브런치용 완성본** 느낌으로 다듬어서 전체 리라이팅 버전도 한 번 만들어줄게요.

### ❓ 질문 (User)
AI Agent 만들 때 LLM API 만 연결하면 된다고요? 한 번도 evaluation을 안 해본 분일겁니다.. 제대로 만들기 위해서는 ML 모델링하듯 평가를 접근해야 합니다. 이런 관점이 일반적인 머신러닝(ML)을 할 때의 경험이 큰 도움이 됩니다. 제가 경험하며 정리한, 특히 Vertical Domain Agent의 평가 팁은 이렇습니다.

1. LLM as a Judge: 기본기부터 확실하게, 이것만 해도 절반은 갑니다.
일반적으로 다음과 같은 지표들을 사용합니다. 다행인 점은, 이런 일반적인 지표들은 복잡한 프롬프트 엔지니어링 없이도 LLM이 꽤 잘 평가해줍니다.

- Conciseness: 답변이 간결하고 군더더기가 없는가?
- Relevance: 질문의 의도에 맞는 답변인가?
- Correctness: 사실 관계가 정확한가?
- Coherence: 답변의 논리가 일관적인가?
- Harmfulness: 유해한 내용은 없는가?
- Criminality: 범죄를 조장하지는 않는가?

2. Training 셋과 Test 셋의 분리: Agent도 '과적합'된다

"학습(Training)을 시키는 것도 아닌데 Training/Test 셋이 왜 필요해?"라고 생각하실 수 있습니다. 하지만 Agent 개발에서도 이 개념은 매우 중요합니다.

우리는 Agent의 성능을 높이기 위해 시스템 프롬프트를 깎고, Few-shot 예제를 추가하고, RAG/Tool 파이프라인을 수정합니다. 만약 준비된 데이터셋(Training Set)에만 맞춰서 프롬프트를 최적화하다 보면, 시스템 프롬프트가 해당 데이터에만 과적합(Overfitting)되는 현상이 발생합니다. 이런 역학이 ML에서의 '학습'과 유사합니다. 

결국 "우리 evaluation set에서는 다 맞췄어!"라고 자신했지만, 실제 유저들의 질문에서는 엉뚱한 대답을 하는 경우가 생깁니다.

저는 문제를 쉽게 풀기 위해서 이렇게 합니다.
 1. 일단 Training 셋에 대해 오버피팅을 시킵니다. (Test 셋에서는 성능이 떨어짐)
 2. 그 후, Test 셋과의 성능 격차를 줄이기 위해 요소를 하나씩 제거하거나 일반화합니다.

3. Garbage In, Garbage Out: 도메인 엑스퍼트와 함께 만드는 Q-A 셋의 중요성

평가의 핵심은 결국 데이터입니다. 제품의 목적에 딱 맞는 Q-A(질문-답변) 셋을 구성하는 것이 무엇보다 중요합니다.

특히 답변(Ground Truth)의 기준이 모호하면 안 됩니다. "적당히 좋은 답변" 같은 건 없습니다. 기준이 모호하다는 건 제품의 방향성이 명확하지 않다는 뜻이기도 합니다. Vertical Domain에서 이렇게 접근하면 성능을 절대 만족시킬 수 없습니다.

또한, 모든 질문에 답하려고 하지 마세요.
- 유저의 질문이 들어왔을 때, "이게 우리 Agent가 답변할 질문인가?"를 먼저 판단하는 가드레일이 필요합니다.
- 악성 케이스를 막겠다고 검증 로직을 무한정 늘리기보다는, 목적에 따라 기능을 쪼개서 평가하는 것이 성능 유지에 훨씬 유리합니다.

4. 결국은 도메인 이해도 (Domain Knowledge)

마지막으로 강조하고 싶은 건 도메인에 대한 깊은 이해입니다.
프로젝트 초기에 도메인을 제대로 이해하지 못했다면, 개발자가 혼자 끙끙대기보다 빠르게 프로토타입을 만들어 도메인 전문가와 함께 이터레이션을 돌면서 기준을 잡아가는 것이 100배 좋습니다.

재미있는 건, 프로젝트 초기에는 도메인 전문가조차 "어떤 질문과 답으로 이 Agent를 평가해야 할지" 모르는 경우가 많아요. 결국 개발자와 도메인 전문가가 함께 이터레이션을 돌며 기준을 잡아가는 과정이 필수적입니다.

사실 Agent 개발은 단순히 프롬프트 몇 줄 적는다고 뿅하고 나오지 않는 것 다들 알고 계실거에요. 에이전트 만들고 있는 수많은 엔지니어들 화이팅입니다!

이 글에 대해서 평가해줘.

### 💡 답변 (Assistant)
**AI 에이전트, 왜 이렇게 쉽게 생각하시나요**  
_“LLM API만 붙이면 끝”에서 벗어나기_

---

요즘 “AI Agent 만든다”라는 말을 정말 많이 듣습니다.  
그런데 자세히 들어보면, 실제로 하는 일은 대략 이렇죠.

> “LLM API 하나 붙이고, 시스템 프롬프트 몇 줄 써보고,  
>  예제 질문 몇 개 넣어본 다음에… 출시!”

이렇게 만들어진 Agent는 데모에서는 그럴듯해 보이지만,  
실사용 단계에 가면 금방 한계를 드러냅니다.  

이유는 단순합니다.  
**ML 모델링할 때처럼 ‘평가(evaluation)’를 진지하게 하지 않기 때문입니다.**

저는 Vertical Domain Agent(특정 산업·도메인에 특화된 에이전트)를 만들면서,  
**모델링하듯 평가하는 관점**이 얼마나 큰 차이를 만드는지 몸소 경험했습니다.  
그 과정을 정리하면, 특히 다음 네 가지 포인트로 요약할 수 있습니다.

---

## 1. LLM as a Judge: 기본기부터 꽉 잡기

LLM을 “평가자(Judge)”로 쓰는 방법은 이미 많이 알려져 있습니다.  
의외로 좋은 소식은, **한 번만 제대로 세팅해두면 여기서 퀄리티가 상당 부분 갈린다는 것**입니다.

일반적으로 이런 지표들을 많이 사용합니다.

- **Conciseness**: 답변이 불필요하게 길지 않고, 핵심만 담고 있는가?  
- **Relevance**: 질문의 의도에 정확히 맞는 내용을 다루고 있는가?  
- **Correctness**: 사실 관계가 맞는가, 헛소리는 하지 않는가?  
- **Coherence**: 앞뒤 논리가 자연스럽고 일관적인가?  
- **Harmfulness**: 유해한 표현, 차별적 표현은 없는가?  
- **Criminality**: 범죄를 조장하거나, 불법 행위를 부추기지 않는가?

다행히도, **이 정도의 일반적인 지표들은 복잡한 프롬프트 엔지니어링 없이도**  
대부분의 LLM이 꽤 안정적으로 평가를 잘 해줍니다.

실무에서는 보통 이런 식으로 씁니다.

1. 질문–답변 쌍(Q-A pair)을 여러 개 준비해두고  
2. 각 지표별로 1~5점 같은 스코어를 매기도록 LLM에게 요청한 후  
3. 평균 점수나 가중 합산 점수로 Agent 성능을 모니터링합니다.

이 단계만 제대로 돌려도  
“느낌상 좋은 것 같다”에서 **“숫자로 보이는 퀄리티 관리”**로 한 단계 올라갈 수 있습니다.

---

## 2. Agent도 ‘과적합’된다: Training / Test 셋을 꼭 나누자

여기서 많이 나오는 질문이 있습니다.

> “Agent는 학습(Training) 시키는 것도 아닌데,  
>  굳이 Training / Test 셋을 나눌 필요가 있을까요?”

제 답은 **“네, 꼭 필요합니다.”** 입니다.

에이전트 성능을 높이기 위해 우리는 계속해서 이런 작업을 합니다.

- 시스템 프롬프트를 조금씩 다듬고  
- Few-shot 예제를 더 넣거나 바꾸고  
- RAG 쿼리 방식과 Tool 호출 로직을 바꾸고

이 과정은 겉으로 보기엔 “프롬프트 수정” 같지만,  
실제로는 **준비해둔 데이터셋에 Agent를 점점 맞춰가는 과정**,  
즉 **ML에서 말하는 ‘과적합(Overfitting)’과 매우 유사한 역학**을 가집니다.

그래서 저는 보통 이렇게 접근합니다.

> 1️⃣ **일단 Training 셋에 과감하게 오버피팅시킵니다.**  
>   - “이 데이터에 대해서만큼은 정말 말도 안 되게 잘 맞추자”에 집중합니다.  
> 2️⃣ 그러면 자연스럽게 Test 셋에서는 성능이 떨어집니다.  
> 3️⃣ 그 다음부터는  
>   - 시스템 프롬프트  
>   - Few-shot 예제  
>   - RAG/Tool 사용 방식  
>   을 **하나씩 일반화·정리**하면서  
>   Training / Test 성능 간 격차를 줄이는 방향으로 반복합니다.

이 과정을 거치면,  
“우리 eval 셋에서는 다 맞췄는데, 실제 유저 질문에는 계속 헛다리 짚는다”는  
전형적인 실패 패턴을 많이 줄일 수 있습니다.

---

## 3. Garbage In, Garbage Out:  
### 도메인 전문가와 함께 만드는 Q-A 셋이 전부다

결국 평가의 핵심은 **데이터 그 자체**입니다.  

아무리 LLM as a Judge 세팅을 잘해도,  
**Q-A 셋이 제품 목적과 어긋나 있으면 Agent도 그 방향으로 끌려갑니다.**

### 3-1. “적당히 좋은 답변”은 없다

Vertical Domain에서 특히 중요한 점은,  
**답변(Ground Truth)의 기준이 애매하면 안 된다는 것**입니다.

- “이 정도면 괜찮지 않아요?”  
- “이 답도 틀린 건 아닌데…”  

이런 상태로는 결코 만족스러운 Agent가 나오지 않습니다.  
기준이 모호하다는 것은 곧 **제품의 방향성도 모호하다**는 뜻이니까요.

가능하다면 도메인 전문가와 함께 이런 기준을 맞춰가야 합니다.

예를 들어,  
보험 설계사 보조 Agent를 만든다고 해보겠습니다.

- **반드시 정확해야 하는 질문**  
  - 보장 범위, 예외 조건, 해지 시 불이익 등  
- **약간은 유연해도 되는 질문**  
  - 말투, 상담 진행 방식, 예시 설명 등  

이렇게 **“어디까지가 절대선인지”를 먼저 정의**해두면,  
Q-A 셋을 만드는 방향이 훨씬 명확해집니다.

### 3-2. 모든 질문에 답하려고 하지 마세요

또 한 가지 중요한 점은,  
**에이전트가 “모든 질문에” 답하려고 해서는 안 된다는 것**입니다.

- 유저의 질문이 들어왔을 때,  
  → “이게 우리 Agent가 답변해야 할 질문인가?”를 먼저 판단하는 **가드레일**이 필요합니다.
- 악성 케이스/엣지 케이스를 막겠다고  
  계속해서 검증 로직을 덕지덕지 붙이다 보면,  
  유지보수도 어렵고 성능도 오히려 떨어집니다.

경험상,  
**“모든 걸 다 하는 하나의 Agent”보다는  
“목적에 따라 기능을 쪼개서 평가하고 운영하는 Agent 여러 개”가  
훨씬 안정적이고 성능 관리도 쉽습니다.**

---

## 4. 결국은 도메인 이해도(Domain Knowledge)의 싸움

마지막으로, 제가 가장 강조하고 싶은 부분입니다.

> **Agent 개발의 성패는 결국 도메인 이해도에서 갈립니다.**

재미있는 건,  
프로젝트 초기에 **도메인 전문가조차** 이런 말을 한다는 겁니다.

- “어떤 질문으로 Agent를 평가해야 할지 잘 모르겠어요.”  
- “어디까지를 자동화하고, 어디부터는 사람에게 넘겨야 할까요?”

이건 이상한 일이 아닙니다.  
처음부터 “완벽한 기준”을 알고 있는 경우가 오히려 드뭅니다.

그래서 저는 이렇게 하는 편입니다.

1. 빠르게 프로토타입 Agent를 하나 만든 뒤  
2. 도메인 전문가와 함께 직접 써보면서  
3. “이 질문은 꼭 잘 답해야 한다”, “이런 건 아예 답하지 말자” 같은 기준을  
   **실제 사용 경험을 통해 차근차근 쌓아갑니다.**

개발자가 혼자 책상 앞에서 끙끙대기보다,  
**도메인 전문가와의 이터레이션을 짧은 주기로 반복하는 것**이  
체감상 정말로 **“100배 효율적”**입니다.

---

## 마치며: 프롬프트 몇 줄로는 안 되는 일

사실 우리 모두 알고 있습니다.

> “에이전트 개발은 프롬프트 몇 줄 적어놓고 뿅 하고 끝나는 일이 아니다”라는 것을요.

그렇다면 다음 정도는 **당연히** 따라와야 합니다.

- LLM as a Judge로 **지표를 정의하고**,  
- ML 모델처럼 **Training / Test 셋을 나누고**,  
- 도메인 전문가와 함께 **Q-A 셋과 기준을 다듬고**,  
- 실제 유저 질문과의 갭을 줄이기 위해 **계속해서 이터레이션**하는 작업.

겉으로 보기엔 번거롭고 느린 것 같지만,  
결국 이 과정을 거친 Agent가 **실전에서 오래 살아남습니다.**

AI Agent 만들고 있는 수많은 엔지니어 분들,  
오늘도 고생 많으십니다.  

**“API 한 번 붙이면 끝” 같은 허상을 지나,  
진짜로 현장에서 쓰이는 Agent들을 더 많이 같이 만들어갔으면 좋겠습니다.**
