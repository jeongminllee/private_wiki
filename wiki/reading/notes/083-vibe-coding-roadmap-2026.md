# 한눈에 보기

이 글은 하나의 기술 강좌가 아니라 최근 바이브 코딩 관련 기사들을 네 단계로 연결한 읽기 안내서다. “누구나 개발자가 된다”와 “개발자가 사라진다” 사이의 논쟁보다, 실제 사용 과정에서 명세·검증·운영 책임이 어떻게 변하는지를 살피는 데 가치가 있다.

# 네 단계

1. **현황 파악**: 비개발자가 아이디어를 구현하는 사례와 신입 개발자에게 AI 도구 활용이 요구되는 변화를 함께 본다.
2. **실무 사용**: Claude로 코드를 배포한 교훈, 실무 입문법, 베테랑 개발자의 경험과 기획자의 Antigravity 사용기를 비교한다.
3. **새로운 문제**: 빠르게 생성한 코드의 정리 비용, 비개발자가 만든 결과물을 개발자가 유지보수할 때 생기는 맥락과 품질 문제를 다룬다.
4. **도구와 미래**: 추천 도구 일곱 가지, 한국 개발자의 도구 사례와 “읽지 않은 코드를 배포한다”는 OpenClaw 창시자의 관점을 통해 개발자의 역할 변화를 묻는다.

# 실무 로드맵으로 바꾸기

첫 단계는 작은 내부 도구 하나를 만들어 문제 정의와 배포를 경험하는 것이다. 다음에는 acceptance criteria, test, lint, type check와 review 기준을 붙인다. 이후 실제 사용자의 feedback과 운영 log를 모아 수정하고, 마지막으로 자신이 이해하지 못한 dependency·권한·data migration을 자동화 범위에서 제외한다.

# 주의할 점

큐레이션은 2025년 말부터 2026년 초의 담론을 잘 보여주지만 보편적인 학습 순서는 아니다. 도구 이름은 빠르게 바뀌고, 생성 속도가 제품 가치나 유지보수성을 자동으로 보장하지 않는다. 따라서 “어떤 도구를 쓰는가”보다 요구를 명확히 쓰고 결과를 검증하고 운영 책임을 질 수 있는가를 기준으로 읽어야 한다.
