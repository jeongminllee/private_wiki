# 한눈에 보기

저자는 과거에는 자신이 “해커이지 엔지니어가 아니다”라는 말을 들었고, 이제는 에이전트에게 프롬프트를 주는 방식이 새로운 엔지니어링이라는 말을 듣는 상황을 아이러니하게 연결한다. 소프트웨어는 결정적이고, 이해 가능하며, 효율적이어야 한다는 오래된 가치가 비결정적 모델 중심 개발에서 약해질 수 있다고 우려한다.

# 핵심 문제 제기

컴파일러, 타입 시스템, 사람이 이해한 코드처럼 명시적 규칙을 선호하는 관점에서 보면 확률적 모델이 결정적 프로그램을 대량 생산하는 흐름은 역설적이다. 결과가 동작하더라도 팀이 왜 동작하는지 설명하지 못하고, 수정할 때마다 다시 생성해야 한다면 유지보수성과 소유권이 약해진다.

에세이는 “소프트웨어 엔지니어링”이라는 이름이 도구 유행에 따라 넓어지는 것도 비판한다. 프롬프트와 에이전트 관리가 실제로 설계, 증거, 책임을 포함하는지 아니면 결과를 운에 맡기는 행위인지 묻는다.

# 읽을 때 가져갈 질문

- 같은 입력과 환경에서 빌드와 테스트를 재현할 수 있는가?
- 생성된 핵심 로직을 팀이 설명하고 고칠 수 있는가?
- 모델을 제거해도 명세, 테스트와 운영 지식이 남는가?
- 빠른 생성이 장기 변경 비용과 장애 복구 시간까지 줄였는가?
- 도구가 사라질 때 개발자의 판단과 기술이 유지되는가?

# 주의할 점

이는 실험 보고서가 아니라 개인적·철학적 에세이다. AI가 만든 코드는 본질적으로 유지보수할 수 없다는 증거로 사용할 수 없다. 대신 낙관적인 생산성 주장에 결정성, 이해 가능성, 책임이라는 평가 축을 보태는 반대편 관점으로 읽는 것이 좋다.
