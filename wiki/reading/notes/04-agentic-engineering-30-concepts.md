# 한눈에 보기

특정 프레임워크 사용법보다 에이전트를 안정적으로 만드는 반복 가능한 개념을 익히자는 글이다. 에이전트를 `생각-행동-관찰` 루프로 보고, 컨텍스트·상태·도구·오케스트레이션·가드레일·관측성을 하나의 시스템으로 묶는다.

# 핵심 내용

- 프로젝트 규칙 파일은 길게 쌓기보다 짧고 구체적인 판단 기준으로 유지한다.
- 프롬프트 캐시는 비용을 줄이지만 오래된 컨텍스트가 판단을 흐리는 문제까지 해결하지는 않는다.
- 상태는 어디에 저장하느냐가 중요하다. 파일은 사람이 읽고 diff할 수 있어 많은 코딩 작업에서 좋은 기본값이다.
- 복잡한 작업은 하위 에이전트와 격리된 작업 공간으로 나누되, 권한·샌드박스·훅·프롬프트 인젝션 방어를 함께 설계한다.
- 비용, 토큰, 지연 시간은 대리 지표다. CI 통과, PR 병합, 배포 성공처럼 실제 결과를 별도로 측정해야 한다.

# 왜 읽을 만한가

도구 이름이 빠르게 바뀌어도 남는 설계 질문을 한 번에 훑을 수 있다. 특히 "에이전트가 성공했다고 말한 것"과 "검증 가능한 성공"을 구분하라는 조언이 실무적으로 중요하다.

# 적용 아이디어

- 에이전트 작업 정의에 종료 조건과 검증 명령을 함께 적는다.
- 상태 파일과 실행 로그를 사람이 검토 가능한 형식으로 남긴다.
- 토큰 절감과 별개로 테스트 통과율, 수정 재작업률, 사용자 승인률을 추적한다.

# 주의할 점

논문이나 표준이 아니라 경험 기반의 실무 가이드다. 개념 지도를 얻는 데는 좋지만 보안이나 평가 설계를 확정할 때는 각 분야의 원 자료를 추가로 확인해야 한다.
