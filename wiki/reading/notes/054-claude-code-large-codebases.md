# 한눈에 보기

가이드는 거대한 저장소 전체를 한 번에 모델 컨텍스트에 넣기보다, 작업 시점에 파일 검색·참조 탐색·테스트로 필요한 맥락을 가져오는 방식을 권한다. 성능은 모델만이 아니라 저장소 지침, 검색 도구, 작업 범위와 검증 루프를 어떻게 구성하느냐에 크게 좌우된다.

# 구성 원칙

- 작업과 가까운 하위 디렉터리에서 시작해 탐색 공간을 줄인다.
- 루트와 하위 폴더의 `CLAUDE.md`에는 변하지 않는 명령, 구조, 제약만 얇게 둔다.
- hook, skill, plugin, MCP는 반복되는 절차와 외부 시스템 접근을 명시적으로 만든다.
- LSP는 정의·참조·타입 관계를, 텍스트 검색은 정확한 문자열과 빠른 후보 탐색을 맡긴다.
- 서로 독립적인 조사에는 서브에이전트를 쓰고, 최종 변경의 범위와 검증은 한곳에서 통합한다.
- 생성 파일과 대형 산출물을 탐색에서 제외하고 좁은 테스트와 린트를 먼저 실행한다.

# 실무 적용

저장소 지도를 짧게 만들고 서비스 경계, 주요 진입점, 테스트 명령을 링크한다. 에이전트가 자주 틀리는 규칙만 지침에 추가하며, 3~6개월마다 오래된 내용을 걷어낸다. 팀에서는 설정의 담당자를 두고 에이전트가 실제로 어떤 파일과 도구를 사용했는지 관찰한다.

# 다른 관점

원문은 실시간 검색이 중앙 임베딩 인덱스의 stale 문제를 피한다고 강조한다. 그러나 `grep`만으로 동적 호출, 타입 관계와 영향 범위를 항상 이해할 수 있는 것은 아니다. [CodeGraph](052-codegraph-code-knowledge-graph.md)처럼 사전 인덱스를 쓰는 접근과 대립시키기보다 저장소 크기와 질문 종류에 맞춰 조합해야 한다.
