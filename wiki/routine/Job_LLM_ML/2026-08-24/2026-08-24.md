이번 공고의 핵심은 NAVER Cloud 자체 LLM의 **Post-training(SFT·강화학습)과 Evaluation**입니다. 실제 업무가 Self-Evolve 실험 설계, LLM benchmark 실행, 오답 유형 분석, 검색 기반 synthetic-data 생성, Rule filter + **LLM Judge**를 이용한 데이터 품질 검증 자동화, 학습 전후 성능 비교까지 이어집니다. 즉 단순 데이터 정제 인턴이 아니라 **모델의 약점을 찾아 → 데이터를 만들고 → 학습시키고 → 실제 성능이 개선됐는지 다시 측정하는 역할**입니다. ([Naver Cloud Corp Recruiting][1])

자격·우대사항도 이번 채용 알림 조건과 거의 정확히 일치합니다. **Python, PyTorch/TensorFlow/Transformers**, LLM 프로젝트 경험을 기본으로 요구하고, **LLM fine-tuning, `lm-eval-harness`, RLHF/RLVR 논문 재현, GitHub 공개 프로젝트, 데이터 품질 분석과 실험 문서화**를 명시적으로 우대합니다. ([Naver Cloud Corp Recruiting][1])

### 왜 특히 잘 맞는가

현재 가진 **Python·PyTorch·Hugging Face Transformers 경험과 모델 평가·벤치마크에 대한 관심**을 가장 직접적으로 사용할 수 있는 공고 중 하나입니다. 특히 지금 참여하고 있는 benchmark 작업에서 **외부 조건을 통제하고 특정 변수를 바꿔 결과를 비교하는 방식** 자체가 NAVER Cloud 팀이 말하는 실험 문화와 잘 맞습니다. 공식 JD에서도 “가설을 세우고 작은 실험으로 빠르게 검증하며, 실패한 실험도 기록한다”고 명시합니다. ([Naver Cloud Corp Recruiting][1])

또한 학부 전공을 AI/CS로 제한하지 않고 **학사 기졸업자를 명시적으로 허용**합니다. 다른 LLM Research Intern처럼 현재 석·박사 재학생이어야 한다는 조건도 없습니다. 경력 전환 과정에서 형식적 자격 때문에 걸러질 가능성이 상대적으로 낮다는 점이 상당히 중요합니다. ([Naver Cloud Corp Recruiting][1])

그리고 이 포지션은 장기적으로 LLM Training과 ML Infra 양쪽으로 확장하기도 좋습니다. `benchmark → synthetic data → post-training → evaluation harness`를 경험하면 이후 **LLM Training Engineer, Evaluation Engineer, Model Quality Engineer** 포지션으로 바로 연결할 수 있고, 평가 자동화 규모가 커지면 ML Platform/MLOps 방향으로도 이어집니다.

### 부족할 가능성이 높은 부분

가장 큰 간극은 **LLM post-training을 실제로 끝까지 수행한 증거**입니다. PyTorch나 Transformers 사용 경험만으로는 경쟁력이 충분하지 않을 수 있습니다. 특히 우대사항에 `fine-tuning`, `lm-eval-harness`, `RLHF/RLVR 논문 재현`이 직접 명시되어 있으므로, 이 중 최소 하나는 GitHub에서 확인할 수 있는 형태가 좋습니다. ([Naver Cloud Corp Recruiting][1])

두 번째는 **synthetic-data quality evaluation**입니다. 단순히 GPT로 데이터를 생성한 것보다 어떤 rule로 필터링했고, LLM Judge 결과를 어떻게 검증했으며, 그 데이터가 실제 downstream benchmark를 얼마나 올렸는지 보여주는 것이 중요합니다.

오픈소스 기여 역시 우대사항입니다. 반드시 큰 PR일 필요는 없지만 `lm-eval-harness`, Transformers 같은 프로젝트의 issue reproduction, test, documentation PR이라도 하나 있다면 차별화 요소가 됩니다. ([Naver Cloud Corp Recruiting][1])

### 지원 전에 가장 효과적인 준비

마감이 **8월 26일 18:00**이라 큰 프로젝트를 새로 만드는 것은 권하지 않습니다. 지금 가진 결과를 **작은 Evaluation → Improvement Cycle** 하나로 정리하는 편이 훨씬 좋습니다.

예를 들어 공개 3B~7B LLM 하나에 50~200문항의 소형 평가셋을 만든 뒤 `baseline → lm-eval 또는 자체 harness 평가 → 오답 분류 → 취약 유형 synthetic data 생성 → LoRA/SFT → 동일 benchmark 재평가`까지 연결하세요. 결과는 단순 최종 점수뿐 아니라 **카테고리별 accuracy 변화, 개선된 문제/악화된 문제, 데이터 개수, seed, generation configuration**을 기록하는 것이 좋습니다.

여기에 synthetic data를 `rule filter → LLM Judge → 최종 selection`으로 거르고, Judge가 맞게 평가했는지 사람이 일부 표본을 확인해 **Judge-human agreement**까지 계산하면 이번 JD와 상당히 정확하게 대응됩니다.

GitHub README의 메시지는 한 문장으로 명확해야 합니다.

**“LLM의 실패 유형을 benchmark로 발견하고, 해당 실패를 겨냥한 synthetic training data를 구축하여 fine-tuning 후 성능 변화를 재현 가능하게 검증했다.”**

이 공고에는 특히 강한 문장입니다.

현재 공식 페이지에서 지원 가능하며 **마감까지 이틀 정도밖에 남지 않았습니다.** 오늘 확인한 글로벌 후보 중에는 기술적으로 맞는 공고들이 있었지만, 현재 재학생 필수·미국 내 취업자격·지역 거주 조건 또는 높은 경력 조건 때문에 이번 알림 기준을 넘는 신규 후보는 추가하지 않았습니다.
