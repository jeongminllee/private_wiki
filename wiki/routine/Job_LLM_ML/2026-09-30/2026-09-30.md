### 1. Upstage — AI Engineer Internship · LLM Inference

이건 현재 준비 중인 포트폴리오와 **거의 정면으로 일치하는 공고**입니다. [Upstage AI Engineer Internship - LLM Inference 지원 페이지](https://app.superpasshr.com/positions/14425237-c70c-4410-a37f-7e428b62fbc9?utm_source=chatgpt.com)

현재 진행해온 **B200 + vLLM TP1/TP2 benchmark**가 이 JD에 사실상 그대로 대응합니다. 지금 측정하고 있는 `TTFT, TPOT, throughput, request/s, p99 latency, GPU memory/utilization`은 Upstage가 말하는 latency·throughput·cost 최적화 문제의 핵심 지표입니다. 또한 Python, Linux 환경과 실제 대규모 GPU 사용 경험도 강한 연결점입니다. Upstage는 우대사항에 **대규모 GPU cluster 경험, vLLM/SGLang/TensorRT-LLM/Transformers, CI/CD, AI 모델 연구·개발 경험**까지 적고 있습니다. [SuperpassHR](https://app.superpasshr.com/positions/14425237-c70c-4410-a37f-7e428b62fbc9)

현재 가장 부족한 부분은 **serving runtime 내부를 직접 수정한 경험**입니다. vLLM을 이용해 벤치마크하는 것과 scheduler, KV-cache management, kernel, distributed communication 병목을 코드 수준에서 추적하는 것은 한 단계 차이가 있습니다. GPU programming/compiler 경험과 vLLM/SGLang 오픈소스 contribution도 아직 강한 증거는 아닙니다. 또 필수사항에 **한국어 및 영어 능통**을 명시하고 있어 기술 설명 영어도 변수입니다. [SuperpassHR](https://app.superpasshr.com/positions/14425237-c70c-4410-a37f-7e428b62fbc9)

지원 전에는 프로젝트를 새로 만들지 말고 B200 실험을 **연구형 보고서로 마감**하는 것이 가장 효과적입니다. `TP1 vs TP2 × concurrency 1/8/32` 결과에서 단순 성능 비교를 넘어서 **prefill-bound / decode-bound / communication overhead** 가설을 세우고, GPU utilization과 결과를 연결하세요. 가능하면 `256→128` 고정 workload 외에 **prefill-heavy와 decode-heavy workload 각각 1개**를 추가하면 JD와 훨씬 가까워집니다. 마지막으로 benchmark 실행을 shell/Python script와 결과 JSON→표 생성까지 자동화하면 Upstage가 요구하는 benchmark CI와도 연결할 수 있습니다.

이 공고는 현재 기준으로 **FuriosaAI AI System Researcher와 함께 LLM Serving/ML Systems 축의 최우선 지원 대상**으로 보겠습니다.

### 2. Upstage — AI Research Engineer · LLM Eval Internship

두 번째는 현재 커리어 방향에서 **Evaluation Engineer / Research Engineer 쪽으로 매우 좋은 포지션**입니다. 공고는 2026년 8월 27일 게시됐고 경력 무관, 정규직 전환형 인턴, 상시채용으로 확인됩니다. [직행](https://zighang.com/recruitment/a6c86192-eac2-4576-8c34-165fdaaa3e93?utm_source=chatgpt.com)

[Upstage LLM Eval Internship 공식 지원 페이지](https://careers.upstage.ai/ko/o/194889?utm_source=chatgpt.com)

LLM Eval 팀은 **LLM benchmark와 evaluation toolkit을 직접 연구·개발**합니다. 기존 benchmark 확장·신규 구축, 한국어·한국 문화 benchmark, 실제 업무 기반 Work Intelligence benchmark, 비용·자원 효율적인 evaluation framework, 추론 결과 분석 환경을 개발합니다. 또한 frontier LLM benchmark 동향을 지속적으로 추적해 Solar의 기술 로드맵에 반영합니다. [Upstage Careers](https://careers.upstage.ai/ko/o/194889?utm_source=chatgpt.com)

여기서는 기존 석사 연구 경험이 꽤 의미 있게 살아납니다. 단순히 “LLM을 써봤다”보다 **가설 설정 → 실험 설계 → 변수 통제 → 통계 분석 → 결과 해석**을 해본 경험이 evaluation 연구와 직접 연결되기 때문입니다. 현재 LLM fine-tuning 작업에 고정 eval set, category별 오류 분석, confidence interval을 붙이면 과거 연구 방법론과 현재 LLM 기술을 하나의 이야기로 만들 수 있습니다.

공고의 필수 방향도 잘 맞습니다. **AI 모델 평가 기획, 데이터 수집·생성·정제, 평가 기준 수립, 최신 기술 동향 파악 및 빠른 적용**을 중요하게 보고, Agentic flow/tool use, failure analysis, 자체 evaluation framework, Git 협업을 우대합니다. 현재 진행 중인 보안 LLM 프로젝트의 `정적 분석 → LLM 판단 → 근거 → 평가` 구조도 활용 가능합니다. [직행](https://zighang.com/recruitment/a6c86192-eac2-4576-8c34-165fdaaa3e93?utm_source=chatgpt.com)

가장 큰 부족점은 **공개적으로 보여줄 수 있는 독립적인 evaluation framework**입니다. 지금까지 여러 성능 지표를 측정해왔지만, “모델의 품질을 어떤 기준으로 정의하고 평가 데이터를 어떻게 설계했는가”까지 완성된 산출물은 상대적으로 약합니다. 논문 실적도 우대사항이므로 연구 경쟁력이 높은 지원자 대비 약점일 수 있습니다. [Upstage Careers](https://careers.upstage.ai/ko/o/194889?utm_source=chatgpt.com)

지원 전에는 작은 `eval/` 모듈 하나를 만드는 것이 좋습니다. 예를 들어 동일한 테스트셋에서 `Base vs Fine-tuned`를 평가하면서 **overall score + category별 score + FP/FN + bootstrap 95% CI + failure taxonomy**를 자동 생성하게 하세요. 여기에 qualitative error 20~30개를 직접 읽고 “무엇이 개선됐고 무엇이 악화됐는가”를 기술하면 Upstage가 원하는 **failure analysis 기반 모델 진단**과 상당히 가까워집니다.

두 공고 중 하나만 선택해야 한다면 지금은 **LLM Inference를 먼저** 권합니다. 이미 B200/vLLM이라는 강한 실험 증거가 있어서 지원서에서 “현재 할 수 있는 것”을 가장 확실하게 보여줄 수 있기 때문입니다. 반대로 **LLM Eval은 석사 연구에서 길러온 실험·통계 방법론과 LLM을 연결할 수 있다는 점에서 장기적인 Research Engineer 방향에 매우 좋은 두 번째 카드**입니다.
