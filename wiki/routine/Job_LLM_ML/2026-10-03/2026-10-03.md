### 가장 먼저 볼 트랙: KV 캐시 인프라 소프트웨어 엔지니어

이 트랙은 최근 확인한 신입 공고 중 **LLM Serving/ML Systems 방향에서는 특히 주목할 만합니다.** 업무가 CXL 메모리 기반 KV-cache storage engine과 cache pipeline을 만드는 것이고, **vLLM·SGLang과 직접 연동**합니다. GPU–CPU–CXL 간 계층적 KV-cache 관리와 데이터 이동 최적화, 여러 LLM instance 사이의 cache sharing, memory pooling, concurrency control, RPC까지 다룹니다. 심지어 **LMCache와 vLLM 오픈소스 기여**도 업무에 명시돼 있습니다. [직행](https://zighang.com/recruitment/e7c33efe-1b4b-4af2-b8fc-f61cc506c982)

현재의 B200 `vLLM TP1 vs TP2 × concurrency` 벤치마크 경험은 이 직무에 바로 연결할 수 있습니다. TTFT·TPOT·throughput·P99·GPU memory/utilization을 측정한 경험을 **“LLM inference workload의 병목을 실험적으로 분석했다”**로 정리하면 좋습니다. 특히 지금까지 살펴본 Upstage LLM Inference나 FuriosaAI AI System Research와 동일한 **LLM Systems 축**에 있으면서, 이쪽은 명시적인 **신입 정규직**이라는 장점이 있습니다.

### 두 번째로 좋은 트랙: Performance & Developer Tools

이 직무는 LLM 자체보다 **ML/Systems 성능 엔지니어링**에 가깝지만 현재 실험 방식과 놀라울 정도로 잘 맞습니다. Profiler·Debugger·**Benchmark Framework**를 만들고, profiling/tracing metric을 설계하며, launch overhead·memory bandwidth 등을 측정하고 최적화합니다. Benchmark framework를 **CI pipeline에 연결하고 performance regression을 자동 탐지**하는 업무까지 포함합니다. [직행](https://zighang.com/recruitment/e7c33efe-1b4b-4af2-b8fc-f61cc506c982)

즉 지금의 B200 실험에서 `benchmark script → JSON 결과 → 비교표 → 병목 가설`까지 해온 것을 한 단계 발전시켜 **benchmark automation + regression detection**까지 보여준다면 직접적인 포트폴리오 증거가 됩니다. 장기적으로 ML Infrastructure/LLM Serving Engineer를 병렬 옵션으로 두고 있다는 점까지 고려하면 꽤 좋은 포지션입니다.

### 세 번째 후보: Device Runtime & SDK

여기는 CXL device용 runtime/SDK와 multi-device scheduling, memory allocator, Linux device driver interface를 개발합니다. 흥미롭게도 **Python binding을 통해 PyTorch·PyArrow·Pandas와 연동**하는 업무가 명시돼 있습니다. [직행](https://zighang.com/recruitment/e7c33efe-1b4b-4af2-b8fc-f61cc506c982)

다만 세 트랙 중에서는 현재 준비 상태와 거리가 가장 있습니다. Python/PyTorch/Linux는 익숙하지만, NUMA topology, device runtime, driver, memory allocator 쪽 저수준 시스템 지식이 추가로 필요하기 때문입니다.

### 중요한 지원 리스크

여기는 **기술 적합도와 형식적 지원자격을 분리해서 봐야 합니다.** SW 트랙들은 공통적으로 **전산·컴퓨터·전기전자공학 또는 SW 관련 전공 BS/MS/PhD**를 지원자격으로 적고 있고, C/C++/Java/Scala 계열 언어도 요구합니다. [Alion](https://alion.io/job/cena-2026nyeon-aksa-it-eokbaksa-w-aebal-inip-haeyong)

따라서 현재 기술 스택을 기준으로 보면 `KV Cache Infrastructure`는 **기술 적합도 약 9.5/10**까지 줄 수 있지만, **목재물리 석사라는 전공 때문에 서류상 적격성은 명확한 리스크**입니다. 이건 “유사 경험으로 충분히 대체된다”고 단정하기 어렵습니다. 그럼에도 신입 정규직이면서 vLLM/KV-cache/benchmark를 이렇게 직접 다루는 공고가 드물기 때문에, **지원 비용이 크지 않다면 도전해볼 가치가 있는 상향 지원 카드**로 분류하겠습니다.

또한 Python 중심의 LLM 응용 개발자가 아니라 **C/C++와 시스템 프로그래밍 역량을 보는 회사**입니다. 현재 기준 가장 큰 부족점은 C++ 자체보다도 `memory hierarchy → concurrency → RPC → cache → runtime profiling`을 코드 수준에서 설명할 수 있는 깊이입니다.

### 지원 전 가장 효율적인 준비

새 프로젝트를 만들 필요는 없습니다. **B200/vLLM 프로젝트를 XCENA용으로 한 단계만 확장**하는 편이 훨씬 좋습니다.

`TP1/TP2 × concurrency` 실험 결과에 `KV-cache가 어디에 저장되고 요청 수가 증가할 때 memory pressure가 어떻게 바뀌는가`를 분석하고, vLLM의 KV-cache manager와 scheduler 코드를 직접 따라가 보세요. 여기에 **prefill-heavy vs decode-heavy workload**를 추가하고 `TTFT / TPOT / throughput / GPU memory` 변화의 원인을 설명하면 됩니다.

그리고 한 단계 더 할 수 있다면 **LMCache + vLLM**으로 작은 실험을 해보는 것이 가장 직접적입니다. 동일 prefix가 반복되는 workload에서 `vanilla vLLM vs external/persistent KV caching`의 latency·TTFT·cache hit 효과를 측정하면 이 JD와 거의 정확히 맞닿습니다.
