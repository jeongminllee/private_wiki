이 포지션은 모델 학습 연구보다는 **LLM Agent를 실제 제품으로 만드는 엔지니어링**에 가깝습니다. Agent prototype 개발, hallucination 탐지, 내부 데이터셋을 이용한 Agent 정확도 검증, **RAG·Knowledge Base·custom toolchain용 backend API**, prompt 테스트 및 개선을 직접 담당합니다. 특히 prompt와 agent deployment를 위한 **CI/CD**, 실시간 성능 모니터링, logging·dashboard·observability까지 업무에 포함돼 있어 단순 LLM API wrapper 인턴보다 시스템 범위가 넓습니다. ([LinkedIn][1])

사용자가 이번 검색에서 우선한 역량 중에서는 **Python, 평가·검증, LLM Agent, RAG, 시스템 배포와 Git/CI 계열 엔지니어링**이 강하게 맞습니다. 내부 데이터셋으로 Agent accuracy를 검증한다는 점도 benchmark/evaluation 경험을 포트폴리오로 연결하기 좋습니다. LangChain과 AWS Lambda·Vercel·GCP Cloud Functions 경험도 우대합니다. ([LinkedIn][1])

반대로 분명한 한계도 있습니다. **PyTorch, Hugging Face Transformers, fine-tuning, 분산학습은 이 JD의 중심이 아닙니다.** 따라서 모델 자체를 학습·최적화하는 LLM Research/Training Engineer를 최우선 목표로 본다면 앞서 확인했던 Scatter Lab·DEEPX·카카오 계열보다 직접적인 매치는 낮습니다. 이 공고의 중심축은 `LLM model engineering`보다는 **Agent + Backend + Evaluation + Production**입니다. ([LinkedIn][1])

지원 전에 가장 효과적인 준비는 Agent 프로젝트 하나를 **프로덕션 형태로 마감하는 것**입니다. `FastAPI → RAG → tool calling → agent` 흐름을 구현하고, 50~100개의 고정 evaluation case를 만들어 **task success rate, hallucination rate, retrieval 성공률, p95 latency, API cost**를 측정하는 구성이 좋습니다. 이후 prompt 버전이 변경될 때 `pytest + GitHub Actions`로 regression을 자동 탐지하고, 요청·오류·latency를 로그나 간단한 dashboard로 남기면 JD의 **accuracy validation → CI/CD → observability** 요구사항을 거의 그대로 증명할 수 있습니다. ([LinkedIn][1])
