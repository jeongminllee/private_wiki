## 1. 필독 | OpenAI GPT‑5.6 Sol Ultrafast — “작은 모델로 내려가야 빨라진다”는 전제가 흔들린다

### 무엇이 바뀌었나

OpenAI가 8월 13일 **GPT‑5.6 Sol Ultrafast**를 limited preview로 공개했습니다. Cerebras가 inference를 담당하며, OpenAI는 Standard processing 대비 **최대 14배**, 최대 **750 output tokens/s**를 제시했습니다. 현재는 일부 고객만 사용할 수 있고 일반 API 사용자를 대상으로는 아직 확장 일정이나 가격이 공개되지 않았습니다. ([OpenAI][2])

OpenAI가 제시하는 대상도 흥미롭습니다. incident response, 실시간 금융·보안 분석, 복잡한 voice support, live research처럼 기존에는 frontier model의 reasoning은 원하지만 응답 시간이 너무 길어 작은 모델로 내려갔던 workflow를 겨냥합니다. OpenAI 내부에서도 로그·trace·대화 내용을 빠르게 훑으며 장애 원인을 좁히거나, 연구 실험의 hypothesis→result→next experiment loop를 짧게 만드는 용도로 테스트했다고 설명합니다. ([OpenAI][2])

### 왜 중요한가

기존 model router는 보통 두 축으로 생각했습니다.

```text
높은 품질 / 느림 → 큰 frontier model
낮은 latency     → 작은 model
```

Ultrafast가 production에서 실제로 안정화되면 이 축이 분리됩니다.

```text
Model intelligence
        ×
Inference speed
        ×
Price
```

즉 “응답시간 SLO가 3초이므로 작은 모델”이 아니라 **같은 frontier model을 더 빠른 inference tier로 보내는 선택지**가 생깁니다. Agent에서는 더 중요합니다. LLM 호출이 1회가 아니라 10~30번 이어지면 호출당 2~3초 절감도 전체 task completion time에서 수십 초 차이를 만들 수 있기 때문입니다. OpenAI가 실시간 incident-response와 interactive research를 예시로 든 이유도 이 구조와 맞닿아 있습니다. ([OpenAI][2])

### 실제 시스템에 적용한다면

Ultrafast를 평가할 때 `tokens/s`만 비교하면 안 됩니다. 다음 네 시간을 분리해야 합니다.

```text
queue_time
TTFT
decode_time
tool_wait_time
```

예를 들어 decode가 14배 빨라도 전체 agent 작업의 70%가 browser·database·test 실행이라면 end-to-end 개선은 훨씬 작습니다. 반대로 autoresearch나 coding처럼 모델이 장문 reasoning·code를 반복 생성하는 workload에서는 상당한 차이가 날 수 있습니다.

특히 같은 모델이므로 **quality degradation 없이 latency만 바뀌는지**를 paired evaluation으로 확인하기 좋습니다. 동일 prompt·seed 가능 조건에서 Standard와 Ultrafast의 strict task success, tool trajectory, output consistency, total task time을 비교해야 합니다.

### 주의할 점·후속 관찰

“최대 14배”와 “750 tok/s”는 peak 표현입니다. OpenAI는 TTFT, context 길이별 속도, 높은 concurrency에서의 처리량, 가격을 아직 공개하지 않았습니다. 또한 750 tok/s는 **output generation 속도**이지 API request 전체 latency가 아닙니다. ([OpenAI][2])

관찰할 포인트는 **가격**, context가 길어질 때 속도 유지 여부, batch/concurrency 조건, Codex 같은 agent surface 도입 여부입니다. 만약 이 tier가 일반화되면 향후 agent FinOps는 `model × reasoning effort`뿐 아니라 **`inference tier`까지 router가 결정**하게 될 가능성이 큽니다.

**원문:** **[공식 발표] OpenAI — GPT‑5.6 Sol Ultrafast** ([OpenAI][2]) · **[Cerebras 공식 발표] Ultrafast infrastructure** ([Cerebras][4])

## 2. 모델·과학 AI | Intern‑S2‑Preview 397B — 과학 모델이 “논문 QA”에서 long-horizon agent training으로

### 무엇이 바뀌었나

8월 14일 신규 등재된 Intern‑S2 기술 보고서는 **397B급 scientific multimodal agentic foundation model**의 전체 training stack을 상세화했습니다. 모델은 scientific document의 rendered page, image-text interleave, 전문 과학 corpus를 활용한 multimodal pretraining 이후 SFT, scalable multi-task RL, black/white-box agentic RL, on-policy distillation을 거칩니다. Training system에는 partial rollout with off-policy correction, adaptive length regularization, **online speculative decoding**, trace-aware experience assembly 등이 포함됩니다. ([arXiv][5])

공식 repository와 Hugging Face model card도 공개돼 있으며, 397B 모델은 일반 reasoning뿐 아니라 과학 문서·과학 modality와 long-horizon agent를 하나의 모델 안에서 다루는 것을 목표로 합니다. 별도의 **Memory Decoder 4B**를 frozen 397B backbone에 붙여 Biology-Instructions 평균을 56.92에서 60.32로 올렸다는 결과도 보고했습니다. ([GitHub][6])

### 왜 중요한가

기존 scientific LLM은 흔히:

```text
논문 / 데이터 입력
→ 질문
→ 답변
```

형태였습니다.

Intern‑S2가 겨냥하는 구조는 더 가깝습니다.

```text
논문 / 이미지 / 시계열
        ↓
가설 설정
        ↓
tool / sandbox
        ↓
실험
        ↓
결과 해석
        ↓
다음 행동
```

즉 scientific intelligence를 knowledge benchmark가 아니라 **agent trajectory로 학습**하기 시작했다는 점이 중요합니다. 특히 black-box agentic RL과 white-box agentic RL을 모두 포함하고, rollout efficiency를 위해 speculative decoding까지 training pipeline에 넣었다는 것은 scientific agent 학습도 결국 distributed systems 문제로 변하고 있음을 보여줍니다. ([arXiv][5])

### 실무 적용

과학·연구용 모델을 평가한다면 이제 benchmark accuracy만 기록하지 않는 것이 좋습니다.

```text
hypothesis_quality
tool_selection
experiment_validity
result_interpretation
recovery_after_failure
novelty
cost_per_valid_experiment
```

같은 지표가 필요합니다.

또 Intern‑S2의 Memory Decoder 접근은 흥미롭습니다. 거대한 backbone을 계속 fine-tune하기보다 **별도의 작은 memory-adaptation path**를 붙이는 형태라서, 특정 연구실의 domain knowledge를 빠르게 specialization하는 방법으로 볼 수 있습니다. 다만 이건 아직 저자들의 모델 내부 실험 결과입니다. ([arXiv][5])

### 주의할 점·후속 관찰

397B 모델의 “leading” 성능 주장은 연구진 측 benchmark 결과이며, 과학 분야별 task distribution이 매우 다르므로 모든 scientific workload에 일반화해서는 안 됩니다. 또한 long-horizon agent 성능은 model뿐 아니라 sandbox, tool interface, reward design에 크게 영향을 받습니다. ([Hugging Face][7])

후속으로 볼 것은 397B 모델의 실제 serving cost, 35B 모델과의 cost-performance, online speculative decoding이 RL rollout throughput에 미치는 실측 효과, Memory Decoder의 다른 domain 전이입니다.

**원문:** **[논문] Intern‑S2‑Preview: Scientific Agentic Foundation Model** ([arXiv][5]) · **[모델 카드] Intern‑S2‑Preview‑397B** ([Hugging Face][7]) · **[GitHub] Intern‑S2 repository** ([GitHub][6])

## 3. GPU·추론 연구 | DARTree — diffusion drafter + AR correction을 tree로 확장해 최대 9.73× lossless speedup

### 무엇이 바뀌었나

8월 14일 신규 등재된 **DARTree**는 speculative decoding에서 diffusion-based drafter가 만드는 후보를 **autoregressive correction tree**로 다루는 training-free 방식입니다. Diffusion drafter는 token block 전체를 병렬로 예측할 수 있지만 각 위치의 확률이 선택된 이전 token에 조건화되지 않는 문제가 있습니다. DARTree는 pretrained AR correction head를 chain이 아니라 tree branch 전체로 확장합니다. ([arXiv][8])

저자 평가에서 math·code·chat 7개 benchmark, 네 개 model-temperature 설정 모두에서 가장 높은 평균 acceptance length와 speedup을 기록했고, 특정 조건에서는 verification round당 **12.97 token**을 accept했습니다. 같은 조건에서 DFlash보다 98.6%, Domino보다 27.9% 많은 accepted token이며, 저자들의 locally measured autoregressive baseline 대비 최대 **9.73× lossless speedup**을 보고했습니다. ([arXiv][8])

### 왜 중요한가

Speculative decoding에서 진짜 병목은 draft token을 많이 만드는 것이 아니라 **target model이 실제로 얼마나 많이 받아들이는가**입니다.

```text
Draft 16 tokens
↓
2 tokens accept
→ 대부분 계산 낭비
```

반대로:

```text
Draft tree
↓
target distribution과 잘 맞는 path 선택
↓
10+ tokens accept
```

가 되면 target forward 횟수를 크게 줄일 수 있습니다.

최근 DFlash·xPress·DARTree가 연속해서 나오고 있다는 것은 speculative decoding 연구가 단순 “작은 draft model + 큰 target”에서 **candidate geometry와 correction algorithm 최적화** 단계로 들어가고 있다는 신호입니다. ([arXiv][8])

### 실제 시스템 적용

재현할 때는 `speedup`보다 아래 네 개가 핵심입니다.

```text
draft_latency
accepted_tokens / round
verification_latency
temporary_memory
```

그리고 batch=1 microbenchmark와 production concurrency를 분리해야 합니다. Tree 후보가 많아지면 acceptance는 올라가지만 tree storage·verification memory와 GPU kernel complexity도 올라갑니다.

Agent workload에서는 평균 decode 속도보다 **task completion time**으로 봐야 합니다. Tool call 사이마다 짧은 decode를 반복하면 speculative tree 구축 overhead가 상대적으로 커질 수 있기 때문입니다.

### 주의할 점·후속 관찰

9.73×는 논문에서 사용한 모델·temperature·local AR baseline 중 최대 수치입니다. vLLM/SGLang production service 전체가 9배 빨라진다는 의미는 아닙니다. ([arXiv][8])

후속 관찰은 SGLang/vLLM 통합, high-concurrency acceptance, long reasoning에서 draft quality 유지 여부, DFlash와 같은 실제 배포용 drafter와의 end-to-end 비교입니다.

**원문:** **[논문] DARTree: Speculative Diffusion Decoding with Autoregressive Draft Trees** ([arXiv][8])

## 4. AI 투명성 | Anthropic, Claude text watermark 구조 공개 — 코드·사실문에는 오히려 약하다

### 무엇이 바뀌었나

Anthropic은 **8월 14일** 향후 Claude 모델의 text watermarking 방식을 자세히 공개했습니다. Claude가 사용할 방식은 Google DeepMind의 **SynthID‑Text 계열**로, 숨은 문자나 metadata를 텍스트에 넣는 것이 아니라 여러 개의 “둘 다 자연스러운 다음 token” 후보 중 무엇을 고를지 결정하는 randomness를 secret key에 따라 조정합니다. Anthropic은 이를 전 세계에 적용할 계획이며 EU AI Act 관련 투명성 요구에 대응하기 위한 것이라고 설명합니다. ([Anthropic][9])

Anthropic 내부 평가와 기존 SynthID 연구에서는 품질·가독성에 유의미한 저하가 관찰되지 않았고, token을 추가하지 않으므로 가격이나 속도 영향도 negligible하다고 회사는 설명합니다. 향후 Claude watermark를 확인하기 위한 detection API도 제공할 예정입니다. 이미지·SVG 등 지원 파일에는 text watermark 대신 C2PA signed credential을 metadata에 붙입니다. ([Anthropic][9])

### 왜 중요한가

이 방식은 전통적인 “AI detector”와 완전히 다릅니다.

AI detector:

```text
문체를 보고 추정
```

watermark detector:

```text
secret key와 token 선택 패턴의
통계적 일치 여부 검사
```

이므로 공급자가 key를 갖고 있다는 점이 핵심입니다. 따라서 일반 detector보다 provenance 신호는 강할 수 있지만, **Claude가 관여했다는 확률적 증거일 뿐 작성자·소유자·사용자를 식별하지는 못합니다.** ([Anthropic][9])

### 엔지니어 관점에서 재미있는 한계

Code와 factual text에서는 watermark signal이 약합니다. `2+2=4`, API name, 변수명처럼 “정답 token이 사실상 하나”인 곳에서는 token 선택 자유도가 없기 때문에 watermark를 넣을 수 없습니다. Anthropic도 code는 자연어 prose보다 watermark density가 낮다고 명시합니다. Proofreading도 Claude가 몇 단어만 바꾸면 signal이 매우 약합니다. ([Anthropic][9])

즉 source-code provenance를 위해 이 기술 하나에 의존하면 안 됩니다. 코드 artifact에는 commit signing, SBOM, C2PA/metadata, build provenance 같은 별도 chain이 필요합니다.

### 주의할 점·후속 관찰

짧은 text에서는 detection confidence가 낮고, 전체 rewrite는 watermark를 제거할 수 있습니다. 또한 watermark는 “Claude가 일부 관여했다”는 것 이상을 증명하지 못합니다. ([Anthropic][9])

후속으로 가장 중요한 것은 detection API의 false-positive/false-negative, 최소 text length, multilingual text·한국어에서의 검출력, 모델별 key rotation 정책입니다.

**원문:** **[공식 발표] Anthropic — How Claude’s text watermarking works** ([Anthropic][9])

## 5. Agent Harness | AutoDesign — 모델을 개선하지 않고 모델을 둘러싼 Harness를 스스로 개선한다

### 무엇이 바뀌었나

**AutoDesign**은 long-horizon multimodal 작업에서 foundation model 대신 **harness 자체를 recursive optimization**하는 연구입니다. Meta-harness optimizer가 code agent의 rollout 결과를 보고, agent가 실제로 사용하는 workflow·tool·control logic을 수정합니다. 평가 과제로 academic paper→conference poster 생성을 선택했고 100개 논문의 PosterBench를 만들었습니다. ([arXiv][10])

저자 평가에서 학습된 DesignHarness를 적용한 7개 code-agent/model 조합의 평균 score는 **54.99 → 67.39**, 즉 12.40점 상승했습니다. AutoDesign 최종 시스템은 PosterBench 78.32를 기록해 저자들이 비교한 Claude Design보다 7.45점 높았습니다. 완전 자율 장기 실행에서는 40분 동안 253번의 tool call과 11번의 editing turn을 수행했고 비용은 3달러 미만이라고 보고했습니다. ([arXiv][10])

### 왜 중요한가

최근 연구에서 반복해서 등장하는 패턴입니다.

```text
Model 고정
+
Harness 변경
=
성능 크게 변화
```

이는 model tuning과 별개의 최적화 공간이 매우 크다는 뜻입니다.

Harness가 결정하는 것은 단순 system prompt가 아닙니다.

```text
어떤 context를 언제 넣는가
언제 tool을 쓰는가
실패하면 어떻게 복구하는가
결과를 어떻게 검증하는가
어떤 intermediate artifact를 보존하는가
```

이런 결정이 수십 turn 누적되면 foundation model의 2~3점 차이보다 더 크게 작용할 수 있습니다. AutoDesign 결과는 특정 poster task에 한정되지만, 이런 **meta-harness optimization**의 가능성을 보여줍니다. ([arXiv][10])

### 실무 적용

내부 agent를 개선할 때 “모델을 교체할까?” 전에 harness parameter를 별도 search space로 만들 수 있습니다.

```text
context compaction
retry policy
tool ordering
verification policy
memory retention
planner/executor split
```

그리고 성공 trajectory만 학습하지 말고 **실패 trajectory에서 harness patch를 생성**한 뒤 held-out task에서 검증하는 방식이 좋습니다.

### 주의할 점·후속 관찰

PosterBench는 저자들이 만든 benchmark이며 paper→poster라는 매우 구조화된 영역입니다. DesignHarness가 SWE-bench·research agent·data analysis에도 같은 정도로 transfer된다는 증거는 아직 없습니다. 또한 meta-optimizer가 validation set에 과적합할 가능성도 있습니다. ([arXiv][10])

후속 관찰 포인트는 다른 domain transfer, harness patch의 regression, 장기간 optimization 시 complexity explosion, 사람이 유지보수 가능한 형태로 남는지 여부입니다.

**원문:** **[논문] AutoDesign** ([arXiv][10]) · **[GitHub] AutoDesign code** 논문 공식 artifact에서 연결됩니다. ([arXiv][10])

## 6. 필독 | QuoteBench — 모델이 맞는 명령을 생성했는데 Harness parser가 망가뜨릴 수 있다

### 무엇이 바뀌었나

**QuoteBench**는 coding agent benchmark에서 지금까지 거의 숨겨져 있던 계층을 직접 평가합니다. 모델이 Bash command를 정확하게 만들더라도 agent framework가 이를 JSON으로 serialize하고 shell wrapper를 통과시키고 다시 parser에서 해석하는 과정에서 quoting·escaping이 바뀔 수 있습니다. ([arXiv][11])

56개 one-shot task, 14개 실제 incident-derived family에서 같은 model output을 **raw execution path와 parser 하나가 추가된 path**에 각각 재생했습니다. 추가 parser를 통과시키자 여덟 configuration에서 성공률이 **55.4~73.2 percentage points 감소**했습니다. 모델에게 boundary를 명시적으로 알려주자 6개 configuration에서는 30.4~60.7점 회복했지만 두 개에서는 거의 회복하지 못했습니다. ([arXiv][11])

특히 GPT‑5.6 Sol의 aggregate score만 보면 차이가 -3.6점처럼 보였지만, 내부적으로는 execution path가 **-64.3점의 손상**을 만들고 모델이 **+60.7점을 보정**해 겉으로 숨겼다는 분석이 인상적입니다. ([arXiv][11])

### 왜 중요한가

Agent benchmark에서:

```text
Model output
→ command
→ success/fail
```

로 생각하면 안 됩니다.

실제로는:

```text
Model
↓
tool schema
↓
JSON serialize
↓
SDK
↓
shell wrapper
↓
parser
↓
OS
↓
final state
```

입니다.

같은 model이라도 **command transport contract가 달라지면 model ranking 자체가 바뀔 수 있습니다.** 따라서 “Model A가 terminal benchmark 5점 높다”는 말에는 어떤 harness·parser·shell이 사용됐는지가 반드시 붙어야 합니다. ([arXiv][11])

### 실제 시스템 적용

Tool telemetry에 model이 생성한 command string 하나만 저장하면 부족합니다.

```text
generated_command
serialized_payload
post_parse_command
actual_argv
exit_code
final_state
```

를 모두 남겨야 합니다.

가장 중요한 validator도 exit code가 아니라 **최종 filesystem·repository 상태**여야 합니다. `exit 0`이지만 잘못된 파일에 쓰는 경우를 잡을 수 있기 때문입니다.

### 주의할 점·후속 관찰

QuoteBench는 deliberately 추가된 parser boundary를 이용한 통제 실험입니다. 모든 production agent가 성공률 70%p 하락을 겪는다는 뜻은 아닙니다. 핵심은 **model-level score가 transport bug를 숨길 수 있다**는 방법론입니다. ([arXiv][11])

이 결과는 coding agent benchmark의 artifact report에 `model + tool schema + execution transport + validator`를 함께 기록해야 한다는 강한 근거입니다.

**원문:** **[논문] QuoteBench: How Matched Scores Can Hide Command-Path Failures** ([arXiv][11])

## 7. 검증 가능한 코딩 | Vero — 함수 하나가 아니라 repository 전체를 “코드 + 증명”으로 생성할 수 있는가

### 무엇이 바뀌었나

**Vero**는 AI coding agent에게 implementation뿐 아니라 **machine-checked proof까지 repository 단위로 생성**하게 하는 benchmark입니다. 실제 Python, Dafny, Verus, Coq repository에서 가져온 43개 multi-module instance를 Lean 4 기반의 API·formal specification 형태로 구성합니다. 분야도 cryptographic protocol부터 distributed system까지 포함합니다. ([arXiv][12])

현재 frontier coding-agent configuration을 Lean toolchain과 함께 평가한 결과 가장 강한 agent도 **43개 중 27개만 완전 해결**했고, 가장 어려운 repository에서는 specification 하나도 완전히 닫지 못했습니다. ([arXiv][12])

### 왜 중요한가

AI 코딩의 현재 검증은 대부분:

```text
unit tests pass
```

입니다.

하지만 test는 관찰한 case만 검사합니다. Formal verification은:

```text
implementation
+
formal specification
+
machine-checked proof
```

를 요구하기 때문에 훨씬 강한 correctness contract를 가질 수 있습니다.

특히 multi-module repository에서는 함수별 proof가 맞는 것만으로 부족합니다. API invariant, module interaction, data structure assumptions가 여러 파일에 걸쳐 일관돼야 합니다. Vero가 function benchmark가 아니라 repository benchmark를 만든 이유입니다. ([arXiv][12])

### 실무 적용

모든 production code를 Lean으로 만들 필요는 없습니다. 대신 high-risk component부터 AI-generated change에 **strong verifier**를 붙이는 사고방식을 가져갈 수 있습니다.

```text
AI patch
→ compiler
→ type checker
→ property test
→ static analyzer
→ formal proof (critical core)
```

특히 crypto, serialization, permission policy, protocol logic처럼 specification을 비교적 명확하게 적을 수 있는 영역부터 유효합니다.

Vero의 좋은 설계 중 하나는 benchmark specification 자체가 틀릴 수 있음을 인정하고, agent가 specification unsatisfiable 또는 reference implementation incorrect임을 증명할 수 있게 한 것입니다. 검증기 자체도 검증 대상이라는 뜻입니다. ([arXiv][12])

### 주의할 점·후속 관찰

Formal proof가 존재한다고 제품 요구사항 자체가 올바른 것은 아닙니다. **잘못된 specification을 완벽하게 증명할 수 있습니다.** 따라서 formal method의 병목은 앞으로 proof generation뿐 아니라 specification engineering이 될 가능성이 큽니다.

후속 관찰은 proof-carrying PR, repository 규모 확장, agent가 자연어 requirement를 formal specification으로 바꾸는 단계까지 포함한 end-to-end 평가입니다.

**원문:** **[논문] Vero: Can AI Agents Build Formally Verified Software Repositories?** ([arXiv][12]) · **[GitHub] benchmark/evaluation harness** 논문 공식 artifact에서 공개됩니다. ([arXiv][12])

## 8. Agent 평가 | Beyond Final Scores — “점수가 높다”보다 어떻게 높아졌는지가 중요하다

### 무엇이 바뀌었나

8월 14일 등재된 **Beyond Final Scores**는 7개 frontier model을 36개의 long-horizon AI R&D task에서 평가하면서 최종 점수 대신 agent 내부 과정을 **Solution Framing → Execution → Feedback Control** 단계로 분해했습니다. 또 한 task에서 얻은 experience가 다음 run과 다른 task에서 실제로 도움이 되는지도 통제 실험했습니다. ([arXiv][13])

결론은 현재 agent가 완전한 autonomous researcher라기보다 **engineering optimizer에 가깝다**는 것입니다. 실용적인 solution을 만들고 구현하는 능력은 있지만 run 간 변동성이 크고, 가장 좋은 solution도 새로운 방법론을 발명하기보다는 기존 technique을 조합·적응하는 경우가 많았습니다. Experience reuse도 항상 도움이 되는 것이 아니라 다음 판단을 잘못 유도하기도 했고, harness 차이가 안정성에 영향을 미쳤습니다. ([arXiv][13])

### 왜 중요한가

두 agent가 최종 score 80을 받았다고 해도 내부는 다를 수 있습니다.

```text
Agent A:
좋은 가설
→ 좋은 실험
→ 한 번에 성공

Agent B:
잘못된 가설 5개
→ 대량 compute
→ 우연히 마지막에 80
```

Production에서는 둘을 동일한 시스템으로 볼 수 없습니다.

특히 autoresearch에서는 최종 benchmark가 올라갔더라도:

```text
몇 번 실패했는가
같은 실험을 반복했는가
feedback을 반영했는가
이전 경험을 제대로 재사용했는가
```

가 compute efficiency와 reliability를 결정합니다. 이 연구는 바로 이 부분을 정량화하려고 합니다. ([arXiv][13])

### 실제 시스템 적용

Research-agent log를 최종 metric뿐 아니라 단계별 decision artifact로 남기는 것이 좋습니다.

```text
hypothesis
expected_effect
experiment
observed_result
decision_after_result
```

특히 **experiment result가 다음 행동을 실제로 바꾸었는가**를 추적해야 합니다. 결과를 읽고도 원래 계획을 그대로 반복하면 feedback control이 사실상 작동하지 않는 것입니다.

### 주의할 점·후속 관찰

36개 task라는 규모와 연구진이 설계한 metric에 한정된 초기 결과입니다. “현재 AI는 연구를 못한다”는 결론도, 반대로 “자동 연구가 완성됐다”는 결론도 아닙니다. 핵심은 **final score 하나로 autonomous R&D capability를 평가하는 것은 불충분하다**는 것입니다. ([arXiv][13])

후속으로는 novelty를 어떻게 객관적으로 측정할지, 경험 memory가 도움이 되는 경우와 해로운 경우를 어떻게 분리할지, compute budget을 포함한 evaluation이 중요합니다.

**원문:** **[논문] Beyond Final Scores: A Systematic Evaluation of Agents for Long-Horizon AI Research and Development** ([arXiv][13])

# 오늘 꼭 볼 것 3개

**1. QuoteBench.** 오늘 가장 실무적인 논문입니다. Agent가 “잘못된 명령을 만들었다”와 **agent framework가 올바른 명령을 망가뜨렸다**를 분리하지 않으면 모델 비교와 debugging 모두 틀릴 수 있다는 것을 매우 크게 보여줍니다. ([arXiv][11])

**2. GPT‑5.6 Sol Ultrafast.** Frontier model을 작게 줄이지 않고 inference hardware tier만 바꿔 최대 750 tok/s까지 밀어붙이는 방향은 agent architecture에 큰 영향을 줄 수 있습니다. 특히 긴 reasoning loop의 **time-to-solution**을 바꾸는 변화인지 지켜볼 가치가 큽니다. ([OpenAI][2])

**3. Vero.** Coding agent가 이제 “코드를 생성하는가?”에서 **“repository 단위 implementation과 machine-checkable proof를 동시에 유지할 수 있는가?”**로 평가되기 시작했습니다. AI-generated software의 신뢰성을 고민할 때 매우 중요한 방향입니다. ([arXiv][12])

# 오늘의 실습 | Coding Agent의 “명령 생성 오류”와 “Harness 오류”를 분리해보기

오늘은 QuoteBench 아이디어를 아주 작은 로컬 실험으로 재현해보는 것을 추천합니다. 모델 성능 benchmark라기보다 **agent runtime debugging 감각**을 얻기 좋은 실습입니다. ([arXiv][11])

1. 작은 temporary directory에서 15~20개의 shell task를 준비합니다. 단순한 `touch file.txt`뿐 아니라 `"file with space.txt"`, JSON 문자열, 작은따옴표·큰따옴표가 섞인 문자열, pipe와 redirect, `$VAR`, Python `-c`처럼 quoting에 민감한 사례를 넣습니다.

2. 같은 command를 세 경로로 실행합니다. **A는 직접 argv 형태의 `subprocess.run([...])`, B는 command string을 `bash -lc`로 실행, C는 JSON serialize → deserialize → `bash -lc`처럼 parser boundary 하나를 더 넣습니다.** 여기서 command 내용 자체는 완전히 동일하게 유지합니다.

3. 각 실행에서 다음 값을 저장합니다.

```text
original_command
serialized_payload
command_after_parse
actual_argv
return_code
stdout
stderr
```

4. 성공 여부를 `return_code == 0`로 판단하지 말고 **final-state validator**로 판단합니다. 예를 들어 “정확한 파일 이름이 생성됐는가”, “JSON 내용이 한 글자도 바뀌지 않았는가”, “원하는 line만 수정됐는가”를 확인합니다.

5. 마지막으로 같은 task를 coding agent에게 수행시켜 봅니다. Agent가 만든 raw command는 성공하는데 wrapper를 통과하면 실패한다면 **model failure가 아니라 harness failure**입니다. 반대로 agent가 wrapper 특성을 알고 command를 스스로 escaping해서 성공한다면 QuoteBench가 말한 `boundary adaptation`을 직접 관찰한 것입니다. ([arXiv][11])

결과 표는 다음 네 값이면 충분합니다.

```text
raw_success_rate
wrapped_success_rate
parser_induced_failure
agent_compensation_rate
```

이 실험의 핵심은 아주 단순합니다.

> **Agent가 실패했을 때 가장 먼저 “모델이 틀렸다”고 생각하지 말고, 모델 출력에서 실제 side effect까지의 transport path를 확인한다.**

최근 agent 연구를 묶어서 보면 오늘 가장 중요한 엔지니어링 메시지는 이것입니다. **모델, harness, execution transport, verifier를 하나의 시스템으로 보고 각각의 실패를 따로 계측해야 합니다.** ([arXiv][10])
