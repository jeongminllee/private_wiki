# AI 엔지니어 데일리 브리핑 — 2026년 9월 8일

오늘 아침 기준으로 가장 신선한 엔지니어링 릴리스는 **9월 7일 공개된 vLLM의 Tenstorrent 플러그인**입니다. 연구 쪽은 9월 4일 공개된 최신 논문 묶음에서 건질 것이 많았는데, 특히 **MoE 추론량 절반 줄이기, prefix cache와 양자화가 재현성을 깨는 문제, sharded MoE Allgather 최적화, layer dropout의 재평가**가 실용적입니다. 에이전트 쪽에서는 context를 문자열 누적 문제가 아니라 **데이터베이스 query planning 문제**로 보는 접근과, persistent memory가 실제 authorization policy가 될 수 있다는 보안 연구가 눈에 띕니다.

## 1. vLLM이 Tenstorrent를 정식 플러그인 방식으로 지원 — “GPU 전제”가 inference runtime에서 조금씩 깨진다 ★★★★★

9월 7일 vLLM이 **vLLM TT Plugin**을 공개했습니다. 핵심은 단순히 “Tenstorrent에서도 vLLM이 돈다”가 아닙니다. Tenstorrent는 GPU처럼 host가 layer마다 collective를 호출하는 구조가 아니라 여러 chip으로 구성된 mesh를 하나의 traced program으로 실행하기 때문에, 기존 GPU 중심 scheduler를 그대로 가져갈 수 없습니다. 그럼에도 vLLM core를 fork하지 않고 `platform_plugins`와 pluggable scheduler만으로 별도 backend를 구현했다는 점이 상당히 중요합니다. citeturn976704search0turn602904search0

TT backend에서는 한 step이 **prefill-only 또는 decode-only**이며, Galaxy 같은 32-chip mesh에서는 여러 process를 띄우는 일반 DP 대신 하나의 engine process 안에 여러 독립 scheduler/KV cache를 가진 `lane-DP`를 둡니다. 또한 조건이 맞으면 sampling까지 device에서 수행해 host로 logits 자체를 가져오지 않고, steady-state decode에서는 host readback과 다음 scheduling을 overlap합니다. GPU에서 당연하게 쓰던 `TP rank`, mixed prefill/decode batch 같은 abstraction이 다른 accelerator에서는 최적이 아닐 수 있다는 좋은 사례입니다. citeturn976704search0

지원 범위도 생각보다 넓습니다. Llama 3.x, Qwen 2.5/3 계열, Qwen-VL, Mistral, Gemma, DeepSeek V3, GPT-OSS 20B/120B 등이 등록되어 있고 OpenAI-compatible API를 그대로 사용할 수 있습니다. 반대로 speculative decoding, LoRA, multi-host serving 등은 아직 제한적이며 plugin repo와 blog의 vLLM 기준 버전 표기가 다소 빠르게 움직이고 있으므로 **실제 설치 시 README의 현재 pinned commit을 source of truth로 보는 편이 안전**합니다. citeturn976704search0turn602904search0

엔지니어링적으로는 “vLLM = NVIDIA CUDA inference engine”으로 생각하지 않는 게 핵심입니다. 앞으로 accelerator backend마다 `scheduler`, `KV representation`, `sampling location`, `parallelism topology`가 달라지고 vLLM은 그 위에 공통 serving API를 제공하는 **hardware-neutral control plane** 쪽으로 진화할 가능성이 있습니다.

## 2. “Dropout은 옛날 기법”이라는 통념에 반격 — 2,400회 실험에서 training FLOPs 최대 25% 절감 ★★★★★

9월 4일 공개된 **Don't Drop Dropout**은 꽤 재미있는 결과입니다. 최근 대형 LLM pretraining recipe에서는 dropout, 특히 layer dropout/stochastic depth가 거의 사라졌는데, 연구진은 271M부터 8.2B까지, 최대 160B token 규모에서 **2,400회 이상의 training experiment**를 수행해 layer dropout을 다시 체계적으로 검증했습니다. citeturn904108academia12

적절한 layer별 dropout distribution, 시간 schedule, optimizer 설정을 사용하면 동일 training step에서 **최대 약 25%의 FLOPs를 덜 사용하면서 비슷하거나 더 낮은 validation loss**를 얻었다고 보고합니다. 더 흥미로운 점은 학습 이후입니다. stochastic-depth를 경험한 모델은 일부 layer를 건너뛰는 것에 견고해져 `early exit`, `intermediate-layer skipping`, `self-speculative decoding`을 적용하기 쉬워졌고, 연구진은 최대 약 **1.5배 inference speedup**을 보고했습니다. citeturn904108academia12

이 결과는 단순 regularization 이야기가 아닙니다. 모델을 학습할 때부터 **“모든 layer가 항상 존재한다”는 가정을 약하게 만들어 inference-time elasticity를 심어주는 것**으로 볼 수 있습니다. future serving에서는 request difficulty에 따라 32개 layer 전체를 돌릴지 24개만 돌릴지 동적으로 결정하는 구조로 연결될 수 있습니다.

다만 이 연구의 pretraining은 Cerebras CS-3에서 수행됐고 최대 모델도 8.2B이므로 70B~수백B급 dense/MoE에서 그대로 25%가 나올 것이라고 보면 안 됩니다. 또한 “layer dropout 0.2를 넣으면 된다” 같은 단순 recipe가 아니라 **layer distribution과 schedule을 함께 최적화해야 한다**는 것이 논문의 핵심입니다.

## 3. Prefix Cache가 결과를 바꾼다 — 그리고 4-bit 양자화에서는 훨씬 심해진다 ★★★★★

**Same Request, Different Answer**는 inference benchmark를 하는 사람이라면 꼭 봐둘 만합니다. 같은 model, 동일 seed, 동일 decoding parameter, 동일 request order, batch size 1 조건에서 prefix caching만 켜고 끄면서 80개의 multi-turn agent tool-use episode를 비교했습니다. citeturn151187view0

16-bit에서는 cache 사용 여부에 따라 **36.2%의 episode trajectory가 달라졌고**, 4-bit weight에서는 **75.0%**까지 올라갔습니다. 반대로 cache를 끄고 다시 실행하면 모든 구성에서 800/800 episode가 bit-identical했습니다. 연구진은 cache path 자체가 무작위라기보다 **cache state가 request specification 밖에 존재하는 hidden state**라는 것이 실제 재현성 문제라고 분석합니다. 동일 cache state를 복원하면 cached path와 recompute path는 각각 재현되지만 서로 다른 결과를 만들었습니다. citeturn151187view0

이건 serving benchmark 설계에 직접 영향을 줍니다. 현재 대부분의 benchmark record에는 `model / seed / temperature / prompt / quantization` 정도만 저장합니다. 그런데 prefix caching을 켠다면 사실상 다음 정보도 experimental state입니다.

`cache enabled`
`cache configuration`
`cache warm/cold`
`request sequence`
`cache reset boundary`

특히 BF16 모델과 AWQ/GPTQ/NVFP4 모델을 비교하면서 prefix cache 상태가 다르면 작은 accuracy 차이를 quantization 영향이라고 잘못 해석할 가능성이 있습니다. Agent workload에서는 첫 token 하나가 바뀌면 이후 tool trajectory 전체가 갈라지므로 일반 QA보다 영향이 더 큽니다.

논문은 두 inference engine과 80개 episode라는 제한된 구성에 대한 결과이므로 “prefix cache가 항상 품질을 망친다”는 결론은 아닙니다. 실제 메시지는 **cache를 transparent optimization으로 취급하지 말고 benchmark provenance에 포함하라**는 쪽에 가깝습니다.

원문은 url논문 · Same Request, Different Answer: Quantization Amplifies Cache-Induced Divergence in LLM Servingturn151187view0입니다.

## 4. Qwen MoE에서 expert 절반만 써도 거의 안 떨어졌다 — 핵심은 `top-k`가 아니라 normalization reference ★★★★★

**Training-Free Halving of Activated Experts in Fine-Grained MoE Models**는 현재 MoE inference 최적화 쪽에서 상당히 실용적인 아이디어입니다.

일반 MoE에서 training 시 `top-k=8`이었다면 inference에서도 보통 8개 expert를 호출합니다. 단순히 4개로 줄이면 compute는 절반으로 줄지만 router probability를 선택된 네 expert에 다시 normalization하면서 **expert branch 전체 gain까지 바뀌어버립니다**. 연구진은 실제 문제가 expert 수 자체뿐 아니라 이 normalization calibration이라는 점을 분리했습니다. citeturn151187view1

제안 방식은 실행할 expert는 `k₁=4`개만 고르되 normalization probability mass는 더 큰 `k₂`, 예를 들어 16개 expert까지 사용합니다. parameter도 추가되지 않고 별도 training도 없습니다. Qwen3.6-35B-A3B에서 8→4 experts로 줄였을 때 일반 renormalization은 MMLU가 **4.65점 하락**했지만 제안 방식에서는 **0.35점 감소**에 그쳤고 routed-expert compute는 절반이 됐습니다. Qwen3.5-397B-A17B에서도 10→5 experts에서 적절한 reference set을 사용하면 하락폭이 0.55점이었습니다. citeturn151187view1

또 하나 중요한 발견은 perplexity와 downstream accuracy가 선호하는 `k₂`가 달랐다는 점입니다. 즉 MoE compression 설정을 WikiText perplexity 같은 unlabeled metric 하나만 보고 선택하면 잘못된 설정을 고를 수 있습니다.

B200에서 MoE serving을 benchmark한다면 상당히 좋은 실험 후보입니다. 기존 top-k와 `k₁/k₂` 분리 방식을 비교하면서 `tokens/s`, `expert GEMM time`, `all-to-all bytes`, `MMLU/task metric`을 같이 측정하면 **model architecture와 inference system 양쪽을 묶은 실험**이 됩니다.

다만 논문 수준의 아이디어라 vLLM/SGLang에 바로 옵션 하나로 존재하는 것은 아닙니다. 실제 kernel/router path에 적용하려면 expert weighting 구현을 수정해야 하고, 특히 fused MoE kernel과의 호환성을 확인해야 합니다.

원문은 url논문 · Training-Free Halving of Activated Experts in Fine-Grained Mixture-of-Experts Modelsturn151187view1입니다.

## 5. MoE training Allgather를 “lossless compression”으로 3.7배 — iteration 간 exponent가 거의 안 바뀐다는 관찰 ★★★★★

**CIERA**는 distributed training 쪽에서 오늘 가장 흥미로운 시스템 논문입니다. FSDP/sharded MoE에서는 expert weight가 GPU에 쪼개져 있기 때문에 해당 layer를 계산할 때 전체 weight를 다시 모으는 Allgather가 필요하고, 이 communication이 iteration time 상당 부분을 먹을 수 있습니다. citeturn151187view5

CIERA의 관찰은 단순하지만 독특합니다. warmup 이후 floating-point weight의 **exponent bit는 iteration 사이에서 대부분 바뀌지 않는다**는 것입니다. 그래서 이전 iteration의 exponent를 receiver가 cache하고, exponent가 그대로인 weight는 sign+mantissa만 전송한 뒤 bitwise 동일하게 재구성합니다. layer shape와 bandwidth를 보고 compression이 이득일 때만 적용하고, compression·Allgather·compute도 overlap합니다. citeturn151187view5

OLMoE-1B-7B, 16 GPU 실제 실험에서 lossless baseline 대비 **3.70×**, lossy baseline 대비 3.68× speedup을 보고했고, trace-driven simulation에서는 128 GPU에서 각각 4.28×/4.42×까지 예상합니다. 중요한 점은 evaluated runs에서 parameter reconstruction이 **bitwise exact**였다는 것입니다. citeturn151187view5

이 연구에서 바로 가져갈 수 있는 원칙은 “gradient/parameter communication을 압축하려면 무조건 low-bit approximation을 해야 하는 것은 아니다”입니다. **iteration 간 temporal redundancy**를 활용하는 방법도 있습니다. 특히 MoE처럼 expert matrix가 크고 parameter update가 상대적으로 작은 training regime에서는 이런 접근이 잘 맞을 수 있습니다.

다만 128 GPU 수치는 simulation이고 실제 측정은 16 GPU입니다. B200/NVLink/NVSwitch 환경처럼 interconnect bandwidth가 매우 높은 경우 compression kernel 비용 대비 communication savings가 줄 수도 있으므로 `compression time / NCCL time / overlap efficiency`를 반드시 따로 측정해야 합니다.

원문은 url논문 · CIERA: Cross-Iteration Exponent Reuse for Lossless Allgather in Sharded MoE Trainingturn151187view5입니다.

## 6. Puffin-World: “World Model = 다음 RGB frame 생성”에서 physics + geometry + appearance로 확장 ★★★★☆

멀티모달 쪽에서는 **Puffin-World**가 재미있습니다. 많은 world model이 다음 frame의 appearance를 중심으로 학습하는 반면 Puffin-World는 세계를 세 가지 native state로 분해합니다.

`physics = gravity field + latitude`
`geometry = depth`
`appearance = RGB`

그리고 absolute physical orientation과 relative camera motion을 동시에 표현하는 **Omni-Camera** representation을 사용해 perception, camera-controllable generation, image/text-to-3D generation과 reconstruction을 하나의 framework로 묶습니다. citeturn298003view0turn298003academia24

데이터 규모도 큽니다. Puffin-Cam-15M은 약 90만 panorama에서 만든 1,500만 vision-language-camera triplet이고, Puffin-Traj-1M은 회전·상하 이동·360도 탐색 등이 포함된 100만 trajectory입니다. 추가로 28개의 기존 public dataset 약 **4,450만 image**에 roll/pitch/vertical-FoV annotation도 생성했다고 공개했습니다. 코드, 모델 weight, dataset construction script도 공개되어 있습니다. citeturn546230view3turn738120view0

중요한 방향은 world model이 단순한 video generator에서 **explicit state model**로 이동한다는 것입니다. 로봇·embodied agent 입장에서는 “앞으로 장면이 어떻게 보일까?”뿐 아니라 “카메라/로봇의 orientation은 무엇이고, geometry는 어떻게 변하며, 이 state에서 어떤 action이 가능한가?”가 필요하기 때문입니다.

하지만 현재 model이 말하는 physics는 gravity와 latitude 중심이며 **dynamic object physics, collision, contact, force dynamics**까지 모델링하는 것은 아닙니다. 연구진도 static scene과 제한된 physical state를 현재 한계로 명시합니다. 따라서 “physics world model”이라는 표현을 일반-purpose simulator처럼 받아들이면 과장입니다. citeturn298003view0

## 7. Agent memory가 권한을 “세탁”한다 — false permission이 한 번 저장되면 98.6%가 그대로 실행 ★★★★★

**Agent Memory Is a Surface for Endogenous Authorization Laundering**은 에이전트 memory를 보안 component로 봐야 한다는 점을 아주 명확하게 보여줍니다.

예를 들어 과거 기록에는 “A 계정은 서버 재부팅 권한이 없다 → 임시로 권한 부여 → 이후 권한 철회”라는 history가 존재한다고 합시다. LLM memory writer가 이를 계속 요약·갱신하다가 “A는 서버 재부팅 권한이 있다”라는 잘못된 persistent fact를 남기면, 나중의 executor는 그 memory를 정상적인 authorization evidence로 사용할 수 있습니다. 공격자가 prompt injection을 넣지 않아도 **agent 자신의 memory compression 과정에서 권한이 생성**되는 것입니다. citeturn151187view4

EAL-Bench에서 5개 memory writer 모델과 2개 executor를 procurement, cybersecurity, finance에 적용했는데 incremental memory update 방식에서 unauthorized request 중 최대 **50.2%에 false authority가 생성**됐습니다. 더 심각한 것은 false authority가 memory에 들어간 뒤 executor가 실제 unauthorized action을 수행한 비율이 **98.6%**였다는 것입니다. citeturn151187view4

해결책도 상당히 distributed-systems스럽습니다. `현재 권한 상태`만 memory에 저장하는 대신 **권한을 생성한 source event를 함께 보존**하거나 bounded event sourcing으로 grant/revoke history를 추적하면 laundering이 크게 줄었습니다. 대신 legitimate action까지 차단되는 false reject가 증가하는 safety-utility tradeoff가 나타났습니다. citeturn151187view4

Agent architecture에서는 따라서

`memory = knowledge`
`authorization = source-of-truth ledger`

로 분리하는 것이 좋습니다. “사용자가 전에 허락했다”고 LLM memory가 말하는 것과 실제 ACL/credential/policy engine에서 현재 허가되어 있는지는 반드시 별도로 검증해야 합니다.

EAL-Bench 코드도 공개되어 있어서 memory implementation 비교 benchmark로 바로 사용할 수 있습니다. citeturn361195search2

## 8. ContextPipe: Agent context를 “대화 이어붙이기”가 아니라 데이터베이스 query optimizer처럼 다뤄라 ★★★★★

**ContextPipe**는 agent runtime에서 제가 특히 좋아할 만한 방향입니다. long-horizon agent에서는 매 turn마다 `system + history + memory + tool outputs + files`를 어떤 순서와 양으로 넣을지가 점점 복잡해집니다. 보통 이 로직이 prompt builder, compaction code, cache workaround 곳곳에 흩어져 있는데, 연구진은 이를 **relational database query execution과 같은 문제**라고 봅니다. citeturn151187view2

ContextPipe는 context construction을

`Plan → Bind → Optimize → Execute → Feedback`

다섯 단계로 나눕니다. structured data-source catalog를 두고, token budget과 byte-sensitive prompt cache를 고려해 deterministic optimizer가 어떤 context source를 얼마나 포함할지 정합니다. 그리고 SQL의 `EXPLAIN ANALYZE`처럼 “왜 이 문서와 memory가 이번 prompt에 들어왔는지”를 trace로 남겨 replay와 debugging이 가능하도록 합니다. citeturn151187view2

SWE-bench Pro Qutebrowser subset의 preliminary evaluation에서는 단순 append-only context 방식보다 **전체 token 31% 감소, LLM call 23% 감소, response time 9% 감소**를 보고했습니다. 대신 KV cache hit ratio는 감소했습니다. 즉 context를 공격적으로 정리하면 prompt 자체는 작아지지만 stable prefix가 줄면서 cache economics가 나빠질 수 있다는 흥미로운 trade-off입니다. citeturn151187view2

실무에서는 이 논문을 그대로 구현할 필요까지는 없습니다. 다만 agent harness의 context를 하나의 문자열로 보지 말고

`system`
`task`
`project_state`
`recent_events`
`retrieved_memory`
`tool_schema`
`artifacts`

같은 **typed data source**로 정의하고 각 source에 token cost, freshness, priority, cache stability를 부여하는 것만으로도 architecture가 상당히 깨끗해집니다.

현재 평가는 작고 preliminary합니다. 특히 token 절감과 cache hit 감소 중 실제 API 비용이 어느 쪽이 유리한지는 provider의 prompt-cache 가격 정책과 trajectory 길이에 따라 달라질 가능성이 큽니다.

## 오늘 꼭 볼 것 3개

1. **Same Request, Different Answer** — 지금 inference benchmark를 한다면 바로 실험 설계에 영향을 줍니다. 특히 quantization + prefix cache 조합에서 “같은 요청 = 같은 모델 실행”이라는 가정이 무너질 수 있다는 점이 중요합니다.
2. **Training-Free Halving of Activated Experts** — MoE 모델을 실제 GPU에서 돌릴 계획이라면 `top-k`를 단순 고정값이 아니라 **compute/quality knob**로 다룰 수 있다는 굉장히 좋은 연구 주제입니다.
3. **vLLM TT Plugin** — Tenstorrent 자체를 쓰지 않더라도 vLLM이 GPU와 매우 다른 accelerator topology를 어떻게 plugin interface로 흡수했는지 읽어보면 inference runtime architecture 공부에 좋습니다.

## 오늘 직접 해볼 만한 실습 — `Prefix Cache × Quantization` 2×2 재현성 벤치마크

오늘 실습은 현재의 vLLM benchmark 흐름과 가장 잘 연결됩니다. 동일한 모델 하나를 **BF16과 4-bit(or FP8)** 두 형태로 준비하고 각 모델에서 prefix caching을 `ON/OFF`로 나눠 네 조건을 만드십시오.

각 조건에서 동일 prompt 20~50개를 동일 seed, temperature 0, batch size 1로 세 번 반복하면서 단순 최종 text만 비교하지 말고

`first divergent token`
`full output hash`
`tool-call trajectory`
`TTFT / TPOT`
`prefix cache hit`
`GPU memory`

를 기록하는 것이 핵심입니다.

만약 `BF16/no-cache`는 완전히 동일하고 `4-bit/cache`에서 trajectory divergence가 크게 증가한다면 오늘 3번 논문의 현상을 자신의 serving stack에서 직접 재현한 것입니다. 이후 B200 2장 환경의 vLLM benchmark에서는 **cache configuration까지 실험 메타데이터에 저장하는 습관**을 잡을 수 있어서, 이후 논문이나 기술 보고서의 reproducibility도 훨씬 좋아집니다. memcite
