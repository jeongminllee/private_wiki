# AI 엔지니어 데일리 브리핑

**2026년 8월 11일 화요일**
**분석 범위:** 8월 10일까지 공개·갱신된 공식 발표, 모델 카드, 기술 자료와 최신 논문

오늘은 꽤 볼거리가 많습니다. 가장 큰 흐름은 **“에이전트용 모델”이라는 말이 단순히 모델 가중치를 뜻하지 않게 됐다는 것**입니다. Meta는 30B 모델과 멀티모달 encoder, 4-bit 배포 artifact, speculative drafter까지 묶어 로컬 agent stack을 공개했고, 실제 GitHub Copilot의 대규모 production trace를 분석한 Microsoft 연구에서는 coding agent가 일반 chatbot과 완전히 다른 KV-cache·tool-call·idle-time 특성을 갖는다는 사실이 정량적으로 확인됐습니다. 동시에 장기 agent가 경험을 “skill”로 승격하는 과정 자체가 새로운 보안 경계로 떠오르고 있습니다. ([Hugging Face][1])

## 1. 필독 | Meta Muse Glimmer 30B — 24GB급 로컬 GPU를 겨냥한 ‘에이전트 패키지’

Meta가 8월 10일 **Muse Glimmer 30B**를 open-weight로 공개했습니다. Apache 2.0 라이선스이며, 약 29.6B 파라미터의 dense causal Transformer에 약 1.8B 규모 ViT-G/14 perception encoder를 결합했습니다. Text+image 입력, text 출력, 131K+ context를 지원하며 Muse Spark에서 distillation됐습니다. Meta는 OpenClaw, Hermes Agent 같은 agent scaffold와의 사용을 명시적으로 지원합니다. ([Hugging Face][1])

흥미로운 것은 **체크포인트 하나만 공개한 것이 아니라 inference system을 함께 설계했다는 점**입니다. 약 4-bit 양자화한 언어 모델은 20GB 아래로 줄어들며, Meta는 KV cache·vision encoder·speculative drafter를 포함해 24GB 또는 32GB VRAM 안에 배치하는 구성을 제공합니다. 공식 측정에서 `K-Quant-Dynamic`은 15개 benchmark 평균 정확도 저하 0.2%, `K-Quant-17GB`는 1.0%라고 보고했습니다. ([Hugging Face][1])

특히 **DFlash speculative drafter**가 눈에 띕니다. 5-layer companion model이 16-token block을 한 번에 제안하고 본 모델이 이를 병렬 검증합니다. Meta 측 batch=1·greedy 실험에서는 RTX 5090에서 74.9 tok/s가 DFlash 사용 시 평균 233.4 tok/s로 올라가 **3.1배**를 기록했습니다. M4 Max에서는 23.7→37.8 tok/s, M5 Max에서는 26.6→50.2 tok/s였습니다. RTX 측정은 llama.cpp, Mac 측정은 ExecuTorch를 사용했으므로 이 숫자를 서로 같은 runtime benchmark로 비교해서는 안 됩니다. ([Hugging Face][1])

모델 성능도 단순 chat benchmark보다 agent 측에 초점이 맞춰져 있습니다. Meta 자체 결과에서 MCP Atlas 75.5, DeepSearch QA 74.6, SWE-Bench Pro 51.2, SWE-Bench Verified 76.0을 기록했습니다. 다만 Qwen3.6-27B가 OSWorld-Verified·TerminalBench·SkillsBench 등 일부 task에서는 Glimmer보다 높았기 때문에 “30B급에서 전 영역 최고”라고 표현할 수는 없습니다. ([Hugging Face][1])

### 엔지니어 관점

이 릴리스의 핵심은 **local agent 모델의 비교 단위가 이제 `checkpoint`가 아니라 `checkpoint + quantization + drafter + runtime + scaffold`가 된다는 점**입니다.

예를 들어 같은 Glimmer라도 다음은 사실상 다른 시스템입니다.

```text
BF16 + SGLang
K-Quant + llama.cpp
K-Quant + DFlash
GGUF + OpenClaw
멀티모달 입력 + long context
```

따라서 벤치마크에서는 모델 이름만 기록하지 말고 `quantization`, `runtime`, `drafter`, `reasoning_strength`, `context_length`, `agent scaffold`를 함께 고정해야 합니다.

안전성도 확인할 필요가 있습니다. Meta 자체 Siren AgentDojo 평가에서 Glimmer의 attack success rate는 28.4%였으며, Meta 역시 모델 단독 endpoint가 아니라 추가 guardrail을 포함한 전체 시스템으로 배포할 것을 권고합니다. 즉 “로컬이므로 안전하다”와 “데이터가 외부 API로 나가지 않는다”는 서로 다른 주장입니다. ([Hugging Face][1])

**후속 관찰 포인트:** DFlash의 긴 coding trajectory acceptance rate, vLLM·SGLang 구현 성숙도, 128K에서 실제 KV memory, Q4 양자화가 function-call schema에 주는 영향, Muse Spark open-weight 공개.

**원문:** **[모델 카드] Muse Glimmer 30B** ([Hugging Face][1]) · **[NVIDIA 기술 가이드] 로컬 Glimmer 배포** ([NVIDIA Developer][2])

## 2. 연구 | Claude가 리만 가설을 풀지는 못했지만, 41.6% → 67.2% 하한을 만들고 Lean 증명까지 공개

Anthropic은 8월 10일 unreleased research version Claude가 리만 가설 자체를 증명하려다 실패했지만, 관련된 중요한 결과를 얻었다고 발표했습니다. 리만 제타 함수의 영점 가운데 critical line 위에 존재하는 비율에 대한 기존 unconditional lower bound를 **41.6%에서 67.2%로 높였습니다.** Anthropic의 두 수학자가 논문을 검토했고, Brian Conrey와 Dan Goldston도 짧은 기간 동안 결과를 살펴봤습니다. ([Anthropic][3])

여기서 AI 엔지니어에게 더 흥미로운 부분은 결과의 크기보다 **검증 파이프라인**입니다. Anthropic은 결과를 설명하는 자연어 논문만 공개한 것이 아니라 Lean 4/Mathlib 형식 증명을 함께 공개했습니다. GitHub artifact는 Theorem A–E 전체에 대한 `sorry` 없는 formalization을 포함하며, headline theorem들은 별도의 사용자 정의 axioms 없이 Lean의 표준 axioms만 사용한다고 명시합니다. strongest theorem은 0.67250…의 하한을 형식화합니다. ([GitHub][4])

이 구조는 AI-for-science의 이상적인 역할 분리를 보여줍니다.

```text
Discovery model
      ↓
새로운 아이디어·증명 후보
      ↓
전문가 검토
      ↓
Formal specification
      ↓
Lean kernel verification
```

모델 자신이 “증명이 맞다”고 판단하는 것이 verification이 아니라는 점이 중요합니다. 마지막 판정은 LLM과 독립적인 proof kernel이 수행합니다.

### 실제 ML·소프트웨어 업무에 적용한다면

이 사고방식은 수학에만 해당하지 않습니다. AI가 생성한 결과물을 **검증 가능한 artifact로 변환**하면 됩니다.

코드라면 `patch → type checker → static analyzer → test → property test`, 인프라라면 `policy proposal → schema validation → simulator → admission controller`, 데이터 분석이라면 `answer → source-cell lineage → deterministic recomputation`으로 구성할 수 있습니다.

즉 앞으로 강력한 AI 시스템의 중요한 설계 원칙 중 하나는:

> **Generator와 verifier를 가능한 한 다른 실패 모드를 가진 시스템으로 구성하는 것**

입니다.

### 주의할 점

“Claude가 리만 가설을 해결했다”는 해석은 명백히 틀립니다. Anthropic도 리만 가설에는 성공하지 못했다고 명시하며, 이번 기법이 리만 가설 자체의 증명으로 이어질 것으로 기대하지 않는다고 설명합니다. 또한 Lean formalization은 명시된 형식 theorem을 검증하는 강력한 증거지만, 연구 결과의 수학사적 중요성·해석·선행연구와의 관계까지 자동으로 평가해주는 것은 아닙니다. ([Anthropic][3])

**후속 관찰 포인트:** 독립 수학자들의 장기 검토, 연구 모델 공개 여부, AI가 발견한 새로운 수학 결과에서 formal proof가 표준 artifact가 되는지.

**원문:** **[공식 연구 발표] Anthropic mathematical capabilities** ([Anthropic][3]) · **[GitHub·형식 검증] Zeta23 Lean proof** ([GitHub][4])

## 3. GPU·ML 인프라 | GitHub Copilot 95조 토큰 trace가 보여준 것: Agent KV cache는 ‘세션’이 아니라 ‘turn’ 단위로 움직인다

Microsoft Research가 GitHub Copilot coding agent의 production workload를 분석했습니다. 규모가 상당합니다. 2026년 6월 한 주에서 sampling한 데이터가 **320만 사용자, 1,300만 session, 7억6,100만 LLM call, 950억?가 아니라 95T, 즉 95조 token, 약 7억7,500만 tool invocation**입니다. ([Microsoft][5])

가장 중요한 결과는 agent workload가 일반 chat과 구조적으로 다르다는 점입니다. 전체 LLM call 가운데 **87%가 사용자가 직접 시작한 것이 아니라 agent의 auto-continuation**에서 발생했습니다. 평균적으로 한 번 사용자 message가 들어온 뒤 agent가 약 6.6회의 LLM call을 스스로 수행했고, LLM call과 tool call의 비율도 거의 1:1이었습니다. ([arXiv][6])

Serving 관점에서는 KV cache 결과가 특히 중요합니다. 같은 turn 내부에서는 평균 **90%의 KV-cache hit**가 발생하지만, user turn 경계를 지나가면 약 **55%**까지 떨어집니다. Model switch나 context compaction이 일어나면 cache 재사용성이 더 크게 무너집니다. ([Microsoft][5])

또 agent가 사용자에게 답을 돌려준 뒤에는 수분 단위의 긴 idle 구간이 나타났고, 연구진의 가벼운 idle predictor가 전체 idle time의 86~90%를 포착했습니다. 이는 agent serving에서 **KV를 계속 HBM에 보관할지, DRAM/SSD로 내릴지 결정할 수 있는 시간 창**이 상당히 크다는 의미입니다. ([Microsoft][5])

### 시스템 설계에 적용하면

기존 cache 정책이 단순 LRU라면 다음 방향을 실험할 가치가 있습니다.

```text
같은 turn 안
→ KV 적극 유지

tool 실행 대기
→ 짧은 idle, 유지 가능

user에게 control 반환
→ idle prediction

장기 idle 예상
→ KV demote / offload

model switch / compaction
→ stale KV 정리
```

그리고 telemetry에 단순 cache-hit 하나가 아니라 `within_turn_hit`, `cross_turn_hit`, `idle_duration`, `model_switch`, `context_compaction`, `reload_TTFT`를 분리해야 합니다.

논문에서 P90 turn은 16회에 가까운 LLM call과 21회가 넘는 tool invocation, 100만 token 이상의 prompt traffic을 만들었습니다. Agent가 실패 loop에 빠지는 `Deep-loop w/failures`는 median 36 LLM calls와 34 tool batches를 발생시켜, **실패 복구가 곧 compute amplification**이 될 수 있음을 보여줍니다. ([arXiv][6])

### 주의할 점

이 데이터에는 prompt/response 내용이나 task success signal이 없기 때문에 높은 resource consumption이 실제로 더 좋은 결과를 만들었는지는 판단할 수 없습니다. 또한 GitHub Copilot이라는 특정 agent의 2026년 workload이므로 모든 agent framework의 분포와 동일하다고 보면 안 됩니다. ([arXiv][6])

**후속 관찰 포인트:** session-aware radix cache와 실제 production trace의 결합, KV tiering, user idle prediction 기반 GPU memory reclamation, 실패 loop용 compute circuit breaker.

**원문:** **[Microsoft Research] Agentic Coding in the Wild** ([Microsoft][5]) · **[논문] arXiv 원문** ([arXiv][7])

## 4. ML 인프라 | LLMRouter: “어떤 모델을 부를 것인가”를 하나의 sequential decision 문제로 통합

8월 7일 공개된 **LLMRouter**는 난립하고 있는 model router 구현을 하나의 프레임워크로 정리하려는 연구입니다. 저자들은 routing을 `context encoder → model encoder → scoring → decision rule → learning signal`의 다섯 요소로 분해하고, single-turn뿐 아니라 multi-turn·personalized routing까지 같은 formulation으로 다룹니다. ([arXiv][8])

함께 공개한 `xRouteBench`에는 일반 LLM routing뿐 아니라 memory-augmented, vision, time-series, personalized routing task가 포함되고, 오픈소스 infrastructure에는 16개 이상의 대표 router가 구현됐습니다. 저자들의 실험에서 learned router는 strongest fixed-model baseline보다 상대적으로 14.6% 높은 결과를 보였고, 비용 제한이 강할수록 lightweight router가 경쟁력을 보였으며 user-conditioned routing은 personalization을 꾸준히 개선했다고 보고했습니다. ([arXiv][8])

### 왜 중요한가

지금 많은 agent 시스템의 router는 사실상 다음 수준입니다.

```python
if task_is_hard:
    use_big_model()
else:
    use_small_model()
```

하지만 multi-turn agent에서는 결정 상태가 훨씬 많습니다.

```text
현재 task 난이도
+ 남은 budget
+ 이전 모델의 실패 여부
+ cache 상태
+ 사용자 특성
+ latency SLO
+ tool 결과
```

따라서 routing을 단순 classifier가 아니라 **시간에 따라 상태가 변하는 sequential decision process**로 보는 접근이 더 적절합니다.

Sonnet 5처럼 가격이 변경되거나 새로운 local model이 출시되면 optimal routing boundary도 그대로 유지되지 않습니다. Router도 model registry와 pricing table 변경에 따라 재평가되어야 합니다. 이 부분은 LLMRouter의 문제 설정과 오늘의 가격 변화를 종합한 실무적 해석입니다. ([arXiv][8])

### 주의할 점

14.6%는 연구진의 benchmark와 비용 정의에 기반한 상대적 개선입니다. 실제 운영에서는 model API latency, cache pricing, batch discount, failure/retry, tool cost까지 포함해야 합니다. 또한 너무 복잡한 router가 오히려 작은 요청의 latency를 늘릴 수 있으므로 **router 자체의 inference cost도 비용 함수에 포함**해야 합니다.

**후속 관찰 포인트:** agent trajectory router, speculative model escalation, cache-aware routing, local↔cloud 모델 routing.

**원문:** **[논문] LLMRouter** ([arXiv][8])

## 5. AI 보안 | “경험을 모아 자동으로 Skill을 개선한다”가 새로운 supply-chain attack surface

`When Experience Becomes Instruction`은 self-evolving agent의 꽤 위험한 약점을 다룹니다.

Self-evolving skill 시스템은 agent가 실제 task를 수행하며 얻은 trajectory를 분석한 뒤, 반복적으로 유용해 보이는 패턴을 **영구적인 skill instruction**으로 승격합니다. 문제는 여기서 untrusted experience가 trusted instruction으로 바뀐다는 점입니다. ([arXiv][9])

연구가 제시한 `PoisonedEvolution` 공격자는 skill bank 자체를 편집하거나 내부 evolution algorithm을 볼 필요가 없습니다. 공격자는 단지 정상적인 experience pool에 제한된 수의 trajectory를 제공하고, 특정 행동이 반복적으로 유용한 것처럼 보이게 만듭니다. ([arXiv][9])

저자들의 inert-canary 실험에서 공격 trajectory가 전체 evidence의 10%일 때 SkillClaw의 여섯 LLM evolver에서 **600회 중 546회, 91%**에서 목표 behavior가 skill에 포함됐습니다. 구조가 다른 Trace2Skill에서도 61.5%가 발생했습니다. 30개 trajectory batch에서는 서로 일관된 세 개의 공격 기록만으로도 상당한 효과가 나타났고, 단일 기록은 훨씬 약했습니다. ([arXiv][9])

### 핵심 보안 교훈

다음 변환을 **학습 기능이 아니라 privilege escalation**으로 보아야 합니다.

```text
temporary trajectory
        ↓
experience
        ↓
persistent memory
        ↓
shared skill
        ↓
future agent behavior
```

특히 여러 사용자의 경험을 한 skill repository로 합치는 경우, 한 사용자가 남긴 행동 패턴이 다른 사용자의 agent에도 배포될 수 있습니다.

따라서 skill artifact에는 최소한 `source_trajectory`, `source_principal`, `promotion_reason`, `evidence_count`, `review_status`, `skill_version`, `expiry`가 필요합니다. 새로운 skill을 즉시 전역 배포하지 말고 quarantine에서 기존 task와 adversarial counterexample을 재실행한 뒤 승격시키는 구조가 안전합니다.

또 “세 번 반복됐으므로 유용한 패턴” 같은 빈도 기반 heuristic만으로 promotion해서는 안 됩니다. **서로 독립된 principal에서 나온 증거인지**도 중요합니다.

### 주의할 점

논문의 공격 성공률은 실제 악성 운영환경이 아니라 inert canary를 사용한 연구 환경의 수치입니다. 91%를 실제 서비스 compromise 확률로 해석하면 안 됩니다. 하지만 경험→skill 변환이 보안 경계라는 지적은 꽤 강력하며, 유사한 별도 연구인 SkillJack도 같은 방향의 위험을 보고하고 있습니다. ([arXiv][9])

**후속 관찰 포인트:** 여러 사용자 identity를 고려한 promotion, signed trajectory provenance, skill diff security review, poisoning-resistant skill evolution.

**원문:** **[논문] Trajectory Poisoning in Self-Evolving Agent Skill Systems** ([arXiv][9])

## 6. 멀티모달 | StreamArena: 1분짜리 동영상 벤치마크로는 ‘항상 보고 있는 에이전트’를 평가할 수 없다

StreamArena는 streaming video agent를 **hour-scale 환경**에서 평가하는 새로운 benchmark입니다. 243개의 full-length video가 평균 88.8분이며, 3,646개의 open-ended QA가 real-time perception, 과거 사건 회상, proactive interaction, multimodal tool use를 평가합니다. ([arXiv][10])

저자들이 기존 평가의 문제로 지적하는 부분이 흥미롭습니다. 짧은 clip과 multiple choice 위주의 benchmark에서는 **마지막 네 frame만 보는 단순 baseline이 복잡한 streaming system과 비슷하거나 더 좋은 결과를 낼 수 있습니다.** 하지만 실제 continuous agent는 한 시간 전의 사건도 기억해야 합니다. ([arXiv][10])

실험에서는 최근 frame만 보존하는 모델은 먼 과거의 사건을 놓치고, 과거 정보를 text로 압축하는 방식은 visual evidence를 잃으며, image memory를 반복적으로 압축하면 fine-grained detail이 소실되는 문제가 나타났습니다. ([arXiv][10])

연구진이 제안한 StreamMind는 이를 두 계층으로 나눕니다.

```text
Frontend workers
→ 실시간 인지
→ 빠른 interaction
→ proactive alert

Backend workers
→ persistent multimodal memory
→ 과거 사건 retrieval
→ external search
```

즉 모든 video token을 거대한 context에 계속 넣는 대신 **stream processing과 비슷한 asynchronous architecture**를 사용합니다. 저자들은 이 방식이 네 평가 capability 모두에서 기존 baseline을 앞섰고, persistent state 재사용으로 query latency도 낮췄다고 보고했습니다. ([arXiv][10])

### 실무 적용

CCTV, 회의 기록, 로봇, screen-watching agent를 개발한다면 `accuracy` 하나보다 다음이 중요합니다.

`event_recall(time_gap)`, `memory_bytes/hour`, `query_latency`, `compression_loss`, `proactive_false_alarm`, `visual_evidence_retrieval`, `tool_cost`.

특히 text summary만 장기 memory로 사용하는 시스템이라면 “빨간 차량의 번호판”, “그래프의 특정 위치”, “UI 버튼 상태” 같은 visual detail이 summary 과정에서 사라지는지 별도 테스트가 필요합니다.

### 주의할 점

StreamArena는 아직 초기 arXiv benchmark이며, real-world continuous video의 모든 상황을 대표하지는 않습니다. StreamMind가 benchmark에서 우수하다고 해서 하나의 architecture가 모든 robotic·surveillance workload에 최적이라는 의미도 아닙니다.

**후속 관찰 포인트:** video KV/cache tiering, event-triggered retention, multimodal memory compression, 개인정보 삭제와 장기 visual memory의 충돌.

**원문:** **[논문] StreamArena** ([arXiv][10])

## 7. 산업·FinOps | Claude Sonnet 5의 $2/$10 가격이 ‘이벤트 가격’이 아니라 영구 가격으로

Anthropic은 8월 10일 Sonnet 5의 introductory pricing을 **영구 가격으로 전환**했습니다. 입력은 100만 token당 $2, 출력은 $10입니다. 기존 계획은 9월 1일부터 $3/$15로 올리는 것이었지만 이 계획을 취소했습니다. Opus 4.8은 현재 $5/$25입니다. ([Anthropic][11])

표면적으로는 단순 가격 뉴스지만 agent system에서는 routing threshold를 바꿀 수 있는 변화입니다.

예를 들어 지금까지:

```text
저난도 → Sonnet
고난도 → Opus
```

였다면, Sonnet의 높은 effort를 더 오래 사용한 뒤 Opus로 escalate하는 것이 경제적으로 유리할 수 있습니다. Anthropic 자체 cost-performance 그래프에서도 Sonnet 5의 high-effort가 일부 task에서 Opus 4.8 수준에 도달한다고 주장합니다. 다만 이는 Anthropic의 benchmark이므로 동일한 task/harness에서 직접 재측정해야 합니다. ([Anthropic][11])

여기에는 중요한 함정도 있습니다. Sonnet 5는 tokenizer가 바뀌어 **동일한 입력이 이전 Sonnet보다 약 1.0~1.35배 많은 token**으로 변환될 수 있다고 Anthropic이 명시합니다. 따라서 명목 가격만 보고 기존 workload 비용에 `$2/$10`을 곱하면 실제 비용을 잘못 추정할 수 있습니다. ([Anthropic][11])

실제 FinOps에서는 다음 식을 봐야 합니다.

```text
cost_per_success =
(model tokens
 + retry
 + tool-triggered context
 + compaction
 + failed runs)
 / successful tasks
```

즉 **token 가격 하락과 task 비용 하락은 같은 말이 아닙니다.**

### 추가로 눈여겨볼 점

Anthropic은 Sonnet 5 출시 글의 BrowseComp 결과도 6월 말 한 차례 수정했습니다. 기존 단순 methodology를 대신해 10M token budget, compaction, programmatic tool calling을 사용하는 표준 agentic-search methodology로 다시 계산했습니다. 이것 역시 모델 비교에서 harness와 inference budget을 함께 봐야 한다는 좋은 사례입니다. ([Anthropic][11])

**후속 관찰 포인트:** Sonnet↔Opus router의 cost-per-success, tokenizer 변경이 long-context 비용에 미치는 영향, effort별 latency와 cache usage.

**원문:** **[공식 발표·가격 변경] Claude Sonnet 5** ([Anthropic][11])

# 오늘의 실습 | Muse Glimmer에서 ‘DFlash가 실제 Agent 업무도 3배 빠른지’ 확인하기

오늘 실습은 단순 `tokens/s` 벤치마크보다 조금 더 실전적으로 해보는 것을 추천합니다.

공식 `K-Quant-17GB` 또는 24GB 대상 quantization을 사용해 **DFlash ON/OFF 두 환경**을 준비합니다. 동일 runtime, 동일 prompt, 동일 context와 동일 sampling을 사용합니다. Meta의 3.1배 수치는 batch=1·greedy·llama.cpp 조건이므로 먼저 그 조건에 가깝게 재현한 뒤 agent workload로 확장하는 편이 좋습니다. ([Hugging Face][1])

테스트 작업은 세 종류면 충분합니다.

```text
A. 순수 생성
8K context → 2K output

B. Coding
repository 탐색 → 파일 수정 → test

C. Agent
search/read tool 5~10회 → 최종 답변
```

각 조건을 5회 이상 반복해서 다음을 기록합니다.

```text
TTFT
output_tokens_per_second
wall_clock_time

draft_tokens
accepted_tokens
acceptance_rate

tool_wait_time
LLM_active_time

peak_VRAM
strict_task_success
```

여기서 가장 중요한 지표는 `tokens/s`가 아니라:

```text
wall_clock_time_per_success
```

입니다.

예를 들어 DFlash가 decode를 3배 빠르게 해도 전체 agent 시간이 다음과 같다면:

```text
LLM     4초 → 1.3초
tools   15초
tests   10초
```

실제 end-to-end 개선은 3배가 아니라 약 10% 수준일 수 있습니다.

반대로 code generation처럼 LLM decode 비중이 크다면 상당한 이득이 나타날 수 있습니다. 또한 `reasoning_strength=low/high/xhigh`를 하나 더 축으로 추가하면 **reasoning budget × speculative decoding × strict success**의 관계까지 볼 수 있습니다. Glimmer는 이 네 단계 reasoning strength를 공식 지원합니다. ([Hugging Face][1])

최종적으로 다음 세 숫자만 뽑아도 충분합니다.

```text
Speculative speedup
End-to-end agent speedup
Cost/energy per successful task
```

이 세 값이 서로 얼마나 다른지 확인하는 것이 오늘 실습의 핵심입니다. **GPU kernel이나 speculative decoder의 microbenchmark 개선이 실제 agent 생산성으로 얼마나 전달되는지를 직접 확인하는 실험**이 됩니다.
