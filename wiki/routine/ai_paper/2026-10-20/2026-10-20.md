## 1. Gemini 4 Argon 정식 공개 — frontier 모델 경쟁이 다시 “long-horizon work”로 이동 ★★★★★

Google이 10월 13일 **Gemini 4 Argon**을 개발자·기업에 글로벌 공개했습니다. Gemini API뿐 아니라 Google Antigravity, Gemini 앱, Search의 AI Mode에서도 사용할 수 있습니다. Google은 coding, finance, legal, cybersecurity, science 같은 복잡한 multi-step task를 핵심 사용처로 제시하고 있습니다. [blog.google](https://blog.google/intl/en-mena/product-updates/explore-get-answers/gemini-4-argon-built-to-solve-your-hardest-problems/?utm_source=chatgpt.com)

가격은 출시 프로모션 기준 **입력 $2 / 1M tokens, 출력 $10 / 1M tokens**, cached input은 95% 할인입니다. [blog.google](https://blog.google/intl/en-mena/product-updates/explore-get-answers/gemini-4-argon-built-to-solve-your-hardest-problems/?utm_source=chatgpt.com)

### 무엇이 바뀌었나

중요한 것은 단순히 “새 frontier model”이 아닙니다.

Argon의 공개 방식 자체가:

```text
기존

LLM
 ↓
single response
```

에서

```text
Argon
 ↓
long-horizon reasoning
 ↓
tool use
 ↓
multi-step execution
 ↓
real-world workflow
```

를 명시적으로 겨냥하고 있습니다.

Google은 10월 1일 처음 공개했을 때부터 실제 software engineering, enterprise knowledge work, cybersecurity defense를 대상으로 단계적으로 접근을 확대한다고 밝혔습니다. [blog.google](https://blog.google/intl/en-mena/company-news/technology/gemini-4-argon-our-next-era-of-frontier-intelligence/?utm_source=chatgpt.com)

### 엔지니어 관점에서 중요한 이유

이제 frontier model 비교에서 단순 benchmark score보다:

- 긴 작업에서의 state 유지
- tool-use reliability
- 실패 후 recovery
- context 관리
- 비용/성공 작업당 비용
- 실제 repository 변경 능력

이 더 중요해집니다.

즉 평가 단위가:

\[
\text{tokens/sec}
\]

에서

\[
\text{successful task / dollar}
\]

로 이동하고 있습니다.

### 실무 적용

Coding agent를 비교한다면 단순히 SWE benchmark 하나만 돌리지 말고:

```text
Task
 ├─ planning
 ├─ tool calls
 ├─ code changes
 ├─ tests
 ├─ recovery
 └─ final verification
```

전체 trace를 저장하는 것이 좋습니다.

### 주의점

Google이 발표한 benchmark 우위는 **Google 자체 평가와 선택된 benchmark에 기반한 주장**입니다. 실제 production task에서는 모델별 tool harness와 context management 차이가 결과를 크게 바꿀 수 있습니다.

# 2. NVIDIA Vera — “AI accelerator” 다음 경쟁은 Agent CPU가 된다 ★★★★★

NVIDIA가 **Vera CPU**를 agentic AI용 핵심 CPU로 포지셔닝하고 있습니다. NVIDIA는 Vera가 agent execution, reinforcement learning, data processing 같은 CPU-heavy workload를 대상으로 하며 x86 CPU 대비 최대 **1.8× faster task completion**을 주장합니다. [NVIDIA Investor Relations](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Unveils-Vera-the-CPU-for-Agents/default.aspx?utm_source=chatgpt.com)

Vera는:

- 88 Olympus cores
- 최대 1.2 TB/s LPDDR5X bandwidth
- NVLink-C2C 최대 1.8 TB/s coherent bandwidth
- CPU standalone / GPU coupled deployment

를 제공합니다. [NVIDIA Investor Relations](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Unveils-Vera-the-CPU-for-Agents/default.aspx?utm_source=chatgpt.com)

### 왜 중요한가

이건 상당히 중요한 architectural signal입니다.

LLM inference에서는 흔히:

```text
GPU
 ↓
LLM
```

만 생각하지만 실제 agent는:

```text
Agent
 ├─ Python
 ├─ shell
 ├─ browser
 ├─ database
 ├─ filesystem
 ├─ sandbox
 ├─ orchestration
 └─ LLM
```

을 반복합니다.

따라서 GPU가 아무리 빨라도 CPU-side orchestration이 느리면 전체 agent throughput은 제한됩니다.

NVIDIA가 Vera를 **“CPU for Agents”**로 명시적으로 설계한 이유가 바로 이것입니다. [NVIDIA Investor Relations](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Unveils-Vera-the-CPU-for-Agents/default.aspx?utm_source=chatgpt.com)

### 실제 시스템에서

agent throughput은 단순히:

\[
T_{\text{GPU}}
\]

가 아니라:

\[
T_{\text{agent}}
=
f(
T_{\text{LLM}},
T_{\text{CPU}},
T_{\text{tool}},
T_{\text{network}},
T_{\text{storage}}
)
\]

입니다.

특히 사용자가 진행 중인 B200/vLLM benchmark에서도 **GPU utilization이 높지 않은 구간을 CPU-side orchestration latency와 분리해서 보는 것**이 중요합니다.

### 실무 적용

agent benchmark에 다음 metric을 추가하세요.

```text
GPU busy time
CPU busy time
scheduler latency
tool execution latency
sandbox startup
network RTT
LLM TTFT
LLM TPOT
```

그렇게 해야 “GPU가 느린 것인지, GPU가 기다리고 있는 것인지”를 구분할 수 있습니다.

### 주의점

Vera의 1.8× 수치는 NVIDIA가 인용한 benchmark와 특정 agent workload에 기반합니다. **일반적인 서버 workload에서 1.8× 향상을 의미하지 않습니다.**

[공식 발표 · NVIDIA Vera CPU](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Unveils-Vera-the-CPU-for-Agents/default.aspx?utm_source=chatgpt.com)

# 3. AMD Helion — Agentic AI 인프라가 GPU rack이 아니라 CPU/GPU heterogeneous rack으로 재정의된다 ★★★★★

AMD가 10월 12일 **AMD Helion**을 공개했습니다.

핵심은 단순한 GPU 서버가 아니라 **agentic AI용 open rack-scale infrastructure blueprint**라는 점입니다. OCP 설계를 기반으로 CPU-only rack과 CPU+GPU 구성 모두를 지원합니다. [AMD Newsroom](https://newsroom.amd.com/news/open-rack-blueprint-scale-agentic-ai/?utm_source=chatgpt.com)

특히 Helion에는 **Token Router**를 포함해 frontier model과 open model 사이에서 agent model call을 routing하는 구조도 들어갑니다. [AMD Newsroom](https://newsroom.amd.com/news/open-rack-blueprint-scale-agentic-ai/?utm_source=chatgpt.com)

### 이것이 의미하는 것

AI infrastructure가:

```text
GPU Cluster
```

에서:

```text
Agent Compute Fabric

CPU
GPU
Memory
Network
Storage
Router
Scheduler
Security
```

로 이동하고 있다는 의미입니다.

AMD가 공개한 CPU-only configuration은 agent execution을 CPU 중심으로 처리하고 GPU는 필요할 때 사용하는 구조를 전제로 합니다. [AMD Newsroom](https://newsroom.amd.com/news/open-rack-blueprint-scale-agentic-ai/?utm_source=chatgpt.com)

### 왜 중요한가

Agent workload는 homogeneous하지 않습니다.

```text
Task A → CPU-heavy
Task B → GPU-heavy
Task C → network-heavy
Task D → storage-heavy
Task E → frontier-model-heavy
```

따라서 GPU cluster 하나로 모든 workload를 처리하는 것은 비효율적일 수 있습니다.

### 실무 적용

Agent infrastructure를 설계한다면 workload를 먼저 분류하세요.

| workload | 주요 자원 |
|---|---|
| planning | GPU |
| LLM inference | GPU |
| tool execution | CPU |
| sandbox | CPU + memory |
| browser | CPU/network |
| retrieval | CPU/storage |
| embedding | GPU/CPU |
| orchestration | CPU |
| KV transfer | network + memory |

이 분해가 향후 **AI factory 설계의 기본 단위**가 될 가능성이 높습니다.

### 주의점

Helion은 아직 blueprint 단계의 성격이 강합니다. 발표된 rack-level 설계가 실제 production TCO나 utilization까지 검증됐다고 해석해서는 안 됩니다.

**원문**

[공식 발표 · AMD Helion](https://newsroom.amd.com/news/open-rack-blueprint-scale-agentic-ai/?utm_source=chatgpt.com)

# 4. vLLM 0.31.0 — inference optimization의 중심이 “kernel”에서 “전체 serving system”으로 이동 ★★★★★

현재 vLLM 공식 release에서 0.31.0은 **717 commits / 307 contributors** 규모의 큰 릴리스입니다. [GitHub](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

특히 B200/vLLM을 직접 다루는 입장에서는 오늘 반드시 확인할 가치가 있습니다.

### 핵심 변화

#### Fast restart

`vllm preload`가 post-quantized weights를 GPU memory에 유지하는 weight-cache daemon을 지원합니다.

즉:

```text
기존

restart
 ↓
load weights
 ↓
quantize
 ↓
initialize
 ↓
serve
```

에서:

```text
GPU memory
    ↓
weight cache
    ↓
restart
    ↓
fast restore
```

구조로 바뀝니다. [GitHub](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

#### Speculative decoding

Model Runner V2에:

- draft-model speculative decoding
- LiLiCorr
- DFlash
- DSpark
- adaptive verification

등이 통합됐습니다. [GitHub](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

#### Large-scale serving

또:

- MoonEP
- DeepEPv2
- EPLB
- prefill context parallelism
- E/P/D disaggregation
- KV offloading

등이 들어갔습니다. [GitHub](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

### 중요한 시스템적 변화

이제 serving pipeline은:

```text
Request
  ↓
Router
  ↓
Prefill
  ↓
KV
  ↓
Decode
  ↓
Speculation
  ↓
Detokenization
```

전체를 하나의 distributed system으로 최적화해야 합니다.

즉:

\[
\text{LLM serving performance}
\neq
\text{GPU kernel performance}
\]

입니다.

### 실제로 오늘 확인할 만한 vLLM 이슈

10월 19일 기준 vLLM repository에는:

- structured-output에서 tool 사용 시 schema enforcement 문제
- DSpark가 DeepSeek-V4.1-Flash에서 출력 corruption을 일으킬 수 있다는 이슈
- structured-output decode throughput 약 2× regression 보고
- 장문 Qwen4Exp prefill에서 CUDA illegal memory access

등이 올라와 있습니다. [GitHub](https://github.com/vllm-project/vllm/issues/?utm_source=chatgpt.com)

따라서 **“최신 vLLM = 무조건 production-ready”가 아닙니다.**

릴리스 노트와 issue tracker를 함께 봐야 합니다.

# 5. Agent test-time scaling — “더 많이 생각하게 하면 좋아진다”에서 “예산을 어디에 쓸 것인가”로 ★★★★☆

Google Research의 **CATS(Cost-effective Agent Test-Time Scaling)** 연구가 오늘 특히 볼 만합니다.

연구진은 tool-augmented agent에서 단순히 inference compute를 늘리는 기존 test-time scaling이 충분하지 않다고 지적합니다. Agent에는 **token cost뿐 아니라 tool-call cost도 존재하기 때문**입니다. [Google Research](https://research.google/pubs/cost-effective-agent-test-time-scaling/?utm_source=chatgpt.com)

### 문제

일반적인 reasoning scaling은:

```text
더 많은 tokens
       ↓
더 많은 reasoning
       ↓
더 높은 accuracy
```

를 기대합니다.

하지만 agent는:

```text
reasoning
 ↓
tool call
 ↓
search
 ↓
observation
 ↓
reasoning
 ↓
tool call
```

이므로 비용이:

\[
C =
C_{\text{token}}
+
C_{\text{tool}}
\]

이 됩니다. [Google Research](https://research.google/pubs/cost-effective-agent-test-time-scaling/?utm_source=chatgpt.com)

### CATS의 핵심

CATS는 sequential exploration과 parallel exploration 사이에서 **budget을 동적으로 배분**합니다.

즉:

```text
Budget = 100

Sequential
████████████████

Parallel
████████████████

Adaptive
███████
   + 
   ███████████
```

처럼 task에 따라 예산을 배분합니다.

### 왜 중요한가

Agent system의 최적화 목표가:

> “모델에게 더 많은 token을 주자.”

가 아니라:

> **“이 task의 성공 확률을 가장 적은 token + tool call budget으로 최대화하자.”**

로 바뀝니다.

### 실무 적용

Agent scheduler에:

```text
max_tokens
max_tool_calls
max_wall_time
max_subagents
max_budget
```

을 모두 별도의 budget으로 넣어야 합니다.

특히 multi-agent system에서는:

```text
3 agents × 20 tool calls
```

가

```text
1 agent × 30 tool calls
```

보다 항상 좋은 것이 아닙니다.

**원문**

[논문 · Budget-Aware Tool Use Enables Effective Agent Scaling](https://research.google/pubs/cost-effective-agent-test-time-scaling/?utm_source=chatgpt.com)

# 6. OpenAI Agents API — agent harness가 이제 하나의 플랫폼 계층으로 독립한다 ★★★★☆

OpenAI가 9월 10일 **Agents API** 공개 beta를 발표했습니다. 핵심은 단순한 API가 아니라 **Codex를 구동하는 agent harness와 infrastructure를 개발자에게 서비스 형태로 제공하는 것**입니다. [OpenAI](https://openai.com/ko-KR/index/introducing-the-agents-api/?utm_source=chatgpt.com)

### 구성 요소가 중요합니다

OpenAI가 공개한 구조는:

```text
Agent
 ├─ Model
 ├─ Tools
 ├─ MCP
 ├─ Environment
 ├─ Context
 ├─ Subagents
 └─ Sandbox
```

입니다.

특히 multi-agent에서 subagent를 병렬 실행할 수 있고, 최대 concurrent subagent를 지정할 수 있습니다. [OpenAI](https://openai.com/ko-KR/index/introducing-the-agents-api/?utm_source=chatgpt.com)

### 왜 중요한가

예전에는 애플리케이션 개발자가 직접:

```text
tool loop
context management
retry
subagent orchestration
sandbox
state persistence
```

를 구현해야 했습니다.

이제 foundation-model 회사가 **agent runtime 자체를 product boundary로 만들고 있습니다.**

즉 향후 LLM API 경쟁은:

```text
Model API
```

가 아니라:

```text
Model
+
Agent Runtime
+
Tool Runtime
+
Sandbox
+
Observability
+
Evaluation
```

경쟁이 될 가능성이 높습니다.

### 실무 적용

자체 agent runtime을 만들고 있다면 OpenAI Agents API를 **architecture reference**로 보는 것이 좋습니다.

특히 다음을 별도 layer로 분리하세요.

- model abstraction
- tool abstraction
- execution environment
- persistent state
- subagent orchestration
- evaluator

## B200 vLLM Benchmark를 “Agent-aware benchmark”로 확장하기

현재 진행 중인 B200/vLLM 실험에서 단순한:

```text
Input tokens
Output tokens
Throughput
TTFT
TPOT
```

측정에서 한 단계 확장하세요.

### 1단계 — 기존 inference metric

```text
TTFT
TPOT
ITL
Output tok/s
GPU utilization
GPU memory
```

### 2단계 — execution metric

추가:

```text
CPU utilization
CPU scheduling latency
network latency
KV transfer time
prefill time
decode time
```

### 3단계 — agent metric

가상의 coding/research agent workload를 만들어:

```text
Task
 ├─ model call #1
 ├─ tool call #1
 ├─ model call #2
 ├─ tool call #2
 ├─ model call #3
 └─ final answer
```

를 실행하고:

\[
T_{\text{total}}
=
T_{\text{LLM}}
+
T_{\text{tool}}
+
T_{\text{CPU}}
+
T_{\text{network}}
+
T_{\text{queue}}
\]

를 측정합니다.

그리고 최종적으로:

\[
\boxed{
\text{Agent Throughput}
=
\frac{\text{Successful Tasks}}
{\text{GPU-hours}}
}
\]

를 계산하세요.

이렇게 하면 기존 **B200 vLLM Tensor Parallel Benchmark**가 단순 GPU benchmark에서 **agent-serving infrastructure benchmark**로 자연스럽게 확장됩니다.

## 오늘의 핵심 결론

오늘 공개 자료를 하나의 architecture로 합치면 다음 그림이 나옵니다.

```text
                    Agent
                      │
             ┌────────┴────────┐
             │                 │
          Planner           Router
             │                 │
             │        ┌────────┼────────┐
             │        ↓        ↓        ↓
             │      Small    Medium   Frontier
             │        │        │        │
             └────────┴────────┴────────┘
                      │
                   Tools
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       Sandbox      Browser      DB
          │
       CPU / Vera
          │
       GPU / B200
          │
    vLLM / E-P-D / KV
          │
       Network
```

**2026년 10월의 AI 인프라는 더 이상 “GPU에 LLM을 올리는 문제”가 아닙니다.**

이제 핵심 문제는 **agent가 실제 작업을 수행하는 전체 execution graph를 어떻게 빠르고, 싸고, 안전하고, 관측 가능하게 운영할 것인가**입니다.

그리고 이 관점에서 보면 사용자가 진행 중인 **B200 + vLLM benchmark도 `GPU throughput`에서 끝내지 않고 `end-to-end agent throughput / GPU-hour / task success`까지 확장하는 것이 포트폴리오 측면에서도 상당히 강한 방향**입니다.

- 오늘 vLLM 0.31.0을 B200 × 2 환경에서 검증할 benchmark matrix를 설계해줘
- Vera·Helion·B200을 agent workload 관점에서 비교해줘
- 오늘 CATS 논문을 agent benchmark 설계에 적용해줘
