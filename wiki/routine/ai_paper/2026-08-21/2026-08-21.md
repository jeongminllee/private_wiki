# AI 엔지니어 데일리 브리핑

**2026년 8월 21일 금요일**
**분석 범위:** 8월 20일 공식 발표·릴리스를 최우선으로 확인했고, 연구는 8월 19일 신규 논문까지 포함했습니다.

오늘은 새 대형 모델 발표보다 **모델을 실제 시스템에 넣는 방법**이 훨씬 재미있습니다. Liquid AI는 speculative decoding을 에이전트의 function calling까지 연결했고, PyTorch·IBM은 AI coding agent를 이용해 새 가속기의 compiler/runtime가 미처 지원하지 못한 수천 개 Hugging Face 모델을 빠르게 enable하는 방식을 공개했습니다. 연구 쪽에서는 20년짜리 agent benchmark와, multi-agent 장애 원인을 굳이 비싼 LLM으로 분석하지 않아도 된다는 GNN 기반 접근이 나왔습니다. ([Hugging Face][1])

## 1. 필독 | LFM2.5-DSpark — Speculative decoding이 function-calling latency까지 줄인다

### 무엇이 바뀌었나

Liquid AI가 8월 20일 `LFM2.5-1.2B-Instruct`, `LFM2.5-2.6B`, `LFM2.5-8B-A1B`용 **DSpark draft checkpoint**를 공개했습니다. DSpark는 DFlash식 병렬 backbone에 이웃 token 간 의존성을 보완하는 lightweight Markov head, 그리고 “이 suffix를 검증할 가치가 있는가”를 confidence로 판단해 낮은 확률의 뒤쪽 후보를 잘라내는 verifier를 결합합니다. llama.cpp와 SGLang 지원도 함께 공개됐습니다. ([Hugging Face][1])

Liquid 측 batch=1, temperature=0 실험에서 LFM2.5-2.6B는 단일 H100 BF16 기준 평균 **323→864 tok/s, 2.67배**, M4 Max FP16에서는 **61→139 tok/s, 2.27배**였습니다. 여러 multi-tool 시나리오에서는 function-calling latency가 평균 57% 감소했다고 보고했습니다. 다만 8B-A1B MoE는 H100에서 평균 2.54배 빨라졌지만 M4 Max에서는 1.18배에 그쳤는데, llama.cpp Metal의 현재 MoE 경로와 여러 token을 검증할 때 더 많은 expert weight를 읽게 되는 비용이 원인으로 지목됐습니다. ([Hugging Face][1])

### 왜 중요한가

Speculative decoding의 장점은 단순 채팅에서 `tok/s`가 올라가는 것보다 **여러 번 짧은 generation을 수행하는 agent loop의 LLM 구간을 줄일 수 있다는 것**입니다.

```text
reasoning → tool call
          → tool result
reasoning → tool call
          → tool result
reasoning → final answer
```

이 구조에서는 한 번 2,000 token을 생성하는 것보다 100~500 token짜리 호출을 반복하는 경우가 많습니다. Function-call 구간까지 acceptance가 충분히 높다면 agent의 체감 latency에 더 직접적으로 전달될 수 있습니다. DSpark가 function-calling 데이터를 draft-model 학습 mix에 포함한 점도 이 관점에서 중요합니다. ([Hugging Face][1])

### 실무 적용과 주의점

Benchmark에서는 `output_tokens/s`만 기록하지 말고 `draft_tokens`, `accepted_tokens`, `acceptance_rate`, `draft_latency`, `verification_latency`, `peak_VRAM`, 그리고 가장 중요하게 `wall_clock_per_successful_task`를 함께 기록하는 편이 좋습니다. Greedy decoding에서는 검증된 token만 사용하므로 target의 원래 출력과 일치하도록 설계됐지만, 이것이 높은 concurrency·다른 sampling 설정에서도 동일한 end-to-end speedup을 보장한다는 뜻은 아닙니다. 공식 수치 역시 single request, batch=1 조건입니다. ([Hugging Face][1])

특히 MoE 사례가 좋은 경고입니다. **acceptance rate가 높다고 무조건 빠른 것은 아닙니다.** 검증 과정에서 더 많은 expert가 활성화돼 memory traffic이 증가하면 draft quality는 좋아졌는데 wall-clock은 거의 개선되지 않을 수 있습니다. ([Hugging Face][1])

**후속 관찰 포인트:** concurrency 8~64에서의 처리량, radix/prefix cache와의 결합, 긴 coding trajectory에서 acceptance 변화, DSpark와 MTP·DFlash의 동일 workload 비교.

**원문:** **[공식 기술 글] LFM2.5-DSpark** ([Hugging Face][1]) · **[SGLang 실행 가이드] DSpark integration** ([Hugging Face][1])

## 2. 필독 | PyTorch × IBM Spyre — AI Agent가 새 AI Accelerator의 “호환성 레이어”를 만든다

### 무엇이 바뀌었나

PyTorch와 IBM Spyre 팀은 8월 20일, 새 accelerator의 compiler/runtime가 Hugging Face 생태계를 완전히 따라잡기 전에 **AI coding agent가 runtime adapter를 만들어 stock Transformers 모델을 enable하는 방식**을 공개했습니다. Adapter는 모델의 수학을 바꾸는 최적화 kernel이 아니라, 아직 backend가 잘 처리하지 못하는 표현을 수학적으로 동등한 형태로 바꾸거나 hardware constraint에 맞게 shape를 조정하는 얇은 patch layer입니다. ([PyTorch][2])

최종 snapshot에서는 **13개의 adapter가 Hugging Face에서 다운로드 상위 10,000개 embedding 모델 중 7,960개를 cover했고, 그중 6,804개가 Spyre end-to-end test를 통과**했습니다. 핵심은 checkpoint 하나마다 patch를 작성한 것이 아니라 architecture family마다 adapter 하나를 만들면서 coverage가 계단식으로 커졌다는 점입니다. ([PyTorch][2])

### 왜 중요한가

새 GPU/NPU/ASIC이 출시됐을 때 진짜 병목은 silicon만이 아닙니다.

```text
새 모델 architecture
        ↓
PyTorch / Transformers
        ↓
compiler / op lowering
        ↓
runtime
        ↓
accelerator
```

모델 생태계의 변화 속도가 compiler stack보다 빠르면 좋은 hardware가 있어도 모델이 돌아가지 않습니다. IBM의 접근은 AI agent를 **“모델 코드와 compiler backend 사이를 읽고 임시 compatibility layer를 작성하는 엔지니어”**로 쓰는 것입니다. ([PyTorch][2])

이 패턴은 특정 Spyre만의 이야기가 아닙니다. 신규 accelerator, 사내 custom compiler, TensorRT/Triton backend migration처럼 “상위 model semantics는 이미 알려져 있고 하위 backend gap을 찾아야 하는 문제”에 AI coding agent가 상당히 잘 맞을 가능성이 있습니다. 이는 공개 사례에서 도출되는 실무적 해석입니다. ([PyTorch][2])

### 그런데 사람이 여전히 필요한 이유

IBM이 오히려 강조한 부분은 **Agent가 자신 있게 틀릴 수 있다는 점**입니다. CPU/GPU에서는 동일한 결과가 나오지만 target accelerator에서만 값이 달라지는 경우, 이것이 정상적인 numerical drift인지 compiler mis-lowering인지 판단하기 매우 어렵습니다. 개별 op를 떼어냈을 때는 정상인데 주변 op와 fusion됐을 때만 깨지는 경우도 있습니다. ([PyTorch][2])

따라서 adapter 생성 pipeline은 다음처럼 가져가는 편이 좋습니다.

```text
Agent patch proposal
→ CPU/GPU reference equivalence
→ target accelerator test
→ block-level localization
→ end-to-end numerical regression
→ human review
```

**후속 관찰 포인트:** adapter가 실제 compiler fix로 언제 흡수되는지, vision·generation 모델까지 coverage가 확장되는지, architecture별 adapter를 자동 추출·승격하는 CI 구조.

**원문:** **[PyTorch 공식 기술 글] Harnessing AI for Day-One Model Enablement** ([PyTorch][2])

## 3. Agent 평가 | FM-Bench — Agent에게 20년 동안 회사를 운영시키면 무엇이 드러나는가

### 무엇이 바뀌었나

8월 19일 공개된 **FM-Bench**는 LLM agent에게 축구 클럽을 20년 동안 맡깁니다. Agent는 26개 tool을 사용해 선수 영입·계약 협상·시설·유소년 투자·라인업·재무 의사결정을 수행하며, 한 campaign에 약 **340~400개의 decision stop**이 존재합니다. 최종 점수는 deterministic simulation engine이 계산하기 때문에 LLM judge나 human rater를 사용하지 않습니다. ([arXiv][3])

15개 frontier model을 세 seed에서 평가한 결과 모든 모델은 20년 horizon을 끝까지 버텼지만, 순위는 초반이 아니라 장기 누적 의사결정 이후에야 갈렸습니다. 논문에서는 model size, 가격, vendor가 순위를 예측하지 못했고 **token 사용량도 최종 성과를 예측하지 못했다**고 보고합니다. 좋은 agent는 horizon 끝에 가까워질수록 장기 투자 비중을 줄이고, 현금을 놀리지 않고, 계약 만료 전에 일찍 renewal을 시작했습니다. ([arXiv][4])

### 더 흥미로운 실패

모델들은 수백 번의 rejected transfer bid를 경험하고도 숨겨진 시장 가격을 제대로 학습하지 못했습니다. Self-managed memory도 두 극단으로 무너졌습니다. 어떤 agent는 모든 것을 계속 archive해 memory가 끝없이 커졌고, 다른 agent는 매 시즌 plan을 완전히 다시 써 장기 전략의 continuity가 사라졌습니다. ([arXiv][4])

### 왜 중요한가

현재 agent benchmark는 대부분:

```text
문제 제시
→ 5~50분
→ 성공 / 실패
```

입니다.

그러나 실제 조직의 agent는 **수백 번의 action이 누적되고 초기 결정의 효과가 몇십 step 뒤에 나타나는 환경**에서 동작합니다. FM-Bench의 가치도 축구 자체가 아니라 delayed reward, hidden information, long-term memory, recovery, competing agents를 deterministic simulation으로 묶었다는 데 있습니다. ([GitHub][5])

Repository는 `seed + action log`로 bit-identical replay가 가능하도록 설계됐고, 결과에는 `engine_commit`, `params_hash`, `score_version`이 기록됩니다. Agent benchmark를 재현 가능한 software benchmark로 만들려는 점도 좋은 설계입니다. ([GitHub][5])

### 실무 적용

장기 업무 agent를 평가한다면 최종 success 외에 다음 같은 축이 필요합니다.

```text
단기 성공률
장기 목표 유지
잘못된 전략 수정 속도
memory growth
반복 실패 학습 여부
resource utilization
```

특히 “더 많은 token을 쓴 agent가 더 좋은가?”라는 질문에 FM-Bench 결과는 적어도 이 환경에서는 **아니다**라고 답합니다. ([arXiv][4])

**주의:** 축구 simulation이라는 특정 domain이고 아직 research preview입니다. 공식 Arena도 연구팀이 운영하며 self-hosted Arena는 아닙니다. 따라서 순위를 범용 agent intelligence leaderboard처럼 해석하기보다 장기 evaluation methodology에 주목하는 것이 좋습니다. ([GitHub][5])

**원문:** **[논문] FM-Bench** ([arXiv][3]) · **[GitHub] Analogy-AI/fm-bench** ([GitHub][5])

## 4. Agent Observability | 장애 원인 분석에도 굳이 대형 LLM이 필요하지 않을 수 있다

### 무엇이 바뀌었나

새 논문 **AFANet**은 multi-agent trajectory가 실패했을 때 “어느 agent가, 어떤 종류의 오류를 냈는가”를 찾는 Agent Failure Attribution을 generative LLM 대신 **작은 graph neural network**로 처리합니다. 대화의 turn을 graph node로 만들고 temporal relation·agent relation·step-level semantic/statistical signal을 이용해 culprit와 error type을 예측합니다. ([arXiv][6])

저자들은 AFANet이 기존 LLM prompting, fine-tuned model, 복잡한 agentic attribution pipeline과 비교해 훨씬 적은 parameter와 거의 무시할 수 있는 inference 비용으로 in-domain benchmark에서 동등하거나 더 좋은 성능을 보였고, OOD 환경에서는 저비용 test-time adaptation으로 추가 개선할 수 있었다고 보고했습니다. ([arXiv][6])

### 왜 중요한가

Agent 시스템의 모든 문제를 또 다른 LLM에게 맡기는 구조는 빠르게 비싸집니다.

```text
Agent 5개 실행
       ↓
trajectory 100K tokens
       ↓
"왜 실패했지?"
       ↓
또 frontier LLM 100K tokens
```

그런데 실제 failure attribution에서 중요한 정보는 agent interaction graph, 이상한 turn 위치, 반복 패턴, agent 간 dependency처럼 **구조화된 signal**일 수 있습니다. 그런 경우 작은 classifier/GNN이 더 싸고 안정적인 control-plane component가 될 수 있습니다. ([arXiv][6])

### 실무 적용

Production agent trace를 다음처럼 graph로 만들 수 있습니다.

```text
Node:
agent_turn / tool_call / tool_result

Edge:
temporal
delegated_to
depends_on
retry_of
reads_result_from
```

그 위에서 먼저 lightweight detector로 culprit 후보를 좁힌 뒤, 사람이 읽어야 하는 복잡한 incident에만 frontier LLM RCA를 호출하면 됩니다.

이건 model router의 또 다른 형태입니다.

```text
cheap structured attribution
        ↓ uncertain only
expensive LLM diagnosis
```

### 주의할 점

AFANet 결과는 연구 benchmark에 대한 초기 논문입니다. 실제 production의 auth failure, network timeout, stale state, partial side effect 같은 장애까지 같은 품질로 진단한다는 증거는 아직 없습니다. 또한 graph construction 자체가 잘못되면 진단도 잘못될 수 있습니다. ([arXiv][6])

**후속 관찰 포인트:** OpenTelemetry agent trace와 GNN attribution의 결합, online incident classification, failure detector 자체의 distribution drift.

**원문:** **[논문] Beyond LLM-Based Reasoning: Lightweight GNNs for Agent Failure Attribution** ([arXiv][6])

## 5. 머신러닝 연구 | ECMWF HourGlass — 6시간짜리 AI 예보 사이를 “확률적으로” 한 시간 단위로 채운다

### 무엇이 바뀌었나

ECMWF와 MET Norway는 8월 20일 **HourGlass**를 공개했습니다. 많은 AI weather model이 6시간 간격으로 상태를 출력하는데, HourGlass는 두 forecast state 사이의 대기 변화를 추정해 **시간 단위의 coherent forecast**를 생성합니다. 직접 1시간 간격으로 autoregressive forecast를 반복하면서 오차를 누적하는 대신, 이미 존재하는 앞뒤 forecast state를 조건으로 중간 trajectory를 재구성합니다. ([ECMWF][7])

기존 deterministic temporal downscaling은 중간 시간이 지나치게 smooth해지는 문제가 있었는데, HourGlass는 CRPS 계열 probabilistic objective와 시간적 일관성을 위한 추가 loss를 사용합니다. 또 reanalysis가 아니라 **forecast trajectory 자체를 training data**로 사용해 시간축에서 일관된 evolution을 학습합니다. ECMWF의 AIFS Single·AIFS ENS와 MET Norway의 Bris 모두에서 관측 skill을 유지하면서 더 현실적인 hourly variability를 생성했다고 연구팀은 보고했습니다. ([ECMWF][7])

ECMWF는 이 기술을 **2026년 후반 AIFS v3 운영 시스템**에 포함해 AIFS Single과 Ensemble의 주요 surface variable을 hourly로 제공할 계획이며, MET Norway에서는 이미 near-real-time 평가가 진행 중입니다. ([ECMWF][7])

### 왜 중요한가

이 방식은 weather forecasting을 넘어 ML 시스템 설계 관점에서도 흥미롭습니다.

비싼 모델이:

```text
t=0 → t=6 → t=12 → ...
```

처럼 sparse한 상태만 생성하고, 별도 작은 모델이:

```text
t=0, t=6
   ↓
t=1,2,3,4,5
```

를 조건부로 복원하는 구조입니다.

즉 **expensive core model + specialized temporal super-resolution model**이라는 분업입니다. Simulation, robotics trajectory, video state prediction처럼 high-frequency output은 필요하지만 core model을 매 timestep 실행하기 비싼 문제에도 생각해볼 수 있는 패턴입니다.

### 주의할 점

중간 trajectory가 자연스럽다고 해서 모든 extreme event를 복원하는 것은 아닙니다. HourGlass도 hourly precipitation field의 realism은 개선했지만 **가장 강한 강수 극값을 여전히 과소예측**한다고 명시합니다. 평균 RMSE나 시각적 자연스러움만 보고 downscaler를 평가하면 안 되는 이유입니다. ([ECMWF][7])

**후속 관찰 포인트:** AIFS v3 운영 투입 후 실전 검증, 극한 강수 개선, probabilistic ensemble calibration.

**원문:** **[ECMWF 공식 연구 글] HourGlass** ([ECMWF][7]) · **[논문] HourGlass preprint** ([arXiv][8])

## 6. 개발 도구 | NVIDIA Holoscan — 좋은 Agent Harness는 “CLI + Skill + 문서 + Benchmark”다

### 무엇이 바뀌었나

NVIDIA는 Holoscan 기반 실시간 endoscopic segmentation application을 범용 coding agent와 함께 개발한 사례를 공개했습니다. Agent는 Holoscan CLI, HoloHub 문서·예제, 개발 lifecycle을 설명하는 Skill을 이용해 코드 작성뿐 아니라 실행·test·benchmark를 반복했습니다. 첫 iteration의 agent processing time은 약 40분이었고, 두 번째 iteration에서는 `visual`, `smoke`, `benchmark`라는 명시적 실행 mode를 추가했습니다. ([NVIDIA Developer][9])

최종 benchmark에서는 동일 test system에서 rendered throughput이 204.0→306.9 FPS, mean application-path latency가 4.891→3.247ms, P95가 6.273→4.554ms로 개선됐습니다. 이는 한 Holoscan sample application에 대한 NVIDIA의 case study 결과입니다. ([NVIDIA Developer][9])

### 더 중요한 것은 Ablation

같은 coding agent와 sandbox를 사용한 비교에서 `CLI + Skill + docs/examples` 조합은 첫 end-to-end app까지 **40분·11M tokens**, `CLI + docs`는 65분·20M tokens, `docs/examples`만 제공한 경우는 40분·15M tokens이었지만 결과 코드가 기존 Holoscan optimized operator를 제대로 활용하지 않아 다른 두 구현보다 2.6배 느렸습니다. ([NVIDIA Developer][9])

### 왜 중요한가

Agent에게 documentation을 많이 주는 것만으로는 충분하지 않습니다.

가장 좋은 환경은:

```text
문서 → 무엇을 해야 하는지 이해
Skill → 조직이 선호하는 workflow
CLI → 정확히 같은 실행 계약
Benchmark → 결과 검증
```

처럼 **사람과 agent가 동일한 deterministic developer interface를 공유하는 환경**입니다.

Agent가 generic Bash로 환경을 탐색하게 두면 package install, container entrypoint, lint·test command를 추측하면서 token을 많이 낭비합니다. 반대로 `project test`, `project benchmark`, `project env-check`처럼 조직이 표준 CLI를 제공하면 탐색 공간이 크게 줄어듭니다. NVIDIA의 ablation은 이 차이를 잘 보여줍니다. ([NVIDIA Developer][9])

### 주의할 점

이는 NVIDIA의 단일 application 사례이며 의료 시스템의 clinical safety를 검증한 것이 아닙니다. 사람 개발자가 각 iteration 뒤 visual output, test, benchmark를 확인했고 최종 handoff도 다시 검증했습니다. “Agent가 40분 만에 의료 AI를 완성했다”는 해석은 부정확합니다. ([NVIDIA Developer][9])

**후속 관찰 포인트:** 다른 HoloHub application에서의 재현, CLI contract가 coding-agent token 사용량에 미치는 영향, Skill regression CI.

**원문:** **[NVIDIA 공식 기술 글] Holoscan Applications with CLI, Skills, and AI Coding Agents** ([NVIDIA Developer][9])

## 7. GitHub | Code Quality가 Code Scanning과 별도의 운영·과금 단위로 분리된다

### 무엇이 바뀌었나

GitHub는 8월 20일 Code Quality 실행에 별도의 GitHub Actions path와 actor를 GA했습니다. 이제 Code Quality 분석은 `dynamic/github-code-quality/codeql`과 `github-code-quality` actor로 표시되어, 기존 Code Scanning의 `dynamic/github-code-scanning/codeql` 및 `github-advanced-security`와 명확하게 구분됩니다. 기존 path나 actor를 기준으로 Actions billing·dashboard를 집계했다면 필터를 수정해야 합니다. ([The GitHub Blog][10])

동시에 repository에서 Code Quality를 enable·disable·변경하면 `repo.code_quality_enabled`, `repo.code_quality_disabled`, `repo.code_quality_updated` audit event가 기록되기 시작했습니다. Repository, 변경한 actor, timestamp가 남기 때문에 어떤 repository가 언제 billing scope에 들어왔는지 추적할 수 있습니다. ([The GitHub Blog][11])

Code scanning에는 **Mitigated** dismissal reason도 추가됐습니다. 취약점이 코드에 남아 있지만 WAF나 network policy 같은 외부 control로 위험이 완화된 경우를 단순 false positive나 “won’t fix”와 구분할 수 있습니다. ([The GitHub Blog][12])

### 왜 중요한가

AI가 code review·quality·security analysis를 늘릴수록 다음 세 가지를 같은 것으로 취급하면 안 됩니다.

```text
Code Quality
Code Security
AI Code Review
```

목적, 과금, severity, remediation SLA가 서로 다릅니다. GitHub가 workflow와 audit event를 분리한 것은 이 영역들이 독립적인 **control plane**으로 발전하고 있다는 신호입니다. ([The GitHub Blog][10])

`Mitigated` 상태도 좋은 개선이지만 운영상 함정이 있습니다. 외부 WAF rule이 삭제됐는데 취약점 alert는 계속 mitigated로 남아 있으면 위험합니다. 실무에서는 `mitigation_control_id`, `owner`, `expiry`, `revalidation_date`를 함께 관리하는 편이 안전합니다.

**후속 관찰 포인트:** AI-generated code 품질과 security alert를 함께 묶는 dashboard, mitigation 자동 재검증, Code Quality 비용 대비 defect 감소 측정.

**원문:** **[GitHub 릴리스] Code Quality Actions path 분리** ([The GitHub Blog][10]) · **[GitHub 릴리스] Audit log events** ([The GitHub Blog][11]) · **[GitHub 릴리스] Mitigated dismissal** ([The GitHub Blog][12])

### 왜 중요한가

AI infrastructure 사업이 이제 “언젠가 monetization 될 투자” 단계에서 **cloud revenue와 margin에 직접 잡히는 사업**으로 이동하고 있다는 긍정적 신호가 있는 동시에, compute capacity 확보에 필요한 자본비용도 매우 큽니다. ([Alibaba Group][13])

-

# 오늘의 실습 | LFM2.5-2.6B에서 DSpark의 “실제 Agent Speedup” 측정하기

오늘은 Liquid AI의 공식 숫자를 그대로 받아들이기보다 **microbenchmark speedup이 실제 agent workflow까지 얼마나 전달되는지** 확인해보는 실험을 추천합니다.

우선 동일한 `LFM2.5-2.6B`를 두 서버로 비교합니다.

```bash
# Baseline
python -m sglang.launch_server \
  --model-path LiquidAI/LFM2.5-2.6B \
  --port 30000
```

DSpark 조건은 공식 예제대로 DSpark 지원이 들어간 SGLang build를 사용합니다. ([Hugging Face][1])

```bash
python -m sglang.launch_server \
  --model-path LiquidAI/LFM2.5-2.6B \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path LiquidAI/LFM2.5-2.6B-DSpark \
  --speculative-draft-attention-backend flashinfer \
  --disable-radix-cache \
  --mem-fraction-static 0.75 \
  --port 30000
```

첫 실험은 공식 조건과 최대한 비슷하게 `temperature=0`, concurrency=1로 맞춥니다. 다음 세 workload를 각각 20회 정도 실행하십시오.

```text
A. 일반 generation
   2K input → 512 output

B. Coding
   bug 설명 → patch 생성

C. Tool Agent
   tool call → result → tool call → final
```

기록할 지표는 다음이면 충분합니다.

```text
TTFT
decode_tok_s

draft_tokens
accepted_tokens
acceptance_rate

peak_vram

tool_call_exact_match
strict_task_success

wall_clock_per_success
```

Greedy 조건에서는 baseline과 DSpark 출력이 동일해야 하므로 **최종 text 또는 token sequence equality를 regression assertion으로 넣는 것**도 좋습니다. Speculative decode의 목적은 다른 답을 더 빨리 만드는 것이 아니라 동일 target distribution을 더 적은 target-model forward로 생성하는 것이기 때문입니다. ([Hugging Face][1])

그다음 concurrency를 `1 → 8 → 32`로 올립니다. 여기서 가장 중요한 결과가 나옵니다.

```text
Microbenchmark speedup
vs.
End-to-end agent speedup
```

예를 들어 decode가 2.7배 빨라도:

```text
LLM generation  3초 → 1.1초
tool execution  8초
test execution  6초
```

라면 실제 Agent는 약 10% 정도만 빨라질 수 있습니다. 반대로 tool call이 매우 짧고 LLM turn이 여러 번 이어지는 workflow라면 개선폭이 훨씬 커질 수 있습니다.

최종적으로 이 세 숫자만 남기면 됩니다.

```text
decode_speedup
agent_wall_clock_speedup
VRAM_cost_per_speedup
```

그리고 DSpark가 유리한 task와 그렇지 않은 task를 분리하십시오. **Speculative decoding을 “항상 켜는 최적화”가 아니라 workload에 따라 router가 켜고 끄는 execution policy로 볼 수 있는지**까지 확인하면 이번 실험의 가치가 훨씬 커집니다. ([Hugging Face][1])
