# AI 엔지니어 데일리 브리핑

**2026년 8월 26일 수요일**
오늘은 **8월 25일 공개된 공식 발표·모델 릴리스**를 최우선으로 보고, 8월 24~25일 공개된 최신 agent·memory 연구까지 확인했습니다.

오늘의 흐름은 꽤 강합니다. **OpenAI가 첫 자체 inference ASIC의 실측 결과를 공개하면서 inference 최적화가 GPU kernel 경쟁에서 chip–memory–network–software 공동 설계로 확대됐고, IBM은 3B~30B open-weight 모델에 실제 sandbox를 사용하는 agentic RL을 넣었습니다. Agent 시스템 쪽에서는 context를 “요약할 문자열”이 아니라 실행 가능한 state environment로 다루거나, harness 자체가 지속적으로 진화하는 방향이 빠르게 커지고 있습니다. 반대편에서는 persistent memory가 한 번의 악성 interaction만으로 장기 공격 표면이 될 수 있다는 결과가 나왔습니다.**

## 1. 필독 | OpenAI Jalapeño — 첫 자체 Inference ASIC의 실측 결과 공개

### 무엇이 바뀌었나

OpenAI가 **8월 25일** 첫 custom inference chip **Jalapeño**의 실제 benchmark 결과를 공개했습니다. GPT‑OSS 120B, DeepSeek R1 670B, Kimi K2.5 1T를 SemiAnalysis의 공개 InferenceX benchmark에서 테스트했고, 비교 시스템 대비 peak throughput에서 **1.5~1.9배 높은 AI work/W**, end-to-end latency는 **1.7~3.6배 낮았다**고 보고했습니다. Highly interactive operating point에서는 2.1~4.1배의 성능 차이를 제시합니다. ([OpenAI][1])

세부적으로 GPT‑OSS 120B에서는 GB200 대비 peak mixed throughput/kW가 약 **1.9배**, DeepSeek R1에서는 GB300 대비 E2E latency가 **5.99초→1.65초**, Kimi K2.5 1T에서는 **5.31초→1.56초**였습니다. Jalapeño package TDP는 700W로 명시됐지만 OpenAI는 테스트 중 sustained power가 550W 이하였다고 설명합니다. ([OpenAI][1])

SemiAnalysis 측도 OpenAI 연구실에서 자사 InferenceX suite로 실제 chip을 benchmark했다고 확인했습니다. 다만 비교 대상은 현재 상용 Blackwell **GB200·GB300**이고, 아직 폭넓게 배포되지 않은 Vera Rubin과의 비교는 아닙니다. 따라서 “현존하는 모든 NVIDIA architecture를 이겼다”는 식의 해석은 과합니다. ([SemiAnalysis][2])

### 왜 중요한가

Jalapeño의 설계 철학은 상당히 흥미롭습니다. OpenAI는 inference를 하나의 GEMM workload로 보지 않고 다음 세 단계의 병목을 동시에 고려했습니다.

```text
Prefill
→ compute intensive

Decode
→ memory-bandwidth intensive

Multi-chip execution
→ communication / state movement
```

KV cache를 포함한 model state를 가능한 한 local하게 유지하고, compute·memory·network를 **하나의 connected domain**으로 설계했습니다. 즉 prefill은 GPU A, decode는 accelerator B처럼 workload를 쪼개는 최근 heterogeneous architecture와 달리, Jalapeño는 하나의 fungible architecture 안에서 데이터 이동을 최소화하는 쪽입니다. ([OpenAI][1])

Agent workload에서는 이 부분이 특히 중요합니다. 한 요청이 한 번 끝나는 chat보다 agent는:

```text
LLM
→ tool
→ LLM
→ tool
→ LLM
...
```

처럼 여러 inference step을 직렬로 실행하기 때문에 **각 step의 수십~수백 ms 차이가 전체 task에서 누적**됩니다.

### AI가 chip 개발에도 직접 들어갔다

OpenAI는 초기 설계에서 tapeout까지 **9개월**이 걸렸으며 AI를 implementation exploration, verification, arithmetic-circuit optimization에 사용했다고 밝혔습니다. 또 GPT‑Astra 기반 Codex를 이용해 원래 production 계획에 없던 세 open-weight model을 두 달 안에 Jalapeño에 최적화했고, 일부 GPT‑OSS attention·MoE block에서는 AI-generated implementation이 기존 human-expert implementation보다 **1.5~1.8배 빨랐다**고 보고했습니다. 이 수치는 일부 block의 결과이며 full-model speedup이 아닙니다. ([OpenAI][1])

이건 ML infra 쪽에서 중요한 변화입니다.

```text
AI model
→ chip 설계 지원
→ compiler/kernel 생성
→ benchmark
→ 다시 AI가 최적화
```

라는 **hardware–software self-improvement loop**가 실제 silicon 개발 workflow 안으로 들어오고 있습니다.

### 주의할 점

Jalapeño는 현재 OpenAI 내부 chip이며 구매·임대 가능한 accelerator가 아닙니다. OpenAI는 **2026년 말부터 자체 compute infrastructure에 배치**할 계획이고 Gen 2는 이미 개발 중이라고 밝혔습니다. 따라서 현재 B200/GB300을 대체할 일반적인 hardware 선택지로 볼 단계는 아닙니다. ([OpenAI][1])

**후속 관찰 포인트:** Rubin 대비 비교, actual rack-level power와 PUE, AgentX 같은 multi-turn workload, production deployment에서 TTFT/P99, Gen 2 architecture.

**원문:**
[공식 발표 — OpenAI Jalapeño 첫 실측 결과](https://openai.com/index/jalapeno-first-results/)
[독립 Benchmark — SemiAnalysis InferenceX](https://inferencex.semianalysis.com/?utm_source=chatgpt.com)

## 2. 필독 | IBM Granite 4.2 — 8B·30B를 실제 Sandbox에서 Agentic RL

### 무엇이 바뀌었나

IBM이 **8월 25일 Granite 4.2** reasoning-model family의 전체 training recipe와 weights를 공개했습니다. 모델은 **3B·8B·30B dense decoder-only** 세 종류이고 Apache 2.0입니다. 약 15T token으로 from-scratch pretraining한 뒤 SFT와 다단계 RL을 수행하며 thinking / low-effort thinking / non-thinking mode와 native tool calling을 지원합니다. ([huggingface.co][3])

가장 중요한 부분은 8B·30B에 적용된 post-training입니다.

```text
SFT
 ↓
RLVR
 ↓
skill boosters
 ↓
SWE agent
 ↓
Terminal agent
 ↓
Search agent
 ↓
RLHF
```

SWE stage에서는 실제 open-source repository가 들어간 sandbox에서 OpenHands harness가 코드를 수정하고 hidden test로 검증합니다. Terminal stage에서는 live shell에서 최대 **64 environment turn**을 수행하며, Search stage에서는 실제 web search loop를 돌립니다. 최종 reward는 “좋은 답처럼 보이는가”보다 **환경에서 실제 task가 완료됐는가**를 중심으로 설계됩니다. ([huggingface.co][3])

### 왜 중요한가

Open-weight post-training도 이제 instruction dataset만 늘리는 방식에서:

```text
Model
↔ real repository
↔ shell
↔ browser
↔ deterministic verifier
```

형태로 이동하고 있습니다.

특히 IBM은 reward를 세 종류로 분리했습니다.

* deterministic/verifiable reward: unit test, exact match, format checker
* LLM judge/reward model: search나 preference처럼 열린 문제
* agentic outcome reward: 실제 environment task 성공 여부 ([huggingface.co][3])

가능한 곳에서는 verifier를 먼저 쓰고, 사람이 규칙으로 정의할 수 없는 부분에만 judge model을 사용하는 구조가 좋습니다.

### 공개 benchmark는 어느 정도인가

IBM 자체 평가에서 Granite 4.2 30B는 SWE-Bench Verified **57.0**, SWE-Bench Pro **33.29**, Terminal-Bench 2.1 **29.24**, BFCL v4 **61.39**를 기록했습니다. 8B는 SWE-Bench Verified 47.67입니다. 절대 수치가 frontier proprietary model보다 높다고 보기는 어렵지만, **Apache 2.0의 8B·30B 모델이 실제 agentic RL trajectory까지 공개된 것**이 더 중요한 부분입니다. ([huggingface.co][3])

### 배포 측면도 잘 갖춰졌다

vLLM·SGLang을 공식 지원하며 FP8, NVFP4, MXFP4, GGUF artifact도 제공합니다. FP4 model은 SFT 데이터에서 2K sample을 이용해 GPTQ calibration했습니다. ([huggingface.co][3])

여기서 한 가지 확인할 부분이 있습니다. IBM은 pretraining의 마지막 phase에서 **512K long-context training**을 수행했다고 설명하지만 public architecture table의 sequence length는 **131,072**로 표기합니다. 따라서 “Granite 4.2 = runtime 512K 모델”이라고 단정하지 말고 실제 checkpoint·runtime별 `max_model_len`을 확인하는 것이 안전합니다. ([huggingface.co][3])

### 실무 적용

8B는 agentic-RL이 들어간 모델 중 규모가 작기 때문에 local tool-agent 실험에 꽤 좋은 후보입니다.

```text
Granite 4.2 8B
→ vLLM
→ OpenAI-compatible endpoint
→ OpenHands / 자체 harness
```

형태로 연결해 tool-selection, retry, shell recovery, structured output을 평가하기 좋습니다.

**후속 관찰 포인트:** quantized checkpoint의 tool-call regression, 한국어 tool-use 성능, 128K+ long-context, same-model agentic-RL ablation 공개 여부.

**원문:**
[공식 기술 글 — Granite 4.2 전체 Training Recipe](https://huggingface.co/blog/ibm-granite/granite-4-2)
[모델·GitHub Collection — Granite 4.2 Resources](https://huggingface.co/collections/ibm-granite/granite-42-language-models?utm_source=chatgpt.com)

## 3. Agent Observability | OpenSearch MCP Apps — Agent의 설명 옆에 “실제 증거 화면”을 붙인다

### 무엇이 바뀌었나

AWS는 Amazon OpenSearch Service에 **MCP Apps 기반 agentic observability** workflow를 공개했습니다.

기존 observability agent는:

```text
logs + metrics + trace 조회
→ "checkout-service가 원인입니다"
```

라는 자연어 결과를 빠르게 만들지만, 엔지니어는 결국 OpenSearch/Grafana 같은 dashboard를 다시 열어 trace waterfall과 service map을 직접 확인해야 합니다.

새 구조에서는 MCP tool call이 **두 개의 결과를 동시에 반환**합니다.

```text
1. Agent가 읽을 structured text
2. 사람이 볼 interactive visualization
```

Trace waterfall, service map, alert view, metric graph가 IDE/chat conversation 안에 직접 렌더링됩니다. ([아마존 웹 서비스][4])

### 왜 중요한가

여기서 좋은 설계는 “AI가 그래프를 그린다”가 아닙니다.

Visualization은 모델이 생성한 것이 아니라 **OpenSearch가 실제 data source에 query를 실행해 deterministic하게 만든 결과**입니다. Agent는 text summary를 사용해 reasoning하고, 사람은 같은 query의 실제 trace/metric 결과를 옆에서 검증합니다. ([아마존 웹 서비스][4])

즉:

```text
LLM hypothesis
      ↓
deterministic query
      ↓
actual evidence
      ↓
human verification
```

구조입니다.

최근 agent 시스템에서 계속 등장하는 **generator와 verifier 분리**가 observability 제품에도 적용된 셈입니다.

### 실제 구조

Local MCP server가 IDE와 OpenSearch UI 사이의 bridge 역할을 합니다.

```text
Claude / VS Code / ChatGPT / Cursor
              ↓
        local MCP server
              ↓
     authenticated query
              ↓
        OpenSearch UI
              ↓
text result + visualization
```

Data는 사용자의 AWS account에 남고, MCP server는 로컬에서 실행됩니다. OpenSearch·Serverless·Prometheus 등을 backend로 사용할 수 있습니다. ([아마존 웹 서비스][4])

AI/agent observability 도구도 포함돼 있어 LLM call과 agent trace map을 시각화할 수 있습니다. ([아마존 웹 서비스][4])

### 실무 적용

Agent 기반 RCA를 만든다면 최종 답변에 다음 형태의 **evidence artifact**를 같이 반환하게 하는 것이 좋습니다.

```text
root_cause
evidence_query
trace_id
affected_services
metric_window
visualization_id
```

“Agent가 이렇게 생각했습니다”에서 끝내지 않고 사람이 즉시 원본 관측값으로 내려갈 수 있어야 합니다.

### 주의할 점

Deterministic visualization이 있다고 agent의 root-cause interpretation까지 자동으로 맞는 것은 아닙니다. 잘못된 query를 실행하면 **틀린 질문에 대한 정확한 그래프**를 얻을 수도 있습니다. 따라서 query provenance와 query parameters도 같이 보존해야 합니다.

**후속 관찰 포인트:** MCP App standardization, write/remediation action의 approval, OTel agent trace와 infra trace 연결, visualization payload의 client portability.

**원문:**
[AWS 기술 가이드 — OpenSearch MCP Apps Agentic Observability](https://aws.amazon.com/blogs/machine-learning/agentic-observability-with-amazon-opensearch-service-mcp-apps/)

## 4. Agent Harness | Prime Agent — Context를 Prompt가 아니라 Persistent REPL로 다룬다

### 무엇이 바뀌었나

**8월 24일** Prime Intellect가 `Prime Agent` technical report를 arXiv에 공개했습니다. 핵심은 일반적인:

```text
대화 history
→ context compaction
→ model
```

구조를 벗어나, **persistent IPython REPL을 agent의 computational workspace**로 사용한다는 것입니다. ([arXiv][5])

Recursive Language Model(RLM) abstraction에서는 large context를 prompt 문자열로 계속 집어넣는 대신 Python variable로 보관하고, agent가 code로 검색·변환·분석합니다.

Continual Harness는:

```text
history
memory
skill
prompt
subagent specification
```

을 trajectory 사이에도 durable state로 유지하고 작은 evidence-backed update로 계속 개선할 수 있게 합니다. ([GitHub][6])

### 왜 중요한가

지금 agent harness의 가장 큰 낭비 중 하나는 tool output을 매 turn 다시 token으로 직렬화하는 것입니다.

예를 들어 repository search 결과가 100KB라면:

```text
tool result 100KB
→ 다음 prompt에 삽입
→ 또 다음 prompt에 삽입
→ ...
```

하게 됩니다.

Prime Agent식 접근에서는:

```python
search_result = ...
test_history = ...
failed_attempts = ...
```

처럼 environment에 보존해두고, 필요할 때만 projection을 model context에 넣을 수 있습니다.

### 결과는 어떻게 봐야 하나

저자들은 ARC-AGI-3 RHAE Best@1이 **30% → 95.5%**로 증가했다고 보고하며 coding, GPU kernel generation, emulator construction, nanoGPT speedrun 등에서도 기존 harness와 경쟁한다고 설명합니다. ([arXiv][5])

다만 이 수치는 foundation model 자체의 65.5%p 향상으로 읽으면 안 됩니다.

```text
Model
+
RLM
+
persistent computation
+
subagent
+
memory
+
verification
```

전체 시스템의 점수입니다.

오히려 바로 그 사실이 중요합니다. **모델 weight보다 harness architecture가 성능을 크게 제한할 수 있다**는 또 하나의 사례입니다.

### 주의할 점

Persistent REPL은 강력하지만 security surface도 커집니다. 이전 turn에서 생성된 object·credential·file handle·실패한 intermediate state가 장기간 남을 수 있기 때문에:

```text
namespace isolation
TTL
secret redaction
resource limit
snapshot / rollback
```

이 필요합니다.

또 self-improving memory나 Skill은 잘못된 경험도 영구화할 수 있으므로 automatic promotion 이전에 regression test가 필요합니다.

**후속 관찰 포인트:** model-harness co-training, persistent REPL memory 비용, session checkpoint portability, harness self-modification의 regression 관리.

**원문:**
[논문 — Prime Agent: A Self-Improving RLM Harness](https://arxiv.org/abs/2608.23552)
[GitHub — Prime Agent 구현](https://github.com/PrimeIntellect-ai/prime-agent/blob/main/README.md?utm_source=chatgpt.com)

## 5. Agent Memory | Scroll — Context Window를 “실행 가능한 Session Environment”로 바꾼다

### 무엇이 바뀌었나

`Context as an Environment` 연구는 **Scroll**이라는 long-horizon context manager를 제안합니다.

기존 long-term context 방법은 보통:

```text
오래된 내용
→ summarize
또는
→ embedding memory
```

입니다.

문제는 미래에 어떤 정보가 필요할지 모르는 상태에서 미리 “무엇을 버릴지” 결정해야 한다는 것입니다.

Scroll은 원본 history를 **append-only Event Log**에 lossless하게 남겨두고, 별도 persistent Python kernel에 typed state를 유지합니다. ([arXiv][7])

Agent가 다음 context를 만들 때도 memory retriever가 자동으로 text chunk를 넣지 않습니다.

```text
Event Log
  ↓
model-written Python
  ↓
필요한 data 검색 / 계산
  ↓
print된 projection만
  ↓
다음 model context
```

즉 **context management 자체를 programming task**로 만듭니다. ([arXiv][7])

### 왜 중요한가

이 구조에서는 tool result와 계산 state를 text로 계속 들고 다닐 필요가 없습니다.

예를 들어 ML experiment agent라면:

```python
runs["exp_31"].metrics
failed_configs
best_checkpoint
dataset_version
```

을 environment에 그대로 보관하고 질문에 필요한 일부만 보여줄 수 있습니다.

그리고 context budget을 넘어서 오래된 span을 evict하더라도 Event Log의 정확한 위치가 남아 있어 나중에 원문을 다시 가져올 수 있습니다.

### 연구 결과

Qwen3.8-Max 기반으로 저자들은:

* LongMemEval_S: **94.8%**
* BEAM_10M: **73.1%**
* LOCA_256K: **86.7%**

를 보고했습니다. BEAM_10M에서는 기존 최고 memory system 대비 +5.1p, LOCA에서는 +37.4p라고 설명합니다. ([arXiv][7])

### 실무에서 얻을 수 있는 아이디어

모든 tool output을 자연어 memory로 만들지 말고:

```text
Lossless state
→ DB / event log / object store

Structured working state
→ variables / tables

Model-visible context
→ 필요한 projection만
```

으로 세 계층을 나누는 방식이 좋습니다.

특히 experiment log, benchmark result, Git commit, numerical metrics처럼 **정확한 값이 중요한 데이터는 요약기에 맡기지 않는 것**이 중요합니다.

### 주의할 점

Model에게 `exec` 기반 context management를 맡기면 잘못된 filtering이나 code execution 자체가 새로운 failure mode가 됩니다. Persistent kernel은 반드시 sandbox되어야 하며 model-generated query가 원본 event를 삭제하거나 변조하지 못하도록 Event Log는 immutable하게 유지하는 편이 좋습니다.

**후속 관찰 포인트:** open-source implementation, multi-user session isolation, persistent kernel crash recovery, context-selection 비용과 token 절감의 실제 break-even.

**원문:**
[논문 — Context as an Environment / Scroll](https://arxiv.org/abs/2608.21690)

## 6. AI 보안 | InjecMEM — Agent와 한 번 대화했을 뿐인데 Memory가 지속적인 공격 Trigger가 될 수 있다

### 무엇이 바뀌었나

COLM 2026 채택 논문 **InjecMEM**은 persistent agent memory를 겨냥한 공격을 보여줍니다.

위협 모델이 특히 강합니다. 공격자는:

* memory DB를 읽을 권한 없음
* memory DB를 직접 수정할 권한 없음
* 단 **한 번 agent와 정상 interaction**할 수 있음

뿐입니다. ([arXiv][8])

공격 input은 두 부분으로 구성됩니다.

```text
Retriever-agnostic anchor
→ 특정 topic으로 memory에 분류·검색되게 만듦

Adversarial command
→ 나중에 retrieval됐을 때
   원하는 output으로 generation을 유도
```

예를 들어 한 번의 악성 health-related interaction이 memory에 저장되고, 나중에 다른 사용자가 health 관련 질문을 하면 그 record가 다시 retrieval되어 model behavior를 오염시키는 형태입니다. ([arXiv][9])

### 결과

MemoryOS와 여러 backbone을 사용한 연구에서 InjecMEM은 19개 domain 평균 장기 retrieval에서 최대 **35.4% RSR**, retrieval됐을 때 targeted output으로 이어지는 conditional attack success는 **76.6%**를 기록했습니다. MemGPT와 여러 open backbone에서도 실험했습니다. ([arXiv][9])

### 더 중요한 결과: 기존 Prompt Injection Detector가 잘 안 막는다

Retrieve-time filter로 LLM judge, ProtectAI, PromptGuard를 사용했지만 conditional ASR은 각각 **75.4%, 76.3%, 76.6%** 수준으로 거의 유지됐습니다.

Perplexity filter를 매우 강하게 적용하면 attack retrieval을 0으로 만들 수 있었지만, **정상 memory의 71.8%도 차단**했습니다. ([arXiv][9])

즉 단순:

```text
memory retrieve
→ prompt-injection classifier
→ model
```

만으로는 충분하지 않을 수 있다는 결과입니다.

### 왜 중요한가

Memory를 지금까지는 주로 품질 feature로 봤습니다.

```text
Memory ↑
→ personalization ↑
→ continuity ↑
```

하지만 security 관점에서는:

```text
User input
→ persistent storage
→ future sessions
→ other context
```

라는 **trust-level escalation**입니다.

Temporary user input이 future system behavior에 영향을 주는 persistent artifact로 승격됩니다.

### 실무 적용

Memory entry마다 최소 다음 metadata를 두는 것이 좋습니다.

```text
source_principal
source_session
created_at
trust_level
write_reason
retrieval_count
provenance
expiry
```

또 memory를 retrieval했다고 곧바로 instruction으로 해석하지 말고:

```text
memory = untrusted data
system/tool policy = authority
```

경계를 강제로 유지해야 합니다.

고위험 domain에서는 memory write 자체를 승인하거나, user-authored text와 system-generated structured facts를 서로 다른 store에 넣는 방법도 고려할 수 있습니다.

### 주의할 점

강한 attack command 생성에는 backbone 접근을 사용하는 white-box optimization이 포함됩니다. 논문도 **완전히 모르는 model family로의 zero-shot transfer는 제한적**이라고 밝힙니다. 따라서 제시된 성공률을 모든 closed API agent의 실제 공격 확률로 일반화하면 안 됩니다. ([arXiv][9])

**후속 관찰 포인트:** rewrite/summarization-heavy memory에 대한 공격, write-time defense, provenance-aware retrieval, memory poisoning benchmark의 표준화.

**원문:**
[논문 — InjecMEM](https://arxiv.org/abs/2608.23471)
[GitHub — InjecMEM 구현](https://github.com/BlueBlood6/InjecMEM?utm_source=chatgpt.com)

## 7. GPU·Agent 인프라 | NVIDIA Vera CPU — Agent workload에서 CPU가 다시 핵심 자원이 된다

### 무엇이 바뀌었나

NVIDIA는 8월 24일 SpaceXAI가 차세대 agentic AI workload에 **Vera CPU**를 도입한다고 발표했습니다. Vera는 88개의 NVIDIA Olympus core와 Spatial Multithreading, 최대 **1.2TB/s LPDDR5X memory bandwidth**를 갖습니다. NVIDIA는 agentic AI·RL·data-processing workload에서 x86 대비 최대 **1.8배 빠른 task completion**을 주장합니다. ([NVIDIA Newsroom][10])

### 왜 중요한가

LLM 시스템에서 흔히 GPU만 봅니다.

하지만 Agent workload는 모델 호출 사이에:

```text
code execution
JSON serialization
database query
tool orchestration
retrieval
simulation
compression
network protocol
```

같은 CPU workload를 대량으로 발생시킵니다.

그래서 실제 critical path가:

```text
GPU inference 400 ms
→ CPU tool processing 300 ms
→ DB 500 ms
→ CPU orchestration 150 ms
→ GPU inference 300 ms
```

라면 GPU를 20% 빠르게 해도 전체 task는 크게 빨라지지 않습니다.

NVIDIA가 Vera를 **“CPU for agents”**라고 마케팅하는 이유도 이 지점입니다. GPU를 계속 feeding하면서 inference 사이의 orchestration work를 처리하려는 것입니다. ([NVIDIA Newsroom][10])

### 실무 적용

Agent server의 profiling에서도 이제 CPU를 phase별로 나누는 것이 좋습니다.

```text
llm_prefill
llm_decode
tool_execution
serialization
retrieval
network_wait
orchestrator
```

각 phase마다:

```text
CPU time
GPU active time
memory bandwidth
queue time
P95 latency
```

를 기록하면 “GPU가 놀고 있는 이유”를 찾기 쉬워집니다.

### 주의할 점

1.8배는 NVIDIA가 제시한 workload 결과이고 세부 benchmark 조건이 모두 공개된 독립 비교는 아닙니다. 또한 Vera CPU를 썼다고 agent model 자체가 빨라지는 것이 아니라 **CPU-intensive surrounding work가 병목일 때** 효과가 있는 것입니다. ([NVIDIA Newsroom][10])

**후속 관찰 포인트:** production agent trace에서 CPU/GPU utilization split, Vera vs x86 동일 workload benchmark, tool-heavy agent의 E2E task latency, CPU와 KV-storage path의 결합.

**원문:**
[공식 발표 — SpaceXAI adopts NVIDIA Vera CPU](https://nvidianews.nvidia.com/news/spacexai-adopts-nvidia-vera-cpu-to-accelerate-agentic-ai-at-massive-scale)

# 오늘 꼭 볼 것 3개

**1. OpenAI Jalapeño.** 오늘 가장 중요한 infra 자료입니다. 첫-generation custom silicon이 단순 FLOPS가 아니라 **prefill·decode·KV locality·network를 하나의 inference workload로 설계**했고, 공개 benchmark에서도 실제 수치가 나온 단계까지 왔습니다. 특히 AI가 chip 설계와 kernel optimization에도 직접 쓰였다는 부분을 볼 가치가 큽니다. ([OpenAI][1])

**2. Granite 4.2.** Open-weight model을 직접 다루는 엔지니어라면 가장 실용적입니다. 8B·30B가 실제 repository·terminal·search environment에서 agentic RL을 받았고, vLLM/SGLang·FP4/GGUF 경로가 동시에 제공됩니다. ([huggingface.co][3])

**3. InjecMEM.** Agent memory를 붙일 계획이 있다면 꼭 볼 만합니다. **“사용자 입력 → persistent memory”가 사실상 새로운 privilege boundary**라는 점을 명확하게 보여줍니다. 특히 기존 prompt-injection filter가 conditional attack을 거의 막지 못한 결과가 중요합니다. ([arXiv][9])

# 오늘의 실습 | Granite 4.2 8B에서 “Thinking Budget × Tool Reliability” 직접 측정하기

오늘은 새로 공개된 **Granite 4.2 8B**가 상당히 좋은 실험 대상입니다. 8B부터 실제 repository·terminal·search를 사용하는 agentic RL이 적용되고, 모델 자체가 `thinking / low-effort / non-thinking` 세 실행 방식을 제공하기 때문입니다. ([huggingface.co][3])

vLLM이나 SGLang으로 같은 checkpoint를 한 번 띄우고 세 조건만 비교하십시오.

```text
A. non-thinking
B. low-effort thinking
C. full thinking
```

20개 정도의 작은 tool-use task를 준비합니다. `read_file`, `search_repo`, `run_test`, `get_system_status` 같은 **side-effect가 없거나 쉽게 검증 가능한 도구**가 좋습니다.

각 실행에서 다음을 기록합니다.

```text
strict_success
tool_selection_accuracy
argument_exact_match

input_tokens
reasoning_tokens
output_tokens

tool_calls
retry_count

TTFT
wall_clock
```

가장 중요한 것은 한 turn의 latency가 아니라 다음 두 값입니다.

```text
tokens_per_success
wall_clock_per_success
```

예를 들어 결과가:

```text
non-thinking
→ 빠름
→ 분석 부족
→ test 실패
→ retry 3회

low-effort
→ 조금 느림
→ 대부분 한 번에 성공

full
→ 정확도 약간 증가
→ reasoning token 크게 증가
```

라면 production 기본값은 full thinking이 아니라 **low-effort**일 가능성이 큽니다.

여기에 한 가지 실험을 더 추가하면 좋습니다. 동일 8B 모델의 **BF16과 NVFP4**를 비교하십시오. IBM의 FP4 checkpoint는 2K sample·최대 2K context calibration을 사용했기 때문에, short tool call에서는 괜찮더라도 긴 context에서 구조화 출력이나 argument fidelity가 달라지는지 확인할 가치가 있습니다. ([huggingface.co][3])

최종적으로 네 값만 남기면 됩니다.

```text
strict_success
tool_call_parse_rate
wall_clock_per_success
peak_VRAM
```

이 네 축으로 보면 **“8B open model을 얼마나 많이 생각하게 할 것인지, 그리고 어느 quantization까지 내려도 agent reliability가 유지되는지”**를 자신의 workload 기준으로 바로 판단할 수 있습니다.
