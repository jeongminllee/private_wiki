## 1. TokenRouter — 여러 LLM 사이에서 토큰 단위로 작업을 이동시키는 추론 엔진 ★★★★★

**공개: 10월 8일 | NeurIPS 2026 채택 논문 | 분야: LLM Serving · Model Routing · Distributed Systems**

오늘 가장 주목할 만한 추론 시스템 연구입니다.

기존 멀티모델 에이전트는 대부분 요청이나 작업 단위로 모델을 선택합니다. 그러나 TokenRouter는 **하나의 응답을 생성하는 중에도 모델을 변경하는 Token-level Routing**을 다룹니다.

### 무엇이 달라졌는가?

예를 들어 작은 모델과 큰 모델이 함께 응답을 생성한다고 가정하겠습니다.

```text
Request
   │
   ▼
Small LLM
   │
   ├── Token 1~20 생성
   │
   ▼
Routing Decision
   │
   ├── Small LLM 유지
   │
   └── Large LLM 전환
            │
            ├── 어려운 구간 처리
            │
            ▼
        Small LLM 복귀
```

기존 서빙 시스템은 하나의 요청이 하나의 모델에서 지속적으로 실행된다는 가정에 최적화돼 있습니다.

따라서 모델을 자주 변경하면 두 문제가 발생합니다.

첫째, 서로 다른 모델이 요청을 처리하는 시점이 일치하지 않는 **Step Desynchronization**입니다.

둘째, 모델을 변경한 요청이 다시 실행 대기열에 들어오면서 발생하는 **Batch Admission Delay**입니다.

TokenRouter는 모델별로 독립적인 Subserver를 실행하고, 요청 상태를 비동기적으로 전달합니다.

연구진은 개발자가 Routing 알고리즘을 `route()`, `send()`, `receive()` 인터페이스로 구현하도록 만들었습니다. 실제 배칭과 모델별 실행은 Runtime이 담당합니다. [arXiv](https://arxiv.org/abs/2610.12242)

### 핵심 기술 — Delayed Batching

일반적으로 요청이 도착하면 최대한 빨리 실행하는 것이 좋다고 생각하기 쉽습니다.

그러나 Token-level Routing에서는 짧은 시간 기다렸다가 같은 모델로 이동하는 요청을 함께 처리하는 편이 유리할 수 있습니다.

TokenRouter는 이를 **Delayed Batching**이라고 부릅니다.

```text
Small Model → Large Model 요청 A
Small Model → Large Model 요청 B
Small Model → Large Model 요청 C

              ↓

     Delayed-Batching Queue
              ↓
       하나의 Batch로 실행
```

연구진은 이 과정을 이산시간 마르코프 체인(DTMC)으로 모델링했습니다.

모델별 처리시간, 요청 수, 모델 간 이동 확률을 이용해 처리량이 최대가 되는 배치 실행 기준값을 계산합니다.

중요한 것은 무조건 대기시간을 늘리는 것이 아닙니다. 대기 기준값이 지나치게 커지면 요청이 쌓여 오히려 GPU가 유휴 상태에 빠질 수 있습니다. [arXiv](https://arxiv.org/html/2610.12242v1)

### 실험 결과와 한계

저자들은 여러 Routing 알고리즘과 모델 조합에서 기존 구현 대비 **2.01~64.15배의 Decoding Throughput 개선**을 보고했습니다.

그러나 64배라는 수치를 일반적인 vLLM 대비 속도 향상으로 해석하면 안 됩니다.

비교 대상에는 Token-level Routing을 비효율적으로 실행하는 기존 구현이 포함돼 있습니다. 따라서 개선의 상당 부분은 불필요한 요청 재등록과 상태 복구 비용을 제거한 효과입니다.

별도의 R2R 실험에서 동시 요청 8개 기준 처리량은 약 135 tokens/s에서 372 tokens/s로 증가했습니다. 이 조건에서는 약 2.76배 개선입니다.

연구진은 라우팅 확률이 일정하다는 가정도 사용하므로 실제 에이전트의 비정상적·급격한 작업 전환에서는 별도 검증이 필요합니다. [arXiv](https://arxiv.org/html/2610.12242v1)

**실무 적용:** 작은 모델이 일반적인 토큰 생성을 담당하고, 큰 모델은 특정 구간에서만 사용하는 하이브리드 서빙 구조를 실험할 수 있습니다.

**후속 관찰:** 모델 전환 비용, KV Cache 재사용, 모델별 GPU 배치 전략, 동시 요청 증가 시 Tail Latency, Routing 정확도와 처리량의 관계입니다.

**원문:** [논문 · TokenRouter: Efficient Serving System for Token-Level LLM Routing](https://arxiv.org/abs/2610.12242) · [GitHub · thu-nics/TokenRouter](https://github.com/thu-nics/TokenRouter)

## 2. REMORY — 에이전트의 대화 요약 뒤에 학습 가능한 메모리 토큰을 추가 ★★★★★

**공개: 10월 8일 | 분야: LLM Architecture · Agent Memory · Context Compaction**

장시간 실행되는 에이전트는 Context Window가 가득 차면 이전 기록을 요약합니다.

하지만 요약 과정에서는 정보가 손실됩니다.

예를 들어 다음과 같은 작업을 생각해보겠습니다.

```text
Repository 분석
   │
   ├── 오류 원인 조사
   ├── 관련 코드 탐색
   ├── 가설 수립
   ├── 실험 실패
   ├── 새로운 가설
   └── 수정 완료
```

이 과정을 단순히 다음과 같이 요약하면 문제가 생길 수 있습니다.

> 특정 함수에서 버그를 발견했고 수정했다.

어떤 증거를 확인했는지, 어떤 시도가 실패했는지, 이후 작업에서 참고해야 할 상태가 사라집니다.

### REMORY의 접근

REMORY는 기존 텍스트 요약을 없애지 않습니다.

대신 텍스트 요약 뒤에 **학습된 Soft Memory Token**을 추가합니다.

```text
Full Interaction History
          │
          ▼
    Text Summary
          │
          ├──────────────────┐
          │                  │
          ▼                  ▼
      Summary         Memory Encoder
                              │
                              ▼
                       Soft Memory Tokens
                              │
                              ▼
                  Summary + Residual Memory
                              │
                              ▼
                       Frozen LLM
```

Memory Encoder는 전체 기록과 요약을 입력받아, 요약만으로는 부족한 정보를 보완하는 벡터를 생성합니다.

이후 원래 LLM의 가중치는 변경하지 않고 해당 벡터를 추가 입력으로 제공합니다.

핵심은 과거 기록을 완벽하게 복원하는 것이 아닙니다.

**원래 전체 기록을 제공했을 때의 후속 행동에 가까워지도록 필요한 잔여 정보를 학습하는 것**입니다. [arXiv](https://arxiv.org/abs/2610.11287)

### 실험 결과

SummHay에서는 다음 결과를 보고했습니다.

| 입력 형태 | Joint Score |
|---|---:|
| 전체 원본 Context | 43.41 |
| 텍스트 요약 | 39.84 |
| 텍스트 요약 + 추가 텍스트 | 39.78 |
| 텍스트 요약 + REMORY | 43.39 |

REMORY는 전체 원본 입력 위치의 **약 5.2%만 사용하면서** 해당 평가의 Joint Score를 거의 회복했습니다.

다만 요약만 제공한 경우보다 Insight Coverage의 개선은 작았습니다. 주요 개선은 Citation F1, 즉 추출한 정보와 근거의 연결 정확도에서 발생했습니다. [arXiv](https://arxiv.org/html/2610.11287v1)

에이전트 평가에서도 흥미로운 결과가 나타났습니다.

Qwen3.8-27B의 Terminal-Bench 2.1 점수는 71.9에서 76.4로, GLM-5.3-Flash는 84.3에서 87.6으로 증가했습니다.

반복적인 Tool Output과 Tool Error도 감소했다고 저자들은 보고했습니다.

하지만 논문의 비용 추정에서는 Memory Encoder 실행 비용 등이 제외됩니다. 따라서 발표된 비용 감소율을 실제 GPU 운영 비용 절감으로 그대로 해석하면 안 됩니다. [arXiv](https://arxiv.org/html/2610.11287v1)

### 연구 관점에서 중요한 점

REMORY는 에이전트 메모리를 두 종류로 구분합니다.

**Explicit Memory**는 사람이 읽을 수 있는 텍스트·파일·실행 기록입니다.

**Implicit Memory**는 모델이 후속 행동에 활용하도록 학습된 연속 벡터 표현입니다.

두 방식은 서로 대체하기보다 보완적인 관계가 될 수 있습니다.

특히 내부 표현을 직접 사용할 수 있는 오픈웨이트 LLM에서 연구 가치가 높습니다.

현재 공개 구현에는 SGLang 통합이 포함돼 있지만, 공식 저장소는 Qwen3.8-27B 기준 최소 80GB GPU 2장을 권장합니다. 따라서 일반적인 API 모델에 단순히 메모리 플러그인을 추가하는 방식과는 다릅니다. [GitHub](https://github.com/1ring2rta/Remory)

**실무 적용:** 텍스트 요약을 사용하는 기존 하네스와 Soft Memory를 추가한 하네스의 작업 성공률을 비교할 수 있습니다.

**후속 관찰:** 모델 변경 시 메모리 벡터 호환성, 반복 Compaction의 정보 손실, 메모리 생성 비용, 코드 수정 작업에서의 실제 효용입니다.

**원문:** [논문 · REMORY: Learning Residual Memory for Context Compaction](https://arxiv.org/abs/2610.11287) · [GitHub · 1ring2rta/Remory](https://github.com/1ring2rta/Remory)

## 3. AgentGarten — 에이전트의 학습 환경을 코드와 생성형 렌더러로 구성 ★★★★★

**공개: 10월 8일 | 분야: Agent Learning · World Model · Multimodal AI**

AgentGarten은 AI 에이전트가 다양한 환경에서 반복적으로 경험을 쌓고 학습할 수 있도록 만든 연구 프레임워크입니다.

이 연구가 다루는 핵심 문제는 **학습용 가상 환경의 정확성과 현실성**입니다.

### 기존 World Model의 문제

생성형 비디오 모델만 이용해 가상 환경을 만들면 화면은 현실적으로 보일 수 있습니다.

그러나 물체의 위치와 상태가 일관되게 유지되지 않거나, 동일한 행동에 서로 다른 결과가 발생할 수 있습니다.

반대로 게임 엔진이나 시뮬레이터는 상태와 규칙이 명확하지만 시각적 현실성이 제한될 수 있습니다.

AgentGarten은 두 방식을 결합합니다.

```text
Program-defined World
        │
        ├── Persistent State
        ├── Physics / Rules
        └── Action Execution
                 │
                 ▼
       Structured Geometry
                 │
                 ▼
         Neural Renderer
                 │
                 ▼
       Visual Observation
                 │
                 ▼
             Agent
                 │
                 ▼
              Action
                 │
                 └── World State Update
```

시뮬레이터는 세계의 상태와 행동 규칙을 유지합니다.

Neural Renderer는 해당 상태를 바탕으로 에이전트가 관찰할 시각 정보를 생성합니다. [arXiv](https://arxiv.org/abs/2610.12374)

### Adversarial Forcing

연구진은 사전학습된 비디오 생성 모델을 Geometry Condition에 맞게 조정하고, 이를 실시간 렌더링에 적합하도록 Distillation했습니다.

여기서 사용한 방법이 **Adversarial Forcing**입니다.

생성 과정의 과거 상태를 정확하게 재현하면서 후속 생성 결과의 Loss가 이전 상태 인코딩에도 반영되게 설계했습니다.

추가로 실제 영상 데이터에 기반한 Adversarial Supervision을 사용해 시각적 품질을 개선했습니다.

이 과정은 단순한 화면 생성보다 **시간적으로 일관된 관찰을 유지하는 것**에 초점을 맞춥니다. [arXiv](https://arxiv.org/abs/2610.12374)

### 에이전트는 어떻게 발전하는가?

에이전트는 환경에서 반복적으로 행동한 뒤 각 라운드의 경험을 Playbook으로 정리합니다.

다음 라운드의 에이전트는 해당 Playbook을 이어받아 행동을 개선합니다.

연구진은 특정 환경에서 4번의 학습 라운드만으로 의미 있는 개선이 나타났다고 보고합니다.

다만 이를 기존 RL보다 수백만 배 효율적이라고 해석하는 것은 부적절합니다. 두 방식의 사전학습, 학습 데이터, 경험 전달 방법이 다르기 때문입니다.

### 현재 공개 상태

공식 저장소에는 Neural Renderer의 학습 및 추론 코드가 공개됐습니다.

하지만 코드로 정의한 World 전체와 Agent Practice Loop는 추가 공개 예정입니다.

따라서 현재는 전체 연구 결과를 그대로 재현할 수 있는 완성된 프레임워크라고 보기 어렵습니다. [GitHub](https://github.com/MirroS-Lab/AgentGarten)

**실무 적용:** 게임·로봇 환경뿐 아니라 GUI Agent의 테스트 환경을 생성하는 연구에도 구조적인 참고가 됩니다.

**후속 관찰:** 생성된 환경과 실제 환경의 분포 차이, 행동 결과의 일관성, Playbook의 장기적 유용성, 전체 코드 공개 여부입니다.

**원문:** [논문 · AgentGarten: Code Worlds for Evolving Agents](https://arxiv.org/abs/2610.12374) · [GitHub · MirroS-Lab/AgentGarten](https://github.com/MirroS-Lab/AgentGarten)

## 4. vLLM 0.31.0 — 추론 스케줄러·Speculative Decoding·KV 관리의 동시 개선 ★★★★★

**릴리스: 10월 5일 | 분야: GPU Infrastructure · LLM Serving · Open Source**

이번 주 공개된 vLLM 0.31.0은 이전 브리핑에서 다룬 0.30.0 이후의 후속 릴리스입니다.

공식 릴리스 노트에 따르면 **307명의 기여자가 참여한 717개 Commit**이 포함됐습니다.

이번 릴리스에서 특히 중요한 부분은 스케줄러와 상태 관리입니다.

### 새로운 Admission Control

vLLM은 `--max-num-active-seqs` 옵션을 도입했습니다.

기존 `max_num_seqs`와 별도로 실제 실행 상태에 들어갈 수 있는 시퀀스 수를 제한합니다.

이는 장문 요청과 짧은 요청이 섞인 환경에서 중요합니다.

예를 들어 모든 요청을 최대한 많이 받아들이면 GPU KV Cache가 빠르게 소진되거나, 긴 Prefill 작업 때문에 짧은 요청의 지연시간이 증가할 수 있습니다.

실행 중인 요청 수를 별도로 관리하면 이러한 상황을 제어할 수 있습니다.

대기열도 변경됐습니다.

이미 KV Block을 보유한 요청을 우선 실행하도록 스케줄링 정책을 개선했습니다. [GitHub](https://github.com/vllm-project/vllm/releases)

### Fast Restart와 Speculative Decoding

`vllm preload` 명령은 모델 가중치를 GPU 메모리에 유지하는 Weight Cache Daemon을 실행합니다.

이를 이용하면 Engine 재시작 시 모델 Weight를 매번 처음부터 적재하는 비용을 줄일 수 있습니다.

또한 실험적인 Engine Snapshot 기능이 추가됐습니다. 다만 현재 초기화된 TP1 Engine을 대상으로 하는 제한적인 기능입니다.

Speculative Decoding에서는 Model Runner V2 지원 확대, 새로운 Drafter, 비동기 스케줄링 및 검증 기능이 추가됐습니다.

이번 릴리스에는 KV Offloading의 Back-pressure 감지와 HiSparse 관련 안정성 수정도 포함됐습니다. [GitHub](https://github.com/vllm-project/vllm/releases)

### 중요한 보안 변경

이번 버전부터 요청 단위의 일부 Multimodal Processing 옵션은 명시적인 신뢰 설정이 없는 한 거부됩니다.

또한 Prefix Cache Hash 구성에서 LoRA 및 Cache Salt 관련 충돌 가능성을 줄이는 변경이 포함됐습니다.

이는 여러 모델과 LoRA Adapter를 동시에 제공하는 Multi-tenant Serving에서 중요한 부분입니다.

### 적용 시 주의점

이번 릴리스에는 Breaking Change가 있습니다.

일부 환경변수와 Tokenizer 옵션이 제거되거나 이름이 변경됐고, 온라인 FP8 Quantization 설정도 변경됐습니다.

따라서 기존 서버를 업데이트할 때는 **모델 실행 성공뿐 아니라 출력 일치성, KV Cache 동작, TTFT, TPOT, GPU 메모리 사용량을 다시 측정**해야 합니다.

**후속 관찰:** 동시 요청 수 증가에 따른 Tail Latency, 새로운 Admission Control의 효과, Speculative Decoding과 KV Offloading의 조합 안정성입니다.

## 8. SGLang Q4 로드맵 — 스케줄러의 Rust 전환과 Agent-aware KV Cache 관리 ★★★★★

**로드맵 공개: 10월 4일 | 분야: LLM Serving · Runtime Architecture · Open Source**

SGLang 개발팀이 2026년 4분기 로드맵을 공개했습니다.

이번 문서는 신규 릴리스가 아니라 **앞으로 구현하거나 개선할 기술의 개발 계획**입니다.

그러나 추론 시스템 연구 관점에서는 매우 중요한 방향을 보여줍니다.

### 첫 번째 축 — Scheduler의 구조 변경

SGLang은 스케줄러를 더 Stateless한 구조로 만들고, CPU 측 실행 오버헤드를 줄이려 합니다.

이를 위해 Rust 기반 Scheduler 전환도 추진합니다.

여기서 중요한 문제는 GPU Kernel이 충분히 빠르더라도 CPU가 요청을 준비하고 스케줄링하는 시간이 커지면 전체 성능이 제한된다는 점입니다.

특히 출력 토큰이 짧거나 모델 자체가 빠른 환경에서는 CPU Scheduling Overhead가 상대적으로 커질 수 있습니다.

### 두 번째 축 — Agent-aware KV Cache

장기 에이전트는 반복적인 문맥을 재사용합니다.

SGLang은 이를 위한 KV Cache Scheduling과 Hierarchical Cache Reuse 개선을 계획하고 있습니다.

또한 Hybrid Architecture 지원과 HiSparse의 호환성 개선도 목표로 제시했습니다.

### 세 번째 축 — 여러 최적화 기능의 결합

현재 Serving Runtime에서 중요한 문제는 개별 기능을 구현하는 것만이 아닙니다.

예를 들어 다음 요소가 모두 존재하더라도 함께 실행되지 않을 수 있습니다.

```text
Prefix / Hierarchical KV Cache
        │
        ▼
Prefill-Decode Disaggregation
        │
        ▼
Speculative Decoding
        │
        ▼
Tensor / Expert Parallelism
        │
        ▼
Continuous Batching
```

SGLang은 이러한 기능을 함께 사용할 수 있도록 호환성을 확대하려 합니다.

Expert Parallelism에서는 통신과 계산의 Overlap, 장애 복구, 탄력적인 Scale-in/out을 개선하는 것이 목표입니다. [GitHub](https://github.com/sgl-project/sglang/issues/42473)

### 중요한 한계

로드맵에 포함됐다는 사실만으로 기능이 이미 안정적으로 구현됐다고 볼 수 없습니다.

특히 Rust 전환, 새로운 Scheduler, KV Cache 정책을 실제 서비스에 적용하려면 기능별 성능 측정뿐 아니라 조합별 Correctness Test가 필요합니다.

**후속 관찰:** Rust Scheduler의 실제 성능, Agent-aware KV Cache의 처리량 개선, PD Disaggregation과 Speculative Decoding의 조합 안정성, vLLM과의 비교입니다.

# 오늘 직접 해볼 만한 실습
## TokenRouter의 `Delayed Batching` 효과 측정

오늘은 TokenRouter를 이용해 **모델 간 Routing과 배치 정책이 전체 처리량에 어떤 영향을 주는지** 실험하는 것이 좋겠습니다.

### 연구 질문

> **모델 간 전환이 빈번한 환경에서 비동기 실행과 Delayed Batching이 처리량과 지연시간을 얼마나 개선하는가?**

### 실험 환경

모델 조합은 TokenRouter 공식 예제를 기준으로 다음과 같이 설정할 수 있습니다.

```text
Small Model: Qwen3-0.6B
Large Model: Qwen3-32B

Routing: R2R
Concurrency: 1 / 4 / 8 / 16 / 32
```

GPU는 가능하면 각각 다른 장치에 모델을 배치합니다.

두 모델을 같은 GPU에 배치하면 모델 간 Scheduling 효과와 GPU 자원 경합의 영향이 섞일 수 있기 때문입니다.

### 실험 조건

**A. Sequential Routing**

모델 간 전환을 동기적으로 처리합니다.

**B. Asynchronous Routing**

모델별 Subserver가 독립적으로 실행되며 요청 상태를 비동기적으로 전달합니다.

**C. Asynchronous Routing + Delayed Batching**

B 조건에 배치 대기 정책을 추가합니다.

가능하다면 공식 저장소의 Ablation 구성을 활용하는 편이 가장 좋습니다.

### 측정 지표

| 지표 | 목적 |
|---|---|
| Decoding Throughput | 초당 실제 생성 토큰 수 |
| Requests/s | 전체 요청 처리량 |
| TTFT P50/P95 | 초기 응답 지연 |
| TPOT P50/P95 | 토큰 생성 간 지연 |
| Batch Admission Delay | 모델별 실행 대기시간 |
| Model Handoff Count | 모델 전환 횟수 |
| GPU Utilization | 자원 활용도 |
| GPU Memory | KV Cache 및 Weight 메모리 |
| Output Accuracy | Routing 변경에 따른 품질 변화 |

특히 평균 처리량만 측정하지 않는 것이 중요합니다.

Delayed Batching은 전체 처리량을 높이면서 일부 요청의 대기시간을 증가시킬 수 있습니다.

따라서 다음 두 가지를 함께 분석해야 합니다.

**Throughput vs. Latency**

**Routing Frequency vs. Handoff Overhead**

또한 실험 결과가 개선되더라도 그 원인이 비동기 실행인지, CUDA Graph 최적화인지, 배치 정책인지 분리해야 합니다.

최종 결과는 다음과 같은 형태로 정리할 수 있습니다.

```text
Experiment
├── Model Pair
├── GPU Topology
├── Routing Algorithm
├── Batch Threshold
├── Concurrency
├── Throughput
├── Latency
├── Memory
└── Accuracy
```

이렇게 정리하면 논문의 실험을 단순히 재현하는 데 그치지 않고, **어떤 Routing 정책이 어떤 동시성 조건에서 유리한가**라는 시스템 연구 질문으로 발전시킬 수 있습니다.

공식 저장소에는 Qwen3-0.6B/Qwen3-32B 설정과 Benchmark 실행 스크립트가 포함돼 있습니다.

## 오늘의 종합 판단

오늘 조사한 자료에서 가장 중요한 흐름은 **LLM 시스템의 구성 요소가 점점 더 독립적인 최적화 대상으로 분리되고 있다는 점**입니다.

TokenRouter는 모델 간 작업 이동과 Scheduling을 다룹니다.

REMORY는 장기 실행에 필요한 정보를 어떻게 압축할지 연구합니다.

AgentGarten은 에이전트가 학습하는 환경 자체를 설계합니다.

vLLM과 SGLang은 KV Cache, GPU Scheduling, 모델 실행 계층을 개선하고 있습니다.

DeepSeek와 Broadcom의 발표는 이러한 최적화가 결국 실제 가속기와 네트워크 토폴로지 위에서 구현돼야 한다는 점을 보여줍니다.

특히 이번에 주목할 연구 주제는 **모델 내부 정보 흐름과 모델 외부 실행 시스템을 구분하면서도, 두 계층의 상호작용을 측정하는 것**입니다.

> **오늘의 핵심 결론: 더 좋은 모델을 선택하는 것뿐 아니라 모델 간 상태를 어떻게 전달하고, 어떤 정보를 보존하며, 어떤 작업을 언제 실행할 것인가가 실제 AI 시스템의 성능을 결정하고 있습니다.**
