## 1. Codex 0.154.0 + Python SDK: Agent 외부 입력에 `authority` 개념이 본격적으로 들어간다 ★★★★★

OpenAI Codex의 안정판 **0.154.0**이 9월 9일 UTC에 공개됐고, Python SDK 0.154.0은 9월 10일 공개됐습니다. CLI에는 experimental worktree가 추가되어 새로운 세션이나 fork된 세션을 별도의 checkout에서 실행할 수 있게 됐고, 실행 중에도 사용자가 inline으로 질문에 답하거나 방향을 수정할 수 있습니다. Windows에서는 background Codex server를 여러 세션이 공유하는 구조도 추가됐습니다. :chatgpt-content-reference{index="0"}

보안 쪽 변화가 더 중요합니다. startup 단계에서 **workspace가 신뢰되기 전에 workspace-controlled helper를 실행하지 않도록 수정**됐고, macOS sandbox에는 terminal-input injection 방어가 들어갔습니다. MCP OAuth token refresh가 실패했을 때 rejected tool call을 자동 replay하지 않으며, compaction 이후에도 approval의 authorization context를 보존하고 사용자의 새 지시로 authorization이 무효화되면 기존 approval을 거부합니다. 이는 coding agent에서 permission이 단순 `yes/no` flag가 아니라 **시간과 context에 따라 invalidation되는 state**라는 것을 명확히 반영한 설계입니다. :chatgpt-content-reference{index="1"}

특히 새 Python SDK의 `ExternalMessage`가 흥미롭습니다. 외부 시스템의 content가 실행 중 turn에 들어올 수 있지만 OpenAI는 이것이 **tool-level authority를 가질 수는 있어도 user authorization을 부여하지 않는다**고 명시합니다. 즉 Slack, CI, MCP, webhook 같은 외부 이벤트를 Codex에 넣을 때 `외부에서 왔다 → 사용자 지시와 동급`으로 취급하면 안 된다는 뜻입니다. :chatgpt-content-reference{index="2"}

Agent harness를 직접 설계한다면 message마다 최소한 `source`, `authority`, `authorization`, `freshness`를 분리해서 들고 가는 구조가 좋습니다. `source=CI`라는 사실과 `production deploy 권한 있음`은 전혀 같은 개념이 아닙니다.

주의할 점은 worktree와 일부 lifecycle 기능은 아직 experimental 영역이라는 점입니다. 기존 repository 자동화에 바로 넣기보다 branch/worktree cleanup과 permission persistence를 별도로 테스트하는 편이 안전합니다.

원문: [릴리스 노트 · Codex 0.154.0 / Python SDK 0.154.0](https://github.com/openai/codex/releases)

## 2. vLLM × AMD MI355X: MiniMax M3가 3배 빨라진 것보다 중요한 것은 “병목이 계속 이동했다”는 사실 ★★★★★

9월 10일 vLLM 팀과 AMD가 **MiniMax M3 on MI355X** 최적화 후속 보고서를 공개했습니다. 고정 topology MXFP8 기준 concurrency 32의 출력 throughput이 **109.1 → 342.4 output tok/s/GPU, 약 3.14배**, median TTFT는 1.46초 → 0.67초로 줄었습니다. concurrency 128에서는 297.8 → 623.7 tok/s/GPU였고, MXFP4 TP2 구성은 최종적으로 943.5 output tok/s/GPU까지 도달했습니다. :chatgpt-content-reference{index="4"}

하지만 이 글의 가치가 benchmark 숫자 자체에 있는 것은 아닙니다. 팀은 최적화 과정에서 계속 **kernel → repeated work → memory traffic → distributed state → queue/cache** 순으로 병목이 이동했다고 설명합니다. 예를 들어 shared expert를 routed expert table에 넣어 동일 grouped GEMM으로 fuse하자 concurrency 1에서는 throughput이 30.2% 올라갔지만 concurrency 128에서는 5.6%에 그쳤습니다. launch overhead가 batch에 의해 amortize된다는 전형적인 Amdahl's Law 사례입니다. :chatgpt-content-reference{index="5"}

Sparse attention에서도 비슷합니다. 인접 layer의 Top-K sparse block 선택이 거의 같다는 점을 활용해 index를 공유하자 TPOT가 concurrency 1에서 약 10%, 높은 concurrency에서 약 4% 줄었습니다. KV data 자체를 복사하는 대신 **128-token logical block을 16-token page ID table로 변환해 기존 KV allocation을 그대로 참조**하도록 만든 것도 매우 좋은 systems pattern입니다. :chatgpt-content-reference{index="6"}

이번 글에서 가장 중요한 문장은 사실 성능 숫자가 아니라 다음입니다.

`configured != eligible != executed`

INT4 QuickReduce가 설정 파일에는 켜져 있었지만 실제 collective 크기가 eligibility threshold보다 작아 kernel이 실행되지 않았던 사례가 있었습니다. 팀은 profiler나 dispatch trace 없이 “이 옵션 덕분에 빨라졌다”고 주장해서는 안 된다고 명시적으로 정정했습니다. :chatgpt-content-reference{index="7"}

또 P/D disaggregation도 좋은 교훈을 줍니다. 초기 구성은 GPU당 총 throughput은 높았지만 median TTFT가 **223초**까지 올라가 사실상 unusable했습니다. worker 비율을 다시 설계한 뒤 concurrency 512에서 6,370.5 total tok/s/GPU와 median TTFT 1.32초를 달성했지만 TPOT는 오히려 나빠졌습니다. 즉 **throughput, TTFT, TPOT를 하나의 “성능” 숫자로 합쳐서는 안 됩니다.** :chatgpt-content-reference{index="8"}

AgentX workload에서는 theoretical prefix-cache hit 96.7%인데 실제 GPU hit는 92.1%, KV cache usage는 88.5%였습니다. 이 지점부터는 GEMM kernel보다 **prefix alignment, admission, eviction, offload**가 더 큰 최적화 후보가 됩니다. :chatgpt-content-reference{index="9"}

원문: [공식 기술 블로그 · Following the Bottleneck: Optimizing MiniMax M3 on AMD Instinct MI355X](https://vllm.ai/blog/2026-09-10-minimax-m3-mi355x)

## 3. UnitBoost: Multi-Agent manager를 또 다른 LLM으로 만들 필요가 없을 수도 있다 ★★★★★

9월 9일 제출된 **UnitBoost**는 compound LLM system의 꽤 근본적인 가정을 건드립니다. 흔한 구조는 여러 worker의 결과를 다시 상위 LLM manager에게 넘겨 최종 답을 합치고, 어떤 worker를 더 부를지 결정하고, 언제 멈출지도 manager가 판단하게 하는 것입니다.

UnitBoost는 이 manager를 **생성 모델이 아닌 deterministic merge operator**로 교체합니다. worker output을 task가 정의한 unit/slot proposal로 변환하고, constrained argmax로 각 slot의 후보를 고른 뒤 아직 채워지지 않았거나 근거가 약한 slot만 residual로 남겨 다음 round의 작업 대상으로 보냅니다. :chatgpt-content-reference{index="11"}

세 held-out benchmark에서 UnitBoost는 gold label로 고른 최상의 single candidate보다 **0.060~0.195 absolute task score**, 동일 input을 받은 generative manager보다 0.048~0.076 높았고, management 단계만 UnitBoost로 바꿔도 여섯 compound configuration에서 0.013~0.182 개선됐다고 보고합니다. FanOutQA에서는 residual-directed 추가 round가 cell F1을 0.4778 → 0.5524로 올렸습니다. :chatgpt-content-reference{index="12"}

이 접근의 장점은 accuracy 못지않게 **order invariance와 provenance**입니다. LLM manager는 worker A/B/C 결과가 어떤 순서로 prompt에 들어가느냐에 영향을 받을 수 있지만 deterministic merge는 각 unit이 어느 worker에게서 왔는지를 명시적으로 기록할 수 있습니다.

실제 Agent system에서는 특히 structured report, 코드 리뷰 finding, vulnerability list, 데이터 분석 result처럼 **출력이 decomposable한 문제**에 잘 맞습니다. 예를 들어 reviewer 세 명의 결과를 또 다른 LLM에게 “합쳐줘”라고 하는 대신 CWE별 finding slot을 만들고 confidence/evidence로 deterministic merge한 뒤 conflict만 stronger model에게 넘기는 식입니다.

반대로 최종 결과가 하나의 불가분한 창작물처럼 unit으로 분리하기 어렵거나 cross-unit coupling이 강한 작업에서는 이 방식의 장점이 줄어듭니다. 논문도 이러한 failure condition을 명시합니다.

원문: [논문 · UnitBoost: Managing Compound LLM Systems with a Merge Operator, Not a Model](https://arxiv.org/abs/2609.09815)

## 4. TRACE: “정답을 검증하기 어려운 Agent 작업”도 simulator를 만들면 RLVR 문제로 바꿀 수 있다 ★★★★★

**TRACE**는 9월 9일 제출된 Agent post-training 연구입니다. 수학·코딩에서는 답을 채점하기 쉬워 RL with Verifiable Rewards가 잘 작동하지만, 장애 원인 분석이나 데이터 진단은 실제 root cause 자체가 불확실해 reward를 만들기가 어렵습니다.

TRACE는 순서를 뒤집습니다. 먼저 simulator에 **숨겨진 intervention/root cause를 주입한 다음**, 그 원인 때문에 발생해야 하는 noisy observation을 생성합니다. Agent는 Python과 SQL을 이용해 데이터를 조사하지만, 학습 시스템은 애초에 어떤 intervention을 심었는지 알고 있으므로 objective reward를 계산할 수 있습니다. :chatgpt-content-reference{index="14"}

논문의 digital-advertising diagnostic environment에는 12종 root cause와 segment attribution이 존재합니다. held-out 235 episode에서 가장 강한 prompted baseline인 Claude Opus 5의 FullAttr@1은 **0.686**, Qwen3.5-35B-A3B base는 0.159였습니다. SFT 후 0.637, synthesized-reward RL 후에는 **0.757**까지 상승했고, prompted 122B Qwen과 평가된 closed frontier model도 넘어섰다고 보고합니다. tool call 수도 base prompting보다 감소했습니다. :chatgpt-content-reference{index="15"}

이 아이디어는 상당히 확장성이 좋습니다. `실제 정답 라벨 수집이 어려움 → RL 못 함`이 아니라 **원인을 우리가 제어할 수 있는 synthetic environment를 만들고 결과를 관측시키는 것**입니다.

예를 들어 시스템 장애 Agent라면 `packet loss`, `OOM`, `disk saturation`, `misconfigured port`, `NCCL timeout`을 testbed에 의도적으로 주입해 metric/log를 생성하고, Agent가 root cause를 찾게 할 수 있습니다. 보안에서도 취약 구성이나 악성 behavior를 sandbox에 삽입한 뒤 탐지·설명 정확도로 reward를 줄 수 있습니다.

다만 simulator가 현실을 충분히 반영하지 못하면 policy가 simulator artifact를 학습할 위험이 큽니다. 따라서 최종 평가는 simulator 안이 아니라 **unseen real trace / 다른 simulator / human-curated failure**에서 수행해야 합니다.

원문: [논문 · TRACE: Training Reasoning Agents for Causal Exploration with Synthesized Rewards](https://arxiv.org/abs/2609.10315)

## 5. ConvMem: 100K+ context를 순차 memory update가 아니라 `tree-reduction`처럼 처리한다 ★★★★★

9월 9일 제출된 **ConvMem**은 long-context Agent/LLM memory를 꽤 다른 관점에서 봅니다. MemAgent 계열 방식은 긴 입력을 여러 segment로 나눠 `memory₀ → chunk₁ → memory₁ → chunk₂ → memory₂ ...`처럼 순차적으로 처리합니다. 이 구조는 context가 길어질수록 latency가 선형으로 증가하며 앞선 memory error가 뒤로 누적됩니다. :chatgpt-content-reference{index="17"}

ConvMem은 LLM 자체를 query-conditioned **convolution kernel**처럼 보고 segment들을 병렬 요약한 뒤 상위 계층에서 다시 합칩니다. 즉 순차 chain을 hierarchical tree로 바꿔 reasoning path를 linear depth에서 logarithmic depth로 줄이는 구조입니다. configurable stride, skip connection, multi-kernel을 사용해 evidence loss를 줄입니다. 별도 RL training도 필요하지 않습니다. :chatgpt-content-reference{index="18"}

이걸 systems 관점에서 보면 MapReduce와 상당히 비슷합니다.

`긴 context`
→ `병렬 local reasoning`
→ `hierarchical reduction`
→ `query-specific global state`

RULER-HotpotQA와 2WikiMultiHopQA에서 training-free baseline보다 좋은 결과를 보고했고, RL-trained memory model에서 나타날 수 있는 OOD overfitting도 피했다고 주장합니다. 다만 abstract에는 wall-clock speedup이나 token-cost 수치가 구체적으로 제시되지 않아 **“logarithmic 구조 = 실제 n배 빠름”으로 해석해서는 안 됩니다.** :chatgpt-content-reference{index="19"}

Agent system에서는 거대한 repository를 한 번에 넣기보다는 package/module 단위로 독립 reasoning을 병렬 실행한 뒤 상위 evidence graph를 구성하는 식으로 적용 가능합니다. 특히 여러 GPU/endpoint를 동시에 사용할 수 있으면 이 구조가 더 자연스럽습니다.

원문: [논문 · ConvMem: Convolutional Memory for Long-Context Reasoning](https://arxiv.org/abs/2609.10441)

## 6. VIP-Router: Visual token pruning도 “고정 전략 하나”가 아니라 input별 routing 문제다 ★★★★★

멀티모달 쪽에서는 9월 9일 제출된 **VIP-Router**가 흥미롭습니다. MLLM은 한 이미지에서도 수백~수천 개 visual token을 처리하므로 inference cost를 줄이기 위해 visual token pruning을 씁니다. 그런데 기존 연구들은 보통 하나의 pruning algorithm을 정한 뒤 모든 이미지에 동일하게 적용합니다.

연구진은 실제로는 **sample마다 최적인 pruning 전략이 다르다**는 점을 발견했습니다. 평균 benchmark에서는 전략 A가 최고여도 상당수 sample에서는 B/C 전략이 더 좋았습니다. VIP-Router는 저비용 visual/text feature를 보고 어떤 pruning strategy를 적용할지 input마다 선택하며, pruning 자체가 불리할 것으로 예상되면 full-token inference도 선택지로 남겨둡니다. :chatgpt-content-reference{index="21"}

VTC-Bench Group A에서 고정 최고 전략 대비 모든 reduction ratio에서 성능이 개선됐고, 평균 accuracy 기준 **26.9% 상대 향상**, 실제 token cost까지 반영한 utility 기준 22.0% 상대 향상을 보고했습니다. router의 trainable parameter는 backbone의 약 **0.017%**입니다. :chatgpt-content-reference{index="22"}

이건 앞서 LLM에서 나타난 mixture-of-models routing과 동일한 패턴입니다. 이제 multimodal inference도

`항상 같은 pruning ratio`
가 아니라

`input complexity → pruning strategy → token budget`

으로 가는 방향입니다.

실제 OCR/document VLM에서는 text-dense page는 token을 많이 보존하고 단순 사진은 공격적으로 줄이는 식의 adaptive policy를 만들 수 있습니다. Video라면 frame마다 pruning policy를 바꿀 수도 있습니다.

주의점은 아직 code가 “곧 공개 예정” 상태이고, reported result는 pruning-sensitive benchmark에서 나온 것입니다. 일반 VQA나 OCR, chart understanding에서 동일한 utility gain이 보장되지는 않습니다. :chatgpt-content-reference{index="23"}

원문: [논문 · Beyond One-Size-Fits-All: Sample-Adaptive Strategy Routing for Vision Token Pruning in MLLMs](https://arxiv.org/abs/2609.10346)

## 7. Audit Without Verification: Agent 감사 시스템이 증거보다 “다른 Agent의 결론”을 따라갈 수 있다 ★★★★★

Agent safety/evaluation에서는 **Audit Without Verification**을 볼 가치가 큽니다. 연구진은 여섯 Agent가 조직 경계를 넘어 순차 작업을 수행하고 각 Agent가 자신의 observation과 결론을 report로 남기는 구조를 345,600 request 규모로 실험했습니다. :chatgpt-content-reference{index="25"}

Auditor Agent는 아무도 문제를 제기하지 않은 7,996개의 clean episode에서는 false allegation을 하나도 새로 만들지 않았습니다. 문제는 **상류 Agent가 틀린 의심을 제기했을 때**였습니다. 이 경우 auditor가 innocent agent를 원인으로 지목하는 비율이 두 chain model에서 각각 34.4%, 62.6%였습니다. :chatgpt-content-reference{index="26"}

더 강력한 결과는 report에서 상류 Agent가 작성한 **“내 결론은 X다”라는 clause 하나만 제거한 실험**입니다. observation은 동일하게 유지했는데 origin attribution accuracy가 **4.1% → 45.2%, +41.2 percentage points** 상승했습니다. 반대로 상류 결론이 정말 맞는 경우에는 그 clause를 지우면 정확도가 떨어졌습니다. 즉 auditor는 독립 검증자가 아니라 **upstream conclusion을 relay하는 역할**로 쉽게 변할 수 있습니다. :chatgpt-content-reference{index="27"}

실무적 결론은 명확합니다.

Reviewer Agent에게

`worker report = evidence + worker conclusion`

을 통째로 주는 것보다,

`raw evidence`
`worker conclusion`
`audit conclusion`

을 별도 channel로 분리해야 합니다.

가능하다면 auditor에게는 먼저 **raw evidence only** 판단을 시키고 그 결과를 lock한 다음 worker의 결론을 보여주어 disagreement analysis를 하게 하는 편이 훨씬 강한 구조입니다.

이 연구는 특정 6-Agent chain을 이용한 controlled experiment이므로 모든 multi-agent reviewer가 동일한 정도로 취약하다고 일반화할 수는 없습니다. 하지만 “독립 reviewer를 하나 더 붙였다 = 독립적인 검증이 이루어졌다”는 가정은 확실히 경계해야 합니다.

원문: [논문 · Audit Without Verification: When LLM Accountability Layers Relay Rather Than Check](https://arxiv.org/abs/2609.07680)

## 8. Avatar: HPC workflow에도 LLM을 직접 executor로 넣기보다 `Orchestrator / Executor / Provenance Monitor`로 분리 ★★★★☆

분산 시스템 쪽에서는 9월 9일 제출된 **Avatar**가 재미있습니다. 기존 scientific workflow manager는 DAG와 hand-written rule에 따라 job을 제출합니다. Avatar는 여기에 LLM을 무작정 붙이지 않고 시스템을 **orchestrator, executor, provenance monitor**라는 actor로 나눕니다. :chatgpt-content-reference{index="29"}

더 중요한 것은 각 actor가 임의 shell command를 생성하는 게 아니라 하나의 **adapter-validated action catalog**를 통해 움직인다는 점입니다. 같은 core 위에서 actor policy만 rule-based 또는 LLM-backed로 교체할 수 있기 때문에 traditional scheduler와 agent scheduler를 동일 조건에서 비교할 수 있습니다. :chatgpt-content-reference{index="30"}

세 workload에서 rule mode는 기존 native workflow execution을 재현했고, LLM-backed mode에서는 연구진 기준 **compute wastage 55% 감소, GPU-busy time 40% 감소**를 보고했습니다. :chatgpt-content-reference{index="31"}

이 architecture가 좋은 이유는 LLM의 판단과 **실제 resource-control primitive를 분리**했기 때문입니다.

`LLM decides intent`
→ `validated action catalog`
→ `executor`
→ `provenance monitor`

Agent에게 Slurm/Kubernetes/AWS CLI 전체를 직접 주는 것보다 훨씬 audit하기 쉽습니다.

다만 논문은 8페이지의 초기 연구이고 세 workflow 규모입니다. 특히 55%, 40%는 일반 HPC cluster 전체에 적용되는 수치로 읽으면 안 됩니다. 그래도 **agentic scheduler를 deterministic scheduler와 동일 core에서 A/B할 수 있는 구조**는 매우 좋은 설계 패턴입니다.

원문: [논문 · Avatar: Toward Autonomous End-to-End Orchestration of Scientific Workflows using LLMs](https://arxiv.org/abs/2609.10509)

# 오늘 꼭 볼 것 3개

1. **vLLM × MI355X 최적화 보고서** — 단순 kernel tuning이 아니라 `shape → repeated work → bytes → execution verification → queue/cache`로 병목 분석 수준을 계속 올려가는 과정이 아주 좋습니다. 특히 `configured != eligible != executed`는 inference benchmark에서 꼭 기억할 문장입니다. :chatgpt-content-reference{index="33"}
2. **TRACE** — Agent RL을 하려면 “정답 있는 데이터가 필요하다”가 아니라 **검증 가능한 simulator를 만들어 reward를 engineering할 수 있다**는 방향이 매우 강합니다. :chatgpt-content-reference{index="34"}
3. **Audit Without Verification** — multi-agent 구조에서 reviewer를 하나 추가하는 것만으로 독립 검증이 생기는 게 아니라는 사실을 대규모 controlled study로 보여줍니다. :chatgpt-content-reference{index="35"}

# 오늘 직접 해볼 만한 실습 — `Configured → Eligible → Executed → Correct → Faster` 5단계 vLLM 검증

오늘은 vLLM 글의 핵심 원칙을 그대로 실험 harness에 넣어보는 걸 추천합니다.

현재 사용하는 옵션 하나를 선택하십시오. 예를 들어 `prefix caching`, `FlashAttention backend`, `FP8 KV`, `speculative decoding`, `tensor parallel` 중 하나면 됩니다. 그리고 benchmark 결과 JSON에 단순히 `"enabled": true`를 기록하는 대신 다음 다섯 상태를 남깁니다.

```text
configured  : 내가 옵션을 켰는가?
eligible    : 현재 shape/hardware/backend가 실제 fast path 조건을 만족하는가?
executed    : profiler/dispatch log상 해당 kernel/path가 실제 실행됐는가?
correct     : baseline과 task accuracy/output validity가 유지되는가?
faster      : 동일 workload에서 TTFT/TPOT/throughput이 실제 개선됐는가?
```

여기에 `concurrency`, `input/output length`, `TP size`, `GPU model`, `cache hit`, `GPU KV usage`까지 같은 JSON에 넣으십시오.

이렇게 하면 나중에

> “TP=2가 빨랐다”

가 아니라

> “concurrency 32, 256/128 tokens에서 TP=2가 특정 attention backend의 eligible fast path를 활성화했고, accuracy는 동일하며 TPOT가 X%, throughput이 Y% 개선됐다”

라고 쓸 수 있게 됩니다.

단순 benchmark 결과표가 **재현 가능한 systems research artifact**로 바뀌는 지점이 바로 여기입니다.
