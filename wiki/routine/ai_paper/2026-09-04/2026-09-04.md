오늘은 **오픈 AI 생태계의 구조 변화, 로컬 에이전트 인프라, 멀티모달 RAG, 에이전트 메모리, GPU scheduling** 쪽이 특히 중요합니다. 가장 큰 사건은 단연 **NVIDIA의 Hugging Face 인수 계약**이고, 기술적으로는 NVIDIA PAIR가 보여주는 “여러 로컬 PC를 agent inference pool로 쓰는 방식”, 그리고 작은 모델을 목적별로 후학습하는 흐름이 눈에 띕니다. 연구 쪽에서는 shared-GPU scheduling과 장문-context prefill interconnect, 그리고 agent fleet 전체의 위험을 누적 관리하는 새로운 safety abstraction이值得 볼 만합니다.

## 1. NVIDIA, Hugging Face를 약 129억 달러에 인수하기로 합의 ★★★★★

NVIDIA가 9월 3일 **Hugging Face를 $12.9303B에 인수하기로 합의했다고 공식 발표**했습니다. Hugging Face는 현재 1,800만 명 이상의 개발자, 300만 개 이상의 모델, 50만 개 이상의 dataset, 100만 개 이상의 application을 보유한 사실상의 open-model distribution layer입니다. NVIDIA는 인수 이후에도 Hugging Face가 특정 NVIDIA hardware를 요구하지 않으며, multi-cloud·multi-accelerator 환경과 다양한 model builder를 계속 지원하겠다고 명시했습니다. citeturn979595view0

이건 단순한 플랫폼 M&A가 아닙니다. NVIDIA의 stack을 보면 `GPU → CUDA → TensorRT/vLLM ecosystem → Nemotron/open models → Hugging Face model/data distribution`까지 연결됩니다. 즉 NVIDIA가 이제 compute vendor를 넘어 **AI artifact distribution과 developer workflow 자체를 소유하는 방향**으로 이동합니다. 모델을 찾고, 평가하고, quantize하고, inference provider를 선택하고, 배포하는 경로가 NVIDIA 생태계와 더 밀접해질 가능성이 큽니다.

엔지니어 입장에서 당장 Transformers를 버리거나 대응할 필요는 없습니다. 오히려 CUDA·TensorRT·vLLM·NVFP4·FlashInfer 같은 NVIDIA optimization이 Hugging Face model card, Inference Endpoints, benchmark 등에 더 빠르게 녹아들 가능성이 있습니다. 반면 AMD, Intel, AWS Trainium, Google TPU, Apple Silicon 같은 non-NVIDIA backend가 **실제로 지금과 같은 1급 지원을 유지하는지**는 반드시 관찰해야 합니다.

특히 NVIDIA가 “open platform”을 명시적으로 약속했다는 것과 실제 default inference provider, benchmark 노출 순서, optimization tooling, enterprise pricing이 hardware-neutral하게 유지되는 것은 별개의 문제입니다. 거래가 완료된 뒤 Transformers·Accelerate·PEFT·Safetensors·Inference Providers의 governance가 어떻게 운영되는지가 더 중요합니다. citeturn979595view0

## 2. NVIDIA PAIR: 집이나 연구실의 여러 PC를 하나의 “Agent inference pool”로 묶는다 ★★★★★

같은 날 NVIDIA는 **PAIR(Personal AI Router)** beta도 공개했습니다. PAIR는 LAN에 있는 RTX PC, DGX Spark, Apple Silicon Mac을 자동 발견하고 Ollama·LM Studio 요청을 available node로 routing하는 local inference layer입니다. 중요한 점은 여러 GPU의 VRAM을 합쳐 하나의 거대한 GPU처럼 만드는 기술이 아니라, **독립적인 inference request를 여러 node로 분산하는 scheduler**라는 것입니다. NVIDIA도 명시적으로 “one virtual GPU로 합치지 않는다”고 설명합니다. citeturn951808view0

Agent workload에는 이 방식이 상당히 잘 맞습니다. 예를 들어 planner가 5개의 subagent를 병렬 실행한다면 한 GPU queue에 모두 넣는 대신 `subagent A → PC1`, `B/C → PC2`, `D/E → PC3`처럼 request-level scheduling을 할 수 있습니다. tensor parallelism이 아니라 **task parallelism**입니다. 멀티에이전트 구조에서는 오히려 이쪽이 구현과 failure isolation 측면에서 훨씬 단순합니다.

NVIDIA가 같이 공개한 inference optimization도 주목할 만합니다. llama.cpp는 RTX 5090에서 kernel optimization·speculative decoding·prefill 개선으로 최대 1.9배 throughput, vLLM은 RTX PRO 6000 Blackwell에서 약 1.2배, 두 DGX Spark 환경에서 최대 약 1.4배를 보고했습니다. 이 수치는 특정 hardware와 workload에 대한 vendor 측 결과이므로 일반화하면 안 되지만, **local LLM inference가 llama.cpp와 vLLM 양쪽에서 본격적인 optimization target이 되고 있다는 흐름**은 확실합니다. citeturn906125view0

현재처럼 WSL에서 Codex 계열을 쓰고 Hermes 같은 local agent도 실험한다면 이 architecture는 꽤 참고할 만합니다. 직접 PAIR를 쓰지 않더라도 `OpenAI-compatible router → 여러 vLLM/Ollama backend → capacity-aware scheduling` 구조를 구현하면 같은 원리를 재현할 수 있습니다. citeturn906125view0turn951808view0

관찰 포인트는 latency-aware routing, model locality, warm KV/cache locality입니다. 단순 “빈 GPU로 보내기”는 모델이 다른 node에 없거나 cold load가 필요하면 오히려 느릴 수 있습니다. 앞으로 PAIR가 model placement와 KV/cache affinity까지 고려하는지가 핵심입니다.

## 3. NeoMME: Visual RAG에 꼭 거대한 VLM을 사용할 필요가 없다는 접근 ★★★★★

H Company가 9월 3일 **NeoMME 260M/800M**을 공개했습니다. 일반적인 visual document retriever는 pretrained vision tower와 causal LLM을 조합하는 경우가 많은데, NeoMME는 아예 처음부터 **text token과 raw image patch를 하나의 bidirectional Transformer에서 처리**하도록 설계했습니다. 16,384 token context를 지원하며 모든 checkpoint는 Apache 2.0으로 공개됐습니다. citeturn565546view0turn354195view1

이 구조가 중요한 이유는 RAG에서 “생성 능력”이 필요 없는 retrieval stage까지 수십억 parameter VLM을 쓰는 것이 과한 경우가 많기 때문입니다. NeoMME-Retriever는 한 번의 forward에서 dense embedding과 late-interaction embedding을 동시에 생성합니다. 먼저 dense ANN 검색으로 후보를 좁히고 late interaction으로 rerank하는 **two-stage retrieval**을 한 backbone에서 구현할 수 있습니다. citeturn565546view0

260M 모델은 ViDoRe v3에서 nDCG@10 0.523을 기록했고, 2048×2048 페이지 기준 L40S에서 초당 약 51 page를 encode했다고 보고합니다. 더 재미있는 부분은 late-interaction index입니다. 기본 약 1.5MB/page 수준인 embedding을 hierarchical token pooling과 asymmetric quantization을 통해 **약 6KB/page까지 255배 압축하면서 baseline nDCG의 95% 이상을 유지**했다고 합니다. citeturn565546view0

이 정도면 PDF가 수백만 페이지인 enterprise RAG에서 storage economics가 달라집니다. OCR → chunking → text embedding pipeline 대신 `PDF page → image → NeoMME → vector index` 구조를 고려할 수 있습니다. 표, diagram, font, layout 같은 정보도 유지됩니다.

다만 benchmark 비교 중 일부 NeoMME 결과는 저자 자체 평가이고 경쟁 모델 중 일부 값은 MTEB에서 가져왔기 때문에 완전히 동일한 evaluation harness라고 단정하기 어렵습니다. 한국어 PDF, 복잡한 표, 스캔 문서에서는 별도 benchmark가 필요합니다. citeturn565546view0

## 4. Hugging Face `funes`: Codex·Claude Code·Hermes의 기억을 하나로 합친다 ★★★★★

오늘 개인적으로 가장 실용적인 open-source release 중 하나는 **funes**입니다. coding agent가 생성한 session trace를 수집해서 Claude Code, Codex, pi, Hermes가 공유할 수 있는 durable memory로 만드는 도구입니다. citeturn906125view1turn120162view0

구현도 꽤 합리적입니다. session을 공통 turn/block schema로 변환한 뒤 local Lance dataset에 저장하고, query에서는 **vector search + BM25 → rank fusion → cross-encoder reranking → recency weighting → neighboring chunk expansion**을 수행합니다. 중요한 점은 memory를 요약된 “fact”로 미리 변환하지 않고 원본 trace를 보존한다는 것입니다. recall 결과에서 agent, timestamp, session, turn까지 provenance를 추적할 수 있습니다. citeturn906125view1

이 패턴은 멀티에이전트 harness를 설계할 때 상당히 유용합니다.

`Agent memory ≠ giant context window`

대신

`Agent trace → durable event store → retrieval → 필요한 evidence만 context에 주입`

이라는 구조입니다.

이렇게 하면 Claude Code에서 한 설계 결정을 다음 주 Codex가 가져오거나, 다른 PC의 Hermes가 이전 실패 원인을 조회하는 식의 **agent-independent memory layer**가 가능해집니다. 실제로 funes는 이 네 agent를 기본 지원합니다. citeturn120162view0

보안 측면에서는 local embedding/reranking을 기본으로 하고 Hub에 publish할 때 credential redaction과 추가 secret scanning을 수행합니다. 하지만 secret scanner가 완벽할 수는 없으므로 회사 code/session trace를 Hub dataset에 sync할 때는 private repository라 해도 별도의 DLP 정책이 필요합니다. citeturn906125view1

## 5. 350M 모델도 목적을 좁히면 GRPO 100 step으로 꽤 달라진다 ★★★★☆

Hugging Face와 Liquid AI가 공개한 새 실습은 **LFM2.5-350M을 약 500개 sample, 100 GRPO step만으로 structured-output 전문 모델로 만드는 것**입니다. 16GB GPU에서도 실행할 수 있도록 설계된 공개 recipe입니다. citeturn728571view1

동일한 llama.cpp/BF16 serving 환경에서 IFStruct 전체 통과율은 **22.6% → 29.7%**, JSON은 **18.0% → 31.9%**로 올랐습니다. 반면 YAML은 27.2% → 27.5%로 거의 변하지 않았습니다. 이 결과가 오히려 중요합니다. 학습이 모델의 “전반적 지능”을 향상시킨 것이 아니라 **reward가 집중된 capability가 선택적으로 개선됐다**는 증거에 가깝습니다. citeturn728571view0

Agent tool calling이나 API backend를 만들 때 30B 모델을 항상 부를 필요가 없는 이유이기도 합니다. 예를 들어 JSON schema generation, SQL formatting, classifier, router, validation처럼 task가 좁은 영역은 0.3B~3B specialist를 post-train하고 강한 모델은 planning에만 사용하는 구조가 비용 측면에서 훨씬 합리적일 수 있습니다.

다만 29.7% 자체는 절대적으로 높은 성공률이 아닙니다. 실제 production tool-call system이라면 모델 fine-tuning과 별개로 **JSON schema constrained decoding, parser validation, retry/repair loop**가 여전히 필요합니다. “RL을 했으니 parser가 필요 없다”는 결론으로 가면 안 됩니다.

## 6. 새 연구: 여러 AI 모델이 한 GPU를 공유할 때 모든 조합을 profiling할 필요가 없을 수도 있다 ★★★★★

**MeanField Surrogate Modeling for Scalable Runtime Scheduling of Concurrent Heterogeneous AI Inference on Shared GPUs**가 9월 2일 제출됐습니다. 문제는 간단합니다. LLM, vision model 등 여러 workload를 하나 GPU에서 동시에 돌리면 서로 resource contention을 일으키는데, 최적 configuration을 찾으려면 모든 model 조합을 profiling해야 합니다. 모델 수가 늘면 조합 수가 폭발합니다. citeturn776494view1

연구진은 각 모델의 local configuration과 GPU의 aggregate state만 이용하는 **MeanField surrogate**를 제안했습니다. N=2~6의 LLM/vision concurrent workload에서 약 `R²≈0.96`을 기록했고, profiling sample 수가 조합적이 아니라 대략 선형으로 증가했다고 보고합니다. citeturn776494view1

N=5에서는 가능한 joint configuration이 78,732개였는데, surrogate + genetic algorithm scheduler가 exhaustive search 대비 **0.10% 이내의 결과와 0건의 SLA violation**, median decision latency 약 26ms를 기록했습니다. citeturn776494view1

이 아이디어는 GPU cluster scheduler에서도 굉장히 유용합니다. production 환경에서 매번 모든 `batch size × memory fraction × model × concurrency` 조합을 benchmark할 수 없습니다. 대신 offline benchmark로 surrogate를 학습하고 runtime에서는 GPU utilization, memory pressure, active sequences 같은 상태를 넣어 placement를 결정할 수 있습니다.

주의점은 논문이 4페이지이고 평가 scale도 최대 6개 동시 모델 수준이라는 것입니다. vLLM continuous batching, MoE expert parallelism, KV cache fragmentation까지 들어간 대규모 serving에서는 interaction이 mean-field approximation보다 복잡할 수 있습니다.

## 7. 1M-token 시대의 병목: GPU FLOPS보다 prefill interconnect가 먼저 터질 수 있다 ★★★★☆

새 연구 **Scaling Inference Prefill with High-Radix Photonic Interconnects**는 long-context MoE inference를 interconnect 관점에서 분석합니다. 연구진은 1K~8K, 128K, **1M token context** MoE workload를 copper 기반 GPU system과 high-bandwidth 3D photonic interconnect를 사용하는 system에서 simulation했습니다. citeturn741090view0

고부하 batch 조건에서 photonic 구성은 latency를 2.1~3.2배 줄였고 communication-limited configuration에서는 baseline 대비 2.8~5.8배 개선됐다고 보고합니다. 특히 TTFT를 줄이기 위해 1,152 GPU까지 확장한 경우 electrical scale-up pod의 한계를 넘어서면서 2.2~4.5배 speedup이 나타났습니다. citeturn741090view0

여기서 얻어갈 핵심은 photonics 제품 자체보다 **prefill scaling law**입니다. 긴 context에서는 모든 token의 attention/activation과 MoE routing이 대량의 GPU 간 communication을 발생시키기 때문에 FLOPS를 늘려도 interconnect가 따라오지 못하면 TTFT가 개선되지 않습니다.

따라서 B200 같은 GPU를 여러 장 쓸 때 profiling을 한다면 GPU utilization만 보면 부족합니다. 적어도 `prefill tokens/s`, `decode tokens/s`, `TTFT`, `NCCL collective time`, `NVLink/NVSwitch throughput`, `expert all-to-all traffic`을 분리해서 측정하는 것이 좋습니다.

다만 이번 결과는 **simulation 연구**입니다. 1,152-GPU photonic system에서 실측한 production benchmark가 아닙니다. packaging, switch contention, power, topology, cost 등의 현실적인 constraint가 추가되면 결과가 달라질 수 있습니다.

## 8. Agent safety의 새 abstraction: 위험한 행동 하나가 아니라 “전체 fleet의 누적 비가역성”을 제한하라 ★★★★☆

**The Irreversibility Budget** 논문은 agent operating system을 설계할 때 흥미로운 문제를 제기합니다. 기존 permission system은 보통 `이 agent가 지금 이 행동을 해도 되는가?`를 개별적으로 판정합니다. 하지만 수백 개 agent가 동시에 돈을 이동하고, code를 deploy하고, 데이터를 삭제하고, 외부로 정보를 보내면 각 행동이 모두 허용 범위여도 **전체 조직 차원의 위험 한도**를 초과할 수 있습니다. citeturn776494view2

연구진은 각 principal에 대해 누적 residual risk를 계산하는 `irreversibility budget`을 두고, agent·workflow·tenant를 넘어 위험을 하나의 resource처럼 accounting하자는 접근을 제안합니다. controlled study에서는 per-action gate만 사용할 경우 tenant risk limit의 최대 **48배까지 fleet-level overdraw**가 발생할 수 있었지만, 올바르게 위험이 pricing된 경우 budget 방식은 한도를 유지했습니다. citeturn776494view2

이건 멀티에이전트 orchestration에서도 상당히 좋은 abstraction입니다. token budget이나 GPU budget처럼

`financial_budget`
`external_api_budget`
`delete_budget`
`deployment_budget`
`data_exposure_budget`

를 root task 단위로 설정한 뒤 subagent가 실행할 때마다 차감하는 방식입니다. 그러면 agent 하나가 규칙을 지켜도 전체 tree가 과도한 side effect를 만드는 문제를 막을 수 있습니다.

가장 어려운 문제는 논문도 인정하듯 **risk pricing**입니다. `git push` 하나와 production DB delete를 같은 unit으로 환산하는 것은 쉽지 않고, 서로 correlated된 action의 risk도 단순 합산하기 어렵습니다. 따라서 당장은 정확한 value-at-risk 모델보다 high-impact action에 coarse budget을 적용하는 수준이 현실적입니다. citeturn776494view2

**1순위는 NVIDIA × Hugging Face 인수 발표**입니다. 향후 Transformers, PEFT, model distribution, inference provider ecosystem에 장기적으로 영향을 줄 수 있는 구조적 사건입니다.

**2순위는 NVIDIA PAIR**입니다. 멀티에이전트와 local LLM의 관계를 `multi-GPU model parallelism`이 아니라 `distributed request scheduling` 관점에서 보여주는 좋은 실제 구현입니다.

**3순위는 Funes**입니다. Agent memory를 특정 모델이나 특정 coding agent에 묶지 않고 **durable retrieval layer**로 분리한 설계가 꽤 깔끔합니다.

# 오늘 직접 해볼 만한 실습 — Codex/Hermes 공용 Agent Memory 만들기

오늘은 `funes`를 가장 추천합니다. 설치 후 Codex session을 몇 개 index하고, 과거에 했던 기술적 결정 하나를 새로운 session에서 `recall`하게 해보십시오. 그다음 같은 memory를 Hermes에도 연결해서 **Codex에서 만들어진 decision trace를 Hermes가 검색할 수 있는지** 확인하는 방식입니다.

여기서 단순히 “기억하네”에서 끝내지 말고 `retrieval latency`, `top-k relevance`, `잘못된 session recall`, `token 절감량`, `원본 provenance 추적 가능 여부`를 기록하면 좋습니다. 이후 직접 만들고 있는 agent harness에도 `agent → persistent trace → hybrid retrieval → evidence injection` 구조를 적용할 수 있습니다. 이 실습 하나로 오늘 나온 **agent memory, context compression, multi-agent orchestration** 흐름을 상당히 직접적으로 체감할 수 있습니다. memcite
