# AI 엔지니어 데일리 브리핑 — 2026년 9월 24일

한국시간 **9월 24일 오전** 기준으로 확인했습니다. 오늘은 모델 신제품보다 **Agent 평가·실행환경·관측성·AI 보안·추론 재현성** 쪽이 훨씬 중요합니다. 특히 눈에 띄는 공통 흐름은 **“모델이 코드를 잘 짰는가?”에서 “실제 서버가 뜨고, 권한이 격리되고, 실행 trace가 남고, 다른 GPU에서도 결과가 재현되는가?”로 엔지니어링 기준이 올라가고 있다는 것**입니다.

## 1. NVIDIA SWE-Serve — Coding Agent가 테스트를 통과해도 실제 LLM 서버에서는 3개 중 1개가 실패 ★★★★★

NVIDIA가 9월 23일 **SWE-Serve**를 공개했습니다. 일반 SWE-bench가 repository issue 해결 능력을 본다면 SWE-Serve는 **LLM inference engine 자체를 수정하는 Agent**를 평가합니다. 최근 SGLang의 merged PR 83개를 기반으로 53개 task를 만들었고, model enablement, speculative decoding, quantization, caching, serving API, scheduler, distributed execution 등 여섯 영역을 포함합니다. 41개 task는 H100 한 장에서 실제 GPU execution을 요구합니다. :chatgpt-content-reference{index="0"}

결과가 꽤 강합니다. 실제 model server를 띄우는 19개 task에서 Agent patch 627개를 평가했을 때, **live-serving test를 제외하면 69.4%가 통과했지만 전체 verifier에서는 45.9%만 통과**했습니다. 즉 unit/regression test를 모두 통과한 patch 상당수가 실제 model load, expert routing, batching, log probability, OpenAI-compatible API를 거치면서 실패했습니다. 또 request handling·scheduler·model execution·KV cache 등 여러 runtime domain을 동시에 건드리는 task는 single-domain task보다 pass rate가 **21.3 percentage points 낮았습니다.** :chatgpt-content-reference{index="1"}

이건 LLM infrastructure 개발에서 상당히 중요한 결과입니다. 앞으로 Coding Agent가 vLLM/SGLang 코드를 수정했을 때 검증 pipeline을

`ruff/mypy/pytest`
→ `model load`
→ `real API request`
→ `batched generation`
→ `concurrency`
→ `latency/performance gate`

까지 내려야 합니다. 특히 scheduler·KV cache·TP 코드는 unit test만으로 correctness를 확인하기 어렵습니다.

흥미롭게도 Claude Opus 5와 GPT-5.6 Sol이 약 75% 수준으로 최상위였지만 cost와 wall-clock은 크게 달랐습니다. 또 Codex/Claude Code 같은 native harness가 mini-swe-agent보다 반드시 좋지는 않았습니다. 즉 **model score와 harness branding보다 verifier가 실제 production path를 얼마나 재현하느냐가 더 중요**합니다. :chatgpt-content-reference{index="2"}

첫 릴리스는 SGLang, single-H100 중심이고 multi-GPU·multi-node는 아직 포함하지 않습니다. 따라서 TP/NCCL 문제까지 대표한다고 보면 안 됩니다.

원문: [논문 · SWE-Serve: Benchmarking Agentic Engineering For Production Inference Serving](https://arxiv.org/abs/2609.26777) · [GitHub · NVIDIA/swe-serve](https://github.com/NVIDIA/swe-serve) · [공식 기술 블로그 · How SWE-Serve Exposes the Gap Between Local Tests and Live Serving](https://developer.nvidia.com/blog/how-swe-serve-exposes-the-gap-between-local-tests-and-live-serving/)

## 2. GitHub Copilot — `Sandbox + OpenTelemetry`가 Agent runtime의 기본 구성으로 들어간다 ★★★★★

GitHub가 9월 23일 Copilot app에 **local sandboxing**을 추가했습니다. 프로젝트마다 filesystem read/write 범위, denied folder, outbound internet, local network, Git credential, GitHub CLI credential을 제한할 수 있습니다. 더 중요한 것은 OS가 해당 policy를 실제로 강제할 수 없으면 **sandbox 없이 실행하는 대신 shell 자체를 실패시킨다는 것**입니다. :chatgpt-content-reference{index="6"}

전날인 9월 22일에는 **OpenTelemetry export**도 추가됐습니다. Enterprise 관리자는 Agent session에서 model request와 tool 사용을 span 형태로 기존 observability stack에 보내고, 실행 흐름과 비정상 동작을 step-by-step으로 조사할 수 있습니다. Prompt/response 본문은 기본적으로 telemetry에서 제외됩니다. :chatgpt-content-reference{index="7"}

둘을 묶어서 보는 것이 중요합니다. Agent 운영 stack이 사실상

`LLM`
→ `sandboxed tool execution`
→ `filesystem/network/credential policy`
→ `OTel trace`
→ `incident analysis`

형태로 굳어지고 있습니다.

즉 system prompt에 “절대로 workspace 밖 파일을 수정하지 마라”고 쓰는 것보다 OS sandbox에서 실제로 차단하고, 이후 OTel에서 어떤 tool을 호출했는지 확인하는 구조가 훨씬 강합니다.

직접 Agent harness를 만든다면 span에도 일반 web service와 다른 필드가 필요합니다.

`agent_id`
`session_id`
`tool_name`
`resource`
`authorization`
`input/output size`
`side_effect`
`approval`
`latency`
`error`

같은 attribute를 표준화해두면 Agent 장애를 분산시스템 trace처럼 분석할 수 있습니다.

현재 sandbox는 public preview이고 **기본 OFF**라는 점은 주의해야 합니다. 또 cloud/remote-host session에는 동일한 설정이 적용되지 않습니다. :chatgpt-content-reference{index="8"}

원문: [릴리스 노트 · Local sandboxing in the GitHub Copilot app](https://github.blog/changelog/2026-09-23-local-sandboxing-in-the-github-copilot-app) · [릴리스 노트 · OpenTelemetry in the GitHub Copilot app](https://github.blog/changelog/2026-09-22-opentelemetry-in-the-github-copilot-app/)

## 3. RRSI — Agent가 자기 Harness를 개선하게 하면 benchmark를 외우기 시작한다 ★★★★★

9월 21일 UTC 제출된 **RRSI: Regularized Recursive Self-Improvement of Agent Harnesses**는 최근 빠르게 늘어나는 “Agent가 자기 prompt/tool/memory/control flow를 스스로 개선한다”는 연구의 중요한 약점을 다룹니다. 문제는 finite benchmark를 반복해서 보면서 harness를 수정하면 실제 일반화가 아니라 **benchmark-specific trick을 누적하는 방향으로 overfit**하기 쉽다는 것입니다. :chatgpt-content-reference{index="11"}

RRSI는 무엇을 수정할 수 있는지는 제한하지 않습니다. Prompt, tool, skill, memory, subagent, context policy 모두 수정 가능하지만 **어떻게 수정하는가**를 regularize합니다. 초기에는 여러 component를 동시에 탐색하되 round가 진행될수록 candidate 하나에서 바꿀 수 있는 edit 수를 줄이고, 과거 실패한 hypothesis를 history로 남겨 반복하지 않게 합니다. Candidate 선택 시에는 benchmark-specific logic을 critic이 걸러내고, evaluation noise보다 작은 개선은 인정하지 않으며, token cost 증가가 성능 개선보다 크면 reject합니다. :chatgpt-content-reference{index="12"}

8개 benchmark에서 evolve split에서는 최대 **+14.1 points**, 사용하지 않은 OOD benchmark에서는 최대 **+4.7 points** 개선했고, regularization 없는 self-evolution보다 policy-token 사용량도 약 **30% 감소**했습니다. 특히 unregularized search는 evolve benchmark score는 더 높아지는데 OOD 성능과 token efficiency는 더 나빠지는 전형적인 overfitting pattern을 보였습니다. :chatgpt-content-reference{index="13"}

이 연구가 harness 설계에 주는 교훈은 상당히 실용적입니다. Agent 개선 loop를 돌릴 때

`benchmark score 상승 → 채택`

이면 부족합니다.

최소한

`score improvement`
`evaluation noise`
`OOD validation`
`token cost`
`complexity`
`task-specific leakage`

를 동시에 gate로 두어야 합니다.

특히 자동으로 AGENTS.md, prompt, skill을 계속 수정하는 시스템을 만들 경우 **“최종 harness가 왜 복잡해졌는가?”를 설명할 edit ledger**가 필요합니다.

원문: [논문 · RRSI: Regularized Recursive Self-Improvement of Agent Harnesses](https://arxiv.org/abs/2609.24972?utm_source=chatgpt.com) · [GitHub · google-research/rrsi](https://github.com/google-research/rrsi?utm_source=chatgpt.com)

## 4. GPU가 바뀌면 temperature=0도 결과가 달라진다 — Ampere·Ada·Hopper 간 bitwise deterministic inference 연구 ★★★★★

9월 22일 제출된 **Accelerating the Mitigation of LLM Inference Nondeterminism Across GPU Architectures**는 inference reproducibility에서 상당히 중요한 문제를 다룹니다. 동일 weight, prompt, software, greedy decoding을 써도 A100·L40S·H100처럼 GPU architecture가 달라지면 GEMM kernel과 floating-point reduction order가 달라져 logits가 조금씩 달라지고, top-1/top-2가 가까운 경우 token 자체가 달라질 수 있습니다. :chatgpt-content-reference{index="16"}

원인은 seed 문제가 아니라 **floating-point non-associativity + device별 GEMM 선택 + Tensor Core 내부 arithmetic 차이**입니다. 특히 BF16 reasoning model에서는 초기의 작은 수치 차이가 autoregressive decoding을 거치면서 완전히 다른 trajectory로 증폭될 수 있습니다. :chatgpt-content-reference{index="17"}

연구진은 BF16 weight를 HBM에서 읽고 register 안에서 FP32로 upcast한 뒤, device마다 다른 vendor GEMM을 쓰지 않고 **problem shape만으로 결정되는 고정 reduction order + IEEE-754 FMA**를 사용했습니다. Ampere·Ada·Hopper에서 linear-layer output이 bitwise identical했고, 기존 cross-architecture reproducibility 방식보다 end-to-end **1.17×~3.1× 빠르면서 weight memory traffic도 절반**으로 줄였습니다. vLLM end-to-end evaluation도 수행했습니다. :chatgpt-content-reference{index="18"}

이 연구는 benchmark 재현성에서 특히 중요합니다. 예를 들어

`A6000 개발`
→ `B200 테스트`

처럼 GPU architecture가 달라지면 software version과 seed가 같더라도 output difference가 생길 수 있습니다. 이런 경우 evaluation score 변화가 code/model change 때문인지 GPU numerical behavior 때문인지 분리해야 합니다.

그래서 reproducible inference artifact라면 최소한

`GPU architecture`
`GPU count`
`batch size`
`kernel/backend`
`precision`
`TF32 여부`

까지 기록해야 합니다.

다만 deterministic kernel은 peak-performance kernel과 trade-off가 있습니다. 모든 production inference를 bitwise deterministic으로 만들 필요는 없고, **regression testing·audit·scientific evaluation**처럼 reproducibility가 필요한 path에 선택적으로 적용하는 것이 현실적입니다.

원문: [논문 · Accelerating the Mitigation of LLM Inference Nondeterminism Across GPU Architectures](https://arxiv.org/abs/2609.25624)

## 6. Anthropic 생명과학 Agent — 950개 Agent가 21시간 동안 DNA를 뒤져 새 enzyme system 후보 발견 ★★★★☆

Anthropic이 9월 23일 새 **life sciences research group과 실험실**을 공개하면서 첫 연구 결과를 발표했습니다. Claude Agent 약 **950개가 21시간 동안 2.1억 token을 사용해 대규모 DNA sequence database를 탐색**했고, reverse transcriptase 주변에 반복되는 non-coding DNA array와 accessory protein이 함께 존재하는 패턴을 발견했습니다. Anthropic은 이 system을 **array-associated reverse transcriptase(ART)**라고 부르고 있습니다. :chatgpt-content-reference{index="28"}

중요한 부분은 Agent orchestration입니다. 사람은 초기 목표를 주고 wet-lab verification을 담당했으며, Agent들이 protein family 조사, 후보 탐색, 문헌 검토, anomaly 발견과 후보 우선순위 결정을 병렬로 수행했습니다. 이후 살아남은 후보를 인간 과학자가 실제 실험으로 확인했습니다. :chatgpt-content-reference{index="29"}

이것은 “LLM이 CRISPR를 새로 발견했다”로 표현하면 과장입니다. Anthropic도 **ART의 실제 biological function은 아직 모른다**고 명시합니다. 기존 연구에서 해당 RT 자체는 알려져 있었고, 새로 발견한 것은 RT와 반복 array·accessory protein을 하나의 uncharacterized system으로 연결한 것입니다. :chatgpt-content-reference{index="30"}

그럼에도 연구 automation 측면에서는 중요합니다.

`large search space`
→ `수백 parallel Agents`
→ `candidate generation`
→ `critical filtering`
→ `human review`
→ `physical experiment`

구조가 실제 과학 discovery workflow에 적용됐기 때문입니다.

흥미로운 점은 950 Agent를 돌렸다고 결과 후보가 950개가 되는 것이 아니라 **대부분을 제거하는 것이 Agent의 주요 역할**이었다는 것입니다. 대규모 Agent system에서 중요한 것은 candidate 생성보다 **failure/rejection funnel을 얼마나 잘 설계하는가**라는 또 하나의 사례입니다.

## 7. AWS + OpenCode — Open-weight Coding Agent가 `로컬 UX + Managed Inference + Multi-Model Routing` 구조로 간다 ★★★★☆

AWS가 9월 23일 **OpenCode + Amazon Bedrock open-weight model** 기반 coding-agent architecture를 공개했습니다. OpenCode는 로컬 terminal에서 filesystem과 shell, LSP diagnostic을 처리하고 inference만 Bedrock으로 보냅니다. 예제로 Kimi K3, GPT-OSS 120B, NVIDIA Nemotron 3 Super 120B를 사용합니다. :chatgpt-content-reference{index="32"}

이 architecture에서 중요한 것은 “open weight를 쓴다”보다 **Agent UI와 inference infrastructure를 분리**한 것입니다.

`Local OpenCode`
→ source/tool execution

`Bedrock`
→ managed model inference

`IAM / CloudTrail / PrivateLink`
→ identity·audit·network control

형태입니다. 사용자는 한 coding Agent UI를 유지하면서 task마다 model을 변경할 수 있습니다. AWS는 reasoning-heavy task, interactive code generation, large-context task 등을 다른 model tier로 routing하는 multi-model 구조도 제안합니다. :chatgpt-content-reference{index="33"}

Enterprise에서는 이 방식이 self-hosted GPU와 proprietary SaaS 사이의 중간 지점이 됩니다. 로컬 repository와 tool execution은 개발자 환경에 두면서도 inference model 선택·region·audit은 중앙에서 통제할 수 있습니다.

다만 여기서 **“open weight”와 “self-hosted”를 혼동하면 안 됩니다.** Bedrock에 올라간 open-weight 모델을 사용하는 것이므로 weight가 공개돼 있다는 것과 사용자가 inference infrastructure를 직접 통제한다는 것은 다른 의미입니다.

또 1M context가 있다고 repository 전체를 항상 prompt에 넣는 것이 최적이라는 뜻도 아닙니다. Context가 길수록 cache, TTFT, retrieval precision이 중요해지므로 large-context와 code indexing/RAG를 실제 task에서 비교해야 합니다.

원문: [공식 기술 가이드 · Use open weight models as your AI coding agent with Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/use-open-weight-models-as-your-ai-coding-agent-with-amazon-bedrock/)

# 오늘 직접 해볼 만한 실습 — `CAIRN식 Metadata Triage → 기존 Static Analyzer` 2단계 분석

오늘은 현재 악성코드 분석 시스템에 **CAIRN의 metadata-first 관점만 작게 가져와 보는 것**이 가장 가치 있습니다.

실행 파일을 바로 LLM에 넣거나 deep analysis부터 하지 말고 먼저 파일마다 다음과 같은 metadata feature를 추출합니다.

```text
AI_PROVIDER
  openai / anthropic / gemini / deepseek / mistral

AI_RUNTIME
  ollama / llama.cpp / vllm / transformers / litellm

AGENT_ARTIFACT
  tool_call / function_call / prompt template / JSON decision schema

AI_EVASION_TEXT
  AI 분석기·LLM에게 특정 판단을 유도하는 문자열

OFFENSIVE_BEHAVIOR
  credential access / process injection / persistence / shell execution
```

그다음 기존 pipeline을 두 조건으로 비교하면 됩니다.

```text
A. 기존 Static Analyzer → LLM
B. Metadata Triage → Static Analyzer → LLM
```

B에서는 metadata를 최종 verdict로 사용하지 말고 **분석 우선순위를 정하는 signal**로만 사용하십시오. `AI provider 문자열이 존재한다 → 악성`으로 판단하면 false positive가 폭발합니다. Cisco도 PyInstaller·Go·Tauri artifact 때문에 T1/T2 단계에서 noise가 많다고 명시합니다. :chatgpt-content-reference{index="38"}

평가에서는 `precision/recall`, `false-positive rate`, `deep-analysis 호출 수`, `sample당 분석 시간`, `LLM token`, 그리고 **metadata 단계에서 새로 발견했지만 기존 analyzer가 놓친 sample 수**를 기록하면 좋습니다.

이렇게 하면 기존의 **“정적분석 결과 → LLM 보고서”**에서 한 단계 확장해,

**`AI-native malware metadata → deterministic static evidence → LLM reasoning → report`**

라는 상당히 최신 연구 구조를 직접 실험할 수 있습니다. 특히 CAIRN은 코드와 taxonomy까지 공개되어 있어 비교 기준을 만들기 좋습니다. :chatgpt-content-reference{index="39"}
