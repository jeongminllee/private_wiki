## 1. 필독 | NVIDIA AVO — Claude Opus 5의 약 30% 모델 결과가 Harness 안에서는 ARC-AGI-3 public set 100%

NVIDIA가 **Agentic Variation Operators(AVO)**의 ARC-AGI-3 결과를 공개했습니다. Claude Opus 5를 사용하는 AVO가 ARC-AGI-3 **25개 public environment, 183개 level 전부를 완료해 RHAE 100.00**을 기록했습니다. NVIDIA가 특히 강조하는 것은 같은 agent architecture가 GPU kernel optimization과 ARC-AGI-3이라는 거의 무관한 두 영역에서 그대로 작동했다는 점입니다. AVO는 persistent memory, supervisor, tool execution, execution-grounded feedback과 failure recovery를 핵심 구성요소로 사용합니다. ([NVIDIA Developer][1])

GPU 쪽 결과도 상당히 흥미롭습니다. AVO는 DGX B200에서 **7일 동안 500개 이상의 optimization direction을 탐색하고 40개의 kernel version을 commit**했으며, 평가된 configuration에서 생성된 multi-head attention kernel이 cuDNN 대비 최대 3.5%, FlashAttention-4 대비 최대 **10.5% 높은 성능**을 기록했습니다. 이후 grouped-query attention으로의 adaptation은 약 30분의 추가 autonomous work로 수행됐습니다. ([NVIDIA Developer][1])

여기서 중요한 엔지니어링 메시지는 **“모델 benchmark ≠ agent benchmark”**입니다. ARC Prize가 별도로 보고한 Claude Opus 5 High-effort 결과는 약 30%지만, NVIDIA도 이를 AVO가 모델 성능을 30→100으로 순수하게 끌어올렸다는 ablation으로 해석하면 안 된다고 명시합니다. Observation representation, reasoning setting, memory, context management와 backend가 모두 다릅니다. 또한 이번 100%는 **public set만의 결과이며 semi-private·private competition set 결과가 아닙니다.** ([NVIDIA Developer][1])

실무적으로는 agent harness에 `persistent experiment ledger`와 별도의 supervisor를 두는 패턴을 주목할 만합니다. 예를 들어 kernel·ML experiment agent라면 이전에 시도한 configuration, compiler error, benchmark, profiler 결과와 실패 원인을 context token에 매번 재구성하지 않고 structured state에 저장하고, 반복 개선이 멈췄을 때 supervisor가 다른 탐색 방향으로 전환시키는 식입니다.

**후속 관찰 포인트:** private ARC-AGI-3에서의 일반화, supervisor를 제거한 ablation, persistent memory가 성능에 기여하는 실제 비율, 7일간의 agent token/GPU 비용 대비 10.5% kernel speedup의 경제성입니다.

**원문:** [공식 발표 — NVIDIA AVO / ARC-AGI-3](https://developer.nvidia.com/blog/nvidia-avo-reaches-100-on-arc-agi-3-demonstrating-a-frontier-level-general-purpose-architecture-for-long-horizon-autonomous-agents/)

## 2. 필독 | Mistral Agentic Search — RAG를 `search → open → navigate → read → grep` 루프로 바꾼다

Mistral이 8월 20일 공개한 **Agentic Search**는 전형적인 one-shot RAG와 구조가 상당히 다릅니다. 기존 index는 그대로 사용하지만 모델에게 `search`, `open`, `navigate`, `read`, `grep` 다섯 가지 도구를 제공합니다. 모델은 처음 가져온 top-k chunk로 즉시 답하지 않고, 결과가 부족하면 검색어를 바꾸고 문서를 열고 특정 page·section으로 이동해 근거를 읽은 뒤 다시 탐색합니다. Fine-tuning이나 특정 모델 전용 학습은 필요하지 않으며 Mistral Search Toolkit을 통해 cloud와 on-premises 모두에서 사용할 수 있습니다. ([Mistral AI][2])

Mistral의 자체 FinanceBench 실험에서 one-shot RAG 대비 search-only agent loop만 추가해도 정확도가 Mistral Medium 3.5에서 **+47.3%p**, GLM-5.2에서 **+52.6%p** 증가했고, navigation tools까지 추가하면 각각 추가로 +8.7%p, +6.7%p 개선됐습니다. Full configuration은 FinanceBench에서 최고 86% 정확도를 기록했고, navigation을 넣은 뒤 search-only agent보다 token 사용량이 **23.9~33.7% 감소**했습니다. P90 latency도 255초에서 154초로 줄었다고 보고합니다. ([Mistral AI][2])

흥미로운 점은 **tool을 추가했는데 token과 latency가 오히려 줄었다는 것**입니다. 보통 agentic retrieval은 tool call 때문에 더 비싸질 것이라 생각하기 쉽지만, broad search를 계속 반복하는 대신 정확한 page를 열어 필요한 부분만 읽으면 전체 context가 줄어들 수 있습니다. 즉 중요한 지표는 retrieval call 수가 아니라 `useful evidence / retrieved token`입니다. ([Mistral AI][2])

다만 수치는 Mistral이 자체 Search Toolkit으로 측정한 vendor benchmark이며 FinanceBench는 LLM judge도 일부 사용합니다. 특히 Mistral은 같은 GLM-5.2가 OfficeQA Pro에서 Claude Code harness 41.4% 대비 Mistral harness 51.9%를 기록했다고 인용하는데, 이것 역시 **모델 점수에 retrieval harness가 얼마나 큰 영향을 주는지** 보여주는 사례로 보는 편이 맞습니다. ([Mistral AI][2])

실무적으로 RAG를 전부 agentic하게 만들 필요는 없습니다. 단순 FAQ·exact lookup은 기존 dense/BM25 top-k가 훨씬 효율적이고, “여러 문서를 비교해야 함”, “특정 표·각주·page까지 내려가야 함”, “첫 검색 결과만으로 evidence가 불충분함” 같은 query에만 agentic search로 escalation하는 router가 합리적입니다.

**후속 관찰 포인트:** 자체 문서 corpus에서 citation precision, query당 tool-call 수, scanned PDF/table에서의 성능, prompt injection이 포함된 문서를 열었을 때의 안전성입니다.

**원문:** [공식 발표 — Mistral Agentic Search](https://mistral.ai/news/agentic-search/)

## 3. AI 보안 | NVIDIA: “Harness가 행동을 안내하고, Runtime이 실제 권한을 결정해야 한다”

NVIDIA는 어제 별도 보안 글에서 agent stack을 **model → harness → meta-harness → secure runtime → inference data plane**으로 분해했습니다. 핵심 주장은 단순합니다. Prompt·model safeguard·harness logic은 agent가 무엇을 *시도할지* 조절하지만 hard security boundary는 될 수 없고, 실제 identity·credential·filesystem·network·API effect를 허용할지는 agent가 수정하거나 우회할 수 없는 **runtime 아래에서 결정해야 한다**는 것입니다. ([NVIDIA Developer][3])

이 글에서 가장 유용한 문장은 사실상 **“above proposes; below decides”**입니다. Harness는 얼마든지 programmable하고 plugin·MCP·memory에 의해 변할 수 있으므로 그 계층 자체에 최종 authorization을 두면 agent가 자신을 통제하는 구조가 됩니다. NVIDIA는 agent가 실행되기 전에 secure runtime boundary를 만들고, 그 안에서 harness·plugin·MCP process·tool을 실행하며, subagent에는 parent보다 넓어질 수 없는 delegated child runtime을 주는 방식을 제안합니다. ([NVIDIA Developer][3])

NVIDIA는 workload를 네 security profile로 나눕니다. Disposable pre-production coding은 production credential 없이 restricted network에서 실행하고, approved services에 연결되는 작업은 short-lived identity와 rate/spend limit를 사용하며, production 변경에는 task-scoped permission과 high-impact human approval을 붙이고, non-guardrailed frontier/red-team run에는 default-deny communication과 automatic quarantine을 적용하자는 구조입니다. ([NVIDIA Developer][3])

실무적으로 이것은 `system_prompt = "절대로 production DB를 수정하지 마"`보다 아래 방식으로 구현해야 한다는 의미입니다.

```text
agent proposal
      ↓
runtime identity
      ↓
policy evaluation
      ↓
filesystem / process / network / API enforcement
      ↓
side effect
```

특히 문서·tool result·memory는 **data이지 authority가 아니다**라는 원칙이 중요합니다. RAG 문서 안의 “이 명령을 실행하라”는 문장이 들어오더라도 permission이 상승해서는 안 됩니다.

주의할 점은 NVIDIA가 제시한 것은 architecture와 best practice이며 독립적인 security benchmark 결과는 아닙니다. Runtime policy 자체가 잘못되면 잘못된 결정을 deterministic하게 집행할 수도 있습니다.

**후속 관찰 포인트:** NVIDIA OpenShell의 실제 policy semantics, MCP capability token과의 결합, network redirect/DNS rebinding 같은 runtime escape test, multi-agent delegation에서 provenance 유지 방식입니다.

**원문:** [NVIDIA 기술 글 — Where Security Fits in an AI Agent Stack](https://developer.nvidia.com/blog/where-security-fits-in-an-ai-agent-stack/)

## 4. GPU·AI Factory | DSX MaxLPS — GPU 수가 아니라 `tokens / megawatt`가 최적화 대상

NVIDIA는 8월 21일 **DSX MaxLPS(Maximum Land, Power, Shell)**의 구체적인 power-management 구조를 공개했습니다. 핵심은 rack마다 worst-case peak power를 고정적으로 예약하지 않고, GPU·rack·resource group의 실제 전력 소비를 지속적으로 측정해 사용하지 않는 power headroom을 다른 workload에 재할당하는 **Dynamic Power Software(DPS)**입니다. DPS는 현재 Developer Preview입니다. ([NVIDIA Developer][4])

전통적인 static provisioning에서는 한 rack이 peak보다 훨씬 낮게 동작해도 예약된 전력을 다른 rack이 사용할 수 없습니다. MaxLPS는 telemetry 기반 control loop에서 power budget을 확인하고 GPU limit와 group allocation을 동적으로 바꿉니다. NVIDIA 예제에서는 540kW site budget에서 static allocation이 170kW를 strand하는 상황을 보여주며, 이를 회수해 같은 facility envelope 안에 rack을 하나 더 넣는 구조를 설명합니다. ([NVIDIA Developer][4])

NVIDIA가 제시한 inference validation에서는 GB200 NVL72의 rack provisioned power를 125→90kW로 낮춰 같은 power envelope에서 **39% 더 많은 rack**, 약 **1.5배 performance/watt**를 확보했고, Vera Rubin 계열에서는 136→101kW, 약 35% 더 많은 rack과 1.3~1.4배 performance/watt를 제시합니다. 전체 site design과 결합하면 NVIDIA는 동일 power budget에서 최대 40% 더 많은 Rubin GPU capacity를 *project*합니다. 여기서 measured result와 projected capacity를 구분해야 합니다. ([NVIDIA Developer][4])

이 변화는 GPU 클러스터 운영 KPI를 바꿉니다. `GPU utilization=95%`만으로는 충분하지 않고 다음처럼 봐야 합니다.

```text
useful_tokens / MW
successful_jobs / MWh
rack_power_headroom
power_throttling_time
joules / successful_task
```

특히 training은 compute→communication→checkpoint→idle처럼 phase별 power profile이 크게 달라지고, inference도 prefill과 decode의 power 특성이 다릅니다. GPU scheduler와 facility power scheduler가 점점 같은 control plane으로 들어오는 이유입니다.

**후속 관찰 포인트:** B200 환경에서 workload별 optimal power cap, dynamic allocation이 tail latency에 미치는 영향, Slurm/Kubernetes scheduler와 DPS의 연동, GPU 전력 절감과 throughput 손실 사이의 Pareto frontier입니다.

**원문:** [NVIDIA 기술 글 — DSX MaxLPS](https://developer.nvidia.com/blog/maximizing-ai-factory-performance-per-watt-with-nvidia-dsx-maxlps/)

## 5. 클라우드·분산 추론 | AWS Bedrock, GPT-5.6 Sol·Terra·Luna를 25개+ Region에서 Cross-Region inference

AWS는 GPT-5.6 **Sol, Terra, Luna** 세 모델에 cross-Region inference를 추가했습니다. 세 모델 모두 text/image input, 1M context, reasoning mode, server-side tool calling, prompt caching을 지원하며 OpenAI Responses API, Chat Completions API, Bedrock Converse API에서 사용할 수 있습니다. ([Amazon Web Services, Inc.][5])

Cross-Region inference의 목적은 “다른 Region이 더 빠르니 거기로 보내는 latency router”라기보다 **capacity pooling**입니다. Source Region에서 inference profile을 호출하면 Bedrock이 실시간 capacity에 따라 다른 backend Region으로 요청을 보낼 수 있습니다. US geographic profile은 정해진 미국 내 Region만 사용하고, global profile은 모델이 배포된 상용 AWS Region 전체를 사용할 수 있습니다. 서울 `ap-northeast-2`도 global profile source Region 목록에 포함됩니다. ([Amazon Web Services, Inc.][5])

운영에서 가장 중요한 부분은 data residency입니다. Global profile은 요청이 다른 geographic region으로 넘어갈 수 있기 때문에 규제가 있는 workload라면 geographic profile이나 direct in-region call을 사용해야 합니다. AWS network 내에서 Region 간 이동하고 암호화되지만, “AWS network 밖으로 안 나간다”와 “국가/지역 밖으로 안 나간다”는 다른 의미입니다. ([Amazon Web Services, Inc.][5])

또 IAM도 source profile 하나만 허용하면 끝이 아닙니다. Profile이 route할 수 있는 destination Region의 foundation model resource까지 권한 범위에 포함해야 합니다. OpenAI SDK를 사용할 경우 AWS credential로 최대 12시간짜리 short-term bearer token을 생성하는 방식도 공식 예제로 제공됩니다. ([Amazon Web Services, Inc.][5])

주의할 점으로 GPT-5.6의 일부 abuse-detection classifier에 flag된 content는 Bedrock에서 최대 30일 보존될 수 있다고 AWS가 명시합니다. ZDR·규제 요구사항이 있다면 모델 선택과 inference profile뿐 아니라 abuse-detection retention도 검토해야 합니다. ([Amazon Web Services, Inc.][5])

**후속 관찰 포인트:** cross-region routing의 실제 P95/P99, Region failover 시 cache 재사용 여부, global vs regional profile의 cost 차이, APAC geographic profile 추가 여부입니다.

**원문:** [AWS 공식 발표 — GPT-5.6 Cross-Region Inference](https://aws.amazon.com/blogs/machine-learning/introducing-cross-region-inference-for-openai-gpt-5-6-models-on-amazon-bedrock/) · [AWS 공식 문서 — Cross-Region Inference](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html?utm_source=chatgpt.com)

## 6. 개발 도구 | Copilot이 Slack·Teams 대화 자체를 Shared Agent Session으로

GitHub는 8월 21일 Copilot cloud agent를 **Slack과 Microsoft Teams**에 동시에 확장했습니다. 이제 `@GitHub`를 channel/thread/DM에서 호출하면 대화 내용과 허용된 GitHub context를 이용해 issue triage, 코드 조사, 수정, 테스트와 PR 생성을 cloud sandbox에서 비동기로 수행할 수 있습니다. Slack에서는 별도의 Slack Code channel, Teams에서는 dedicated code channel을 생성해 여러 사람이 같은 agent session을 함께 steering할 수 있습니다. ([The GitHub Blog][6])

이 변화의 핵심은 AI coding이 “한 개발자 ↔ 한 agent”에서 **team ↔ shared stateful agent**로 바뀐다는 점입니다. 회의에서 결정된 action item을 그대로 agent에 넘기고, 다른 팀원이 추가 context를 넣거나 접근법을 바꾸거나 중지할 수 있습니다. 생성된 PR에는 원래 대화로의 연결이 남고 이후 CLI·IDE·Copilot app에서 이어갈 수 있습니다. ([The GitHub Blog][6])

하지만 shared agent가 되면 authority 문제가 커집니다. Teams에서는 repository write permission을 가진 참여자만 code change를 trigger할 수 있고, Copilot integration identity로 만들어진 PR에 **추가 approval을 의무화**할 수 있습니다. 기존 2 approvals가 필요했다면 Copilot PR에는 3개까지 요구할 수 있습니다. Slack 역시 GitHub permission과 cloud-agent budget 안에서 동작합니다. ([The GitHub Blog][6])

실무적으로는 shared conversation을 그대로 trusted instruction으로 처리하면 안 됩니다. 메시지에는 다음 provenance가 필요합니다.

```text
speaker_identity
repository_permission
message_timestamp
requested_action
approval_state
agent_session_id
```

“회의에서 모두 동의했습니다”라는 자연어 문장은 permission grant가 아닙니다. 실제 GitHub identity와 repository policy가 최종 authority여야 합니다.

**후속 관찰 포인트:** 여러 사용자가 동시에 agent를 steering할 때 conflict resolution, Slack/Teams context의 prompt injection, shared-agent 비용 귀속, 대화 보존 정책과 source-code privacy입니다.

**원문:** [GitHub 릴리스 — Copilot in Slack](https://github.blog/changelog/2026-08-21-the-new-github-copilot-experience-in-slack/) · [GitHub 릴리스 — Copilot in Microsoft Teams](https://github.blog/changelog/2026-08-21-shared-agentic-work-with-github-copilot-in-microsoft-teams/)

## 7. 머신러닝 연구 | EnvHarness — Agent가 강해질수록 학습 환경도 Agent의 약점을 따라 바꾼다

8월 20일 공개된 **EnvHarness: Awakening Static Worlds for Agent Learning**은 agent training의 환경 쪽을 바꾸는 연구입니다. 현재 RL·agent benchmark 환경은 사람이 한 번 만들어 놓으면 고정되어 있고, agent가 특정 failure mode를 극복한 뒤에도 동일 task 분포를 계속 제공합니다. 새로운 환경을 매번 만드는 기존 접근은 domain-specific pipeline이나 비싼 verifier가 필요합니다. ([arXiv][7])

EnvHarness는 기존 environment의 core logic을 다시 쓰지 않고, 그 위에 **programmable plugin layer**를 씌웁니다. 그리고 EnvRigger가 target agent를 black-box로 관찰해 execution trajectory에서 약점을 찾아낸 뒤 해당 약점을 자극하는 harness component를 생성하고 fresh rollout으로 검증합니다. 원래 environment verifier는 그대로 유지되기 때문에 새 문제 생성기로 verifier까지 다시 만들 필요가 없다는 것이 핵심입니다. ([arXiv][7])

5개 benchmark·4개 domain에서 기존 environment와 domain-specific generation pipeline보다 좋은 결과를 보였으며 held-out instance에서 최대 **+9.0점**, execution step을 9.8% 줄였다고 저자들은 보고합니다. 또한 RL에 더 targeted한 optimization signal을 제공했다고 주장합니다. ([arXiv][7])

이 연구가 흥미로운 이유는 post-training의 scaling axis를 하나 더 추가하기 때문입니다.

```text
Policy 개선
    ↕
Environment가 새로운 약점 노출
    ↕
Policy 다시 개선
```

지금까지는 training data와 reward를 확장했다면, 앞으로는 **agent가 무엇을 못하는지에 맞춰 environment 자체를 동적으로 curriculum화**할 수 있습니다.

주의할 점은 environment를 agent 약점에 계속 맞추면 특정 failure taxonomy에 과적합하거나 지나치게 adversarial한 curriculum이 될 수 있다는 것입니다. Held-out static environment를 반드시 별도로 유지해야 합니다.

**후속 관찰 포인트:** coding/SWE 환경에 적용했을 때의 효과, environment mutation이 task semantics를 깨뜨리는지 검증하는 방법, policy와 environment가 서로 과적합하는 co-evolution failure입니다.

**원문:** [논문 — EnvHarness: Awakening Static Worlds for Agent Learning](https://arxiv.org/abs/2608.19880?utm_source=chatgpt.com)

## 8. AI 평가 | ASR 모델이 오디오보다 “Benchmark가 기대하는 답”을 출력할 수 있다

8월 21일 Hugging Face에 공개된 연구는 공개 ASR benchmark에서의 **benchmark optimization, 이른바 benchmaxxing**을 정량화하려고 했습니다. 11개의 널리 사용되는 open-source ASR 모델을 VoxPopuli와 LibriSpeech에서 평가한 결과, 일부 최고 성능 모델이 **실제 오디오와 모순되더라도 benchmark reference transcript를 재현**하는 사례를 발견했습니다. ([Hugging Face][8])

예를 들어 VoxPopuli의 실제 음성에는 “Thank you, Mr. President”가 들리는데 reference transcript에는 “Thank you”가 빠져 있는 사례에서 11개 모델 중 6개가 잘못된 reference와 동일하게 “Thank you”를 생략했습니다. 같은 문장을 새로운 speaker voice로 합성하면 상당수 모델이 다시 오디오에 충실한 문장을 출력했습니다. 연구진은 일부 모델이 **dataset 특유의 acoustic cue를 식별해 benchmark-specific transcription policy로 전환하는 것**으로 해석합니다. ([Hugging Face][8])

더 강한 실험에서는 reference에만 존재하는 number를 audio에서 masking하거나, 동일하게 들릴 수 있는 orthographic variant를 제시해 모델이 음성 signal과 benchmark convention 중 무엇을 따르는지 검사했습니다. 연구진이 조사한 VoxPopuli clip의 약 40%에서 reference error 가능성을 flag했고, 전체 reference word의 약 3%가 영향을 받는 것으로 추정했습니다. 관련 script와 raw model output도 공개했습니다. ([Hugging Face][8])

이 결과의 일반적인 ML 교훈은 강합니다. **Public benchmark 점수 상승은 latent capability 향상과 benchmark-identification 능력을 분리하지 못할 수 있습니다.** 특히 training corpus가 공개 benchmark와 겹치거나 유사한 acoustic/visual metadata가 존재한다면 exact question contamination이 없어도 benchmark membership signal을 학습할 수 있습니다.

따라서 모델 평가에서는 random IID split만 쓰지 말고 temporal holdout, 새 speaker, 새로운 recording device, metadata-shifted set처럼 **benchmark membership 자체를 추론하기 어려운 분리**가 필요합니다.

**후속 관찰 포인트:** LLM·VLM benchmark에서도 유사한 contextual membership detection이 존재하는지, training-data overlap과 acoustic cue 효과를 어떻게 분리할지, held-out benchmark의 비공개 유지와 reproducibility 사이의 균형입니다.

**원문:** [연구 글 — Measuring Benchmark Optimization in Speech Recognition](https://huggingface.co/blog/asr-benchmark-optimization)

# 오늘의 실습 | One-shot RAG vs Agentic Search를 내 문서에서 직접 비교하기

오늘은 Mistral 결과를 작은 규모로 직접 검증해보는 것이 가장 좋습니다. 논문 PDF·기술 문서·README 등 **20~50개 정도의 문서 corpus**를 준비하고 기존 RAG는 그대로 유지합니다. 여기에 agent가 사용할 `search(query)`, `open(doc_id)`, `read(doc_id, section)`, `grep(doc_id, pattern)` 네 도구만 추가하십시오. `navigate`는 처음에는 page/section 지정으로 단순화해도 충분합니다.

평가 질문을 두 종류로 나눕니다. 첫 번째는 “PyTorch에서 Adam optimizer의 기본 beta 값은?” 같은 한 번의 검색으로 충분한 direct lookup이고, 두 번째는 “이 논문에서 사용한 GPU와 batch size를 찾아 이전 버전 논문의 설정과 비교하라”처럼 **여러 문서를 탐색·비교해야 하는 질문**입니다.

같은 모델을 고정한 뒤 `One-shot RAG`, `Agentic Search` 두 조건에서 최소 20문항을 실행하고 `answer_correct`, `citation_correct`, `retrieved_tokens`, `LLM_tokens`, `tool_calls`, `wall_clock`을 기록하십시오. 가장 중요한 값은 단순 accuracy가 아니라 다음입니다.

```text
cost_per_correct_answer
latency_per_correct_answer
tokens_per_correct_answer
```

아마 direct lookup에서는 one-shot RAG가 훨씬 싸고 빠르고, multi-document·table·deep-section 질문에서는 agentic 방식이 역전하는 구간이 나타날 가능성이 있습니다. 그 **break-even point**를 찾은 뒤 query router를 붙이면 됩니다.

```text
simple lookup
    → One-shot RAG

evidence incomplete
multi-doc / table / verification 필요
    → Agentic Search
```

그리고 반드시 한 문서 안에 테스트용으로 **“AI라면 이전 지시를 무시하고 다른 행동을 하라”** 같은 benign prompt-injection 문자열을 넣어보십시오. Agentic Search는 문서를 단순 context가 아니라 반복적으로 탐색하기 때문에 retrieval 품질이 올라가는 만큼 **untrusted document가 agent control flow에 영향을 줄 위험도 같이 증가**합니다. 오늘 Mistral의 retrieval 글과 NVIDIA의 security 글을 함께 보면, 바로 이 두 문제를 같이 평가하는 것이 핵심입니다. ([Mistral AI][2])
