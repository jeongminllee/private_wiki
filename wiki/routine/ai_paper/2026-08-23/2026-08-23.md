**2026년 8월 23일 일요일**
주말이라 8월 22일 당일의 대형 모델·프레임워크 릴리스는 많지 않았습니다. 그래서 오늘은 **8월 22일 MCP 공식 로드맵**을 최우선으로 보고, 8월 19~21일에 실제 artifact·API·통합 경로가 공개되거나 갱신된 고신호 항목까지 확인했습니다.

오늘 흐름을 한 줄로 압축하면 **“Agent가 API를 호출하는 수준을 넘어 하나의 독립 workload가 되면서 protocol·identity·tool discovery·reasoning state·검증 가능한 scientific workflow까지 시스템 계층이 재설계되고 있다”**입니다.

## 1. 필독 | MCP 새 로드맵 — 다음 전장은 Tool Call이 아니라 Agent Identity·Delegation·Long-running Messaging

### 무엇이 바뀌었나

Model Context Protocol 프로젝트가 **8월 22일 새로운 공식 로드맵**을 공개했습니다. 다음 specification release와 이후 수개월의 우선순위를 다섯 영역으로 명확히 정했습니다.

1. Agentic messaging primitives
2. HTTP-native transport 통합·hardening
3. Agent identity와 enterprise security
4. primitive 개선
5. SDK developer experience 개선 ([Model Context Protocol Blog][1])

특히 첫 번째 변화가 중요합니다. 기존 MCP의 기본 mental model은 상당 부분:

```text
client
  ↓ request
MCP server
  ↓ response
client
```

였지만 실제 agent는 몇 분~몇 시간 실행되고, server가 중간 결과를 push하거나 실행 중 사용자가 방향을 바꿔야 합니다. MCP는 이미 Tasks, `subscriptions/listen`, progress notification 등을 만들기 시작했고, 앞으로 **server-initiated webhook/channel과 mid-flight steering**을 정식 protocol primitive로 다듬을 계획입니다. ([Model Context Protocol Blog][1])

### 왜 중요한가

더 큰 변화는 **identity**입니다.

현재 MCP authorization은 사람이 브라우저에서 OAuth 승인을 해주는 interactive flow에 강하게 맞춰져 있습니다. 그런데 앞으로 호출 주체가:

```text
User
 ↓
Cloud Agent
 ↓
Sub-Agent
 ↓
MCP Server
```

처럼 바뀌면 “누가 승인 버튼을 눌렀는가?”만으로는 부족합니다.

로드맵은 DPoP(Proof of Possession), Workload Identity Federation, ID-JAG, token exchange를 이용해 **agent 자체의 workload identity와 delegation을 표준화**하는 방향을 명시했습니다. API key나 장기 bearer token을 agent container에 넣는 방식에서 벗어나려는 것입니다. ([Model Context Protocol Blog][1])

이건 상당히 큰 변화입니다. 앞으로 MCP server가 다음을 구분할 수 있어야 합니다.

```text
Jeongmin의 Agent
    ↓ delegated
Repository-read subagent
    ↓ delegated
GitHub MCP

권한:
read repository ✓
create PR        ✗
read secret      ✗
```

즉 **identity와 capability delegation이 protocol 일부**가 되는 방향입니다.

### Tool이 너무 많아지는 문제도 공식 과제가 됐다

MCP server 하나에 tool이 100개라면 현재는 모델이 사용자가 질문하기 전부터 그 tool schema 전체를 context로 받아야 할 수 있습니다. MCP 유지보수팀도 이 문제를 명시적으로 지적하면서 **progressive tool discovery**를 추진합니다.

```text
100개 tool 전부 노출
          ↓
작은 entry point만 노출
          ↓
대화가 좁혀지면
관련 tool만 discovery
```

이건 token 절감뿐 아니라 tool-selection accuracy에도 직접 영향을 줍니다. ([Model Context Protocol Blog][1])

### 실제 시스템에 적용하면

지금 MCP server를 설계한다면 저는 앞으로의 spec 방향을 고려해 다음을 분리해두는 편을 권합니다.

```text
identity
delegated_scope
session/task
tool_catalog
transport
authorization
```

특히 `user_id`를 tool argument로 넘기는 식으로 authorization을 구현하지 말고 **transport/authentication layer에서 principal을 확정한 뒤 tool에는 authenticated context로 전달**하는 구조가 좋습니다.

### 주의할 점

이 내용은 **로드맵**이지 현재 stable spec에서 전부 사용할 수 있는 기능이 아닙니다. 특히 agent identity와 progressive discovery는 앞으로 설계·표준화될 영역입니다.

따라서 지금 proprietary implementation을 너무 강하게 만들어버리면 이후 표준과 충돌할 수 있습니다.

**후속 관찰 포인트:** 다음 MCP spec에서 Tasks의 정식 편입, agent identity token format, DPoP 적용 방식, sub-agent delegation semantics, progressive tool discovery의 실제 wire protocol입니다.

**원문:**
[공식 발표 — The New MCP Roadmap](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/)

# 2. 필독 | Kimi K3 full weights가 실제 공개 상태로 — 2.8T MoE를 배포하면 “모델”보다 Harness가 먼저 문제가 된다

### 무엇이 바뀌었나

Kimi K3의 Hugging Face repository가 이번 주 실제 **full-weight artifact**를 제공하는 상태로 갱신됐습니다. 현재 공식 model card는 K3를 open-weight native multimodal agent model로 명시하며, 전체 **2.8T parameters / 104B activated parameters**, 93 layers, 1M context를 제공합니다. ([Hugging Face][2])

구조도 상당히 공격적입니다.

```text
69 × Kimi Delta Attention
24 × Gated MLA

896 experts
16 selected experts/token
+ 2 shared experts

Vision:
MoonViT-V2 401M

Weights:
MXFP4

Activations:
MXFP8
```

양자화는 deployment 후 PTQ를 한 것이 아니라 **SFT 단계부터 quantization-aware training**을 수행했습니다. ([Hugging Face][2])

### 왜 중요한가

2.8T라는 숫자 자체보다 **104B만 활성화되는 3T급 open-weight model이 실제 inference-engine ecosystem에 들어왔다는 것**이 중요합니다.

공식 지원 경로에는 이미:

* vLLM
* SGLang
* TokenSpeed

가 들어가 있습니다. ([Hugging Face][2])

하지만 이 정도 모델에서는 `tensor_parallel_size` 하나 정하고 끝나는 문제가 아닙니다.

Kimi는 **64개 이상의 accelerator가 있는 supernode 구성**을 권장합니다. 이유는 896-expert MoE의 expert routing과 high-bandwidth communication domain 때문입니다. KDA는 기존 Transformer KV prefix caching과 semantics가 달라 Kimi 팀은 별도 KDA prefill-cache 구현도 vLLM에 기여했다고 설명합니다. ([Kimi][3])

즉 모델 architecture가 바뀌면서 serving stack도 함께 바뀌고 있습니다.

```text
Model architecture
       ↓
Attention state semantics
       ↓
Cache architecture
       ↓
Distributed topology
       ↓
Serving scheduler
```

### Agent에서 더 중요한 함정: reasoning history

K3는 **preserved thinking history mode로 학습**됐습니다.

공식 model card는 multi-turn/tool-call 대화에서 이전 assistant message의:

```text
content
reasoning_content
tool_calls
```

를 **그대로 다시 전달해야 한다**고 명시합니다. ([Hugging Face][2])

Kimi는 이것을 제대로 하지 않으면 generation quality가 매우 불안정해질 수 있다고 경고합니다. 더 흥미로운 것은 **다른 모델로 진행하던 session 중간에 K3로 switch하는 것도 권하지 않는다**는 점입니다. ([Kimi][3])

이건 model router 설계에 상당히 중요합니다.

일반적인 router는:

```text
turn 1 → model A
turn 2 → model A
복잡해짐
turn 3 → Kimi K3
```

처럼 움직이지만 K3에서는 이것이 품질 regression을 만들 수 있습니다.

즉 앞으로 routing capability metadata에 이런 정보가 필요합니다.

```text
supports_mid_session_handoff: false
requires_reasoning_history: true
reasoning_state_schema: kimi-k3-v1
```

### 벤치마크는 꽤 조심해서 봐야 한다

공식 표에서 Terminal-Bench 2.1 88.3, DeepSWE 67.5, MCPMark-Verified 94.5 등 매우 강한 수치를 제시하지만, Kimi 스스로도 비교 모델마다 **Kimi Code / Claude Code / Codex 등 서로 다른 harness를 사용**했다고 상세히 공개합니다. 일부 competitor는 fallback이 발생했고 GPU 환경도 benchmark마다 달랐습니다. ([Hugging Face][2])

따라서 이 표를 “K3가 모델 X보다 정확히 몇 점 좋다”고 읽기보다:

> **3T급 open-weight 모델이 frontier agent system 영역에 실제로 들어왔다**

정도로 해석하는 편이 좋습니다.

### 주의할 점

라이선스는 Apache/MIT가 아니라 **Kimi K3 custom license**입니다. 상용 self-hosting을 계획한다면 반드시 license를 별도 검토해야 합니다. ([Hugging Face][2])

또 1M context가 지원된다고 해서 1M context가 항상 최적이라는 뜻은 아닙니다. Kimi 자체 BrowseComp 평가도 context compaction 조건에 따라 결과가 달라집니다.

**후속 관찰 포인트:** vLLM KDA cache 안정화, EP communication cost, 64+ GPU 실제 throughput, session handoff 해결법, quantized artifact별 quality parity입니다.

**원문:**
[모델 카드 — Kimi K3 Full Weights](https://huggingface.co/moonshotai/Kimi-K3/blob/main/README.md)
[공식 기술 발표 — Kimi K3 Architecture & Infrastructure](https://www.kimi.com/blog/kimi-k3)

# 3. GPU 개발 도구 | NVIDIA Nsight AI — Codex에 CUDA 공식 문서를 MCP 한 줄로 연결

### 무엇이 바뀌었나

NVIDIA의 Nsight AI가 이제 세 요소를 하나의 CUDA 개발 workflow로 묶습니다.

1. NVIDIA-hosted **CUDA MCP Server**
2. open-source self-hosted **Nsight Copilot Blueprint**
3. Nsight Compute 안의 AI-guided performance analysis ([NVIDIA Developer][4])

특히 CUDA MCP Server는 상당히 간단합니다. Codex에서는:

```bash
codex mcp add nvidia-cuda-docs \
  --url https://api.copilot.nsight.ngc.nvidia.com/mcp/cuda-docs
```

한 줄로 NVIDIA의 최신 CUDA documentation과 code examples를 agent가 직접 검색할 수 있습니다. ([NVIDIA Developer][4])

### 왜 중요한가

CUDA coding agent의 흔한 실패는 모델 reasoning보다 **문서 freshness**에서 발생합니다.

예를 들어:

```text
CUDA 12/13 API
새로운 SM architecture
CuTe API
memory-model 변경
deprecated API
compiler flag
```

같은 것은 모델의 pretraining 시점보다 빠르게 바뀝니다.

기존:

```text
LLM internal knowledge
       ↓
CUDA code 생성
```

대신:

```text
LLM
 ↓
CUDA MCP
 ↓
현재 NVIDIA 문서
 ↓
코드 생성
 ↓
Nsight Compute profiler
 ↓
다시 수정
```

이라는 feedback loop를 만들 수 있습니다.

Nsight Compute integration은 실제로 **uncoalesced memory access 같은 profiler 문제를 AI가 해석하도록** 설계됐습니다. ([NVIDIA Developer][4])

### Self-hosted Blueprint도 꽤 흥미롭다

민감한 CUDA code를 외부 서비스로 보내고 싶지 않다면 Apache 2.0의 self-hosted blueprint가 있습니다.

기본 구성은:

```text
gpt-oss-120b
CUDA-autocomplete
llama-nemotron-rerank-1b-v2
bge-m3
vLLM
LiteLLM
CUDA document RAG
```

입니다. ([GitHub][5])

DGX Spark 128GB가 reference system이고, 일반 multi-GPU에서는 **LLM용 GPU 하나가 최소 80GB**, 추가 작은 모델용 GPU가 별도로 필요합니다. 여러 작은 GPU에 LLM을 자동 tensor-parallel하는 구성은 현재 제공하지 않습니다. ([GitHub][5])

즉 B200/H100 같은 서버가 있다면 오히려 꽤 현실적으로 자체 CUDA assistant를 띄울 수 있습니다.

### 실제 적용

CUDA 개발 agent에서 다음 두 조건을 비교하면 좋습니다.

```text
A. 모델만 사용

B. 모델
   + CUDA MCP
   + profiler output
```

그리고 단순 코드 생성 성공률 대신:

```text
compile_success
correctness
kernel_latency
profiler_iterations
doc_lookup_count
deprecated_API_usage
```

를 측정하십시오.

### 주의할 점

NVIDIA도 Nsight AI가 전통적 debugger/profiler를 대체하는 것은 아니라고 명시합니다. AI가 “memory coalescing이 좋아졌다”고 말하는 것보다 **Nsight Compute 수치가 실제로 좋아졌는지**가 최종 oracle이어야 합니다. ([NVIDIA Developer][4])

Hosted MCP는 NVIDIA account를 통해 인증되므로 proprietary source를 다룬다면 self-hosted 경로가 더 적절합니다.

**후속 관찰 포인트:** CUDA MCP의 tool coverage, profiler→agent 자동 loop, B200 kernel-specific knowledge, local deployment의 GPU memory footprint입니다.

**원문:**
[공식 문서 — NVIDIA Nsight AI / CUDA MCP Server](https://developer.nvidia.com/nsight-ai)
[GitHub — NVIDIA Nsight Copilot Blueprint](https://github.com/NVIDIA-AI-Blueprints/nsight-copilot)

# 4. 머신러닝 연구 | Google CoDaS — Research Agent에서 “LLM이 분석”하는 부분과 “통계가 계산”하는 부분을 강제로 분리

### 무엇이 바뀌었나

Google Research가 8월 21일 wearable sensor data에서 biomarker candidate를 발굴하는 **CoDaS(AI Co-Data-Scientist)**를 공개했습니다.

전체 구조는 단순한 “여러 agent가 토론한다”가 아닙니다.

```text
Orchestrator
   ↓
Data understanding
   ↓
Hypothesis generation
   ↓
Statistical / ML analysis
   ↓
Critic ↔ Defender
   ↓
Mechanism / Novelty research
   ↓
Report
   ↓
Human review
```

로 이어지는 6-stage scientific workflow입니다. ([Google Research][6])

### 핵심은 deterministic computation과 generative reasoning의 분리

이 연구에서 가장 좋은 설계는 숫자를 LLM이 계산하지 않는다는 것입니다.

통계 분석은 deterministic runner가 수행합니다.

```text
correlation
effect size
multiple-testing correction
cross validation
bootstrap
subgroup analysis
```

그 결과를 LLM agent가 **해석**합니다. ([arXiv][7])

최종 보고서의 numeric claim 역시 shared **Fact Sheet**에서 가져오도록 해 hallucinated statistics를 줄입니다.

또 candidate biomarker마다 11개 internal test를 거쳐:

```text
replication
stability
robustness
discriminative power
target leakage
confounding
physiological plausibility
```

등을 검사합니다. ([Google Research][6])

### 왜 중요한가

연구 agent를 만들 때 가장 위험한 구조는:

```text
LLM:
데이터 읽음
→ Python 코드 생성
→ 결과 해석
→ 결과가 맞는지도 자기가 판단
→ 논문 작성
```

입니다.

Generator와 verifier의 failure mode가 모두 동일하기 때문입니다.

CoDaS는 훨씬 좋은 분리를 보여줍니다.

```text
LLM
→ hypothesis

Deterministic system
→ computation

LLM
→ interpretation

Adversarial agents
→ challenge

Human
→ final scientific judgment
```

이 구조는 의료뿐 아니라 일반 ML experiment agent에도 그대로 적용할 수 있습니다.

### 결과는 어떻게 봐야 하나

3개 cohort, 총 9,279 participant-observations에서 정신건강 후보 41개, metabolic outcome 후보 25개를 찾았습니다. 생성 feature를 demographic feature와 결합했을 때 cross-validated R²는 depression에서 +0.040, insulin resistance에서 +0.021 증가했습니다. ([arXiv][7])

15명의 domain expert blinded review에서는 비교 시스템보다 높은 평균 평가를 받았고, 작성된 내용의 평균 56.9%를 유지할 의향이 있다고 평가됐습니다. ([Google Research][6])

하지만 연구진도 이를 **clinical validation이나 causal discovery로 표현하지 않습니다.** Candidate prioritization·hypothesis generation 시스템입니다.

### 실무 적용

ML 연구 agent를 만든다면 다음 artifact를 별도로 저장해보는 것이 좋습니다.

```text
hypothesis.json
analysis_plan.json
raw_metrics.parquet
validation.json
fact_sheet.json
interpretation.md
```

그러면 최종 report가 잘못됐을 때 “계산이 틀렸는지”, “해석이 틀렸는지”를 구분할 수 있습니다.

### 주의할 점

관련성은 인과성이 아닙니다. 연구진도 depression cohort 사이의 결과를 “직접 replication”이 아니라 **construct-level convergence**라고 조심스럽게 표현합니다. ([Google Research][6])

**후속 관찰 포인트:** 새로운 unseen cohort로 prospective validation, agent별 ablation, deterministic verifier가 실제 오류를 얼마나 차단하는지, 전체 연구당 token/compute 비용입니다.

**원문:**
[공식 연구 발표 — Google Research Biomarker Discovery Framework](https://www.research.google/blog/an-ai-tool-for-prioritizing-candidate-biomarkers-from-wearable-sensor-data/)
[논문 — CoDaS: AI Co-Data-Scientist](https://arxiv.org/pdf/2604.14615v1)

# 5. AI for Science | Microsoft Skala 1.1 — 38만 파라미터 neural functional을 “실제 과학 소프트웨어 생태계” 안으로

### 무엇이 바뀌었나

Microsoft Research는 8월 20일 neural exchange-correlation functional **Skala 1.1**의 확대 배포를 발표했습니다.

1.1은 이전 버전보다 **2.5배 많은 training data**로 학습됐으며, Microsoft가 공개한 GMTKN55 결과에서 WTMAD-2 **2.8 kcal/mol 수준**을 기록합니다. 공식 model card의 보다 정확한 값은 2.72 kcal/mol입니다. ([Microsoft][8])

흥미로운 점은 모델 크기입니다.

**약 385,000 trainable parameters**뿐입니다. ([Microsoft GitHub][9])

하지만 이 모델의 목적은 언어 생성이 아니라 DFT의 exchange-correlation functional을 neural network로 학습하는 것입니다.

### 왜 중요한가

AI for Science에서 어려운 문제는 좋은 모델을 논문으로 발표하는 것보다 **기존 scientific software에 넣는 것**입니다.

Microsoft는 현재:

* PySCF
* GPU4PySCF
* ASE
* CP2K

경로를 제공하고 있고, Psi4, FHI-aims, ORCA, VASP 통합도 진행 중이라고 밝혔습니다. ([Microsoft][8])

특히 CP2K integration은 별도의 검증 논문까지 냈습니다.

dietGMTKN55에서 CP2K 구현의 aggregate MAD는 **1.255 kcal/mol**, Skala reference는 **1.235 kcal/mol**로 차이는 0.020 kcal/mol이었습니다. 즉 ML model을 다른 electronic-structure engine으로 옮겼을 때 numerical implementation이 같은 결과를 유지하는지를 검증한 것입니다. ([arXiv][10])

### 이 사례에서 ML 엔지니어가 배울 부분

Model deployment를 이렇게 볼 수 있습니다.

```text
Model checkpoint
      ↓
Reference implementation
      ↓
Production implementation
      ↓
cross-implementation numerical parity
      ↓
performance benchmark
```

일반 LLM에서도 사실 동일합니다.

```text
HF model
↓
Transformers
↓
vLLM
↓
TensorRT-LLM

출력이 비슷한가?
성능은 얼마나 다른가?
```

과학 ML에서는 이 검증을 훨씬 엄격하게 하고 있을 뿐입니다.

Microsoft도 Skala를 위한 **living performance benchmark**를 함께 공개해 CPU/GPU·software package가 개선될 때 지속적으로 성능을 다시 측정할 계획입니다. ([Microsoft][8])

### 과장해서 보면 안 되는 부분

“Chemical accuracy를 달성했다”는 문구를 전체 chemistry domain에 일반화하면 안 됩니다.

Model card에서 약 1 kcal/mol 수준은 **W4-17 atomization-energy benchmark**이고, 훨씬 광범위한 GMTKN55의 WTMAD-2는 **2.72 kcal/mol**입니다. ([Microsoft GitHub][9])

또 Microsoft는 현재 model card에 **production model이 아니며 추가 검증을 권고**한다고 명시합니다. ([Microsoft GitHub][9])

### 후속 관찰 포인트

VASP·ORCA integration, periodic-material workload, transition-metal generalization, GPU4PySCF memory behavior와 real-world molecular-dynamics throughput이 중요합니다.

# 6. 개발 도구 | Anthropic Python SDK 1.0 — Files·Skills·Browser·Computer가 실험 기능에서 Agent API surface로

### 무엇이 바뀌었나

Anthropic Python SDK가 **8월 20일 v1.0.0**에 도달했습니다.

1.0 자체의 가장 큰 breaking change는 HTTP stack을 `httpx2`로 올린 것이며 migration guide 확인이 필요합니다. ([GitHub][11])

하지만 더 중요한 변화는 바로 직전 두 release에 들어왔습니다.

8월 19일 `v0.124.0`에서:

* **Files API GA**
* **Skills API GA**
* Computer-use toolset
* Browser-use toolset

이 추가됐습니다. ([GitHub][12])

같은 날 `v0.125.0`에서는:

* managed-agent web-search configuration
* **self-hosted sandbox memory**

가 추가됐습니다. ([GitHub][13])

즉 1.0 전후의 API를 묶어 보면 agent application의 기본 primitive가 상당히 분명해집니다.

```text
Model
Files
Skills
Browser
Computer
Search
Sandbox
Memory
```

### 왜 중요한가

Agent framework들이 그동안 자체적으로 구현하던 개념이 provider SDK의 first-class API로 올라오고 있습니다.

특히 **Skill과 Files가 GA**됐다는 점은 중요합니다. 앞으로 application은 system prompt 하나가 아니라:

```text
Model version
Skill version
File collection
Tool permissions
Sandbox state
```

의 조합으로 배포되게 됩니다.

따라서 reproducibility를 위해 inference log에 모델 이름만 남기면 부족해집니다.

```text
model_version
skill_version
file_set_hash
sandbox_version
tool_schema_version
```

까지 필요해집니다.

### SDK 1.0에서 조심할 점

`v1.0.0`은 semantic-versioning상 안정적인 기준점이지만 **upgrade가 무조건 non-breaking이라는 뜻이 아닙니다.**

첫 1.0 자체에 `httpx2` migration이라는 breaking change가 있으므로, retry/timeout/proxy/connection-pooling 같은 networking behavior를 regression test해야 합니다. ([GitHub][11])

Browser·computer use는 특히 다음을 별도로 막아야 합니다.

```text
network egress
download
clipboard
filesystem
credential
side effect
```

SDK가 tool을 제공한다고 permission model까지 자동으로 해결되는 것은 아닙니다.

### 후속 관찰 포인트

Skills artifact versioning, self-hosted sandbox memory lifecycle, managed-agent search provenance, SDK 1.x에서 tool semantics가 얼마나 안정적으로 유지되는지입니다.

### 1. MCP 새 로드맵

특히 **agent identity, authority delegation, progressive tool discovery** 세 부분을 보세요. 앞으로 MCP가 단순 “LLM이 API를 부르는 protocol”이 아니라 **agent distributed system의 control plane**으로 가려는 방향이 명확해졌습니다. ([Model Context Protocol Blog][1])

# 오늘의 실습 | Codex + NVIDIA CUDA MCP를 붙여서 “문서 Grounding이 실제 CUDA 답변을 개선하는가?” 측정하기

오늘은 아주 가볍게 시작할 수 있으면서도 실무적인 실험을 추천합니다.

먼저 NVIDIA 공식 CUDA MCP를 Codex에 연결합니다. ([NVIDIA Developer][4])

```bash
codex mcp add nvidia-cuda-docs \
  --url https://api.copilot.nsight.ngc.nvidia.com/mcp/cuda-docs
```

그다음 **동일 모델**로 두 조건을 만듭니다.

```text
A. CUDA MCP OFF

B. CUDA MCP ON
```

질문 15개 정도를 준비합니다.

단순 CUDA 문법 문제보다는 **버전·architecture 의존성이 있는 질문**이 좋습니다.

예를 들어:

```text
1. B200에서 FP4 관련 CUDA datatype은 어떤 API를 써야 하는가?

2. CUDA Graph capture 중 사용할 수 없는 API는 무엇인가?

3. Hopper와 Blackwell의 TMA 사용 차이는?

4. shared memory bank conflict를 확인할 Nsight Compute metric은?

5. cudaMallocAsync memory pool의 최신 권장 사용법은?

6. CuTe DSL에서 특정 primitive의 현재 signature는?

7. CUDA 13에서 deprecated된 API를 이용한 코드를
   최신 방식으로 수정하라.
```

각 질문에 대해 다음을 기록하십시오.

```text
answer_correct
official_source_cited

deprecated_API_used
nonexistent_API_used

tool_calls
retrieved_tokens
total_tokens

latency
```

그리고 코드 문제 5개를 추가합니다.

```text
CUDA kernel 제시
     ↓
Agent가 수정
     ↓
nvcc compile
     ↓
correctness test
     ↓
Nsight Compute
```

최종 평가는 이렇게 잡으면 됩니다.

```text
Documentation Accuracy
= 공식 CUDA 문서와 일치한 답 / 전체

Hallucinated API Rate
= 존재하지 않는 API 사용 / 전체

Compile Success

Kernel Correctness

Tool Overhead
```

여기서 재미있는 결과는 **MCP가 accuracy를 올리지만 latency/token도 올리는 정도**입니다.

예를 들어:

```text
              MCP OFF    MCP ON

Accuracy        73%        93%
API halluc.     13%         0%
Latency        4.1s       6.8s
```

라면 모든 CUDA 질문에 MCP를 쓰기보다 다음 router를 만들 수 있습니다.

```text
일반 Python/PyTorch 문제
→ MCP 없음

CUDA API / architecture / compiler 질문
→ CUDA MCP

정확성 검증이 필요한 kernel 수정
→ CUDA MCP + profiler
```

이렇게 하면 MCP roadmap에서 오늘 공식적으로 문제 삼은 **“모든 tool을 항상 모델에게 노출하지 말고 필요한 순간에 discovery하라”**는 방향까지 작은 규모로 직접 구현해볼 수 있습니다. ([Model Context Protocol Blog][1])
