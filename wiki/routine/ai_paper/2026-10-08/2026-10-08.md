## 1. Claude Haiku 5.5 공개 — 소형 모델의 역할이 단순 요약에서 실제 에이전트 실행으로 확대 ★★★★★

**공개일: 2026년 10월 7일 | 분야: LLM · Agent · Model Routing**

Anthropic이 Claude Haiku 5.5를 정식 공개했습니다. 이번 모델은 단순한 저가형 챗봇보다 **대량으로 반복되는 에이전트 작업에 최적화된 소형 모델**이라는 성격이 강합니다.

공식 발표에 따르면 Haiku 5.5는 기존 Haiku 4.5 대비 평균 실행 비용이 약 75% 감소했습니다.

특히 입력이 100K 토큰 이하인 경우 API 가격은 다음과 같습니다.

| 구분 | Haiku 4.5 | Haiku 5.5 |
|---|---:|---:|
| 입력 100만 토큰 | $1.00 | $0.10 |
| 출력 100만 토큰 | $5.00 | $0.50 |
| 캐시 읽기 100만 토큰 | $0.10 | $0.01 |

단, **입력 프롬프트가 100K 토큰을 초과하면** Haiku 5.5의 입력·출력 가격은 각각 $0.50/$2.50으로 높아집니다. 새로운 tokenizer로 인해 동일 텍스트의 토큰 수도 달라질 수 있으므로 명목상 90%의 단가 인하가 실제 작업 비용 90% 감소를 보장하지는 않습니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com)

### 엔지니어링 관점

이번 발표에서 중요한 것은 **Agent Architecture의 모델 계층화**입니다.

지금까지 상당수 에이전트 시스템은 하나의 강력한 모델이 모든 작업을 처리하는 구조였습니다.

```text
Agent
  └── Frontier LLM
       ├── 파일 탐색
       ├── 코드 분석
       ├── 문서 요약
       ├── 계획 수립
       ├── 코드 수정
       └── 결과 검증
```

그러나 모든 작업에 높은 수준의 추론 능력이 필요한 것은 아닙니다.

Haiku 5.5처럼 저렴하면서 상당한 성능을 제공하는 모델이 등장하면 다음 구조가 더 경제적일 수 있습니다.

```text
Orchestrator
    │
    ├── Small Model
    │    ├── Repository 탐색
    │    ├── 정보 추출
    │    ├── Context Compaction
    │    └── 단순 Tool Decision
    │
    └── Frontier Model
         ├── 연구 가설 수립
         ├── 복잡한 코드 변경
         ├── 아키텍처 설계
         └── 최종 검증
```

다만 이러한 분리는 단순히 작은 모델이 저렴하다는 이유만으로 정당화되지 않습니다.

작은 모델이 잘못된 정보를 추출하면 상위 모델이 그 결과를 다시 검증해야 하므로 전체 비용이 증가할 수 있습니다.

따라서 **`작업당 비용`이 아니라 `성공한 작업당 비용`**을 비교해야 합니다.

### 성능과 한계

Anthropic 자체 평가에서 Haiku 5.5는 Terminal-Bench 4.0에서 39.2%, Sonnet 5.5는 70.6%를 기록했습니다.

반면 OSWorld 2.1의 오프라인 평가에서는 Haiku 5.5가 72.4%를 기록해 이전 Haiku 4.5의 15.7%보다 크게 개선됐습니다.

이 수치는 Haiku 5.5가 모든 코딩 작업에서 상위 모델을 대체한다는 의미가 아닙니다. **짧고 반복적인 작업에는 적합하지만 복잡한 터미널 작업에서는 여전히 상당한 성능 차이**가 존재합니다. 평가 하네스와 설정도 직접 확인해야 합니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5)

**후속 관찰 포인트:** 실제 Coding Agent에서 Haiku 5.5를 서브에이전트로 사용할 때 작업 완료율, 재시도 횟수, 상위 모델의 재검증 비용이 어떻게 달라지는지입니다.

**원문:** [공식 발표 · Anthropic — Claude Haiku 5.5](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com) · [릴리스 노트 · GitHub Copilot의 Haiku 5.5 지원](https://github.blog/changelog/2026-10-07-claude-haiku-5-5-in-github-copilot/)

## 2. Mistral Large 4 — 1조 파라미터급 멀티모달 MoE, 유럽의 오픈웨이트 경쟁 확대 ★★★★★

**공개일: 2026년 10월 6일 | 분야: LLM Architecture · MoE · Open Weights**

Mistral AI가 **Mistral Large 4(ML4)**의 공개 프리뷰를 발표했습니다.

공식 모델 문서 기준 주요 사양은 다음과 같습니다.

| 항목 | 사양 |
|---|---|
| 전체 파라미터 | 1.05T |
| 활성 파라미터 | 52B |
| 구조 | Mixture of Experts |
| Vision Encoder | 1.6B |
| Context Window | 1M |
| 주요 입력 | 텍스트·이미지 |
| 현재 제공 형태 | API Public Preview |

Mistral은 약 3,800개의 NVIDIA Grace Blackwell GPU를 이용해 유럽 데이터센터에서 모델을 학습했다고 밝혔습니다.

**중요한 구분이 있습니다.** 10월 8일 현재 API 프리뷰는 이용할 수 있지만 모델 가중치는 아직 공개되지 않았습니다. Mistral은 10월 말 공개를 예고했습니다. 따라서 현재는 오픈웨이트 모델로 발표됐더라도 사용자가 직접 내려받아 배포할 수 있는 상태는 아닙니다. [Mistral AI](https://docs.mistral.ai/models/mistral-large-4)

### 엔지니어링 관점

이번 모델의 중요한 특징 중 하나는 **멀티모달 추론과 장기 에이전트 작업을 하나의 MoE 기반 모델에 통합했다는 점**입니다.

Mistral은 모델의 Post-training 시스템도 일부 공개했습니다.

해당 시스템은 여러 종류의 학습 환경을 공통 인터페이스로 구성하고, 대규모 Actor들이 Rollout을 생성하는 동안 모델 학습이 비동기적으로 진행됩니다.

공식 발표에서 설명한 구조를 단순화하면 다음과 같습니다.

```text
Task Environments
    │
    ├── Coding
    ├── Scientific Reasoning
    ├── Cybersecurity
    └── Long-Horizon Agent
           │
           ▼
    Parallel Rollout Actors
           │
           ▼
    Reward / Verification
           │
           ▼
    Asynchronous Training
           │
           └── Updated Policy
```

Mistral은 약 3,000 GPU 규모의 현재 학습 설정에서 하루 약 330억 토큰을 생성하고, 필터링과 마스킹 후 약 160억 토큰을 학습 대상으로 사용한다고 설명했습니다. 이 수치는 자체 학습 인프라에 대한 회사 측 보고입니다. [Mistral](https://mistral.ai/news/mistral-large-4/)

여기서 중요한 것은 단순한 GPU 규모가 아닙니다.

**학습 환경과 평가기를 공통 인터페이스로 관리하면서 대규모 Rollout을 지속적으로 생산하는 구조**가 대형 모델 Post-training의 주요 경쟁력이 되고 있다는 점입니다.

### 보안 모델 연구에서의 의미

Mistral은 ML4를 보안 분석에도 적극적으로 활용할 계획입니다.

자체 공개 평가에서 DeepSWE v1.1은 61.7%, Terminal-Bench 4.0은 28.3%를 보고했습니다. 또한 Cybench 등 사이버 보안 평가에서도 높은 성능을 주장합니다.

다만 사이버 벤치마크에서는 모델이 실제 문제를 해결하지 못한 경우와 안전 정책 때문에 수행을 거부한 경우를 구분해야 합니다.

따라서 **보안 특화 LLM을 비교할 때는 취약점 탐지 정확도, 분석 성공률, 거부율, 실제 도구 실행 권한을 별도 평가 축으로 분리**하는 것이 바람직합니다.

또한 ML4의 전체 가중치 규모를 고려하면 단일 48GB GPU에서 모델 전체를 직접 배포하는 실험은 현실적인 출발점이 아닙니다.

**후속 관찰 포인트:** 10월 말 실제 가중치 공개 여부, 모델 라이선스, Attention/MoE 세부 구조, KV cache 요구량, vLLM·SGLang 지원 상태입니다.

**원문:** [공식 발표 · Mistral Large 4](https://mistral.ai/news/mistral-large-4/) · [공식 모델 문서 · Mistral Large 4 Specifications](https://docs.mistral.ai/models/mistral-large-4)

## 3. PHBA — 선형 메모리와 원거리 정확 검색을 결합하는 새로운 하이브리드 어텐션 ★★★★★

**arXiv 등록: 2026년 10월 6일 | 분야: LLM Architecture · Attention · Long Context**

오늘 아키텍처 연구 분야에서 가장 주목할 만한 논문은 **PHBA(Prefix-State Hybrid Block Attention)**입니다.

이 연구는 현대 하이브리드 LLM에서 반복적으로 등장하는 문제를 다룹니다.

> 선형 어텐션의 효율성을 유지하면서 먼 위치에 존재하는 정보를 정확하게 검색하려면 어떻게 해야 하는가?

### 기존 구조의 한계

Linear Attention 계열은 과거 정보를 고정 크기의 상태로 압축합니다.

이 방식은 메모리 사용량을 줄일 수 있지만, 오래된 정보에 대한 정확한 토큰 단위 검색이 어려워질 수 있습니다.

반면 Sliding Window Attention은 최근 토큰에 대한 정확한 접근을 제공하지만, 윈도우 밖의 중요한 정보를 직접 읽을 수 없습니다.

PHBA는 이 두 방식의 한계를 동시에 개선하려고 합니다.

### PHBA의 핵심 구조

```text
Input Sequence
      │
      ▼
Block Partition
      │
      ├── Block 1
      ├── Block 2
      ├── Block 3
      └── Block N
             │
             ▼
      Recurrent Prefix State
             │
             ▼
      Top-K Block Retrieval
             │
             ▼
   Retrieved Token Blocks
             +
   Corresponding Prefix States
             │
             ▼
        Hybrid Attention
```

가장 중요한 특징은 **원거리에서 검색된 블록과 그 블록 이전의 문맥을 압축한 상태를 함께 사용한다는 점**입니다.

단순 Block Sparse Attention은 특정 블록의 토큰을 가져옵니다.

PHBA는 여기에 해당 블록 이전의 정보를 요약한 recurrent prefix state를 추가합니다.

즉 검색된 토큰만 보지 않고, 해당 정보가 등장하기까지의 문맥도 함께 고려합니다.

연구진은 이를 위해 gated linear recurrence와 hardware-aware Triton 구현을 사용했습니다. [arXiv](https://arxiv.org/abs/2610.08527)

### 실험 결과

저자들은 760M 및 1.3B 규모 모델에서 실험했습니다.

모델은 8K context로 학습하고, 이후 16K·32K·64K 구간에서 추가 학습 없이 평가했습니다.

연구진은 RULER, NIAH, LongBench 등에서 기존 효율형 어텐션보다 좋은 결과를 보고했습니다.

그러나 여기에는 중요한 제한이 있습니다.

**LongBench에서는 8K를 초과하는 입력을 앞부분 4K와 뒷부분 4K로 잘라 평가했습니다.** 따라서 해당 결과만으로 64K 전체 문서를 이해하는 능력이 검증됐다고 해석하면 안 됩니다.

또한 저자들의 구현 기준으로 Prefix State를 추가하면 MoBA 대비 일정한 계산 오버헤드가 발생합니다. [arXiv](https://arxiv.org/html/2610.08527v1)

### 아키텍처 연구에 적용한다면

이 논문은 하이브리드 LLM 설계 공간을 세 요소로 나누어 볼 수 있게 해줍니다.

**Exact Retrieval:** 어떤 원거리 토큰을 직접 읽을 것인가?

**Compressed Memory:** 과거 정보를 얼마나 압축해 유지할 것인가?

**Routing:** 현재 Query에 필요한 블록을 어떻게 선택할 것인가?

이 세 요소를 독립적으로 조정하면 아키텍처 성능에 영향을 주는 원인을 분리할 수 있습니다.

예를 들어 다음과 같은 실험이 가능합니다.

```text
Baseline A: Sliding Window Only
Baseline B: Recurrent State Only
Baseline C: Block Sparse Only
Proposed:   Block Sparse + Prefix State
```

이후 검색 정확도와 메모리 비용을 동시에 측정하는 것입니다.

**후속 관찰 포인트:** 더 큰 모델 규모에서의 성능, 학습 비용, Sparse Routing 오버헤드, 실제 코드 검색 및 장문 보안 분석 태스크에서의 개선 여부입니다.

**원문:** [논문 · PHBA: Prefix-State Hybrid Block Attention](https://arxiv.org/abs/2610.08527)

## 4. VETTA — 멀티턴 에이전트 RL에서 턴 단위와 토큰 단위 보상을 동시에 학습 ★★★★★

**arXiv 등록: 2026년 10월 6일 | 분야: Reinforcement Learning · Agent Training**

**VETTA(Coordinating Turn- and Token-Level Credit Assignment for Multi-Turn LLM Agents)**는 에이전트 강화학습에서 중요한 문제를 다룹니다.

일반적인 멀티턴 에이전트는 여러 행동을 거쳐 최종 보상을 얻습니다.

예를 들어 다음과 같은 상황입니다.

```text
Turn 1: 환경 분석
Turn 2: 파일 탐색
Turn 3: 코드 수정
Turn 4: 테스트 실행
Turn 5: 수정 완료

Final Reward = 1
```

문제는 최종 보상이 1이라는 사실만으로 어느 턴이 성공에 기여했는지 구분하기 어렵다는 점입니다.

동시에 한 턴 안에서도 어떤 토큰 선택이 중요한 행동을 결정했는지 구분해야 합니다.

### VETTA의 접근

연구진은 두 종류의 Value를 함께 추정합니다.

**Turn-level Value**는 각 응답이나 행동이 전체 작업 성공에 얼마나 기여했는지 평가합니다.

**Token-level Value**는 한 응답 내부에서 개별 생성 결정이 얼마나 중요한지 평가합니다.

두 값을 별도 Head로 학습하되 경량 Critic Backbone을 공유합니다.

```text
Agent Trajectory
       │
       ▼
Lightweight Critic
       │
       ├── Turn Value Head
       │
       └── Token Value Head
       │
       ▼
Combined Advantage
       │
       ▼
PPO Policy Update
```

VETTA는 턴 수준 Advantage에 응답 내부의 평균을 제거한 Token-level Residual을 더해 학습 신호를 구성합니다.

이렇게 하면 턴 전체의 기여도를 유지하면서 해당 턴 안에서 중요한 토큰 선택을 구분할 수 있습니다. [arXiv](https://arxiv.org/abs/2610.08402)

### 주요 결과

Qwen2.5-7B-Instruct를 사용한 평가에서 다음 성공률을 보고했습니다.

| Benchmark | VETTA 성공률 |
|---|---:|
| ALFWorld | 95.5% |
| WebShop | 76.0% |

더 흥미로운 것은 Critic의 크기입니다.

전체 28개 Transformer Block을 사용하지 않고 초기 2개 Block만 남긴 Critic을 사용했을 때, 실험 환경에서 Critic 관련 계산 시간이 ALFWorld 약 87%, WebShop 약 91% 감소했습니다.

저자들은 이러한 경량 Critic이 오히려 더 좋은 평균 작업 성공률을 보이는 조건도 확인했습니다. [arXiv](https://arxiv.org/html/2610.08402v1)

### 왜 중요한가?

Agent RL에서는 실제 Policy Model뿐 아니라 Rollout, Reward 계산, Critic Update가 모두 GPU 자원을 사용합니다.

따라서 Critic을 작게 만들 수 있다면 같은 자원으로 더 많은 Rollout을 수행할 여지가 생깁니다.

다만 이 연구의 주요 검증 환경은 ALFWorld와 WebShop입니다.

실제 코드 수정, 장기간 연구 에이전트, 수십만 토큰의 Trajectory에서도 동일한 효과가 나타나는지는 아직 확인해야 합니다.

**후속 관찰 포인트:** PPO 대비 다른 RL 알고리즘과의 비교, Reward Sparsity 변화에 대한 안정성, 실제 Coding Agent에서의 Credit Assignment 성능입니다.

**원문:** [논문 · VETTA: Coordinating Turn- and Token-Level Credit Assignment](https://arxiv.org/abs/2610.08402) · [GitHub · VETTA 공식 구현](https://github.com/Jiaju-Chen/VETTA-official)

## 5. NVIDIA AICR 1.0 — GPU 클러스터 구성을 검증 가능한 실험 결과로 관리 ★★★★★

**공개일: 2026년 10월 7일 | 분야: GPU Infrastructure · Kubernetes · Reproducibility**

NVIDIA가 **AI Cluster Runtime(AICR) v1.0**을 발표했습니다.

이 프로젝트는 Kubernetes 기반 GPU 클러스터의 구성을 **버전이 고정된 Recipe와 검증 증거**로 관리하는 오픈소스 도구입니다.

GPU 인프라에서는 CUDA 버전 하나만 맞춰도 시스템이 정상 작동하는 것이 아닙니다.

실제로는 다음 요소가 함께 맞아야 합니다.

```text
Linux Kernel
GPU Driver
CUDA Runtime
Container Runtime
Kubernetes
GPU Operator
Network / Storage
Scheduler
Training / Inference Framework
```

각 요소는 독립적인 릴리스 주기를 갖기 때문에 버전 충돌과 설정 불일치가 발생하기 쉽습니다.

### AICR의 구조

AICR은 네 가지 핵심 기능을 제공합니다.

```text
Snapshot
    ↓
현재 Cluster 환경 기록
    ↓
Recipe
    ↓
검증된 버전 조합 정의
    ↓
Bundle
    ↓
Helm / Argo CD / Flux 등으로 배포
    ↓
Validation
    ↓
실제 환경과 Recipe 비교
    ↓
Signed Evidence
```

특히 중요한 것은 **설치 성공과 시스템 검증을 구분한다는 점**입니다.

패키지가 정상적으로 설치됐더라도 GPU Discovery, Scheduling, Network 기능이나 성능 요구사항이 충족된다는 보장은 없습니다.

AICR은 구성 자체뿐 아니라 실제로 어떤 하드웨어에서 무엇을 검증했는지 기록할 수 있습니다. 이번 1.0에서는 CLI, REST API, Go SDK, Artifact Schema에 대한 안정적인 호환성 계약도 도입했습니다. [NVIDIA Developer](https://developer.nvidia.com/blog/aicr-v1-0-open-stable-and-verifiable-gpu-cluster-configuration/)

### GPU 연구 환경에서의 의미

멀티 GPU 실험을 진행할 때 성능 결과만 저장하면 재현성이 부족할 수 있습니다.

예를 들어 같은 모델을 TP=2로 실행했더라도 다음 환경 변화가 결과에 영향을 줄 수 있습니다.

```text
Experiment
 ├── GPU Model
 ├── GPU Topology
 ├── Driver Version
 ├── CUDA Version
 ├── NCCL Version
 ├── vLLM Version
 ├── PyTorch Version
 └── Benchmark Configuration
```

AICR은 이러한 환경 관리가 단순 운영 문서에서 검증 가능한 구성 관리 시스템으로 발전하는 사례입니다.

다만 AICR은 Kubernetes GPU 클러스터를 중심으로 설계됐습니다. 단일 Ubuntu 서버에서 수행하는 모든 실험에 직접 필요한 도구는 아닙니다.

**후속 관찰 포인트:** Slurm 환경 지원 확대, NCCL 및 네트워크 토폴로지 검증, 성능 검증 결과의 표준화, 연구 실험 메타데이터와의 연계입니다.

**원문:** [공식 기술 블로그 · NVIDIA AICR 1.0](https://developer.nvidia.com/blog/aicr-v1-0-open-stable-and-verifiable-gpu-cluster-configuration/) · [GitHub · NVIDIA/aicr](https://github.com/NVIDIA/aicr)

## 7. GitHub의 보안 전용 모델 — 생성형 LLM 대신 Context-Aware Secret Classifier 사용 ★★★★☆

기존 Secret Scanning은 정규식이나 알려진 API Key Pattern을 기반으로 동작하는 경우가 많습니다.

예를 들어 다음과 같은 형식입니다.

```text
API_KEY = "sk-..."
```

이런 경우 알려진 접두사나 문자열 패턴을 이용해 탐지할 수 있습니다.

하지만 실제 코드에서는 다음과 같은 형태도 나타납니다.

```text
config = {
    "username": "service_user",
    "password": "example-placeholder"
}
```

이 경우 특정 토큰 형식만으로는 실제 자격증명인지 판단하기 어렵습니다.

특히 이 모델은 코드나 자연어를 생성하는 일반 LLM이 아니라 **비밀정보 탐지에 특화된 모델**입니다. [The GitHub Blog](https://github.blog/changelog/2026-10-07-purpose-built-model-for-leaked-secret-detection/)

```text

     │

     │

     │
```

# 오늘 직접 해볼 만한 실습
## `Agent Model Routing` — 소형 모델에 업무를 위임하면 정말 비용이 줄어들까?

오늘은 Claude Haiku 5.5 출시를 계기로 **에이전트의 작업 분할 방식에 따른 비용과 성능 차이**를 측정해보는 것을 추천합니다.

핵심 질문은 다음입니다.

> **하나의 강력한 모델이 전체 작업을 처리하는 것과, 작은 모델이 일부 작업을 대신 처리하는 것 중 실제로 어느 쪽이 효율적인가?**

### 실험 구성

동일한 Repository 분석 작업 10개 정도를 준비합니다.

작업은 실제 코드 수정이 필요한 경우와 단순 정보 추출만 필요한 경우를 섞는 것이 좋습니다.

예를 들어 `함수 위치 탐색`, `의존성 파악`, `오류 원인 분석`, `단순 수정`, `복잡한 수정`을 포함합니다.

세 조건을 비교합니다.

```text
A. Single Model

   Main LLM
      │
      ├── 탐색
      ├── 분석
      ├── 수정
      └── 검증


B. Multi-Model

   Main LLM
      │
      ├── Small Model
      │     ├── 탐색
      │     └── 정보 추출
      │
      ├── 분석
      ├── 수정
      └── 검증


C. Multi-Model + Verification

   Main LLM
      │
      ├── Small Model
      │     ├── 탐색
      │     └── 정보 추출
      │
      ├── Evidence Validation
      │
      ├── 분석
      ├── 수정
      └── 검증
```

이 실험에서 Small Model은 Haiku 5.5 같은 API 모델을 사용해도 되고, 이미 보유한 로컬 LLM을 사용해도 됩니다. 중요한 것은 모델 비교가 아니라 **업무 위임 구조의 효과**를 측정하는 것입니다.

### 측정 지표

```text
task_success_rate
total_model_calls
main_model_calls
small_model_calls

fresh_input_tokens
cached_input_tokens
output_tokens

tool_calls
verification_calls
retry_count

wall_clock_time
cost_per_task
cost_per_success
```

특히 다음 두 항목에 집중해야 합니다.

**1. 상위 모델의 호출 횟수가 실제로 줄어드는가?**

서브에이전트가 생성한 결과를 Main Agent가 전부 다시 검토한다면 전체 연산량은 늘어날 수 있습니다.

**2. 작은 모델이 만든 오류가 전체 작업에 어떤 영향을 주는가?**

서브에이전트의 탐색 오류로 Main Agent가 잘못된 파일을 수정한다면 저렴한 모델을 사용한 이점이 사라집니다.

따라서 다음 형태로 결과를 정리하면 좋습니다.

| 실험 조건 | 성공률 | 평균 모델 호출 | 평균 재시도 | 성공당 비용 |
|---|---:|---:|---:|---:|
| A. Single Model | 측정 | 측정 | 측정 | 측정 |
| B. Multi-Model | 측정 | 측정 | 측정 | 측정 |
| C. Multi-Model + Verification | 측정 | 측정 | 측정 | 측정 |

실험에서 가장 중요한 것은 C 조건입니다.

서브에이전트가 추출한 파일 경로와 함수 위치를 실제 Repository에서 확인하는 정도의 저렴한 Deterministic Verifier만 추가해도 잘못된 정보가 Main Agent로 전달되는 문제를 줄일 수 있는지 평가할 수 있습니다.

이 실험은 단순한 모델 성능 비교를 넘어 **모델 계층화, 하네스 설계, 검증 비용, 전체 작업 성공률**을 하나의 통제 실험으로 연결합니다.

### 오늘의 종합 판단

오늘 공개된 자료를 연구 주제별로 정리하면 **PHBA는 LLM 내부 정보 흐름**, **VETTA는 에이전트 학습 신호**, **Haiku 5.5는 에이전트의 모델 계층화**, **AICR은 GPU 실험 환경의 재현성**, **GitHub의 업데이트는 실행 권한과 전용 보안 모델**이라는 서로 다른 문제를 다룹니다.

이 중 당장 심층적으로 읽을 가치가 가장 높은 것은 **PHBA와 VETTA 두 논문**입니다. 두 연구 모두 구조적 아이디어가 명확하고, 비교 대상과 실험 조건을 확인할 수 있습니다.

다만 두 논문은 아직 새로운 프리프린트입니다. PHBA는 모델 규모와 장문 평가 방식에 제한이 있고, VETTA는 소규모 에이전트 벤치마크 중심이므로 실제 대규모 LLM이나 Production Agent에서의 개선을 별도로 검증해야 합니다.

**오늘의 핵심 결론은 모델을 더 크게 만드는 것만큼, 정보를 어떻게 보존하고 검색할지, 행동의 기여도를 어떻게 학습할지, 실행환경을 어떻게 통제하고 검증할지가 중요해지고 있다는 점입니다.**
