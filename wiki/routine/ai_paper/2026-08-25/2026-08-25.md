## 1. 필독 | NVIDIA Groq 3 LPX — Prefill은 GPU, Decode·FFN은 LPU로 쪼개는 Heterogeneous Inference가 현실화

8월 24일 NVIDIA는 Vera Rubin 플랫폼에 결합되는 **Groq 3 LPX**의 첫 third-party benchmark 결과를 공개했습니다. Artificial Analysis가 NVIDIA 데이터센터에 설치된 LPX에서 Gemma 4 31B를 100K input-context 조건으로 측정한 결과 **3,431 output tok/s**를 기록했습니다. 같은 비교에서 가장 빠른 public endpoint는 870 tok/s였고, 10K context에서도 median 3,382 tok/s였습니다. NVIDIA가 별도로 수행한 SPEED-Bench coding workload에서는 median **4,767 tok/s**, P80 5,520 tok/s를 보고했습니다. ([NVIDIA Developer][1])

중요한 건 숫자보다 구조입니다. LPX는 256개의 LPU와 총 128GB SRAM을 사용하며 compiler가 compute와 chip-to-chip communication을 미리 deterministic schedule로 배치합니다. NVIDIA가 제시한 실제 serving 구성은 세 가지입니다. **Vera Rubin이 prefill하고 LPX가 decode를 맡는 P/D disaggregation**, Rubin이 attention·KV cache를 맡고 LPX가 FFN을 실행하는 Attention–FFN disaggregation, 그리고 LPX가 작은 draft model을 실행하고 Rubin이 target model을 검증하는 external speculative drafter 구성입니다. ([NVIDIA Developer][1])

이 방향은 꽤 중요합니다. 지금까지의 LLM 서버는 대체로 “한 종류의 GPU에서 모델 전체를 최대한 잘 실행한다”는 사고방식이었습니다. 앞으로는 workload를 `prefill / attention / FFN / draft / tool execution`으로 쪼개고 **각 연산 특성에 가장 맞는 processor로 배치**하는 형태가 더 일반적일 수 있습니다.

```text
Long-context prefill  → GPU
Attention + KV state  → GPU / HBM
Latency-sensitive FFN → LPU
Draft model           → LPU
Tool execution        → CPU
```

Agent workload에서는 이 구조가 특히 유리할 가능성이 있습니다. Agent는 한 번의 긴 generation보다 수십 번의 짧은 inference와 tool call을 반복하기 때문에 decode latency가 매 turn 누적됩니다. 따라서 평균 `tok/s`보다 `TTFT + per-turn decode + KV handoff + tool gap`을 합친 **전체 trajectory latency**를 측정해야 합니다. ([NVIDIA Developer][2])

같은 날 NVIDIA는 SemiAnalysis AgentX workload를 이용한 Vera Rubin의 power-efficiency preview도 공개했습니다. DeepSeek V4-Pro에서 160 tok/s/user 조건으로 Vera Rubin NVL72가 GB300 NVL72보다 최대 **30배 높은 throughput/MW**를 기록했다고 NVIDIA가 보고했습니다. 다만 이 숫자는 **NVIDIA 자체 측정이며 현재 SemiAnalysis 검토가 아직 끝나지 않은 preview**입니다. 따라서 Groq 3 LPX의 Artificial Analysis 측정과 같은 수준의 독립 검증 결과로 취급하면 안 됩니다. ([NVIDIA Developer][2])

실무적으로 새로운 hardware를 볼 때는 앞으로 다음 네 축을 분리해서 보는 것이 좋습니다. `prefill tok/s`, `decode tok/s/user`, `E2E task latency`, `successful agent tasks/MWh`. 특히 accelerator 사이의 activation·KV 이동 비용이 추가되므로 microbenchmark에서 4배 빨라도 network handoff가 크면 실제 agent에서는 이득이 상당히 줄 수 있습니다.

**후속 관찰 포인트:** Rubin↔LPX KV transfer latency, multi-trillion MoE 실측, 높은 concurrency에서의 tail latency, heterogeneous serving을 Dynamo·vLLM·SGLang이 어느 수준까지 자동 scheduling할지입니다.

**원문:** [NVIDIA 기술 블로그 — Groq 3 LPX 100K Context Benchmark](https://developer.nvidia.com/blog/how-nvidia-groq-3-lpx-unlocks-ultrafast-interactivity-at-long-context-on-nvidia-vera-rubin/?utm_source=chatgpt.com) · [NVIDIA 기술 블로그 — Vera Rubin AgentX Performance/Watt](https://developer.nvidia.com/blog/nvidia-vera-rubin-and-blackwell-set-a-new-standard-for-agentic-ai-performance-per-watt/)

## 2. 개발 도구 | GPT‑5.6 × Kiro — 모델 가격보다 “Spec를 먼저 만드는 Harness”가 성공당 비용을 크게 바꾼다

OpenAI는 8월 24일 GPT‑5.6 **Sol·Terra·Luna**가 AWS의 software-development agent인 Kiro에서 제공된다고 발표했습니다. Kiro는 사용자 의도를 바로 코드로 바꾸기보다 먼저 요구사항, 기술 설계, executable task로 구조화하고 codebase와 팀 표준을 이 context에 넣은 뒤 구현을 수행하는 **spec-driven harness**입니다. Property-based testing과 implementation checkpoint도 workflow에 포함합니다. ([OpenAI][3])

가장 눈에 띄는 수치는 OpenAI와 AWS의 Terminal-Bench 2.1 공동 테스트입니다. 두 회사는 GPT‑5.6 Terra가 Kiro 안에서 **성공한 task당 비용을 약 82% 줄였다**고 보고했습니다. 다만 발표에는 정확히 어떤 baseline configuration·model·reasoning budget과 비교한 것인지 세부 breakdown이 충분히 공개되어 있지 않습니다. 따라서 “Kiro를 쓰면 모든 coding task 비용이 82% 떨어진다”는 의미로 받아들이면 안 됩니다. ([OpenAI][3])

그럼에도 이 결과가 던지는 문제는 중요합니다. Coding-agent 비용은 단순히:

```text
API token price × token 수
```

가 아니라 실제로는:

```text
초기 요구사항 이해
+ 잘못된 구현
+ 재탐색
+ test 실패
+ retry
+ 수정
```

의 총합입니다. 모델에 처음부터 명확한 requirement와 success criterion을 주면 prompt 자체는 길어져도 **misstep·retry가 줄어 성공당 총 token은 오히려 감소**할 수 있습니다. 최근 harness 연구에서 반복해서 나타나는 패턴과 동일합니다. ([OpenAI][3])

따라서 coding agent를 비교할 때 `input/output token`만 보지 말고 `requirement clarification turns`, `files touched`, `failed tests`, `retry count`, `human correction minutes`, `cost_per_merged_change`를 같이 기록하는 편이 좋습니다. 모델 A가 30% 비싸도 한 번에 구현하고 모델 B가 세 번 재작업하면 실제 운영 비용은 역전될 수 있습니다.

한 가지 더 주목할 점은 spec-driven workflow가 **코딩 전에 사람이 intervention할 checkpoint를 자연스럽게 만든다는 것**입니다. 고위험 production change라면 “모델이 코드를 만든 뒤 검토”보다 요구사항·설계·task decomposition 단계에서도 승인할 수 있어 blast radius를 줄이기 쉽습니다.

**후속 관찰 포인트:** 82% 수치의 세부 baseline 공개, large repository에서 spec 작성 overhead, 요구사항 자체가 잘못됐을 때의 failure amplification, Kiro와 다른 harness에서 동일 GPT‑5.6을 비교한 paired benchmark입니다.

**원문:** [OpenAI 공식 발표 — GPT‑5.6 in Kiro](https://openai.com/index/gpt-5-6-in-kiro/?utm_source=chatgpt.com)

## 3. GPU·ML 인프라 | LMCache 0.5.4 — KV Cache가 “GPU 서버의 Cache”에서 Fleet Control Plane으로

LMCache `v0.5.4`는 8월 20일 안정 릴리스됐지만, 이번 주말을 지나면서 architecture 측면에서 특히 볼 가치가 있습니다. 가장 큰 변화는 **MP coordinator가 사실상의 fleet-level KV-cache control plane으로 확장된 것**입니다. Cache event를 별도 ingest 계층에서 받아 fleet controller로 전달하고, L1 tier usage를 중앙에서 추적하며, fleet 상태를 외부 metrics로 내보내는 기능이 들어갔습니다. ([GitHub][4])

더 중요한 변화는 CacheBlend lookup입니다. 이전에는 reusable KV가 현재 node에 있는지를 주로 봤다면, 이제 coordinator의 key directory를 통해 **fleet 어디에 있는 KV cache도 찾아 재사용**할 수 있습니다. Lazy offload와 enqueue-time prefetch도 추가돼 storage·network transfer를 request critical path 밖으로 밀어내는 방향입니다. ([GitHub][4])

이건 LLM serving architecture를 꽤 크게 바꿉니다.

```text
기존:
GPU Worker
 └─ 자신의 KV cache

변화:
GPU Worker A ─┐
GPU Worker B ─┼─ KV Cache Fleet Directory
GPU Worker C ─┘
              ├─ HBM/L1
              ├─ DRAM
              └─ storage
```

즉 KV cache가 allocator 구현 세부사항이 아니라 **분산 데이터 시스템**이 됩니다. Agent session에서는 동일한 system prompt, repository context, tool history가 여러 worker를 이동할 수 있기 때문에 worker-local LRU보다 fleet-wide lookup의 가치가 더 커집니다.

Operator 측에는 prefill/decode disaggregation 지원이 추가됐고, NIXL backend의 transfer-error 복구도 개선됐습니다. Grace-Blackwell GB200/GB300/Thor/Spark용 aarch64 wheel과 외부 device backend plugin도 들어가 hardware surface가 넓어졌습니다. ([GitHub][4])

실무에서는 hit rate 하나만 보면 부족합니다. 적어도 다음을 분리해야 합니다.

```text
local_KV_hit
remote_KV_hit
remote_lookup_latency
bytes_transferred
prefetch_hit
restore_latency
recompute_latency
```

핵심 판단은 “KV가 있느냐”가 아니라 **가져오는 것이 다시 prefill하는 것보다 싼가**입니다. 2K prefix와 200K prefix의 break-even point는 완전히 다릅니다.

주의할 점은 control plane이 커질수록 새로운 장애 모드도 생긴다는 것입니다. Coordinator가 stale key를 반환하거나 network가 흔들리면 cache 최적화가 오히려 TTFT를 악화할 수 있습니다. 따라서 KV fleet에는 cache correctness와 control-plane health를 별도 SLO로 두는 게 좋습니다.

**후속 관찰 포인트:** multi-node remote KV hit의 실제 TTFT 이득, fleet directory consistency, vLLM/SGLang과의 scheduler co-design, heterogeneous GPU/AMD/NVIDIA 환경에서의 KV portability입니다.

**원문:** [GitHub 릴리스 — LMCache v0.5.4](https://github.com/LMCache/LMCache/releases/tag/v0.5.4)

## 4. GPU 연구 | TreeWY — Hybrid Attention의 Speculative Decoding 병목은 KV가 아니라 “Recurrent State 복제”

8월 21일 공개된 **TreeWY**는 Qwen3.5 같은 hybrid architecture의 speculative decoding에서 매우 구체적인 병목을 다룹니다. Gated DeltaNet(GDN) layer는 일반 Transformer처럼 token마다 KV cache가 계속 자라는 대신 작은 recurrent state를 유지합니다. 일반 decoding에서는 메모리 효율적이지만 speculative decoding에서는 draft token을 여러 개 검증한 뒤 reject된 branch를 되돌려야 하므로 **각 draft 위치마다 recurrent state snapshot을 복사**해야 합니다. Tree draft가 넓어질수록 메모리가 급격히 커집니다. ([arXiv][5])

TreeWY는 gated-delta recurrence를 tree-structured WY transform으로 다시 표현합니다. 각 branch마다 full state를 저장하는 대신 작은 pseudo-value matrix를 보존하고, 최종적으로 accept된 branch의 state만 reconstruct합니다. 즉 메모리 복잡도를 “draft node 수 × state snapshot”에서 훨씬 작은 구조로 줄입니다. ([arXiv][5])

Qwen3.5 35B와 397B를 B200에서 평가한 결과, 저자는 **메모리가 실제 병목이 되는 구간에서는 HBM을 풀어 더 많은 request를 동시에 처리할 수 있었고 throughput과 p99 TTFT가 크게 개선**됐다고 보고합니다. 반대로 메모리 여유가 충분한 구간에서는 새로운 reconstruction 계산 때문에 기존 방식보다 몇 % 느릴 수도 있습니다. ([arXiv][5])

이 결과의 핵심은 “TreeWY가 항상 빠르다”가 아닙니다. 오히려 serving benchmark를 다음처럼 봐야 한다는 점입니다.

```text
속도 @ batch=1
```

보다:

```text
throughput @ fixed HBM budget
TTFT @ target concurrency
```

가 더 의미 있습니다. TreeWY는 kernel을 더 빠르게 만드는 기법이 아니라 **메모리 제약 때문에 batch를 키우지 못하던 영역을 열어주는 기법**이기 때문입니다.

또 wider speculative tree가 메모리상 가능해지기는 했지만, 논문은 현재 wide tree가 아직 throughput win은 아니라고 명확히 말합니다. Target이 더 많은 후보 token을 검증해야 하는 비용과 tree kernel 구현 overhead가 남아 있습니다. ([arXiv][6])

Hybrid model이 늘어날수록 serving engine도 단순 `KV cache manager`만으로는 충분하지 않습니다.

```text
Transformer KV
+ recurrent state
+ speculative branch state
+ rollback semantics
```

를 하나의 memory subsystem으로 봐야 합니다.

**후속 관찰 포인트:** SGLang/vLLM upstream 적용, fused graph-capturable tree kernel, Qwen 외 다른 GDN 계열에서의 재현, DSpark/DFlash와 조합했을 때의 concurrency scaling입니다.

**원문:** [논문 — TreeWY: Speculative Verification for Gated DeltaNet Hybrids](https://arxiv.org/abs/2608.20961)

## 5. 필독 | COTA — Agent를 감시하는 모델은 Agent만큼 똑똑할 필요가 없을 수 있다

8월 21일 공개된 **COTA(Comparison-Only Tiny Advisor)**는 runtime intervention의 비용 구조를 바꾸는 아이디어입니다. 기존 agent safety/reliability 시스템에서는 actor가 잘못된 행동을 제안하면 비슷하거나 더 강한 critic에게 “문제가 무엇인지 분석하고 올바른 대안을 작성하라”고 시키는 경우가 많습니다. 즉 동일 task를 사실상 두 모델이 다시 풀게 됩니다. ([arXiv][7])

COTA는 advisor의 역할을 극단적으로 줄입니다. Actor가 행동 A를 제안하면 실행 가능한 대안 몇 개를 만든 뒤 **0.5B comparator는 “A와 B 중 어느 쪽이 이후 trajectory가 더 좋아질 것 같은가?”만 비교**합니다. 여러 대안이 actor proposal을 이기면 실행을 잠시 막고, 가장 좋은 대안을 non-binding hint로 되돌려 actor가 다시 계획하게 합니다. Comparator는 해결책을 생성하지도 않고 task를 독립적으로 풀지도 않습니다. ([arXiv][7])

실험은 Qwen3-8B, Qwen3.6-35B-A3B, DeepSeek-V4-Flash와 WebShop·ALFWorld·τ³-Retail의 9개 조합에서 수행됐고 **모든 조합에서 original actor보다 개선**됐습니다. 예를 들어 Qwen3-8B는 WebShop reward가 0.396→0.563, ALFWorld 성공률이 82.84→90.30%, Retail이 37.5→45.0%로 올랐습니다. Qwen3.6 ALFWorld는 85.07→94.03%, DeepSeek-V4-Flash ALFWorld도 90→95%였습니다. ([arXiv][7])

Online overhead는 전체 episode 시간 기준 평균 **1.38배**, 9개 조건 중 7개는 1.5배 미만이었습니다. 흥미롭게도 일부 조건에서는 intervention 때문에 실패 loop가 줄어 오히려 원래 actor보다 episode 시간이 짧아졌습니다. ([arXiv][7])

이 연구에서 실무적으로 가져갈 수 있는 사고방식은 매우 좋습니다.

```text
고난도 Task
→ 강한 Agent

모든 행동의 검토
→ 또 다른 강한 Agent
```

가 아니라:

```text
강한 Agent
→ action proposal

작은 Advisor
→ A vs B 비교만 수행

의심스러운 경우만
→ Agent 재계획
```

입니다. Reliability layer의 model capacity를 **그 역할에 맞게 최소화**하는 겁니다.

다만 COTA를 deterministic security policy로 착각하면 안 됩니다. 0.5B comparator도 ML model이며 틀릴 수 있습니다. 결제·파일 삭제·production deploy 같은 high-impact action은 여전히 IAM·policy engine·approval 같은 hard guard가 최종 권한을 가져야 합니다. COTA는 “좋지 않은 결정의 빈도를 줄이는 reliability controller”에 더 가깝습니다. 또한 training용 same-prefix counterfactual branch를 만드는 offline 비용도 작지 않습니다.

**후속 관찰 포인트:** 실제 coding/MCP action으로 확장, comparator를 여러 actor에서 공유할 수 있는지, candidate 생성 비용, security policy와 comparator를 함께 사용할 때의 intervention precision입니다.

**원문:** [논문 — Don’t Solve, Just Compare: COTA](https://arxiv.org/abs/2608.21027)

## 6. Agent Skill 연구 | AUSO — “이 Task에 Skill을 쓸까?”가 아니라 “이 Action에 Skill이 도움이 되는가?”

최근 Skill 연구는 “Skill을 넣으면 평균적으로 좋아지는가?”에서 한 단계 더 내려가고 있습니다. **AUSO(Action-Level Unified Skill Optimization)**는 동일 trajectory 안에서도 Skill이 어떤 결정에는 도움이 되고 다른 결정에는 방해가 될 수 있다는 데서 출발합니다. ([arXiv][8])

AUSO는 training lifecycle을 세 단계로 나눕니다. 초기에는 external teacher Skill을 model 내부로 internalize하면서 task reward도 같이 학습하고, 중간에는 autonomous RL 비중을 늘리며, 후반에는 각 sampled action을 **Skill-conditioned와 Skill-free context 양쪽에서 비교**합니다. Skill 때문에 실제로 decision quality가 좋아지는 action은 더 강하게 학습하고, Skill이 방해하는 action은 억제합니다. ([arXiv][8])

Qwen2.5-7B-Instruct를 4×H200에서 같은 rollout·optimization budget으로 비교한 결과, WebShop에서 AUSO는 ID 49.7, OOD 51.2를 기록해 기존 Skill0.5보다 각각 **+9.3, +10.6점** 개선했습니다. ALFWorld에서는 ID 94.3, OOD 67.9를 기록했습니다. Ablation에서는 action-level gate와 Skill utilization/internalization 단계를 제거할 때 성능이 의미 있게 떨어졌습니다. ([arXiv][9])

이 결과가 실제 Skill 시스템에 주는 메시지는 꽤 직접적입니다.

기존 방식:

```text
이 Task가 Python 관련?
→ Python Skill 전체 삽입
```

보다 앞으로는:

```text
현재 Action = 코드 탐색
→ Skill 불필요

현재 Action = packaging
→ packaging Skill 사용

현재 Action = regression verification
→ test Skill 사용
```

처럼 **progressive discovery·action-level Skill loading**이 유리할 수 있습니다.

이건 token 효율 측면에서도 중요합니다. 모든 Skill 문서를 매 turn context에 넣는 방식은 모델이 이미 잘하는 결정에 불필요한 instruction을 추가해 오히려 distraction을 만들 수 있습니다. 최근 “Agent Skills Can Be Harmful” 계열 결과와도 방향이 맞닿습니다.

다만 AUSO는 지금 바로 Agent Plugins에 옵션 하나를 켜는 runtime 기능이 아닙니다. **RL training framework**이며 7B backbone과 세 benchmark에서의 초기 연구입니다. Production에서 Skill ON/OFF를 action마다 판단하려면 먼저 telemetry와 paired evaluation infrastructure가 필요합니다.

**후속 관찰 포인트:** 큰 모델에서 Skill sensitivity 감소 여부, coding Skill로의 확장, inference-time Skill router와 training-time AUSO의 결합, 여러 Skill 간 interaction입니다.

**원문:** [논문 — AUSO: Action-Level Unified Skill Optimization](https://arxiv.org/abs/2608.21292)

## 7. AI 평가 | “판정은 맞았는데 이유는 틀렸다” — LLM Judge에 Counterfactual Receipt를 요구하자는 제안

마지막 연구는 Agent 평가·safety gate를 설계할 때 꽤 중요한 문제를 건드립니다. **No Judgment Without a Reason**은 evaluator가 최종 `ALLOW/DENY`, `PASS/FAIL`을 맞히는 것만으로는 충분하지 않다고 주장합니다. 실제로는 잘못된 evidence나 rule을 사용했는데 우연히 정답 label을 출력할 수 있기 때문입니다. ([arXiv][10])

논문은 판단의 출처를 세 가지로 나눕니다.

```text
Grounds    → 사실·증거
Norms      → 적용할 규칙
Authority  → 이 규칙을 적용할 권한/범위
```

그리고 이 세 요소를 하나씩 또는 조합해서 바꿨을 때 판정이 어떻게 달라지는지를 실제로 실행해 **“어떤 source change가 이 verdict를 바꾸는 데 충분했는가?”라는 최소 counterfactual set**, 즉 judgment receipt를 만듭니다. ([arXiv][11])

ReasonBench는 19,520 case와 7,200 control로 구성됩니다. 표면적으로는 Qwen3-1.7B가 receipt prediction에서 98.41%라는 높은 점수를 냈지만, 의미를 보존한 source permutation을 적용하자 valid receipt recovery가 **54.8% 수준까지 하락**했습니다. 더 심한 경우 simple single-source change로 학습된 모델은 final verdict accuracy를 93.75% 유지하면서도 복잡한 multi-source update의 올바른 receipt는 **7.16%만 복원**했습니다. ([arXiv][10])

즉:

```text
Evaluator accuracy = 94%
```

가 곧:

```text
94%가 올바른 이유로 판단함
```

은 아닙니다.

Agent에서 이 차이는 특히 위험합니다. LLM judge가 “이 PR은 안전하다”고 판정했는데 실제로는 잘못된 policy version을 사용했다면, 지금은 맞더라도 다음 변경에서 실패할 가능성이 높습니다.

실무에서는 LLM-as-a-judge 결과에 최소한 다음 artifact를 붙이는 것이 좋습니다.

```text
verdict
evidence_ids
policy_version
authority_scope
counterfactual_test
```

그리고 중요한 evaluator는 “판정 이유를 자연어로 설명하라”가 아니라 **evidence나 policy 하나를 바꿔 실제 verdict가 예상대로 움직이는지 테스트**하는 편이 더 강합니다. 이 방향은 최근 Anthropic CHIVE가 강조한 counterfactual intervention과도 닿아 있습니다.

주의할 점은 exact counterfactual certification 비용이 source 수와 함께 빠르게 증가한다는 것입니다. 논문도 black-box evaluator에서 모든 조합을 정확하게 인증하는 데 최악의 경우 지수적인 query가 필요함을 보여줍니다. 따라서 production에서는 high-impact action만 강한 certification을 적용하고 저위험 판단은 sampled metamorphic test로 줄이는 식의 tiering이 현실적입니다. ([arXiv][11])

**후속 관찰 포인트:** 코드 리뷰 judge·security judge로 확장, evaluator version upgrade의 regression receipt, human policy와 LLM policy interpretation 차이, counterfactual test 자동 생성입니다.

**원문:** [논문 — No Judgment Without a Reason](https://arxiv.org/abs/2608.20938)

# 오늘의 실습 | “강한 Critic vs 작은 Comparator” Runtime Intervention A/B 테스트

오늘은 COTA 아이디어를 **논문 완전 재현이 아니라 작은 runtime experiment**로 단순화해보는 것을 추천합니다. 별도 RL training 없이도 “모든 검토를 큰 모델에게 맡길 필요가 있는가?”라는 시스템 질문을 확인할 수 있습니다.

먼저 side effect가 없는 mock tool environment를 만들고 20~30개의 task를 준비합니다. 각 state에서 actor에게 **원래 행동 A와 대안 B·C 두 개**를 만들게 하십시오. 예를 들면 file search, repository 탐색, 다음 API 선택처럼 정답을 deterministic하게 검증할 수 있는 작업이 좋습니다.

세 조건을 비교합니다.

```text
A. Actor Only
actor의 첫 action을 그대로 실행

B. Strong Critic
큰 모델이 action을 분석하고
문제점 + 새 action을 생성

C. Small Comparator
작은 0.5B~3B 모델은
A vs B, A vs C 중
어느 쪽이 나은지만 선택
```

작은 comparator에는 해결책을 생성시키지 않습니다. 출력도 다음 정도로 제한하면 됩니다.

```json
{
  "preferred": "B",
  "confidence": 0.82
}
```

두 대안 모두 A보다 낫다고 판단될 때만 원래 actor에게:

> “B 방향이 더 유망하다는 외부 비교 신호가 있다. 다시 계획하라.”

정도의 non-binding feedback을 주십시오.

기록할 지표는 `strict_success`, `interventions`, `correct_interventions`, `harmful_interventions`, `actor_tokens`, `critic_or_comparator_tokens`, `wall_clock`, `cost_per_success`면 충분합니다.

가장 중요한 값은 단순 성공률이 아니라:

```text
Intervention Precision
= 실제 개선을 만든 intervention / 전체 intervention

Success Gain
= success_with_advisor - actor_only

Advisor Cost
= advisor compute / successful task
```

입니다.

예를 들어 결과가:

```text
Actor Only       72%   비용 1.0×

Strong Critic    82%   비용 2.1×

Small Comparator 80%   비용 1.25×
```

처럼 나온다면 comparator는 absolute accuracy에서 critic보다 약간 떨어져도 **성공당 비용 측면에서는 더 좋은 control layer**가 될 수 있습니다.

그리고 한 단계 더 가려면 high-risk action을 하나 넣으십시오. 예를 들어 mock `delete_file()`이나 `deploy()`입니다. 여기서는 comparator 결과와 관계없이 deterministic policy가 최종 승인하게 하십시오.

```text
Actor
 ↓
Comparator     ← reliability
 ↓
Policy Engine  ← authority
 ↓
Tool
```

이 구조를 쓰면 오늘 연구의 핵심도 명확하게 볼 수 있습니다. **작은 모델은 판단 품질을 보조할 수 있지만, 실제 권한을 행사하는 security boundary가 되어서는 안 됩니다.** ([arXiv][7])
