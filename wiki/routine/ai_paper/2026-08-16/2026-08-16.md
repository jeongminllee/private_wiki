## 1. 필독 | GLM‑5.3 — Base model은 그대로인데 post-training만으로 coding·cyber 능력이 급상승

Z.ai가 **8월 14일 GLM‑5.3**을 발표했습니다. 특이한 점은 architecture나 pretraining model을 새로 만든 것이 아니라 **GLM‑5.2와 동일한 base model에서 post-training만 확장했다**는 것입니다. Z.ai 공식 문서는 자사 Code Bench에서 GLM‑5.2 대비 coding 성능이 50% 개선됐다고 주장하며, 현재 1M context, 최대 128K output, function calling, context caching, structured output와 MCP를 지원한다고 설명합니다. 현재 GLM Coding Plan 사용자는 사용할 수 있지만 일반 GLM‑5.3 API는 공식 문서상 “coming soon” 상태입니다. ([Overview - Z.AI DEVELOPER DOCUMENT][2])

Coding 쪽 자체 평가에서는 Terminal-Bench 3.0이 4.6→28.3, DeepSWE 1.1이 46.2→66.9로 증가했다고 Z.ai가 보고했습니다. 회사가 강조하는 변화는 단순 code completion이 아니라 수만 줄의 코드와 수백 개 파일, 여러 subsystem이 얽힌 장기 engineering workflow를 post-training 환경에 넣었다는 것입니다. 이런 결과가 재현된다면 중요한 메시지는 **pretraining compute를 다시 쓰지 않고도 environment-rich RL/post-training을 확장해 agent capability를 크게 올릴 수 있다**는 것입니다. ([Overview - Z.AI DEVELOPER DOCUMENT][2])

Cybersecurity 쪽은 더 눈여겨봐야 합니다. Z.ai 측 CyberGym 결과는 84.5%로 Anthropic Mythos 5의 83.8%와 비슷하지만, 실제 exploit을 요구하는 ExploitBench에서는 **54.4% 대 78.0%**로 여전히 큰 차이가 납니다. 즉 “취약점을 찾는 능력”과 “실제로 exploit chain을 완성하는 능력”을 분리해서 봐야 합니다. Reuters 역시 이 수치들이 Z.ai가 보고한 결과이며 독립 검증된 benchmark 결과가 아니라는 점을 짚고 있습니다. ([Reuters][3])

그리고 중요한 정정이 하나 있습니다. Z.ai는 공식 자료에서 GLM‑5.3을 “open-source/open-weights” 계열로 표현하지만 **8월 16일 현재 GLM‑5.3 weight checkpoint는 아직 공개되지 않았습니다.** Z.ai는 cyber safety assessment 때문에 약 2주 뒤 공개할 계획이며 고위험 capability에는 verified-user 기반 trusted access를 적용할 예정이라고 밝혔습니다. 따라서 지금 정확한 표현은 **“Coding Plan에서 사용 가능하며, open-weight 공개가 예고된 모델”**입니다. 로컬 배포 가능한 open-weight model이라고 부르기에는 아직 이릅니다. ([Reuters][3])

실무적으로는 GLM‑5.2→5.3 비교에서 일반 benchmark보다 같은 repository·same harness·same tool budget을 유지하고 `strict_success`, `tool_calls`, `output_tokens`, `retries`, `wall_clock`, `cost_per_success`를 측정하는 것이 좋습니다. 특히 post-training이 길어진 모델은 benchmark 점수가 좋아져도 과도한 탐색이나 긴 reasoning으로 task당 compute가 늘 수 있으므로 **성공률과 작업량을 분리해서 봐야 합니다.**

**후속 관찰 포인트:** 실제 weight 공개일과 라이선스, API 가격, 공개 checkpoint와 Coding Plan hosted model의 품질 parity, independent Terminal-Bench/DeepSWE 결과, trusted-access의 구체적 capability restriction입니다. ([Overview - Z.AI DEVELOPER DOCUMENT][2])

**원문:** **[공식 발표] GLM‑5.3** ([Z.ai][4]) · **[공식 문서] GLM‑5.3 사양·지원 기능** ([Overview - Z.AI DEVELOPER DOCUMENT][2]) · **[독립 보도] Reuters — weight 공개 지연·cyber 평가 검증** ([Reuters][3])

## 2. 필독 | Qwen3.8‑27B weight 공개 — 27B Dense + Vision + Hybrid Attention + Agent를 한 모델로

Qwen은 **Qwen3.8‑27B의 실제 weight와 configuration을 Apache 2.0으로 공개**했습니다. GLM‑5.3과 달리 이쪽은 지금 바로 checkpoint를 받을 수 있습니다. 모델은 27B dense causal LM에 vision encoder를 결합한 native multimodal model이며 Hugging Face Transformers, vLLM, SGLang, TokenSpeed와 바로 호환됩니다. ([Hugging Face][5])

Architecture가 특히 재미있습니다. 64개 layer를 전부 full attention으로 쌓지 않고,

```text
16 × [
    3 × (Gated DeltaNet → FFN)
    1 × (Gated Attention → FFN)
]
```

구조를 사용합니다. 즉 linear/recurrent 계열의 Gated DeltaNet과 full attention을 섞은 hybrid architecture입니다. MTP(Multi-Token Prediction)도 여러 step으로 학습돼 있습니다. Native context는 **262,144 token**, YaRN 등을 이용해 최대 1M까지 확장하는 구성을 공식적으로 안내합니다. ([Hugging Face][5])

Agent 관점에서 새롭게 볼 부분은 `reasoning_effort`와 `preserve_thinking`입니다. 공식적으로 `low`, `medium`, `xhigh` 세 단계이며 기본값은 `xhigh`입니다. 또한 이전 turn의 reasoning block을 계속 유지하는 `preserve_thinking=True`가 기본값입니다. Qwen은 이것이 multi-turn agent에서 reasoning continuity와 KV-cache 재사용에 도움이 된다고 설명합니다. 반대로 low effort가 한 turn에서는 빨라도 분석 부족→실패→retry가 늘면서 **전체 task completion time이 오히려 길어질 수 있다**는 점도 모델 카드에 명시했습니다. ([Hugging Face][5])

Qwen 자체 agent benchmark에서는 Terminal Bench 2.1 73.0, SWE-bench Pro 61.7, CoWorkBench 70.7을 보고했고, 멀티모달 agent에서는 OSWorld-Verified 84.3, WebArena-Verified 64.8, AndroidWorld 81.9를 제시합니다. 다만 QwenSWEBench·CoWorkBench·RecreationBench 등 일부는 자사 benchmark이며, SWE-bench Pro와 DeepSWE 등은 Claude Code harness를 사용한 자체 재평가입니다. 숫자를 다른 vendor 표와 단순 비교하기보다 **동일 harness 재평가 전의 vendor-reported result**로 보는 것이 맞습니다. ([Hugging Face][5])

실무적으로 꽤 가치 있는 모델입니다. 하나의 27B checkpoint로 text coding, screenshot·document 이해, browser/computer-use perception과 tool calling을 모두 시험할 수 있기 때문입니다. 다만 “1M context 모델”이라고 단순 표기하면 안 됩니다. **native context는 262K이고 1M은 RoPE scaling 확장 경로**입니다. Qwen Cloud의 native production 1M service 역시 모델 카드상 아직 “coming soon”입니다. ([Hugging Face][5])

**후속 관찰 포인트:** quantization별 tool-call regression, DeltaNet state가 장기 agent session에서 실제 memory footprint를 얼마나 줄이는지, MTP serving 지원, `preserve_thinking`이 장기 task의 KV cache와 total tokens에 주는 효과입니다.

**원문:** **[모델 카드·Weight] Qwen3.8‑27B** ([Hugging Face][5])

## 3. GPU·ML 인프라 | CAKE — GPU Kernel Agent에게 CUDA를 쓰게 하는 대신 ‘Compiler 자체’를 Agent 친화적으로 바꾼다

8월 12일 공개된 **CAKE: Compiler-Agent Co-Design for Frontier Kernel Evolution**은 오늘 GPU 쪽에서 가장 볼 가치가 높은 연구입니다. NVIDIA·CMU·University of Washington 연구진 등이 참여했습니다. 기존 GPU coding agent는 CUDA/PTX를 작성하고 compiler에서 “compile error / correctness / latency” 정도만 받아 다시 수정합니다. CAKE는 이 구조 자체가 agent에게 너무 불친절하다고 봅니다. ([arXiv][6])

CAKE는 agent가 직접 **CAKE IR**이라는 typed·hardware-explicit schedule representation을 작성하게 합니다. IR에는 warp 역할, memory movement, synchronization, pipeline 같은 GPU scheduling decision이 명시돼 있으며 compiler는 verifier, cost model과 **문제가 발생한 위치를 훨씬 구체적으로 알려주는 diagnostic**을 제공합니다. ([arXiv][6])

더 흥미로운 부분은 compiler harness도 고정돼 있지 않다는 점입니다.

```text
Agent failure
    ↓
반복되는 실패 패턴 발견
    ↓
Verifier rule 추가
IR primitive 추가
Model calibration
Optimization tactic 추가
    ↓
다음 agent run의 환경 자체 개선
```

즉 모델만 self-improve하는 것이 아니라 **agent가 자주 틀리는 부분을 compiler가 새로운 abstraction으로 흡수**합니다. GPU performance engineering의 암묵지를 system artifact로 누적시키는 접근입니다. ([arXiv][6])

B200의 Flash-KMeans clean-start 실험에서 8천만 token budget으로 탐색했을 때 CAKE IR 최선 후보는 tuned FlashML baseline 대비 **1.144×**, 직접 CUDA/PTX 생성은 0.928×였습니다. 더 큰 실험에서는 agent-generated Kimi Delta Attention kernel이 공식 FlashKDA 대비 geometric mean **2.05×**를 기록하면서 end-to-end serving validation까지 통과했다고 저자들은 보고했습니다. Dispatcher 기반 KNN/KMeans도 400개 이상의 shape에서 1.42~2.12× 개선됐고, 일부 변경은 upstream PR 형태로 제출됐습니다. ([arXiv][6])

이 연구가 중요한 이유는 “LLM이 CUDA를 잘 짠다”가 아닙니다. **AI가 performance engineering을 하게 하려면 인간용 compiler interface가 아닌 agent용 compiler interface가 필요할 수 있다**는 것입니다. 앞으로 Triton/CuTe/MLIR 계열에서도 compiler diagnostic, structured schedule space와 profile feedback을 agent가 직접 탐색할 수 있도록 설계하는 흐름이 커질 가능성이 있습니다.

다만 8천만 token search budget은 상당한 compute입니다. 1.144×라는 결과만 보면 사람이 직접 최적화하는 편이 경제적일 수도 있습니다. 따라서 실제 생산성은 `best_kernel_speedup`보다 **agent search compute + human engineer time + kernel 재사용 범위**까지 포함해서 판단해야 합니다. 또한 KDA 2.05×는 특정 kernel·shape 분포의 결과이며 일반적인 LLM inference가 2배 빨라졌다는 의미는 아닙니다. ([arXiv][6])

**후속 관찰 포인트:** CAKE IR 공개와 compiler maturity, FlashAttention/MoE kernel로의 확장, agent search token budget 대비 실제 GPU-hour 절감, 새로운 GPU architecture에 기존 optimization knowledge가 얼마나 전이되는지입니다.

**원문:** **[논문] CAKE: Compiler-Agent Co-Design for Frontier Kernel Evolution** ([arXiv][6])

## 4. 개발 도구 | Qwen Code 0.21.12 — AI Code Review가 ‘그럴듯한 지적’에서 Evidence-backed Review로

Qwen Code가 **8월 14일 v0.21.12**를 stable로 공개했습니다. 이번 릴리스는 새 모델보다 agentic code-review runtime이 어떻게 변하고 있는지를 보는 게 더 흥미롭습니다. ([GitHub][7])

가장 중요한 변화는 **Critical finding을 확정하려면 실제로 실행한 witness와 관측한 output이 필요해졌다는 점**입니다. 실행 증거가 없는 주장에는 low confidence를 붙이고 PR post에서도 숨깁니다. Review ledger에는 기준 commit SHA를 넣어 “어느 commit까지 실제로 검토했는가”를 추적하며, 이후 변경된 code range를 과거 리뷰 결과로 잘못 인증하지 않도록 했습니다. ([GitHub][7])

Autofix에도 hard budget이 생겼습니다. Source/test line 증가량을 window별로 제한하는 **diff growth brake**가 추가됐고, 여러 round에 걸쳐 budget을 계속 초과하면 agent가 계속 patch를 키우는 대신 maintainer에게 escalation합니다. 이는 coding agent의 흔한 failure mode인:

```text
작은 bug
→ helper 추가
→ wrapper 추가
→ test infrastructure 추가
→ 300줄짜리 “수정”
```

를 runtime에서 막는 구조입니다. ([GitHub][7])

Observability도 강화됐습니다. OpenTelemetry trace/span ID, main-agent의 OTel-compatible trace, agent별 JSONL transcript에 prompt·tool call·result를 기록할 수 있습니다. 동시에 concurrent code review끼리 verdict를 overwrite하지 않도록 isolation을 추가했고 cross-worktree Git mutation도 차단합니다. ([GitHub][7])

이 접근은 production code-review agent에 바로 참고할 만합니다. Severity를 model confidence만으로 판정하지 말고:

```text
claim
→ reproducer
→ executed witness
→ observed result
→ affected commit
→ severity
```

순서로 artifact를 만드는 것입니다.

다만 “실행 가능한 witness가 없는 보안 문제”도 있습니다. Race condition, architecture-level authorization flaw, 정보 흐름 문제처럼 안전한 재현이 어렵거나 exploit을 직접 실행하기 부적절한 취약점까지 낮은 confidence로 묻히면 안 됩니다. 따라서 **dynamic witness와 static evidence를 별도 evidence class로 관리**하는 편이 좋습니다.

또 JSONL transcript와 OTel에 prompt·tool 결과를 저장하면 source code, credential, proprietary data가 telemetry backend로 유출될 수 있습니다. Observability를 켜는 것과 모든 payload를 기록하는 것은 분리해야 합니다. ([GitHub][7])

**후속 관찰 포인트:** witness sandboxing, static-only vulnerability의 evidence 정책, diff-growth budget과 fix success의 관계, OTel agent semantic convention 정착입니다.

**원문:** **[GitHub 릴리스] Qwen Code v0.21.12** ([GitHub][7])

## 5. ML 인프라 | The Embedder’s Dilemma — LLM이 Embedding보다 조금 좋아도 최대 1,431배 비쌀 수 있다

COLM 2026 채택 논문 **The Embedder’s Dilemma**는 “RAG에서 embedding model을 그냥 LLM으로 대체하면 더 좋아지지 않을까?”라는 질문을 매우 실용적으로 검증했습니다. 6개 family의 LLM 10개와 118M~14B의 embedding model 26개를 classification, STS, clustering, pair classification, retrieval을 포함한 **37개 task**에서 비교했습니다. ([arXiv][8])

흥미로운 결과는 성능 차이가 생각보다 작다는 것입니다. 전체 평균 최고 LLM은 Gemini 3.1 Pro 77.6, 최고 embedding model은 77.2로 **0.4점 차이**였습니다. LLM은 reasoning-heavy retrieval에서 강했고 embedding model은 classification에서 강했으며 clustering·STS·pair classification은 비슷했습니다. ([arXiv][8])

그런데 비용은 완전히 다릅니다. 동급 quality 조건에서 LLM은 benchmark 전체 pass 기준 최대 **$154 대 $0.11, 1,431배** 비쌌고, open LLM도 같은 GPU에서 embedding model 대비 2.5~736배 느렸습니다. LLM inference cost의 28~81%가 reasoning token이었으며 reasoning budget을 낮춰도 대부분의 retrieval 설정에서는 성능이 유지되거나 오히려 좋아졌습니다. ([arXiv][8])

이 결과에서 추천할 수 있는 architecture는 “LLM retrieval로 전환”보다 **cascade**입니다.

```text
전체 corpus
    ↓
Embedding model
cheap candidate retrieval
    ↓
top-k ambiguous / reasoning-heavy only
    ↓
LLM semantic reasoning / rerank
```

예를 들어 1,000만 문서 전체를 LLM으로 처리하는 대신 embedding을 first stage로 유지하고 **실제로 관계 추론이 필요한 query만 LLM으로 올리는 구조**입니다. Model router와 같은 생각을 retrieval pipeline에 적용하는 셈입니다.

평가할 때는 `NDCG@10` 하나가 아니라 `recall@k`, `GPU seconds/query`, `$ / 1K queries`, `index build cost`, `P95 latency`를 함께 봐야 합니다. 특히 embedding은 corpus representation을 한 번 계산해 재사용할 수 있다는 점 때문에 반복 query가 많은 실제 서비스에서는 논문의 단일 benchmark-pass 차이보다 비용 차이가 더 커질 수도 있습니다. 이 부분은 논문 결과에서 이어지는 시스템적 추론입니다. ([arXiv][8])

반대로 가격은 빠르게 변하므로 `$154 vs $0.11`을 영구적인 경제성으로 볼 수는 없습니다. API 가격·batch discount·cache·hardware에 따라 절대 비용은 달라집니다. 핵심은 **현재 품질 parity를 얻기 위해 요구되는 compute gap이 매우 크다**는 것입니다.

**후속 관찰 포인트:** reasoning-aware query router, LLM reranker와 cross-encoder 비교, multimodal retrieval에서도 같은 pattern이 유지되는지입니다.

**원문:** **[논문] The Embedder’s Dilemma: LLMs Are Better, but at What Cost?** ([arXiv][8])

## 6. Agent Memory | RippleMem — Memory 검색을 top‑k 한 번으로 끝내지 말고 ‘연상 회상’으로

8월 13일 공개된 **RippleMem**은 장기 agent memory의 문제가 저장 용량보다 **분산된 증거를 어떻게 다시 조립할 것인가**라고 봅니다. Full-context 방식은 noise가 많고, 일반 vector retrieval은 서로 떨어진 memory 가운데 query와 직접 닮은 몇 개만 가져오며, 기존 graph memory는 graph 구축 비용이 클 수 있습니다. ([arXiv][9])

RippleMem은 interaction history를 cue-rich episodic memory unit으로 저장한 뒤 event-centric graph를 구성합니다. Query가 들어오면 바로 모든 답을 찾으려 하지 않습니다.

```text
Query
  ↓
Hybrid retrieval
  ↓
Memory anchor 발견
  ↓
anchor와 연결된
semantic + structural edge 탐색
  ↓
누락된 evidence 회수
```

즉 첫 retrieval 결과를 **answer context가 아니라 다음 retrieval의 cue**로도 사용합니다. 사람의 episodic recollection과 비슷한 형태입니다. ([arXiv][9])

저자 실험에서는 LoCoMo의 LLM-as-a-Judge accuracy가 3.95% 개선됐고 LongMemEval-S에서는 최대 11.87% 향상됐으며, 비교 대상 graph memory 대비 graph construction cost를 약 30배 낮췄다고 보고했습니다. ([arXiv][9])

실무에서는 기존 vector DB를 버릴 필요가 없습니다. 먼저 다음처럼 작은 확장을 해볼 수 있습니다.

```text
Dense / BM25 top-k
        ↓
Anchor 3개
        ↓
각 anchor에서
entity / time / task / artifact edge
1~2 hop만 expansion
        ↓
final evidence
```

중요한 것은 expansion에 hard budget을 두는 것입니다. `max_hops`, `max_nodes`, `max_tokens`, `max_latency`를 제한하지 않으면 graph retrieval이 또 하나의 agent search explosion이 될 수 있습니다.

보안도 생각해야 합니다. 잘못된 memory 하나가 anchor로 잡히면 graph expansion을 통해 관련 memory까지 광범위하게 끌고 올 수 있기 때문에 **edge마다 provenance·trust level을 유지하는 것**이 좋습니다.

30배 수치는 **graph construction cost**이지 query latency가 30배 빨라졌다는 뜻이 아닙니다. 또한 LoCoMo의 주요 결과는 LLM judge에 의존하므로 독립적인 실제 업무 memory에서의 검증이 필요합니다. ([arXiv][9])

**후속 관찰 포인트:** dynamic graph update 비용, poisoned anchor 전파 문제, time/version aware edges, code-agent repository memory 적용입니다.

**원문:** **[논문] RippleMem: From Isolated Retrieval to Associative Recollection for Long-Term Agent Memory** ([arXiv][9])

## 7. AI 보안·FinOps | Convergent Detour Hijacking — 결과는 맞는데 돈과 시간이 2배 가까이 든다

Agent Skill 보안에서 상당히 흥미로운 공격이 나왔습니다. **Convergent Detour Hijacking(CDH)**은 agent에게 악의적인 최종 행동을 시키지 않습니다. 오히려 **사용자의 task는 정상적으로 완료시키면서 중간에 불필요한 Skill·Tool을 잔뜩 호출하게 만듭니다.** ([arXiv][10])

Skill-based agent는 보통 description을 보고 사용할 Skill을 고른 뒤 본문 instruction을 읽어 workflow를 계획합니다. CDH는 이 두 단계를 같이 공격합니다. Skill description에는 “이 작업과 관련 있다”는 자연스러운 이유를 넣고, 본문에서는 그 이유를 이용해 다른 정상 Skill들이 꼭 필요한 dependency인 것처럼 꾸며 **불필요한 detour**를 만듭니다. 마지막에는 원래 경로로 돌아와 task를 성공시키기 때문에 final-answer 기반 보안 검사는 공격을 발견하기 어렵습니다. ([arXiv][10])

491개 held-out task에서 DeepSeek-V4-Pro 기준 공격자 coordinator Skill이 **80.02%** 선택됐고, 해당 coordinator가 선택된 뒤 작업까지 완료된 run에서는 token 사용량이 66.91%, end-to-end execution time이 **92.45% 증가**했습니다. 그런데 전체 task completion은 비슷했습니다. ([arXiv][10])

즉 기존 안전 지표:

```text
task success = true
harmful action = false
```

만 보면 정상입니다.

하지만 운영 관점에서는:

```text
정답은 같음
API bill +67%
latency +92%
```

인 **denial-of-wallet / resource amplification attack**입니다.

Skill marketplace나 Agent Plugin을 도입한다면 Skill별로 다음을 기록해야 합니다.

```text
selected_skill
publisher
declared_dependencies
actual_dependencies
tool_calls
tokens
wall_clock
fan_out
```

그리고 runtime에 `max_skill_depth`, `max_fanout`, `max_task_tokens`, `max_wall_clock` 같은 hard limit을 두는 편이 좋습니다. 특히 third-party Skill이 또 다른 Skill을 동적으로 선택할 수 있다면 dependency graph를 무제한으로 허용하지 않는 것이 중요합니다.

물론 연구가 만든 threat model에서 나온 결과이므로 “실제 Skill marketplace의 80%가 공격된다”는 의미는 아닙니다. 또한 너무 작은 hard budget은 legitimate complex workflow를 끊을 수 있습니다. 따라서 absolute limit뿐 아니라 **baseline 대비 비정상적인 work amplification**을 탐지하는 방식도 필요합니다. ([arXiv][10])

**후속 관찰 포인트:** Agent Plugins marketplace에서의 dependency provenance, signed Skill manifest, token-budget-aware authorization, multi-agent delegation과 결합된 amplification입니다.

**원문:** **[논문] Convergent Detour Hijacking** ([arXiv][10])

## 8. MLOps | AgentCore Observability — AWS 밖의 Agent도 OpenTelemetry 한 규약으로 관측

AWS는 8월 13일 **on-premises, GCP, Azure 등 AWS 외부에서 실행되는 agent를 AgentCore Observability로 보내는 공식 패턴**을 공개했습니다. 핵심은 Agent framework마다 별도 proprietary logger를 만드는 대신 **OpenTelemetry의 Generative AI semantic convention**을 사용하는 것입니다. ([Amazon Web Services, Inc.][11])

예제에서는 ADOT(AWS Distro for OpenTelemetry)을 agent Python process에 auto-instrumentation하고 다음 정보를 OTLP로 전송합니다.

```text
session
agent reasoning span
model call
token usage
tool invocation
trace / span
```

AWS 밖에서 실행되는 agent도 SigV4로 CloudWatch OTLP endpoint에 보내면 AgentCore의 session·trace·span dashboard에서 함께 볼 수 있습니다. AWS는 on-premise와 GCP 환경에서 이 구성을 검증했다고 설명합니다. ([Amazon Web Services, Inc.][11])

중요한 것은 Agent MLOps의 공통 데이터 모델이 생기고 있다는 점입니다. 앞으로 특정 agent framework에 종속되지 않고:

```text
service.name
session.id
model
tool
tokens
latency
status
```

같은 공통 telemetry를 수집하면 Claude Code, 자체 LangGraph agent, local model agent를 같은 dashboard에서 비교할 수 있습니다.

AWS 예제에서 더 주의해서 볼 부분은 credential입니다. Tutorial은 편의를 위해 access key를 환경 변수에 두지만 AWS도 **production에서는 장기 access key 대신 IAM Roles Anywhere를 사용하라**고 명시합니다. 또한 외부 agent가 CloudWatch endpoint에 접근할 outbound HTTPS가 필요하기 때문에 air-gapped 환경용 구조는 아닙니다. ([Amazon Web Services, Inc.][11])

그리고 observability가 오히려 새로운 정보 유출 경로가 될 수 있습니다. Reasoning, model output, tool result를 중앙 수집한다면 source code, customer data와 credential까지 log에 섞일 수 있습니다. 따라서 production에서는:

```text
trace metadata → 항상 수집
token counts   → 항상 수집
prompt/output  → default redacted
tool payload   → schema별 필터
full trace     → sampled / incident only
```

처럼 payload와 metadata sampling을 분리하는 편이 안전합니다.

AWS backend를 사용할 필요는 없습니다. 더 큰 의미는 **Agent trace를 OpenTelemetry semantic convention으로 맞추면 instrumentation과 storage backend를 분리할 수 있다**는 것입니다. AgentCore/CloudWatch는 이 패턴의 한 구현입니다. ([Amazon Web Services, Inc.][11])

**후속 관찰 포인트:** agent OTel semantic convention의 안정화, 여러 agent runtime 간 span naming 일치, GPU trace와 agent trace 통합, privacy-preserving telemetry입니다.

**원문:** **[AWS 공식 기술 가이드] Monitor on-premises and multi-cloud AI agents with AgentCore Observability** ([Amazon Web Services, Inc.][11])

# 오늘 꼭 볼 것 3개

**1. GLM‑5.3.** 오늘 가장 큰 모델 뉴스입니다. 핵심은 “새 base model”이 아니라 **같은 base model에 real-world long-horizon post-training을 더 밀어붙여 coding과 cyber capability가 얼마나 달라질 수 있는가**입니다. 동시에 weight 공개를 약 2주 늦췄다는 사실까지 같이 봐야 합니다. ([Overview - Z.AI DEVELOPER DOCUMENT][2])

**2. CAKE.** GPU·ML infrastructure 관점에서는 오늘 가장 추천합니다. LLM에게 CUDA를 잘 쓰게 가르치는 것보다 **compiler/IR 자체를 agent가 탐색하기 쉽게 공동 설계한다**는 방향은 향후 ML kernel 자동화에서 상당히 중요한 아이디어가 될 수 있습니다. ([arXiv][6])

**3. Convergent Detour Hijacking.** Agent safety를 정확한 final answer나 데이터 유출 여부만으로 보면 놓치는 문제가 있습니다. **결과를 그대로 유지하면서 compute·API 비용만 증폭시키는 공격**이 가능하다는 점에서 Skill/Plugin 생태계를 운영한다면 꼭 읽어볼 만합니다. ([arXiv][10])

# 오늘의 실습 | Qwen3.8‑27B의 `reasoning_effort × preserve_thinking` 직접 측정하기

오늘은 막 공개된 Qwen3.8‑27B가 정말 좋은 실험 대상입니다. 모델 카드에서 **“low effort가 per-turn은 빠르지만 retry가 늘어 전체 agent 시간이 더 길어질 수도 있다”**고 직접 경고하고 있기 때문에 이를 재현해보면 agent serving 감각을 얻기 좋습니다. ([Hugging Face][5])

먼저 vLLM 또는 SGLang으로 동일 checkpoint를 띄웁니다. 두 serving 경로 모두 공식 model card가 지원합니다. ([Hugging Face][5])

```bash
vllm serve Qwen/Qwen3.8-27B
```

그다음 10~20개의 작은 coding/tool task를 준비하고 네 조건을 비교합니다.

| 조건 | reasoning_effort | preserve_thinking |
| -- | ---------------- | ----------------- |
| A  | low              | true              |
| B  | medium           | true              |
| C  | xhigh            | true              |
| D  | medium           | false             |

한 번의 QA로 끝내지 말고 최소 4~6 turn짜리 task를 쓰는 것이 핵심입니다.

예를 들어:

```text
1. repository 구조 파악
2. bug 원인 찾기
3. 수정 계획
4. 코드 수정
5. test 결과 전달
6. 실패하면 재수정
```

각 run에서 다음을 기록합니다.

```text
strict_success

TTFT
wall_clock

reasoning_tokens
output_tokens
total_tokens

tool_calls
failed_tool_calls
retry_count

context_tokens_per_turn
KV_cache_hit_rate     # server에서 노출 가능하면
```

여기서 보고 싶은 값은 `xhigh가 제일 정확한가?`만이 아닙니다.

```text
tokens_per_success
wall_clock_per_success
retries_per_success
```

를 계산하십시오.

예를 들어 결과가:

```text
low
1 turn은 빠름
→ 분석 부족
→ test 실패
→ 3회 재시도
→ 총 9,000 tokens

medium
조금 느림
→ 한 번에 성공
→ 총 5,500 tokens
```

이라면 **reasoning을 줄였는데 오히려 compute를 더 쓴 것**입니다.

`preserve_thinking=False` 조건에서는 이전 reasoning을 버린 대가로 context는 작아질 수 있지만 agent가 이미 검토했던 원인을 다시 분석하는지 확인하면 됩니다. 반대로 `True`에서는 context가 계속 커지는 비용과 KV cache reuse 이득을 함께 측정하십시오. Qwen은 preserved thinking이 reasoning continuity와 KV-cache utilization에 도움이 된다고 주장하지만, 실제 최적점은 task·runtime별로 달라질 수 있습니다. ([Hugging Face][5])

최종적으로 아래 그래프 하나를 그리면 상당히 좋은 실험이 됩니다.

```text
X축: 평균 task 비용 또는 total tokens
Y축: strict success rate

각 점:
low / medium / xhigh /
medium-no-preserve
```

좋은 설정은 가장 많이 생각하는 설정도, 가장 적게 생각하는 설정도 아니라 **Pareto frontier에 있는 설정**입니다.

이 실험은 이후 GLM‑5.3, Nemotron, Gemini Flash 같은 모델에도 동일 harness를 적용할 수 있습니다. 그렇게 되면 vendor benchmark가 아니라 **자신의 workload에서 reasoning budget·memory policy·model choice를 비교하는 작은 Agent Systems Benchmark**가 됩니다. ([Hugging Face][5])
