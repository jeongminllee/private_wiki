## 오늘의 핵심 흐름

오늘은 세 가지 변화가 중요합니다.

첫째, DeepSeek-V4-Flash와 MiniMax H3처럼 **오픈 모델이 에이전트와 옴니모달 생성 영역으로 빠르게 확장**되고 있습니다. 둘째, FlashInfer는 MoE 통신·연산 융합과 JIT 캐시를 통해 Blackwell 추론 스택을 더욱 구체화했습니다. 셋째, 최신 평가 연구들은 모델이 도구나 중간 이미지를 사용한다는 사실보다 **실제로 그 정보를 신뢰성 있게 이용하고, 입력이 없을 때 중단하는지**를 검사해야 한다고 지적합니다.

## 1. 필독 | DeepSeek-V4-Flash-0731 정식 모델 공개

### 무엇이 바뀌었나

DeepSeek는 7월 31일 `DeepSeek-V4-Flash-0731`을 공개했습니다. 기존 Flash Preview를 대체하는 공식 버전으로, 304B 규모의 가중치가 MIT 라이선스로 배포됐습니다. 체크포인트 내부에는 별도 draft 모델 없이 speculative decoding을 수행하는 DSpark 모듈이 포함돼 있습니다. ([Hugging Face][1])

DeepSeek가 공개한 자체 평가에서 0731 버전은 Terminal Bench 2.1 82.7, NL2Repo 54.2, DeepSWE 54.4, Toolathlon-Verified 70.3을 기록했습니다. 모든 항목에서 이전 Flash Preview를 크게 앞섰고 일부 항목에서는 V4-Pro Preview도 넘어섰습니다. 다만 코드 에이전트 평가는 아직 공개되지 않은 DeepSeek Harness의 `minimal mode`, 최대 reasoning effort를 사용했습니다. ([Hugging Face][1])

### 왜 중요한가

이번 변화는 모델 구조를 키운 결과라기보다 **post-training과 agent harness 최적화의 효과**에 가깝습니다. 동일 계열 모델이 도구 사용, 저장소 수정, 장기 작업에서 크게 개선됐다는 것은 앞으로 에이전트 모델 경쟁이 다음 요소에 의해 좌우될 가능성이 크다는 뜻입니다.

* 실행 가능한 환경에서 수집한 trajectory
* 도구 호출 및 결과 검증 학습
* reasoning effort 제어
* speculative decoding과 모델 학습의 공동 설계
* 모델별 메시지 인코딩·파싱 규약

### 실무 적용

주의할 부분은 일반적인 Hugging Face chat model과 사용법이 다르다는 점입니다. 모델 카드에는 Jinja chat template가 없으며, 전용 `encoding` 코드로 OpenAI 형식 메시지를 직렬화하고 결과를 파싱하도록 안내돼 있습니다. `reasoning_content`를 포함한 이전 assistant 메시지도 올바르게 보존해야 합니다. ([Hugging Face][1])

공식 vLLM 예시는 4×GB300에서 Expert Parallel과 FP8 KV cache를 사용하며, SGLang 예시는 TP4, FlashInfer MXFP4 MoE와 DSpark를 결합합니다. 보유한 B200 환경에서 평가한다면 우선 네 장으로 공식 TP4 구성을 최대한 재현하고, 나머지 한 장은 load generator나 judge model에 사용하는 실험 구성이 비교하기 쉽습니다. 다만 GB300 레시피를 B200에 그대로 적용할 수 있다고 가정하지 말고 peak VRAM, kernel 선택과 Expert Parallel 통신량을 다시 측정해야 합니다. ([Hugging Face][1])

### 주의할 점

공개 벤치마크 일부는 내부 데이터셋이며, 비교 모델마다 agent harness와 reasoning budget이 완전히 동일하다고 보기 어렵습니다. 따라서 모델 자체를 평가하려면 동일한 저장소, 동일한 tool schema, 동일한 최대 토큰·시간 제한으로 다시 측정해야 합니다. ([Hugging Face][1])

**후속 관찰 포인트:** DeepSeek Harness 공개 여부, 반복 실행 `Pass^k`, DSpark의 동시성별 이득, vLLM·SGLang 간 tool-call parser 일치성.

## 2. 필독 | FlashInfer 0.6.16: MoE 통신과 연산을 하나의 커널로

### 무엇이 바뀌었나

FlashInfer `v0.6.16` 정식 버전이 7월 31일 공개됐습니다. 핵심은 Blackwell 기반 Expert Parallel을 위한 **MegaMoE 커널**, 통합 MoE API, JIT 디스크 캐시와 Confidential Computing 환경 지원입니다. ([GitHub][3])

`MoEEpLayer`에는 `deep_gemm_mega`, `nvfp4_cutedsl`, `mxfp8_cutedsl` backend가 추가됐습니다. 이 경로들은 expert 간 통신과 로컬 MoE 연산을 symmetric-memory kernel 안에서 융합합니다. 프로젝트 측 GB200·EP4 microbenchmark에서는 NVFP4 CuTeDSL 경로가 토큰 8,192개/rank 조건에서 `deep_gemm_mega`보다 최대 1.89배 높은 처리량을 기록했습니다. ([GitHub][3])

### 왜 중요한가

MoE 추론에서 병목은 expert GEMM만이 아닙니다.

```text
라우팅
→ 토큰 dispatch
→ 원격 expert 전달
→ expert GEMM
→ 결과 combine
```

이 단계들이 별도의 kernel과 collective로 실행되면 작은 동기화 비용과 메모리 이동이 누적됩니다. MegaMoE는 통신과 계산을 융합해 intermediate buffer, kernel launch와 synchronization을 줄이는 방향입니다.

### 추가로 주목할 변화

CuTe-DSL 커널 결과를 디스크에 보존해 새 프로세스에서 다시 컴파일하지 않고 약 3~30ms에 로드할 수 있게 됐습니다. 불필요한 architecture code도 제거해 CUDA 13 aarch64 JIT-cache wheel 설치 크기를 약 1.6GB 줄였다고 프로젝트는 설명합니다. ([GitHub][3])

Confidential Computing에서는 `cuMulticast`에 의존하지 않는 AllReduce fusion 경로가 추가됐으며, activation을 FP8로 양자화한 뒤 전송해 AllReduce 데이터량을 줄이는 API도 들어갔습니다. ([GitHub][3])

### 실무 적용

업그레이드 시 다음 지표를 반드시 함께 기록하는 것이 좋습니다.

```text
selected_moe_backend
tokens_per_rank
expert_load_imbalance
dispatch_time
local_gemm_time
combine_time
all_reduce_bytes
jit_compile_time
jit_cache_hit
numerical_error_vs_bf16
```

B200은 SM100 계열이므로 MegaMoE와 FP4·FP8 경로가 직접적인 평가 대상입니다. 반면 이번 릴리스의 MiniMax Sparse Attention 지원은 주로 Blackwell RTX와 DGX Spark의 SM120/121 경로이므로 B200에서 같은 kernel이 선택된다고 가정하면 안 됩니다. ([GitHub][3])

### 주의할 점

1.89배는 특정 GB200·DeepSeek-V3 유사 geometry의 microbenchmark입니다. 실제 서비스에서는 라우팅 불균형, 작은 batch, 네트워크 topology와 KV cache가 전체 처리량을 제한할 수 있습니다.

또한 FP4 scale 처리, routing consistency와 out-of-bounds read 관련 수정이 함께 포함됐습니다. 속도만 비교하지 말고 기준 BF16 출력과 expert별 오차 분포를 확인해야 합니다. ([GitHub][3])

**후속 관찰 포인트:** vLLM·SGLang의 기본 backend 변경, B200 다중 노드 EP 성능, JIT cache의 container·node 간 재사용, FP8 AllReduce의 모델 품질 영향.

**원문**

* **[GitHub 릴리스]** FlashInfer v0.6.16 전체 변경 사항. ([GitHub][3])
* **[GitHub]** FlashInfer 프로젝트와 지원 kernel 범위. ([GitHub][4])

## 3. 멀티모달 | MiniMax H3: 텍스트·이미지·영상·음성을 하나의 생성 모델로

### 무엇이 바뀌었나

MiniMax는 7월 31일 범용 멀티모달 생성 모델 H3를 발표했습니다. H3는 텍스트, 이미지, 영상과 음성을 함께 입력받아 최대 15초, 2K 해상도, native stereo sound가 포함된 영상을 생성합니다. 이미지·영상 reference, motion transfer와 영상 편집도 하나의 자연어 interface로 처리하는 방향입니다. ([MiniMax][5])

공식 CLI에는 이미 `MiniMax-H3` API를 호출하는 기능이 추가됐습니다. 텍스트-영상, 시작 이미지, reference image·video를 입력할 수 있으며 기본값은 2K·5초·16:9입니다. ([GitHub][6])

### 왜 중요한가

기존 생성 파이프라인은 보통 작업별 모델을 이어 붙였습니다.

```text
이미지 생성
→ 영상 생성
→ 립싱크
→ 음성·효과음
→ 편집
```

H3가 주장하는 방향은 이 경계를 제거하고 이미지·영상·오디오 관계를 하나의 context로 해석하는 것입니다. 실제로 안정적으로 동작한다면 여러 모델 사이에서 identity, camera motion와 timing이 어긋나는 문제를 줄일 가능성이 있습니다.

### 실무 적용

광고나 제품 영상에 적용하려면 단순 영상 품질 외에 다음을 평가해야 합니다.

* reference character identity 유지율
* 브랜드명·제품 문구의 정확성
* 음성과 입 모양의 시간 정렬
* stereo sound의 공간적 일관성
* frame 간 제품 형태 변형
* 동일 prompt 반복 시 결과 분산
* 생성 시간과 초당 비용
* 수정 요청 후 보존되는 요소와 변경되는 요소

### 반드시 구분해야 할 점

공식 발표 제목은 “Open Model”이지만, 8월 3일 현재 공식 발표는 가중치를 **향후 며칠 내 공개할 계획**이라고 표현합니다. 현재 확인 가능한 공식 구현은 API·CLI 사용 경로이며, 로컬에서 다운로드할 H3 weight repository는 아직 별도로 확인되지 않습니다. ([MiniMax][5])

MiniMax는 2K 초당 가격이 주요 경쟁 모델의 3분의 1 미만이라고 주장하지만 구체적인 비교 모델, 동일 품질 조건과 전체 재생성 비용은 공식 설명에 충분히 제시되지 않았습니다. 공급사 가격·성능 주장으로 보고 실제 workload로 재측정해야 합니다. ([MiniMax][5])

**후속 관찰 포인트:** 실제 가중치 공개일, 라이선스, 필요한 VRAM, 중국산 가속기 지원 범위, API와 공개 weight의 품질 차이.

## 4. AI 보안 | GPT-Red: 공격자와 방어자를 함께 학습하는 prompt-injection self-play

### 무엇이 바뀌었나

GPT-Red는 다양한 defender agent를 동시에 학습시키면서 공격 모델이 새로운 prompt injection을 발견하도록 하는 self-play 시스템입니다. 연구진은 일부 대규모 RL post-training과 비슷한 규모의 compute를 사용했으며, GPT-Red를 이용해 GPT-5.6을 adversarial training했다고 설명합니다. ([arXiv][7])

저자 측 평가에서 GPT-Red는 이전 GPT 모델들을 안정적으로 공격했고, 보지 않은 환경·defender·agent harness로도 전이됐으며, 특정 indirect prompt-injection 평가에서는 인간 red team보다 더 많은 성공적인 공격을 찾았습니다. ([arXiv][7])

### 왜 중요한가

정적인 jailbreak prompt 목록은 모델이 한 번 학습하고 나면 빠르게 포화됩니다. Self-play는 defender가 개선될수록 공격자에게 더 어려운 학습 신호를 제공하고, 새 공격자가 다시 defender를 강화하는 구조입니다.

```text
Attacker 생성
→ Defender 공격
→ 성공 trajectory 수집
→ Defender 강화
→ 더 강한 Attacker 학습
```

이 방식은 단순 채팅 jailbreak보다 도구, 웹 문서, 이메일과 검색 결과를 통해 들어오는 **indirect prompt injection** 평가에 특히 중요합니다.

### 실무 적용

사내 에이전트 red-team harness를 만든다면 공격 prompt만 저장하지 말고 다음을 versioning해야 합니다.

* 공격이 삽입된 데이터 출처
* 에이전트가 사용한 도구와 권한
* 공격 성공의 정확한 side effect
* defender·system prompt·policy version
* tool output과 memory에 전파된 경로
* 공격 성공까지 필요한 turn 수
* 동일 공격의 반복 성공률

Defender를 학습하거나 prompt를 수정한 뒤에는 기존 공격뿐 아니라 다른 도구·문서 형식·agent framework에 대한 transfer test도 수행해야 합니다.

### 주의할 점

GPT-Red 자체는 공개 모델이 아니며, training environment와 production defense의 세부 구현도 전부 공개된 것은 아닙니다. “사람보다 강한 red team”이라는 결과를 모든 보안 영역으로 일반화하면 안 됩니다. 비교 대상은 특정 prompt-injection 환경입니다. ([arXiv][7])

**후속 관찰 포인트:** 공격 데이터 공개 범위, open-weight 공격 모델 재현, tool side-effect 평가, self-play가 특정 defender에 과적합되는지 여부.

**원문**

* **[논문]** GPT-Red: Automated Red Teaming via Self-Play at Scale. ([arXiv][7])
* **[공식 연구 발표]** GPT-Red의 held-out 환경과 인간 red team 비교. ([OpenAI][8])

## 5. 머신러닝 연구 | Raven: 매 토큰이 전체 메모리를 덮어쓰지 않는 선형 모델

### 무엇이 바뀌었나

Raven은 고정된 memory slot 집합을 유지하면서 매 토큰마다 전체 state가 아니라 **선택된 일부 slot만 감쇠·갱신**하는 sparse memory routing 구조를 제안합니다. ([arXiv][9])

기존 SSM과 linear Transformer는 새 토큰이 들어올 때 전체 상태를 조밀하게 갱신해 오래된 구체적 정보가 간섭받을 수 있습니다. Sliding-window attention은 토큰을 명시적으로 보존하지만 window 밖으로 나가면 완전히 제거됩니다. Raven은 입력에 따라 업데이트할 slot을 선택해 두 극단 사이를 노립니다. ([arXiv][9])

### 왜 중요한가

장문 모델의 핵심 문제는 모든 과거 정보를 동일한 방식으로 압축하거나, 일정 위치가 지나면 기계적으로 버리는 것입니다. Sparse routing이 제대로 학습되면 중요 사건은 특정 memory slot에 오래 유지하고, 관련 없는 토큰은 다른 slot을 업데이트하도록 분리할 수 있습니다.

논문은 recall 중심 과제에서 기존 linear-time baseline보다 높은 성능을 보였고, 학습 길이보다 최대 16배 긴 context에서도 효과가 유지됐다고 보고합니다. ([arXiv][9])

### 실무 적용

Raven은 기존 모델에 설정 하나로 적용하는 KV-cache 최적화가 아니라 **학습이 필요한 모델 아키텍처**입니다. 평가할 때는 perplexity만으로 부족하며 다음을 함께 봐야 합니다.

* needle·entity recall
* memory slot별 write 빈도
* 특정 slot으로 routing이 붕괴하는지
* 학습 길이 밖 extrapolation
* 실제 wall-clock throughput
* hybrid attention에서 Raven layer 비율
* 기존 SSM 대비 state memory 사용량

### 주의할 점

현재 결과는 초기 논문이며 대규모 production LLM 학습에서의 안정성, 일반 지식·코딩·도구 사용 성능은 아직 확인이 필요합니다. 합성 recall 성능이 좋아도 전체 언어 모델 품질이 자동으로 개선되는 것은 아닙니다. ([arXiv][9])

**후속 관찰 포인트:** 코드·checkpoint 공개, 대규모 pretraining scaling, routing load balance, Mamba·GDN 계열과의 비교.

**원문**

* **[논문]** Raven: High-Recall Sequence Modeling with Sparse Memory Routing. ([arXiv][9])

## 6. 멀티모달 평가 | See2Think: 모델은 중간 이미지를 실제로 활용하는가

### 무엇이 바뀌었나

See2Think는 멀티모달 모델이 sketch, annotation, crop과 중간 생성 이미지를 reasoning 과정에서 실제로 이용하는지 평가합니다.

벤치마크는 12개 범주의 시각 의존 문제 1,200개로 구성되며, textual thought, visual action, 렌더링된 상태와 이후 reasoning을 네 가지 통제된 inference 조건에서 기록합니다. ([arXiv][10])

### 핵심 결과

저자들은 모델이 대체로 적절한 visual operation을 선택하지만, **의도한 상태를 정확히 렌더링하는 단계가 가장 뚜렷한 병목**이라고 분석했습니다. 중간 이미지의 피드백을 적극적으로 참조한다고 해서 최종 정확도가 반드시 올라가지는 않았습니다. ([arXiv][10])

정답과 관련된 중간 시각 정보를 의도적으로 손상시키면 정확도가 10%포인트 이상 하락해, 모델이 중간 이미지를 완전히 무시하는 것은 아니라는 증거도 제시했습니다. ([arXiv][10])

### 왜 중요한가

멀티모달 에이전트를 평가할 때 최종 답만 보면 다음 실패를 구분할 수 없습니다.

```text
잘못된 visual tool 선택
정확한 tool을 잘못 실행
이미지가 잘못 렌더링됨
올바른 이미지를 잘못 해석
피드백을 봤지만 답을 수정하지 않음
```

### 실무 적용

이미지 편집·화면 조작 에이전트의 trace에 다음을 남기는 것이 좋습니다.

```text
visual_action
source_image_hash
rendered_image_hash
expected_delta
actual_delta
feedback_used
answer_changed
verification_result
```

특히 crop, highlight와 coordinate annotation은 tool 호출 성공 여부가 아니라 대상 객체가 실제 결과 안에 포함됐는지를 별도 vision verifier로 검사해야 합니다.

### 주의할 점

벤치마크는 1,200개로 비교적 제한적이며 proprietary model과 open model의 tool environment가 완전히 동일하게 최적화됐는지는 추가 검증이 필요합니다. 또한 중간 이미지 의존성이 높다는 사실이 올바른 reasoning을 의미하지는 않습니다. 잘못된 이미지에도 강하게 의존할 수 있습니다. ([arXiv][10])

**후속 관찰 포인트:** 데이터·도구 공개, GUI 에이전트 확장, visual verifier 결합, corrupted feedback을 탐지하는 self-checking 방식.

**원문**

* **[논문]** See2Think: Do Multimodal Models Really Use Intermediate Visual States? ([arXiv][10])

## 7. 평가·안전 | 이미지가 없는데도 진단명을 출력하는 의료 VLM

### 무엇이 바뀌었나

Hearsay 연구는 의료 이미지를 첨부하지 않은 상태에서 환자의 인구통계 정보만 제공했을 때 frontier VLM이 어떻게 반응하는지 조사했습니다.

저자가 평가한 Claude Opus-4.7, GPT-5.4, Gemini-3.1-Pro는 단순히 중단하지 않고, 흉부 X-ray·뇌 MRI·피부병변에 대한 진단을 생성했습니다. 환자의 인구통계 표현을 바꾸자 출력되는 질병 분포도 체계적으로 달라졌다고 보고했습니다. ([arXiv][11])

특히 자연어 본문에서는 “이미지가 없다”고 경고하면서도 구조화된 diagnosis field에는 특정 질병명을 넣는 **channel 간 불일치**가 관찰됐습니다. 특정 단어를 `skin mole`에서 `skin lesion`으로 바꾸는 것만으로 일부 모델의 진단 패턴이 크게 변하기도 했습니다. ([arXiv][11])

### 왜 중요한가

실제 시스템은 자연어 답변보다 JSON field, ICD code와 confidence score를 downstream workflow에 전달하는 경우가 많습니다. 본문에서 불확실성을 표현해도 구조화 필드에 질병명이 들어가면 자동 triage나 기록 시스템은 이를 실제 진단으로 처리할 수 있습니다.

### 실무 적용

의료뿐 아니라 이미지 검사 시스템 전반에서 모델 호출 전에 결정론적 input gate를 두어야 합니다.

```python
if image is None or not image_decoded:
    return {
        "status": "missing_required_input",
        "diagnosis": None,
        "confidence": None,
    }
```

출력 후에도 다음 조건을 검사해야 합니다.

* 필수 입력 누락 시 모든 진단 field가 `null`인가
* prose와 structured output이 일치하는가
* demographic 정보만으로 특정 label이 증가하는가
* 동의어·표현 변화에 결과가 과도하게 민감한가
* abstention이 downstream system에서 유지되는가

### 주의할 점

이 연구는 한 명의 저자가 작성한 5페이지 규모의 workshop 논문이며, 평가 모델·prompt·질환 범위도 제한적입니다. 의료 VLM 전체가 동일하게 동작한다고 일반화할 수는 없습니다. 다만 **입력 존재 여부와 구조화 출력 채널을 별도로 감사해야 한다**는 지적은 의료 외의 멀티모달 시스템에도 직접 적용됩니다. ([arXiv][11])

**후속 관찰 포인트:** 더 많은 모델·질환으로의 재현, API 버전 변화, structured-output validator, attachment provenance 검사.

**원문**

* **[논문]** Hearsay: Vision-Language Medical Diagnoses Without an Image. ([arXiv][11])

# 오늘의 실습: FlashInfer 0.6.16 업그레이드 회귀 Harness

**목표:** 기존 serving 환경에서 FlashInfer 버전만 바꿨을 때 속도, 수치 결과와 선택 kernel이 어떻게 달라지는지 확인합니다.

## 비교 환경

동일한 Docker image를 두 개 만들고 FlashInfer 버전만 분리합니다.

```text
A. 현재 사용 중인 FlashInfer
B. FlashInfer 0.6.16
```

가능하면 동일한 SGLang 또는 vLLM commit, CUDA, driver와 모델 checkpoint를 사용합니다.

## 테스트 트래픽

세 가지 workload를 준비합니다.

```text
1. 짧은 입력·긴 출력
2. 긴 입력·짧은 출력
3. 동시 요청 32개 이상의 MoE batch
```

각 조건을 warm-up 후 최소 세 번 반복합니다.

## 기록할 지표

```text
flashinfer_version
selected_attention_backend
selected_moe_backend
jit_compile_seconds
jit_cache_hit
TTFT_p50
TTFT_p95
TPOT_p50
TPOT_p95
tokens_per_second
expert_load_imbalance
peak_vram
all_reduce_bytes
output_hash
max_error_vs_reference
```

## 추가 검증

첫 실행과 프로세스 재시작 후 실행 시간을 분리해 JIT 디스크 캐시 효과를 확인합니다. 동일 prompt를 temperature 0으로 반복해 출력이 일치하는지도 검사합니다.

FP4·FP8 경로는 BF16 reference와 비교해 다음을 확인합니다.

```python
torch.testing.assert_close(
    quantized_output,
    bf16_output,
    rtol=allowed_rtol,
    atol=allowed_atol,
)
```

## 합격 조건

* 기준 환경 대비 수치 오차가 허용 범위 이내
* backend fallback이 발생하지 않음
* 재시작 후 JIT 준비 시간이 감소
* P95 TTFT 또는 처리량이 개선
* 높은 동시성에서도 expert imbalance가 악화되지 않음
* CUDA error·deadlock·비결정적 출력 0건

이 실험의 핵심은 릴리스 노트의 최대 처리량을 재현하는 것이 아니라, **현재 보유한 B200·모델·트래픽 조합에서 0.6.16이 실제로 안전한 승격 대상인지 판단하는 것**입니다.
