## 1. Anthropic: Claude가 이미 자사 AI R&D의 26%를 “주도” — 내부에서 동시에 약 3만 개 Agent가 동작 ★★★★★

Anthropic이 9월 18일 공개한 자료에서 가장 중요한 숫자는 새 모델 benchmark가 아니라 **AI가 다음 세대 AI를 얼마나 직접 개발하고 있는가**입니다. Anthropic은 자체 `R&D Automation Index`를 만들었고, 2026년 8월 기준 Claude가 AI R&D 업무의 **26%를 AL4, 즉 인간이 고수준 목표를 주면 대부분의 작업을 end-to-end로 완료하는 수준으로 주도**한다고 밝혔습니다. AL3 이상, 즉 AI가 상당 부분 협업하는 업무는 90%를 넘습니다. 2026년 2월에는 AL4 비율이 1% 미만이었다고 Anthropic은 설명합니다. :chatgpt-content-reference{index="0"}

더 흥미로운 것은 infrastructure 규모입니다. Anthropic의 가장 많이 쓰이는 내부 연구·엔지니어링 플랫폼에서 **동시에 약 3만 개 Agent가 동작**하고 있으며, 이들의 행동에는 online monitor와 offline monitor가 붙어 있습니다. Anthropic은 `coverage`, `review latency`, `escalation rate`를 Agent oversight의 핵심 metric으로 정의했습니다. 즉 Agent observability도 단순 로그 수집이 아니라 **“몇 %의 action이 감시되는가, 위험 action을 몇 초 후에 발견하는가”**라는 SRE식 지표로 바뀌고 있습니다. :chatgpt-content-reference{index="1"}

또 AI R&D에 사용된 compute 가운데 약 **6%가 safety**, AI가 직접 수행한 AI R&D compute 중에서는 약 **12%가 safety 관련 작업**에 사용됐다고 보고했습니다. 다만 Anthropic 스스로도 이 분류가 내부 기준이며, 자사 모델이 자사 업무를 평가한다는 circularity 문제가 있다고 인정합니다. 제3자 검증이 없다면 회사 간 직접 비교용 숫자로 쓰기는 어렵습니다. :chatgpt-content-reference{index="2"}

엔지니어 관점에서 중요한 부분은 **Agent 수가 늘면 개별 Agent reliability보다 fleet-level monitoring이 중요해진다는 것**입니다. 99.99% 안전한 action도 수억 번 실행되면 incident가 발생합니다. 따라서 multi-agent system에서는 `task success rate`뿐 아니라 `monitor coverage`, `blocked-action rate`, `human escalation latency`, `unreviewed actions`를 함께 측정하는 방향이 맞습니다.

원문: [공식 연구 · Measurements for understanding the pace of AI development inside frontier labs](https://www.anthropic.com/institute/measuring-pace-of-ai-development)

## 2. NVIDIA AIPerf: GenAI-Perf를 대체 — LLM benchmark client 자체가 병목이 되는 문제를 해결 ★★★★★

NVIDIA가 9월 18일 **AIPerf**를 공식 소개했습니다. AIPerf는 GenAI-Perf의 후속이지만 내부 구조를 이어받은 버전업이 아니라 **ground-up rewrite**입니다. 기존 benchmark client는 Python single-process 구조 때문에 concurrency가 커질수록 GIL이나 client-side request generation 자체가 병목이 될 수 있었습니다. AIPerf는 worker process가 load를 발생시키고 별도의 record-processor service가 결과를 처리하며, ZMQ로 coordination하는 multiprocess 구조를 사용합니다. :chatgpt-content-reference{index="4"}

실제 production benchmark에서 특히 좋은 변화는 workload 생성 방식입니다. 단순 `concurrency=32`만 지원하는 것이 아니라 **constant / Poisson / gamma arrival**, burstiness 조절, request-rate ramping, variable ISL/OSL distribution을 지원합니다. ShareGPT뿐 아니라 **Mooncake, Baseten, WEKA AgentX trace replay**까지 지원해 실제 serving workload를 재생할 수 있습니다. Chat, Responses, ranking, image generation 등 15개 이상의 endpoint type도 지원합니다. :chatgpt-content-reference{index="5"}

Metric도 `tok/s`에서 끝나지 않습니다. TTFT, ITL, request latency, output throughput의 percentile을 기록하고 DCGM이나 pynvml이 있으면 GPU telemetry까지 같이 저장합니다. 즉 benchmark를

`서버 시작 → 요청 N개 → 평균 tok/s`

가 아니라

`arrival distribution → queue → TTFT → ITL → P95/P99 → GPU state`

전체 pipeline으로 봅니다. :chatgpt-content-reference{index="6"}

이건 vLLM/B200 실험에 바로 적용 가치가 큽니다. 특히 concurrency `1/8/32` 고정 비교 이후에는 Poisson arrival과 AgentX trace replay를 추가하면 **synthetic peak throughput benchmark → production-load benchmark**로 한 단계 올라갈 수 있습니다.

주의할 점은 benchmark tool을 바꾸면 이전 GenAI-Perf 결과와 완전히 동일 조건이라고 가정하면 안 된다는 것입니다. load-generation semantics와 metric 계산법을 같이 versioning해야 합니다.

원문: [공식 기술 블로그 · Benchmarking LLM Inference at Scale with AIPerf](https://developer.nvidia.com/blog/benchmarking-llm-inference-at-scale-with-aiperf/)

## 3. GitHub: Copilot Agent Runtime 80만+ LOC를 TypeScript → Rust로 Agent와 함께 재작성 ★★★★★

GitHub가 공개한 Copilot runtime migration 사례는 coding agent 분야에서 올해 나온 사례 중 상당히 강합니다. Copilot CLI·App·SDK 뒤에 있는 공통 Agent runtime을 기존 Node.js/TypeScript에서 **832,378줄의 production Rust**로 옮겼고, **128개 PR**로 incremental하게 main에 병합했습니다. GitHub는 대부분의 코드가 AI Agent에 의해 작성됐고, 과거라면 팀 단위로 1~2년이 걸릴 규모를 한 개발자가 주도해 몇 달 만에 수행했다고 설명합니다. :chatgpt-content-reference{index="8"}

성능 차이가 상당합니다. `client 생성 → session 생성 → 1 turn → teardown`이 약 **5.25초 → 55.3ms**, 1,000개의 one-turn lifecycle pressure test에서는 **7.55 → 120 session/s**까지 올라갔습니다. 10개 client 기준 추가 private memory는 **1,383MB → 126MB**, 약 91% 감소했습니다. 다만 GitHub도 “Rust가 일반적으로 15.9× 빠르다”는 의미는 아니며, Node/V8 process를 매 client마다 띄우던 기존 architecture가 특히 불리했던 workload라고 명시합니다. :chatgpt-content-reference{index="9"}

Agent engineering 관점에서는 성능보다 **개발 방법론**이 더 중요합니다. 기존 E2E test는 port 중 수정하지 않고 oracle로 유지했으며, PR이 기존 test를 깨면 병합하지 않았습니다. GitHub는 회고에서 명시적으로 **“Protect the oracle from the agent”**를 원칙으로 제시했습니다. 구현을 변경하는 Agent에게 correctness 기준인 test까지 자유롭게 수정하게 하면 Agent가 테스트를 약화시켜 성공한 것처럼 만들 수 있기 때문입니다. :chatgpt-content-reference{index="10"}

경제성 데이터도 흥미롭습니다. 전체 port에 약 **136.3B tokens**를 사용했고 token 비용은 약 **$120,000**이었습니다. 하지만 input-side token의 **96.22%가 prompt-cache hit**였으며 fresh input은 0.71%에 불과했습니다. 장시간 coding agent workflow의 경제성이 prompt-cache 안정성에 크게 의존한다는 실제 사례입니다. :chatgpt-content-reference{index="11"}

이 사례에서 얻을 수 있는 가장 중요한 교훈은 `Agent가 80만 줄을 작성했다`가 아니라 **incremental PR + immutable E2E oracle + human architecture review + static analysis**가 있었기 때문에 그 규모의 Agent 작업이 가능했다는 점입니다.

원문: [공식 기술 사례 · Migrating the GitHub Copilot runtime to Rust, using Copilot](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)

## 4. Kimi K3, Amazon Bedrock 지원 — 2.8T open-weight + 1M context에 explicit prompt cache까지 ★★★★★

AWS가 9월 18일 **Kimi K3를 Amazon Bedrock에 추가**했습니다. Moonshot AI 기준 K3는 **2.8T total parameter**, Kimi Delta Attention과 Attention Residuals 기반 MoE이며 native vision과 최대 **1M-token context**를 제공합니다. Moonshot의 기술 자료에서는 896개 expert 가운데 token당 16개 expert를 활성화하는 sparse 구조라고 설명합니다. :chatgpt-content-reference{index="13"}

Bedrock 쪽에서 더 중요한 것은 **explicit prompt caching을 지원하는 첫 open-weight model**이라는 점입니다. 장시간 coding/research Agent에서는 system prompt, tool schema, repository context의 상당 부분을 반복해서 보내므로 1M context 자체보다 **얼마나 많이 재사용할 수 있는가**가 비용과 TTFT에 더 중요할 수 있습니다. :chatgpt-content-reference{index="14"}

AWS는 K3에 OpenAI-compatible `Responses`와 `Chat Completions` API도 제공합니다. Global cross-region profile은 지원 region으로 요청을 routing하며 geographic profile보다 약 **10% 낮은 비용**으로 제공된다고 AWS는 설명합니다. 반대로 residency가 중요하면 US geographic profile처럼 처리 지역을 제한할 수 있습니다. :chatgpt-content-reference{index="15"}

주의해야 할 점은 **2.8T라는 숫자가 곧 inference compute가 2.8T dense 모델과 같다는 뜻이 아니라는 것**입니다. MoE이기 때문에 active parameter와 routing architecture를 같이 봐야 합니다. 또한 “frontier-level” benchmark 수치는 상당수가 Moonshot 자체 평가이므로 model 선택 시에는 동일 harness에서 별도 검증이 필요합니다.

직접 self-hosting을 고려할 경우에는 1M context와 huge MoE weight 때문에 weight residency, expert parallelism, KV memory가 모두 큰 infra 문제입니다. 오히려 Bedrock availability 자체가 “이 정도 규모 open-weight 모델은 managed inference로 소비하는 수요도 크다”는 산업 신호에 가깝습니다.

원문: [공식 AWS 발표 · Introducing Kimi K3 on Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/introducing-kimi-k3-on-amazon-bedrock/) · [공식 모델 소개 · Kimi K3](https://www.kimi.ai/ko/ai-models/kimi-k3?utm_source=chatgpt.com)

## 5. SafeHarness: 안전 규칙을 Prompt에 써놓는 것만으로는 장기 Agent가 지키지 못한다 ★★★★★

9월 17일 제출된 **Coding Agents with an Obstacle-Aware Harness for Safe Robot Manipulation**은 robotics 논문이지만 Agent engineering 일반에 적용할 수 있는 결과가 매우 좋습니다. 연구진은 robot coding agent에게 장애물을 건드리지 말라고 명확히 지시했습니다. Agent는 reasoning trace에서 장애물을 인식하고 안전 규칙도 반복해서 언급했지만 실제 움직임에서는 대부분 충돌했습니다. 즉 문제가 perception이나 instruction understanding이 아니라 **계획 과정에서 safety constraint가 우선순위에서 밀리는 것**이었습니다. :chatgpt-content-reference{index="18"}

SafeHarness는 이를 prompt 강화로 해결하지 않았습니다. route를 먼저 생성하고 **외부 verifier가 obstacle intersection을 검사**, 실패하면 replan하게 했습니다. grasp/release 단계에서도 별도 contact safety check를 수행합니다. 이 구조에서 task success는 **71.9%**, collision avoidance는 **87.5%**였고 같은 Agent에 harness가 없을 때보다 각각 2.3×, 1.5× 개선됐습니다. :chatgpt-content-reference{index="19"}

논문의 가장 중요한 문장은 사실 결과 숫자보다 설계 철학입니다. 장기 task가 수백 step, 수만 token까지 길어지면 처음 prompt에 있던 “절대 하지 말 것” 규칙이 context 앞부분에 묻히게 됩니다. 저자들은 **“step 300에서도 유지돼야 하는 invariant를 step 0의 문장 하나에 맡기면 안 된다”**고 봅니다. 그래서 안전 constraint를 stateless external verifier로 매 실행 단계에 다시 적용합니다. :chatgpt-content-reference{index="20"}

이 원리는 coding/security Agent에도 그대로 적용할 수 있습니다.

`production DB 삭제 금지`  
`workspace 밖 파일 수정 금지`  
`network egress 금지`  
`test file 수정 금지`

같은 rule은 system prompt보다 filesystem sandbox, policy engine, test gate에서 **실행 시점마다 강제**하는 것이 맞습니다.

현재 논문은 SafeLIBERO robot benchmark에서의 결과이므로 일반 software Agent 성능을 직접 증명한 것은 아닙니다. 하지만 “long-horizon invariant는 prompt가 아니라 harness에 둬야 한다”는 결론은 매우 강합니다.

원문: [논문 · Coding Agents with an Obstacle-Aware Harness for Safe Robot Manipulation](https://arxiv.org/abs/2609.20822)

## 6. CoFree: Embedding 모델을 retrieval에 맞게 학습하다 reasoning 능력을 망가뜨리는 `Reasoning Collapse` 문제 ★★★★★

9월 17일 신규 논문 **Reasoning Quality Matters**는 LLM 기반 embedding 모델에서 꽤 흥미로운 문제를 제기합니다. Foundation LLM을 retrieval embedding에 맞게 specialization하면 두 가지 failure가 발생할 수 있습니다. 모델이 더 이상 유용한 reasoning을 생성하지 못하거나, reasoning은 하지만 retrieval relevance와 상관없는 방향으로 흐를 수 있습니다. 연구진은 이를 **reasoning collapse**라고 정의합니다. :chatgpt-content-reference{index="22"}

제안한 **CoFree**는 두 단계로 학습합니다. 먼저 reference-guided SFT로 reasoning 능력을 복원하면서 embedding representation을 유지하고, 이후 RL에서 `embedding quality reward`와 `reasoning quality reward`를 동시에 사용합니다. 즉 retrieval metric만 최적화하지 않고 reasoning 자체도 독립 objective로 유지합니다. :chatgpt-content-reference{index="23"}

CoFree-4B는 Qwen3-Embedding-4B 대비 **MTEB와 BRIGHT 22개 dataset 평균 +2.8 nDCG@10 absolute improvement**를 보고했고 실제 online retrieval system에서도 개선됐다고 저자들은 밝힙니다. 아직 code와 model checkpoint는 “공개 예정”이라 결과를 독립적으로 검증하기는 어렵습니다. :chatgpt-content-reference{index="24"}

RAG 관점에서 중요한 부분은 embedding model이 앞으로 단순한 `text → vector` encoder가 아닐 수 있다는 점입니다. 복잡한 query에서는 **문서와 query 간 관계를 reasoning한 뒤 representation을 만드는 방식**이 강해질 가능성이 있습니다.

다만 reasoning token을 생성하는 embedding pipeline은 latency와 cost가 커집니다. production RAG에서는 모든 query에 reasoning embedding을 쓰기보다 `easy query → standard embedding`, `complex query → reasoning embedding`처럼 router를 두는 것이 더 현실적일 수 있습니다.

원문: [논문 · Reasoning Quality Matters: Combating Reasoning Collapse in LLM-based Embedding Learning](https://arxiv.org/abs/2609.20563)

## 7. FootprintRAG: RAG의 최종 답보다 먼저 **“어떤 evidence가 context에 들어갔는가”를 사람이 검사할 수 있게 한다** ★★★★☆

**FootprintRAG**는 9월 17일 제출된 scientific literature RAG 연구입니다. 현재 RAG는 내부에서 retrieval → reranking → filtering을 수행한 뒤 최종 evidence context만 LLM에 전달합니다. 사용자는 최종 citation은 볼 수 있어도 **어떤 candidate가 검색됐고, 왜 빠졌으며, 더 좋은 근거가 있었는지**는 보지 못하는 경우가 많습니다. :chatgpt-content-reference{index="26"}

FootprintRAG의 핵심은 evidence context를 LLM prompt의 숨은 intermediate state가 아니라 **명시적으로 inspect·edit 가능한 artifact**로 만든다는 것입니다. 논문과 figure를 evidence unit으로 나누고, query를 여러 방향으로 확장한 뒤 iterative retrieval을 수행하며, 선택·제외된 evidence와 retrieval trajectory를 UI에서 확인하고 수정할 수 있습니다. 최종 summary 역시 provenance를 따라 원래 evidence unit으로 돌아갈 수 있습니다. :chatgpt-content-reference{index="27"}

이건 RAG evaluation에서 매우 중요한 방향입니다. Hallucination이 발생했을 때

`LLM이 근거를 잘못 해석했는가?`
`Retriever가 근거를 못 찾았는가?`
`Reranker가 좋은 근거를 버렸는가?`

를 구분하지 않으면 개선 포인트를 찾기 어렵습니다.

보안 RAG나 review-paper 시스템을 만든다면 각 evidence에 `source`, `retrieval score`, `reranker score`, `accepted/rejected reason`, `revision`을 저장해 **evidence provenance table**을 만드는 방식이 실용적입니다.

다만 현재 평가는 case study와 user study 중심이므로 일반 QA benchmark에서 정확도가 몇 % 오른다는 유형의 연구는 아닙니다. 장점은 accuracy보다는 **inspectability와 human steerability**에 있습니다.

원문: [논문 · FootprintRAG: Visual Analytics for Evidence Context Refinement in RAG-based Scientific Literature Exploration](https://arxiv.org/abs/2609.19601)

## 8. Multi-Agent Trading 연구: 악성 Prompt가 아니라 “그럴듯한 공개 정보”만으로 Agent 집단의 판단이 전염될 수 있다 ★★★★☆

9월 17일 제출된 **Contagion on the Trading Floor**은 LLM multi-agent system의 information poisoning 문제를 다룹니다. 공격자는 system prompt나 tool을 해킹하지 않고, Agent가 정상적으로 읽도록 허용된 **social-media feed에 그럴듯한 콘텐츠만 주입**합니다. 그 정보가 analyst agent → coordinator → trading decision으로 어떻게 전염되는지를 측정합니다. :chatgpt-content-reference{index="29"}

연구진은 analyst와 coordinator 단계의 belief shift, 그리고 최종 backtest의 Sharpe ratio 변화를 추적했고, 단순 input-only 공격도 portfolio의 risk-return profile을 크게 악화시킬 수 있다고 보고했습니다. 반면 multi-agent topology와 coordinator prompt를 잘 설계하면 동일 poisoning budget에서도 충격을 완화할 수 있었습니다. :chatgpt-content-reference{index="30"}

이 결과는 finance보다 일반 Agent architecture에 더 중요합니다. Multi-agent system에서 upstream researcher가 잘못된 정보를 받아들이면 reviewer나 manager가 존재한다고 자동으로 교정되는 것이 아닙니다. 이전의 auditor 연구들과 마찬가지로 downstream Agent가 **upstream conclusion을 신뢰하면서 오류를 증폭**할 수 있습니다.

따라서 중요한 external evidence는 Agent 간 자연어 summary만 전달하는 것보다 `source URL/hash`, `timestamp`, `confidence`, `independent verification status`를 함께 넘기는 것이 좋습니다. 특히 하나의 외부 source가 여러 subagent에게 동시에 영향을 주는 **correlated failure**를 경계해야 합니다.

이 연구는 historical market data 기반 offline simulation이므로 실제 trading deployment의 손실 규모를 의미하지 않습니다. 하지만 “멀티에이전트 = 다수결 때문에 더 robust하다”는 단순 가정을 반박하는 데는 충분히 의미가 있습니다.

원문: [논문 · Contagion on the Trading Floor: How Adversarial Signals Spread in Multi-Agent Trading Systems](https://arxiv.org/abs/2609.19789)

# 오늘 직접 해볼 만한 실습 — 기존 vLLM Benchmark를 `AIPerf Production Load`로 확장

오늘은 기존 `concurrency=1/8/32`, `input=256`, `output=128` 실험을 버릴 필요는 없습니다. 대신 그것을 **baseline**으로 두고 AIPerf로 production-like load를 한 단계 추가해보는 것이 좋습니다.

먼저 동일한 model·TP 구성에서 `constant concurrency` 결과를 재현하고, 다음으로 request arrival을 **Poisson**으로 바꿉니다. 평균 request rate는 같게 유지하십시오. 마지막으로 가능하면 AgentX 같은 trace-replay workload를 실행합니다.

세 조건에서 공통적으로 `request/s`, `output tok/s`, median/P95/P99 TTFT, median/P95/P99 ITL, E2E latency, GPU util, HBM usage`를 기록합니다.

핵심 연구 질문은 이것입니다.

> **평균 부하는 같아도 burstiness가 커졌을 때 TP1과 TP2의 P99 latency ranking이 바뀌는가?**

여기에 한 단계 더 나가면 `constant`, `Poisson`, `gamma burst`를 비교해 **throughput-optimal configuration과 tail-latency-optimal configuration이 같은지** 확인할 수 있습니다.

이 실험부터는 단순한 “B200 두 장이 한 장보다 몇 % 빠르다”가 아니라 **production traffic distribution에서 어떤 topology가 실제 SLO를 만족하는가**를 분석하게 됩니다. 현재 진행 중인 B200 serving 포트폴리오를 시스템 연구 수준으로 올리기에 아주 좋은 다음 단계입니다. :chatgpt-content-reference{index="35"}
