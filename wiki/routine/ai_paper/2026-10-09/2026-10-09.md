## 1. Google Gemini Enterprise Agent — 모델보다 오래 살아남는 에이전트 시스템 ★★★★★

**공개일: 2026년 10월 8일 | 분야: Agent Architecture · Multi-Agent · Enterprise AI**

Google Cloud가 Gemini at Work 2026에서 기업 업무를 수행하는 새로운 통합형 **Gemini Agent**를 발표했습니다.

이번 발표에서 주목할 부분은 단순한 업무 자동화 기능이 아닙니다.

Google은 에이전트를 특정 모델에 종속된 프로그램이 아니라, **독립적인 실행 상태와 메모리, 도구, 권한을 가진 지속적인 시스템**으로 설계하고 있습니다.

### 무엇이 달라졌는가?

Google이 공개한 구조에는 다음 기능이 포함됩니다.

| 구성 요소 | 주요 기능 |
|---|---|
| Persistent Execution | 장기간 작업 상태 유지 |
| Multi-Agent Orchestration | 작업별 서브에이전트 생성 및 조정 |
| Model Routing | 작업에 적합한 모델 선택 |
| Skill Registry | 조직 공통 작업 절차 관리 |
| Tool Registry | 조직 내 도구와 API 관리 |
| Persistent Memory | 세션·의미·절차·경험 메모리 |
| Agent Identity | 독립적인 에이전트 계정 및 권한 |
| Cost Governance | 프로젝트별 사용 비용 제한 |

특히 Google은 현재 Gemini 계열뿐 아니라 **Anthropic Claude 모델도 작업에 따라 선택하는 구조**를 지원한다고 밝혔습니다.

즉 에이전트의 정체성과 실행 상태는 유지하면서, 실제 추론에 사용하는 모델을 변경할 수 있습니다. [Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026)

### 엔지니어링 관점

이번 발표에서 가장 흥미로운 것은 네 종류의 메모리입니다.

```text
Enterprise Agent
│
├── Session Memory
│   └── 현재 작업의 실행 상태
│
├── Semantic Memory
│   └── 조직·프로젝트에 관한 지식
│
├── Procedural Memory
│   └── 작업 수행 방법 및 Skill
│
└── Episodic Memory
    └── 과거 작업과 실행 경험
```

이 구분은 중요한 의미가 있습니다.

현재 진행 중인 작업의 임시 상태와 장기간 유지해야 하는 지식을 같은 메모리 저장소에 넣으면 불필요한 검색과 문맥 오염이 발생할 수 있습니다.

반대로 메모리의 종류별로 갱신 정책과 접근 범위를 분리하면, 장기 작업에서 불필요한 모델 호출을 줄일 여지가 있습니다.

또한 Google은 에이전트가 직접 서브에이전트를 생성하고 서로 다른 업무를 병렬·순차적으로 수행하도록 설계했습니다.

이는 고정된 역할의 에이전트를 여러 개 만들어 두는 방식과 다른 접근입니다.

**작업에 필요한 역할과 실행 구조를 동적으로 구성한다는 점**이 핵심입니다.

### 주의할 점

이것은 Google의 제품 아키텍처 발표입니다. 모든 기능이 동일한 수준으로 일반 제공된다는 뜻은 아닙니다.

특히 장기 메모리가 실제로 정확도를 얼마나 개선하는지, 자동 생성된 서브에이전트가 고정형 하네스보다 효율적인지에 대한 독립적인 비교 결과는 별도로 필요합니다.

권한 측면에서도 독립적인 에이전트 계정이 생기는 순간 credential lifecycle, stale permission, 외부 서비스 접근 범위 등의 문제가 발생합니다.

**후속 관찰:** 서브에이전트 동적 생성 비용, 메모리 검색 품질, 모델 라우팅 정확도, 세션 복구와 권한 격리 수준.

**원문:** [공식 발표 · Google Cloud — Gemini at Work 2026: Introducing the Gemini Agent](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026?utm_source=chatgpt.com)

## 2. OpenAI Decisions API — 생성형 LLM 대신 빠른 판단 전용 인터페이스 사용 ★★★★★

**공개 베타 발표: 2026년 10월 6일 | 분야: Model Routing · Agent Decision · AI Evaluation**

OpenAI의 **Decisions API**가 Public Beta로 제공되고 있습니다.

이 API는 일반적인 자연어 생성보다 특정 조건을 판단하거나, 정해진 선택지 중 하나를 고르는 작업에 초점을 맞춥니다.

현재 GPT-6 Luna를 기반으로 동작하며 텍스트와 이미지를 입력받습니다.

### 세 가지 판단 방식

**Predicate**는 어떤 명제가 참일 확률을 추정합니다.

예를 들어 정적분석 결과를 입력하고 취약점 근거가 충분한지 평가하는 방식입니다.

**Choice**는 미리 정의된 선택지 중 하나를 선택합니다.

에이전트의 다음 작업을 `search`, `analyze`, `verify`, `escalate` 중 하나로 결정하는 데 사용할 수 있습니다.

**Score**는 단계별 평가 기준에 따라 점수를 계산합니다.

예를 들어 코드 변경의 위험도를 0~4단계로 평가하는 방식입니다.

이 세 가지는 일반 생성형 LLM의 자유로운 텍스트 출력과 다릅니다.

```text
Agent State
    │
    ▼
Decisions API
    │
    ├── Predicate
    ├── Choice
    └── Score
    │
    ▼
Application Policy
    │
    ▼
Tool / Model Execution
```

OpenAI 공식 문서에 따르면 Responses API를 이용한 동급 모델의 판단 작업보다 최대 약 10배 빠른 응답을 목표로 합니다.

현재 가격은 GPT-6 Luna 기준 **입력 100만 토큰당 $0.10**이며 출력 토큰 요금은 없습니다. 다만 캐싱을 제공하지 않고, 장문 입력이나 지역별 처리에는 추가 요금 조건이 적용될 수 있습니다. [OpenAI Developers](https://developers.openai.com/api/docs/guides/decisions)

### 왜 중요한가?

에이전트는 매 작업 단계에서 여러 가지 결정을 반복합니다.

예를 들어 코드 분석 에이전트는 다음 중 하나를 선택해야 합니다.

```text
현재 분석 결과
      │
      ▼
추가 분석이 필요한가?
      │
      ├── No
      │    └── 보고서 작성
      │
      └── Yes
           ├── 코드 검색
           ├── 정적분석 실행
           └── 상위 모델 호출
```

이러한 선택을 위해 매번 대형 LLM이 수백 토큰의 설명을 생성하는 것은 불필요할 수 있습니다.

Decisions API처럼 결과 유형이 제한된 인터페이스를 사용하면 판단 자체의 지연시간과 출력 비용을 줄일 여지가 있습니다.

### 중요한 한계

**판단 확률이 곧 잘 보정된 실제 성공 확률이라는 보장은 없습니다.**

예를 들어 모델이 0.9의 확률을 출력했다고 해서 실제 동일 조건 100개 가운데 정확히 90개가 참이라는 의미는 아닙니다.

따라서 운영에서는 Brier Score, Expected Calibration Error(ECE), False Positive Rate 같은 지표를 함께 확인해야 합니다.

또한 모델이 선택한 행동과 실제 실행 권한은 반드시 분리해야 합니다. Decisions API가 위험한 작업을 허용한다고 판단하더라도 최종 권한은 별도 정책 엔진에서 검사해야 합니다.

**후속 관찰:** 판단 결과의 calibration, 선택지 순서에 따른 편향, 장문 입력 비용, 실제 에이전트에서의 성공당 비용.

**원문:** [공식 문서 · OpenAI Decisions API](https://developers.openai.com/api/docs/guides/decisions) · [API 레퍼런스 · Create a Decision](https://developers.openai.com/api/reference/typescript/resources/decisions/methods/create?utm_source=chatgpt.com)

## 3. Reflection Beam 501B — 대규모 RL의 병목은 학습보다 Rollout 관리에 있다 ★★★★★

**최초 공개: 2026년 10월 5일 · 결과표 갱신: 10월 8일 | 분야: LLM Architecture · MoE · Distributed Training**

Reflection AI가 **Beam**이라는 새로운 MoE 모델을 공개했습니다.

모델은 총 501B 파라미터를 가지며 토큰당 약 23B 파라미터가 활성화됩니다.

사전학습에는 23.8조 토큰을 사용했다고 밝혔습니다.

이번 발표에서 특히 중요한 것은 모델의 벤치마크 순위보다 **Post-training 인프라에 관한 상세한 운영 수치**입니다.

### 대규모 강화학습 인프라

Reflection은 약 4주 동안 10,500개의 NVIDIA GB300 GPU를 활용해 1억 개 이상의 Rollout을 생성했다고 보고했습니다.

평균적으로 약 **110,000개의 동시 Rollout**을 유지했으며, 실행 환경도 대규모로 생성하고 관리했습니다.

핵심 구조는 다음과 같습니다.

```text
Rollout Workers
      │
      ▼
Environment Execution
      │
      ▼
Reward / Verification
      │
      ▼
Experience Queue
      │
      ▼
Asynchronous Trainer
      │
      ▼
Weight Distribution
      │
      └───────→ Rollout Workers
```

이 구조에서는 학습에 사용하는 Policy와 Rollout을 생성한 Policy의 버전이 다를 수 있습니다.

이를 **Policy Staleness**라고 합니다.

예를 들어 Rollout이 시작될 때 모델 버전은 100이었지만 학습기가 데이터를 소비할 때 최신 모델이 110이라면, 과거 Policy에서 생성된 데이터를 현재 Policy 업데이트에 사용하게 됩니다.

Reflection은 토큰별로 생성 당시의 모델 버전을 기록하고, 학습과 추론 엔진 간의 수치적 불일치를 줄여 이 문제를 관리했다고 설명합니다.

최대 107개 Weight 버전의 차이가 발생한 조건에서도 학습이 유지됐다는 결과를 보고했습니다. [Reflection](https://www.reflection.ai/blog/introducing-beam)

### 인프라 성능

Reflection 측에 따르면 새로운 모델 가중치를 추론 서버 전체에 전달하는 데 걸린 시간의 중앙값은 약 12초였습니다.

또한 계층적 Weight Distribution을 이용해 Cross-Rack 트래픽을 줄였고, 학습 중 발생한 추론 서버 장애를 전체 학습 중단 없이 복구했습니다.

여기서 중요한 것은 **GPU 개수를 늘리는 것과 GPU를 효율적으로 사용하는 것은 다른 문제**라는 점입니다.

Rollout 속도가 학습 속도보다 느리면 Trainer가 기다립니다.

반대로 Trainer가 느리면 Rollout 결과가 오래된 Policy 데이터로 쌓일 수 있습니다.

따라서 전체 시스템의 처리량은 다음 요소에 의해 결정됩니다.

`Rollout Throughput × Reward Throughput × Trainer Throughput × Weight Synchronization`

실제로는 단순 곱셈 관계가 아니라, 가장 느린 단계와 단계 간 대기 시간이 전체 처리량을 제한합니다.

### 모델 아키텍처 관점

Beam은 Local/Global Attention을 혼합하고, 세밀한 Expert Routing과 여러 Load Balancing 기법을 사용합니다.

Residual Stream 안정화를 위해 정규화와 FP32 누적을 활용한다는 점도 주목할 만합니다.

다만 아키텍처 개선 효과와 대규모 학습 데이터·연산량의 효과를 구분하려면 추가적인 Ablation이 필요합니다.

**주의:** 10월 9일 기준 Beam의 가중치와 전체 기술 보고서는 아직 정식 공개되지 않았습니다. Reflection은 10월 중 공개를 예고했습니다. 공개된 성능 비교 역시 기업 자체 평가이며, 추론 FLOPs 비교에는 Prefill과 Attention 비용 등이 제외돼 있습니다.

**후속 관찰:** 실제 모델 카드, 라이선스, 학습 코드 공개 여부, MoE Routing 및 Residual 설계의 세부 Ablation, 독립 성능 평가.

**원문:** [공식 기술 발표 · Reflection AI — Introducing Beam 501B](https://www.reflection.ai/blog/introducing-beam?utm_source=chatgpt.com)

## 4. GPT-6.1 Sol Ultrafast — 추론 지연시간을 서비스 등급으로 분리 ★★★★★

**공개일: 2026년 10월 8일 | 분야: Inference Serving · Agent Runtime**

OpenAI가 GPT-6.1 Sol을 위한 **Ultrafast 서비스 등급**을 확대했습니다.

공식 발표에 따르면 Ultrafast는 일반 Standard 서비스 대비 최대 8배 빠른 속도를 목표로 합니다.

API 가격은 다음과 같습니다.

| 항목 | Ultrafast 가격 |
|---|---:|
| 입력 100만 토큰 | $12 |
| 출력 100만 토큰 | $60 |

이 서비스는 API뿐 아니라 지원되는 Codex 및 ChatGPT Work 환경으로도 확대되고 있습니다. 실제 제품 내 이용 가능 여부는 요금제와 조직 설정에 따라 다릅니다. [OpenAI Developer Community](https://community.openai.com/t/ultrafast-is-rolling-out-today-for-gpt-6-1-sol-in-the-api-codex-and-chatgpt-work/1404475)

### 엔지니어링 관점

이번 발표를 단순히 모델이 빨라졌다는 의미로 해석하면 중요한 부분을 놓칠 수 있습니다.

에이전트 작업의 전체 실행 시간은 일반적으로 다음 요소로 구성됩니다.

\[
T_{\text{total}}
=
T_{\text{model}}
+
T_{\text{tool}}
+
T_{\text{network}}
+
T_{\text{verification}}
\]

모델 추론 시간이 8배 빨라지더라도 실제 작업 시간 전체가 8배 빨라지는 것은 아닙니다.

예를 들어 추론에 10초, 도구 실행에 20초가 걸린다면 추론 시간이 1.25초로 감소하더라도 전체 시간은 30초에서 21.25초로 감소합니다.

여기에 Agent의 여러 턴과 네트워크 오버헤드가 추가되면 효과가 더 달라집니다.

공식 문서에서 지속적인 WebSocket 연결을 권장하는 이유도 매번 새로운 연결을 생성하는 데 소요되는 비용을 줄이기 위해서입니다. [OpenAI Developers](https://developers.openai.com/api/docs/guides/ultrafast-mode?utm_source=chatgpt.com)

### 실무 적용

모든 요청에 고속 서비스 등급을 사용할 필요는 없습니다.

장시간 오프라인 분석이나 배치 작업에서는 일반 처리 등급이 유리할 수 있습니다.

## 5. SharpDraft — 긴 문맥에서 Speculative Decoding의 승인율이 떨어지는 원인을 분석 ★★★★★

**논문 제출: 2026년 10월 4일 | 분야: LLM Architecture · Attention · Inference Optimization**

**SharpDraft: Accelerating Long-Context Speculative Decoding with Cardinality-Aware Query Scaling**은 이번 주 추론 아키텍처 연구에서 주목할 만한 논문입니다.

Speculative Decoding은 작은 Draft Model이 여러 토큰을 먼저 생성하고, 큰 Target Model이 해당 토큰들을 검증하는 방식입니다.

Draft Token이 많이 승인될수록 추론 속도가 개선될 가능성이 높습니다.

문제는 **문맥 길이가 증가하면서 Draft Token Acceptance가 떨어질 수 있다는 점**입니다.

### 논문이 제시한 원인

연구진은 이를 Attention Mass Dilution과 연결합니다.

Softmax Attention은 다음과 같이 계산됩니다.

\[
\alpha_i
=
\frac{\exp(qk_i^\top/\sqrt{d})}
{\sum_{j=1}^{N}\exp(qk_j^\top/\sqrt{d})}
\]

여기서 문맥 길이 \(N\)이 증가하면 Softmax 분모에 포함되는 Key의 수가 늘어납니다.

다른 조건이 동일하다면 높은 점수를 가진 일부 Key에 집중되는 확률 질량이 감소할 수 있습니다.

SharpDraft는 이 현상을 줄이기 위해 **문맥의 Cardinality를 고려한 Query Scaling**을 사용합니다.

중요한 점은 별도의 대규모 재학습 없이 적용할 수 있도록 설계했다는 것입니다.

### 실험 결과

연구진은 DFlash, PARD, EAGLE 3.1을 대상으로 SharpDraft를 적용했습니다.

AIME-26, GPQA-Diamond, LongGenBench Diary 등의 평가에서 Target Model 단독 자동회귀 추론 대비 **2.59~3.19배의 기하평균 End-to-End 속도 향상**을 보고했습니다. [arXiv](https://arxiv.org/abs/2610.05106)

다만 이것은 SharpDraft를 사용하지 않은 Speculative Decoding 대비 2.59~3.19배 빨라졌다는 의미가 아닙니다.

**비교 기준은 Target-only Autoregressive Decoding**입니다. 기존 Drafting 방법 대비 추가 개선량은 별도로 확인해야 합니다.

### 아키텍처 연구에 주는 의미

이 연구는 Attention Mechanism과 Speculative Decoding이 서로 독립적인 문제가 아니라는 점을 보여줍니다.

현재 최적화는 다음 요소들이 서로 영향을 주는 구조로 확장되고 있습니다.

```text
Attention Distribution
        │
        ▼
Draft Model Prediction
        │
        ▼
Draft Acceptance Rate
        │
        ▼
Verification Efficiency
        │
        ▼
End-to-End Latency
```

이론적인 Attention 품질이 실제 Serving 성능으로 이어지는 경로를 분석할 수 있다는 점에서 가치가 있습니다.

**주의:** 이 연구는 새로운 프리프린트이며, 모든 모델에서 동일한 속도 향상이 검증된 것은 아닙니다. Query Scaling이 실제 분포와 모델 품질에 미치는 영향, Batch Size에 따른 이득도 추가로 확인해야 합니다.

**후속 관찰:** Context Length별 Acceptance Rate, Batch Size 증가 시 이득, GPU Memory Bandwidth와 Target Verification 비용의 상호작용.

**원문:** [논문 · SharpDraft: Accelerating Long-Context Speculative Decoding with Cardinality-Aware Query Scaling](https://arxiv.org/abs/2610.05106)

## 6. GitHub ReviewBench — AI 코드 리뷰를 실제 PR 분포와 연결해 평가 ★★★★★

**공개일: 2026년 10월 5일 | 분야: AI Evaluation · Code Review · Open Source**

GitHub가 새로운 코드 리뷰 에이전트 평가 시스템인 **ReviewBench**를 공개했습니다.

이 Benchmark의 중요한 특징은 단순한 취약점 데이터셋이 아니라 **실제 Pull Request에서 코드 리뷰 품질을 측정하도록 설계**됐다는 점입니다.

GitHub는 1억 건 이상의 PR 분포를 분석하고, 실제 평가에는 19개 프로그래밍 언어에 걸친 219개 공개 PR을 선정했습니다.

Golden Set은 인간 리뷰어, 정적분석, 여러 LLM에서 발견한 문제를 취합하고 검증해 구성했습니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/?utm_source=chatgpt.com)

### 평가 방법의 차별점

일반적인 코드 리뷰 벤치마크에는 중요한 문제가 있습니다.

Golden Set에 등록된 오류만 정답으로 인정하면 새로운 오류를 발견한 모델이 오히려 불이익을 받을 수 있습니다.

ReviewBench는 이 문제를 해결하기 위해 두 가지 평가 방식을 제공합니다.

**Grounded Evaluation**은 기존 Golden Set과 비교합니다.

```text
Agent Findings
       │
       ▼
Known Golden Findings
       │
       ▼
Precision / Recall
```

**Augmented Evaluation**은 Golden Set에 없는 새로운 Finding도 검증합니다.

```text
Agent Findings
       │
       ├── Known Findings
       │       └── Matching
       │
       └── Unknown Findings
               └── Independent Validation
```

이 방식은 정답이 완벽하게 알려져 있지 않은 코드 리뷰 환경에서 특히 중요합니다.

GitHub는 별도 전문 엔지니어 검토에서 Golden Finding에 대한 판정 일치율이 96.6%였다고 보고했습니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

### 보안 AI 연구에 적용한다면

정적분석 시스템과 LLM을 결합한 보안 파이프라인에서 다음과 같은 비교가 가능합니다.

`Static Analyzer Only`  
`LLM Review Only`  
`Static Analyzer + LLM Review`

평가 결과를 단순 Precision·Recall로 끝내지 않고 Finding의 유형과 심각도별로 분리할 수 있습니다.

특히 실제 업무에서는 False Positive가 매우 중요합니다.

탐지율이 높더라도 중요하지 않은 경고가 과도하게 발생하면 개발자가 리뷰 결과를 무시하게 될 수 있습니다.

이때 Precision 중심의 Fβ 점수와 Recall 중심의 Fβ 점수를 각각 계산하면 서로 다른 운영 목적에 맞는 리뷰 시스템을 비교할 수 있습니다.

### 주의할 점

ReviewBench는 실제 PR을 기반으로 하지만 데이터셋은 219개로 제한됩니다.

또한 Golden Set 밖의 Finding을 평가하는 LLM Judge 자체에도 오류가 있을 수 있습니다.

따라서 보안성이 중요한 Finding은 실행 가능한 재현 테스트나 인간 전문가의 검토가 추가로 필요합니다.

**후속 관찰:** 보안 Finding에 대한 세부 성능, LLM Judge의 편향, 신규 오류 발견률, 실제 Production Code Review 결과와의 상관관계.

**원문:** [공식 기술 발표 · GitHub ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/) · [공식 벤치마크 · ReviewBench 평가 및 데이터셋](https://review-bench.ai/?utm_source=chatgpt.com)

# 오늘 직접 해볼 만한 실습
## `Attention Mass Dilution`을 PyTorch로 직접 관찰하기

오늘은 SharpDraft 논문의 핵심 문제의식을 작은 실험으로 확인하는 것이 좋겠습니다.

**실험 질문은 다음과 같습니다.**

> 문맥에 포함되는 Key의 수가 증가하면 Softmax Attention에서 높은 점수를 가진 일부 Key에 집중되는 확률 질량은 어떻게 변할까?

### 실험 설정

Query와 Key의 차원을 고정한 상태에서 Context Length만 변경합니다.

`Context Length = 1K / 4K / 16K / 64K`

각 조건에서 동일한 분포로 Q와 K를 생성하고 다음을 측정합니다.

`Top-16 Attention Mass`  
`Attention Entropy`  
`Maximum Attention Probability`

이후 Query Scaling을 적용했을 때 결과가 어떻게 달라지는지 비교합니다.

```python
import torch
import math

torch.manual_seed(42)

device = "cuda" if torch.cuda.is_available() else "cpu"

d = 128
lengths = [1024, 4096, 16384, 65536]

q = torch.randn(d, device=device)

for n in lengths:
    k = torch.randn(n, d, device=device)

    logits = (k @ q) / math.sqrt(d)

    for scale in [1.0, 1.2, 1.5]:
        attn = torch.softmax(logits * scale, dim=0)

        top16_mass = attn.topk(16).values.sum().item()

        entropy = -(
            attn * torch.log(attn.clamp_min(1e-12))
        ).sum().item()

        max_prob = attn.max().item()

        print(
            f"N={n:6d} | "
            f"scale={scale:.1f} | "
            f"top16={top16_mass:.4f} | "
            f"entropy={entropy:.4f} | "
            f"max={max_prob:.4f}"
        )
```

### 관찰해야 할 내용

먼저 Scale=1.0에서 Context Length를 증가시켰을 때 Top-16 Attention Mass가 어떻게 변하는지 확인합니다.

이후 동일한 Logit에 Scaling을 적용하면 Softmax 분포가 얼마나 뾰족해지는지 확인할 수 있습니다.

여기서 중요한 점은 **Scaling이 실제로 중요한 Key를 새롭게 찾아주는 것은 아니라는 사실**입니다.

양수 Scaling은 Logit의 순서를 바꾸지 않기 때문입니다.

즉 중요하지 않은 Key가 높은 Logit을 갖고 있다면, Scaling은 그 잘못된 집중을 강화할 수도 있습니다.

또한 이 코드는 독립적인 무작위 Q/K 분포를 이용한 Toy Experiment입니다. 실제 LLM의 학습된 Attention 분포나 SharpDraft의 Cardinality-Aware Scaling 알고리즘 자체를 재현한 것은 아닙니다.

### 이후 확장 방향

실제 모델에 적용할 때는 다음 항목을 추가로 측정하는 것이 좋습니다.

| 지표 | 측정 목적 |
|---|---|
| Context Length | 장문 입력의 영향 |
| Attention Entropy | 분포의 집중도 |
| Draft Acceptance Rate | Draft 품질 |
| Mean Accepted Tokens | 검증 단계당 승인 토큰 |
| Verification Latency | Target Model 검증 비용 |
| End-to-End Latency | 실제 추론 성능 |
| Peak GPU Memory | 메모리 오버헤드 |

이렇게 실험하면 단순히 Query Scaling을 적용하는 수준에서 벗어나 **Attention 분포의 변화가 Draft 품질과 검증 비용에 어떻게 연결되는지** 단계적으로 분석할 수 있습니다.
