## 1. SGLang 0.5.22 — B200/AMD/PD disaggregation까지 inference engine의 하드웨어 범위가 빠르게 넓어진다 ★★★★★

SGLang 0.5.22가 10월 19일 공개됐습니다. 공식 release에는 **950 PR, 245 contributors**가 포함됐고, DeepSeek-V4.1뿐 아니라 AMD MI350X/MI355X, B200, B300, Apple Silicon까지 폭넓은 최적화가 들어갔습니다. [GitHub](https://github.com/sgl-project/sglang/releases?utm_source=chatgpt.com)

특히 눈에 띄는 수치는:

- DeepSeek-V4.1: **H200에서 최대 2.3× throughput/GPU**
- DeepSeek-V4.1: AMD MI350X/MI355X에서 최대 **1.9×**
- Qwen3.8-Flash-Next: B200 decode **12% 향상**
- PD disaggregation: 최대 **27% throughput 증가**, long-prompt p95 TTFT 약 **50% 감소**
- GLM-5.3 + DFlash: B300 decode 최대 **10% 향상**
- 모델 로딩: 새로운 InstantTensor loader로 최대 **10× 빠른 로딩** [GitHub](https://github.com/sgl-project/sglang/releases?utm_source=chatgpt.com)

### 왜 중요한가

이제 inference engine benchmark를 단순히:

> "B200에서 몇 tok/s인가?"

로 보는 것은 부족합니다.

동일한 모델이라도:

```text
             Model
                │
     ┌──────────┼──────────┐
     ▼          ▼          ▼
   NVIDIA      AMD       Apple
    B200      MI355X     Silicon
     │          │
     └──────┬───┘
            ▼
       SGLang runtime
```

처럼 **hardware backend + runtime optimization의 조합**이 성능을 결정합니다.

그리고 PD disaggregation 개선은 특히 중요합니다.

```text
Request
  │
  ├── Prefill GPU pool
  │        │
  │       KV
  │        │
  └────────┘
       ↓
 Decode GPU pool
```

이 구조에서는 GPU를 단순히 늘리는 것이 아니라 **prefill과 decode의 서로 다른 자원 요구를 분리**할 수 있습니다.

### 사용자의 B200 실험에 적용

현재 B200 × 2 vLLM benchmark를 다음처럼 확장하는 것이 좋습니다.

```text
                 Same workload
                      │
             ┌────────┼────────┐
             ▼        ▼        ▼
           vLLM     SGLang   DeepInfer
             │        │        │
             └────────┼────────┘
                      ▼
                   B200 × 2
```

그리고 단순 throughput 외에:

- TTFT
- TPOT
- p95 TTFT
- decode throughput
- GPU memory
- GPU utilization
- prefill/decode 비율

을 비교해야 합니다.

**주의:** SGLang의 release 숫자는 각 모델·하드웨어·traffic 조건에서의 프로젝트 측정값입니다. 서로 다른 workload의 숫자를 그대로 비교하면 안 됩니다. 특히 2.3× 같은 수치는 baseline과 configuration을 확인해야 합니다.

**후속 관찰:** SGLang과 vLLM이 앞으로 **DeepSeek/V4 계열과 B200/B300/MI355X에서 각각 어떤 parallelism 전략을 선택하는지**가 중요합니다.

# 2. llm-d 1.0 — inference engine 위에 진짜 “Day-2 distributed serving” 계층이 자리잡는다 ★★★★★

현재 llm-d는 vLLM·SGLang 같은 model server 위에서 동작하는 **Kubernetes-native distributed inference stack**으로 자리 잡고 있습니다. 공식 프로젝트 설명은 다음 네 가지를 핵심으로 둡니다.

- intelligent routing
- advanced KV-cache management
- massive model serving
- production operations [GitHub](https://github.com/llm-d/llm-d/?utm_source=chatgpt.com)

특히 llm-d 1.0의 release 목표가 흥미롭습니다.

> **“State-of-the-art inference. Ready for Day 2.”**

즉 단순히 모델을 띄우는 Day-0 문제가 아니라:

```text
Day 0
  ↓
Model server 실행

Day 1
  ↓
Traffic / scaling

Day 2
  ↓
Multi-tenancy
HA
Rolling update
Priority
Failure recovery
Agent workload
```

까지 해결하려는 것입니다. [GitHub](https://github.com/llm-d/llm-d/issues/2619?utm_source=chatgpt.com)

### 왜 중요한가

이제 inference stack을 다음처럼 계층적으로 보는 것이 정확합니다.

```text
┌──────────────────────────────┐
│ Application / Agent          │
├──────────────────────────────┤
│ llm-d                        │
│ routing / KV / HA / scaling  │
├──────────────────────────────┤
│ vLLM / SGLang                │
│ model execution              │
├──────────────────────────────┤
│ CUDA / ROCm / TPU runtime    │
├──────────────────────────────┤
│ GPU / TPU / CPU              │
└──────────────────────────────┘
```

llm-d 공식 문서에서도 vLLM과 SGLang을 **model server**, llm-d를 그 위의 orchestration/optimization layer로 명확히 구분합니다. [GitHub](https://github.com/llm-d/llm-d/?utm_source=chatgpt.com)

### 사용자의 연구 방향과 정확히 연결되는 부분

현재:

```text
B200 × 2
   ↓
vLLM
   ↓
TP benchmark
```

에서 다음 단계는:

```text
B200 × N
   ↓
Kubernetes
   ↓
llm-d
   ↓
┌───────┬───────┬───────┐
vLLM   vLLM   SGLang
```

입니다.

그리고 여기서부터는 benchmark metric도 달라집니다.

### GPU benchmark

```text
tok/s
TTFT
TPOT
GPU utilization
```

### Distributed inference benchmark

```text
routing latency
KV hit rate
queue time
p95/p99 TTFT
scale-up latency
failover latency
GPU utilization across replicas
```

이렇게 됩니다.

### 주의

llm-d가 “production-ready”라고 해서 모든 production workload에서 자동으로 더 빠르다는 의미는 아닙니다.

**prefix locality가 낮거나, 요청이 짧거나, replica 수가 작으면 cache-aware routing의 이점이 작을 수 있습니다.**

따라서 실제 traffic trace를 replay해서 비교해야 합니다.

# 3. NVIDIA Vera Rubin + Google Cloud A5X — Agent/RL infrastructure가 “GPU cluster”에서 experience loop 시스템으로 이동한다 ★★★★★

10월 21일 NVIDIA와 Google Cloud가 **Vera Rubin NVL72 기반 A5X infrastructure**의 발표를 했습니다. Google Cloud는 A5X를 agentic inference와 large-scale reinforcement learning에 맞춘 시스템으로 설명하고 있습니다. [NVIDIA Blog](https://blogs.nvidia.com/blog/google-cloud-vera-rubin-infrastructure/?utm_source=chatgpt.com)

구성은:

- NVIDIA Vera Rubin NVL72
- ConnectX-9 SuperNIC
- Google Cloud Virgo Network
- liquid cooling
- training / inference / RL 통합

입니다. Google Cloud는 여러 사이트에 걸쳐 최대 **960,000 Rubin GPU** 규모로 확장할 계획도 밝혔습니다. [NVIDIA Blog](https://blogs.nvidia.com/blog/google-cloud-vera-rubin-infrastructure/?utm_source=chatgpt.com)

### 여기서 진짜 중요한 부분

이 시스템은 단순히:

```text
GPU → inference
```

가 아닙니다.

agentic RL에서는:

```text
Generate experience
       ↓
Evaluate
       ↓
Train
       ↓
Updated model
       ↓
Generate new experience
       ↓
...
```

라는 loop가 계속 돌아갑니다.

따라서:

\[
\text{RL throughput}
\neq
\text{training throughput}
\]

이고,

\[
\text{RL throughput}
\approx
f(
\text{inference},
\text{training},
\text{network},
\text{memory},
\text{experience pipeline}
)
\]

가 됩니다.

### 왜 이것이 중요한가

향후 frontier agent를 만들 때 가장 중요한 infrastructure metric 중 하나가:

> **experience를 얼마나 빨리 생성하고 다시 학습에 반영할 수 있는가?**

가 될 가능성이 높습니다.

즉 **inference cluster와 training cluster를 완전히 분리하는 architecture가 오히려 병목**이 될 수 있습니다.

### 사용자의 B200 연구와 연결

이 흐름은 상당히 중요합니다.

지금의:

```text
B200
 ↓
Inference benchmark
```

를 장기적으로:

```text
B200
 ↓
Inference
 ↓
Agent rollout
 ↓
Experience
 ↓
Training
 ↓
New checkpoint
 ↓
Inference
```

로 확장할 수 있습니다.

그러면 **inference benchmark가 RL/agent training infrastructure의 일부가 됩니다.**

**주의:** Google Cloud의 960,000 GPU 계획은 향후 확장 계획이며 현재 실제 배치 규모로 해석하면 안 됩니다. A5X의 GA 역시 발표상 다음 달부터 시작되는 일정입니다. [NVIDIA Blog](https://blogs.nvidia.com/blog/google-cloud-vera-rubin-infrastructure/?utm_source=chatgpt.com)

**원문**

# 4. Anthropic 내부 데이터 — Agent가 인간보다 더 많은 runtime을 사용하기 시작했다 ★★★★★

오늘 가장 흥미로운 **실제 agent 운영 데이터** 중 하나입니다.

Anthropic이 10월 17일 공개한 내부 분석에 따르면, **2026년 3월부터 autonomous + interactive agent work hours의 합계가 인간 work hours를 넘어섰고**, 8월에는 직원이 직접 사용하는 agent가 인간 handler보다 약 **6배 많은 시간**을 작업했습니다. [Anthropic](https://www.anthropic.com/research/employment-at-anthropic?utm_source=chatgpt.com)

특히 소프트웨어 엔지니어링에서:

- agent fleet이 routine test 수행
- infrastructure maintenance
- 대규모 codebase translation
- coding 작업

등을 수행했다고 설명합니다. [Anthropic](https://www.anthropic.com/research/employment-at-anthropic?utm_source=chatgpt.com)

### 더 중요한 결과

Anthropic은 agent 사용 엔지니어와 미사용 엔지니어를 비교했고, agent 도입 이후 코드 추가량이 증가했다고 보고합니다.

그러나 동시에 중요한 검증도 했습니다.

**“코드가 더 많이 생성되면 AI slop도 증가하는가?”**

이에 대해 같은 직원·같은 월·같은 coding directory에서 agent 작성 코드와 직접 작성 코드를 비교했을 때, 삭제/revert 등의 일부 품질 지표에서는 차이를 찾지 못했다고 설명합니다. [Anthropic](https://www.anthropic.com/research/employment-at-anthropic?utm_source=chatgpt.com)

### 이 자료에서 주의해야 할 부분

Anthropic도 **인과관계의 한계**를 명시합니다.

agent를 먼저 도입한 직원들이 원래부터 생산성이 빠르게 증가하던 사람들이었을 가능성이 있습니다. 즉:

\[
Correlation \neq Causation
\]

입니다. [Anthropic](https://www.anthropic.com/research/employment-at-anthropic?utm_source=chatgpt.com)

### 그런데 엔지니어에게 더 중요한 사실

agent가 실제로 사람보다 훨씬 긴 runtime을 갖기 시작하면:

```text
Human
  ↓
PR
  ↓
Review
```

가 아니라:

```text
Human
  ↓
Agent fleet
 ├── Agent A
 ├── Agent B
 ├── Agent C
 ├── Agent D
 └── ...
        ↓
Validation / Review
```

가 됩니다.

그러면 **agent orchestration과 observability가 software engineering infrastructure의 핵심이 됩니다.**

### 실무 적용

agent마다 최소한:

```text
agent_id
task_id
model
tokens
tool_calls
wall_time
cost
files_changed
tests_run
tests_passed
human_review
```

를 기록해야 합니다.

이 데이터가 있어야:

\[
\text{Agent Productivity}
=
\frac{\text{Validated Output}}
{\text{Agent Runtime}}
\]

같은 metric을 만들 수 있습니다.

# 6. TorchTPU 오픈소스화 — accelerator abstraction이 다시 중요해진다 ★★★★

Google이 **TorchTPU를 오픈소스로 공개**했습니다. Google은 이를 PyTorch에서 TPU를 native하게 사용할 수 있도록 하는 소프트웨어 stack으로 설명하며, training·serving·deployment를 기존 PyTorch workflow에서 사용할 수 있다고 밝혔습니다. [Google Cloud](https://cloud.google.com/blog/topics/ai-infrastructure/torchtpu-is-now-open-source-run-native-pytorch-on-tpus?utm_source=chatgpt.com)

### 왜 중요한가

현재 AI infrastructure가:

```text
PyTorch
  ↓
CUDA
  ↓
NVIDIA GPU
```

중심으로 발전해왔지만, 실제 production fleet은 점점 heterogeneous해지고 있습니다.

```text
PyTorch
 ├── CUDA → NVIDIA
 ├── ROCm → AMD
 ├── TPU  → Google
 └── other accelerators
```

TorchTPU는 이 중 TPU를 PyTorch ecosystem에 더 직접적으로 연결합니다.

### 중요한 이유

사용자의 benchmark 관점에서도:

> **GPU 자체를 비교하는 것**

보다

> **동일한 workload abstraction을 여러 accelerator에서 실행하는 것**

이 점점 중요해집니다.

향후 benchmark를:

```text
B200
MI355X
TPU
```

로 확장한다면 **model/runtime/compiler/accelerator 계층을 분리한 benchmark methodology**가 필요합니다.

**주의:** TorchTPU가 CUDA 수준의 성숙도나 ecosystem parity를 의미하는 것은 아닙니다. 실제 workload별 operator coverage와 performance는 별도로 검증해야 합니다.

**원문**

[공식 발표 · Google Cloud TorchTPU 오픈소스화](https://cloud.google.com/blog/topics/ai-infrastructure/torchtpu-is-now-open-source-run-native-pytorch-on-tpus?utm_source=chatgpt.com)

# 오늘 직접 해볼 실습 1개

## B200 × 2에서 `vLLM vs SGLang` 동일 조건 benchmark

오늘은 DeepInfer까지 한꺼번에 넣기보다 **vLLM과 SGLang을 먼저 동일 조건에서 비교**하는 것을 추천합니다.

### 실험 matrix

| 변수 | 값 |
|---|---|
| GPU | B200 × 2 |
| Model | 동일 checkpoint |
| CUDA | 동일 |
| Driver | 동일 |
| TP | 2 |
| Input | 1K / 8K / 32K |
| Output | 256 / 1K / 4K |
| Concurrency | 1 / 2 / 4 / 8 / 16 / 32 |
| Engine | vLLM 0.32.0 / SGLang 0.5.22 |

측정:

```text
TTFT
TPOT
p95 TTFT
output tok/s
request throughput

GPU utilization
HBM usage
HBM bandwidth

CPU utilization
engine startup time
```

그리고 특히 **32K input**을 넣어 보세요.

그 이유는 오늘의 핵심인 **KV cache + long-context + prefill/decode scheduling** 차이가 짧은 prompt보다 훨씬 잘 드러날 가능성이 높기 때문입니다.

최종적으로:

\[
\text{Throughput/GPU}
=
\frac{\text{output tokens/sec}}{2}
\]

와

\[
\text{p95 TTFT}
\]

를 함께 비교하면 좋습니다.

## 오늘의 핵심 결론

오늘의 변화는 단순한 “새 모델/새 GPU” 뉴스가 아닙니다.

```text
             Agent
               │
        ┌──────┴──────┐
        │             │
    Inference       Tools
        │             │
   ┌────┴────┐       CPU
   │         │        │
 vLLM     SGLang   Sandbox
   │         │        │
   └────┬────┘        │
        ▼             │
      llm-d ──────────┘
        │
   Kubernetes
        │
 ┌──────┼──────────────┐
 ▼      ▼              ▼
B200   MI355X         TPU
        │
        ▼
   Agent / RL loop
```

**Inference infrastructure가 하나의 GPU-serving problem에서 heterogeneous distributed system 문제로 바뀌고 있습니다.**

특히 사용자의 현재 연구 방향에서는:

**B200 → vLLM → SGLang → distributed inference(llm-d) → agent runtime → RL/experience loop**

가 하나의 연속된 기술 스토리가 됩니다.

그리고 오늘 가장 중요한 엔지니어링 질문은 이것입니다.

> **“가장 빠른 GPU를 사용하는가?”가 아니라, “주어진 accelerator·memory·network 자원으로 검증된 agent work를 얼마나 많이 만들어내는가?”**

이 질문으로 benchmark의 단위를 `tokens/sec`에서 **validated task/sec, cost/task, GPU-sec/task**로 확장하면 향후 포트폴리오의 깊이도 크게 올라갑니다.
