## 1. NVIDIA NemoClaw: Agent memory를 vector DB가 아니라 `Evidence → Knowledge → Governed Action`으로 재설계 ★★★★★

NVIDIA가 9월 4일 공개한 NemoClaw의 Memory-Driven Chief of Staff 사례가 오늘 가장 실무적입니다. 핵심은 agent memory를 단순히 “대화 embedding을 쌓고 similarity search”하는 구조에서 벗어나 **사람·프로젝트·우선순위·업무 패턴을 나타내는 human-readable self model**로 만든 것입니다. 파생 지식은 Markdown에 저장하고, obligation·ranking·correction·audit event는 SQLite ledger에 별도로 기록합니다. 즉 기억 자체와 실행 상태를 분리합니다. citeturn382886search1

구조적으로 더 중요한 부분은 **Evidence → Knowledge → Governed execution**입니다. 이메일이나 task 같은 원본 evidence에서 knowledge를 만들어도 그것이 곧바로 권한이 되지는 않습니다. NemoClaw는 OpenShell sandbox에서 filesystem·process·network 접근을 runtime policy로 제약하고, inference나 MCP credential은 sandbox 외부에 둡니다. NVIDIA도 “memory와 retrieved content는 model input이지 trusted security policy가 아니다”라고 명시합니다. citeturn382886search1

이 원칙은 agent memory 설계에서 꽤 중요합니다. 예를 들어 과거 기록에 “production DB를 삭제한다”는 문장이 저장돼 있다고 해서 retrieval 결과가 `delete_db()` 실행 권한으로 승격돼서는 안 됩니다. 메모리는 **사실과 선호를 제공하는 control input**이어야 하고, 권한은 deterministic policy에서 별도로 결정되어야 합니다.

NVIDIA의 자체 Agent Memory Benchmark에서는 self-model 방식이 agentic RAG baseline 대비 전체 정확도를 82.8%에서 90.9%로 높였고, 변경된 사실 추적은 60%에서 100%로 개선했다고 보고했습니다. 다만 이 수치는 NVIDIA가 설계한 recipe와 benchmark에 대한 자체 평가이므로 외부 workload로 일반화해서는 안 됩니다. citeturn382886search1

실제 시스템에 적용한다면 memory를 최소한 `facts / preferences / obligations / decisions / audit`로 나누고, vector search 결과만 바로 context에 넣기보다 현재 task에 필요한 bounded subset만 가져오는 편이 좋습니다. 후속 관찰 포인트는 이 구조가 실제 Gmail·Calendar·Slack 같은 live connector에서 deletion/retention/privacy policy와 함께 어떻게 운용되는지입니다.

## 2. Jetson에서 27B reasoning model: NVFP4 + speculative decoding으로 최대 6.28× decode throughput ★★★★★

NVIDIA는 같은 날 Jetson에서 **Nemotron 3.5 Lightning 30B-A3B와 Qwen3.8-27B를 로컬 reasoning/agent model로 배포하는 방법**을 공개했습니다. 이제 edge deployment에서도 단순 1~7B classifier가 아니라 27~30B급 reasoning model을 vLLM로 서빙하는 시나리오가 현실적인 범위에 들어왔습니다. citeturn382886news0

구조 차이가 재미있습니다. Qwen3.8-27B는 dense라 token당 27B parameter 전체가 활성화되고, Nemotron 3.5 Lightning은 30B total이지만 MoE로 token당 3B만 활성화됩니다. NVIDIA는 response-heavy agent loop에는 후자가, 응답 수는 적지만 한 번의 판단이 어려운 task에는 Qwen이 더 적합할 수 있다고 설명합니다. 결국 parameter count보다 **activated parameter와 trajectory 형태**를 같이 봐야 합니다. citeturn382886news0

성능 향상은 두 층입니다. NVFP4가 한 번의 model pass 비용을 낮추고 speculative decoding이 pass당 여러 token을 생산합니다. NVIDIA Jetson 테스트에서 Nemotron은 BF16 대비 NVFP4만으로 2.2×, NVFP4+DSpark로 3.37×, Qwen3.8은 NVFP4 2.33×, NVFP4+DFlash2에서 **최대 6.28× decode throughput**을 보고했습니다. citeturn382886news0

중요한 것은 speculative decoding method가 모델마다 달랐다는 점입니다. Nemotron에는 DSpark가, Qwen에는 DFlash2가 가장 빨랐습니다. 즉 “speculative decoding 켜기”라는 하나의 knob가 있는 게 아니라 **actor model × draft model × speculative token count × workload** 조합을 benchmark해야 합니다.

NVIDIA가 공개한 vLLM config도 꽤 참고할 만합니다. Nemotron 예제는 FP8 KV cache, prefix caching, DSpark, Mamba state cache 등을 동시에 사용하고, Qwen은 DFlash2를 붙입니다. 이건 edge뿐 아니라 B200 inference tuning에서도 그대로 가져갈 수 있는 실험 패턴입니다. citeturn382886news0

주의점은 6.28×가 end-to-end application speedup이 아니라 특정 Jetson·model·decode configuration의 **decode throughput**이라는 것입니다. 실제 agent에서는 prefill, tool latency, network I/O, JSON validation 등이 섞이기 때문에 전체 task latency 개선은 훨씬 작을 수 있습니다.

## 3. AWS HyperPod InstantStart: Agent에게 AWS CLI를 주지 말고 “안전한 control-plane API”를 주라 ★★★★★

AWS가 9월 4일 공개한 SageMaker HyperPod InstantStart 사례는 **AI agent에게 production infrastructure를 맡기는 방법**을 꽤 현실적으로 보여줍니다. HyperPod cluster 생성, accelerator capacity, storage, training, inference, monitoring은 각각 비동기 API와 failure mode가 다른데, InstantStart는 이를 stateful operation으로 감싸고 agent가 MCP를 통해 실행하도록 합니다. citeturn865125view2

AWS가 강조하는 핵심은 Agent에게 AWS CLI나 SDK를 그대로 주지 않았다는 점입니다. 대신

`Agent → MCP tool → Control Plane API → validation/idempotent reconciliation → AWS/Kubernetes`

구조로 만들었습니다.

즉 agent가 즉흥적으로 `aws eks ...`, `kubectl ...` 명령을 조립하는 것이 아니라 **사전에 검증된 operation contract**만 호출합니다. AWS는 이를 “operational rules를 control-plane API에 encode하는 것”이라고 설명합니다. citeturn865125view2

오픈소스 repository를 보면 cluster management, vLLM/SGLang inference, HyperPod Training Operator, KubeRay/VERL RL training, MLflow, Karpenter autoscaling까지 한 제어면 아래 들어갑니다. inference operator는 intelligent routing과 L1/L2 KV-cache sharing까지 지원하며, agent-driven orchestration은 MCP server로 노출됩니다. citeturn675596view0

이 패턴은 상당히 중요합니다. agentic DevOps에서 흔한 구조는

`LLM → shell`

인데, production에서는

`LLM → typed operation → validation → reconciliation loop`

가 훨씬 안전합니다.

Kubernetes operator의 declarative reconciliation model을 agent tool design에 적용한 셈입니다. 예를 들어 직접 GPU 서버를 관리할 때도 `deploy_vllm(model, replicas, gpu_type)` 같은 bounded API를 만들고 내부에서 Helm/kubectl을 처리하게 하는 게 agent에게 raw shell을 주는 것보다 낫습니다.

후속 관찰 포인트는 error recovery입니다. agent가 실패 원인을 해석하는 능력보다 control plane이 **idempotency, retry, rollback, operation state**를 얼마나 deterministic하게 보장하는지가 더 중요합니다.

## 4. Harness-of-Harness: 장기 coding agent에서 “더 긴 한 번의 실행”보다 반복 가능한 개발 루프가 훨씬 강했다 ★★★★★

Shanghai AI Laboratory의 **Harness-of-Harness(HoH)** 연구는 이번 주 coding-agent 논문 중 가장 볼 가치가 높습니다.

HoH는 기존 Codex/OpenCode/Pi 같은 agent harness를 교체하지 않고 그 위에

`Planning → Coding → Local test → Independent QA → Next planning`

의 반복 loop를 올립니다. 각 iteration에서는 기존 bug repair뿐 아니라 반드시 **작고 검증 가능한 신규 capability 하나**를 추가하게 합니다. citeturn865125view3turn786084view0

세 benchmark와 세 harness-model 조합에서 3회 iteration 이후 standalone harness 대비 평균 상대 향상 **52.25%**, 최대 82.86%를 보고했습니다. FrontierSWE에서 Codex + GPT-5.5는 반복을 10회로 늘렸을 때 22%에서 72.67%까지 올라갔습니다. 또 별도 실험에서는 70회 넘는 iteration 동안 FPS 게임을 자율 개발했습니다. citeturn786084view0

특히 memory 방식이 흥미롭습니다. 별도의 거대한 memory DB를 만드는 대신 plan, QA report, issue, history, artifact를 filesystem에 저장하고 **간단한 index만 먼저 보여준 뒤 필요할 때 세부 내용을 읽는 progressive disclosure**를 사용합니다. 이는 long context를 통째로 넣는 대신 `durable project state + retrieval` 구조를 택한 것입니다. citeturn786084view0

또 development-time test와 independent evaluator를 분리하고 hidden benchmark 결과는 다음 iteration에 되돌려주지 않습니다. Agent가 최종 benchmark를 직접 최적화해 overfit하는 것을 막는 구조입니다. citeturn343921view2

실제 coding harness에 적용한다면 subagent를 많이 만드는 것보다 먼저 다음 구조를 만드는 편이 낫습니다.

`PLAN.md → 작업 → unit/integration test → QA_REPORT.json → commit → next iteration`

그리고 planner가 전체 repo를 매번 다시 읽기보다 최신 QA와 unresolved issues부터 읽게 하면 context 소비를 크게 줄일 수 있습니다.

주의할 점은 각 task-condition당 generation이 1회이고 모델 generation seed도 고정할 수 없었다는 점입니다. 따라서 reported gain의 정확한 크기는 추가 재현이 필요합니다. 하지만 **agent harness 자체를 optimization 대상으로 봐야 한다는 방향성**은 매우 강합니다. citeturn343921view2

## 5. Multi-Agent GPU scheduler: 모델을 “어느 GPU에 둘까?”가 아니라 미래 workflow까지 예측해야 한다 ★★★★★

9월 3일 제출되고 9월 4일 신규 목록에 올라온 **Latency-Aware Orchestration for Multi-Agent LLM Workflows on Heterogeneous GPUs**는 agent serving과 GPU scheduling을 직접 연결합니다.

멀티에이전트 workflow는 일반 inference request와 달리 dependency graph를 미리 어느 정도 알 수 있습니다.

`planner → researcher → coder → reviewer`

처럼 현재 agent가 실행되는 동안 **다음에 어떤 model이 필요할지** 예측할 수 있습니다.

연구진은 device별 activation latency, peak memory, model-loading cost를 예측한 뒤 workflow dependency를 따라 **향후 model demand와 activation readiness**를 forecast합니다. 그다음 model fusion/lifecycle option, placement, execution order를 하나의 physical graph로 최적화합니다. citeturn865125view4

heterogeneous GPU pool의 세 workflow scenario에서 기존 scheduler 대비 end-to-end makespan을 최대 **36.8%**, burst 환경 p95 completion latency를 25.9% 낮췄고 session당 최대 24.63 GPU-seconds를 절감했다고 보고합니다. citeturn865125view4

이건 멀티에이전트 infra에서 꽤 중요한 관점 전환입니다.

일반 LLM scheduler는 현재 queue를 봅니다.

`지금 GPU A가 비었으니 request를 보낸다.`

Agent workflow scheduler는 **미래 dependency**까지 봅니다.

`현재 planner가 끝나면 2초 뒤 coder model 두 개가 필요하므로 미리 weight를 resident 상태로 둔다.`

즉 scheduling 문제에 model residency와 workflow DAG가 같이 들어갑니다.

여러 로컬 GPU나 서로 다른 VRAM GPU를 묶어 agent fleet을 돌린다면 `GPU utilization`만으로 routing하지 말고 `model already loaded`, `expected next agent`, `cold-load cost`, `memory pressure`까지 routing score에 넣는 것이 좋습니다.

아직 평가 GPU pool과 workflow 규모가 제한적이므로 production hyperscale 결과로 일반화할 수는 없습니다. 하지만 **multi-agent graph와 physical GPU graph를 같이 최적화한다**는 문제 설정은 앞으로 상당히 중요해질 가능성이 큽니다.

## 6. Speculative Macro Commit: speculative decoding 개념을 “tool action chain”까지 확장 ★★★★☆

**Speculative Macro Commit(SMC)**은 상당히 재미있는 agent runtime 연구입니다.

Speculative decoding에서는 작은 모델이 future token을 먼저 생성하고 큰 모델이 검증합니다. SMC는 같은 아이디어를 tool-using agent에 적용합니다.

`Large actor → 공식 행동`
`Small drafter → 앞으로 실행할 여러 tool action을 미리 예측`

그리고 drafter가 **격리된 environment snapshot에서 tool call까지 미리 실행**해 observation을 확보합니다. 이후 authoritative actor의 다음 행동이 draft 첫 행동과 일치하면 이미 실행해 둔 나머지 action/observation chain을 공식 trajectory로 commit합니다. citeturn654427view0

즉 token speculation이 아니라 **environment speculation**입니다.

Qwen3.5-27B INT4를 actor, Qwen3.5-4B를 drafter로 사용했을 때 τ²-Bench Telecom에서는 sequential execution 대비 18.59% latency 감소, AppWorld에서는 최대 **44.9% wall-time 감소**를 보고했습니다. 다만 AppWorld에서는 task completion이 소폭 감소했습니다. citeturn654427view0

이 방식은 latency가 model inference보다 tool round-trip에서 많이 발생하는 workload에 특히 흥미롭습니다.

예를 들어

`ls → grep config → cat file → run test`

같은 반복 pattern은 작은 agent가 먼저 sandbox snapshot에서 실행해둘 수 있습니다.

실제 구현 시 가장 중요한 것은 **side-effect isolation**입니다. database write, network send, git push 같은 action을 draft agent가 production environment에서 미리 실행하면 안 됩니다. 따라서 copy-on-write filesystem, transaction snapshot, mock API 같은 speculative sandbox가 필수입니다.

또 drafter가 예상하는 tool chain이 자주 틀리면 speculative work가 그대로 낭비됩니다. 따라서 speculative decoding과 마찬가지로 `acceptance rate`를 주요 metric으로 봐야 합니다.

## 7. PlanFence: 최신 memory를 읽었다고 최신 plan을 실행하는 것은 아니다 ★★★★★

**Fresh Memory, Stale Plans**는 distributed multi-agent system에서 꽤 중요한 consistency bug를 정의합니다.

예를 들어 planner가 requirement `r3`를 읽고 deployment plan을 만들었다고 합시다. 이후 다른 agent가 requirement를 `r4`로 업데이트합니다. Executor가 실행 직전에 최신 `r4`까지 읽었다고 하더라도, **현재 실행할 plan 자체는 r3를 기반으로 만들어진 상태**일 수 있습니다.

연구진은 이를 `stale-plan execution`이라고 부릅니다. citeturn654427view1

PlanFence의 해결책은 각 plan이 **어떤 shared records를 근거로 만들어졌는지 dependency를 명시**하게 하는 것입니다. 외부 action 직전에 executor는 전체 memory를 다시 sync하지 않고 현재 action에 영향을 주는 record만 검사합니다. dependency version이 변했다면 replan하거나 action을 block합니다. citeturn654427view1

30개의 controlled live workflow에서 freshness-only executor는 post-plan revision이 발생한 모든 task에서 obsolete plan을 실행했지만, PlanFence는 invalid action 없이 전부 완료했다고 보고합니다. 다만 연구진 스스로 이것이 general task-accuracy 개선 결과가 아니라 controlled safety/system-cost 결과라고 제한합니다. citeturn654427view1

이건 distributed systems의 optimistic concurrency control과 거의 같은 문제입니다.

Agent action에도 다음과 같은 precondition을 붙일 수 있습니다.

`deploy_model(plan_id, requires=[config:v8, model:v12])`

실행 직전 `config == v8`, `model == v12`인지 확인하고 하나라도 바뀌었으면 재계획합니다.

특히 shared memory를 사용하는 멀티에이전트에서는 “최신 데이터를 읽었다”는 것보다 **이 행동을 만든 reasoning이 어떤 version의 state를 기반으로 했는가**가 더 중요합니다.

직접 agent harness를 만들 때 plan artifact에 `depends_on` field 하나를 추가하는 것만으로도 꽤 많은 concurrency bug를 막을 수 있습니다.

1. **Harness-of-Harness** — 현재 coding-agent와 orchestration을 공부한다면 오늘 가장 중요합니다. 모델을 바꾸지 않고도 `planning → implementation → independent QA → iteration`이라는 harness 설계만으로 큰 차이를 만들 수 있다는 사례입니다.
2. **NVIDIA Jetson reasoning inference** — NVFP4 + speculative decoding + vLLM config가 실제로 어떻게 조합되는지 볼 수 있습니다. B200/Blackwell inference tuning에도 직접 연결되는 내용입니다.
3. **PlanFence** — 멀티에이전트 memory를 구현할 때 대부분 놓치기 쉬운 consistency 문제입니다. 최신 state와 최신 plan은 전혀 같은 개념이 아닙니다.

# 오늘 직접 해볼 만한 실습 — `Versioned Plan + PlanFence`를 Agent Harness에 붙이기

오늘은 GPU를 쓰지 않아도 되는 실습이 더 가치 있습니다. 현재 멀티에이전트 harness를 아주 작게 흉내 내서 shared state를 다음처럼 JSON으로 두면 됩니다.

```json id="ypx2uc"
{
  "requirements": {
    "version": 3,
    "value": "Use vLLM with port 8000"
  }
}
```

Planner가 plan을 만들 때

```json id="djiqr1"
{
  "action": "deploy_vllm",
  "depends_on": {
    "requirements": 3
  }
}
```

를 같이 기록하게 합니다.

그 뒤 executor가 실행되기 전에 requirements를 version 4로 바꿔 `port 9000`으로 수정해봅니다.

첫 번째 실험은 **version check 없이 실행**, 두 번째는 **PlanFence를 넣어 dependency version이 바뀌면 replan**하게 만듭니다.

여기에 HoH 방식까지 결합하면 구조가 꽤 좋아집니다.

`Requirements → Planner → Versioned Plan → Developer → Tests → Independent QA → Commit → Next Iteration`

이 정도만 구현해도 단순 “LLM 여러 개 호출” 수준에서 벗어나 **실제 software/distributed-systems 원리를 적용한 agent runtime**이 됩니다. 그리고 이후 GPU가 여러 장 있는 환경에서는 오늘 5번 논문의 아이디어를 붙여 `next agent prediction → model residency → GPU placement`까지 확장할 수 있습니다. memcite
