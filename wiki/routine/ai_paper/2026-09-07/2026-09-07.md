## 1. Claude Code 2.1.263 / 2.1.261: Agent CLI에서 이제 “불필요한 context 비용”을 직접 진단한다 ★★★★★

Anthropic은 9월 6일 Claude Code **v2.1.263**을 공개했고, 이 버전은 주로 reliability hotfix입니다. 그 직전인 9월 4일 **v2.1.261**에 실제로 중요한 기능이 들어갔습니다. `bashOutputMaxChars`와 `taskOutputMaxChars`로 shell/background task 결과를 최대 128K 문자까지 inline context로 유지할 수 있고, 긴 subagent system prompt는 `--append-subagent-system-prompt-file`로 파일에서 읽을 수 있게 됐습니다. 더 흥미로운 기능은 `/skill-doctor`입니다. 현재 로딩된 skill 중 실제로 사용되지 않는 것과 그것이 소비하는 context 비용을 보여줍니다. citeturn681243view1

Agent CLI가 발전하면서 문제는 “context window가 충분한가?”보다 **context 안에 가치 없는 token이 얼마나 들어가고 있는가**로 이동하고 있습니다. tool definition, skill description, system instruction, shell output이 매 turn 반복되면 prompt cache가 있더라도 context management와 attention 비용은 계속 발생합니다. `/skill-doctor` 같은 기능은 agent runtime에서 context를 단순 저장 공간이 아니라 **budgeted resource**로 다루기 시작했다는 신호입니다. v2.1.260에서도 prompt-cache miss의 추정 원인을 `/cost`와 status line에 표시하기 시작했습니다. citeturn681243view2

실무에서는 Agent에 기능을 계속 추가하는 방식보다 `기본 skill 최소화 → task에 필요한 skill만 동적 load → 사용되지 않는 skill 제거`가 더 합리적입니다. 특히 여러 subagent를 사용하는 구조에서는 각 agent에게 전체 tool set을 주기보다 역할별로 tool/schema를 잘라주는 것이 context·보안 양쪽에서 유리합니다.

주의할 부분도 있습니다. 출력 제한을 128K까지 늘릴 수 있다고 해서 무조건 키우는 것은 좋지 않습니다. 로그 전체를 context에 넣기보다 실패 지점 전후만 넣거나 파일로 저장한 뒤 필요할 때 검색하는 것이 일반적으로 더 효율적입니다.

## 2. Environment Evolution: Terminal Agent RL에서 문제를 새로 만드는 것보다 “기존 문제를 계속 진화”시킨다 ★★★★★

9월 3일 제출된 **Environment Evolution for Terminal Agents**는 agent post-training에서 상당히 중요한 연구입니다. 현재 terminal/coding agent를 강화할 때는 새로운 sandbox task를 생성하고 rollout을 수행한 뒤 그 실패를 다시 데이터로 만드는 방식이 많습니다. 문제는 모델이 강해질수록 처음부터 생성한 문제들이 너무 쉬워지고, 매번 on-policy rollout을 통해 난이도를 다시 맞추는 것도 비쌉니다. citeturn151077view2

연구진은 기존 environment를 **off-policy 방식으로 점진적으로 더 어렵게 진화**시킵니다. multi-turn 학습 목적에서 세 가지 난이도 축을 도출하고, 여러 agent가 환경을 수정하는 harness를 사용해 training generation마다 적절한 난이도의 environment를 공급합니다. Hy4 preview, Claude Opus 5, GPT-5.6 Sol을 사용한 rollout에서도 진화된 environment가 더 어려운 task를 지속적으로 만들었다고 보고했습니다. citeturn151077view2

실제 효과는 꽤 큽니다. Qwen3.6-27B와 Qwen3.6-35B-A3B를 long-horizon RL로 학습했을 때 Terminal-Bench 2.1 성능이 각각 **+14.4p, +18.0p** 향상됐습니다. 다만 이는 논문 저자들의 training recipe에 대한 결과이므로 다른 coding agent에 그대로 적용된다고 보기는 어렵습니다. citeturn151077view2

엔지니어 관점에서는 모델보다 **training environment lifecycle**이 중요해지고 있다는 점이 핵심입니다. Agent training pipeline을 만든다면 task를 일회성 JSON dataset으로 저장하는 것보다 executable environment에 version을 붙여

`v1 → dependency 추가 → hidden edge case 추가 → partial failure 추가 → concurrency 추가`

같이 진화시키는 편이 장기적으로 더 좋은 학습 자산이 됩니다.

주의점은 난이도 증가가 항상 좋은 것은 아니라는 것입니다. 모델 능력 범위를 너무 많이 벗어나면 reward가 거의 항상 0이 되어 학습 신호가 사라집니다. 따라서 environment difficulty 자체를 curriculum scheduler가 관리해야 합니다.

## 3. Interface-Induced Trajectory Censoring: Tool-call benchmark가 모델이 아니라 “parser bug”를 측정할 수 있다 ★★★★★

오늘 가장 경고성이 강한 연구입니다. **Interface-Induced Trajectory Censoring**은 LLM Agent의 tool-use benchmark에서 `tool-call rate = 모델 capability`라는 가정을 정면으로 깨뜨립니다.

연구에서는 모델 weight, benchmark case, decoding, seed를 모두 동일하게 유지하고 **serving adapter만 교체**했는데 BFCL v4 점수가 한쪽에서는 0.00, 다른 구성에서는 0.96/0.19까지 바뀌었습니다. chat template이나 parser 하나가 개별적으로 잘못된 것이 아니라 **둘의 contract가 맞지 않을 때** tool-call trajectory가 server 단계에서 사라지는 문제였습니다. citeturn151077view3

Qwen2.5-Coder 계열을 21배 규모 범위로 확장한 실험은 더 충격적입니다. server가 parse한 tool call은 모든 크기에서 `0/100`이었지만, raw model output을 직접 보면 32B 모델은 `80/100`에서 문법적으로 정상적인 tool call을 생성했습니다. 즉 benchmark만 보면 “32B도 tool calling을 전혀 못한다”가 되지만, 실제 문제는 **model → chat template → parser → executor contract**에 있었습니다. citeturn151077view3

문제는 evaluation에서 끝나지 않습니다. verl AgentLoop에서도 7B 모델이 115 generation 중 45개에서 완전한 tool call을 생성했지만 parser가 하나도 받아들이지 않아 **실행 0, observation 0**이 됐습니다. 이런 상태로 RL을 수행하면 모델은 자신이 올바른 tool call을 생성해도 reward를 받지 못합니다. interface bug가 training signal을 오염시키는 것입니다. citeturn151077view3

Agent 시스템을 평가할 때는 최소한 네 단계를 별도로 log해야 합니다.

`raw model output → tool-call detection → schema validation → execution`

`tool-call accuracy`라는 단일 숫자만 보면 어느 단계가 실패했는지 알 수 없습니다. 연구진은 이 문제를 찾는 **98-line preflight check**도 공개했습니다. citeturn151077view3turn188322view3

특히 vLLM·SGLang·Transformers의 chat template이나 tool parser를 바꿀 때는 모델 accuracy benchmark보다 먼저 **gold tool-call set을 raw output부터 executor까지 end-to-end로 통과시키는 integration test**가 필요합니다.

## 4. LeanStream: 모바일 LLM inference에서 SSD를 사실상 “느린 VRAM”처럼 사용한다 ★★★★★

MobiCom 2026 게재 예정인 **LeanStream**은 edge inference 관점에서 상당히 흥미롭습니다.

모바일이나 embedded device에서는 LLM weight가 DRAM보다 훨씬 커서 일부 weight를 flash/SSD에 저장하고 필요한 layer나 expert만 불러오는 방식이 필요합니다. 그런데 여기에는 모순이 있습니다. **어떤 weight가 필요한지 정확하게 알려면 현재 token 계산이 진행돼야 하고, SSD I/O를 미리 겹치려면 필요한 weight를 그보다 먼저 예측해야 합니다.** citeturn151077view1

LeanStream은 이를 `speculate-and-refine`으로 풉니다. 부분적으로 계산된 GPU 결과를 이용해 다음 computation priority, weight-loading priority, cache retention priority를 계속 수정하면서 GPU compute와 storage I/O를 overlapping합니다. 즉 한 번 예측해서 맞추는 게 아니라 inference가 진행될수록 **prediction을 refinement**합니다. citeturn151077view1

모바일과 embedded 구현에서 기존 on-device inference system 대비 동일한 최고 throughput 조건에서 memory를 **4.8~7.5배 줄였고**, 그 상태에서도 token throughput을 **1.6~2.1배** 높였다고 보고했습니다. citeturn151077view1

이 연구가 더 큰 GPU 서버에도 주는 메시지가 있습니다. 앞으로 inference memory hierarchy는 점점

`HBM → RAM → NVMe`

가 됩니다. KV cache뿐 아니라 model weight, embedding table, sparse expert까지 tiering 대상이 됩니다. 중요한 것은 무엇을 offload할지보다 **다음에 무엇이 필요할지를 얼마나 빨리 예측해서 prefetch할 수 있는가**입니다.

주의할 점은 mobile workload와 B200 서버 workload의 storage bandwidth·compute ratio가 매우 다르다는 것입니다. 따라서 2배 throughput을 데이터센터에 그대로 일반화하면 안 됩니다. 하지만 `prediction → prefetch → refine`이라는 scheduling 원리는 MoE expert loading이나 tiered KV cache에도 충분히 확장 가능한 아이디어입니다.

## 5. MoE + LoRA에서 routing이 분리돼도 domain interference가 생긴다 — SpawnLoRA ★★★★★

EMNLP 2026 Findings에 채택된 **Routing Is Not Enough**는 MoE fine-tuning을 할 때 꽤 중요한 결과를 보여줍니다.

일반적인 기대는 이렇습니다.

`Python token → coding expert`  
`biomedical token → biomedical expert`

라우터가 서로 다른 expert를 사용하면 두 domain의 fine-tuning gradient도 자연스럽게 분리될 것 같지만 실제로는 그렇지 않았습니다. Python code와 biomedical text를 함께 학습했을 때 **expert routing overlap은 거의 없었지만 biomedical 데이터를 추가하면 code perplexity가 크게 악화**됐습니다. citeturn188322view2

연구진은 원인을 LoRA adapter 내부에서 찾았습니다. 서로 다른 domain의 gradient가 거의 직교하면서도 **동일한 low-rank subspace를 두고 경쟁**하고 있었습니다. 즉

`MoE expert 분리 ≠ adapter update 분리`

입니다.

이를 해결하기 위해 **SpawnLoRA**를 제안합니다. adapter-gradient contention이 발견되면 router 자체는 건드리지 않고 해당 expert 내부에 gated sub-adapter를 추가합니다. Phi-tiny-MoE-instruct와 OLMoE-1B-7B에서 표준 LoRA와 rank-adaptive LoRA보다 negative transfer를 줄였다고 보고했습니다. citeturn188322view2

MoE fine-tuning에서 아주 유용한 diagnostic도 제안합니다. `Jaccard routing overlap`만 측정하지 말고 **adapter-gradient cosine similarity**도 같이 보라는 것입니다. domain별 expert routing이 완전히 분리되어 있어도 adapter gradient가 충돌하면 capacity를 늘리거나 adapter를 분리해야 합니다.

실제 multi-domain SFT에서는 한 LoRA adapter에 데이터를 무작정 섞기보다 먼저 domain별 gradient similarity를 몇 batch만 측정해보는 것이 유용합니다. negative/near-zero cosine이 반복되는 domain은 adapter를 분리하거나 mixture-of-adapters 구조를 고려할 수 있습니다.

다만 실험 모델 규모가 작은 편이므로 대형 MoE에서도 같은 contention 패턴이 동일한 강도로 나타나는지는 추가 검증이 필요합니다.

원문: url논문 · Routing Is Not Enough / SpawnLoRAturn188322view2

## 6. Agentic VLM 학습: 최종 정답만 reward하지 말고 “왜 이 tool을 불렀는지”까지 학습한다 ★★★★★

**Making Every Tool Call Count**는 agentic multimodal 모델을 학습할 때 reward 설계가 얼마나 세분화돼야 하는지를 보여줍니다.

VLM이 어려운 이미지를 만나면 `crop`, `image search`, `text search` 같은 tool을 사용할 수 있습니다. 기존 RL에서는 최종 답만 맞으면 tool trajectory 전체가 어느 정도 보상됩니다. 그러면 모델은 정답을 맞히면서도 **필요 없는 crop을 여러 번 하거나, 이미 확인한 정보를 다시 검색하거나, 올바른 tool을 호출했는데 observation에서 중요한 evidence를 놓치는** 문제가 생깁니다. citeturn188322view0

연구진은 **NTEP(Necessary Tool-Evidence Path)**라는 annotation을 도입했습니다. 문제를 풀기 위해 반드시 확보해야 하는 evidence와 그 evidence를 얻는 데 필요한 tool call을 명시합니다. 이후 NTEP-R reward는 tool 호출 전에는

`이 호출이 필요한 evidence를 얻으려는 목적과 일치하는가?`

를 보고, 호출 후에는

`observation에서 실제 필요한 evidence를 제대로 추출했는가?`

까지 검사합니다. 이미 해결된 목표를 다시 검색하면 별도의 penalty도 줍니다. citeturn188322view0

8B 모델을 세 가지 tool로 학습해 7개 image-grounded benchmark에서 search accuracy와 tool efficiency를 동시에 개선했다고 보고했습니다. 절대 수치는 abstract에 상세히 공개되지 않았기 때문에 “몇 배 개선” 같은 식으로 과장해서 해석하면 안 됩니다. citeturn188322view0

이 아이디어는 VLM에만 국한되지 않습니다. 일반 coding/search agent에도 그대로 적용할 수 있습니다.

현재 대부분은

`task success reward`

를 쓰지만

`tool intent → tool result → evidence extraction → state update`

각각에 reward를 주면 **불필요한 tool call을 줄이고 trajectory quality 자체를 학습**시킬 수 있습니다.

특히 agent benchmark에서 `정답률`과 함께 `tool calls / successful task`, `redundant tool-call rate`, `evidence utilization rate`를 기록할 가치가 있습니다.

원문: url논문 · Necessary Tool-Evidence Path Rewards for Agentic VLMsturn188322view0

## 7. DSAQuant: Video Diffusion quantization은 timestep마다 중요도가 다르다 ★★★★☆

**DSAQuant**는 video diffusion model을 W4A4·W3A3 수준으로 quantize할 때 생기는 특이한 문제를 다룹니다.

기존 QAT를 적용하면 prompt 의미, 전체 scene layout, 큰 motion은 살아남는데 **texture, sharpness, local detail이 크게 무너지는 현상**이 있습니다. 연구진은 원인을 video diffusion의 denoising stage마다 기능이 다른데 conventional QAT가 모든 timestep을 동일하게 취급하기 때문이라고 분석합니다. 초기 step은 scene 구조와 motion을 만들고, 후반 step은 texture와 고주파 detail을 복원합니다. citeturn188322view1turn124694view1

DSAQuant는 training에서는 초기 step에 teacher distillation을 강하게 적용하고 후반으로 갈수록 target reconstruction을 강조합니다. inference에서는 마지막 denoising 구간에서 CFG를 꺼서 quantization noise를 amplification하지 않도록 합니다. Wan과 CogVideoX 계열의 W4A4·W3A3 실험에서 기존 QAT보다 개선됐고, 가장 공격적인 W3A3 조건에서는 VBench 평균이 최대 **+6.60** 향상됐다고 보고했습니다. citeturn188322view1

코드까지 공개됐습니다. 현재 공개 runtime은 Wan 2.1 1.3B/14B와 Wan 2.2 5B를 지원하며, symmetric W4 weight + dynamic A4 activation, fused QKV CUDA kernel을 제공합니다. repository의 tested environment는 CUDA 12.6이고 sm86/A6000과 sm89/RTX 4090 kernel path가 명시돼 있습니다. citeturn124694view0

특히 구현에서 중요한 부분은 후반 CFG drop입니다. guidance scale 숫자만 1로 바꾸는 것이 아니라 **unconditional branch forward 자체를 건너뛰기 때문에 실제 compute 절감도 발생**합니다. citeturn124694view0

## 오늘 꼭 볼 것 3개

1. **Interface-Induced Trajectory Censoring** — Agent를 직접 평가하거나 RL 학습한다면 가장 중요합니다. 모델 문제가 아니라 parser/chat-template contract 문제 때문에 tool capability가 완전히 사라질 수 있다는 걸 보여줍니다.
2. **Environment Evolution for Terminal Agents** — coding-agent 학습 데이터의 다음 단계가 “더 많은 문제 생성”보다 **실행 환경 자체의 curriculum evolution**이 될 가능성을 보여줍니다.
3. **LeanStream** — edge inference 연구지만, `HBM → RAM → NVMe` 계층화와 speculative prefetch라는 아이디어는 대형 GPU serving에도 연결해서 볼 가치가 큽니다.

## 오늘 직접 해볼 만한 실습 — `Tool-call Preflight Test` 만들기

오늘은 GPU 없이도 할 수 있고 실용성이 매우 높은 실습을 추천합니다. 사용하는 모델 하나와 tool schema 5~10개를 준비해 동일한 prompt를 **① raw Transformers inference, ② vLLM/OpenAI-compatible endpoint** 두 경로로 실행해보십시오.

각 요청마다 다음 네 단계만 저장합니다.

```text id="fl8vp2"
raw_generation
→ parser_detected_tool
→ schema_valid
→ tool_executed
```

예를 들어 raw generation에

```json id="wkd5r1"
{"name":"search_file","arguments":{"path":"main.py"}}
```

가 명확하게 존재하는데 `parser_detected_tool=false`라면 모델을 fine-tuning하거나 prompt를 바꿀 문제가 아닙니다. chat template·tool parser·server adapter를 먼저 고쳐야 합니다.

그다음 모델 크기나 quantization을 바꾸지 않고 **chat template만 교체 → parser만 교체 → 둘 다 교체**하는 2×2 실험을 하면 오늘 3번 논문의 핵심 결과를 직접 검증할 수 있습니다.

이 검사를 agent benchmark와 RL pipeline 앞단에 한 번만 붙여두면, 앞으로 **“모델이 tool을 못 쓰는 것인지, serving stack이 tool을 못 읽는 것인지”**를 명확하게 분리할 수 있습니다.
