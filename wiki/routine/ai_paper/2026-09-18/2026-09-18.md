# AI 엔지니어 데일리 브리핑 — 2026년 9월 18일

한국시간 **9월 18일 아침** 기준입니다. 어제 이후 공개된 자료 중에서는 **Claude Code의 다중 Agent Project 구조, NVIDIA의 Edge Agentic MLPerf 결과, Anthropic의 AI 기반 과학 모델 최적화**가 가장 큽니다. 연구 쪽에서는 Agent serving에서 tool 실행 시간을 추측하지 말고 tool 자체가 진행률을 runtime에 알려주자는 제안, 그리고 보안 Agent가 prompt injection이 아닌 **가짜 증거 자체**에 흔들리는 문제를 정량화한 연구가 특히 좋습니다.

오늘 전체 흐름을 압축하면 **Agent가 커질수록 모델 자체보다 `shared state`, `KV lifecycle`, `tool/runtime contract`, `verification`, `trust boundary`가 시스템 성능과 안전성을 결정하는 비중이 빠르게 커지고 있습니다.**

## 1. Claude Code Projects 재설계: `Coordinator → Parallel Threads → Shared Memory → PR`이 제품 기본 구조로 들어왔다 ★★★★★

Anthropic이 **9월 17일 Claude Code Projects를 완전히 재설계**했습니다. 사용자가 큰 목표를 하나 주면 coordinator가 범위를 나누고 여러 thread에 작업을 분배합니다. 각 thread는 단순 subagent call이 아니라 **자신만의 repository copy와 branch를 가진 독립적인 Claude Code cloud session**입니다. 각 thread가 테스트하고 PR을 열며, coordinator가 진행 상황과 결과를 다시 합칩니다. :chatgpt-content-reference{index="0"}

구조를 단순화하면 다음과 같습니다.

`Goal → Coordinator → Thread A/B/C → independent branch/test/PR → Coordinator`

여기서 특히 중요한 변화는 **shared memory**입니다. 모든 thread가 프로젝트 차원의 memory를 읽고 쓰며, 과거 결정이나 release 변경, 특정 service를 건드리기 전에 누구와 확인해야 하는지 같은 정보를 다음 작업이 재사용합니다. 파일과 Claude가 만든 artifact도 별도 library에 누적됩니다. :chatgpt-content-reference{index="1"}

이 구조는 멀티에이전트를 구현할 때 좋은 현실적 기준점입니다. 모든 Agent를 동일 working tree에서 동시에 돌리는 것보다 **Agent마다 branch/worktree를 분리하고 Git merge를 synchronization primitive로 쓰는 방식**이 훨씬 관리하기 쉽습니다. 동일 코드를 두 thread가 수정하면 Anthropic도 이를 별도 AI conflict-resolution magic으로 처리하지 않고 일반적인 merge conflict로 남깁니다. :chatgpt-content-reference{index="2"}

반대로 shared memory는 새로운 consistency 문제를 만듭니다. `Thread A가 memory를 기반으로 plan 생성 → Thread B가 requirement 변경 → A가 오래된 plan으로 계속 작업` 같은 stale-plan 문제가 생길 수 있습니다. 따라서 multi-agent project를 직접 만든다면 memory item이나 plan에 `revision`, `source`, `depends_on` 같은 metadata를 붙이는 것이 좋습니다.

Anthropic도 여러 thread가 각각 full Claude Code session이기 때문에 **usage limit에 훨씬 빨리 도달할 수 있다**고 명시합니다. 따라서 최적 thread 수는 많을수록 좋은 것이 아니라 `parallelism gain / duplicated exploration / merge conflict / token cost`의 균형점입니다. 현재는 select Pro/Max 사용자를 대상으로 beta이며 local tool/code와 연결된 실행은 추후 제공 예정입니다. :chatgpt-content-reference{index="3"}

원문: [공식 발표 · Projects redesigned: from folder to conversation](https://claude.com/blog/projects-redesigned)

## 2. Jetson AGX Thor가 Agentic MLPerf를 24분에 완료 — 핵심은 GPU 성능보다 `96% KV reuse + Tree MTP` ★★★★★

NVIDIA가 9월 17일 공개한 MLPerf Inference v6.1 Edge Agentic 결과에서 **Qwen3.6-27B를 Jetson AGX Thor 한 대**에서 TensorRT Edge-LLM으로 실행했습니다. 1,007개의 multi-turn Agent turn 전체를 **24분 36초**에 완료했고, llama.cpp reference의 2시간 37분보다 6.4배 빨랐습니다. Output throughput은 52.33 tok/s, median TTFT는 247.12ms, median TPOT는 14.68ms, BFCL accuracy는 87.94%였습니다. :chatgpt-content-reference{index="5"}

그런데 이 결과에서 가장 중요한 것은 NVFP4 자체가 아닙니다. Agent workload에서는 매 turn마다 과거 tool result와 대화가 계속 누적됩니다. 이번 workload도 20개 conversation, 1,007 turn이며 context가 약 **23.5K token**까지 커집니다. TensorRT Edge-LLM은 turn 사이 KV/recurrent state를 유지해 prompt token의 약 **96%를 hot cache에서 처리**했습니다. :chatgpt-content-reference{index="6"}

또 Qwen3.6의 Multi-Token Prediction을 단순 linear speculation이 아니라 **8-step, top-2, 16-node verification tree**로 사용했고, NVIDIA 측 측정에서는 function-calling workload의 decode 성능을 추가로 약 40% 높였습니다. :chatgpt-content-reference{index="7"}

따라서 Edge Agent inference를 최적화할 때 중요도 순서를 이렇게 생각하는 편이 좋습니다.

`weight precision → KV/recurrent-state reuse → speculative/MTP acceptance → tool-call correctness`

Chatbot benchmark처럼 매 request를 독립적인 prompt로 생성하면 Agent workload의 실제 bottleneck을 놓치게 됩니다.

특히 128GB unified memory를 가진 Thor에서 이 결과가 나왔다는 점도 의미가 있습니다. Edge Agent에서는 대형 accelerator의 peak TFLOPS보다 **모델 weight + growing KV + tool runtime을 제한된 memory/power 안에서 어떻게 유지하느냐**가 더 중요해집니다.

다만 6.4배는 Jetson Thor와 llama.cpp reference 사이의 **전체 software/hardware stack 비교**이며 TensorRT 자체가 llama.cpp보다 6.4배 빠르다는 일반적인 결론으로 읽으면 안 됩니다. Quantization, MTP, KV reuse, kernel stack이 모두 함께 달라졌습니다.

원문: [공식 기술 블로그 · TensorRT Edge-LLM Completes MLPerf Edge Agentic 6.4× Faster](https://developer.nvidia.com/blog/tensorrt-edge-llm-completes-the-mlperf-edge-agentic-benchmark-6-4x-faster-on-jetson-agx-thor/) · [공식 benchmark 설명 · MLPerf Edge Agentic Inference](https://mlcommons.org/2026/07/mlperf-inference-v61-edge-agentic/?utm_source=chatgpt.com) · [GitHub · NVIDIA TensorRT Edge-LLM](https://github.com/NVIDIA/TensorRT-Edge-LLM)

## 3. Anthropic: Claude가 30개 넘는 바이오 모델을 평균 약 4× 가속 — AI Agent가 실제 GPU kernel 최적화 팀 역할을 하기 시작 ★★★★★

Anthropic은 9월 17일 Claude를 이용해 **30개가 넘는 biomolecular·genomics open-source 모델을 최적화**한 결과를 공개했습니다. 약 4주 동안 진행했고 평균적으로 약 **4배 가속**, 결과가 정확히 동일한 `exact` mode에서도 약 2배에 가까운 개선을 보고했습니다. 최적화 코드도 모두 공개했습니다. :chatgpt-content-reference{index="11"}

구조 예측 모델의 주요 병목인 triangle attention과 triangle multiplication을 위해 Claude가 만든 **FlashPairformer** custom kernel은 기존 field-standard 구현 대비 triangle attention에서 평균 2.7~2.9배, triangle multiplication에서 1.7~3.2배 빠른 결과를 냈습니다. 모델마다 redundant computation caching, dead branch 제거 같은 higher-level optimization도 추가했습니다. :chatgpt-content-reference{index="12"}

흥미로운 것은 코드 공개 방식입니다. Repository에는 AlphaFold 계열, Boltz, RFdiffusion, protein language model, genomics model 등 **36개의 drop-in optimization kit**가 있으며 각 kit가 동일한 mode abstraction을 가집니다.

`off`는 원본, `exact`는 bit/결과 동일성을 최대한 보존한 가속, `fast`는 작은 numerical difference를 허용한 추가 가속, `big`은 peak GPU memory를 줄이는 모드입니다. 또한 optimization이 실제 활성화되지 못할 경우 조용히 original path로 fallback하지 않고 `NOT ACTIVE`로 종료하도록 만들었습니다. :chatgpt-content-reference{index="13"}

이 설계는 일반 inference optimization에도 굉장히 좋은 패턴입니다. 이전 브리핑에서 다룬

`configured → eligible → executed → correct → faster`

검증과 사실상 같은 철학입니다. Optimization을 넣었다는 것보다 **실제 fast path가 실행됐는지 명시적으로 증명하게 만드는 것**이 중요합니다.

Anthropic의 low-memory `Big` mode는 10,000-token을 넘는 biomolecular system을 하나의 NVIDIA GPU node에서 정확히 예측할 수 있게 했고, 8×B300 node에서는 70K-token 이상의 system까지 실행 자체는 가능했습니다. 하지만 30K~70K token 영역의 초대형 결과는 구조적으로 collapse하기도 했기 때문에 **“실행할 수 있음”과 “모델이 해당 규모에서 일반화함”은 완전히 다른 문제**입니다. Anthropic도 이를 명확히 구분하고 있습니다. :chatgpt-content-reference{index="14"}

원문: [공식 연구 · How Claude is uplifting biomolecular modeling](https://www.anthropic.com/research/claude-uplifts-biomolecular-modeling) · [GitHub · anthropics/uplifting-biomolecular-modeling](https://github.com/anthropics/uplifting-biomolecular-modeling)

## 4. NVIDIA도 같은 방향: AI Agent가 CUDA Tile Python → Rust kernel 24개를 자동 포팅하고 성능 99.5% 보존 ★★★★★

NVIDIA가 9월 16일 공개한 연구도 위 Anthropic 사례와 강하게 연결됩니다. TileGym에 있는 cuTile Python과 Triton-TileIR GPU kernel을 **cuTile Rust로 자동 변환하는 Agent skill**을 만들었고 공개된 24개 operator, 약 40개의 실제 GPU kernel을 모두 포팅했습니다. B200 benchmark에서 cuTile Python 대비 geometric mean 성능이 **99.5%**였습니다. :chatgpt-content-reference{index="17"}

중요한 것은 Agent에게 “Rust로 번역해줘”라고 단순히 요청한 것이 아닙니다. Pipeline을

`분석 → device kernel → host/FFI → validation → benchmark`

로 분리하고 각 stage를 전문 subagent가 수행합니다. 그리고 각 단계의 종료 조건은 다른 LLM의 prose 판단이 아니라 **machine-checkable validator와 verdict**입니다. :chatgpt-content-reference{index="18"}

특히 cuTile Python, Triton-TileIR, cuTile Rust가 모두 **동일 CUDA Tile IR**로 내려간다는 점을 이용해 generated Rust의 IR을 reference kernel의 IR과 diff합니다. Tests를 통과하더라도 tile shape, memory operation, divisibility attribute가 미묘하게 다르면 performance regression이나 unseen input에서 오류가 생길 수 있기 때문입니다. :chatgpt-content-reference{index="19"}

이 설계는 coding agent에서 굉장히 중요한 원칙을 보여줍니다.

**출력이 검증 가능한 intermediate representation을 가진 문제는 Agent 자동화에 특히 유리합니다.**

컴파일러 IR, SQL plan, AST, schema, bytecode 같은 deterministic representation이 있으면 “코드가 그럴듯해 보이는가?” 대신 **구조적 equivalence**를 검증할 수 있습니다.

또 NVIDIA는 top-level Agent의 권한을 사실상 routing으로만 제한하고, stage 간 전달도 file/schema/fixed-format verdict로 만들었습니다. “한 Agent가 모든 context를 들고 다니며 설계·구현·평가까지 한다”보다 훨씬 견고한 harness입니다.

원문: [공식 기술 블로그 · Translating CUDA Tile Operations from Python to Rust Using Agentic AI](https://developer.nvidia.com/blog/translating-cuda-tile-operations-from-python-to-rust-using-agentic-ai/) · [GitHub · NVIDIA TileGym](https://github.com/NVIDIA/TileGym)

## 5. 새 Agent Serving 연구: Tool 실행 시간을 예측하지 말고 **Tool이 진행률을 직접 GPU scheduler에 알려줘라** ★★★★★

9월 16일 제출된 **Ask the Tool, Don't Guess**는 지금 Agent serving을 연구한다면 상당히 직접적인 논문입니다.

Agent가 tool을 호출하면 LLM inference는 멈추지만 해당 session의 KV cache는 GPU HBM을 계속 차지합니다. Serving engine 입장에서는 고민이 생깁니다.

`Tool이 곧 끝나는가? → KV를 GPU에 유지`  
`오래 걸리는가? → CPU/SSD로 offload`

현재 시스템은 tool 종류, 과거 duration, engine occupancy 같은 정보로 **tool duration을 미리 예측**합니다. 논문의 핵심 주장은 아주 단순합니다.

**Tool 본인은 자신이 얼마나 진행됐는지 이미 알고 있는데 왜 serving engine이 추측하는가?** :chatgpt-content-reference{index="22"}

연구진은 tool이 실행되는 동안 `fraction remaining` 또는 최소한 `곧 끝난다` 같은 progress signal을 harness에 노출하게 했습니다. 네 개의 공개 Agent corpus를 조사했을 때 tool 실행 시간 상당 부분에서 이런 정보를 실제로 추출할 수 있었고, Agent가 보는 observation 자체는 바꾸지 않아 benchmark score에 측정 가능한 영향을 주지 않았다고 보고합니다. :chatgpt-content-reference{index="23"}

이 signal을 production engine의 KV placement decision에 연결했더니 LRU 대비 **tool 종료 이후 P90 TTFT를 HBM-only에서 20.7%, HBM+DRAM 환경에서 20.8% 개선**했습니다. 성능은 future duration을 알고 있는 oracle에 근접했습니다. :chatgpt-content-reference{index="24"}

이 아이디어는 Agent infrastructure의 매우 중요한 방향을 보여줍니다.

현재는

`Agent framework → opaque tool call → serving engine이 추측`

이지만 앞으로는

`Tool → progress telemetry → Agent runtime → KV scheduler`

처럼 **application-level semantics가 inference scheduler까지 내려갈 수 있습니다.**

직접 MCP/gRPC tool을 만든다면 return value만 정의하지 말고 `progress`, `estimated_remaining_work`, `cancelable`, `checkpointable` 같은 runtime metadata를 제공하는 것도 고려할 만합니다.

주의할 점은 모든 tool이 진행률을 자연스럽게 표현할 수 있는 것은 아니라는 점입니다. 외부 API request처럼 완료 직전까지 진척도를 전혀 알 수 없는 tool도 있습니다.

원문: [논문 · Ask the Tool, Don't Guess: Agent Tool Calls Hold Their Progress, and the Serving System Should Read It](https://arxiv.org/abs/2609.18849)

## 6. AgentLSD: 보안 Agent는 Prompt Injection이 없어도 **가짜 증거**만으로 유도될 수 있다 ★★★★★

9월 16일 arXiv에 올라온 **AgentLSD**는 AI security Agent 평가에서 중요한 구분을 제시합니다. 지금 Agent 보안 논의는 prompt injection에 집중돼 있지만 실제 security Agent는 web page, source code, log, config, shell output 등 **환경의 관측값 자체**를 신뢰하며 판단합니다. 공격자는 지시문을 심지 않고도 fake flag, misleading hint, decoy endpoint 같은 가짜 증거만 배치할 수 있습니다. 연구진은 이를 **adversarial task contamination**이라고 부릅니다. :chatgpt-content-reference{index="26"}

연구진은 11개의 web CTF challenge에 deterministic trap을 삽입하고 여섯 모델을 비교했습니다. Clean condition에서 Agent들의 flag capture rate는 **41%**였고 어떤 모델도 모든 문제를 해결하지 못했습니다. Trap을 넣었을 때 solve-rate 변화는 모델별로 달랐지만, 정답을 결국 찾은 경우조차 평균적으로 **약 20 turn과 2K reasoning token이 추가**됐습니다. 일부 Agent는 decoy를 따라가거나 잘못된 flag를 제출했습니다. :chatgpt-content-reference{index="27"}

이 결과는 보안 분석 Agent뿐 아니라 일반 coding Agent에서도 중요합니다.

예를 들어 repository 안에

`README: tests pass`  
`old_report.json: vulnerability fixed`  
`fake log: deployment succeeded`

같은 내용이 있다고 합시다. 이것은 prompt injection이 아니지만 Agent가 이를 사실로 받아들이면 잘못된 행동을 할 수 있습니다.

따라서 Agent reliability benchmark에는 **clean task success**만 두면 부족합니다.

동일 task를

`clean environment`  
`stale evidence`  
`contradictory evidence`  
`plausible decoy`

조건으로 만들어 비교할 필요가 있습니다.

특히 악성코드·정적분석 Agent라면 최종 finding을 자연어 증거에 의존하게 하지 말고 가능한 경우 `AST`, `code span`, `execution result`, `hash`, static-tool output처럼 **독립적으로 재검증 가능한 evidence**를 우선시하는 편이 좋습니다.

AgentLSD는 AISec 2026 게재 예정이며 framework, trap configuration과 raw trace도 공개한다고 밝혔습니다. :chatgpt-content-reference{index="28"}

원문: [논문 · AgentLSD: Evaluating AI Security Agents Under Adversarial Task Contamination](https://arxiv.org/abs/2609.19140)

## 7. Multi-Agent에는 개인 Harness뿐 아니라 **Social Harness**가 필요하다는 연구 ★★★★☆

**Agentic Societies Need a Social Harness**는 여러 Agent가 같은 owner를 위해 일하는 기존 multi-agent 설정보다 한 단계 더 어려운 상황을 다룹니다. 서로 다른 사용자·회사·조직을 대신하는 Agent들이 같은 시스템에서 협업하면 각 Agent의 objective와 trust boundary가 서로 다를 수 있습니다. :chatgpt-content-reference{index="30"}

저자들은 기존 구조를 두 층으로 분리해야 한다고 주장합니다.

`Personal Harness`는 Agent와 자신의 principal 사이의 context, permission, tool을 관리하고,

`Social Harness`는 Agent와 Agent 사이의 communication protocol과 trust를 관리합니다.

실험에서는 정직하고 충분히 능력 있는 Agent들만 있을 때도 기존 messaging primitive로 satisfactory joint outcome에 실패하는 경우가 있었고, faulty/malicious participant 하나가 communication을 이용해 collaboration을 지연하거나 결과를 왜곡할 수 있었습니다. :chatgpt-content-reference{index="31"}

제안 architecture는 세 계층입니다. 일부 failure는 protocol 자체로 불가능하게 만들고, runtime에서 invalid message를 detect하며, 사후에는 investigation과 accountability가 가능하도록 logging을 유지합니다. :chatgpt-content-reference{index="32"}

현재 MCP/A2A 기반 시스템을 설계한다면 매우 좋은 관점입니다. 메시지를 단순

`sender → text → receiver`

로 처리하기보다 최소한

`sender identity / principal / capability / message type / artifact hash / request ID / expiry / signature`

를 같이 전달하는 편이 좋습니다.

특히 서로 다른 조직의 Agent가 연결되는 순간 “LLM이 내용을 잘 이해할 것”이 communication protocol이 될 수 없습니다. Distributed system에서 API contract가 필요한 것처럼 **Agent society에도 protocol contract가 필요합니다.**

다만 이 논문은 아직 architecture proposal 성격이 강하며 실제 large-scale production agent network에서 어느 social-harness mechanism이 가장 효과적인지까지 해결한 것은 아닙니다.

원문: [논문 · Agentic Societies Need a Social Harness](https://arxiv.org/abs/2609.17527)

## 8. Anthropic Life Sciences Verification Program: 안전 정책이 `요청별 Block`에서 `사용자 검증 + 장기간 행동 모니터링`으로 이동 ★★★★☆

Anthropic은 9월 17일 **Life Sciences Verification Program(LSVP)**을 public beta로 열었습니다. 검증된 연구기관·팀은 일반 모델에서 차단되는 일부 biology research에 더 넓게 접근할 수 있으며 `Standard Use`와 project-specific `High-risk Use` grant로 권한을 나눕니다. :chatgpt-content-reference{index="34"}

엔지니어링 관점에서 중요한 것은 모델 capability보다 **safety architecture가 바뀐 방식**입니다.

Biology에서는 같은 요청이 vaccine research일 수도 있고 harmful pathogen engineering일 수도 있기 때문에 개별 prompt만 보고 의도를 정확하게 판정하기 어렵습니다. Anthropic은 그래서 LSVP에서 일부 safeguard를 **real-time request blocking에서 offline behavioral monitoring**으로 옮겼습니다. :chatgpt-content-reference{index="35"}

조직의 허용 use case를 먼저 등록하고 여러 request와 session에 걸친 행동 pattern을 분석합니다. 이를 위해 flagged activity와 관련된 데이터는 **30일간 보존**합니다. Anthropic이 명시한 주요 threat model도 단순 악성 prompt가 아니라 `account compromise`, `insider threat`, 그리고 **long-horizon/swarm Agent misuse**입니다. :chatgpt-content-reference{index="36"}

이것은 일반 enterprise Agent security에도 흥미로운 방향입니다.

`request-level safety classifier`

만으로는

`turn 1: 데이터 조회`  
`turn 20: credential 접근`  
`turn 80: 외부 전송`

처럼 여러 turn에 분산된 위험 행동을 잡기 어렵습니다.

따라서 앞으로 Agent security에는 **trajectory-level detector**가 필요합니다. 각 action은 individually benign해도 전체 sequence가 조직의 허용 use case에서 벗어나는지를 봐야 합니다.

반대로 privacy trade-off도 분명합니다. Long-horizon monitoring을 하려면 더 긴 log retention이 필요하기 때문에 기업은 safety gain과 데이터 보존 위험을 함께 평가해야 합니다. 현재 LSVP는 beta이며 BAA-enabled organization에서는 지원되지 않습니다. :chatgpt-content-reference{index="37"}

원문: [공식 발표 · Introducing the Life Sciences Verification Program](https://www.anthropic.com/news/life-sciences-verification-program)

## 오늘 직접 해볼 만한 실습 — `Tool Progress-Aware KV Policy` 미니 구현

오늘은 **5번 논문의 아이디어를 실제 Agent harness에 붙이는 실습**이 가장 좋습니다. 현재 사용 중인 MCP 또는 gRPC tool 가운데 실행 시간이 비교적 긴 작업 하나를 고르십시오. 예를 들면 repository 전체 정적 분석, pytest 실행, malware project scan 같은 작업이 좋습니다.

기존 tool이 마지막에 결과만 반환한다면 중간에 다음 정도의 telemetry를 내보내도록 바꿉니다.

```text
status = running
completed = 43
total = 100
progress = 0.43
estimated_remaining = 18.2s
cancelable = true
```

그다음 Agent runtime에서 tool-call 시작 시점의 예상 시간과 **실제 progress 기반 remaining time**을 모두 기록합니다.

첫 번째 단계에서는 GPU KV eviction까지 구현할 필요가 없습니다. 다음 세 값만 수집해도 충분합니다.

`predicted_tool_duration_before_start`  
`remaining_time_from_live_progress`  
`actual_finish_time`

20~50개의 실행을 모아서 두 예측의 MAE를 비교하십시오.

그다음 serving 쪽까지 확장한다면 아주 간단한 policy를 붙일 수 있습니다.

`remaining < X sec → KV를 HBM에 유지`  
`remaining ≥ X sec → CPU로 offload`

그리고 기존 `LRU 또는 duration prediction`과 비교해 **tool 종료 후 TTFT, HBM 사용량, CPU↔GPU transfer bytes**를 측정하면 됩니다.

이 실험은 현재 진행 중인 Agent/MCP 구조와 LLM serving을 하나의 연구 질문으로 연결합니다. 단순히 “MCP를 구현했다”, “vLLM을 benchmark했다”가 아니라 **Application telemetry가 inference runtime의 resource policy를 어떻게 개선하는가**라는 꽤 강한 systems 포트폴리오 주제가 됩니다.
