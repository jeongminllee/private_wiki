## 2. NVIDIA CUDA Rust 공식화: GPU kernel까지 Rust로 직접 작성하는 두 경로 공개 ★★★★★

NVIDIA가 9월 8일 **CUDA Rust** 방향을 공식 발표했습니다. 지금까지 Rust로 CUDA runtime을 호출하는 것은 가능했지만 kernel 자체는 C++/CUDA 등 다른 언어로 작성하는 경우가 많았습니다. NVIDIA가 공개한 방향은 GPU kernel 자체를 Rust에서 작성해 **직접 PTX로 compile**하는 것입니다. 두 프로젝트가 핵심입니다. `cuda-oxide`는 기존 CUDA C++과 유사한 SIMT programming model이고, `cutile-rs`는 tile 단위 computation을 기술하면 compiler가 thread mapping과 memory layout을 결정하는 상위 abstraction입니다. citeturn219904view0

특히 AI infrastructure와 잘 맞습니다. 최근 inference engine, distributed runtime, scheduler, driver 계층에서 Rust 사용이 빠르게 늘고 있는데 kernel만 다른 언어에 남아 있었습니다. Rust kernel까지 가능해지면 **scheduler/runtime/kernel을 하나의 ownership/type system 아래 두는 구조**가 현실적으로 가능해집니다. 두 구현 모두 aliasing 같은 GPU memory race를 compile-time ownership으로 잡으려 합니다. NVIDIA는 architecture-specific tuning이 꼭 필요하지 않으면 Tile을 먼저 고려하고, shared memory나 thread-level 제어가 필요하면 SIMT로 내려가라는 방향을 제시합니다. citeturn219904view0

현재 바로 production kernel을 옮길 단계는 아닙니다. NVIDIA 스스로 두 프로젝트 모두 production-ready가 아니라고 명시하며 `cuda-oxide`는 early alpha입니다. `cuda-oxide`는 pinned nightly Rust와 LLVM 계열 환경이 필요하고, `cutile-rs`는 stable Rust 1.89+이지만 CUDA 13.3이 요구됩니다. API도 변경될 가능성이 큽니다. citeturn219904view0

그래도 inference engineer 입장에서는 꽤 큰 흐름입니다. Triton, CUDA C++, CuTeDSL에 이어 **Rust가 GPU kernel authoring의 실제 선택지**에 들어오기 시작했습니다. 향후 vLLM/SGLang/Dynamo 계열 Rust control-plane과 GPU kernel 사이의 언어 경계가 줄어드는지를 관찰할 가치가 있습니다.

Google Cloud가 같은 날 **Data Agent Kit**도 공개했습니다. 이것은 BigQuery용 자연어 SQL assistant가 아니라 **MCP server + Skills bundle**을 이용해 warehouse, operational DB, object storage, dbt, terminal을 한 Agent workflow 안에서 연결하는 toolkit입니다. 현재 Antigravity, Claude Code, Codex, Cursor 등에서 사용할 수 있습니다. citeturn988518view1turn205928view0

## 5. OpenHands Automation 1.11.0: 장기 Agent 운영에 RBAC·health gate·자동 격리가 들어간다 ★★★★☆

OpenHands는 9월 8일 **Automation 1.11.0**을 공개했습니다. 모델 기능 추가보다 운영 기능이 중심입니다. automation permission을 `view`와 `manage`로 분리했고, automation 수정 권한을 creator에 제한했으며, 반복 실패하는 automation을 자동 disable하는 기능과 issue/PR의 `ready-for-dev` readiness gate가 들어갔습니다. citeturn868433view0turn868433view2

이 변화는 production Agent에서 중요한 패턴을 보여줍니다. 장기 Agent는 단순 cron job이 아닙니다. **누가 볼 수 있는가, 누가 수정할 수 있는가, 어떤 상태일 때 실행해도 되는가, 반복 실패 시 누가 멈추는가**를 runtime이 알아야 합니다. Agent 자체가 똑똑해질수록 orchestration layer에는 오히려 전통적인 SRE 원칙—RBAC, health state, quarantine, idempotency—가 더 필요합니다.

## 6. KVMem: 1M-token Agent workspace를 `GPU HBM → RAM → NVMe`에 KV 상태로 가상화 ★★★★★

최근 연구 중 인프라 관점에서 오늘 가장 볼 만한 것은 **KVMem**입니다. 기존 long-running Agent는 context가 모델 window를 넘으면 오래된 내용을 summary로 압축하거나 text retrieval로 다시 불러옵니다. 전자는 detail을 잃고, 후자는 이미 계산한 text를 다시 prefill해야 합니다. KVMem은 오래된 context를 **paged KV state 자체로 GPU memory, host RAM, NVMe에 보존**하고 attention-space index를 이용해 현재 query에 필요한 block만 다시 materialize합니다. citeturn578859view2

핵심은 “모델이 1M token을 동시에 attention한다”는 얘기가 아닙니다. **주소 가능한 Agent workspace가 1M token이고, 실행 시에는 모델 native context window 안에 query-specific working set을 구성**하는 방식입니다. 이 차이가 중요합니다. DeepSWE long-context에서 Qwen3.8-27B 기준 compaction-only success 43.8%가 KVMem에서 48.4%로 상승했다고 보고했고, RTX 5090 Laptop 24GB에서 Qwen3.6/3.8-27B NVFP4+MTP를 사용해 1M-token workspace를 virtualize하면서 single-session 약 50 tok/s를 기록했습니다. citeturn578859view0turn578859view1

이 접근이 발전하면 Agent memory가 operating system의 virtual memory와 비슷해집니다.

`hot KV → GPU`
`warm KV → RAM`
`cold KV → NVMe`

그리고 현재 task에 필요한 page만 HBM으로 불러옵니다. 장시간 coding Agent에서는 과거 terminal output이나 source context를 summary로 손실시키지 않고 **계산된 representation 상태로 재사용**할 수 있다는 점이 매력적입니다.

주의할 점도 큽니다. KV는 model weight, tokenizer, positional encoding, backend implementation과 강하게 결합된 state입니다. 모델을 바꾸거나 checkpoint를 update했을 때 cache invalidation 문제가 생깁니다. 또한 multi-tenant 환경에서는 text보다 KV cache의 access control과 삭제 정책이 더 까다로워질 수 있습니다. 아직 preprint이므로 production abstraction으로 받아들이기보다는 **Agent context virtualization이라는 연구 방향**으로 보는 것이 적절합니다.

## 7. Post-training 연구: 전체 token 중 0.05%만 학습 신호를 줘도 reasoning이 개선됐다 ★★★★★

**Extremely Sparse Supervision Incentivizes Reasoning Ability**는 post-training 비용과 credit assignment를 다시 생각하게 만드는 결과입니다. On-policy distillation 환경에서 reasoning trajectory 전체 token에 teacher supervision을 주는 대신 **trajectory당 단 1~2 token, 전체 generated token의 약 0.05%만 loss에 포함**했는데, 다수 조건에서 full-token supervision과 비슷하거나 더 높은 reasoning 성능을 냈다고 보고합니다. citeturn578859view3

이 현상은 Qwen3 기반 9개 teacher–student 구성과 여러 scale의 수학 reasoning에서 관찰됐고, coding reasoning, Llama 계열, PPO 기반 RLVR에서도 추가 검증됐습니다. 연구가 시사하는 것은 모든 reasoning token을 똑같이 수정할 필요가 없고 **몇 개의 critical decision token에 gradient를 주는 것만으로 trajectory 전체 behavior가 바뀔 수 있다**는 가능성입니다. citeturn578859view4turn578859view5

실험적으로 상당히 재미있는 후속 연구가 가능합니다. Full-token distillation과 동일한 trajectory를 사용한 상태에서 `uniform random 1 token`, `high entropy token`, `error-adjacent token`, `tool decision token`만 loss에 넣어 비교하면 “어떤 token에 supervision을 주는 것이 실제로 중요한가?”라는 credit-assignment 문제로 확장할 수 있습니다.

여기서 과장을 가장 조심해야 합니다. **0.05% token supervision이 곧 training compute가 2000배 감소한다는 뜻은 아닙니다.** Trajectory 생성, teacher inference, student forward 등은 여전히 필요할 수 있습니다. 이 논문의 가장 강한 주장은 compute 숫자 자체보다 **학습 신호가 극단적으로 sparse해도 reasoning behavior가 개선될 수 있다는 것**입니다. 실제 wall-clock과 GPU-hours가 얼마나 줄어드는지는 별도의 systems benchmark가 필요합니다. citeturn578859view3

## 8. Visual Prompt Injection이 실제 tool-call까지 넘어왔다 — 이미지도 `untrusted executable input`처럼 봐야 한다 ★★★★★

보안 연구 **Repeat-After-Me: Black-Box Adaptive Visual Prompt Injection**은 multimodal Agent의 threat model을 한 단계 넓힙니다. 연구진은 image 안의 adversarial signal을 통해 VLM이 단순히 이상한 답변을 만드는 수준을 넘어 **정확한 native tool call을 생성하거나 민감 정보를 노출하도록 유도하는 black-box attack**을 제시했습니다. open-weight VLM에서는 80% 이상, 상용 frontier VLM에서는 47% 이상의 attack success rate를 보고했습니다. citeturn578859view6

더 중요한 실험은 실제 Agent 연결입니다. 연구진은 OpenClaw Discord deployment에서 untrusted 사용자가 보낸 injection image를 통해 Agent가 `TOOLS.md`를 덮어쓰게 만들었고, 이 변경이 이후 더 민감한 행동으로 이어질 수 있음을 보였습니다. 즉 이미지는 단순 “분석할 데이터”가 아니라 **Agent의 future execution policy를 바꿀 수 있는 instruction carrier**가 될 수 있습니다. citeturn578859view7

방어 설계는 text prompt injection과 동일한 원칙으로 가야 합니다. Image/OCR/VLM output을 `untrusted` provenance로 표시하고, 그 context를 읽은 후에는 filesystem write, credential access, network send 같은 capability를 자동 승격시키지 않아야 합니다. 특히 “이미지에서 읽은 내용 → TOOL/AGENTS/skill 파일 수정” 같은 경로는 policy layer에서 아예 차단하는 것이 좋습니다.

수치는 논문 저자들의 특정 attack budget과 모델에 대한 결과이므로 모든 VLM이 같은 비율로 취약하다고 일반화하면 안 됩니다. 하지만 **multimodal input도 prompt injection surface라는 사실**은 Agent 제품을 설계할 때 반드시 반영해야 합니다.

# 오늘 직접 해볼 만한 실습 — `Untrusted Context → Tool Policy Gate` 만들기

오늘은 작은 Agent harness에 **provenance-aware tool gate** 하나를 붙여보는 것을 추천합니다.

입력 context를 `trusted_user`, `trusted_local`, `untrusted_web`, `untrusted_image`처럼 분류하고 Agent가 tool call을 생성하면 실행 전에 policy engine이 `source provenance × tool capability`를 검사하도록 만듭니다.

예를 들어 `untrusted_image`나 `untrusted_repo`를 읽은 trajectory에서는 `read_file`과 `search`는 허용하되 `write_agent_config`, `write_skill`, `network_send`, `secret_read` 같은 high-impact action은 차단하거나 human approval로 전환합니다.

그다음 동일한 task 20개를 `prompt-only guardrail`과 `provenance + deterministic gate` 두 조건으로 비교하면서 **task success rate, unsafe-action rate, blocked legitimate action rate, tool-call 수, latency**를 기록하면 됩니다.

오늘 Google GTIG의 실제 공격 사례, Antigravity SDK의 `pre_tool_call_decide` 패턴, 그리고 Repeat-After-Me의 multimodal injection 연구를 하나의 짧은 실험으로 연결할 수 있습니다.
