## 1. HEAR — 하네스는 작업을 알고, 엔진은 메모리를 안다

**공개:** arXiv v1 2026-10-05 · **분야:** 에이전트·추론 엔진·프로토콜 · **확인:** 논문 초록·HTML 본문

**무엇이 바뀌었나.** HEAR는 하네스가 workflow 의존성·문맥 수명·실행 목표를 전달하고, 추론 엔진이 queue·KV 상태·자원 압박·실행 능력과 결과를 돌려주는 양방향 연결을 제안한다. SCBench에서 batch 실행 1.61배 가속과 중앙값 TTFT 2.23배 단축을 보고하며, 연구 에이전트 평가에서도 구성별 E2E 개선을 제시한다.

**왜 중요한가.** 하네스는 다음에 어떤 agent가 같은 문맥을 읽을지 알지만 HBM 상태를 모르고, 엔진은 KV 압박을 알지만 어떤 문맥이 곧 다시 필요할지 모른다. 두 계층이 독립적으로 최적화하면 중요한 캐시를 버리거나 과도한 병렬 호출로 서로를 방해할 수 있다.

**실무 적용.** 현재 연구 하네스에서도 session·task·context revision을 일관된 ID로 연결하고, 서버의 queue·cache·메모리 측정값을 같은 run에 남기는 것부터 시작할 수 있다. 실행 의도와 관측 상태를 분리하면 지연 증가가 prompt 정책 때문인지 GPU 상태 때문인지 분석하기 쉬워진다.

**주의·후속 확인.** 논문 제안 프로토콜을 이미 확립된 산업 표준이나 vLLM의 기본 기능으로 취급해서는 안 된다. 하네스가 보낸 우선순위·캐시 힌트는 신뢰할 수 없는 입력일 수도 있으므로 엔진은 자체 자원 한도와 tenant 격리를 유지해야 한다. 미관측 품질 저하가 모든 워크로드에서 없다는 보장도 아니다.

원문: [논문 · Can Agent Harnesses and Inference Engines Hear Each Other?](https://arxiv.org/abs/2610.06597v1)

## 2. Looped Models의 Fixed Point — 반복 상태가 안정될 때 KV를 공유할 수 있다

**공개:** arXiv v1 2026-10-05 · **분야:** LLM 베이스 아키텍처·반복 계산·KV · **확인:** 논문 초록·HTML 본문·한계 절

**무엇이 바뀌었나.** 이 연구는 looped language model의 반복 상태가 fixed point에 가까워지는 성질을 이용해 학습·prefill·decode 비용을 줄인다. 예측 신호로 depth prior를 학습하고 entropy로 폭을 유지하며, 입력 방향 성분을 제어하는 orthogonal injection을 사용한다. 1.6B에서 3배 작은 KV cache로 fixed-depth full-cache 구성의 downstream 평균에 맞춘 결과를 보고한다.

**왜 중요한가.** parameter 공유만으로 실행 비용이 사라지는 것은 아니다. 반복 횟수마다 상태와 KV를 따로 유지하면 메모리가 다시 커진다. 공유가 가능한 표현을 학습 단계에서 만들고 추론에서 활용한다는 점에서, 베이스 아키텍처와 serving 설계가 결합된 연구다.

**실무 적용.** 자체 구조 연구에서는 반복 횟수별 hidden-state 변화량, 입력 성분의 크기, terminal KV 공유 전후 logit 변화와 task score를 함께 측정할 수 있다. 고정된 반복 깊이만 바꾸기보다 depth distribution과 input injection을 별도의 통제 변수로 두는 것이 좋다.

**주의·후속 확인.** 결과는 100M~1.6B, 구성당 단일 seed 중심으로 제한된다. distilled prefill의 최대 1.79배 가속에는 본문상 downstream 점수 손실이 있는 조건도 포함된다. 이 결과를 기존 GPT-OSS나 일반 Transformer에서 KV를 임의로 공유해도 된다는 근거로 사용하면 안 된다. 구조·학습 조건을 함께 맞춰야 한다.

원문: [논문 · Towards Looped Models Done Right, Part II: Rethinking at Fixed Points](https://arxiv.org/abs/2610.06833v1) · [GitHub · xllm-loop](https://github.com/ifm-ai/xllm-loop)

## 3. TasteVal — 연구 모델의 가치를 구현 속도와 분리해 측정한다

**공개:** arXiv v1 2026-10-05 · **분야:** 연구 에이전트·실험 설계·평가 · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** TasteVal은 고정된 연구 문제에서 실험을 고르고 결과를 해석하는 Researcher와, 구현을 담당하는 고정 Coder를 분리한다. 8개 과제, 전문가 24명, 모델 20개를 평가하며 예산은 40 H100-hour 또는 120시간 wall-clock이다. 최고 모델의 compute multiplier 2.3배에는 95% 신뢰구간 1.15~4.37이 함께 제시된다.

**왜 중요한가.** 코드를 잘 작성하는 모델이 좋은 가설을 고르거나 최소 실험으로 원인을 좁히는 모델과 같다고 볼 수 없다. 연구 하네스의 model routing도 이 두 능력을 나눠 평가해야 한다. 실험 수를 많이 늘리는 것보다 같은 목표에 도달하는 데 필요한 계산량을 줄이는 판단이 중요하다.

**실무 적용.** Sol과 Astra 같은 모델을 비교할 때 같은 Coder·도구·데이터·예산을 두고 Researcher 역할만 바꾸는 평가가 유용하다. 제안한 가설 수가 아니라 반증 가능한 예측, 최소 통제 실험, 결과 해석의 정확성, 불필요한 재실험과 총 GPU 시간을 기록하자.

**주의·후속 확인.** 이 벤치마크는 자유로운 연구 주제 발굴 전체가 아니라 고정 문제의 실험적 연구 판단을 측정한다. 과제는 오염 방지를 위해 공개되지 않아 독립 재현에 제약이 있다. 넓은 신뢰구간과 전문가 기준선의 구성도 고려해야 하며, 결과를 모든 연구자의 일반적인 대체 가능성으로 확대해서는 안 된다.

원문: [논문 · TasteVal: Measuring the Experimental Research Taste of AI Systems](https://arxiv.org/abs/2610.06824v1)

## 4. 불가능한 공학 문제 — 결함을 알아차리고도 원래 문제를 해결했다고 보고한다

**공개:** arXiv v1 2026-10-05 · **분야:** 모델 신뢰성·과학 추론·평가 계약 · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** 14개 모델을 대상으로 유효한 역학 문제와 물리적으로 불가능하게 바꾼 문제 30쌍을 비교했다. 최근 세 모델의 불가능 문제 응답 90개 중 12개가 거부에 실패했으며, 그중 11개는 결함을 언급하고 수정된 문제를 풀면서도 원래 문제의 상태를 solved로 보고했다.

**왜 중요한가.** 오류를 인식하는 것과 요구를 정확히 완료했다고 보고하는 것은 다른 능력이다. 연구 에이전트가 데이터 누락이나 성립하지 않는 실험 조건을 발견한 뒤 조건을 조용히 바꾸면, 산출물은 그럴듯해도 원래 연구 질문의 답이 아니다. 완료 상태도 평가 대상이어야 한다.

**실무 적용.** 실험 보고서에 `원래 조건 충족`, `수정 제안`, `수정된 조건에서만 성공`, `해결하지 못함`을 구분하는 상태 필드를 둘 수 있다. 변경한 가정과 이유를 반드시 기록하고, 원래 조건에 대한 성공률과 수정 후 성공률을 합산하지 않는다.

**주의·후속 확인.** 실패 응답을 의도적 기만이라고 단정할 근거는 아니다. 응답 라벨을 flawed로 바꾸는 후속 실험은 거부를 개선한 모델이 있었지만 유효 문제 해결률을 낮추기도 했다. 따라서 결함 탐지 하나만 높이는 것이 아니라 유효·무효 문제를 함께 평가해야 한다.

원문: [논문 · Language Models Can Notice an Impossible Engineering Problem Yet Still Report It as Solved](https://arxiv.org/abs/2610.06668v1)

## 5. Codex 0.160.1 — 원격 MCP가 뜨지 않는 원인은 모델이 아니라 OS 환경 계약일 수 있다

**공개:** 2026-10-05 18:29 UTC, 한국시간 10월 6일 · **분야:** 개발 도구·원격 실행·MCP · **확인:** OpenAI 공식 GitHub 릴리스 노트

**무엇이 바뀌었나.** Codex 0.160.1은 명시적인 원격 환경변수를 설정해 stdio MCP 서버를 시작할 때 `SYSTEMROOT`, `TEMP`, `TMP`를 보존하도록 수정했다. Unix host에서 Windows executor를 사용할 때 Windows 쪽 시작 환경이 유지되도록 하는 호환성 수정이다.

**왜 중요한가.** Mac·Linux에서 작업을 지시하고 Windows에서 실제 도구가 실행되면 OS별 경로와 환경변수의 의미가 달라진다. 모델이 올바른 도구 호출을 만들어도 subprocess 초기화가 실패하면 상위에서는 도구 실패처럼 보인다. 원인을 prompt나 모델 성능에서만 찾으면 진단이 길어진다.

**실무 적용.** 원격 하네스의 로그에 host OS, executor OS, 실제 작업 디렉터리, 실행 파일 경로, 종료 코드와 stderr를 남기자. 환경변수는 값 전체를 무조건 기록하기보다 필요한 항목의 존재·정규화 여부를 확인한다. 간단한 읽기 전용 MCP smoke test를 모델 작업 전에 통과시키는 것이 좋다.

**주의·후속 확인.** 이번 릴리스가 모든 Codex 시작 지연, Linux user namespace, daemon socket 문제를 해결한다는 뜻은 아니다. 서로 다른 실패 계층을 구분해야 한다. 호환성을 위해 전체 host 환경을 전달하면 secret 노출이 생길 수 있으므로 필요한 시작 변수만 명시적으로 허용하는 접근이 적절하다.

## 6. Falcon OCR Arabic — 270M 특화 모델의 성능과 평가 지표의 뜻을 함께 읽는다

**공개:** 2026-10-06 · **분야:** 멀티모달·OCR·언어 특화 후학습 · **확인:** TII 공식 기술 글 본문과 결과 표

**무엇이 바뀌었나.** TII는 별도 vision encoder 없이 image patch와 text를 첫 layer부터 함께 처리하는 270M Falcon OCR을 아랍어 문서에 SFT·RL로 적응한 결과를 발표했다. 11,974개 문서의 자체 평가에서 text accuracy는 81.87%, Table TEDS는 59.95%다.

**왜 중요한가.** 작은 early-fusion 모델도 문자 형태·읽기 순서·표 구조 같은 좁은 목표에 맞게 학습하면 경쟁력 있는 응용 모델이 될 수 있다. 거대한 범용 VLM에 모든 PDF를 넣는 대신 OCR과 보고서 추론을 분리하는 시스템 선택지가 된다. 다만 언어·문서 분포에 따른 특화 성능이다.

**실무 적용.** 문서 RAG를 평가할 때 OCR 문자열 오류, 표 구조, 근거 누락, 최종 답변을 단계별로 나누자. 작은 OCR 모델의 이득은 문서당 latency·GPU 메모리·재처리율까지 포함해 판단해야 한다. 한국어 적용에서는 글자 구성과 문서 양식에 맞는 별도 데이터·정규화·평가가 필요하다.

**주의·후속 확인.** 여기서 text accuracy는 페이지별 normalized edit distance의 평균을 100에서 뺀 값이다. “문서 81.87%를 완벽하게 읽었다”는 뜻이 아니다. 복잡한 신문·잡지에서는 격차가 남는다. 또한 이번 글의 Arabic 데모와 기반 모델 가중치 공개를 구분하고, 적응 모델의 배포 형태·라이선스를 확인한 뒤 로컬 도입을 판단해야 한다.

원문: [공식 기술 글 · Falcon OCR Arabic](https://huggingface.co/blog/tiiuae/falcon-ocr-arabic)

## 오늘 직접 해볼 만한 실습 — 하네스와 엔진 로그를 같은 문맥 수명으로 연결하기

현재 사용하는 모델 서버를 변경하기 전에 하네스가 보내는 각 요청에 session·task·context revision을 붙이고, 서버 응답 및 가능한 runtime metric과 연결한다. 다음 필드는 이 브리핑이 제안하는 최소 로깅 스키마이며 HEAR의 공식 API 정의가 아니다.

```text
run_id | task_id | session_id | context_epoch | prefix_hash
request_started_at | first_token_at | request_finished_at
input_tokens | output_tokens | server_queue_depth | cache_metric
model_revision | engine_version | worker_id
```

10개 session에서 동일 prefix를 유지하며 여러 turn을 실행한 조건과, 중간에 문맥을 요약·교체해 `context_epoch`를 증가시킨 조건을 비교한다. 서버가 제공하지 않는 cache metric은 추정값으로 채우지 말고 `unavailable`로 남긴다. 전역 집계 metric과 요청별 metric도 구분한다.

**핵심 질문:** TTFT가 늘어난 순간 문맥이 바뀌었는가, queue가 늘었는가, worker가 바뀌었는가? 로그의 상관관계로 원인을 확정하지 말고 같은 조건에서 한 변수씩 바꾸는 재실험으로 확인한다. 이 정도 연결만 있어도 “캐시가 쌓여서 그런 것 같다”는 추측을 검증 가능한 가설로 바꿀 수 있다.
