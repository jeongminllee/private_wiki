# AI 엔지니어 데일리 브리핑

**2026년 8월 19일 수요일**
오늘은 **8월 18일 공개 자료를 최우선**으로 확인했고, 연구 쪽은 8월 17일 신규 논문까지 포함했습니다.

오늘의 흐름은 상당히 선명합니다. **① frontier 모델 개발에서 모니터링·격리 비용 자체가 compute budget의 일부가 되고 있고, ② RAG는 single-vector embedding에서 token-level late interaction으로 다시 확장되고 있으며, ③ agent는 memory·identity·tenant isolation·실행 환경을 모델과 별도 시스템으로 설계해야 한다는 방향이 강해지고 있습니다.** 특히 OpenAI가 내부 모니터링 오버헤드를 추론 compute의 약 20%로 추산했다는 사실은, 안전·보안이 더 이상 “추가 로그 몇 개” 수준의 비용이 아니라는 점을 보여줍니다. ([OpenAI][1])

## 1. 필독 | OpenAI, frontier RL을 멈추고 모니터링에 추론 compute 약 20%를 투입

**무엇이 바뀌었나.** OpenAI는 8월 18일 최근 OpenAI–Hugging Face 사고와 차기 모델 Astra가 Preparedness Framework의 **Critical cybersecurity capability 수준에 도달할 가능성**을 근거로 모델 개발 프로세스를 강화했다고 밝혔습니다. 배포 예정 최신 모델의 RL training을 2주간 중단했고, 가장 큰 frontier RL run은 현재도 보류 상태입니다. Astra 관련 workload 상당수 역시 새 보안 기준을 충족할 때까지 멈춰 있습니다. Astra가 이미 Critical로 확정됐다는 의미는 아니며, OpenAI의 표현은 “may meet / may have critical capability”입니다. ([OpenAI][1])

가장 눈에 띄는 변화는 **multistage monitoring**입니다. Activation classifier가 sampled token마다 모델 내부 활동을 검사하고, 의심 신호를 고비용 자동 조사기로 넘깁니다. 이 조사기는 tool action, reasoning, 전체 activity sequence를 함께 보며 unauthorized access·data theft·safeguard bypass 등을 찾습니다. Critical boundary violation 가능성이 제기되면 최고 우선순위 alert가 발생하고, 담당팀이 30분 내 false positive라고 확정하지 못하면 해당 작업을 중단하는 운영 규칙을 사용합니다. Sol급 이상 모델의 tool-using RL/eval과 Astra의 tool-using inference에는 이 모니터링이 필수이며, OpenAI는 현재 **모니터링 비용을 대상 inference compute의 약 20%**로 추산합니다. ([OpenAI][1])

**왜 중요한가.** Frontier training의 실제 계산비용을 앞으로 단순히 `training FLOPs`로만 계산하기 어려워집니다. 더 현실적인 식은 다음에 가까워집니다.

```text
Total frontier compute
=
training
+ evaluation
+ red teaming
+ safety monitoring
+ security replication
+ aborted / quarantined runs
```

즉 safety와 observability가 GPU budget을 직접 소비하는 **first-class workload**가 됩니다. 일반 기업 agent에서도 같은 원칙을 축소해 적용할 수 있습니다. 고위험 tool을 쓰는 요청은 더 강한 sandbox·trace·verification을 거치고, read-only 작업은 더 가벼운 monitoring tier를 사용하는 식입니다. OpenAI도 workload isolation, network isolation, standing privilege 감소와 지속적인 security testing을 함께 강화했습니다. ([OpenAI][1])

**실무 적용.** Agent platform에 다음 네 지표를 별도로 두는 것을 권합니다.

```text
agent_compute
monitoring_compute
blocked_or_paused_runs
security_overhead_ratio
```

그리고 `security_overhead_ratio`가 높아진다고 무조건 비효율로 보지 말고, side effect가 큰 workload의 **운영 비용**으로 분리하는 것이 좋습니다.

**주의·후속 관찰.** Chain-of-thought/activation monitoring이 장기적으로 어느 정도 신뢰할 수 있는지는 아직 열린 문제입니다. OpenAI도 Preparedness Framework를 개정하고 몇 주 안에 기술 보고서를 추가 공개하겠다고 밝혔습니다. ([OpenAI][1])

**원문:** **[공식 발표] OpenAI — Pacing model development in an era of cyber-critical capabilities** ([OpenAI][1])

## 2. 필독 | Sentence Transformers 6.0 — ColBERT식 Multi-Vector retrieval이 표준 API 안으로

**무엇이 바뀌었나.** Sentence Transformers v6.0에 네 번째 모델 유형인 **`MultiVectorEncoder`**가 추가됐습니다. 이제 PyLate checkpoint, Stanford ColBERT checkpoint, ColPali 계열 visual-document retrieval 모델을 Sentence Transformers의 동일한 API로 로드할 수 있습니다. Dense embedding이 문서 전체를 벡터 하나로 압축하는 것과 달리, multi-vector 방식은 token별 representation을 남긴 뒤 query token과 document token 사이의 **MaxSim late interaction**으로 relevance를 계산합니다. ([Hugging Face][2])

이 변화가 흥미로운 이유는 RAG architecture의 선택지가 다시 넓어지기 때문입니다.

```text
Dense embedding
문서 → 1 vector

Late interaction
문서 → N token vectors
query ↔ document token별 MaxSim
```

Dense embedding은 저렴하고 index가 작지만 문서 전체를 하나의 벡터로 압축하면서 희귀 identifier, 여러 조건이 섞인 query, 긴 문서의 세부 문맥을 잃을 수 있습니다. Late interaction은 그 정보를 더 많이 보존하는 대신 index 크기와 scoring 비용이 증가합니다. Visual document retrieval에서는 OCR 없이 page image 자체와 query를 matching하는 ColPali 계열도 같은 API에서 사용할 수 있습니다. ([Hugging Face][2])

비용 차이도 꽤 큽니다. 공식 예제에서 Natural Questions 4,874개 passage는 `all-MiniLM-L6-v2` dense index가 약 7.5MB인 반면 `LateOn` raw float32 multi-vector representation은 311.5MB, 약 **42배**였습니다. 다만 fast-PLAID 압축을 사용하면 같은 608,414 token vector가 92MB로 줄었고, 동일 corpus를 4096차원 `Qwen3-Embedding-8B` dense vector로 저장할 경우 약 80MB 수준이라 고차원 dense embedding과는 비슷한 영역까지 내려옵니다. ([Hugging Face][2])

**실무 적용.** 모든 RAG를 multi-vector로 바꿀 필요는 없습니다. 다음 구조가 현실적입니다.

```text
대량 corpus
   ↓
cheap dense / BM25 retrieval
   ↓
top 50~200 candidates
   ↓
MultiVector MaxSim
   ↓
top 10
   ↓
LLM
```

특히 source-code symbol, 논문 전문용어, 제품 SKU, 법률 조항처럼 **정확한 token-level matching이 중요한 retrieval**에서 먼저 A/B test할 가치가 큽니다.

**주의·후속 관찰.** v6.0은 `transformers 5.x`, `torch 2.2+`, `huggingface-hub 1.x`가 필요하며 migration guide에 breaking change가 포함되어 있습니다. 기존 embedding service에 그냥 `pip install -U`하기보다 별도 environment에서 승격해야 합니다. ([Hugging Face][2])

**원문:** **[공식 기술 글] Hugging Face — Multi-Vector Embedding Models with Sentence Transformers** ([Hugging Face][2])

## 3. GPU·데이터 인프라 | NVIDIA, 1억600만 × 2048차원 UMAP을 8×H100에서 8분

**무엇이 바뀌었나.** NVIDIA는 cuML·cuVS의 multi-GPU all-neighbors kNN 구현을 이용해 UMAP training 전체를 여러 GPU로 확장하는 방법을 공개했습니다. 핵심은 전체 데이터를 여러 balanced cluster로 나누고, cluster 경계의 neighbor 손실을 줄이기 위해 일정량을 overlap한 뒤 각 GPU에서 local kNN graph를 계산하고 최종 graph를 병합하는 방식입니다. 이 구조는 global all-to-all communication을 피하면서 UMAP의 가장 비싼 단계인 all-neighbors graph construction을 분산합니다. ([NVIDIA Developer][3])

실험은 8×H100과 2TiB CPU RAM을 가진 DGX에서 진행됐습니다. **106M × 2048-dimensional MIRACL dataset**, 약 870GB 규모를 end-to-end로 약 8분에 처리했습니다. NVIDIA는 최대 74배 speedup을 보고하지만, 여기에는 중요한 단서가 있습니다. CPU UMAP은 full-scale 데이터에서 2TiB RAM으로도 완료되지 못했기 때문에 **74배의 CPU baseline은 작은 subset의 measured scaling에서 외삽한 projected runtime**입니다. 실제 full-scale CPU 실행 대비 직접 측정된 74배는 아닙니다. ([NVIDIA Developer][3])

**왜 중요한가.** LLM 시대에 UMAP은 단순 시각화 도구가 아닙니다. 수천만~수억 개 embedding을 가진 corpus에서는 다음 용도로 활용됩니다.

```text
RAG corpus 구조 확인
embedding drift 탐지
중복·outlier 탐색
topic / cluster 분석
training-data inspection
```

그동안 데이터가 너무 커지면 UMAP 자체를 subsampling해야 했지만, multi-GPU 경로가 실용화되면 **전체 embedding space를 직접 검사하는 데이터 엔지니어링 workflow**가 가능해집니다. ([NVIDIA Developer][3])

두 핵심 knob은 `knn_n_clusters`와 `knn_overlap_factor`입니다. Overlap을 높이면 cluster boundary의 neighbor recall이 개선되지만 compute·memory가 증가하고, cluster 수를 늘리면 GPU당 memory는 줄지만 partition overhead가 늘어납니다. NVIDIA는 overlap 2를 시작점으로 제시하고, GPU memory에 맞춰 cluster 수를 함께 조절하는 방법을 설명합니다. ([NVIDIA Developer][3])

**주의·후속 관찰.** 8분이라는 숫자보다 **embedding quality를 유지하면서 scale-out이 되는지**가 핵심입니다. 자체 corpus에서는 trustworthiness 외에도 cluster stability와 downstream retrieval 품질을 같이 확인해야 합니다.

**원문:** **[NVIDIA 기술 블로그] Multi-GPU UMAP with cuML/cuVS** ([NVIDIA Developer][3])

## 4. Agent 보안 | Axonius의 multi-tenant 설계: Agent에게 관리자 권한을 주지 않고 사용자 identity를 끝까지 전달

**무엇이 바뀌었나.** Axonius와 AWS가 multi-tenant SaaS 환경에서 AgentCore를 적용한 실제 architecture를 공개했습니다. Axonius는 pool, shared-runtime+gateway인 bridge, tenant별 dedicated runtime인 silo 세 방식을 비교한 뒤 **tenant별 dedicated AgentCore runtime + session별 isolated microVM** 구조를 선택했습니다. 각 고객 runtime은 고객 VPC 안의 전용 ENI를 통해서만 해당 고객 backend에 접근하며, 다른 tenant와 process state를 공유하지 않습니다. ([Amazon Web Services, Inc.][4])

더 중요한 설계는 **사용자의 identity를 agent가 대신 사용하는 방식**입니다. 사용자가 질문하면 Axonius가 short-lived impersonation JWT를 만들고, 여기에 user identity·tenant ID·session ID·actor ID를 담습니다. Agent runtime은 model을 호출하기 전에 token의 signature, expiry, revocation, permission을 검증하며, live-data tool도 동일 JWT를 사용합니다. 따라서 agent는 자신이 가진 별도 superuser credential로 데이터를 보는 것이 아니라 **원래 사용자가 볼 수 있는 데이터 범위만** 접근합니다. ([Amazon Web Services, Inc.][4])

이건 enterprise agent 설계에서 상당히 중요한 패턴입니다.

```text
나쁜 구조
User → Agent(Super Admin) → 모든 시스템

권장 구조
User identity
   ↓
short-lived delegated capability
   ↓
Agent
   ↓
동일 permission으로 Tool 실행
```

Model이 hallucination하더라도 authorization boundary는 application 밖에서 강제됩니다.

**실무 적용.** Tenant-aware agent를 만든다면 최소한 `tenant_id`를 prompt에 넣는 것으로 끝내지 말고 다음 세 계층에서 각각 검증하는 편이 좋습니다.

```text
Identity layer  → JWT / principal
Runtime layer   → tenant isolation
Tool layer      → resource-level permission
```

Axonius는 token budget 초과 시 CloudWatch alert와 IAM deny를 이용해 invocation 자체를 차단하는 비용 통제도 함께 적용합니다. ([Amazon Web Services, Inc.][4])

**주의·후속 관찰.** Silo 방식은 격리가 강한 대신 tenant마다 runtime·endpoint를 관리해야 해 provisioning latency와 운영 복잡도가 증가하며, 기본 account quota도 고려해야 합니다. Axonius 사례에서도 이 trade-off가 명시돼 있습니다. ([Amazon Web Services, Inc.][4])

**원문:** **[AWS·Axonius 기술 사례] Secure multi-tenant AI agents on Bedrock AgentCore** ([Amazon Web Services, Inc.][4])

## 5. Agent Memory | IBM: Memory는 “많을수록 좋다”가 아니라 모델별로 용량을 맞춰야 한다

**무엇이 바뀌었나.** IBM Research가 Hugging Face에 공개한 ALTK-Evolve 연구는 8개 모델에서 agent memory의 효과를 비교했습니다. 여기서 memory는 과거 transcript를 그대로 넣는 것이 아니라 **성공·실패 trajectory에서 추출한 reusable guideline**입니다. 모델 weight는 바꾸지 않고, inference 때 전체 guideline을 넣거나 task 관련 일부만 retrieval해 제공합니다. ([Hugging Face][5])

결과가 재미있습니다. DeepSeek-V3.2처럼 아직 성능 headroom이 있고 많은 context를 처리할 수 있는 강한 모델은 **전체 guideline set**을 넣었을 때 task completion이 +9.5%p 개선됐습니다. 반면 gpt-oss-120b는 compact core + task-specific retrieval 방식에서 **+16.1%p**, 추가 token은 약 5%에 그쳤고, 전체 guideline을 넣으면 개선폭은 더 작으면서 token 비용은 약 50% 더 늘었습니다. GLM-5는 연구진의 해당 task에서는 memory를 추가해도 측정 가능한 개선이 없었습니다. ([Hugging Face][5])

**왜 중요한가.** Agent memory를 기능 on/off로 보면 안 된다는 뜻입니다.

```text
Memory policy A
모든 경험을 매 turn 제공

Memory policy B
고신뢰 core + 관련 경험 retrieval

Memory policy C
memory 없음
```

모델 크기·context window·benchmark headroom·task distribution에 따라 최적점이 달라집니다. 특히 작은 모델에게 긴 memory를 주면 “더 많이 알려줬는데도” 오히려 중요한 instruction이 묻힐 수 있습니다.

**실무 적용.** Agent를 새 모델로 교체할 때 memory system을 그대로 가져오지 말고 다음 세 조건을 반드시 다시 평가하는 것이 좋습니다.

```text
No memory
Selective memory
Full memory
```

평가 지표는 `strict_success`, `tokens_per_success`, `memory_retrieval_precision`, `repeated_error_rate` 정도면 충분합니다.

**주의·후속 관찰.** 결과는 AppWorld의 585개 multi-step task에서 얻은 것이며, “GLM-5는 memory가 필요 없다” 같은 일반화는 할 수 없습니다. 연구진도 saturated라는 표현을 관찰 패턴으로만 사용합니다. ([Hugging Face][5])

**원문:** **[IBM Research 기술 연구] How Much Memory Does Your Agent Actually Need?** ([Hugging Face][5])

## 6. 과학 AI | NVIDIA ALCHEMI: 코드가 실행된다고 과학적으로 맞는 것은 아니다

**무엇이 바뀌었나.** NVIDIA는 ALCHEMI Toolkit의 agent skill·reference file을 coding agent에 제공해 ML interatomic-potential simulation workflow를 생성하는 실험을 공개했습니다. Claude Opus 4.8 High를 사용해 silicon EOS, O/Cu adsorption, lithium self-diffusion 세 workflow × 다섯 prompt 수준 × 세 샘플로 **45개 pipeline**을 만들었습니다. Runnable Python 환경과 toolkit reference를 agent에게 제공한 최종 실험에서는 broken import나 존재하지 않는 API 참조가 사라졌지만, GPU에서 screening하면 45개 중 38개만 완료했고 7개는 GPU-specific execution path에서 실패했습니다. ([NVIDIA Developer][6])

Prompt를 자세하게 만든다고 과학 결과가 좋아지는 것도 아니었습니다. 간단한 Sketch는 평균 약 2.4M token, Contract 수준은 약 10M token을 사용하면서 code structure와 reusability는 개선됐지만, 기본적으로 계산하려는 물리량 자체는 첫 단계부터 동일했습니다. 즉 더 구체적인 prompt가 **약 4배의 token**을 쓰며 주로 software quality를 높였고 physical correctness를 자동 보장하지는 않았습니다. ([NVIDIA Developer][6])

더 중요한 failure가 lithium diffusion에서 나왔습니다. Langevin thermostat을 사용한 pipeline은 통계적으로 안정적인 결과를 냈지만 실제 diffusion coefficient가 NVE 결과보다 **3~5배 낮았습니다.** 숫자와 error bar만 보면 멀쩡하지만, thermostat friction이 물리량 자체를 왜곡한 것입니다. 또 연구진의 별도 probe에서는 agent가 물리적으로 부적절한 simulation request를 스스로 거부한 사례가 없었습니다. ([NVIDIA Developer][6])

**왜 중요한가.** Scientific agent의 verifier는 최소 두 개여야 합니다.

```text
Software verifier
- import 성공
- 실행 성공
- numerical stability
- test 통과

Scientific verifier
- 물리적으로 타당한 protocol인가
- 독립 reference와 맞는가
- ensemble / boundary / units가 적절한가
```

LLM이 만든 self-test만 사용하는 것도 위험합니다. NVIDIA 사례에서는 잘못된 상수를 사용한 코드가 같은 잘못된 상수로 synthetic test data를 만들어 **자기 테스트를 통과**한 경우도 있었습니다. ([NVIDIA Developer][6])

**실무 적용.** 과학·ML 연구 agent에는 `independent_reference`, `physical_invariant`, `target_hardware_run`, `external_ground_truth`를 결과 artifact에 포함시키는 것이 좋습니다.

**원문:** **[NVIDIA 기술 블로그] AI Coding Agents + ALCHEMI Toolkit** ([NVIDIA Developer][6])

## 7. 산업·Coding Agent | Asana: 5년짜리 migration 계획을 4개 Agent 병렬 작업으로 2주에 정리

**무엇이 바뀌었나.** OpenAI와 Asana가 8월 18일 공개한 customer case에 따르면, Asana는 오래된 React testing stack인 Enzyme 제거 작업을 Codex로 약 **2 calendar weeks, 1.5주 수준의 engineering effort** 안에 완료했습니다. 기존 staffing plan은 최소 5년, 약 600만 달러 규모로 추정됐고, 이번 model+infrastructure 비용은 약 1만2천 달러였습니다. 이 숫자는 독립 benchmark가 아니라 Asana의 기존 내부 계획과 실제 agent project를 비교한 customer story라는 점을 전제로 봐야 합니다. ([OpenAI][7])

작업 방식이 더 중요합니다. 최대 **4개 coding agent**가 각각 별도 codebase copy에서 병렬로 작업했고, 사람 engineer가 하루 두 번 진행 상황을 확인하며 **모든 제안 변경을 직접 review**했습니다. 처음부터 복잡한 multi-agent architecture를 만든 것이 아니라 다섯 문장 정도의 비교적 단순한 prompt를 사용했고, Asana는 오히려 elaborate한 instruction보다 단순한 지시가 더 잘 작동했다고 설명합니다. ([OpenAI][7])

**왜 중요한가.** Coding agent에 가장 잘 맞는 대형 프로젝트의 유형을 보여줍니다.

```text
좋은 후보
- 목표 상태가 명확함
- 수정 패턴이 반복됨
- compiler / test라는 강한 oracle 존재
- 병렬화 가능
- 변경 단위 review 가능

나쁜 후보
- 제품 요구사항이 계속 변함
- 정답 oracle이 없음
- architecture 결정이 핵심
- 여러 agent가 동일 global state 수정
```

즉 “에이전트가 5년 일을 2주에 했다”보다 **5년짜리 기술 부채 중 어떤 종류가 agent-parallelizable한가**를 보는 것이 훨씬 유용합니다.

**실무 적용.** 조직의 backlog에서 framework migration, deprecated API replacement, test-library 교체, type annotation 정리처럼 **기계적이고 검증 가능한 장기 부채**를 별도 분류해보는 것이 좋습니다. 각 agent는 독립 worktree에서 실행하고, merge는 CI와 사람이 통제하는 구조가 안전합니다.

**주의·후속 관찰.** `$6M → $12K`를 일반적인 coding-agent ROI로 확대해석해서는 안 됩니다. 600만 달러는 과거 staffing plan의 추정치이며, 모든 legacy migration이 이 정도로 압축되지는 않는다고 Asana 스스로도 명시합니다. ([OpenAI][7])

**원문:** **[OpenAI·Asana 공식 사례] Asana cleared 5 years of engineering work in 2 weeks with Codex** ([OpenAI][7])

## 8. GPU 연구 | DB-SpMSpV — 동적으로 변하는 activation sparsity에 따라 GPU 실행 경로를 런타임에서 바꾼다

**무엇이 바뀌었나.** 8월 17일 공개된 DB-SpMSpV는 Sparse Matrix–Sparse Vector Multiplication에서 matrix layout과 실행 전략을 분리합니다. Matrix를 fixed-size 2D block으로 나누고 상위에는 CSR과 CSC 두 view를 유지하되, 실제 block payload는 하나만 저장합니다. Runtime은 입력 vector의 **global block sparsity**를 보고 row-driven pull 또는 column-driven push를 선택하고, block 내부 sparsity에 따라 microkernel을 다시 고릅니다. ([arXiv][8])

A100과 RTX 4090에서 SuiteSparse·graph workload와 3개 open LLM을 평가한 결과, 논문 저자들은 A100에서 cuSPARSE 대비 평균 **5.48~64.34배**, TileSpMSpV 대비 2.36~14.01배 speedup을 보고했습니다. LLM decoding에 적용한 `DB-Decoding`은 **single-token linear layer를 최대 4.5배** 가속했습니다. ([arXiv][8])

**왜 중요한가.** Autoregressive decode는 batch가 작을수록 GEMM보다 GEMV에 가까워지고 memory bandwidth의 영향을 크게 받습니다. 동시에 activation sparsity가 input마다 변한다면 고정 sparse kernel 하나만으로 모든 token을 최적으로 처리하기 어렵습니다.

```text
Token A → sparsity 높음 → push
Token B → sparsity 낮음 → pull
Block 1 → microkernel X
Block 2 → microkernel Y
```

즉 **dynamic sparsity를 scheduler problem으로 취급**하는 접근입니다.

**실무 적용.** Sparse decoding을 평가할 때 평균 sparsity 하나만 기록하지 말고 다음 분포를 같이 저장하는 것이 좋습니다.

```text
activation_sparsity_per_token
block_sparsity_distribution
kernel_selected
memory_bytes_read
kernel_time
```

그래야 sparsity가 높아도 irregular access 때문에 오히려 느려지는 경우를 구분할 수 있습니다.

**주의·후속 관찰.** 4.5배는 single-token sparse linear layer의 최대치이지 전체 dense LLM server가 4.5배 빨라진다는 뜻이 아닙니다. 실제 모델에서 pruning 품질, sparse representation 변환 비용, attention·KV cache 등의 비중을 포함한 E2E benchmark가 필요합니다. ([arXiv][8])

**원문:** **[논문] DB-SpMSpV: Dual-View Blocked Sparse Matrix-Sparse Vector Multiplication** ([arXiv][8])

# 오늘의 실습 | Dense Retrieval vs Multi-Vector Late Interaction 직접 비교하기

오늘은 Sentence Transformers 6.0을 이용해 **같은 corpus에 dense retrieval과 late interaction을 붙여보는 실험**을 추천합니다. v6.0은 `MultiVectorEncoder`를 기본 API로 제공하고, PyLate·ColBERT 계열 checkpoint를 직접 로드할 수 있습니다. ([Hugging Face][2])

먼저 별도 환경을 만들고 의존성을 올립니다.

```bash
uv venv
source .venv/bin/activate

uv pip install -U sentence-transformers datasets
```

v6.0은 `transformers 5.x`, `torch 2.2+`, `huggingface-hub 1.x`가 필요하므로 기존 프로젝트 환경을 바로 업그레이드하지 않는 것이 좋습니다. ([Hugging Face][2])

비교할 두 모델은 다음처럼 잡으면 충분합니다.

```text
Dense
sentence-transformers/all-MiniLM-L6-v2

Multi-vector
lightonai/LateOn
```

Multi-vector 모델은 다음처럼 로드됩니다.

```python
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("lightonai/LateOn")
```

Corpus는 1,000~5,000개 정도의 문서로 시작하십시오. Query는 세 종류로 나누는 것이 중요합니다.

```text
A. 일반 의미 질의
"GPU memory를 줄이는 방법"

B. exact identifier
"CUDA_ERROR_ILLEGAL_ADDRESS 원인이 뭐야?"

C. multi-clause
"FlashAttention을 사용하면서 FP8 KV cache를 지원하고
B200에서 동작하는 serving backend"
```

각 query에 대해 다음을 기록합니다.

```text
Recall@10
MRR@10

index_size_mb
index_build_time

query_p50_ms
query_p95_ms
```

그리고 가장 중요한 것은 **query type별 성능**입니다.

```text
Dense            Multi-vector

일반 의미        ?
Identifier       ?
Multi-clause     ?
```

Late interaction의 기대 효과는 전체 평균 점수가 무조건 더 높아지는 것이 아니라, **single-vector compression에서 사라지는 token-level evidence를 얼마나 되살리는가**에 있습니다. 반대로 index와 query latency가 크게 증가한다면 모든 query를 late interaction으로 보낼 필요가 없습니다. ([Hugging Face][2])

마지막으로 다음 router를 하나 넣어보면 실전적인 실험이 됩니다.

```text
일반 query
→ Dense

identifier / code symbol / 긴 multi-clause query
→ Multi-vector
```

그리고 세 시스템을 비교합니다.

```text
Dense only
Multi-vector only
Query-routed hybrid
```

평가 기준은 단순 retrieval accuracy가 아니라:

```text
retrieval_quality
÷
(index cost + query latency)
```

입니다.

이 실험을 한 번 만들어두면 이후 ColPali를 추가해 **PDF 페이지·스크린샷을 OCR 없이 검색하는 visual RAG**까지 같은 framework 안에서 확장할 수 있습니다. ([Hugging Face][2])
