# AI 엔지니어 데일리 브리핑 — 2026년 9월 16일

한국시간 **9월 16일 아침** 기준입니다. 오늘은 상당히 좋습니다. 9월 15일 공개된 NVIDIA의 AI Infra Summit 자료와, 9월 14일 UTC 제출 후 15일 신규 목록에 올라온 Agent 관련 연구들이 한꺼번에 나왔습니다. 오늘의 큰 흐름은 **① AI 인프라의 핵심 지표가 GPU 이용률에서 `tokens/MW`로 올라가고 있고, ② Agent workload에 맞춰 KV cache·skill routing·failure diagnosis 자체가 전용 알고리즘으로 분화되며, ③ 강한 Agent를 만드는 방법이 “모델 하나를 크게”보다 harness·router·verifier·실행 인터페이스를 설계하는 문제로 이동하고 있다는 것**입니다.

## 1. NVIDIA DSX MaxLPS 실측: 같은 전력으로 B200 노드를 16→19개 돌려 token throughput +24% ★★★★★

9월 15일 NVIDIA AI Infra Summit에서 가장 주목할 부분은 새 GPU보다 **전력 자체가 scheduler의 resource가 됐다는 것**입니다. Lambda가 HGX B200 서버 5개 rack, 19개 node에서 DSX MaxLPS를 검증했는데, 16개 node를 full power로 운영할 때와 동일한 facility power budget 안에서 19개 node를 운영해 cluster-wide token throughput을 약 **4M → 5M tokens/s, +24%**, performance/W를 **+23%** 높였다고 발표했습니다. MaxLPS는 GPU와 rack의 실시간 전력 사용량을 보고 static provisioning에서 남는 headroom을 다른 node로 재분배합니다. :chatgpt-content-reference{index="0"}

지난 며칠간 살펴본 “모델별 power cap”보다 한 단계 위의 abstraction입니다. 개별 B200의 최적 power limit을 찾는 것에서 끝나는 것이 아니라, `training job A가 순간적으로 전력을 덜 씀 → inference node B가 headroom 사용`처럼 **rack 전체의 power budget을 동적 resource pool로 취급**합니다. CPU cluster에서 scheduler가 memory·core를 배분하듯 앞으로 GPU cluster scheduler는 `GPU / HBM / network / power`를 함께 배분하게 될 가능성이 큽니다. NVIDIA는 Vera Rubin 환경에서는 적절한 deployment 조건에서 같은 megawatt budget으로 최대 40% 더 많은 GPU capacity를 운용할 수 있다고 주장하고 있지만, 이 부분은 차세대 시스템에 대한 NVIDIA의 projection이므로 B200 실측 +24%와 구분해서 봐야 합니다. :chatgpt-content-reference{index="1"}

더 흥미로운 것은 **DSX Flex**입니다. Silicon Valley Power가 grid load-shedding signal을 보내자 수천 GPU 규모 AI factory가 사전에 설정된 job priority에 따라 저우선 작업을 throttle·pause하고 고우선 inference는 유지하면서 전력을 **4MW→3MW**로 낮췄습니다. 실제 electricity grid signal과 AI job scheduler가 연결되는 구조입니다. 즉 데이터센터 scheduling이 `GPU utilization`을 넘어 **전력 가격·grid state·job priority**까지 고려하는 시스템 문제로 확장되고 있습니다. :chatgpt-content-reference{index="2"}

주의할 점은 “tokens/MW”도 workload specification 없이는 비교하기 어렵다는 것입니다. 모델, precision, context length, latency SLO가 다르면 동일 tokens/MW라도 의미가 달라집니다. 앞으로 AI infra benchmark에는 `model + precision + TTFT/TPOT SLO + tokens/s + watts`가 함께 필요합니다.

원문: [공식 발표 · NVIDIA AI Infra Summit — Vera Rubin and DSX](https://blogs.nvidia.com/blog/ai-infra-summit-vera-rubin-dsx-energy-efficiencies-tokens-per-watt-ai-factories/) · [공식 기술 블로그 · From Megawatts to Tokens](https://blogs.nvidia.com/blog/from-megawatts-to-tokens-how-nvidia-maximizes-ai-factory-production/)

## 2. AgentKV: Agent의 KV cache는 “최근 token”보다 `Think / Act / Tool` phase를 봐야 한다 ★★★★★

9월 14일 제출된 **AgentKV**는 현재 Agent serving을 한다면 오늘 가장 볼 만한 논문입니다. 기존 KV eviction은 대체로 최근 query가 미래 query를 대표한다는 가정으로 중요한 key를 선택합니다. 하지만 연구진은 Agent trajectory의 query가 `think`, `act`, `tool`, 기타 phase별로 **서로 다른 subspace를 형성**하며, 최근 thinking token만 보고 KV를 버리면 다음 tool/act phase에 필요한 오래된 key를 과소평가한다고 분석했습니다. :chatgpt-content-reference{index="5"}

AgentKV는 그래서 phase마다 작은 query buffer를 따로 유지하고, 이 buffer들의 union을 기준으로 cached key의 중요도를 계산합니다. 동시에 multi-turn session 간에 압축된 KV state를 유지하고 retained page를 online compaction합니다. 두 모델, 여섯 task domain, 세 KV budget에서 기존 R-KV 대비 평균 **+5.5 task-score point**, Tri-Attention 대비 +5.3p를 보고했으며, full-KV upstream SGLang 대비 output-token throughput은 조건에 따라 최대 **1.80×**였습니다. :chatgpt-content-reference{index="6"}

이건 Agent serving에서 중요한 관점 변화입니다. 일반 chatbot에서는 `최근 대화 ≈ 미래 대화와 비슷함`이라는 가정이 어느 정도 맞지만 Agent에서는 trajectory가

`reasoning → tool selection → tool result → reasoning → action`

으로 상태를 계속 전환합니다. 따라서 KV eviction도 LRU/recency 문제가 아니라 **workflow semantics를 알아야 하는 runtime policy**가 됩니다. Agent framework가 알고 있는 “지금 어느 phase인가”라는 정보가 serving engine까지 내려가야 한다는 뜻입니다. :chatgpt-content-reference{index="7"}

코드도 공개됐습니다. 연구 repository는 compact SGLang-style engine 안에 AgentKV eviction/compaction을 구현하고 `identity`, `agentkv`, `R-KV`, `StreamingLLM`, `TriAttention` policy를 같은 harness에서 비교할 수 있도록 BFCL과 τ²-bench fork까지 포함합니다. 다만 아직 upstream SGLang의 일반 production feature라기보다는 연구 구현이고, repository 자체도 막 공개된 상태이므로 운영 환경에 바로 적용하기보다는 benchmark 대상으로 보는 편이 좋습니다. :chatgpt-content-reference{index="8"}

원문: [논문 · AgentKV: Phase-Aware KV Eviction for Agentic LLMs](https://arxiv.org/abs/2609.14872) · [GitHub · LiuTaowen-Tony/agentkv](https://github.com/LiuTaowen-Tony/agentkv)

## 3. The Router Within: Skill 목록 전체를 prompt에 넣지 않아도 LLM 내부 hidden state가 이미 “어떤 Skill이 필요한지” 알고 있다 ★★★★★

Agent skill library가 커지면 현재 방식에는 문제가 있습니다. Claude/Codex 계열의 progressive disclosure든 custom harness든 일반적으로 skill name·description 등의 metadata를 prompt에 넣거나 별도 retriever/reranker를 사용합니다. Skill이 수천 개가 되면 metadata 자체가 context를 먹고 attention도 분산됩니다. **The Router Within**은 routing signal이 이미 frozen LLM의 hidden representation 안에 있는지 묻습니다. :chatgpt-content-reference{index="11"}

제안한 **Gavel(Glance And Verdict)**은 backbone LLM을 전혀 fine-tuning하지 않고 두 개의 작은 linear projection만 학습합니다. Skill 설치 시 해당 skill을 한 번 LLM에 통과시켜 mid-layer hidden state를 searchable bank로 만들고, runtime에서는 task/trajectory hidden state와 비교해 전체 library를 먼저 shortlist합니다. 이후 후보 skill만 다시 model에 넣어 likelihood와 yes/no relevance 판단을 결합합니다. 즉 `embedding model → reranker → LLM`을 별도로 유지하지 않고 **Agent LLM 자신의 representation을 router로 재사용**합니다. :chatgpt-content-reference{index="12"}

Qwen3-32B에서 progressive disclosure와 1.2B~16B 규모 외부 retrieve/rerank pipeline보다 written task에서 최대 **+13.4p**, agent 실행 중간에 skill 필요성이 드러나는 상황에서는 최대 **+21.9p** 높은 routing 결과를 보고했습니다. 특히 tool output이나 중간 plan에서 새 skill의 필요성이 드러나는 **mid-rollout routing**을 다룬다는 점이 중요합니다. :chatgpt-content-reference{index="13"}

여기서 성능 수치를 “32B Agent가 frontier model보다 task를 잘 해결한다”로 읽으면 안 됩니다. 논문의 주된 metric은 **올바른 skill을 선택·trigger했는가**이고 end-to-end task success와는 다릅니다. 또한 routing projection은 backbone hidden-state geometry에 의존하므로 모델을 교체했을 때 다시 calibration/training해야 할 가능성이 있습니다. 그래도 skill을 수백·수천 개로 확장하려면 “모든 Skill metadata를 context에 밀어넣는다”는 구조가 오래 가기 어렵다는 문제 제기는 매우 적절합니다.

원문: [논문 · The Router Within: Eliciting Native Skill Routing from a Frozen LLM](https://arxiv.org/abs/2609.15982)

## 4. Stellar Colosseum: Long-horizon 연구 Agent는 바로 증명하지 않고 `탐색 → readiness gate → decomposition → falsification → aggregation`한다 ★★★★★

**Stellar Colosseum**은 긴 수학·이론 CS 연구 문제를 Agent에게 맡길 때 단순히 subagent 수를 늘리는 방식에서 벗어난 harness입니다. 먼저 여러 solution strategy를 병렬로 탐색하고, 각 route가 충분히 성숙했는지를 **readiness gate**로 검사한 뒤에만 section-level subproblem으로 분해합니다. 각 section은 서로 dependency를 가지며 verifier의 반론은 전체를 다시 시작시키는 대신 문제가 있는 부분으로 되돌아갑니다. :chatgpt-content-reference{index="15"}

각 단계에서도 하나의 candidate를 믿지 않고 여러 candidate를 생성해 **targeted falsification**으로 공격한 뒤 candidate와 critique를 tree aggregation으로 하나의 research artifact로 합칩니다. 이 workflow는 Google Antigravity Teamwork의 **Long Proof pattern**에도 통합됐다고 논문은 밝힙니다. :chatgpt-content-reference{index="16"}

Gemini 3.1 Pro/3.7 Flash 조합으로 연구 수준 theorem task인 TCS-Bench에서 **71.0%**, Gemini 3.1 Pro 기반 Codeforces 실험에서는 222문제 중 **218개**를 해결했다고 보고합니다. 더 흥미로운 것은 일부 FOCS/JMLR 논문에서 파생된 open problem에도 새로운 결과를 얻었다는 주장입니다. 다만 이는 막 공개된 preprint이며 “새로운 수학적 결과”의 독립적인 peer validation은 별개 문제입니다. benchmark 숫자 역시 Gemini 모델의 독립 성능이라기보다 **상당한 inference budget을 쓰는 harness + model 조합의 결과**로 봐야 합니다. :chatgpt-content-reference{index="17"}

Coding/Research Agent 설계에도 그대로 적용할 수 있는 패턴입니다. 복잡한 task를 받자마자 `Planner → 20 subagents`로 분해하는 대신 **먼저 competing hypotheses를 탐색하고 readiness를 통과한 route만 decomposition**하는 편이 불필요한 fan-out을 줄일 수 있습니다. 여기에 각 subproblem의 실패를 parent plan 전체가 아니라 해당 dependency node로 되돌리는 구조를 붙이면 장기 프로젝트의 수정 비용도 낮아집니다.

원문: [논문 · Stellar Colosseum: A Many-Agent Harness for Long-Horizon Research](https://arxiv.org/abs/2609.15983)

## 5. GitHub Copilot Auto가 `Efficiency / Balance / Intelligence` 세 tier로 — 모델 선택 자체가 사용자 조절 가능한 inference policy가 된다 ★★★★☆

GitHub는 9월 14일 Copilot의 **Auto model selection**에 세 가지 policy tier를 추가했습니다. `Efficiency`는 비용 중심, `Balance`는 비용·품질·latency 균형, `Intelligence`는 복잡한 task의 품질을 우선합니다. 중요한 것은 세 tier가 서로 다른 고정 모델 목록을 사용하는 것이 아니라 **동일한 available model pool에서 prompt별로 모델을 선택**한다는 점입니다. Intelligence를 선택해도 단순 docstring 추가 같은 요청은 작은 모델로 routing될 수 있습니다. :chatgpt-content-reference{index="19"}

이건 model routing이 backend의 숨은 구현 세부사항에서 **사용자가 조절하는 policy knob**로 올라오는 흐름입니다. 앞으로 Agent orchestration에서도 `small/large model`을 직접 hard-code하기보다 `cost budget`, `latency SLO`, `quality target`을 지정하면 router가 모델을 고르는 방식이 점점 일반적이 될 가능성이 큽니다. GitHub도 이번 기능을 사용자에게 model-selection trade-off를 더 많이 노출하기 위한 첫 단계라고 설명합니다. :chatgpt-content-reference{index="20"}

평가에서는 주의해야 할 점이 하나 생깁니다. 같은 Copilot Auto + Intelligence 설정으로 같은 benchmark를 돌려도 prompt 특성이나 available model pool이 바뀌면 실제 underlying model이 달라질 수 있습니다. 따라서 production/evaluation 로그에는 “Auto 사용”만 남길 것이 아니라 가능하면 **실제로 선택된 model, tier, 비용, latency**까지 기록해야 reproducibility가 유지됩니다. 요금도 tier에 고정된 것이 아니라 실제 선택된 모델 기준으로 청구됩니다. :chatgpt-content-reference{index="21"}

원문: [공식 릴리스 노트 · Configure cost and quality in Copilot auto model selection](https://github.blog/changelog/2026-09-14-configure-cost-and-quality-in-copilot-auto-model-selection/)

## 6. Continual Search: Agent가 실패한 이유를 찾는 작업도 “LLM에게 로그 한 번 읽혀보기”보다 검색 문제로 설계해야 한다 ★★★★★

Long-horizon Agent의 failure trace가 수십만 token이 되면 실패 원인이 실제 오류 지점과 매우 멀리 떨어져 있을 수 있습니다. **Root-Cause Attribution Is a Search Problem**은 one-shot LLM judge가 긴 trace를 읽을 때 초기의 그럴듯한 설명에 너무 빨리 고정되고, 뒤쪽의 결정적인 evidence를 충분히 탐색하지 않는 문제를 다룹니다. :chatgpt-content-reference{index="23"}

제안한 **Continual Search**는 첫 진단을 final answer로 취급하지 않습니다. 여러 turn에 걸쳐 현재 hypothesis를 계속 의심하고 아직 확인하지 않은 diagnostic evidence를 탐색하도록 judge를 반복 실행합니다. 기존 네 RCA benchmark와 새로 만든 **MegaRCA-Mix**에서 평가했고, latter는 long-horizon execution-heavy failure 50건을 사람이 annotation한 dataset입니다. :chatgpt-content-reference{index="24"}

MegaRCA-Mix에서 GPT-5.5의 F1은 **0.349 → 0.498**, 40% 이상 상대 개선됐습니다. 더 흥미로운 관찰은 동일 model family에서 잘 설계된 search loop의 lower-tier model이 higher-tier model을 이기는 경우가 있었다는 것입니다. 즉 Agent debugging에서도 모델 크기보다 **로그를 어떻게 탐색하게 만드는가**가 병목일 수 있다는 주장입니다. :chatgpt-content-reference{index="25"}

여기에는 분명한 한계가 있습니다. MegaRCA-Mix는 단 50개의 저자 제작 test case이며 아직 외부 재현도 충분하지 않습니다. 그래도 실무 원리는 꽤 강합니다. Agent 실패 분석을 `trace → LLM → 원인 한 줄`로 만들기보다 `hypothesis → evidence search → counter-evidence → attribution → confidence`라는 debugger workflow로 만드는 편이 더 합리적입니다.

원문: [논문 · Root-Cause Attribution Is a Search Problem: Continual Search for Long-Horizon Agent Failures](https://arxiv.org/abs/2609.13463)

## 7. ZGCM-1: 7B 모델의 의미보다 `Pretrain → 256K Midtrain → SFT` 데이터·체크포인트·로그를 전부 공개했다는 점이 더 중요 ★★★★★

**ZGCM-1**은 7.39B dense model로, 27개의 gated sliding-window attention layer와 5개의 global layer를 사용하고 최대 **256K context**를 지원합니다. Pretraining은 약 **4.19T tokens**, mid-training은 약 600B tokens이며 context를 16K→64K→256K로 단계적으로 확장했습니다. 학습 recipe에는 hybrid FP8와 Muon optimizer가 포함되고, interaction trajectory는 MDP의 state-action transition 형태로 재구성해 agentic capability를 학습시켰습니다. :chatgpt-content-reference{index="27"}

연구진은 16K pretraining에서 기존 설계 대비 **약 4.2× time-to-loss 효율 향상**을 보고하고, 수학·agentic search task 일부에서는 Qwen3-235B-A22B나 GLM-5.1 같은 훨씬 큰 모델과 경쟁 가능한 결과를 주장합니다. 다만 이는 저자들의 evaluation이므로 “7B가 235B보다 좋다”로 단순화하면 안 됩니다. benchmark마다 tool budget과 inference-time compute가 다르고, Agent task에서는 작은 모델이 외부 search/tool을 얼마나 사용하느냐가 parameter count만큼 중요합니다. :chatgpt-content-reference{index="28"}

이 프로젝트의 훨씬 큰 가치가 **reproducibility**에 있습니다. 최종 weight뿐 아니라 pretraining/mid-training/post-training weight, intermediate checkpoint, training code, stage별 data recipe, W&B log를 공개했습니다. Training Data Suite에는 pretraining 약 4.19T tokens, 16K/64K/256K mid-training dataset, 약 **4.57M SFT sample / 19.46B packed tokens**의 구성까지 정리되어 있습니다. 모델 능력 자체보다 “7B 모델을 처음부터 어떻게 만드는가”를 공부하는 사람에게 드문 full-stack training artifact입니다. :chatgpt-content-reference{index="29"}

특히 LLM training/fine-tuning 포트폴리오를 만든다면 최종 checkpoint만 따라 하지 말고 **16K → 64K → 256K checkpoint별 long-context 변화**, data-mixture 변화와 loss curve를 비교하는 식으로 활용하기 좋습니다.

## 8. “Is Bash All You Need?”: Agent에게 수십 개 typed tool을 주는 것보다 Bash 하나가 더 잘하고 token도 덜 썼다 ★★★★★

**Is Bash All You Need?**는 Agent tool interface 설계에서 상당히 도발적인 결과를 냈습니다. Enterprise digital-worker task인 TheAgentCompany와 APEX-Agents에서 Claude Opus 4.8과 GPT-5.5를 사용해 `typed tools`, `typed tools+Bash`, `Bash only`, `Bash+agent-generated persistent tools`, `programmatic tool calling` 다섯 구조를 비교했습니다. :chatgpt-content-reference{index="33"}

Bash-only Agent는 typed tools 대비 TheAgentCompany에서 **+21.8~24.5 percentage points**, APEX-Agents에서 +4.8~7.4p 높은 score를 기록하면서 전체 token 사용량도 **19~72% 적었습니다**. Typed tool을 Bash에 추가하거나 Agent가 persistent tool을 합성하도록 해도 pooled score의 유의미한 개선은 없었습니다. Programmatic tool calling은 direct typed tool보다 token 효율은 좋았지만 전반적으로 Bash-only보다 quality와 cost efficiency가 낮았습니다. :chatgpt-content-reference{index="34"}

왜 이런 결과가 나왔는지도 중요합니다. 수십 개의 tool schema를 계속 context에 실으면 그 자체가 token과 attention budget을 소비하는 반면 shell에서는 Agent가 익숙한 Unix primitive를 조합하고 중간 결과를 programmatically filter할 수 있습니다. 앞서 Gavel 논문에서 모든 Skill metadata를 context에 넣는 것이 비효율적이라고 지적한 것과 같은 방향입니다. **Agent context에 capabilities를 전부 설명하는 것 자체가 control-plane tax**가 되고 있습니다. :chatgpt-content-reference{index="35"}

하지만 production에서는 숫자만 보고 Bash를 주면 안 됩니다. 논문 저자도 **arbitrary execution을 강하게 격리할 수 있을 때 Bash를 사용하고, 보안·compliance상 fixed capability catalog가 필요하면 programmatic tool calling을 고려하라**고 결론냅니다. 즉 성능 최적점은 Bash일 수 있어도 안전 최적점은 다를 수 있습니다. 가장 현실적인 설계는 sandbox 내부에서는 shell을 자유롭게 사용하게 하고 network, credential, filesystem boundary는 OS/runtime layer에서 강제하는 구조입니다. :chatgpt-content-reference{index="36"}

# 오늘 직접 해볼 만한 실습 — `AgentKV Full-KV vs Phase-Aware KV` 재현

오늘은 **AgentKV repository를 이용한 small reproduction**이 가장 좋습니다. 처음부터 B200에서 큰 모델로 하지 말고 7B~20B 정도 모델 하나를 고정한 뒤 repository의 `identity/full KV`, `R-KV`, `agentkv` 세 policy를 동일 Agent workload에서 비교해보십시오. 공개 repository에 Mini-SGLang engine과 BFCL·τ²-bench runner가 이미 들어 있어 starting point로 쓰기 좋습니다. :chatgpt-content-reference{index="41"}

기록할 핵심 지표는 `task score`, `output tok/s`, `TTFT`, `TPOT`, `KV allocated bytes`, `retained KV ratio`, `eviction count`, `phase별 think/tool/act token 수`입니다. 가장 중요한 질문은 **“같은 KV budget에서 recency 기반 정책보다 phase-aware policy가 task accuracy를 더 잘 보존하는가?”**입니다.

그다음 B200으로 옮겨 concurrency를 `1 / 8 / 32`로 올리면 훨씬 좋은 실험이 됩니다. AgentKV가 accuracy를 보존하더라도 compaction/scoring overhead 때문에 concurrency가 높을 때 throughput 이득이 줄 수 있고, 반대로 HBM pressure가 커지는 시점부터 이득이 커질 수도 있습니다. 그러면 결과는 단순 “새 논문 재현”이 아니라 **`Agent semantics × KV budget × concurrency × serving throughput`을 연결한 systems benchmark**가 됩니다. :chatgpt-content-reference{index="42"}
