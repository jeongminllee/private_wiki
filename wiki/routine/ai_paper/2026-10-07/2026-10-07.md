## 1. EmbeddingGemma 2 — 740M 하나로 `text + code + image + video + audio`를 같은 벡터 공간에 넣는다 ★★★★★

Google DeepMind가 10월 6일 **EmbeddingGemma 2**를 공개했습니다. 핵심은 단순히 새 embedding model이 아니라, 텍스트·코드·이미지·비디오·오디오를 **하나의 768차원 embedding space**에 투영하는 740M 규모의 오픈 모델이라는 점입니다. Apache 2.0 라이선스이며, 전체 모델을 항상 올릴 필요도 없습니다. text/code만 쓰면 270M, text+vision은 440M, text+audio는 570M, 전체 multimodal은 740M만 로드할 수 있습니다. [blog.google](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/)

엔지니어링적으로는 **Matryoshka Representation Learning**이 특히 유용합니다. 기본 768차원 벡터를 512/256/128차원으로 잘라 쓸 수 있으며 Google은 최대 약 6배의 vector-storage 절감을 설명합니다. 256차원에서도 text/code 품질 대부분과 이미지·비디오·음성 retrieval 품질 약 95%를 유지한다고 보고합니다. 8K context로 최대 29개 이미지, 58개 video frame, 약 5.5분 audio도 한 입력에서 처리할 수 있습니다. [blog.google](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/)

이 변화가 중요한 이유는 Agent RAG에서 modality별 retrieval stack을 따로 운영해야 할 이유가 줄어들기 때문입니다. 지금까지는 `code embedding`, `document embedding`, `image embedding` 모델과 index가 갈라졌다면, 이제 작은 규모에서는 **하나의 vector DB에서 코드·스크린샷·PDF figure·audio를 cross-modal retrieval**하는 구조를 시험할 수 있습니다. Google 개발자 예제 자체도 Hugging Face Transformers codebase를 270M text-only 모델로 embedding하고 coding agent의 local code search에 사용합니다. [Google Developers Blog](https://developers.googleblog.com/embeddinggemma-2-the-developer-guide/)

다만 “best-in-class” 수치는 Google 자체 benchmark입니다. 특히 multimodal retrieval에서는 실제 데이터의 modality distribution과 false-positive 비용이 중요하므로 MTEB/MAEB 순위를 그대로 production 품질로 보면 안 됩니다. 또한 128차원까지 aggressive하게 줄였을 때 corpus 규모가 커질수록 nearest-neighbor ordering이 얼마나 흔들리는지는 직접 측정할 필요가 있습니다.

원문: [공식 발표 · Google DeepMind — EmbeddingGemma 2](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/) · [공식 개발 가이드 · EmbeddingGemma 2 Developer Guide](https://developers.googleblog.com/embeddinggemma-2-the-developer-guide/)

## 2. GitHub가 Git 자체를 다시 짓는다 — Agent가 만든 **7.38 billion commits/month**가 저장소 architecture를 바꾸고 있다 ★★★★★

GitHub가 10월 6일 공개한 글은 오늘 인프라 분야에서 가장 중요합니다. GitHub에 따르면 2026년 9월 개발자와 Agent가 만든 commit은 **73.8억 개**, 전년 대비 5배 이상으로 증가했습니다. 월간 push도 6.9억→33.5억으로 4.9배 늘었고 GitHub Actions 실행은 32.6억 회였습니다. 가장 바쁜 repository는 8월 한 달에 약 10억 request를 받았습니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

문제는 read보다 **write consistency**입니다. 기존 GitHub Spokes 구조는 repository 전체 copy를 여러 fileserver에 두고 quorum + 3-phase commit으로 reference update를 일관되게 만듭니다. 하지만 read capacity를 올리려고 replica를 늘리면 모든 replica가 write에 참여해야 하므로 오히려 push latency가 증가합니다. 사람이 몇 분에 한 번 commit할 때는 괜찮지만 Agent가 거의 매 action마다 checkpoint·push를 하면 **수백 ms~수 초짜리 Git latency도 Agent loop의 critical path**가 됩니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

GitHub의 새 구조는 전형적인 distributed-systems 해법입니다. Git ref update처럼 정말 합의가 필요한 부분만 coordination하고, object 저장·connectivity validation·secret scanning은 병렬화합니다. Garbage collection과 compaction도 serving path에서 별도 worker로 빼며, authoritative repository data는 **Azure Blob Storage**, read serving은 cache 성격의 stateless/lightweight worker로 분리합니다. 내부 benchmark에서는 최대 **35배 높은 write throughput**을 기록했다고 GitHub는 보고합니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

이건 coding-agent harness 설계에도 중요한 힌트입니다. 여러 Agent가 하나의 repo에서 작업할 때 Agent 수만 늘리고 동일 branch·worktree·Git reference에 commit을 집중시키면 **model inference보다 coordination layer가 먼저 병목**이 됩니다. Agent별 worktree/branch, local checkpoint, batched remote push, merge queue를 별도 계층으로 생각해야 합니다.

후속 관찰 포인트는 새 구조에서 ref contention이 실제로 어떻게 처리되는지와, 수천 Agent의 branch가 하나의 `main`으로 모일 때 merge queue가 다음 병목이 되는지입니다.

원문: [공식 엔지니어링 · GitHub — Building Git infrastructure for agent-scale development](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

[Anthropic](https://www.anthropic.com/news/cyber-verification-program)

즉 production security Agent에서도 모델 자체를 바꾸기보다

`identity → task scope → authorization → safeguard profile`

을 동적으로 결정하는 구조가 현실적일 수 있습니다. 예를 들어 static malware analysis에는 더 넓은 분석 capability를 허용하더라도 실제 exploit deployment나 외부 target 접근은 별도 principal과 runtime policy가 있어야 합니다.

Anthropic도 수집 한계를 명시합니다. [Anthropic](https://www.anthropic.com/news/cyber-verification-program)

## 4. Meta·Sierra `Personal Agent Protocol` — MCP 다음 문제는 **Agent가 누구를 대신하고 무엇까지 할 수 있는가** ★★★★★

10월 6일 Sierra와 Meta가 Genesys, Shopify, Stripe, Walmart 등과 함께 **Personal Agent Protocol**을 발표했습니다. 아직 v0.1 specification은 이달 후반 공개 예정이지만 방향은 중요합니다. MCP가 Agent와 tool 사이의 interface를 표준화했다면, PAP는 **소비자의 Agent와 기업 사이의 identity·authorization·session 문제**를 표준화하려 합니다. [Sierra](https://sierra.ai/blog/introducing-personal-agent-protocol?utm_source=chatgpt.com)

기본 구조는 웹사이트에서 Agent가 기업의 capability를 discovery한 뒤 사용자를 대신해 session을 생성하는 방식입니다. Guest 상태로는 제품 재고 같은 public action만 수행하고 account access가 필요하면 OAuth 기반 authentication을 거칩니다. 사용자는 Agent에게 read-only 또는 write permission을 주며, 같은 session이 웹페이지 navigation, OpenAPI/MCP API, 기업측 Agent conversation 사이를 이어갑니다. [Sierra](https://sierra.ai/blog/introducing-personal-agent-protocol)

여기서 MCP와의 차이를 명확히 볼 필요가 있습니다.

`MCP → 어떤 tool을 어떻게 호출할 것인가`

`PAP → 이 Agent는 누구를 대표하며 어떤 권한으로 이 기업에 접근하는가`

입니다.

Agent commerce가 커질수록 단순 API key로는 부족합니다. `user identity`, `agent identity`, `delegation scope`, `read/write`, `session continuity`, `payment authorization`을 별도 객체로 관리해야 합니다. 특히 “내 Agent가 내 대신 주문을 취소해도 되는가?”처럼 사람→Agent delegation을 auditable capability token으로 표현하는 문제가 중요해집니다.

아직 specification과 reference implementation이 나오지 않았다는 점은 크게 주의해야 합니다. 현재는 **표준 제안의 방향**이지 production-ready protocol이 아닙니다. OAuth scope와 MCP authorization을 실제로 어떻게 연결할지, replay/delegation-chain 문제를 어떻게 해결할지가 v0.1에서 확인해야 할 핵심입니다.

## 6. OpenAI textGrain — EU에서는 ChatGPT·Codex 텍스트에 invisible watermark가 들어가기 시작한다 ★★★★☆

OpenAI는 10월 5일 EU AI Act 대응으로 **textGrain**이라는 text watermarking 방식을 공개했습니다. API 사용자는 전 세계에서 일부 모델에 watermarking을 opt-in할 수 있고, EU의 eligible ChatGPT·Codex 출력에는 앞으로 몇 주 동안 invisible watermark가 적용됩니다. API에서는 기본 OFF입니다. Detector는 당분간 승인된 연구자·전문기관에만 제공합니다. [OpenAI](https://openai.com/index/eu-text-provenance/)

중요한 부분은 OpenAI가 watermark의 한계도 수치로 공개했다는 것입니다. false-positive target 1%에서 약 200-token passage는 대략 80%, 400-token passage는 95% 정도 탐지됐지만 domain에 따라 크게 달랐습니다. 더 중요한 것은 edit robustness입니다. 400-token 문장에서 단어 10%를 synonym으로 바꾸면 탐지율이 약 **92%→66%**, 25%를 바꾸면 **17%**까지 떨어졌습니다. [OpenAI](https://openai.com/index/eu-text-provenance/)

따라서 watermark는 보안상 **proof of authorship**이나 forensic attribution으로 사용하면 안 됩니다. `watermark detected → OpenAI 모델에서 그대로 나온 가능성을 높이는 signal` 정도가 적절합니다. 반대로 detector가 못 찾았다고 인간 작성이라고 결론낼 수도 없습니다.

실제 시스템에서 provenance를 관리한다면 watermark 하나보다 `C2PA/signature`, generation metadata, server-side audit record를 결합하는 구조가 더 안전합니다. 특히 코드가 formatter·lint·LLM review를 반복해서 거치는 development workflow에서는 statistical watermark가 쉽게 약화될 수 있습니다.

원문: [공식 발표 · OpenAI — Our approach to EU text provenance rules](https://openai.com/index/eu-text-provenance/)

## 7. `Harnessing LLMs as Agents: What Does It Cost?` — Agent Harness를 처음으로 **resource theory** 관점에서 본다 ★★★★★

10월 1일 공개된 이 논문은 Agent harness 연구에서 꽤 중요합니다. 연구진은 **Language Model Agent Machine(LAM)**이라는 abstraction을 제안해 모델 자체 성능은 고정하고, harness가 사용하는 `context capacity`, `persistent memory`, `model calls`, `memory transfer`, `verification` 비용을 명시적으로 계산합니다. [arXiv](https://arxiv.org/abs/2610.02488)

특히 좋은 점은 “memory가 있으면 Agent가 좋아진다” 수준에서 멈추지 않고 **어떤 memory interface가 계산량을 어떻게 바꾸는가**를 이론화했다는 것입니다. Pointer chasing에서는 random access와 speculative하지 않은 sequential access 사이에 Θ(n) 차이가 생기며, 특정 computation DAG에서는 context capacity `C`와 persistent memory `S`가 작을수록 model recomputation이 `Θ(n²/(C+S)+n)`까지 증가할 수 있음을 보입니다. [arXiv](https://arxiv.org/abs/2610.02488)

Verification 역시 매 step마다 하면 안전하지만 비쌉니다. 논문은 distributed-system checkpoint theory와 유사하게 **verification/checkpoint interval의 optimum**을 도출합니다. 오류율이 낮으면 모든 step을 검사하는 것이 낭비이고, 오류 비용이 높아지면 verification interval을 짧게 해야 한다는 구조입니다.

이건 Agent harness 평가 metric을 바꾸는 데 유용합니다. 지금까지 `task success / token cost` 정도를 봤다면 앞으로는

`semantic model calls`
`logical context traffic`
`persistent-memory reads/writes`
`recomputation`
`verification calls`
`checkpoint interval`

을 따로 기록할 가치가 있습니다.

다만 아직 새로운 theoretical abstraction이며 실제 software-engineering Agent 전반에서 보편적 scaling law로 검증된 것은 아닙니다. 실험도 GPT-6 Astra와 chained MATH 중심이므로 “이 수식대로 Codex 비용을 정확히 예측할 수 있다” 수준은 아닙니다.

원문: [논문 · Harnessing LLMs as Agents: What Does It Cost?](https://arxiv.org/abs/2610.02488)

## 8. IG-VLA — 로봇 Agent의 미래 예측 reasoning을 **Scene Gist Token 하나로 internalize** ★★★★☆

멀티모달·Physical AI 쪽에서는 10월 2일 공개된 **IG-VLA**가 재미있습니다. VLA가 action을 결정하기 전에 미래 scene을 명시적으로 rollout하면 reasoning은 좋아질 수 있지만 매 action마다 video-like future를 생성하면 latency가 너무 큽니다. IG-VLA는 미래 scene evolution을 pixel space가 아니라 latent representation에서 reasoning하고, 이후 그 패턴을 **Scene Gist Token**으로 압축합니다. [arXiv](https://arxiv.org/abs/2610.02626)

즉 training/reasoning 단계에서

`현재 scene → 미래 변화 상상 → 행동`

을 학습하지만 deployment에서는

`현재 scene + learned gist → 행동`

으로 shortcut을 만드는 구조입니다. LIBERO-Plus Language에서 strongest baseline 대비 success rate가 약 6% 높았고, gist policy는 단일 NVIDIA A6000에서 action-chunk latency를 **1081ms→169.5ms**, 최대 6.38배 줄였다고 보고합니다. [arXiv](https://arxiv.org/abs/2610.02626)

이 아이디어는 robotics 밖에서도 의미가 있습니다. Agent reasoning을 매번 외부 token으로 다시 생성하지 않고 **반복되는 reasoning pattern을 latent state나 learned skill로 internalize**할 수 있다면, 느린 planner와 빠른 policy를 분리하는 구조로 확장할 수 있습니다. 최근 decision model, skill distillation, procedural memory 연구와 같은 큰 방향입니다.

다만 현재 수치는 simulation/robotics benchmark 결과이고 한 A6000 환경에서 측정된 저자 측 benchmark입니다. Real robot에서는 perception latency, camera pipeline, actuator control이 추가되므로 6.38배가 end-to-end robot speedup으로 그대로 이어지지는 않습니다.

원문: [논문 · Imagine the Future, Internalize the Gist: Efficient VLA Reasoning via Internalized Spatiotemporal Imagination](https://arxiv.org/abs/2610.02626)

# 오늘 직접 해볼 만한 실습 — Harness의 `Memory가 실제 model call을 줄이는가?`

오늘은 새 기능을 추가하기보다 현재 Agent harness에서 **persistent memory의 경제성을 계측**해보는 것이 가장 좋습니다.

같은 10~20개 repository task를 `A: context only`, `B: summary memory`, `C: structured persistent memory` 세 조건으로 실행하십시오. 각 run에서 `model calls`, `fresh input tokens`, `cached tokens`, `memory read/write bytes`, `동일 파일·문제 재조사 횟수`, `verifier calls`, `wall-clock`, `task success`를 기록합니다.

가장 중요한 지표는 `memory hit rate` 자체가 아닙니다. 다음 두 값을 보십시오.

**`recomputation avoided / memory read`**  
**`successful task / total model calls`**

Memory가 계속 조회되지만 Agent가 똑같은 분석을 다시 한다면 memory subsystem은 비용만 추가한 것입니다. 반대로 model call이 줄면서 success가 유지된다면 LAM 논문의 `C + S가 증가하면 recomputation이 감소한다`는 아이디어를 실제 coding workload에서 검증할 수 있습니다. 이후 B200/A6000 inference metric까지 붙이면 **Harness architecture → context traffic → KV usage → GPU latency**를 하나의 실험으로 연결할 수 있습니다. [arXiv](https://arxiv.org/abs/2610.02488)
