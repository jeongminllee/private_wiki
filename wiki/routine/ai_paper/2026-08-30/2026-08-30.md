# AI 엔지니어 데일리 브리핑

**2026년 8월 30일 일요일**
주말 특성상 8월 29일 당일 신규 1차 발표는 많지 않았습니다. 오늘은 **8월 28일 늦게 공개된 모델·개발도구 업데이트와 8월 29일 실제 공개 상태가 확인된 artifact**, 그리고 이번 주말 놓치면 아까운 최신 연구를 우선했습니다.

오늘의 큰 흐름은 세 가지입니다. **첫째, GLM‑5.3과 Tencent Hy4처럼 700B급 open-weight MoE가 실제 다운로드·self-hosting 가능한 artifact로 내려오면서 frontier open model의 경쟁축이 “공개할 것인가”에서 “어떤 serving stack과 post-training으로 운용할 것인가”로 이동하고 있습니다. 둘째, Microsoft Agent Lightning은 training 환경과 production harness를 아예 동일하게 만드는 ‘harnessed agentic RL’을 구체화했습니다. 셋째, AgentJudgeBench와 GitHub의 최신 code-review 기능은 agent가 만든 결과를 또 다른 LLM이 검토하는 것만으로는 부족하고, deterministic verifier·harness·policy가 함께 있어야 한다는 방향을 강화합니다.**

## 1. 필독 | GLM‑5.3, 약속했던 Open Weight가 실제 공개됐다

8월 14일 hosted model로 먼저 나온 **GLM‑5.3의 전체 weight가 8월 28일 Hugging Face에 공개**됐습니다. 현재 공식 repository는 753B parameter checkpoint를 제공하며, 별도 BF16 repository와 FP8 계열 artifact도 확인할 수 있습니다. 중요한 점은 기존 GLM‑5.2와 **동일 base model을 사용하고 성능 향상이 전부 post-training에서 발생했다**는 Z.ai의 설명입니다. ([Hugging Face][1])

Z.ai 자체 평가에서 Terminal-Bench 3.0은 GLM‑5.2의 4.6에서 **28.3**, DeepSWE v1.1은 46.2→**66.9**, CyberGym은 77.2→84.5, ExploitBench는 24.4→54.4로 상승했습니다. 다만 model card의 footnote를 보면 Terminal-Bench는 Claude Code 2.1.207 harness, 최대 reasoning effort, 400K context, 최대 600 agent turn과 10시간 timeout을 사용하는 등 **모델 weight만의 평가가 아니라 상당히 무거운 agent system 평가**입니다. 따라서 숫자를 다른 vendor 표와 바로 비교하면 안 됩니다. ([Hugging Face][1])

이번 공개가 중요한 이유는 “GLM‑5.3이 강하다”보다 **post-training만으로 동일 base의 agent capability가 얼마나 크게 움직일 수 있는지를 외부가 직접 검증할 수 있게 됐다는 점**입니다. 특히 coding·terminal·cyber처럼 환경과 상호작용하는 task에서는 앞으로 pretraining scale보다 `environment diversity × rollout compute × verifier quality × harness`가 더 큰 차별화 요인이 될 가능성이 있습니다.

배포 경로도 이미 꽤 넓습니다. 공식 model card는 vLLM, SGLang, Transformers, TokenSpeed, KTransformers, Unsloth와 Ascend NPU 경로를 제공하고, `reasoning_effort=low/high/max`도 지원합니다. 하지만 **라이선스는 GLM‑5.2의 MIT가 아니라 별도의 `GLM‑5.3 License`**이므로 상업 self-hosting 전에는 반드시 조건을 확인해야 합니다. ([Hugging Face][1])

또 하나 중요한 점은 cyber capability입니다. Z.ai는 공개 model card 자체에서 post-training 중 cyber capability가 예상보다 빠르게 성장했다고 밝힙니다. Open weight가 공개됐다는 사실 자체가 이 위험이 “해결됐다”는 증거는 아니며, 공개된 자료에는 2주간 safety review에서 무엇을 변경했고 어떤 release threshold를 적용했는지 상세한 safety report는 없습니다. 따라서 vulnerability research용으로 사용할 때는 network default-deny, scoped sandbox, target allowlist와 execution audit를 별도로 가져가야 합니다. ([Hugging Face][1])

**후속 관찰 포인트:** 독립 Terminal-Bench/DeepSWE 재현, GLM‑5.3 License의 실제 상업 조건, quantized artifact의 tool-call regression, `low/high/max` reasoning의 cost-per-success.

**원문:** [모델 카드 — Z.ai GLM‑5.3 Open Weights](https://huggingface.co/zai-org/GLM-5.3)

## 2. 필독 | Tencent Hy4 Preview — 770B MoE·49B Active·1M Context를 Apache 2.0으로

Tencent가 **8월 28일 Hy4 Preview를 open-source/open-weight로 공개**했습니다. 총 770B parameter이지만 token당 49B만 활성화되는 MoE이며, 78-layer backbone 중 77개 layer가 256 routed expert + 1 shared expert를 사용하고 매 token마다 top-8 routed expert를 선택합니다. Native MTP layer도 하나 들어가 speculative decoding을 지원합니다. ([GitHub][2])

Attention도 눈여겨볼 만합니다. **Gated DeepSeek Sparse Attention(DSA)**에 `IndexCache`를 사용해 sparse index를 layer 사이에서 재사용하고, residual path에는 `iHC(identity Hyper-Connections)`를 적용했습니다. Context length는 **1M token**, 라이선스는 Apache 2.0입니다. ([GitHub][2])

공식 serving recipe가 상당히 공격적입니다. FP8 checkpoint를 vLLM에서 `TP=8`, sparse FlashMLA backend와 native MTP speculative decoding으로 띄우는 예제를 제공하며 SGLang 전용 image도 이미 있습니다. 즉 신규 trillion-class open model이 나온 뒤 inference engine이 몇 주 뒤 따라오는 것이 아니라 **model release 당일부터 model architecture와 serving engine이 공동 배포되는 방식**이 표준이 되고 있습니다. ([GitHub][2])

반면 fine-tuning 자원은 현실적으로 매우 큽니다. Tencent가 공개한 최소 설정은 LoRA만 해도 **8노드·64GPU·GPU당 VRAM 96GB 이상**, full fine-tuning은 16노드·128GPU입니다. “TP=8 recipe가 있다”는 말을 “8장의 아무 GPU에서 손쉽게 돌릴 수 있다”로 읽으면 안 됩니다. ([GitHub][3])

Tencent의 자체 163명·203개 engineering-task blind evaluation에서는 평균 2.99/4.00으로 GLM‑5.3의 2.92와 Kimi K3의 2.94를 근소하게 앞섰습니다. 하지만 **Tencent 내부 전문가·자체 task 결과**이므로 독립 benchmark보다 제품 co-design 성과의 신호 정도로 보는 것이 적절합니다. Tencent도 현재 preview 버전의 known limitation으로 복잡한 task에서 **필요 이상으로 오래 reasoning하거나 자기 작업을 과도하게 검증하는 경향**을 직접 명시합니다. ([GitHub][2])

실무에서는 이 limitation이 꽤 중요합니다. Frontier open model끼리 비교할 때 accuracy뿐 아니라 `reasoning_tokens`, `verification_turns`, `tool_calls`, `wall_clock_per_success`를 같이 봐야 합니다. 정확도 1~2점 차이보다 “같은 task를 해결하면서 2배 더 오래 검증하는 모델”의 실제 운영비 차이가 더 클 수 있습니다.

**후속 관찰 포인트:** independent coding benchmark, MTP acceptance rate, 1M-context TTFT와 KV memory, `high` vs `no_think` cost-per-success.

**원문:** [공식 발표 — Tencent Hy4 Preview](https://www.tencent.com/tencent-releases-and-open-sources-tencent-hy4-preview/?utm_source=chatgpt.com) · [GitHub — Hy4 Preview Architecture·vLLM/SGLang Recipes](https://github.com/Tencent-Hunyuan/Hy4-preview?utm_source=chatgpt.com)

## 3. Agent RL | Microsoft Agent Lightning v1.0 — Production Harness 자체를 RL 환경으로

Microsoft Research가 **Agent Lightning v1.0**을 공개했습니다. 핵심 개념은 `harnessed agentic RL`입니다. 일반 agent RL은 training engine이 environment loop까지 소유하지만, Agent Lightning에서는 **실제 production harness가 context, tool, control flow와 environment interaction을 그대로 수행하고 trainer는 LLM request-response sequence만 관찰**합니다. ([Microsoft][4])

이게 중요한 이유는 train–deploy gap 때문입니다.

```text
기존
훈련용 단순 environment
        ↓
Model RL
        ↓
전혀 다른 production harness

Agent Lightning
실제 production harness
        ↕
LLM proxy
        ↕
RL trainer
```

실제로 agent 성능은 system prompt뿐 아니라 context compaction, retry, tool schema, filesystem, sandbox, execution ordering에 크게 영향을 받습니다. 그런데 학습할 때 이 요소를 제거하면 production에 들어갔을 때 policy distribution 자체가 달라질 수 있습니다.

v1.0은 core Python 약 **3,500 lines**로 재작성됐고, 기존 agent code를 거의 바꾸지 않고 endpoint proxy에 연결할 수 있습니다. Kubernetes Job을 native rollout runner로 지원하며, coding-agent pipeline에는 data cleaning, reward-hacking prevention과 training script까지 공개됐습니다. ([Microsoft GitHub][5])

Microsoft 측 실험에서는 **6K training examples**로 Qwen3.5-9B를 RL해 SWE-bench Verified를 **41.8%→56.4%, +14.6%p** 개선했다고 보고합니다. 상당히 큰 결과지만 아직 연구팀 자체 pipeline 결과이므로 독립 재현을 기다릴 필요가 있습니다. 특히 harnessed RL에서는 retokenization, 여러 turn의 sample merge, advantage calculation, loss normalization과 asynchronous scheduling 자체가 학습 결과를 바꿀 수 있다고 논문도 강조합니다. ([Microsoft][4])

실무적으로는 기존 agent를 새 RL framework로 다시 작성하지 않고 **현재 사용하는 harness를 그대로 학습 환경으로 만드는 방법**이라는 점이 가치 있습니다. 앞으로 coding agent를 post-train한다면 모델 checkpoint와 함께 `harness_version`, `tool_schema_version`, `sandbox_image`, `reward_version`까지 training artifact로 pin하는 것이 필수에 가까워질 겁니다.

**후속 관찰 포인트:** Qwen3.5-9B 결과 독립 재현, multi-agent harness, asynchronous rollout의 off-policy drift, reward-hacking 방지 pipeline의 실제 효과.

**원문:** [Microsoft Research — Agent Lightning v1.0 Paper](https://www.microsoft.com/en-us/research/publication/agent-lightning-v1-0-towards-harnessed-agentic-rl/) · [공식 문서 — Agent Lightning v1.0](https://microsoft.github.io/agent-lightning/latest/)

## 4. AI 평가 | AgentJudgeBench — Judge 모델을 크게 해도 Tool-Workflow 판정 한계가 사라지지 않는다

8월 27일 공개·28일 갱신된 **AgentJudgeBench**는 agent의 tool-call trajectory를 LLM judge가 얼마나 정확하게 평가하는지를 정면으로 다룹니다. 3,808개 instance, 6종의 workflow DAG topology, 3단계 difficulty를 구성하고 5개 generator와 6개 judge를 비교했습니다. ([arXiv][6])

결과가 꽤 중요한데, **ground truth가 없는 hard workflow에서는 모든 judge가 모델 크기에 관계없이 77~82%의 좁은 구간으로 수렴**했습니다. Task 난도가 올라갈수록 judge alignment가 감소했고, ground truth가 없으면 감소 속도가 1.5배 빨랐습니다. 즉 더 큰 frontier judge를 투입하는 것만으로 workflow-evaluation ceiling을 뚫지 못했습니다. ([arXiv][6])

더 오래 생각하게 만드는 것도 큰 효과가 없었습니다. Chain-of-thought와 judge temperature 변경은 의미 있는 개선을 거의 못 만들었고, **structured rubric은 최대 +6.5%p**를 만들었지만 모든 judge-generator 조합에서 일관되지는 않았습니다. 더 흥미롭게도 ground truth를 보여주면 GPT‑5.4와 Gemini-2.5-Pro의 alignment가 각각 1.5p, 3.9p 낮아지는 경우가 있었고 연구진은 이를 over-anchoring 가능성으로 해석합니다. ([arXiv][6])

Agent evaluator를 만들 때 이 결과가 의미하는 것은 명확합니다.

```text
나쁜 구조
trajectory
→ LLM Judge
→ PASS / FAIL

더 나은 구조
trajectory
├─ programmatic state verifier
├─ tool dependency verifier
├─ side-effect verifier
└─ LLM Judge (열린 품질 평가만)
```

Tool call의 ordering, required dependency, final DB/filesystem state처럼 코드로 검증 가능한 것은 LLM에게 판단시키지 않는 편이 좋습니다. 자연어 품질이나 설명의 유용성처럼 deterministic하게 정의하기 어려운 부분에만 judge model을 쓰는 구조가 비용과 신뢰도 모두 유리합니다.

**주의:** 아직 초기 arXiv benchmark이며 judge prompt와 task construction에 결과가 의존합니다. 77~82%를 모든 agent evaluator의 보편적인 ceiling으로 볼 수는 없습니다. 중요한 결과는 **모델 크기보다 workflow 구조와 evaluation contract가 더 큰 병목이 될 수 있다는 점**입니다.

**후속 관찰 포인트:** 실제 SWE/MCP trajectory, multimodal agent judge, programmatic verifier와 judge ensemble, judge disagreement를 이용한 human escalation.

**원문:** [논문 — AgentJudgeBench](https://arxiv.org/abs/2608.26623?utm_source=chatgpt.com)

## 5. 개발 도구 | GitHub Copilot — Agent가 만든 PR을 Agent가 본격적으로 Review하는 단계

GitHub의 8월 27~28일 Copilot 업데이트도 꽤 실무적입니다. Copilot code review는 이제 **bot이 작성한 PR과 Copilot cloud agent가 만든 PR에도 full agentic review**를 수행할 수 있고, 과거 존재했던 **300 files / 20,000 lines 제한도 제거**됐습니다. Review comment를 resolve할 때는 `Addressed / Won't fix / Incorrect` 이유를 남길 수도 있습니다. ([The GitHub Blog][7])

Visual Studio 쪽에서는 organization-level custom agent 배포, Low/Medium/High thinking-effort 제어, 모델의 context window·cost·capability를 한 화면에서 관리하는 기능과, PR 생성 전 **Git agent로 uncommitted change나 commit을 직접 review**하는 workflow가 추가됐습니다. ([The GitHub Blog][8])

이 흐름에서 가장 조심해야 할 것은 **AI 생성 → AI 리뷰의 상관 오류**입니다.

```text
Copilot Cloud Agent
        ↓
PR 생성
        ↓
Copilot Code Review
```

두 단계가 유사한 model family, 동일 repository context, 비슷한 reasoning pattern을 공유하면 첫 agent가 놓친 architecture assumption을 reviewer도 그대로 공유할 수 있습니다. “AI reviewer가 승인했으므로 independent verification”이라고 보면 안 됩니다.

따라서 agent-generated PR에서는 오히려 다음과 같은 서로 다른 verifier를 조합하는 것이 중요합니다.

```text
AI Review
+
compiler/test
+
CodeQL/SAST
+
dependency/secret scan
+
고위험 경로 human review
```

Resolution reason 데이터도 단순 UI 기능 이상으로 활용할 수 있습니다. `Incorrect` 비율이 특정 repository·language·model에서 높다면 AI review의 false-positive distribution을 측정하는 feedback dataset이 됩니다.

대형 PR 제한이 사라진 것도 편리하지만, **context가 많다고 review 품질이 선형으로 좋아지는 것은 아닙니다.** 큰 migration PR은 subsystem별로 분리한 뒤 결과를 aggregate하는 방식이 여전히 더 검증하기 쉽습니다.

**후속 관찰 포인트:** bot-PR reviewer의 defect escape rate, `Incorrect` feedback 학습 효과, Balanced/High effort의 credit 대비 성능, 매우 큰 PR에서 context compaction 방식.

**원문:** [GitHub 릴리스 — Copilot Code Review Expanded Capabilities](https://github.blog/changelog/2026-08-27-copilot-code-review-resolution-reasons-and-expanded-capabilities/) · [GitHub 릴리스 — Copilot Visual Studio August Update](https://github.blog/changelog/2026-08-28-github-copilot-in-visual-studio-august-update-2)

## 6. Speech·Edge | Granite Speech 5.0 Turbo CTC — 470M 모델에서 LLM을 빼니 20배 이상 빨라졌다

IBM이 Granite 4.2와 함께 공개한 **Granite Speech 5.0 Turbo CTC**는 요즘 “모든 문제에 LLM backbone을 붙인다”는 흐름과 반대라서 재미있습니다. 470M parameter의 **encoder-only Conformer + CTC** 구조로, 이전 Granite Speech의 LLM backbone·projector를 완전히 제거했습니다. ([IBM Research][9])

IBM 측 H200 batched-inference 측정에서는 **12,600 RTFx 이상**, 즉 1초에 3.5시간 이상의 audio를 transcription할 수 있다고 보고했습니다. 이전 Granite Speech 대비 throughput은 20배 이상 높아졌습니다. 상용 사용 가능한 Apache 2.0 버전과 추가 데이터를 사용한 CC-BY-NC-SA-4.0 비상업용 버전이 별도로 있습니다. ([Hugging Face][10])

이 모델의 포인트는 “470M이 frontier speech model을 이겼다”가 아닙니다. **업무가 transcription 하나로 잘 정의돼 있다면 범용 LLM decoder를 제거하는 것이 훨씬 좋은 시스템 선택일 수 있다**는 것입니다.

Voice-agent pipeline에서도 모든 audio를 multimodal frontier model에 직접 넣는 대신:

```text
Audio
→ Granite Speech CTC
→ clean transcript
→ LLM agent
```

처럼 분리하면 고용량 call-center archive, meeting ingestion, batch dataset 구축에서는 비용을 크게 줄일 수 있습니다.

대신 capability를 포기합니다. Granite Speech 5.0 Turbo CTC는 이전 LM-backed 계열이 지원하던 **speech translation과 keyword biasing을 제공하지 않습니다.** 그리고 12,600 RTFx는 단일 H200의 대규모 batched throughput이지 smartphone에서 그 속도가 나온다는 뜻이 아닙니다. ([Hugging Face][10])

실제 도입에서는 WER 평균보다 숫자, 제품명, 사람 이름, 코드 identifier 같은 **business-critical entity error rate**를 따로 측정하는 편이 좋습니다.

**후속 관찰 포인트:** 한국어/다국어 version, WebGPU·edge 실제 latency, entity-heavy transcription, CTC transcript + frontier correction cascade의 비용.

**원문:** [IBM 공식 발표 — Granite 4.2·Granite Speech 5.0](https://research.ibm.com/blog/introducing-granite-4-2?utm_source=chatgpt.com) · [기술 글 — Granite Speech 5.0 Turbo CTC](https://huggingface.co/blog/ibm-granite/granite-speech-5-0-470m-turboctc?utm_source=chatgpt.com)

## 7. 산업·개발도구 | OpenAI, Cursor에 대한 직접 모델 공급 종료 계획 — Coding Agent의 Provider Lock-in 문제

OpenAI는 8월 28일 Cursor가 SpaceX에 인수된 뒤 **Cursor에 직접 공급하던 OpenAI model 계약을 종료할 계획**이라고 발표했습니다. 현재 제안된 direct-access 종료일은 **2026년 11월 12일**이며, OpenAI는 future model도 Cursor에 공급하지 않겠다고 밝혔습니다. 이 날짜는 양사가 최종 확정한 종료일이 아니라 현재 OpenAI가 제안한 transition date입니다. ([OpenAI][11])

분쟁 이유 자체에 대해서는 OpenAI가 SpaceX의 향후 terms 준수에 확신을 가질 수 없다는 입장을 밝힌 것이므로 **OpenAI 측 주장으로 구분해서 보는 것이 적절**합니다. Reuters에 따르면 Cursor 측은 OpenAI와 계속 논의 중이라고 밝혔습니다. ([OpenAI][11])

엔지니어에게 더 중요한 부분은 이것입니다. **Coding-agent IDE에서 모델 공급자는 언제든 기술적 이유가 아닌 계약·인수·정책 이유로 사라질 수 있습니다.**

Agent platform을 설계할 때:

```text
IDE / Harness
     ↓
Model abstraction
     ├─ Provider A
     ├─ Provider B
     └─ Local model
```

를 실제로 유지하는 것이 중요합니다. 단순 OpenAI-compatible API만 맞춘다고 portability가 끝나는 것도 아닙니다. 모델마다 tool schema, reasoning history, context compaction, system-prompt behavior가 다르므로 **fallback model에 대한 regression suite**가 있어야 합니다.

OpenAI는 기존 Cursor 사용자가 transition 이후에도 **자신의 OpenAI API key를 직접 연결하거나 Codex IDE extension을 Cursor 안에서 사용할 수 있다**고 안내합니다. 즉 이번 변화는 OpenAI API 자체를 Cursor에서 완전히 못 쓰게 만드는 것은 아니고, Cursor가 제공하던 direct managed access 계약의 종료 계획입니다. ([OpenAI Help Center][12])

실무적으로는 모델 provider 장애나 계약 변경에 대비해 `model capability matrix`, `tool-call compatibility`, `reasoning-state portability`, `fallback strict-success`를 CI에서 주기적으로 확인할 가치가 있습니다.

**후속 관찰 포인트:** 최종 종료일 확정, Cursor의 대체 provider 정책, BYOK workflow, future OpenAI model과 Cursor harness의 호환성.

# 오늘 꼭 볼 것 3개

**1. GLM‑5.3 Open Weights.**
2주 전에는 “안전성 검토 뒤 공개 예정”이었는데 이제 실제 weight가 내려왔습니다. **동일 base + 대규모 post-training만으로 coding·agent·cyber 성능이 얼마나 달라졌는지 외부에서 직접 분석할 수 있게 됐다는 점**이 가장 중요합니다. ([Hugging Face][1])

**2. Tencent Hy4 Preview.**
770B/49B-active, Gated DSA + IndexCache, native MTP, 1M context라는 설계가 vLLM/SGLang serving recipe와 동시에 나왔습니다. **Model architecture와 inference runtime을 함께 출시하는 시대**를 잘 보여줍니다. ([GitHub][2])

**3. Agent Lightning v1.0.**
Agent RL에서 training environment를 별도로 흉내 내지 않고 **실제 deployment harness 자체를 학습 loop 안에 넣는 것**이 핵심입니다. Agent post-training을 고민한다면 구조적으로 가장 볼 가치가 큽니다. ([Microsoft][4])

# 오늘의 실습 | LLM Judge가 Tool Agent를 얼마나 잘못 평가하는지 직접 측정하기

오늘은 AgentJudgeBench 아이디어를 작게 재현하는 것이 좋습니다. 모델 학습이나 대형 GPU가 필요하지 않고, 이후 모든 agent benchmark에 재사용할 수 있습니다.

간단한 tool workflow를 20개 정도 만듭니다. 예를 들어:

```text
Task:
"문서 A에서 주문번호를 찾고
해당 주문의 상태를 조회한 뒤
금액이 10만원 이상이면 알림을 생성하라."

Required DAG:
search_document
   ↓
get_order_status
   ↓
check_amount
   ↓
create_alert
```

각 task마다 세 trajectory를 의도적으로 만듭니다.

```text
A. 완전히 정상
B. 중간 tool 하나 생략
C. 최종 답변은 맞지만 잘못된 tool 순서를 사용
```

그다음 두 evaluator를 비교합니다.

```text
Evaluator 1
LLM Judge:
"이 agent가 task를 올바르게 완료했는가?"

Evaluator 2
Programmatic Verifier:
- 필요한 tool 모두 호출?
- dependency 순서 정확?
- argument 정확?
- final state 정확?
```

LLM Judge에는 처음에는 최종 답변과 trajectory만 주고, 다음 조건에서는 structured rubric도 추가합니다.

```text
1. Free-form Judge
2. Structured Rubric Judge
3. Programmatic Verifier
```

기록할 값은 다음이면 충분합니다.

```text
judge_accuracy
false_accept
false_reject

latency
tokens
cost
```

특히 **“최종 답변은 맞지만 tool trajectory는 틀린 케이스”**의 false accept를 보십시오. 이 부분이 높다면 현재 agent 평가가 사실상 answer-quality만 보고 workflow correctness를 놓치고 있다는 뜻입니다.

최종적으로 구조를 다음처럼 가져가는 것이 좋습니다.

```text
Programmatic Verifier
      ↓
명확한 correctness / side effect

LLM Judge
      ↓
설명 품질 / 유용성 / 자연어 기준

Human
      ↓
고위험·불확실 case
```

이번 실험의 목표는 “어떤 judge model이 제일 좋은가”가 아닙니다.

> **LLM에게 맡기지 않아도 되는 판정을 얼마나 deterministic verifier로 빼낼 수 있는가?**

이 구분을 한 번 만들어두면 coding agent, MCP workflow, benchmark, research agent를 평가할 때 judge 비용과 평가 오류를 동시에 줄일 수 있습니다. ([arXiv][6])
