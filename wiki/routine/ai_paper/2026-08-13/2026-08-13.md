# AI 엔지니어 데일리 브리핑

**2026년 8월 13일 목요일**
**분석 범위:** 8월 12일까지 공개·갱신된 공식 발표·릴리스·모델 자료와 최신 논문

오늘의 핵심 흐름은 **모델 자체보다 모델을 둘러싼 실행 계약이 표준화되고 정교해지고 있다**는 점입니다. ([The GitHub Blog][1])

## 1. 필독 | Agent Plugins 1.0 — Skill + MCP를 하나의 이식 가능한 패키지로

### 무엇이 바뀌었나

GitHub는 8월 12일 **Agent Plugins 1.0** 지원을 VS Code, Copilot CLI, GitHub Copilot SDK와 Copilot app에서 GA로 전환했습니다. 표준 자체는 8월 6일 AWS, Anysphere, Microsoft, OpenAI, Vercel 등이 참여해 공개됐으며 Google도 core maintainer로 합류했습니다. 핵심은 **Agent Skill과 MCP server 설정을 하나의 vendor-independent plugin으로 패키징**하는 것입니다. ([The GitHub Blog][2])

기본 구조도 상당히 단순합니다.

```text
my-plugin/
├── plugin.json
├── skills/
│   └── deploy/
│       └── SKILL.md
├── mcp.json
└── com.vendor.client/
```

`plugin.json`은 공통 manifest, `skills/`와 `mcp.json`은 portable component이며, 특정 agent client에만 필요한 기능은 reverse-domain namespace 아래로 격리합니다. 공식 사양에서 Agent Plugins v1의 표준 component는 정확히 **Skill과 MCP server 두 종류**입니다. ([GitHub][3])

### 왜 중요한가

지금까지 동일한 deployment skill과 동일 MCP server를 Claude Code, Copilot, 기타 agent에 배포하려 해도 각 제품에 맞는 manifest·directory·설정 파일을 따로 관리해야 했습니다. Agent Plugins가 자리 잡으면 agent ecosystem에서도 npm package나 container image처럼 **“한 번 패키징하고 여러 runtime에서 소비하는 artifact”**가 만들어질 가능성이 있습니다. ([The GitHub Blog][2])

특히 앞으로 기업 내부에서는 다음 단위가 하나의 버전 artifact가 될 수 있습니다.

```text
deployment-agent-plugin@1.4.2
├─ 운영 Skill
├─ runbook
├─ scripts
├─ MCP tool contract
└─ client별 extension
```

이렇게 되면 Skill 문서와 실제 tool implementation이 서로 다른 repository에서 독립적으로 drift하는 문제를 줄이기 좋습니다.

### 보안상 아주 중요한 부분

**Portable package ≠ sandbox입니다.**

Agent Plugins 사양은 plugin 내부의 파일 경로가 `../` 등을 통해 plugin root 밖으로 탈출하지 못하도록 요구합니다. 그러나 공식 사양은 이 containment가 **plugin subprocess 자체를 sandbox하거나 runtime에서 전달되는 경로를 제한하는 것은 아니라고 명시**합니다. ([GitHub][3])

즉 MCP server가 들어 있는 plugin을 설치했다면 여전히 다음이 필요합니다.

```text
plugin provenance
→ MCP allowlist
→ process permission
→ filesystem permission
→ network egress
→ secret access
```

GitHub 역시 enterprise 환경에서 `enabledPlugins`, approved marketplace 정책과 함께 **MCP allowlist를 별도로 사용하라**고 안내합니다. ([The GitHub Blog][1])

### 후속 관찰 포인트

관건은 Copilot 이외의 agent client들이 어느 정도 속도로 v1을 구현하는지, plugin signing·provenance·dependency locking이 어떻게 발전하는지입니다. Skill과 MCP의 패키징은 표준화됐지만 **permission semantics까지 표준화된 것은 아니라는 점**을 특히 봐야 합니다. ([GitHub][3])

**원문:** **[공식 발표] Agent Plugins 1.0 GA 지원** ([The GitHub Blog][2]) · **[공식 사양] Agent Plugins Specification v1.0.0** ([GitHub][3])

## 2. 멀티모달·Edge | Liquid AI LFM2.5-VL-3B — 화면을 보고 바로 tool을 부르는 3B VLM

### 무엇이 바뀌었나

Liquid AI가 8월 12일 **LFM2.5-VL-3B**를 공개했습니다. 약 3.1B 규모의 vision-language model로, 이전 모델 대비 screen/UI understanding, grounding, multi-image 처리와 function calling을 크게 강화했습니다. 구조는 SigLIP2 400M NaFlex vision encoder와 LFM2.5-2.6B 계열 text backbone의 결합이며, text 계열 pretraining 규모는 약 34T token입니다. 비라틴 문자 지원 강화를 위해 vocabulary도 128K로 확대했습니다. ([Liquid AI][4])

Liquid 자체 평가에서 ScreenSpot-v2 평균은 80.7, RefCOCO precision@1은 이전 57.1에서 87.9로 상승했습니다. ToolSandbox는 26.4→59.5, BFCL V4는 20.5→32.5로 개선됐습니다. 다만 비교 대상 Qwen3.5-4B는 ToolSandbox 65.0, BFCL V4 53.6으로 더 높기 때문에 **“3B급 최고의 tool model”이라고 일반화할 수는 없습니다.** ([Liquid AI][4])

### 왜 중요한가

이 모델의 흥미로운 위치는 일반 VQA보다 **visual agent의 perception layer**입니다.

```text
화면 캡처
   ↓
UI 요소 grounding
   ↓
tool / function 선택
   ↓
click·search·API action
```

GUI agent를 frontier multimodal API 하나로 전부 처리하는 대신, 화면 해석·bounding box·간단한 tool routing은 작은 local VLM에 맡기고 복잡한 reasoning만 상위 모델로 보내는 구조가 현실적이 됩니다.

특히 model이 reasoning trace를 길게 생성하지 않고 직접 답하도록 설계돼 있어 Liquid는 실시간·온디바이스 latency를 강조하고 있습니다. llama.cpp, MLX, vLLM, SGLang, ONNX를 출시 시점부터 지원합니다. ([Liquid AI][5])

### 실제 성능 수치는 어떻게 볼까

Liquid의 자체 측정에서는 Apple M5 Max 228 tok/s, Ryzen AI Max+ 395에서 116 tok/s, Galaxy S26 Ultra에서 20 tok/s를 보고했고, 온디바이스 구성에서 약 3GB 메모리를 사용했다고 설명합니다. H100 SXM5·BF16·vLLM 0.26 조건의 sustained-load 테스트에서는 높은 동시성에서 약 11K output tok/s를 보고했습니다. 모두 **공급사 측 benchmark**이므로 이미지 크기·precision·batch·thermal 상태를 동일하게 맞춘 재측정이 필요합니다. ([Liquid AI][4])

### 실무 적용

UI agent에 도입한다면 일반 VQA accuracy보다 다음을 먼저 보는 것이 좋습니다.

```text
element_grounding_accuracy
click_coordinate_error
tool_selection_accuracy
argument_schema_accuracy
Korean_OCR_accuracy
TTFT
memory_peak
thermal_throttling
```

특히 화면 요소를 잘 “설명”하는 것과 정확한 clickable coordinate를 반환하는 능력은 다릅니다.

### 후속 관찰 포인트

한국어 UI·OCR 성능, 모바일 장기 실행 시 throttling, grounding 결과를 실제 GUI action으로 연결했을 때의 end-to-end success, 더 큰 reasoning model과의 escalation routing이 관찰 대상입니다.

**원문:** **[공식 발표] LFM2.5-VL-3B** ([Liquid AI][5])

## 3. 필독 | FlashInfer 0.6.17 정식 — MoE Expert Parallel이 실서비스 경로로

### 무엇이 바뀌었나

FlashInfer `v0.6.17` 정식 버전이 8월 11일 공개됐고 현재 최신 안정 릴리스로 표시됩니다. 가장 중요한 변화는 프로젝트가 **MegaMoE 기반 Expert Parallel 경로를 serving engine용 production-ready 상태**라고 선언한 것입니다. ([GitHub][6])

MegaMoE 경로에는 다음이 들어갔습니다.

```text
CUDA Graph capture / replay
fused quantize-and-stage
prequantized weight pack
layer 간 symmetric workspace pool
persistent tuned-knob cache
```

목표는 production session 중 autotuning이나 반복 allocation 같은 변동 요소를 제거하는 것입니다. ([GitHub][6])

또 NCCL-EP와 NIXL-EP에 선택적으로 사용할 수 있는 **fault-tolerance rank mask**가 추가됐습니다. Dispatch/combine 중 peer timeout이 발생하면 해당 rank를 mask하고 skip해 전체 job이 즉시 죽는 것을 피하는 구조입니다. ([GitHub][6])

### 왜 중요한가

MoE inference에서는 GEMM 성능보다 다음 경로가 병목이 되는 경우가 많습니다.

```text
routing
→ token dispatch
→ network / NVLink
→ expert compute
→ combine
```

따라서 kernel benchmark만 빠른 MoE backend와 **CUDA Graph·workspace reuse·fault handling까지 포함해 serving engine 안에서 지속적으로 동작하는 backend**는 다른 문제입니다. 0.6.17은 바로 후자 쪽을 강화했습니다. ([GitHub][6])

Blackwell SM120/121 계열 fused-MoE에서는 NVFP4 quantization 관련 두 오류가 수정됐고 W4A4 decode/prefill parity와 W4A16 persistent launch 경로도 추가됐습니다. 이 FP4 accuracy fix의 대상은 릴리스 노트상 **SM120/121 계열**이므로 다른 Blackwell GPU에 그대로 확대 해석하면 안 됩니다. ([GitHub][6])

Kimi K3의 MLA decode, MiniMax-M3 sparse attention, long-sequence·video diffusion을 위한 Ulysses sequence parallel public API도 추가됐습니다. ([GitHub][6])

### 실무 적용

EP를 켜기 전후로 다음을 분리해 기록해야 합니다.

```text
routing_time
dispatch_time
expert_compute_time
combine_time
all_to_all_bytes
expert_load_imbalance
CUDA_graph_hit
workspace_peak
TTFT
TPOT
```

Fault-tolerance mask도 “server가 안 죽었다”만 보면 부족합니다. 장애 rank가 발생했을 때 **출력 품질과 요청 성공 의미가 어떻게 변하는지**를 failure-injection test로 따로 검증해야 합니다. 릴리스 노트는 job을 살리는 기능을 설명하지만 동일 출력 보존까지 보장한다고 말하지는 않습니다. ([GitHub][6])

### 후속 관찰 포인트

vLLM·SGLang에서 MegaMoE가 얼마나 기본 경로로 채택되는지, multi-node EP에서의 failure recovery, rank loss 시 numerical/quality semantics, FP4·FP8의 실제 end-to-end throughput을 볼 필요가 있습니다.

**원문:** **[GitHub 릴리스] FlashInfer v0.6.17** ([GitHub][6])

## 4. GPU 인프라 | NVIDIA: GPU가 멀쩡해 보여도 InfiniBand 한 링크가 전체 학습을 망칠 수 있다

### 무엇이 바뀌었나

NVIDIA가 8월 12일 AI factory용 **full-stack observability 설계 가이드**를 공개했습니다. 핵심 메시지는 “metric을 많이 수집하라”가 아니라 **GPU·node·fabric·scheduler·inference service를 같은 시간축에서 연결하고, 실제 장애 대응으로 이어지는 최소 metric 집합을 만들라**는 것입니다. ([NVIDIA Developer][7])

NVIDIA가 제시한 예시는 전형적인 gray failure입니다. 3일째 실행 중인 distributed training에서 GPU utilization과 queue wait은 정상인데 처리량만 6시간 동안 떨어지고, 원인을 추적해 보니 InfiniBand 한 링크의 bit error rate 상승이었습니다. BSP 학습에서는 한 rank의 retransmission이 NCCL all-reduce를 늦추면서 다른 rank까지 기다리게 만듭니다. ([NVIDIA Developer][7])

### 왜 중요한가

GPU cluster 운영에서 다음 대시보드는 위험할 수 있습니다.

```text
GPU utilization: 96%  🟢
GPU temperature: OK   🟢
job running: YES      🟢
```

실제로 중요한 것은:

```text
iteration_time ↑
    ↓
rank 13 NCCL latency ↑
    ↓
IB port retransmit / BER ↑
    ↓
특정 cable / switch port
```

처럼 **workload → rank → GPU → fabric component**까지 상관관계를 내려갈 수 있는지입니다.

NVIDIA는 failure domain을 platform, GPU, fabric, cluster/job, inference service로 구분하고 각각 BMC/IPMI, DCGM, NVSM, UFM/NetQ, BCM·Run:ai, NIM 등을 매핑합니다. 동시에 “필요 없는 exporter를 더 붙이면 observability가 아니라 alert noise가 된다”고 강조합니다. ([NVIDIA Developer][7])

### 바로 적용하기 좋은 지표

InfiniBand 기반 GPU cluster라면 다음 정도를 공통 timeline으로 붙이는 것만으로도 가치가 큽니다.

```text
job_id / rank
iteration_time

DCGM_FI_DEV_GPU_UTIL
DCGM_FI_DEV_XID_ERRORS
NVLink throughput

Effective_BER
SymbolErrorCounterExtended

Slurm GPU reservation
queue_wait
```

NVIDIA도 GPU 지표는 DCGM, InfiniBand link health는 UFM, job context는 BCM/Slurm처럼 **전문 telemetry source를 조합**하는 구성을 권장합니다. ([NVIDIA Developer][7])

### 주의할 점

이 가이드는 NVIDIA DGX/HGX 생태계 중심입니다. 다른 GPU·fabric·scheduler를 사용한다면 제품 이름을 복제하는 것이 아니라 **failure-domain coverage와 correlation 원칙**을 가져가는 것이 적절합니다. ([NVIDIA Developer][7])

**후속 관찰 포인트:** training뿐 아니라 inference의 KV cache·TTFT·network telemetry까지 같은 trace에 묶는 방법, 자동 straggler isolation, gray failure 발생 시 node drain 자동화를 볼 만합니다.

**원문:** **[NVIDIA 기술 블로그] Full-Stack Observability for AI Factories** ([NVIDIA Developer][7])

## 5. 에이전트 거버넌스 | “AI가 결제했다”가 아니라 “왜 그 결제가 허가됐는지 증명한다”

### 무엇이 바뀌었나

AWS와 Solv Labs는 8월 12일 AgentCore payments를 이용한 **검증 가능하고 감사 가능한 agent payment architecture**를 공개했습니다. 각 결제는 settlement 전에 ORACLE의 pre-authorization, ICME PreFlight의 policy verification, AWS Nitro Enclave의 integrity attestation과 risk engine을 통과합니다. ([Amazon Web Services, Inc.][8])

핵심 순서는 다음과 같습니다.

```text
agent action
→ policy ALLOW / REVIEW
→ policy proof
→ enclave attestation
→ risk price
→ settlement
```

AWS의 표현대로 **“no decision, no settlement”**가 구조적으로 강제됩니다. AgentCore payment 계층에는 agent나 policy engine과 독립된 per-session spending limit도 있습니다. ([Amazon Web Services, Inc.][8])

Solv의 구현에서는 policy hash, 검증 결과와 proof, 실행 enclave measurement, risk price, settlement artifact를 하나의 signed evidence record에 묶습니다. 파트너 측 측정으로 전체 transaction은 4초 이내, governance overhead는 1초 이내라고 보고됐습니다. 이는 특정 구현의 customer-case 결과이지 AgentCore 전체의 일반 SLA는 아닙니다. ([Amazon Web Services, Inc.][8])

### 왜 중요한가

Agent가 돈·배포·권한·외부 메시지 같은 irreversible side effect를 만들기 시작하면 단순 application log는 부족합니다.

```text
"Agent A가 결제 API를 호출했다"
```

보다 중요한 것은:

```text
누가 요청했는가
어떤 정책 버전인가
당시 한도는 얼마였는가
누가 실행을 승인했는가
실행 코드가 무엇이었는가
실제 settlement와 연결되는가
```

입니다.

이 사례에서 배울 수 있는 더 일반적인 패턴은 **side effect가 발생하기 전에 authorization evidence를 생성하고 action과 cryptographically bind하는 것**입니다. 이 원칙은 결제뿐 아니라 production deployment나 privileged infrastructure change에도 적용할 수 있습니다. 이는 공개 구조를 다른 operational domain으로 확장한 해석입니다. ([Amazon Web Services, Inc.][8])

### 주의할 점

Nitro Enclave와 on-chain anchoring을 사용했다고 해서 agent의 판단 자체가 옳다는 뜻은 아닙니다. AWS 자료도 이 evidence가 **정책 자체가 올바른지, agent 판단이 현명했는지, 상대방이 신뢰할 만한지까지 증명하지는 않는다**고 명시합니다. ([Amazon Web Services, Inc.][8])

즉 attestation은 “잘못된 정책을 정확하게 실행했다”는 것도 증명할 수 있습니다.

**후속 관찰 포인트:** policy update와 evidence versioning, idempotent payment retry, human approval 연결, regulated enterprise에서 audit artifact를 실제로 어떻게 소비하는지가 중요합니다.

**원문:** **[AWS·Solv 기술 사례] Verifiable Agent Payments** ([Amazon Web Services, Inc.][8])

## 6. 머신러닝 연구 | Autoresearch Agent는 GPU보다 먼저 “같은 버그를 여러 번 고치는 데” compute를 낭비한다

### 무엇이 바뀌었나

8월 11일 공개된 **Recovering Wasted Compute in Autoresearch Agents**는 tabular ML 문제를 end-to-end로 해결하는 연구 agent를 분석했습니다. 저자들이 발견한 공통 실패는 네 가지입니다. ([arXiv][9])

1. 서로 다른 search branch가 같은 runtime bug를 반복해서 해결한다.
2. compute budget이 충분히 남았는데도 hyperparameter tuning을 하지 않는다.
3. tree-search라고 부르지만 실제로는 제대로 탐색하지 않는다.
4. EDA를 수행한 뒤 그 결과를 model·feature 선택에 활용하지 않는다. ([arXiv][9])

저자들은 foundation model을 바꾸지 않고 **global debug consultant**, prompt/control 개선과 tree-search 수정만으로 성능을 상당히 개선할 수 있었다고 보고합니다. 논문 abstract는 구체적인 단일 headline 개선율을 제시하지 않으므로 여기서 숫자를 확대해서 해석할 근거는 없습니다. ([arXiv][9])

### 왜 중요한가

Multi-agent나 tree-search를 붙이면 일반적으로:

```text
branch A
branch B
branch C
branch D
```

가 독립적으로 탐색한다고 생각하지만 실제로는 네 branch가 모두:

```text
"이 library에서는 이 argument가 안 먹네"
```

를 각각 10분씩 다시 발견할 수 있습니다.

즉 search parallelism이 **knowledge parallelism이 아니라 failure duplication**이 될 수 있습니다.

### 실무 적용

제가 이 논문의 아이디어를 구현한다면 branch들이 공유하는 별도의 **constraint ledger**를 둡니다.

```text
error_signature
root_cause
working_fix
environment_version
scope
confidence
```

예를 들어 branch A가 `CatBoost GPU + 특정 dtype` 조합이 실패한다는 것을 확인하면 branch B~D는 동일 configuration을 다시 시도하지 않도록 합니다.

또 compute budget도 단일 토큰 한도가 아니라 단계별로 나누는 편이 좋습니다.

```text
30%  baseline / debugging
40%  architecture / feature search
20%  hyperparameter tuning
10%  final validation
```

논문의 또 다른 지적처럼 EDA를 수행했다면 **“이 분석이 어떤 downstream decision을 바꿨는가?”**를 trace에 남기면 ritualistic analysis를 줄일 수 있습니다. ([arXiv][9])

### 주의할 점

연구 대상은 tabular modeling pipeline입니다. Coding agent, 과학 연구, LLM training agent에서도 같은 효과가 그대로 발생한다고 확정할 단계는 아닙니다. 다만 branch 간 failure knowledge 공유라는 설계 원칙은 범용성이 높아 보이며, 실제 적용 여부는 별도 benchmark가 필요합니다. ([arXiv][9])

**후속 관찰 포인트:** shared debug memory가 잘못된 결론을 모든 branch에 퍼뜨리는 failure mode, branch diversity와 knowledge sharing의 균형, cost-per-valid-experiment 기준 평가가 중요합니다.

**원문:** **[논문] Recovering Wasted Compute in Autoresearch Agents** ([arXiv][9])

## 7. AI 안전 | 최종 위반 0건이어도 내부에서는 51번 금지 행동을 시도했을 수 있다

### 무엇이 바뀌었나

8월 10일 공개된 **Multi-Agent AI Safety as an Institutional Design Problem**은 5,280 episode의 multi-agent 실험을 통해 safety rule을 단순 prompt가 아니라 **institution과 authority provenance 문제**로 분석했습니다. ([arXiv][10])

주 실험에서 상세 constitutional prompt는 384건 중 최종 위반 0건을 기록했습니다. Provenance-aware executable guard 역시 최종 위반은 0/384였습니다. 하지만 후자는 내부적으로 **51/384건의 금지 행동 시도를 실제로 차단했고, 그중 44건은 차단 이후 안전한 다른 경로로 task를 완료**했습니다. ([arXiv][10])

이 결과가 상당히 중요합니다.

```text
System A
위반 시도 자체 없음
→ violation = 0

System B
51번 금지 행동 시도
→ runtime이 모두 차단
→ violation = 0
```

최종 metric만 보면 둘은 똑같지만 실제 안전 메커니즘은 완전히 다릅니다.

### Provenance가 왜 중요한가

연구는 현재 local state만 검사하는 guard와 **원래 authority의 provenance까지 추적하는 guard**도 비교했습니다.

정책이 변환·전달되는 laundering scenario에서 local-state guard는 96건 중 22건의 위반을 허용했지만 provenance-based enforcement는 0/96이었습니다. ([arXiv][10])

예를 들면:

```text
원래 authority:
"Agent B는 데이터 외부 전송 금지"

        ↓ 변환

Agent C가 받은 현재 state:
"이 결과를 협력자에게 전달"
```

현재 문장만 보면 정상 요청일 수 있지만 원래 권한을 따라가면 불가능한 행동일 수 있습니다.

### 실무 적용

Agent safety dashboard에는 최소한 다음을 분리해야 합니다.

```text
attempted_violation
blocked_violation
realized_violation

safe_completion_after_block

authority_provenance_valid
```

특히 `blocked_violation`이 증가하는데 `realized_violation=0`이라고 해서 안전성이 개선됐다고 단정해서는 안 됩니다. 모델 behavior가 악화되고 runtime guard가 간신히 막고 있는 상황일 수도 있습니다.

또 block 이후 `STOP`만 강제하는 것보다 **허용된 대체 경로를 제공하는 recovery design**이 중요합니다. 이 연구에서도 차단된 51건 중 44건이 이후 안전하게 완료됐습니다. ([arXiv][10])

### 주의할 점

단일 연구자의 초기 preprint이며 structured workflow와 제한된 model family를 사용했습니다. `0/384`는 일반적인 안전 보장이 아닙니다. 다만 **최종 violation rate 하나만으로 agent safety를 평가하면 메커니즘을 놓친다**는 방법론적 지적은 매우 강합니다. ([arXiv][10])

**후속 관찰 포인트:** MCP delegation의 authority provenance, multi-agent chain에서 capability token 전달, block 이후 recovery policy, provenance 정보 자체의 변조 방지가 핵심입니다.

**원문:** **[논문] Multi-Agent AI Safety as an Institutional Design Problem** ([arXiv][10])

# 오늘의 실습 | Agent Plugins 1.0으로 “Skill + MCP”를 하나의 패키지로 만들어보기

오늘은 표준이 실제로 해결하는 것과 **해결하지 않는 것**을 직접 확인하는 실습이 가장 좋습니다.

먼저 다음 구조의 작은 read-only plugin을 만듭니다. 공식 v1 사양의 directory layout과 동일한 형태입니다. ([GitHub][3])

```text
service-health-plugin/
├── plugin.json
├── skills/
│   └── check-service/
│       └── SKILL.md
└── mcp.json
```

최소 manifest는 공식 사양대로 다음 두 필드만으로 시작할 수 있습니다. ([GitHub][3])

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "service-health-plugin"
}
```

Skill의 업무는 아주 단순하게 잡습니다.

```text
"서비스 상태를 확인하고,
장애 원인을 요약하되
어떠한 변경도 수행하지 않는다."
```

MCP 서버도 실제 production 시스템 대신 mock server를 사용해 다음 하나의 tool만 제공합니다.

```text
get_service_status(service_name)
```

그다음 같은 plugin을 **VS Code와 Copilot CLI 두 client에서 각각 로드**해 다음을 검사합니다. 두 client 모두 Agent Plugins 1.0 GA 지원 대상입니다. ([The GitHub Blog][2])

```text
plugin_install_success
skill_discovered
mcp_server_discovered
tool_call_success

same_skill_behavior
tool_schema_hash
permission_prompt_count
```

여기서 끝내지 말고 보안 테스트를 하나 추가하는 것이 핵심입니다.

MCP server를 조직의 허용 목록에서 제거한 상태로 plugin은 그대로 설치해 보십시오.

기대 결과는:

```text
plugin       → 설치 가능
skill        → 읽기 가능
MCP server   → policy로 차단
```

이어 테스트용 plugin에서 `../`를 이용해 package root 밖의 실행 파일을 참조하도록 바꿉니다. Agent Plugins v1 사양상 client는 이러한 package-path escape를 거부해야 합니다. ([GitHub][3])

마지막으로 결과를 다음 네 축으로 평가하면 됩니다.

```text
Portability
- 두 client가 동일 Skill과 MCP를 찾는가

Compatibility
- client별 extension 없이 핵심 기능이 같은가

Governance
- 허용되지 않은 MCP가 실제로 차단되는가

Isolation
- plugin package containment와
  subprocess 권한이 별개임을 확인했는가
```

이 실습에서 가장 중요한 결론은 **“한 번 만들어 어디서든 실행된다”가 아니라 “한 번 패키징해도 각 runtime의 권한 경계는 계속 별도로 관리해야 한다”**는 것입니다. Agent Plugins 1.0이 해결하는 것은 배포 형식의 중복이고, agent sandbox·network permission·secret access까지 자동으로 해결해 주는 표준은 아닙니다. ([GitHub][3])
