# AI 엔지니어 데일리 브리핑

**2026년 8월 10일 월요일 · 한국시간 오전 기준**
**분석 범위:** 8월 9일까지 확인 가능한 공식 릴리스와 8월 초 공개된 최신 연구

오늘의 흐름은 꽤 선명합니다. **에이전트 성능의 병목이 모델 자체에서 runtime state, cache, sandbox, CPU↔GPU 경계, observability로 빠르게 이동하고 있습니다.** Cline과 Qwen Code의 최신 릴리스는 중단 복구·checkpoint·prompt cache·병렬 tool call을 직접 다루고 있고, Microsoft Azure의 production 분석은 agent workload가 GPU만의 문제가 아니라 CPU orchestration과 불규칙한 tool burst의 문제임을 보여줍니다. 동시에 실제 기업 수준의 sandbox를 적용하면 coding-agent 성공률이 떨어지고 비용은 크게 증가한다는 정량 결과도 나왔습니다. ([GitHub][1])

## 1. 필독 | Cline 4.1.7·Qwen Code 0.21.8 — 장기 에이전트의 핵심은 “중단돼도 상태를 잃지 않는가”

### 무엇이 바뀌었나

Cline은 **8월 9일 v4.1.7**을 공개했습니다. 이번 릴리스의 핵심은 새로운 coding capability보다 실행 상태의 내구성입니다. 실행 중 입력한 다음 prompt가 abort 이후에도 사라지지 않고, hub가 재시작되거나 작업이 중단돼도 session context를 유지합니다. 실패한 queued turn은 정상 완료처럼 사라지지 않고 `run.failed`로 기록되며, MCP 서버 하나가 hang되어도 전체 session 생성이 막히지 않도록 30초 initialize budget을 둡니다. 네트워크가 model output 이전에 끊어진 경우 재시도하고, checkpoint diff에는 snapshot 당시 untracked file까지 포함합니다. ([GitHub][1])

Qwen Code도 **8월 8일 v0.21.8**에서 비슷한 방향으로 움직였습니다. OpenAI·Gemini·Vertex provider 사이에서 conversation prefix용 compression cache를 공유하고, `/review`에 repository-specific context manifest를 추가했습니다. Remote matching 일부를 deterministic CLI 작업으로 옮긴 뒤 Qwen 측 workload에서 최대 **93.3% prompt-cache hit rate**를 기록했다고 설명합니다. ACP agent의 tool fan-out도 설정된 concurrency까지 병렬 실행하도록 바뀌었습니다. 명시적으로 신뢰하지 않는 workspace가 parent directory의 trust를 상속하던 보안 문제도 수정됐습니다. ([GitHub][2])

### 왜 중요한가

실제 coding agent는 다음과 같은 loop를 몇십~몇백 번 반복합니다.

```text
읽기 → 계획 → 수정 → 테스트
       ↓
   MCP / shell / Git
       ↓
   실패 → 재계획
```

여기서 foundation model이 동일해도 runtime이 prompt queue를 잃거나, restart 후 완료 상태를 잊거나, MCP 하나 때문에 전체 session이 멈추면 agent의 체감 성능은 급격히 떨어집니다.

반대로 장기 작업에서는 다음이 모델 accuracy만큼 중요해집니다.

```text
durable state
checkpoint
cache reuse
idempotent retry
bounded timeout
tool concurrency
```

즉 **“좋은 코딩 모델”과 “좋은 코딩 에이전트”는 점점 별개의 엔지니어링 문제**가 되고 있습니다. 두 최신 릴리스가 거의 동시에 state durability와 cache efficiency를 강화한 것은 이 흐름을 잘 보여줍니다. ([GitHub][1])

### 실제 시스템에 적용한다면

Coding-agent telemetry에 다음 필드를 넣는 것을 권합니다.

```text
session_id
checkpoint_id
resume_count
resume_success
queued_turns_lost

prompt_cache_hit_tokens
prompt_cache_miss_tokens

mcp_startup_latency
mcp_timeout_count

tool_calls_serial
tool_calls_parallel
retry_count
```

특히 `resume_success`를 정의할 때 단순히 process가 다시 시작됐는지가 아니라 다음을 확인해야 합니다.

```text
수정했던 파일 유지
완료된 task 유지
실패했던 접근 기억
금지된 재시도 반복 안 함
테스트 결과 유지
```

### 주의할 점

Qwen Code의 **93.3% cache hit**는 `/review` remote-matching 경로에서 프로젝트가 측정한 특정 결과입니다. 모든 repository와 provider에서 동일한 hit rate가 나온다는 뜻은 아닙니다. ACP tool을 병렬화하면 latency는 줄어들 수 있지만 외부 API rate limit, 동일 resource에 대한 race, 중복 side effect가 증가할 수도 있습니다. ([GitHub][2])

Cline의 checkpoint도 rollback 시스템과 동일하지는 않습니다. 특히 DB·GitHub·cloud API처럼 filesystem 밖에서 발생한 side effect는 별도 idempotency와 compensation 처리가 필요합니다.

**후속 관찰 포인트:** agent runtime 간 checkpoint 포맷 표준화, MCP server 상태까지 포함한 resume, prompt-cache 비용과 strict-success 간 관계.

**원문:** **[릴리스 노트] Cline v4.1.7** ([GitHub][1]) · **[릴리스 노트] Qwen Code v0.21.8** ([GitHub][2])

## 2. Anthropic | Claude Code가 개인 CLI에서 분산 에이전트 실행 플랫폼으로 확장

### 무엇이 바뀌었나

Claude Code의 8월 7~8일 릴리스에는 운영 관점에서 중요한 변화가 연속으로 들어왔습니다.

`v2.1.224`에서는 `claude self-hosted-runner`가 추가돼 Team·Enterprise 환경에서 자체 서버나 container를 Claude Code web·desktop·mobile session의 실행 위치로 사용할 수 있게 됐습니다. 여러 machine의 Claude Code session끼리 `SendMessage`로 통신하는 기능도 추가됐고, session discovery는 `ListAgents`로 제공합니다. ([GitHub][3])

보안 측면에서는 JWT claim별 masking, AWS credential pair와 SigV4 재서명 등 structured credential masking이 추가됐고, filesystem deny path 끝에 `/`가 붙으면 제한을 우회할 수 있던 Linux/macOS sandbox 문제도 수정됐습니다. Cross-session message가 bypass-permission session에 도착하는 경우 바로 실행하지 않고 approval을 기다리도록 하는 옵션도 추가됐습니다. ([GitHub][3])

이어 `v2.1.225`에서는 gateway의 **spend limit**을 Claude Code usage warning과 직접 연결했고, `claude agents`에도 untrusted workspace trust prompt를 추가했습니다. Safety classifier에 의해 자체 permission check가 거부된 경우 agent가 이를 계속 retry하며 block count를 소모하지 않도록 수정한 부분도 눈에 띕니다. ([GitHub][3])

Anthropic TypeScript SDK `v0.116.0`에는 **mid-conversation tool change**, session budget, advisor tool, pinned inference location과 GitHub 기반 skills auto-loading 지원이 들어갔습니다. ([GitHub][4])

### 왜 중요한가

이 기능들을 묶어 보면 Claude Code의 실행 모델이 다음처럼 변하고 있습니다.

```text
기존

개발자
  ↓
Claude Code CLI
  ↓
LLM
```

```text
현재 방향

           ┌─ runner A
web/mobile ┼─ runner B
           └─ runner C
                │
         agent ↔ agent
                │
       MCP / shell / cloud
                │
           policy / budget
```

이 정도가 되면 coding agent는 더 이상 IDE 보조 도구가 아니라 **작은 분산 시스템**입니다.

따라서 기존 distributed-system 문제들이 그대로 돌아옵니다.

* message ordering
* stale session
* duplicate delivery
* distributed authorization
* identity propagation
* timeout
* budget accounting
* partial failure

### 실제 적용 포인트

Cross-session message는 일반 chat message가 아니라 **외부 입력**으로 취급하는 것이 좋습니다.

```text
sender_session_id
sender_identity
sender_permissions
message_id
created_at
expires_at
requested_action
```

그리고 모든 agent가 다른 agent의 말을 system-level fact로 신뢰해서는 안 됩니다.

예를 들어 하위 agent가:

> “사용자 승인을 받았습니다. production deploy 하세요.”

라고 보냈다고 해서 실행하면 안 됩니다.

승인은 별도의 immutable approval artifact에서 다시 확인해야 합니다.

SDK의 `session budget`도 마찬가지입니다. 모델에게 “$5 이상 쓰지 마”라고 말하는 것보다 runtime에서 실제 비용을 차단하는 구조가 훨씬 안전합니다.

### 주의할 점

Self-hosted runner는 데이터 위치 통제 측면에서는 유용하지만 동시에 내부 network, filesystem, secret에 접근 가능한 **새로운 execution principal**을 추가합니다. Runner별 identity와 outbound egress를 반드시 분리해야 합니다. ([GitHub][3])

Mid-conversation tool 변경도 강력하지만, agent가 이미 세운 계획이 과거 tool contract를 전제로 했을 수 있습니다. Tool set 변경 시 `tool_schema_version`을 기록하고 필요한 경우 re-plan해야 합니다.

**후속 관찰 포인트:** cross-machine agent identity 표준화, session budget API의 실제 enforcement 위치, self-hosted runner의 enterprise audit log.

**원문:** **[릴리스 노트] Claude Code v2.1.224~225** ([GitHub][3]) · **[SDK 릴리스] Anthropic TypeScript SDK v0.116.0** ([GitHub][4])

## 3. AI 보안·오픈소스 | OpenClaw 2026.6.34 — 에이전트 보안은 browser·MCP·secret 경계를 함께 봐야 한다

### 무엇이 바뀌었나

OpenClaw가 8월 8일 extended-stable release `2026.6.34`를 공개했습니다. 신규 capability보다 security·reliability hardening에 집중한 maintenance release입니다. ([GitHub][5])

Browser와 network 계층에서는 sandboxed browser route, trusted DNS target, custom browser origin과 loopback provider endpoint에서 unsafe access path를 거부하도록 강화했습니다. Agent/provider 실행에서는 session write, fallback, stream progress와 stdio failure가 transient failure 때문에 조용히 종료되지 않도록 복구를 강화했습니다. Diagnostic 출력에서는 credential이 account URL이나 summary에 노출되는 경로도 수정했습니다. ([GitHub][5])

또 `brace-expansion`, PostCSS, `fast-uri`, `ip-address`, Undici 등 production dependency를 보안 수정 버전으로 업데이트했고, browser·sandbox·exec·MCP·secret-resolution 경로의 입력 검증을 강화했습니다. npm과 container artifact에는 signature와 **SLSA provenance attestation**도 제공합니다. ([GitHub][5])

### 왜 중요한가

에이전트의 공격 표면은 모델 endpoint 하나가 아닙니다.

```text
LLM
 ↓
MCP
 ↓
browser
 ↓
HTTP / DNS
 ↓
local files
 ↓
credentials
 ↓
cloud / SaaS
```

따라서 prompt injection 방어만 잘해도 browser layer에서 SSRF성 경로가 열려 있거나, MCP가 localhost metadata endpoint에 접근할 수 있으면 시스템은 여전히 위험합니다.

이번 릴리스는 **모델 alignment와 runtime isolation은 서로 대체 관계가 아니라는 것**을 실무적으로 보여줍니다. ([GitHub][5])

### 실무 적용

Agent container를 배포한다면 이미지 tag만 pin하지 말고 다음을 함께 기록하는 것이 좋습니다.

```text
container_digest
package_lock_hash
release_signature
provenance_attestation

allowed_dns
allowed_cidrs
allowed_mcp_servers
loopback_policy

secret_sources
redaction_policy
```

특히 다음 주소는 기본적으로 agent/browser에서 차단할 이유가 큽니다.

```text
127.0.0.0/8
169.254.0.0/16
RFC1918 private networks
cloud metadata endpoints
host-local admin ports
```

물론 내부 agent가 실제 private API에 접근해야 한다면 전면 허용보다 목적지별 explicit allowlist가 낫습니다.

### 주의할 점

Signed artifact와 SLSA provenance는 **어떤 build가 배포됐는지**를 검증해줄 뿐, 실행된 agent가 안전하다는 것을 증명하지는 않습니다.

또 이번 버전은 extended-stable maintenance release로, 프로젝트 자체도 새로운 release-line 기능을 추가한 버전이 아니라고 명시합니다. ([GitHub][5])

**후속 관찰 포인트:** MCP-level capability token, browser egress policy 표준, agent image에 대한 runtime attestation.

**원문:** **[GitHub 릴리스] OpenClaw 2026.6.34** ([GitHub][5])

## 4. 필독 | Microsoft Azure 실측: Agent workload에서는 CPU도 critical path다

### 무엇이 바뀌었나

`Architectural Implications of Agentic AI Workflows`는 Microsoft Azure production workload와 여러 오픈소스 agent framework를 분석해 agentic AI의 server-level 특성을 조사했습니다.

연구진은 agent request가 단일 inference가 아니라 **LLM inference → tool → orchestration → LLM → tool**을 반복하면서 CPU와 GPU 경계를 계속 넘는다는 점을 지적합니다. Tool과 orchestration이 host에서 실행되기 때문에 CPU가 critical path에 들어가고, 평균 CPU 사용률은 낮더라도 특정 tool phase에서 갑자기 spike하는 bursty load가 나타났습니다. 여러 agent를 동일 CPU core에 multiplex하면 microarchitectural locality도 나빠졌습니다. ([arXiv][6])

연구진이 만든 Agora prototype은 idle CPU core를 co-located 작업에 사용하되 agent tool burst가 발생하면 tail latency를 보호하고, CPU core를 역할별 pool로 나누며 affinity-aware scheduling을 적용합니다. GPU 쪽에서는 agent state를 prefetch하면서 더 많은 agent를 하나의 GPU에 올리는 방식으로 GPU memory oversubscription도 실험했습니다. ([arXiv][6])

비슷한 문제를 hardware 관점에서 본 HeteroPanacea 연구도 공개됐습니다. 이 simulation framework는 prefill·decode뿐 아니라 Attention과 FFN까지 서로 다른 hardware로 분리하는 PDAF 구조를 분석합니다. 현재 GPU를 가정한 simulation에서는 Prefill–Decode 분리로 기존 serving 대비 **최대 75% throughput 증가**를 보고했고, custom NPU가 가능하다는 가정에서는 4-way Prefill–Decode–Attention–FFN 분리가 여러 model에서 가장 일관된 개선을 보였다고 저자들은 보고합니다. ([arXiv][7])

### 왜 중요한가

LLM 서버를 튜닝할 때 흔히 보는 지표는:

```text
GPU utilization
HBM
tokens/s
```

입니다.

하지만 agent server에서는 실제 critical path가 다음처럼 될 수 있습니다.

```text
GPU  500 ms
↓
CPU tool processing 400 ms
↓
network API 800 ms
↓
CPU JSON / orchestration 150 ms
↓
GPU 300 ms
```

이 상황에서 GPU kernel을 20% 빠르게 해봐야 전체 요청 latency 개선은 작습니다.

따라서 **agentic serving에서는 모델 FLOPs만이 아니라 workflow topology가 hardware demand를 결정**합니다. ([arXiv][6])

### 실무 적용

다음과 같이 phase별 utilization을 분리해서 기록하는 것이 좋습니다.

```text
phase=llm_prefill
phase=llm_decode
phase=tool
phase=orchestrator
phase=serialization
phase=network_wait
```

각 phase별로:

```text
cpu_core_time
gpu_active_time
memory_bw
network_bytes
queue_time
P95 latency
```

를 남깁니다.

GPU utilization이 50%라고 바로 GPU workload를 더 넣기보다, **다음 tool burst가 왔을 때 CPU가 tail latency를 망가뜨리지 않는지** 확인해야 합니다.

### 주의할 점

HeteroPanacea의 75% 수치는 실제 production cluster 측정이 아니라 simulation 결과입니다. 특히 PDAF 4-way 결과는 custom NPU가 있다는 가정을 포함하므로 지금 GPU cluster에서 그대로 재현할 수 있는 숫자가 아닙니다. ([arXiv][7])

반면 Microsoft 연구는 production observation이 포함된다는 점에서 workload characterization 신뢰도는 높지만, 공개 abstract만으로 모든 내부 환경과 workload 분포를 확인할 수는 없습니다.

**후속 관찰 포인트:** vLLM/SGLang에서 tool-aware scheduling, CPU role pooling, GPU state swap/prefetch가 agent P95에 미치는 실제 영향.

**원문:** **[논문] Architectural Implications of Agentic AI Workflows** ([arXiv][6]) · **[논문] When Does Disaggregation Pay?** ([arXiv][7])

## 5. GPU 추론 | Bole: Hybrid-attention 모델에서는 speculative decoding의 “state” 처리부터 다시 설계해야 한다

### 무엇이 바뀌었나

Bole은 full attention과 recurrent linear attention을 섞어 사용하는 hybrid-attention LLM용 tree speculative decoding 시스템입니다.

기존 tree speculation은 Transformer의 KV cache를 전제로 설계됐습니다. Hybrid model에서는 recurrent layer의 각 branch마다 전체 state를 복제·순회해야 해 proposal tree가 커질수록 verification latency와 transient memory가 급증합니다. ([arXiv][8])

Bole은 linear-attention recurrence를 tree 구조의 closed form으로 바꾸고 proposal node를 GPU에서 병렬 검증합니다. 저자 측 실험에서는 linear-attention tree verification을 **3.4~7.7배** 빠르게 했고, speculative transient state memory를 **82~99%** 줄였습니다. SGLang에 통합한 네 모델·두 GPU platform 실험에서 autoregressive decoding 대비 offline throughput 최대 4.72배, 가장 강한 tree-speculative baseline 대비 최대 2.03배를 보고했습니다. ([arXiv][8])

Agent workload에서는 baseline 대비 TTFT를 최대 67.6% 줄이고 TPOT를 최대 49.9% 개선했다고 보고합니다. ([arXiv][8])

### 왜 중요한가

최근 모델들은 순수 Transformer만 사용하지 않습니다.

```text
full attention
+
linear attention
+
SSM / recurrence
```

같은 hybrid architecture가 늘어나면 serving framework도 기존의:

```text
KV cache 관리
```

만으로 충분하지 않습니다.

앞으로는:

```text
KV cache
+
recurrent state
+
speculative branch state
```

를 함께 관리해야 합니다.

즉 모델 architecture의 변화가 곧 inference runtime의 데이터 구조 변화로 이어집니다.

### 실무 적용

Hybrid model을 speculative decoding으로 평가할 때는 accepted token 수만 보지 말고 다음을 함께 측정해야 합니다.

```text
draft_length
acceptance_length

verification_latency
recurrent_state_bytes
temporary_state_bytes
KV_cache_bytes

TTFT
TPOT
batch_size
```

특히 speculative algorithm이 평균 tokens/s를 높이면서도 temporary state 때문에 concurrency를 떨어뜨릴 수 있습니다.

따라서 좋은 기준은:

```text
throughput at fixed memory budget
```

입니다.

### 주의할 점

4.72배·67.6%·49.9%는 Bole 저자들의 특정 모델·GPU·workload에서 기록한 최대치입니다. 모든 hybrid model이 같은 recurrence 구조를 갖는 것도 아니며 proposal acceptance rate에 따라 효율이 크게 변할 수 있습니다. ([arXiv][8])

**후속 관찰 포인트:** SGLang upstream 채택 정도, Qwen3.5 등 주요 hybrid family별 효율, high-concurrency에서 state memory 절감이 실제 batch size 증가로 이어지는지.

**원문:** **[논문] Bole: Efficient Tree Speculation for Hybrid-Attention Language Models** ([arXiv][8])

## 6. MLOps | TELLER: LLM serving 장애를 Python 로그와 GPU profiler 따로 보지 말고 하나의 request tree로

### 무엇이 바뀌었나

TELLER는 LLM inference의 root-cause analysis를 request 단위로 연결하는 연구입니다.

하나의 inference 요청은 다음 경로를 지나갑니다.

```text
serving engine
↓
Python / C++
↓
CUDA host API
↓
GPU kernel
↓
NCCL / distributed communication
```

현재는 application log와 Nsight/CUPTI timeline이 따로 존재해 “이 사용자 요청이 느려진 원인이 정확히 어느 kernel·communication·host event인가”를 연결하기 어렵습니다. ([arXiv][9])

TELLER는 model binary를 수정하지 않고 NVTX/CUPTI trace와 service log를 수집한 뒤 **per-request call-chain tree**를 재구성합니다. Parent-child 관계, 시간 순서와 communication dependency를 보존하는 causal slice를 생성하고, 이를 Trace Pair Encoding(TPE)으로 압축합니다. ([arXiv][9])

Multi-node GPU inference 실험에서 적절한 TPE vocabulary를 사용하면 per-step trace 길이를 **80% 이상 감소**시키면서 가장 좋은 진단 성능을 보였고, 지나치게 공격적으로 압축하면 진단 품질이 떨어졌습니다. ([arXiv][9])

### 왜 중요한가

LLM service의 장애는 종종 이렇게 보입니다.

```text
P95 TTFT 증가
```

하지만 실제 원인은 다음 중 무엇이든 될 수 있습니다.

```text
Python scheduler stall
CPU serialization
CUDA launch delay
GPU kernel regression
NCCL straggler
memory pressure
```

즉 **metric → trace → operator → source layer**가 연결되어야 root cause를 빨리 찾을 수 있습니다.

### 실무 적용

모든 request에 공통 ID를 붙이는 것부터 시작하면 됩니다.

```text
request_id
trace_id
model_id
worker_id
gpu_id
rank
```

그리고 span 구조를:

```text
request
├─ scheduler
├─ prefill
│   ├─ attention
│   └─ moe
├─ communication
└─ decode
```

처럼 맞추면 로그와 GPU trace를 훨씬 쉽게 연결할 수 있습니다.

특히 신규 FlashAttention·FlashInfer·CUDA·NCCL 버전을 올린 뒤 latency regression이 생겼을 때 매우 유용합니다.

### 주의할 점

TELLER의 multimodal RCA model이 생성하는 자연어 설명은 **증거 탐색 도구이지 최종 진실 판정기**가 아닙니다. 원인 후보를 좁힌 뒤 원래 trace와 benchmark를 사람이 확인해야 합니다.

또 CUPTI/NVTX tracing 자체가 overhead를 만들 수 있으므로 production에서는 sampling이나 canary worker가 필요합니다. ([arXiv][9])

**후속 관찰 포인트:** vLLM/SGLang native integration, OpenTelemetry GPU semantic convention, inference regression 자동 bisect와 연결.

**원문:** **[논문] TELLER: Non-intrusive Cross-Layer Root-Cause Analysis for LLM Inference** ([arXiv][9])

## 7. 필독 | Boundary-Bench: Sandbox를 현실적으로 만들자 coding agent 성공률은 최대 18.3%p 하락

### 무엇이 바뀌었나

`Permission Denied` 연구는 12개의 coding-agent 구성을 Terminal-Bench 2.1에서 실행하면서 environment security를 단계적으로 강화했습니다.

정책에는 다음과 같은 실제 기업 환경의 제한이 들어갑니다.

```text
scoped credentials
restricted network egress
read-only OS
frozen home
non-root
no privilege escalation
```

가장 엄격한 조건에서 agent별 성공률 손실은 최대 **18.3 percentage points**, 비용 증가율은 최대 **167.3%**였습니다. 특히 흥미로운 점은 성공률을 가장 잘 유지하는 모델이 비용 효율성도 가장 잘 유지하지는 않았다는 것입니다. 따라서 “보안 환경에서 가장 좋은 agent”는 단일 ranking으로 결정하기 어렵습니다. ([arXiv][10])

실패 방식도 변했습니다. Policy가 action을 막았을 때 agent가 즉시 “할 수 없다”고 끝나는 것보다 계속 workaround를 시도하다 timeout이나 잘못된 solution으로 끝나는 경우가 관찰됐습니다. ([arXiv][10])

연구진은 실제 실행 가능한 **Boundary-Bench**도 공개했습니다. `control`, `non-root`, `high-nist` policy를 제공하고 nftables, read-only bind mount, `no_new_privs`, capability drop, Landlock 같은 실제 Linux primitive로 제한을 구현합니다. Claude Code, Codex, Grok와 Terminus 2 harness를 지원합니다. ([GitHub][11])

### 왜 중요한가

SWE-bench나 Terminal-Bench 점수가 높아도 실제 회사 서버에 들어가면 agent는 다음을 마음대로 할 수 없습니다.

```text
sudo apt install
curl arbitrary-site.com
write /etc/*
read ~/.aws/*
```

그런데 agent benchmark가 permissive root container에서만 수행된다면 실제 enterprise deployment 성능을 과대평가할 수 있습니다.

즉 앞으로 coding-agent benchmark에는 최소 두 점수가 필요합니다.

```text
Capability Score
Security-Constrained Score
```

### 실무 적용

직접 평가한다면 다음 네 조건만으로도 유용합니다.

```text
A. root + unrestricted network

B. non-root

C. B + read-only OS

D. C + egress allowlist
```

그리고 단순 pass/fail뿐 아니라 다음을 기록합니다.

```text
strict_success
cost

blocked_actions
repeated_blocked_actions
timeout
wrong_solution

policy_workaround_attempts
```

특히 `blocked action → 동일 행동 변형 → 또 차단 → 반복` 패턴은 agent runtime에 별도 recovery policy를 넣을 좋은 신호입니다.

### 주의할 점

Policy 때문에 원천적으로 해결할 수 없는 task를 agent 실패로 계산하면 안 됩니다. Boundary-Bench 저장소도 현재 Terminal-Bench 2.1 task 가운데 hardened policy 아래에서 수행 불가능한 항목을 별도로 표시하고 성공률 계산에서 구분하며, 일부 verifier는 non-root 환경에서도 올바른 solution을 공정하게 평가하도록 수정본을 사용합니다. ([GitHub][11])

따라서 **security benchmark 자체도 task solvability를 먼저 검증해야 합니다.**

**후속 관찰 포인트:** 실제 기업 CI/CD permission으로 확장, MCP permission policy 결합, sandbox 제한을 인지한 agent용 post-training.

**원문:** **[논문] Permission Denied** ([arXiv][10]) · **[GitHub] Boundary-Bench** ([GitHub][11])

## 8. 멀티모달 연구 | ToolArtist: 이미지 생성 모델도 “검색 → 추론 → 생성”을 하나의 agent policy로

### 무엇이 바뀌었나

ToolArtist는 Unified Multimodal Model을 post-training해 reasoning, 외부 tool과 native image generation을 **하나의 policy가 직접 조정**하도록 한 연구입니다.

기존 agentic image generation은 보통 workflow가 고정돼 있습니다.

```text
검색
→ prompt 개선
→ 이미지 생성
→ 결과 평가
```

또는 일부 단계만 agent가 결정합니다.

ToolArtist는 모델이 상황에 따라 스스로 reasoning하고 검색 도구를 사용할지 결정한 뒤 이미지를 생성하도록 합니다. ([arXiv][12])

SFT 단계에서는 teacher agent에게 검색과 image-generation tool을 제공해 trajectory를 수집합니다. 그 뒤 image generation tool 호출 자체는 숨기고 생성된 이미지만 Unified Multimodal Model training trajectory에 유지합니다. RL 단계에서는 **Reason-Act-Draw GRPO(RAD-GRPO)**를 사용해 intent reward와 visual quality reward를 함께 최적화합니다. ([arXiv][12])

저자들은 전체 open-world generation 과정을 agent policy에 맡긴 방식이 fixed workflow나 부분적으로 agent화한 방식보다 일관되게 높은 결과를 보였다고 보고하며, training data와 post-training infrastructure 공개를 명시했습니다. ([arXiv][12])

### 왜 중요한가

멀티모달 agent가 발전하면 generation도 단순 API가 아니라 다음처럼 변할 수 있습니다.

```text
"1960년대 서울 거리와
실제 당시 광고판 스타일을 참고해
영화 포스터를 만들어줘"

        ↓

사실 확인
→ 이미지 reference 검색
→ 시대적 요소 추론
→ composition 결정
→ 이미지 생성
→ 결과 검증
→ 필요 시 수정
```

즉 생성 품질은 diffusion/decoder의 visual fidelity뿐 아니라 **research와 planning 품질**에 의해 결정됩니다.

### 실무 적용

이런 agent를 평가할 때 최종 이미지 하나만 보고 평가하면 부족합니다.

```text
tool_selection
source_quality
search_grounding

generated_image
intent_match
visual_quality

tool_cost
iteration_count
wall_clock
```

를 별도로 기록해야 합니다.

또 검색 과정에서 가져온 이미지·웹페이지는 prompt injection의 입력이 될 수 있으므로 text agent와 동일한 retrieval-security 문제가 발생합니다.

### 주의할 점

현재는 초기 arXiv 연구입니다. “agent policy가 항상 우수하다”는 결론을 일반화하기 전에 평가 judge, reward design, 검색 비용과 추가 inference 비용을 동일 budget에서 비교해야 합니다. ([arXiv][12])

특히 agent가 여러 번 생성하면 최고의 결과는 좋아져도 **이미지 한 장을 성공적으로 얻는 비용**이 크게 올라갈 수 있습니다.

**후속 관찰 포인트:** 공개 checkpoint와 data의 실제 범위, tool-call budget을 고정한 비교, image agent의 search prompt-injection 방어.

**원문:** **[논문] ToolArtist: Tool-Using Unified Multimodal Models for Agentic Image Generation** ([arXiv][12])

# 오늘의 실습 | Coding Agent를 “회사 서버”처럼 제한해서 돌려보기

오늘은 Boundary-Bench 아이디어를 작은 규모로 직접 재현하는 실습이 좋습니다.

작은 Python repository 하나를 준비하고 agent에게 다음 작업을 줍니다.

> 실패하는 테스트를 분석하고 코드를 수정한 뒤 전체 테스트를 통과시켜라.

같은 agent·model·prompt를 네 환경에서 실행합니다.

```text
A. Permissive
root
network unrestricted
filesystem unrestricted

B. Non-root
ordinary user

C. Hardened FS
non-root
OS read-only
workspace만 writable

D. Enterprise-like
C
+ network allowlist
+ ~/.ssh ~/.aws ~/.config 접근 차단
```

각 조건은 최소 5회 반복합니다.

기록할 지표는 다음으로 충분합니다.

```text
strict_success
wall_clock
input_tokens
output_tokens
cost

blocked_commands
blocked_network_calls

same_block_retries
timeout
wrong_solution
```

여기에 오늘 Cline 릴리스의 핵심을 추가해 **D 환경에서 한 번은 작업 중간에 agent process를 강제 종료했다가 resume**해보십시오.

추가 측정:

```text
resume_success
files_preserved
task_state_preserved
failed_attempt_preserved
duplicate_action_after_resume
```

가장 흥미로운 결과는 다음 표가 됩니다.

| 환경              | 성공률 | 평균 비용 | Block 횟수 | 반복 Block | Resume 성공 |
| --------------- | --: | ----: | -------: | -------: | --------: |
| Permissive      |     |       |          |          |           |
| Non-root        |     |       |          |          |           |
| Hardened FS     |     |       |          |          |           |
| Enterprise-like |     |       |          |          |           |

여기서 목표는 restrictive environment에서도 permissive 환경과 같은 점수를 만드는 것이 아닙니다.

**핵심은 agent가 권한 부족을 정상적인 환경 상태로 이해하고, 위험한 workaround를 반복하지 않으면서 다른 해결책으로 전환하는지를 확인하는 것**입니다.

이 특성이 확보되면 coding-agent의 “벤치마크 점수”에서 한 단계 더 나아가 실제 사내 서버·CI·GPU 개발 환경에서 사용할 수 있는 **operational reliability**를 평가하기 시작한 것입니다. ([arXiv][10])
