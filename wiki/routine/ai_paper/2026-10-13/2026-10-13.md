**조사 범위:** 10월 12일 미국·유럽에서 공개된 기업 공식 발표와 arXiv의 10월 12일 신규 공개 목록을 조사했습니다. 논문은 실제 제출일과 공개 목록 등재일을 구분했습니다.

오늘은 상당히 중요한 발표가 집중됐습니다. **Meta가 Muse Wonder와 Wonder Full을 공개하며 프론티어 모델 경쟁에 다시 진입했고, Microsoft는 차세대 AI 추론 가속기 Maia 300의 구체적인 아키텍처를 발표했습니다.** AMD 역시 에이전트 실행을 위한 CPU 중심 랙 인프라 Helion을 공개했습니다.

오늘의 핵심 흐름은 다음과 같습니다.

> **AI 시스템 최적화의 중심이 모델 크기에서 실제 연산 예산의 배분으로 이동하고 있습니다. 추론에서는 메모리 대역폭·토큰화·반복 연산이, 학습에서는 데이터 난이도·보상 신호·검증 비용이 핵심 변수로 부상하고 있습니다.**

오늘은 중요도 높은 **8개 항목**을 선정했습니다. 공식 발표 수치와 연구자의 실험 결과를 구분했고, 실제 적용 시 확인해야 할 한계도 함께 정리했습니다.

## 1. Meta Muse Wonder — 프론티어 모델 경쟁의 새로운 축은 Active Memory와 Long-Horizon Agent ★★★★★

**공개일: 2026년 10월 12일 | 분야: LLM · Agent Architecture · Model Evaluation**

Meta가 **Muse Wonder와 Muse Wonder Full**을 공식 발표했습니다.

두 모델은 Meta Superintelligence Labs가 개발한 새로운 프론티어급 모델입니다. 기존 Muse Spark가 상대적으로 빠른 응답과 효율적인 실행에 초점을 맞췄다면, Wonder 시리즈는 장기 에이전트 작업과 복잡한 코딩에 초점을 맞춥니다.

### 무엇이 달라졌는가?

공식 개발자 문서에서 확인되는 주요 사양은 다음과 같습니다.

| 항목 | Muse Wonder | Muse Wonder Full |
|---|---|---|
| Context Window | 1M tokens | 1M tokens |
| 제공 방식 | Meta Model API, Muse Code | Muse Code 구독 |
| 입력 100만 토큰 가격 | $4 | 구독형 |
| 캐시 입력 100만 토큰 가격 | $0.20 | 구독형 |
| 출력 100만 토큰 가격 | $20 | 구독형 |
| 핵심 목표 | Coding, Long-Horizon Agent | 복잡한 장기 작업 |

현재 Wonder는 API를 사용할 수 있지만, **Wonder Full은 일반 API가 아닌 Muse Code 구독을 통해 제공**됩니다.

또한 현재 공식 발표는 서비스 제공을 확인하는 자료이지 모델 가중치 공개를 의미하지 않습니다. [Meta Model API](https://dev.meta.ai/models/muse-wonder?utm_source=chatgpt.com)

### 핵심 개념 1 — Active Memory

Meta는 Active Memory를 과거 상호작용에서 중요한 정보를 보존하고, 이후 관련 작업이 발생했을 때 해당 정보를 적극적으로 검색하는 능력으로 설명합니다.

```text
Interaction History
       │
       ▼
Memory Construction
       │
       ▼
Relevant Memory Retrieval
       │
       ▼
Current Task Context
       │
       ▼
Agent Reasoning
```

여기서 중요한 것은 단순히 Context Window를 크게 만드는 것과 다르다는 점입니다.

1M Context를 지원하더라도 모든 과거 기록을 매번 입력하는 것은 비용과 지연시간 측면에서 비효율적입니다.

Active Memory가 지향하는 것은 **장기간 축적된 정보 중 현재 의사결정에 유용한 정보를 선택하는 것**입니다.

이는 장기 에이전트의 메모리 관리 문제를 단순 대화 기록 보존에서 정보 선택 문제로 확장합니다.

### 핵심 개념 2 — Active Focus

Active Focus는 어려운 작업이 발생했을 때 기존 접근법을 수정하고, 대안을 시도하며, 필요한 경우 사용자에게 확인을 요청하는 능력입니다.

Meta는 장기 소프트웨어 개발 작업을 평가하는 SWE-Marathon과 별도의 FocusBench를 사용해 이러한 특성을 측정했다고 밝혔습니다.

공식 자료에 따르면 SWE-Marathon에서 Wonder는 78.8%, Wonder Full은 79.0%를 기록했습니다.

비교 대상으로 제시된 Claude Opus 5.5의 74.2%보다 높지만, **모델별 추론 예산과 실행 환경의 차이를 고려하지 않은 절대적인 우열로 해석해서는 안 됩니다.**

또한 Meta는 일부 평가에 자체 내부 벤치마크를 사용했습니다. 외부 평가와 기업 내부 평가를 구분하는 것이 필요합니다. [Meta AI Research](https://research.meta.ai/blog/muse-wonder)

### 엔지니어링 관점

이번 발표는 장기 에이전트 평가를 세 가지 축으로 분리해야 한다는 점을 보여줍니다.

**Model Reasoning:** 개별 문제를 해결하는 추론 능력.

**Memory Utility:** 과거 정보를 올바르게 보존하고 현재 작업에 적용하는 능력.

**Execution Persistence:** 실패와 상태 변화를 견디면서 작업을 계속 수행하는 능력.

세 능력은 서로 독립적인 평가가 필요합니다.

예를 들어 모델이 MemoryBench에서 높은 점수를 받더라도 실제 Repository 작업에서 오래된 설정 정보를 잘못 사용한다면 시스템의 신뢰성이 낮아질 수 있습니다.

### 주의할 점과 후속 관찰

Meta는 추가적인 Safety Evaluation 보고서를 공개할 예정이라고 밝혔습니다.

현재로서는 Active Memory의 내부 저장 방식, 업데이트 정책, 삭제 정책에 관한 상세 구현을 공식 발표만으로 확정하기 어렵습니다.

또한 장기 메모리를 사용하는 개인 에이전트에서는 정보의 정확성뿐 아니라 **오래된 정보의 만료, 권한 범위, 삭제 요청의 반영**도 중요합니다.

**후속 관찰:** 모델 아키텍처와 Technical Report 공개, Active Memory의 구현 구조, 독립적인 Long-Horizon 평가, 실제 Task당 비용.

## 2. Microsoft Maia 300 — AI 추론 가속기가 FLOPS보다 데이터 이동과 HBM 효율을 중심으로 설계된다 ★★★★★

**공개일: 2026년 10월 12일 | 분야: GPU·AI Accelerator · Memory Architecture · Distributed Inference**

Microsoft가 차세대 추론 가속기인 **Azure Maia 300**의 상세 설계를 공개했습니다.

이번 발표는 단순한 새로운 칩 공개보다 중요합니다.

Microsoft가 AI 추론 시스템을 설계할 때 **연산 능력, 메모리 배치, 저정밀 표현, 네트워크를 하나의 시스템으로 통합해서 최적화**하고 있기 때문입니다.

### 핵심 하드웨어 사양

| 항목 | Maia 300 |
|---|---|
| 제조 공정 | TSMC N2P Compute Chiplet |
| 메모리 | HBM4 × 8 |
| 최대 HBM 대역폭 | 18.0 TB/s |
| TDP | 950W |
| Rack당 가속기 | 96개 |
| Rack당 HBM 용량 | 27.6TB |
| Rack당 집계 HBM 대역폭 | 1.7PB/s |
| Rack 전력 | 167kW |
| 배포 예정 | 2027년 |

Microsoft는 주요 GPU 기반 시스템보다 **MW당 생성 토큰을 40% 더 많이 처리할 것으로 예상**한다고 발표했습니다.

또한 96개 가속기로 구성된 랙에서 Maia 200 대비 최대 7배의 토큰 처리량을 목표로 합니다.

중요한 구분은 **Maia 300은 아직 일반적인 Production 배포가 완료된 제품이 아니며, 2027년부터 배포할 예정**이라는 점입니다. 따라서 성능 수치는 현재의 독립적인 실측 결과로 받아들이면 안 됩니다. [The Official Microsoft Blog](https://blogs.microsoft.com/blog/2026/10/12/microsoft-to-expand-azure-maia-system-to-multi-gigawatt-deployments/)

### 핵심 기술 1 — Software-Defined Dataflow

Maia는 SDLA(Software Defined Locally Accessed Dataflow Architecture)를 사용합니다.

일반적인 GPU 프로그램에서는 연산 Kernel을 호출하고 데이터 배치를 Hardware와 Runtime이 처리합니다.

Maia의 접근은 데이터 배치와 이동을 더 명시적으로 관리하는 방향입니다.

```text
LLM Operations
      │
      ▼
Dataflow Scheduling
      │
      ├── Data Placement
      ├── Data Movement
      ├── Precision Conversion
      └── Synchronization
              │
              ▼
       Compute Engines
```

연산에 필요한 데이터를 가능한 한 가까운 메모리에 배치하고, 불필요한 이동을 줄이는 것입니다.

이는 대규모 모델의 Decoding에서 특히 중요합니다.

### 핵심 기술 2 — Chiplet NUMA

Maia 300은 Compute, Memory Controller, I/O를 서로 다른 Chiplet으로 분리합니다.

이때 모든 메모리에 접근하는 비용이 동일하지 않습니다.

Microsoft는 Chiplet 간 데이터 접근 비용 차이를 고려한 **NUMA 기반 메모리 구조**를 도입했습니다.

이는 단순히 HBM 대역폭을 높이는 것과 다른 문제입니다.

메모리 대역폭이 높더라도 필요한 데이터가 먼 Chiplet에 있다면 통신 비용이 발생할 수 있습니다.

따라서 데이터 배치와 연산 배치를 함께 설계해야 합니다.

### 핵심 기술 3 — KV Cache와 저정밀 추론

Maia 300은 향상된 MXFP4와 3-bit 미만의 저장 표현을 지원하도록 설계됐습니다.

목표는 모델 가중치뿐 아니라 KV Cache의 메모리 사용량과 전송 비용을 줄이는 것입니다.

장문 추론에서는 Context 길이가 늘어날수록 KV Cache 사용량이 증가합니다.

따라서 저정밀 KV 표현과 메모리 배치 최적화가 함께 작동하면 동일한 전력 내에서 더 많은 세션을 유지할 가능성이 있습니다.

다만 낮은 정밀도가 항상 동일한 정확도를 유지하는 것은 아니며, 모델별 품질 평가가 필요합니다. [마이크로소프트 애저](https://azure.microsoft.com/en-us/blog/deep-dive-into-azure-maia-300-architecture/)

### 엔지니어링 관점

이번 발표는 추론 인프라의 성능을 다음 세 단계로 나누어 평가해야 한다는 점을 보여줍니다.

**Compute Efficiency:** 연산량 대비 실제 처리 성능.

**Memory Efficiency:** HBM 용량·대역폭 대비 처리 성능.

**System Efficiency:** 네트워크·전력·냉각까지 포함한 실제 처리 성능.

특히 `tokens/s/GPU`만으로 서로 다른 가속기를 비교하기보다 `tokens/s/W`, `tokens/s/$`, `P99 latency`를 함께 측정하는 것이 중요합니다.

### 후속 관찰

Maia 300의 실제 Production 배포 이후 비교 가능한 모델과 배치 조건에서의 독립 벤치마크를 확인해야 합니다.

특히 저정밀 KV Cache와 NUMA 기반 데이터 배치가 실제 장문 에이전트 작업에서 어느 정도 효과를 내는지가 핵심입니다.

## 3. AMD Helion — 에이전트 실행을 위한 CPU 인프라가 GPU 인프라와 독립된 설계 대상으로 부상 ★★★★★

**공개일: 2026년 10월 12일 | 분야: Agent Infrastructure · CPU/GPU Disaggregation · Open Hardware**

AMD가 OCP Global Summit 2026에서 **Helion Agentic AI Rack**을 발표했습니다.

기존 AMD Helios가 대규모 GPU 기반 AI 시스템에 초점을 맞췄다면, Helion은 **에이전트가 사용하는 CPU 중심 실행 인프라**에 초점을 맞춥니다.

### 무엇이 달라졌는가?

Helion은 크게 두 가지 구성을 지원할 예정입니다.

**CPU-only 구성**은 6세대 EPYC 프로세서를 이용해 랙당 최대 32,768개 CPU Core를 제공하는 설계입니다.

**CPU/GPU 통합 구성**은 EPYC CPU와 Instinct MI350P GPU를 함께 배치하는 형태입니다.

Helion은 OCP 기반 개방형 설계를 사용하며 AMD는 해당 규격을 OCP에 기여할 계획입니다.

현재 파트너사들과 개발 중이고, 초기 구성의 제공 시점은 **2026년 11월로 예정**돼 있습니다. [Advanced Micro Devices, Inc.](https://ir.amd.com/news-events/press-releases/detail/1301/introducing-amd-helion-agentic-ai-compute-at-rack-scale)

### 왜 중요한가?

LLM 중심의 AI 인프라는 GPU에 집중돼 왔습니다.

하지만 Agent는 단순한 LLM 추론 프로그램이 아닙니다.

다음과 같은 다양한 작업을 실행합니다.

```text
Agent Runtime
     │
     ├── LLM Inference → GPU
     │
     ├── Code Execution → CPU
     │
     ├── Browser Automation → CPU
     │
     ├── Search / Retrieval → CPU·GPU
     │
     ├── Verification → CPU
     │
     └── Tool Orchestration → CPU
```

여러 에이전트가 병렬 실행되면 CPU에서 수행하는 작업이 상당히 많아집니다.

특히 Coding Agent의 강화학습에서는 각 Rollout이 독립된 실행 환경에서 테스트를 수행할 수 있습니다.

GPU가 충분하더라도 CPU 환경을 충분히 공급하지 못하면 Rollout Worker가 기다리게 됩니다.

즉 전체 시스템의 처리량은 GPU Token Generation만으로 결정되지 않습니다.

### 에이전트 인프라의 분리형 구조

Helion이 제시하는 중요한 방향은 CPU와 GPU를 서로 다른 자원 풀로 관리하는 것입니다.

```text
Agent Scheduler
      │
      ├── CPU Execution Pool
      │      ├── Tool Runtime
      │      ├── Sandbox
      │      ├── Test Runner
      │      └── Environment Simulation
      │
      └── GPU Inference Pool
             ├── LLM Serving
             ├── Embedding
             └── Reward / Critic
```

이 구조에서는 CPU 실행 환경의 수와 GPU 추론 자원을 독립적으로 확장할 수 있습니다.

AMD는 Helion에 모델 호출을 여러 프론티어 및 오픈소스 모델로 전달하는 Token Router 구조도 포함한다고 설명합니다.

### 주의할 점

Helion은 현재 Reference Design에 해당합니다.

따라서 발표된 최대 CPU Core 수가 실제 애플리케이션에서 선형적인 성능 확장을 제공한다는 의미는 아닙니다.

또한 CPU/GPU를 분리하면 네트워크 비용과 상태 전송 비용이 추가됩니다.

**후속 관찰:** 실제 Agent Rollout 처리량, CPU 대비 GPU 유휴시간, Sandbox 생성 속도, 원격 모델 호출 지연시간, OCP 규격 공개.

**원문:** [공식 발표 · AMD — Introducing Helion Agentic AI Compute at Rack Scale](https://ir.amd.com/news-events/press-releases/detail/1301/introducing-amd-helion-agentic-ai-compute-at-rack-scale?utm_source=chatgpt.com)

## 4. GraphTok — Prefix Cache를 최적화했더니 CPU Tokenization이 새로운 병목이 됐다 ★★★★★

**논문 제출: 10월 9일 · 신규 공개 목록: 10월 12일 | 분야: LLM Serving · GPU Kernel · CUDA Graph**

오늘 추론 엔지니어링 분야에서 가장 추천하는 논문입니다.

**Taking Tokenization off the Host for Agentic LLM Serving**은 Prefix Caching이 발전하면서 발생한 새로운 병목을 분석합니다.

### 기존 추론 시스템의 구조

일반적인 LLM Serving은 다음 순서로 진행됩니다.

```text
Request Text
     │
     ▼
CPU Tokenization
     │
     ▼
KV Prefix Cache Lookup
     │
     ▼
GPU Prefill
     │
     ▼
GPU Decoding
```

Prefix Cache가 없으면 긴 입력을 처리하기 위한 Prefill 계산량이 상당합니다.

그런데 Prefix Cache Hit Rate가 매우 높아지면 이야기가 달라집니다.

GPU는 이미 계산한 KV Cache를 재사용하기 때문에 Prefill 시간이 줄어듭니다.

하지만 **입력 텍스트를 Token ID로 변환하는 과정은 여전히 수행해야 합니다.**

이때 CPU Tokenization 시간이 전체 TTFT에서 차지하는 비율이 증가합니다.

### 실제 병목 측정

연구진은 vLLM에서 긴 입력을 처리할 때 Tokenization 시간 비중을 측정했습니다.

**Llama 3.1 8B, 약 130K 입력 토큰**의 경우:

| 조건 | TTFT 중 Tokenization 비중 |
|---|---:|
| Cold Cache | 약 2% |
| Prefix Cache Hit | 약 67% |

GPU에서 실행할 계산이 크게 줄어들면서 기존에는 무시할 수 있었던 CPU 작업이 Critical Path로 올라온 것입니다. [arXiv](https://arxiv.org/html/2610.13325v1)

### GraphTok의 해결 방법

연구진은 **GraphTok**이라는 GPU Tokenizer를 제안했습니다.

GraphTok은 Tokenization 전체 과정을 CUDA Graph로 실행합니다.

```text
Raw Text
    │
    ▼
GPU Pre-tokenization
    │
    ▼
GPU BPE Merge
    │
    ▼
Token ID Assembly
    │
    ▼
CUDA Graph Replay
```

핵심은 BPE Merge만 GPU로 옮긴 것이 아니라는 점입니다.

Pre-tokenization부터 Token ID 생성까지 전체 과정을 처리합니다.

또한 기존 Tokenizer와 동일한 Token ID를 생성하도록 구현했습니다.

지원 Tokenizer에는 GPT-2, Llama 3, Qwen 2.5, DeepSeek-V3, Gemma 3 계열이 포함됩니다.

### 성능 결과

논문에서 보고한 주요 결과는 다음과 같습니다.

| 평가 항목 | GraphTok 결과 |
|---|---|
| GPT-2 기준 100만 토큰 처리 | 1.7~3.2ms |
| Llama 3, 최적화 CPU Tokenizer 대비 | 4.7~6.0배 빠름 |
| vLLM Prefix Cache 환경 평균 TTFT | 2.1~2.4배 개선 |
| Dynamo Frontend, 121K 입력 | 최대 518 requests/s |

마지막 값은 2초 P99 지연 제한을 만족하는 조건에서 측정했습니다.

동일 조건에서 기존 기본 Tokenizer는 약 18.5 requests/s를 처리했습니다.

단, **GraphTok이 전체 LLM 추론을 6배 빠르게 한다는 뜻은 아닙니다.**

특히 Prefix Cache Hit가 적으면 개선 폭이 작습니다.

연구진은 Cold Cache 환경에서 전체 TTFT 개선이 약 2~4% 수준이라고 보고했습니다. [arXiv](https://arxiv.org/html/2610.13325v1)

### 엔지니어링 관점

이 논문은 최적화의 한계효용을 잘 보여줍니다.

기존 병목을 제거하면 이전에 중요하지 않았던 다른 연산이 새로운 병목이 됩니다.

```text
Before Prefix Caching

GPU Prefill >> CPU Tokenization


After Prefix Caching

GPU Prefill ↓
CPU Tokenization = New Bottleneck
```

다만 모든 시스템에서 GPU Tokenizer가 유리한 것은 아닙니다.

짧은 입력에서는 CUDA 실행 비용 때문에 CPU가 더 효율적일 수 있습니다.

또한 Token ID를 재사용하는 기존 캐시와 GraphTok을 결합할 때는 BPE 경계에 따른 Tokenization 변경 가능성을 고려해야 합니다.

**후속 관찰:** Blackwell GPU에서의 성능, CPU Token Reuse와의 결합, 다중 모델 Frontend 처리량, 실제 Coding Agent Trace에서의 개선.

**원문:** [논문 · Taking Tokenization off the Host for Agentic LLM Serving](https://arxiv.org/abs/2610.13325) · [GitHub · GraphTok 공식 구현](https://github.com/Msiavashi/GraphTok?utm_source=chatgpt.com)

## 5. Elastic Latent Recurrence — 하나의 모델에서 반복 계산 횟수로 추론 성능을 조절한다 ★★★★★

**논문 제출: 10월 8일 · 신규 공개 목록: 10월 12일 | 분야: LLM Architecture · Recurrent Transformer · Test-Time Compute**

오늘 LLM 아키텍처 분야에서 가장 중요한 연구 중 하나입니다.

NVIDIA 연구진이 발표한 **One Model to Loop Them All: Elastic Latent Recurrence for Language Models**는 동일한 모델 가중치를 여러 번 사용해 계산량과 정확도를 조정하는 방법을 다룹니다.

### 기존 Recurrent LLM의 문제

일반적인 Transformer는 여러 Layer를 순차적으로 통과합니다.

Recurrent LLM은 일부 Layer를 반복 사용합니다.

```text
Input
  │
  ▼
Initial Layers
  │
  ▼
Shared Recurrent Block
  │
  ├── Loop 1
  ├── Loop 2
  ├── Loop 3
  └── Loop K
  │
  ▼
Output Layers
```

이 방식은 같은 가중치를 반복 사용하기 때문에 Parameter Count를 늘리지 않고 연산량을 늘릴 수 있습니다.

그러나 기존 방식에는 **One-loop Tax**라는 문제가 있습니다.

반복을 한 번만 수행하면 동일한 크기의 일반적인 비순환 모델보다 성능이 낮아지는 현상입니다.

따라서 지연시간이 중요한 환경에서는 Recurrent Model보다 일반 모델을 사용하는 편이 나을 수 있었습니다.

### ELR의 핵심 개선

ELR은 세 가지 기술을 결합합니다.

**Gated State Update**는 반복 과정에서 이전 상태를 얼마나 유지하고 새로운 정보를 얼마나 반영할지 학습합니다.

**Mixed-depth Training**은 학습 시 반복 횟수를 다양하게 사용합니다.

**Loop-conditioned Modulation**은 현재 반복 횟수와 계산 예산 정보를 모델에 제공합니다.

이렇게 하면 반복 횟수가 적을 때의 성능을 유지하면서 반복 횟수가 증가할 때 추가 계산의 이점을 얻도록 학습할 수 있습니다. [arXiv](https://arxiv.org/abs/2610.12582)

### 실험 결과

연구진은 4B 규모의 비-MoE 하이브리드 모델과 30B-A3B MoE 하이브리드 모델을 평가했습니다.

동일한 데이터로 학습한 비순환 모델과 비교했을 때, 한 번만 반복한 ELR의 성능은 거의 비슷했습니다.

반복 횟수를 네 번으로 늘리자 10개 태스크 평균에서 다음과 같은 개선을 보고했습니다.

| 모델 | 4회 반복 시 추가 개선 |
|---|---:|
| 4B 모델 | +7.25점 |
| 30B-A3B MoE | +4.75점 |

또한 Post-training까지 수행한 **Koi-4B**는 하나의 Checkpoint에서 반복 횟수를 바꾸는 방식으로 Artificial Analysis Intelligence Index 추정 점수를 약 18에서 29까지 높였습니다.

다만 이러한 성능 향상은 추가적인 추론 연산을 사용한 결과입니다.

즉 같은 계산량에서 11점이 향상된 것이 아닙니다. [arXiv](https://arxiv.org/html/2610.12582v1)

### 중요한 기술 — Last-loop KV Cache

반복 횟수가 늘면 Attention KV Cache도 반복 횟수에 따라 증가할 수 있습니다.

ELR은 마지막 Loop의 KV만 보존하는 방법을 연구했습니다.

Koi-4B의 128K Context 예시에서는 4회 반복의 일반적인 KV Cache 요구량이 약 7.5GiB였지만, 마지막 Loop의 KV만 유지하면 약 3.0GiB로 줄일 수 있었습니다.

이 방법은 반복 연산으로 증가하는 메모리 비용을 제한하기 위한 중요한 최적화입니다. [arXiv](https://arxiv.org/html/2610.12582v1)

### 아키텍처 연구 관점

ELR은 다음과 같은 설계 질문을 제시합니다.

> 동일한 모델 크기에서 추론 연산량을 증가시키는 것과 모델의 파라미터 수를 증가시키는 것 중 어떤 방식이 더 효율적인가?

또한 기존 Test-Time Scaling과 중요한 차이가 있습니다.

일반적인 Reasoning Scaling은 더 많은 출력 토큰을 생성하는 방식이 많습니다.

ELR은 **출력 토큰을 늘리는 대신 내부 Hidden State 연산을 반복**합니다.

따라서 연구 변수는 다음과 같이 분리할 수 있습니다.

`Parameter Count`  
`Recurrent Loop Count`  
`Internal Compute FLOPs`  
`Generated Tokens`  
`KV Memory`  
`Task Accuracy`

### 주의할 점

Loop를 증가시키면 연산량과 지연시간도 증가합니다.

또한 Last-loop KV 방식은 일반적인 반복 방식과 내부 상태의 계산 경로가 달라지므로 품질 비교가 필요합니다.

**후속 관찰:** 반복 횟수별 실제 GPU Latency, 단순 모델 크기 증가와의 비교, MoE Expert Routing 재사용, Long-Context 정확도.

**원문:** [논문 · One Model to Loop Them All: Elastic Latent Recurrence](https://arxiv.org/abs/2610.12582)

## 6. MagicBeanStalk — RLVR 데이터 78,000개 중 약 88%가 현재 학습에 유효한 Advantage를 제공하지 못했다 ★★★★★

**논문 제출: 10월 8일 · 신규 공개 목록: 10월 12일 | 분야: LLM Training · RLVR · Synthetic Data**

오늘 Fine-Tuning과 Post-training 연구에서 가장 추천하는 논문입니다.

**MagicBeanStalk: Escaping the RLVR Zero Advantage Trap with Recursive Data Synthesis**는 강화학습 데이터의 난이도를 어떻게 조절해야 하는지 연구합니다.

### 기존 데이터 구성의 문제

RLVR(Reinforcement Learning with Verifiable Rewards)은 모델이 여러 응답을 생성하고, 검증 가능한 정답을 이용해 보상을 계산합니다.

예를 들어 하나의 문제에 대해 8개의 응답을 생성했다고 가정하겠습니다.

```text
Problem A
  8/8 Correct → 너무 쉬움

Problem B
  0/8 Correct → 너무 어려움

Problem C
  3/8 Correct → 학습 가능한 차이 존재
```

Group-relative 학습에서는 모든 응답의 보상이 동일하면 그룹 내부의 상대적 Advantage가 0에 가까워집니다.

문제를 많이 확보하더라도 대부분이 항상 성공하거나 항상 실패한다면 유효한 학습 신호가 부족할 수 있습니다.

### 실제 관찰 결과

연구진은 약 78,000개의 수학 문제를 분석했습니다.

gpt-oss-120b와 32K 토큰 Rollout Budget을 기준으로 약 **88%가 모든 시도에서 성공하거나 모든 시도에서 실패하는 구간**에 속했습니다.

여기서 중요한 점은 이 88%가 데이터 자체의 영구적인 속성이 아니라는 사실입니다.

모델이 바뀌거나 Rollout Budget이 달라지면 같은 문제의 난이도도 달라질 수 있습니다. [arXiv](https://arxiv.org/html/2610.12659v1)

### MagicBeanStalk의 접근

MagicBeanStalk는 너무 어려운 문제를 단순히 제거하지 않습니다.

대신 어려운 문제의 핵심 추론 구조를 유지하면서 해결 가능한 하위 문제를 생성합니다.

```text
Hard Problem
     │
     ▼
Reasoning Blueprint
     │
     ▼
Problem Decomposition
     │
     ▼
Recursive Problem Generation
     │
     ▼
Difficulty Calibration
     │
     ▼
Verified Training Problems
```

목표는 단순히 쉬운 문제를 만드는 것이 아닙니다.

**현재 Policy가 때로는 성공하고 때로는 실패하는 문제를 생성하는 것**입니다.

연구진은 이 범위를 Goldilocks Region으로 설명합니다.

### 실험 결과

8개 수학 추론 벤치마크에서 다음 결과를 보고했습니다.

| 모델 | 학습 전 | 학습 후 | 개선 |
|---|---:|---:|---:|
| gpt-oss-120b | 61.2 | 69.8 | +8.6점 |
| DeepSeek V4 Flash | 72.4 | 77.9 | +5.4점 |

평가 출력 예산은 16K 토큰입니다.

반면 78K 원본 데이터 전체를 그대로 학습하는 조건의 개선은 약 +1.1점이었습니다.

즉 **데이터 규모 증가보다 현재 모델에 맞는 학습 문제 생성이 더 효과적일 수 있음**을 보여줍니다. [arXiv](https://arxiv.org/html/2610.12659v1)

### 엔지니어링 관점

이 연구는 Fine-Tuning 데이터를 만들 때 중요한 설계 원칙을 제시합니다.

데이터 품질을 단순히 사람이 읽기에 자연스러운지, 설명이 충분한지로 판단하면 부족합니다.

실제로는 다음을 측정해야 합니다.

**Current Policy Success Rate:** 현재 모델이 문제를 얼마나 해결하는가?

**Reward Variance:** 동일 문제의 여러 Rollout에서 보상 차이가 발생하는가?

**Training Utility:** 해당 데이터로 학습했을 때 Held-out 평가 성능이 개선되는가?

**Verification Reliability:** 정답 검증이 정확한가?

특히 보안 특화 모델의 경우 쉬운 CWE 분류 데이터만 대량으로 추가하는 것이 실제 어려운 취약점 판단 능력을 개선하지 못할 가능성이 있습니다.

### 주의할 점

이번 연구의 핵심 실험은 수학 및 금융 분야의 검증 가능한 문제를 대상으로 했습니다.

CWE 분류나 악성코드 분석으로 확장하려면 올바른 Label과 재현 가능한 검증기가 필요합니다.

또한 데이터 생성과 검증에도 비용이 발생하므로 전체 학습 비용을 함께 측정해야 합니다.

**후속 관찰:** 다른 도메인으로의 전이, Teacher Model의 데이터 생성 편향, 문제 난이도 조정 비용, 학습 효율과 총 GPU 시간의 관계.

**원문:** [논문 · MagicBeanStalk: Escaping the RLVR Zero Advantage Trap](https://arxiv.org/abs/2610.12659)

## 7. Behavioral Self-Rewarding — Coding Agent의 테스트 결과가 같아도 디버깅 과정의 품질은 다르다 ★★★★★

**논문 제출: 10월 8일 · 신규 공개 목록: 10월 12일 | 분야: Agent RL · Coding Agent · Reward Design**

**Beyond Binary Verifiable Rewards: Behavioral Self-Rewarding for SWE Agents**는 Coding Agent의 강화학습에서 보상 설계 문제를 다룹니다.

### 기존 Binary Reward의 한계

일반적으로 Coding Agent가 수정한 코드에 테스트를 실행하면 다음 결과를 얻습니다.

```text
Tests Pass → Reward = 1
Tests Fail → Reward = 0
```

하지만 실패한 Trajectory 사이에도 품질 차이가 존재합니다.

예를 들어 두 Agent가 동일한 문제 해결에 실패했다고 가정하겠습니다.

**Agent A**는 관련 파일을 확인하고, 원인을 분석한 뒤 적절한 테스트를 실행했습니다.

**Agent B**는 관련 없는 파일을 반복해서 수정하고, 불필요한 명령을 여러 번 실행했습니다.

두 Agent 모두 최종 테스트에는 실패했습니다.

그러나 실제 디버깅 과정의 품질은 다릅니다.

### Behavioral Self-Rewarding의 접근

BSR은 동일한 작업과 동일한 테스트 결과를 가진 Trajectory를 비교합니다.

```text
Same Task
    │
    ▼
Multiple Trajectories
    │
    ▼
Verifier Outcome
    │
    ├── Pass Group
    └── Fail Group
            │
            ▼
     Pairwise Comparison
            │
            ▼
     Behavioral Ranking
            │
            ▼
      Auxiliary Reward
```

이때 현재 Policy Model 자체를 이용해 Trajectory의 상대적 품질을 판단합니다.

별도의 Reward Model을 학습하지 않고 추가적인 보상 신호를 만드는 방식입니다.

다만 BSR은 **최종 검증기의 성공·실패 순서를 유지하도록 보조 보상을 제한**합니다.

즉 디버깅 과정이 우수해 보인다는 이유만으로 실패한 Trajectory가 실제 성공한 Trajectory보다 높은 보상을 받도록 설계하지 않았습니다. [arXiv](https://arxiv.org/html/2610.12598v1)

### 실험 결과

Qwen3-14B의 SWE-bench Verified 평가에서는 다음 결과를 보고했습니다.

| 방법 | 평균 성공률 |
|---|---:|
| Verifier-only RL | 32.1% |
| Behavioral Self-Rewarding | 34.7% |

동일한 400 Training Step Budget에서 약 2.6%p 개선됐습니다.

SWE-bench-Live Lite에서도 6.33%에서 8.11%로 개선됐습니다.

Qwen3-32B에서도 개선이 관찰됐지만, 개선 폭은 모델과 학습 예산에 따라 달랐습니다. [arXiv](https://arxiv.org/html/2610.12598v1)

### 왜 중요한가?

Agent RL에서 성공 여부만 학습하면 모델이 효율적인 문제 해결 절차를 배우지 못할 수 있습니다.

BSR은 작업 수행 과정 자체를 학습 신호로 사용합니다.

예를 들어 다음 행동은 실제 작업 성공과 관련성이 있을 수 있습니다.

- 코드 수정 전에 관련 파일 확인
- 수정 후 관련 테스트 실행
- 동일한 실패 명령 반복 감소
- 실패 원인에 대한 근거 있는 접근

하지만 이러한 행동이 모든 작업에 반드시 유리한 것은 아닙니다.

특히 Process Reward가 강해지면 실제 문제 해결보다 평가자가 선호하는 행동만 반복하는 **Reward Hacking**이 발생할 수 있습니다.

### 적용 시 주의점

자기 평가를 사용하는 구조이므로 모델의 편향이 보상에 반영될 수 있습니다.

또한 Pairwise Comparison에는 추가적인 추론 비용이 발생합니다.

따라서 실제 학습에서는 성공률 개선과 함께 **Reward 계산 비용, Training Throughput, Total GPU Hours**를 측정해야 합니다.

**후속 관찰:** 독립적인 Reward Model 대비 효과, 평가 편향, 장기 Coding Agent에서의 일반화, 실제 디버깅 품질 개선 여부.

**원문:** [논문 · Beyond Binary Verifiable Rewards](https://arxiv.org/abs/2610.12598) · [GitHub · Behavioral Self-Rewarding 공식 구현](https://github.com/yiranwu0/behavioral-self-rewarding)

## 8. VEPA — 에이전트가 보안 정책을 제안하되 실제 적용은 검증된 규칙만 허용 ★★★★★

**논문 제출: 10월 8일 · 신규 공개 목록: 10월 12일 | 분야: AI Security · Formal Verification · Agent Runtime**

오늘 AI 보안 분야에서 가장 중요한 연구입니다.

**VEPA(Verified Evolving Formal Policy for Lifelong LLM Agent Guardrails)**는 에이전트 실행 권한을 동적으로 관리하면서도 정책 판단의 일관성을 유지하는 방법을 연구합니다.

### 기존 Agent Guardrail의 문제

LLM을 이용한 보안 정책 검사는 새로운 상황에 유연하게 대응할 수 있습니다.

하지만 같은 작업에 대해 항상 동일한 판단을 내린다는 보장이 없습니다.

반면 규칙 기반 정책은 일관된 판단을 제공하지만 새로운 위험이 발견되면 규칙을 수동으로 수정해야 합니다.

VEPA는 두 방식을 결합합니다.

### VEPA의 핵심 구조

```text
Agent Tool Request
        │
        ▼
Typed Event Parser
        │
        ▼
Verified Formal Policy
        │
        ├── Allow
        ├── Deny
        └── Abstain
                │
                ▼
         Fallback Policy
```

정책 업데이트 과정은 별도입니다.

```text
Deployment Feedback
        │
        ▼
LLM Policy Proposal
        │
        ▼
Deterministic Verification
        │
        ▼
Evidence Evaluation
        │
        ▼
Verified Policy Activation
```

LLM이 새로운 보안 규칙을 제안할 수는 있지만 **그 제안이 곧바로 실행 정책이 되는 것은 아닙니다.**

정책의 구조가 올바른지, 기존 규칙과 충돌하지 않는지 검사합니다.

그다음 충분한 근거가 축적된 규칙만 활성화합니다. [arXiv](https://arxiv.org/abs/2610.12813)

### 실험 결과

연구진은 ASSEBench-Safety, ASSEBench-Security, ATBench를 대상으로 평가했습니다.

혼합된 보안 이벤트가 계속 들어오는 환경에서 VEPA는 최종 Macro-F1 약 0.86을 기록했습니다.

비교 대상인 AGrail은 약 0.78, LiSA는 약 0.80을 기록했습니다.

일부 피드백 Label을 오염시킨 조건에서도 VEPA가 상대적으로 높은 성능을 유지했다고 보고했습니다. [arXiv](https://arxiv.org/html/2610.12813v1)

### 엔지니어링 관점

이 연구에서 가장 중요한 원칙은 다음과 같습니다.

> **LLM은 정책을 생성하고 수정하는 데 사용할 수 있지만, 최종 권한 판단은 별도의 검증 가능한 실행 계층에서 수행해야 한다.**

이는 기업 내부 Coding Agent나 보안 분석 Agent에서 직접적인 의미가 있습니다.

예를 들어 다음과 같은 정책을 생각할 수 있습니다.

```text
Resource: /workspace/project
Action: read
Decision: allow

Resource: /workspace/project
Action: write
Decision: allow

Resource: /workspace/secrets
Action: read
Decision: deny

Resource: external-network
Action: upload
Decision: deny
```

실제 구현에서는 단순 문자열 비교보다 정규화된 경로, 실제 실행 주체, 심볼릭 링크, 도구별 권한, 네트워크 목적지 등을 함께 고려해야 합니다.

### 중요한 한계

VEPA의 형식적 보장은 **정해진 Event Schema로 변환된 입력에 대해 규칙이 구조적으로 올바르고 충돌하지 않는다는 범위**에 한정됩니다.

즉 모든 보안 위협을 차단한다고 수학적으로 증명한 것은 아닙니다.

Typed Event Parser가 잘못된 정보를 생성하거나 정책 자체가 중요한 위험을 표현하지 못하면 여전히 보안 문제가 발생할 수 있습니다.

규칙에 해당하지 않는 이벤트의 Fallback 처리 역시 별도의 검증 대상입니다.

**후속 관찰:** 실제 운영체제 권한과의 연동, LLM Event Parsing 오류, 정책 업데이트의 안전성, 대규모 Tool Catalog에서의 정책 평가 비용.

**원문:** [논문 · VEPA: Verified Evolving Formal Policy for Lifelong LLM Agent Guardrails](https://arxiv.org/abs/2610.12813)

# 오늘 직접 해볼 만한 실습
## `Prefix Cache 이후의 Tokenization Bottleneck` 측정

오늘은 GraphTok 논문의 문제의식을 현재 LLM Serving 환경에서 직접 검증해보는 실습을 추천합니다.

연구 질문은 명확합니다.

> **Prefix Cache Hit Rate가 증가하면 GPU Prefill 시간이 감소하고, 전체 TTFT에서 CPU Tokenization이 차지하는 비율이 증가하는가?**

### 실험 조건

동일한 모델과 Serving Engine을 사용합니다.

가능하면 기존 vLLM 환경에서 수행하고, Prefix Cache가 실제로 적용되는지 먼저 확인합니다.

| 실험 | Context Length | Prefix Reuse |
|---|---:|---:|
| A | 8K | 0% |
| B | 8K | 90% 이상 |
| C | 32K | 0% |
| D | 32K | 90% 이상 |
| E | 128K | 0% |
| F | 128K | 90% 이상 |

128K 실험은 모델이 해당 Context를 지원하고 충분한 KV 메모리가 확보된 경우에만 수행합니다.

### 1단계 — CPU Tokenization 측정

먼저 Serving Engine과 독립적으로 Tokenizer의 처리시간을 측정합니다.

```python
import time
import statistics

from transformers import AutoTokenizer

model_id = "Qwen/Qwen2.5-1.5B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(
    model_id,
    use_fast=True
)

base_text = (
    "def analyze(data):\n"
    "    result = []\n"
    "    for item in data:\n"
    "        result.append(item)\n"
    "    return result\n"
)

for target_tokens in [8192, 32768, 131072]:

    text = base_text

    while len(tokenizer.encode(text)) < target_tokens:
        text += base_text * 10

    text = tokenizer.decode(
        tokenizer.encode(text)[:target_tokens]
    )

    times = []

    for _ in range(10):
        start = time.perf_counter()

        tokens = tokenizer.encode(text)

        elapsed = time.perf_counter() - start

        times.append(elapsed)

    print(
        f"tokens={len(tokens):7d} | "
        f"mean={statistics.mean(times)*1000:.2f}ms | "
        f"p95={sorted(times)[-1]*1000:.2f}ms"
    )
```

이 코드는 CPU Tokenization의 실행시간을 측정하는 간단한 예제입니다.

표시한 마지막 값은 10회 측정의 최댓값이며 엄밀한 통계적 P95 추정치는 아닙니다. 실제 보고서에서는 반복 횟수를 늘리고 Percentile을 계산하는 편이 좋습니다.

또한 이 예제의 모델과 실제 vLLM Serving 모델이 다르면 두 결과를 직접 비교해서는 안 됩니다.

### 2단계 — vLLM Prefix Cache 측정

다음으로 실제 Serving Engine에서 동일한 Prefix를 반복 사용하는 요청을 실행합니다.

```text
Condition A

Request 1: Prefix A + Suffix 1
Request 2: Prefix B + Suffix 2
Request 3: Prefix C + Suffix 3


Condition B

Request 1: Prefix A + Suffix 1
Request 2: Prefix A + Suffix 2
Request 3: Prefix A + Suffix 3
```

A 조건에서는 Prefix가 서로 달라 Cache 재사용이 적습니다.

B 조건에서는 동일한 Prefix를 재사용하므로 KV Cache Hit가 발생할 수 있습니다.

단, Cache Hit 여부와 비율은 실제 엔진의 메트릭으로 확인해야 합니다. 같은 문자열을 반복 전송했다는 사실만으로 Hit Rate를 확정할 수 없습니다.

### 3단계 — 측정 지표

다음 지표를 수집합니다.

| 지표 | 측정 목적 |
|---|---|
| CPU Tokenization Time | 입력 변환 비용 |
| TTFT P50/P95 | 초기 응답 지연 |
| Prefill Time | GPU Prefill 계산시간 |
| Prefix Cache Hit Rate | KV 재사용 수준 |
| Input Tokens | 전체 문맥 크기 |
| Cached Tokens | 재사용된 토큰 |
| GPU Utilization | GPU 사용률 |
| Requests/s | 시스템 처리량 |

가능하면 Tokenization과 KV Cache Lookup에 대한 별도 Trace도 확보하는 것이 좋습니다.

단순 TTFT만으로는 실제 병목이 Tokenization인지 CPU Scheduling인지 구분하기 어렵기 때문입니다.

### 4단계 — 결과 해석

GraphTok 논문의 핵심은 CPU Tokenization 자체가 새로운 연산이라는 것이 아닙니다.

**다른 연산이 빨라지면서 이전에 중요하지 않았던 연산이 전체 성능을 제한하게 됐다는 사실**입니다.

이를 확인하려면 다음 비율을 비교하면 됩니다.

\[
R_{\text{tokenization}}
=
\frac{T_{\text{tokenization}}}{T_{\text{TTFT}}}
\]

단, Tokenization과 다른 단계가 일부 중첩되는 시스템에서는 이 비율을 전체 지연시간의 엄밀한 가산 분해로 해석해서는 안 됩니다.

예를 들어 다음 결과가 나온다고 가정하겠습니다.

| 조건 | Tokenization | TTFT | 비중 |
|---|---:|---:|---:|
| Cold Cache | 100ms | 1,000ms | 10% |
| Warm Cache | 100ms | 200ms | 50% |

Tokenization 시간은 동일하지만 Prefix Caching으로 GPU Prefill 시간이 감소하면서 Tokenization의 상대적 비중이 증가했습니다.

이러한 결과가 나타난다면 다음 최적화 대상을 검토할 수 있습니다.

**CPU Tokenizer 병렬화**, **Token ID Cache**, **GPU Tokenization**입니다.

여기서 중요한 것은 GPU Tokenizer가 항상 가장 좋은 선택은 아니라는 점입니다.

짧은 입력이나 충분한 CPU 자원이 있는 환경에서는 기존 Tokenizer가 더 경제적일 수 있습니다.

# 오늘의 종합 판단

오늘의 발표와 논문은 서로 다른 분야를 다루지만 중요한 공통점을 갖습니다.

**Meta Muse Wonder**는 모델의 장기 실행과 메모리 활용을 강조합니다.

**Microsoft Maia 300**은 연산량보다 데이터 이동과 메모리 효율에 초점을 맞춘 하드웨어 아키텍처를 제시합니다.

**AMD Helion**은 에이전트 실행을 위한 CPU 인프라와 모델 추론 인프라를 분리해 설계하는 방향을 보여줍니다.

**GraphTok**은 GPU Prefix Cache 최적화가 CPU Tokenization이라는 새로운 병목을 드러낸 사례입니다.

**Elastic Latent Recurrence**는 모델 크기를 늘리지 않고 내부 반복 연산을 조절하는 아키텍처를 연구합니다.

**MagicBeanStalk와 Behavioral Self-Rewarding**은 학습에서 데이터 수와 단순 성공·실패 보상보다 실제 학습에 유효한 신호를 만드는 것이 중요하다는 점을 보여줍니다.

**VEPA**는 에이전트가 새로운 보안 정책을 생성할 수 있더라도 실제 권한 강제는 별도 검증 계층에서 수행해야 한다는 원칙을 제시합니다.

오늘 가장 중요한 연구 질문은 다음과 같습니다.

> **모델의 파라미터 수를 늘리는 대신, 학습 데이터를 더 효과적으로 구성하고, 추론 연산을 필요한 곳에 배분하며, 실행 상태와 메모리 이동을 최적화하면 어느 정도의 성능 향상을 얻을 수 있는가?**

특히 오늘 발표된 **GraphTok과 Elastic Latent Recurrence를 함께 살펴보는 것**을 추천합니다.

하나는 모델 외부 실행 경로의 병목을, 다른 하나는 모델 내부 추론 연산의 배분 문제를 다룹니다.

두 연구를 함께 이해하면 앞으로 LLM 아키텍처와 추론 인프라를 연구할 때 **모델 내부의 계산 효율과 실제 시스템의 End-to-End 효율을 어떻게 분리해서 측정해야 하는지**에 대한 좋은 기준을 얻을 수 있습니다.
