**2026년 8월 20일 목요일**
오늘은 **8월 19일 공개 자료**를 최우선으로 확인했습니다. 오늘 흐름은 크게 네 가지입니다. **Agent Skill을 별도 소프트웨어 artifact처럼 검증하기 시작했고, 4-bit 양자화는 PTQ만이 아니라 QAD로 품질을 복구하는 방향이 구체화됐으며, GPU kernel 최적화에 multi-agent search가 투입되고 있습니다. 동시에 장기 agent에서는 privacy·safety·payment 같은 모델 외부 런타임 기능이 점점 핵심 infrastructure로 편입되고 있습니다.** ([NVIDIA Developer][1])

## 1. 필독 | NVIDIA SkillEvaluator — Skill을 “좋아 보이는 문서”가 아니라 A/B 테스트 가능한 소프트웨어 artifact로

**무엇이 바뀌었나.** NVIDIA가 8월 19일 **SkillEvaluator**를 공개했습니다. Agent Skill을 세 단계로 검사합니다. Tier 1은 schema·PII·license·prompt injection·data exfiltration·script lint 같은 정적 검사를 수행하고, Tier 2는 embedding similarity로 Skill 내부 중복과 catalog 간 overlap을 검사하며, Tier 3는 동일 model·prompt·task·grader 조건에서 **Skill ON / OFF를 독립 sandbox에서 직접 실행**해 성능 차이를 측정합니다. 구현은 Apache 2.0 오픈소스로 공개됐고 Codex·Claude Code 등을 live evaluation 대상으로 사용할 수 있습니다. ([NVIDIA Developer][1])

NVIDIA는 30개 이상 제품의 300개 이상 verified skill을 Codex와 Claude Code 두 harness에서 평가했습니다. 8월 12일 snapshot 기준 평균 점수는 Skill 없이 Correctness 46, Effectiveness 39였고 Skill을 넣었을 때 각각 87, 78로 올라갔습니다. 전체 평균 Skill Lift는 +31점, Security를 제외하면 +39점이었습니다. 다만 대부분의 Skill은 task당 1회만 실행됐고 confidence interval도 공개하지 않았기 때문에 이를 “Skill을 넣으면 성공 확률이 40% 오른다”고 해석하면 안 됩니다. NVIDIA도 이 수치를 pass probability가 아닌 평가 점수 차이로 명시합니다. ([NVIDIA Developer][1])

**왜 중요한가.** 최근 Agent Plugins·Skill 생태계가 커지면서 Skill은 사실상 `system prompt + workflow + scripts + tool contract`를 묶은 executable policy가 되고 있습니다. 따라서 Skill은 문서 리뷰로 승인할 것이 아니라 모델이나 라이브러리와 마찬가지로 **regression CI**를 가져야 합니다. SkillEvaluator가 특히 좋은 점은 “Skill을 설치한 agent가 잘한다”가 아니라 **같은 agent가 Skill 때문에 얼마나 달라졌는지**를 paired experiment로 분리한다는 점입니다. ([NVIDIA Developer][1])

실무에서는 Skill마다 `strict_success_delta`, `tokens_delta`, `tool_calls_delta`, `wall_clock_delta`, `security_regression`, `applicable_task_types`를 registry metadata로 남기는 구조를 추천합니다. 새 Skill이 task success는 올리지만 token과 tool call을 3배 늘린다면 production 기본값으로 넣을지 별도 판단해야 합니다.

**주의·후속 관찰.** SkillEvaluator repository 자체는 현재 **Experimental**, community support·best-effort이며 SLA가 없습니다. Local evaluation mode도 신뢰된 Skill·workspace에만 권장하고, untrusted code는 Docker나 cloud sandbox를 사용하도록 안내합니다. ([GitHub][2])

**원문:** **[공식 발표] NVIDIA SkillEvaluator 평가 결과** ([NVIDIA Developer][1]) · **[GitHub] NVIDIA/SkillEvaluator** ([GitHub][2])

## 2. Edge·양자화 | Liquid AI LFM2.5 QAD Q4_0 — “Q4 속도 그대로, PTQ 손실은 학습으로 복구”

**무엇이 바뀌었나.** Liquid AI는 8월 19일 LFM2.5 230M, 350M, 1.2B-Instruct, 2.6B용 **QAD Q4_0 GGUF** checkpoint를 공개했습니다. 일반 PTQ가 이미 학습된 모델을 사후 압축하는 방식이라면, 이번 checkpoint는 high-precision teacher에서 실제 4-bit student로 distillation하는 Quantization-Aware Distillation을 사용합니다. Liquid 측 5회 반복 benchmark에서 네 모델은 BF16 평균 성능의 약 96.5~97.4%를 유지했습니다. 평가에는 GPQA Diamond, MMLU-Pro뿐 아니라 IFEval·IFBench·Multi-IF와 BFCLv4 tool-use 항목도 포함됐습니다. ([Hugging Face][3])

실제 edge hardware에서도 재미있는 결과가 나왔습니다. QAD Q4_0은 230M·350M에서 더 무거운 Q5_K_M 수준 품질을 유지하면서 decode throughput이 4~33% 높았고, 1.2B·2.6B에서는 Q4_K_M 수준 품질에 3~14% 높은 throughput을 Liquid가 보고했습니다. 측정 대상은 MacBook Pro, NucBox, Galaxy S26 Ultra, Raspberry Pi 5이며 GGUF이므로 llama.cpp 계열 runtime에서 바로 사용할 수 있습니다. ([Hugging Face][3])

**왜 중요한가.** 양자화 목표가 바뀌고 있습니다.

```text
기존:
BF16 → PTQ → 품질이 얼마나 안 깨지는가?

QAD:
BF16 teacher
   ↓
실제 quantized student 학습
   ↓
Q4 deployment artifact
```

특히 Agent model에서는 일반 perplexity보다 function-call syntax, JSON, enum, exact identifier 같은 구조적 token이 깨지는지가 더 중요합니다. 이번 benchmark가 BFCLv4까지 포함한 것은 이 측면에서 의미가 있습니다. ([Hugging Face][3])

실무에서는 같은 모델의 `BF16 / PTQ-Q4 / QAD-Q4`를 비교해 `VRAM`, `tokens/s`, `tool-call parse`, `argument exact match`, `strict task success`를 같이 기록하는 것이 좋습니다. QAD의 추가 학습비용을 지불할 가치가 있는지는 **성공한 task당 비용**으로 판단해야 합니다.

**주의·후속 관찰.** 97%는 Liquid가 선택한 benchmark들의 평균 보존율이며 모든 downstream task에서 97%라는 뜻은 아닙니다. 특히 한국어, 긴 context, 장기 agent trajectory는 별도 평가가 필요합니다. ([Hugging Face][3])

**원문:** **[공식 기술 글] LFM2.5 Q4_0 QAD** ([Hugging Face][3]) · **[모델 카드] LFM2.5-2.6B-GGUF** ([Hugging Face][4])

## 3. 필독 | KernelArc — GPU kernel 최적화도 Multi-Agent Search 문제로

**무엇이 바뀌었나.** 8월 17일 제출돼 8월 19일 arXiv 신규 목록에 올라온 **KernelArc**는 GPU kernel optimization을 multi-agent 문제로 다룹니다. Strategy-specialized agent들이 병렬 탐색하고, 결과 전문을 서로 공유하지 않고 **결론만 공유하는 memory**, deterministic benchmark guard, read-only cross-agent state와 plateau-triggered drafting을 사용합니다. H100·B200에서 BF16 GEMM, cuBLASLt Expert configuration, MoE backward fusion, NVFP4 GQA, paged prefill attention 등을 대상으로 평가했습니다. ([arXiv][5])

저자들은 7월 30일 SOL-ExecBench leaderboard snapshot에서 KernelArc가 생성한 구현들이 L1, L2, Quantization, FlashInfer 계열의 대표 task에서 1위를 기록했다고 보고합니다. 다만 논문의 핵심 결론은 “multi-agent가 항상 single-agent보다 좋다”가 아닙니다. 논문도 coordination feature의 효과가 kernel과 optimization phase에 따라 달라진다고 명시합니다. ([arXiv][5])

**왜 중요한가.** GPU 성능 튜닝은 탐색 공간이 매우 큽니다.

```text
Agent A → memory layout
Agent B → tiling
Agent C → fusion
Agent D → library/kernel selection
       ↓
deterministic correctness + latency benchmark
       ↓
좋은 후보만 공유
```

이 구조는 일반 multi-agent coding보다 GPU optimization에 특히 잘 맞습니다. 정답 여부와 성능이라는 **강한 deterministic oracle**이 있기 때문입니다.

실무에서는 Agent들이 전체 코드를 서로 읽으며 동조하는 대신 `approach`, `measured_latency`, `shape_region`, `failed_reason` 정도만 shared ledger에 올리게 하는 방식이 유용합니다. 이렇게 하면 exploration diversity를 유지하면서 이미 실패한 전략을 반복하는 낭비를 줄일 수 있습니다.

**주의·후속 관찰.** Leaderboard 1위가 production model의 E2E speedup을 의미하지는 않습니다. Kernel은 특정 shape·dtype·hardware에 과적합될 수 있고, search 자체가 상당한 model inference·GPU benchmark compute를 소비합니다. 따라서 `kernel_speedup / search_GPU_hours`까지 봐야 합니다. ([arXiv][5])

**원문:** **[논문] KernelArc: A Multi-Agent Framework for GPU Kernel Optimization** ([arXiv][5])

## 4. Physical AI | Cosmos 3 Edge — 4B world model을 실제 Jetson 로봇 정책으로 post-training

**무엇이 바뀌었나.** NVIDIA가 8월 19일 Cosmos 3 Edge를 robot manipulation policy로 post-train해 **Jetson AGX Thor에서 완전 온디바이스 실행**하는 튜토리얼과 checkpoint를 공개했습니다. Cosmos 3 Edge는 4B omni-model이며 내부에 2B Nemotron 기반 reasoner를 포함합니다. 공식 pipeline은 DROID robot dataset으로 action prediction을 post-train하고 receding-horizon control loop에서 실행하는 방식입니다. ([NVIDIA Developer][6])

Jetson AGX Thor T5000에서 640×540, 15Hz 조건으로 action chunk 하나를 약 **1.53초**에 생성하며, 각 chunk는 약 2.13초의 robot motion을 커버합니다. 따라서 이전 chunk를 실행하는 동안 다음 chunk를 계산해 연속 동작이 가능합니다. 다만 closed-loop RoboLab task 성공률은 **22.9%**로, “실시간으로 돈다”와 “신뢰성 높은 robot policy다”는 아직 큰 차이가 있습니다. ([NVIDIA Developer][6])

**왜 중요한가.** Physical AI에서 foundation model의 deployment target이 data center GPU에서 robot onboard computer로 내려오고 있다는 점이 중요합니다. Network round-trip이 사라지면 latency뿐 아니라 연결 장애·privacy·safety boundary도 바뀝니다.

하지만 training 비용은 작지 않습니다. NVIDIA의 validated post-training run은 64 nodes × 4 GB200, 약 68시간, **약 17.4K GB200-hours**를 사용한다고 명시합니다. 즉 4B 모델이라고 해서 post-training까지 edge-sized인 것은 아닙니다. ([NVIDIA Developer][6])

**실무 적용.** 로봇 정책 평가에서는 `policy inference latency`만 보지 말고 `action horizon`, `replan frequency`, `closed-loop success`, `collision`, `action drift`를 같이 측정해야 합니다. 한 chunk가 빠르게 생성돼도 환경 변화에 대한 replan 주기가 길면 실제 control quality가 떨어질 수 있습니다.

**후속 관찰 포인트:** closed-loop 성공률 향상, 다른 embodiment로 transfer할 때 필요한 data량, post-training compute 절감, quantization 이후 control stability입니다.

**원문:** **[공식 기술 가이드] Cosmos 3 Edge robot post-training** ([NVIDIA Developer][6]) · **[GitHub] cosmos-framework** ([GitHub][7])

## 5. 분산·멀티모달 | NVIDIA FLARE — VLM federated training의 병목은 “모델보다 update payload”

**무엇이 바뀌었나.** NVIDIA는 8월 19일 FLARE를 이용한 federated multimodal training의 구체적인 설계 패턴을 공개했습니다. Raw image·report·prompt는 각 기관에 남겨두고 server에는 승인된 model update만 보냅니다. Full model, adapter, distilled knowledge 등 어떤 state를 federation할지 먼저 계약으로 정하고, 대형 update에는 large-object externalization, tensor streaming, disk-backed aggregation을 사용합니다. ([NVIDIA Developer][8])

FedUMM 사례에서는 frozen multimodal backbone 위의 lightweight LoRA adapter만 교환해, 실험상 client당 round communication을 **28.6GB에서 0.094GB**까지 줄였다고 NVIDIA가 소개합니다. Full model update가 필요한 경우에는 FLARE 2.8의 tensor disk offload로 server가 client update를 전부 RAM에 동시에 올리는 대신 임시 safetensors 파일로 저장해 aggregation memory가 client 수와 선형으로 증가하는 문제를 줄입니다. ([NVIDIA Developer][8])

**왜 중요한가.** Federated learning에서 “데이터를 중앙으로 모으지 않는다”만 보면 부족합니다. 대형 VLM에서는 다음 세 가지가 실제 infrastructure 문제입니다.

```text
무엇을 공유할 것인가?
→ full weights / LoRA / distilled signal

어떻게 전송할 것인가?
→ stream / external object

어디에서 aggregate할 것인가?
→ RAM / disk
```

특히 병원·기업처럼 modality 구성이 site마다 다른 경우에는 client가 어떤 component를 update할 수 있는지도 명시적인 contract가 필요합니다. ([NVIDIA Developer][8])

**주의·후속 관찰.** Adapter만 공유한다고 privacy가 자동으로 보장되는 것은 아닙니다. Gradient/model update에서도 정보 leakage 가능성이 있기 때문에 secure aggregation·DP·access control은 별도 계층입니다. 이번 NVIDIA 글은 주로 orchestration·communication·memory engineering에 초점을 둡니다. ([NVIDIA Developer][8])

**원문:** **[NVIDIA 기술 가이드] Federated Multimodal AI with FLARE** ([NVIDIA Developer][8]) · **[GitHub] NVIDIA/NVFlare** ([GitHub][9])

## 6. AI 보안·Privacy | OpenAI Private Safety Processing — ZDR를 유지하면서 여러 turn의 위험 패턴을 본다

**무엇이 바뀌었나.** OpenAI는 8월 19일 eligible API customer의 **Zero Data Retention(ZDR)**을 유지하면서 장기 위험 패턴을 분석하기 위한 `Private Safety Processing`을 preview했습니다. 기존 ZDR-compatible safeguards가 각 interaction을 개별적으로 평가했다면, 새 방식은 여러 interaction에 걸친 probing, account 간 coordinated activity, 또는 agent가 stop 지시 이후 계속 행동하는 패턴 등을 자동 탐지하는 것을 목표로 합니다. ([OpenAI][10])

ZDR deployment에서는 customer content가 고객이 통제하는 infrastructure에 남습니다. OpenAI-hosted storage를 사용하는 별도 옵션도 개발 중인데, 이 경우 customer-controlled encryption key를 사용하며 OpenAI personnel은 underlying prompt·response를 볼 수 없도록 설계한다고 설명합니다. Automated system은 원문 전체 대신 제한된 safety signal을 반환하는 구조입니다. 현재는 early customer들과 시험 중입니다. ([OpenAI][10])

**왜 중요한가.** Long-horizon agent에서는 위험을 한 prompt만 보고 판단하기 어렵습니다.

```text
Turn 1: 서버 목록 조회
Turn 2: credential 검색
Turn 3: network 확인
Turn 4: 데이터 전송

각 turn은 애매
trajectory 전체는 위험
```

그런데 regulated enterprise에서는 provider가 원문을 30일씩 보관하는 것도 받아들이기 어렵습니다. 결국 agent safety는 **cross-turn stateful detection과 content confidentiality를 동시에 만족해야 하는 시스템 문제**가 됩니다. ([OpenAI][10])

**주의·후속 관찰.** 현재 기술 세부사항—어떤 cryptographic primitive를 쓰는지, false-positive/false-negative, safety signal에 얼마만큼 정보가 포함되는지—는 충분히 공개되지 않았습니다. “OpenAI가 데이터를 보지 않고 완벽하게 misuse를 탐지한다”는 의미로 확대하면 안 됩니다. ([OpenAI][10])

**원문:** **[공식 발표] OpenAI — Zero Data Retention & Private Safety Processing** ([OpenAI][10])

## 7. 개발 보안 | CodeQL 2.26.3 — Agent가 만드는 GitHub Actions까지 공급망 공격면으로 봐야 한다

**무엇이 바뀌었나.** GitHub는 8월 19일 CodeQL 2.26.3을 배포했습니다. GitHub Actions에서는 `merge_group` event의 untrusted data를 새로 인식하고, cache-poisoning과 untrusted-checkout query의 data-flow path를 더 정확하게 추적하도록 수정했습니다. `schedule` event의 외부 trigger 가능성 분류도 바로잡혔고, environment-variable injection query는 untrusted source와 privileged context가 동일 trigger에서 발생해야 alert하도록 정교화됐습니다. ([The GitHub Blog][11])

JavaScript/TypeScript 쪽에서는 Vue `ref/reactive/computed`, Vue Router `useRoute()`, Sails Action2 input을 flow source로 모델링하고, promise-wrapped HTTP response를 threat model이 추적하게 됐습니다. 반면 runner label만으로 self-hosted runner를 식별하는 것이 신뢰할 수 없다는 이유로 `SelfHostedQuery` module이 제거됐습니다. Custom query에서 이 모듈을 썼다면 breaking change입니다. ([The GitHub Blog][11])

**왜 중요한가.** Coding agent가 application code뿐 아니라 `.github/workflows/*.yml`까지 수정하기 시작하면서 CI 자체가 high-privilege execution surface가 됐습니다. 특히 cache poisoning, untrusted checkout, secret context 문제는 agent가 “테스트를 고치겠다”며 workflow permission을 넓힐 때 바로 발생할 수 있습니다.

실무에서는 agent-generated PR에서 `auth/`, `IAM`, `CI/CD`, dependency manifest와 함께 `.github/workflows`를 별도의 high-risk lane으로 분류해 deterministic CodeQL·secret scan을 통과시키는 것이 좋습니다.

**주의·후속 관찰.** GitHub.com code scanning에는 새 CodeQL이 자동 배포되지만 GHES는 future release 또는 manual upgrade가 필요합니다. Custom query를 운영한다면 2.26.3 migration을 먼저 검증해야 합니다. ([The GitHub Blog][11])

**원문:** **[릴리스 노트] CodeQL 2.26.3** ([The GitHub Blog][11])

## 8. Agent 경제 | Bedrock AgentCore Payments GA — Agent가 Tool뿐 아니라 돈까지 직접 쓴다

**무엇이 바뀌었나.** AWS는 8월 18일 AgentCore Payments를 GA로 전환했습니다. Coinbase와 Stripe Privy wallet을 지원하고, agent 자체에는 raw wallet credential을 노출하지 않고 AgentCore Secrets Manager에 보관한 뒤 short-lived token을 사용합니다. Preview의 x402에 더해 GA에서는 Stripe·Tempo가 만든 Machine Payment Protocol(MPP)도 지원합니다. ([Amazon Web Services, Inc.][12])

또 `x402 upto` scheme을 지원해 agent가 “이 작업에 최대 얼마까지 지불하겠다”는 ceiling만 정하고, 실제 token·compute·API 사용량에 따라 나중에 정확한 금액을 결제할 수 있게 했습니다. 즉 Agent가 유료 MCP·검색 API·GPU compute를 **per-execution 방식으로 자율 구매**하는 infrastructure가 실제 product feature로 들어온 것입니다. ([Amazon Web Services, Inc.][12])

**왜 중요한가.** Agent에게 payment capability가 생기면 cost control은 FinOps가 아니라 authorization 문제가 됩니다.

```text
Agent reasoning
   ↓
"이 API를 쓰면 성공 가능성 +20%"
   ↓
cost = $0.08
   ↓
budget / policy check
   ↓
payment
```

Model prompt의 “50달러 이상 쓰지 마”는 충분하지 않습니다. Runtime에 `per_action_limit`, `per_session_limit`, `merchant_allowlist`, `currency`, `approval_threshold`, `idempotency_key`가 필요합니다.

**주의·후속 관찰.** Wallet abstraction이 쉬워졌다고 해서 merchant가 안전하거나 agent가 비용 대비 좋은 판단을 한다는 보장은 없습니다. Agent가 불필요한 paid tool을 반복 호출하는 denial-of-wallet 문제는 여전히 별도 policy가 필요합니다.

**원문:** **[AWS 공식 발표] AgentCore Payments GA** ([Amazon Web Services, Inc.][12])

# 오늘 꼭 볼 것 3개

**1. NVIDIA SkillEvaluator.** 오늘 가장 바로 써볼 가치가 큽니다. Skill을 그냥 설치하는 게 아니라 **동일 task에서 ON/OFF로 정확성·비용·workflow 차이를 측정한다**는 방법론이 매우 좋습니다. Codex나 Claude Code에서 자체 Skill을 운영한다면 곧바로 적용할 수 있습니다. ([NVIDIA Developer][1])

**2. KernelArc.** GPU·ML infrastructure 관점에서 가장 흥미로운 연구입니다. Multi-agent search가 단순 코드 생성이 아니라 **B200/H100 kernel search와 deterministic benchmark loop**까지 들어가기 시작했습니다. ([arXiv][5])

**3. OpenAI Private Safety Processing.** Long-horizon agent에서 privacy와 safety가 서로 반대 요구조건처럼 보이던 문제를 풀려는 시도입니다. 특히 **cross-turn misuse detection을 ZDR과 같이 가져가려는 architecture**라는 점을 보세요. ([OpenAI][10])

# 오늘의 실습 | 내 Codex Skill을 “SkillEvaluator 방식”으로 A/B 검증하기

오늘은 NVIDIA SkillEvaluator를 그대로 사용하거나, 먼저 아주 작은 paired experiment로 원리를 재현해보는 것을 추천합니다. SkillEvaluator는 `uv`로 설치할 수 있고 deterministic Tier 1 검사는 API key나 Docker 없이도 시작할 수 있습니다. ([GitHub][2])

먼저 자신의 `SKILL.md` 하나를 골라 정적 검사를 돌립니다.

```bash
uv tool install --python 3.13 \
  "skillevaluator[all] @ git+https://github.com/NVIDIA/SkillEvaluator.git"

skillevaluator validate ./my-skill \
  --checks schema,pii,license,quality,unicode,lint \
  --no-dedup
```

그다음 이 Skill이 실제로 필요한 task 10개와 **Skill과 무관한 negative task 5개**를 준비합니다. 같은 model·repository·temperature·prompt로 두 조건을 각각 최소 3회 실행합니다.

```text
A. Skill OFF
B. Skill ON
```

다음 지표만 기록해도 충분합니다.

```text
strict_success

tool_calls
test_runs
files_read
files_changed

input_tokens
output_tokens
wall_clock

unsafe_action_attempts
```

마지막으로 아래 차이를 계산하십시오.

```text
Skill Lift(success)
= success_ON - success_OFF

Token Cost
= tokens_ON - tokens_OFF

Tool Overhead
= tool_calls_ON - tool_calls_OFF
```

예를 들어 Skill이 성공률을 `70% → 85%`로 올렸지만 token은 `+8%`라면 꽤 좋은 artifact입니다. 반대로 `70% → 73%`인데 token과 tool call이 각각 80% 늘어난다면 Skill 내용이 지나치게 절차적일 가능성이 큽니다.

그리고 negative task가 중요합니다. **좋은 Skill은 필요한 task에서는 로드되고, 관련 없는 task에서는 agent의 attention을 차지하지 않아야 합니다.** NVIDIA도 Discoverability를 별도 평가 축으로 두는 이유가 이것입니다. ([NVIDIA Developer][1])

이 실험을 Skill repository의 CI로 만들어두면 앞으로 Codex 모델이나 harness가 바뀔 때마다:

```text
Skill version
× Model version
× Harness version
```

세 축의 regression을 자동으로 확인할 수 있습니다. Agent Skill을 markdown 문서가 아니라 **버전 관리되는 production software component**로 다루기 시작하는 가장 좋은 첫 단계입니다.
