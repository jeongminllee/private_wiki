# AI 엔지니어 데일리 브리핑

**2026년 8월 14일 금요일**
**분석 범위:** 8월 13일 공식 발표·릴리스와 8월 12~13일 공개된 최신 연구를 우선 확인했습니다.

오늘 흐름은 꽤 명확합니다. **모델 자체의 성능 향상과 동시에, 에이전트의 Skill·Tool·Memory·Harness를 어떻게 설계하느냐가 모델 선택만큼 중요해지고 있습니다.** Google은 Flash급 가격대에서 coding·agent 성능을 크게 끌어올린 Gemini 3.7 Flash를 공개했고, 최신 연구들은 “Skill을 추가하면 좋아진다”, “실패하면 재시도하면 된다”, “오래된 대화는 요약하면 된다”는 단순한 설계가 실제로는 상당한 실패를 만든다는 것을 정량적으로 보여줍니다. ([Google DeepMind][1])

## 1. 필독 | Gemini 3.7 Flash — Flash급 모델의 coding·agent 성능 기준이 다시 올라갔다

### 무엇이 바뀌었나

Google이 **8월 13일 Gemini 3.7 Flash**를 공개했습니다. 3.6 Flash 출시 불과 3주 뒤 나온 후속 모델로, Google은 software engineering, knowledge work, web development와 multi-step tool-use를 주요 개선 영역으로 제시했습니다. 공식 평가에서는 FrontierCode 1.1 Main이 34.4%→43.6%, DeepSWE v1.1이 약 48.6~49.0%→65.3%, Terminal-bench 2.1이 78.0%→85.8%, AutomationBench가 17.0%→30.4%로 상승했습니다. 다만 이 수치는 Google이 공개한 평가이며 AutomationBench처럼 private set도 포함됩니다. ([Google DeepMind][1])

모델은 text·image·audio·video 입력, 최대 **1M token context**, 64K text output을 지원하며 thinking 수준을 조절해 quality·cost·latency를 바꿀 수 있습니다. 출시 가격은 2026년 12월 31일까지 input $0.75/1M, output $3.75/1M token이고, **2027년 1월 1일부터 각각 $1.50/$7.50으로 인상**됩니다. ([Google DeepMind][1])

GitHub도 같은 날 Copilot에서 Gemini 3.7 Flash rollout을 시작했습니다. VS Code, Visual Studio, Copilot CLI, cloud coding agent 등에서 단계적으로 제공되며 Business·Enterprise는 관리자가 preview model policy를 허용해야 합니다. ([The GitHub Blog][2])

### 왜 중요한가

흥미로운 부분은 단순히 benchmark가 몇 점 올랐다는 것이 아닙니다. Google의 자체 표에서 Gemini 3.7 Flash는 일부 coding benchmark에서 훨씬 비싼 frontier-class 모델과 비슷한 영역까지 접근합니다. 즉 agent architecture에서 **“싼 모델 = 단순 분류·요약용”이라는 기존 routing threshold를 다시 계산해야 할 가능성**이 있습니다. ([Google DeepMind][3])

예를 들어 이전에는:

```text
파일 탐색 / 단순 수정 → Flash
복잡한 coding          → Frontier model
```

이었다면 이제는:

```text
파일 탐색
일반적인 bug fix
tool orchestration
반복 implementation
        ↓
Gemini 3.7 Flash

복잡한 architecture 판단
여러 실패 후 재계획
고위험 검증
        ↓
Frontier model
```

처럼 frontier escalation 시점을 뒤로 미룰 여지가 생깁니다. 다만 이는 **같은 harness·동일 budget에서 직접 측정했을 때** 성립하는 이야기입니다.

### 실제 적용

3.6 Flash나 현재 쓰는 주력 모델과 비교할 때 benchmark score보다 다음을 기록하는 편이 좋습니다.

```text
strict_task_success
tool_calls_per_success
retry_count
thinking_tokens
wall_clock_per_success
cost_per_success
frontier_escalation_rate
```

특히 3.7 Flash가 “더 오래 생각한다”는 Google 설명 때문에, token 단가는 싸더라도 reasoning·tool call 증가로 **task당 비용이 비례해서 줄지 않을 수 있습니다.** ([Google DeepMind][1])

### 주의할 점과 후속 관찰

현재 가격은 영구 가격이 아닙니다. 2027년부터 2배로 올라가기 때문에 router를 현재 가격에 맞춰 지나치게 최적화하면 몇 달 뒤 경제성이 달라집니다. 또한 1M context 지원과 1M context에서의 안정적인 agent 성능은 같은 의미가 아닙니다. 긴 context에서는 TTFT, retrieval quality, context dilution을 별도 측정해야 합니다. ([Google DeepMind][1])

**후속 관찰 포인트:** 실제 coding harness에서 Sonnet/GPT 계열과 cost-per-success 비교, thinking level별 latency, 100K+ repository context에서의 성능, 장기 tool trajectory의 오류율.

**원문:** **[공식 발표] Gemini 3.7 Flash** ([Google DeepMind][1]) · **[모델 카드] Gemini 3.7 Flash** ([Google DeepMind][3]) · **[GitHub 릴리스] Copilot 지원** ([The GitHub Blog][2])

## 2. 개발 도구·로컬 AI | Unsloth Desktop 0.1.702-beta — 학습·서빙·Agent runtime을 한 앱으로

Unsloth가 **8월 13일 `v0.1.702-beta`**를 공개했습니다. Windows·macOS·Linux에서 local model 실행과 학습, OpenAI-compatible API serving, web search, RAG, MCP, Python/Bash sandbox를 하나의 desktop 환경에 통합합니다. 이번 업데이트에서는 외부 provider의 tool calling·web search, VRAM 조절, AMD RDNA3/4·Strix Halo와 Mac 지원 개선, image/video generation 수정, Codex subscription login 등이 추가됐습니다. ([GitHub][4])

특히 눈에 띄는 변경이 하나 있습니다. 릴리스 노트에 **“sandboxing에서 bypass permissions가 작동하지 않던 문제를 수정했다”**고 명시돼 있습니다. Local AI desktop이 단순 chat UI가 아니라 shell·Python·MCP를 실행하는 agent runtime이 되면서, permission regression이 일반 UI bug보다 훨씬 심각한 문제가 된다는 사례입니다. ([GitHub][4])

### 왜 중요한가

로컬 AI stack의 구성 요소가 빠르게 한 제품 안으로 수렴하고 있습니다.

```text
모델 다운로드
↓
양자화 / VRAM 설정
↓
inference
↓
training
↓
OpenAI-compatible serving
↓
RAG / web / MCP
↓
Python / Bash execution
```

초기 실험에는 상당히 편리한 구조입니다. 특히 여러 GPU vendor나 Mac·AMD·NVIDIA 환경을 오가며 모델을 빠르게 비교할 때 환경 구축 비용을 줄일 수 있습니다. ([GitHub][4])

### 실제 적용

이런 통합 도구를 평가할 때 inference 속도보다 먼저 **권한 경계**를 확인하는 것을 권합니다.

```text
filesystem write boundary
network egress
localhost access
MCP allowlist
environment-variable access
credential redaction
subprocess timeout
```

예를 들어 sandboxed Python 코드가 `$HOME/.ssh`, AWS credential, Docker socket, cloud metadata endpoint에 접근 가능한지부터 테스트해야 합니다.

Unsloth는 이번 릴리스에서 10% faster inference, self-healing tool calling 최대 50% 정확도 개선, 일부 workload에서 학습 최대 2배와 VRAM 최대 70% 절감을 주장합니다. 이 숫자들은 **프로젝트 자체 benchmark**이므로 모델·precision·hardware를 고정한 독립 측정 전에는 제품 특성으로만 받아들이는 것이 적절합니다. ([GitHub][4])

### 후속 관찰 포인트

Beta 단계에서 sandbox permission regression이 얼마나 안정화되는지, self-healing tool call이 잘못된 tool call을 “그럴듯하게 고쳐서 실행하는” 부작용은 없는지, AMD와 NVIDIA에서 실제 training parity가 어느 정도인지가 중요합니다.

**원문:** **[GitHub 릴리스] Unsloth Desktop v0.1.702-beta** ([GitHub][4])

## 3. ML 프레임워크 | Transformers 5.15 — Hybrid Attention 시대에는 cache·kernel 설정도 API contract다

Hugging Face `transformers v5.15.0`은 8월 10일 공개됐습니다. Muse Glimmer, GraniteMoeSWA, SKT A.X-K1/K2, Cosmos3 Edge 등 새 모델 지원과 함께, **linear-attention·cache 관련 breaking change**가 상당히 많습니다. ([GitHub][5])

특히 Mamba·GDN·Conv-only 같은 linear-attention 모델에서 kernel 사용이 이제 **자동이 아니라 opt-in**으로 바뀌었습니다. 이전 자동 kernel 선택에 의존하던 환경이라면 upgrade 후 같은 모델이 다른 execution path를 사용할 수 있습니다. Cache cropping API도 absolute size 대신 negative relative offset만 허용하도록 바뀌었고, T5 계열은 SDPA 등 여러 attention backend를 지원하기 시작해 default execution이 달라질 수 있습니다. ([GitHub][5])

MLA cache compression 수정, vision Flash Attention의 maximum sequence 계산 개선, heterogeneous attention 설정 명시화와 FP8 kernel NaN 방지를 위한 kernel version update도 포함됐습니다. ([GitHub][5])

### 왜 중요한가

최근 모델은 더 이상 “모든 layer가 동일한 Transformer attention”이라고 가정하기 어렵습니다.

```text
Full Attention
+
Sliding Window
+
GDN / Linear Attention
+
Convolution
+
Recurrent State
```

처럼 layer마다 state semantics가 달라집니다.

그 결과 같은 checkpoint라도:

```text
transformers version
kernel package
attn_implementation
cache implementation
```

이 달라지면 **성능뿐 아니라 memory 사용량과 numerical behavior까지 달라질 수 있습니다.**

### 실제 적용

Transformers upgrade 회귀 테스트에서 version만 기록하지 말고:

```text
model_commit
transformers_version
torch_version
kernel_version
attn_backend
cache_type
dtype
```

를 artifact로 묶는 것이 좋습니다.

특히 hybrid model이라면 prefill/decode 각각의 latency와 cache memory를 따로 기록해야 합니다. 자동 fallback 때문에 “오류 없이 실행된다”와 “이전 fast path를 그대로 사용한다”는 전혀 다른 상태일 수 있습니다. ([GitHub][5])

### 주의할 점

이번 릴리스는 명시적인 breaking change가 있으므로 기존 환경에 `pip install -U transformers`만 수행하고 benchmark 없이 운영 승격하는 것은 피하는 편이 좋습니다. Private helper function을 직접 import한 downstream code도 깨질 수 있습니다. ([GitHub][5])

**후속 관찰 포인트:** linear-attention kernel API의 안정화, hybrid-model cache abstraction, speculative decoding과 recurrent state의 결합.

**원문:** **[GitHub 릴리스] Transformers v5.15.0** ([GitHub][5])

## 4. 필독 | Agent Skills Can Be Harmful — “관련 있는 Skill”이 오히려 에이전트를 망칠 수 있다

8월 12일 공개된 연구는 SkillsBench와 SWE-Skills-Bench에서 **307개의 skill-induced failure**를 분석했습니다. 이 가운데 125건은 실제 task 실패, 182건은 성공하더라도 비용·실행 시간이 악화되는 efficiency regression이었습니다. ([arXiv][6])

흥미로운 결과는 실패가 대개 **엉뚱한 Skill을 잘못 불러와서 발생한 것이 아니라는 점**입니다. 문제와 관련 있어 보이는 Skill이 agent에게 불필요한 절차를 강요하거나, 실제 요구사항 일부를 잘못 구현·누락하게 만들었습니다. Efficiency regression 가운데 “과도한 검증” 관련 사례가 67건, 무거운 implementation pipeline이 30건이었습니다. ([arXiv][6])

### 왜 중요한가

Skill을 흔히 이렇게 생각합니다.

```text
Model + 좋은 지침
= Model보다 항상 좋음
```

하지만 실제로 Skill은 일종의 **behavioral policy**입니다.

예를 들어 Skill에:

```text
모든 변경 후
1. 전체 저장소 검사
2. lint
3. unit test
4. integration test
5. dependency audit
6. 문서 생성
```

이 들어 있다면 두 줄짜리 수정에도 이 workflow를 매번 수행할 수 있습니다.

즉 Skill quality는 내용이 “좋아 보이는가”가 아니라:

```text
Skill ON
vs
Skill OFF
```

의 differential evaluation으로 측정해야 합니다.

### 실제 적용

Skill registry에 다음 정보를 붙이는 것을 권합니다.

```text
skill_version
applicable_task_types
strict_success_delta
tokens_delta
tool_calls_delta
wall_clock_delta
known_failure_modes
```

새 Skill을 모든 agent에 곧바로 넣지 않고 대표 task에서 **no-skill baseline과 A/B test**한 뒤 승격시키는 구조가 좋습니다.

특히 어제 다룬 Agent Plugins 1.0처럼 Skill 배포 자체가 쉬워질수록, **좋지 않은 Skill 역시 더 빠르게 조직 전체로 퍼질 수 있습니다.** 이 연결은 두 자료를 종합한 실무적 해석입니다. ([arXiv][6])

### 주의할 점

연구는 두 benchmark를 대상으로 한 초기 preprint입니다. “Skill은 쓰면 안 된다”는 결과가 아니라, **Skill 자체도 모델·prompt와 독립적으로 regression test해야 한다**는 결과에 가깝습니다. ([arXiv][6])

**후속 관찰 포인트:** 모델별 Skill sensitivity, 여러 Skill을 동시에 로드했을 때 interaction, 조직 공용 Skill의 canary rollout과 자동 regression detection.

**원문:** **[논문] Agent Skills Can Be Harmful** ([arXiv][6])

## 5. 에이전트 신뢰성 | Retry, Switch, or Abstain? — 실패하면 무조건 3번 재시도하는 agent는 약하다

8월 12일 공개된 BENCH2ROBUST 연구는 tool-use agent를 **도구가 실제로 실패하는 환경**에서 평가합니다. 기존 benchmark는 API 호출이 거의 항상 성공하지만, 운영 환경에서는 timeout 같은 일시적 실패, 계속 반복되는 영구 실패, 성공처럼 보이지만 잘못된 값을 반환하는 silent failure가 모두 존재합니다. ([arXiv][7])

BENCH2ROBUST는 agent가 상황에 따라 세 행동 가운데 하나를 선택하게 합니다.

```text
RETRY   → 같은 경로를 다시 시도
SWITCH  → 다른 tool / 경로로 전환
ABSTAIN → 더 이상 안전한 경로가 없으면 중단
```

7개 모델·4개 model family에서 거의 공통적으로 robustness gap이 발생했습니다. Bayesian Tool Memory(BTM)를 runtime에 추가하면 held-out Retail task에서 최대 16.8%p 개선됐고, RL과 결합했을 때 injected-failure 조건의 성공률은 40.8~45.5%였습니다. ([arXiv][7])

### 중요한 해석

오히려 마지막 숫자가 핵심입니다.

**runtime memory + RL까지 결합해도 절반을 넘지 못했습니다.**

즉 production agent의 tool recovery는 아직 상당히 미성숙합니다. ([arXiv][7])

### 실제 적용

Tool wrapper가 예외를 단순 문자열로 반환하지 말고 machine-readable failure semantics를 제공하는 편이 좋습니다.

```text
failure_type:
  transient
  persistent
  auth
  rate_limit
  invalid_input
  semantic_failure

retryable: true / false
retry_after:
alternate_tool:
idempotency_key:
```

Agent runtime은 이를 바탕으로:

```text
timeout          → bounded retry
rate-limit       → wait / alternative
auth failure     → retry 금지
repeated 5xx     → switch
모든 경로 소진   → abstain
```

처럼 결정적인 정책을 일부 가져갈 수 있습니다.

특히 **HTTP 200을 success로 간주하면 silent failure를 잡을 수 없습니다.** 반환 데이터의 schema뿐 아니라 의미적 invariant까지 verifier가 검사해야 합니다.

### 주의할 점

연구의 failure injection은 통제된 benchmark 환경입니다. 실제 SaaS API에서는 partial write, duplicate side effect, delayed consistency 같은 훨씬 복잡한 failure가 존재합니다. ([arXiv][7])

**후속 관찰 포인트:** idempotent tool protocol, MCP 차원의 표준화된 error semantics, retry budget을 비용·side-effect 위험과 결합하는 방법.

**원문:** **[논문] Retry, Switch, or Abstain?** ([arXiv][7])

## 6. 장기 메모리 | The Sleeping Agent — 요약은 사건을 기억하면서 ‘언제 일어났는지’를 지운다

이 연구는 long-horizon agent에서 흔히 사용하는 **gist-based context compression**을 분석했습니다. LoCoMo의 10개 conversation, 총 1,935개 text-only 질문을 이용한 실험에서 gist compression은 단순 truncation보다 multi-hop·single-hop factual retrieval에 유리했지만, **날짜·시간이 필요한 temporal question에서는 full context보다 크게 약했습니다.** ([arXiv][8])

원인을 추적해 보니 summarization prompt가 사람·사건 관계는 보존하면서 **date와 time을 선택적으로 버리고 있었습니다.** 단 한 문장으로 “시간 정보를 보존하라”는 지시를 추가하자 temporal expression preservation이 3.05%에서 62.39%로 약 20배 증가했고, temporal-question judge accuracy도 +0.314 개선됐습니다. ([arXiv][8])

### 왜 중요한가

Agent memory를 단순히:

```text
old conversation
→ summarize()
→ memory
```

로 만들면 중요한 operational information이 사라질 수 있습니다.

특히 개발·연구 agent에서는 다음이 그렇습니다.

```text
deadline
release version
commit SHA
experiment timestamp
model version
approval time
dataset revision
```

이 정보는 문맥적으로 “덜 중요한 세부사항”처럼 보여도 나중에는 **정확성의 핵심 key**가 됩니다.

### 실제 적용

메모리를 두 계층으로 분리하는 것을 권합니다.

```text
Lossless structured memory
- timestamp
- version
- commit
- deadline
- ID
- approval
- numeric result

Lossy semantic memory
- 사건 요약
- 결정 이유
- 관계
- 계획
```

즉 날짜와 버전을 LLM summarizer의 판단에 맡기지 말고 deterministic extractor나 structured state로 보존합니다.

### 주의할 점

한 명의 연구자가 작성한 초기 연구이며 LoCoMo 10개 conversation이라는 제한된 데이터셋을 사용했습니다. 특정 compression prompt에서 발견한 failure mode가 모든 memory system에서 동일한 비율로 발생한다고 볼 수는 없습니다. ([arXiv][8])

하지만 **“memory compression은 정보량 문제뿐 아니라 어떤 field를 절대 손실시키지 않을지 정하는 schema 문제”**라는 설계 관점은 상당히 실용적입니다.

**후속 관찰 포인트:** coding-agent memory에서 commit·error·test result 보존, long-term memory의 schema evolution, 삭제·수정 요청과 structured memory의 일관성.

**원문:** **[논문] The Sleeping Agent** ([arXiv][8])

## 7. 머신러닝 연구 | AI4AI — 큰 모델로 작은 모델을 학습시키지 않고, ‘Harness’를 만들어준다

8월 12일 공개된 **AI4AI at Test-Time**은 일반적인 distillation과 다른 방향을 실험합니다. 큰 builder model이 작은 target model의 weight를 fine-tuning하는 대신, **target이 inference할 때 사용하는 harness를 자동 설계**합니다. ([arXiv][9])

네 개 Theory-of-Mind benchmark에서 builder는 데이터의 5%를 validation set으로 사용해 harness를 반복 개선했습니다. 최종적으로 target model의 평균 성능이 **0.49에서 0.91로 거의 두 배** 상승했습니다. ([arXiv][9])

그런데 개선 원인이 더 흥미롭습니다. Target model에게 더 오래 reasoning하게 한 것이 아니라:

* 불안정한 reasoning 일부를 deterministic code로 이전하고
* task별 routing을 추가하고
* output format을 강하게 검증하는

방식이 대부분의 이득을 만들었습니다. ([arXiv][9])

### 왜 중요한가

이건 일종의 **weight를 건드리지 않는 distillation**입니다.

```text
강한 모델
   ↓ offline
workflow / validator / router / parser 생성
   ↓
작은 모델
   ↓ online execution
```

반복적으로 수행되는 기업 업무나 정형화된 agent task라면 강한 모델을 매번 호출하기보다, 강한 모델을 **시스템 설계자**로 한 번 사용하고 그 결과를 작은 모델의 runtime에 고정할 수 있습니다.

예를 들어 coding task에서는:

```text
Frontier model가 offline으로
- 오류 taxonomy 설계
- parser 생성
- deterministic verifier 작성
- retry policy 작성

↓

작은 local model이 production 수행
```

하는 구조입니다.

### 주의할 점

현재 결과는 Theory-of-Mind benchmark 네 개에 기반하며, harness가 5% validation data를 반복적으로 사용합니다. 따라서 일부 성능 향상이 **benchmark-specific logic을 harness에 encoding한 효과**일 가능성을 반드시 고려해야 합니다. ([arXiv][9])

실제 적용에서는 새 domain·숨겨진 test·distribution shift에서도 같은 harness가 유지되는지를 확인해야 합니다.

**후속 관찰 포인트:** SWE-bench·data agent·tool agent로의 확장, harness portability, builder가 만든 코드의 보안 검사와 유지보수 비용.

**원문:** **[논문] AI4AI at Test-Time: Strong-to-Weak Capability Transfer via Harnesses** ([arXiv][9])

# 오늘 꼭 볼 것 3개

**1. Gemini 3.7 Flash.** 오늘 가장 큰 모델 변화입니다. Flash급 가격에서 coding·agent 성능이 크게 올라오면서 **small/fast model과 frontier model을 나누는 router의 경계 자체를 다시 측정할 필요**가 생겼습니다. 단, 현재 가격은 2026년 말까지만 적용됩니다. ([Google DeepMind][1])

**2. Agent Skills Can Be Harmful.** 최근 Skill·Plugin 생태계가 빠르게 커지는 상황에서 특히 중요한 연구입니다. Skill을 “추가 context”가 아니라 **성공률·비용을 바꾸는 executable policy artifact**로 보는 시각이 필요합니다. ([arXiv][6])

**3. Retry, Switch, or Abstain?** 실제 agent가 가장 많이 부딪히는 문제 가운데 하나입니다. Tool error 처리에서 `retry=3` 같은 단순 정책을 넘어 **실패 종류에 따라 retry·switch·abstain을 구분해야 한다**는 것을 정량적으로 보여줍니다. ([arXiv][7])

# 오늘의 실습 | Skill × Tool Failure 회귀 테스트 Harness 만들기

오늘은 두 최신 연구를 하나로 묶어 **“Skill을 넣은 Agent가 Tool 장애 환경에서도 정말 더 좋은가?”**를 직접 측정해보는 것을 추천합니다. 두 연구가 각각 Skill-induced regression과 tool-failure robustness를 다루기 때문에 상당히 좋은 작은 실험이 됩니다. ([arXiv][6])

간단한 agent에게 다음 세 tool을 줍니다.

```text
search_file(query)
run_test(test_name)
get_package_info(package)
```

그리고 동일한 task 10~20개를 두 조건으로 실행합니다.

```text
A. No Skill

B. Engineering Skill
- 수정 전 관련 파일을 읽는다.
- 수정 후 최소 관련 테스트를 수행한다.
- 테스트가 성공하면 불필요한 추가 작업을 하지 않는다.
```

그다음 tool environment를 네 가지로 바꿉니다.

```text
Normal
모든 tool 정상

Transient
첫 호출만 timeout

Persistent
특정 tool이 계속 500 반환

Silent
get_package_info가 HTTP 200이지만
오래된 version을 반환
```

Agent runtime에는 다음 recovery policy를 별도로 둡니다.

```text
transient
→ 1회 retry

persistent
→ alternative path가 있으면 switch

silent
→ 다른 source / invariant로 검증

모든 경로 실패
→ abstain
```

핵심은 이 recovery logic을 Skill 문장 안에만 넣지 않고 **runtime에서도 관측 가능하게 만드는 것**입니다.

기록할 지표는 다음이면 충분합니다.

```text
strict_success

skill_success_delta
skill_token_delta
skill_tool_call_delta

retry_count
switch_count
correct_abstain

silent_failure_detected
incorrect_tool_result_used

wall_clock_per_success
tokens_per_success
```

결과는 다음 두 축으로 보는 것이 좋습니다.

```text
Skill 효과
Normal에서 성공률이 올랐는가?
비용만 증가하지 않았는가?

Robustness 효과
Failure 환경에서
retry / switch / abstain을 제대로 선택했는가?
```

가장 흥미로운 결과는 **Normal 환경에서는 유용했던 Skill이 장애 환경에서는 과도한 checklist 때문에 오히려 실패를 키우는 경우가 있는지**입니다.

이 실험을 조금 더 발전시키면 Skill 하나를 추가할 때마다 자동으로 `Skill ON / OFF × Normal / Failure` 네 조건을 실행하는 regression CI를 만들 수 있습니다. 그렇게 되면 Skill을 문서 파일이 아니라 **모델이나 library version과 똑같이 검증·승격해야 하는 engineering artifact**로 관리할 수 있습니다. ([arXiv][6])
