## 1. Claude Code 2.1.269/270: Agent skill도 이제 “느낌”이 아니라 재현 가능한 eval 대상으로 간다 ★★★★★

Anthropic은 9월 11일 Claude Code **v2.1.269**를 공개했고, 9월 12일 **v2.1.270** hotfix를 냈습니다. 가장 중요한 기능은 `claude plugin eval`입니다. 플러그인이나 skill의 eval suite를 실행해 **scored JSON과 HTML report**를 생성할 수 있게 됐습니다. 즉 plugin/skill을 추가한 뒤 “잘 되는 것 같다”가 아니라 동일 task set에서 이전 버전과 reproducible comparison을 할 수 있는 공식 경로가 생겼습니다. :chatgpt-content-reference{index="1"}

멀티에이전트 쪽에서는 `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`가 추가되어 inference-bound fan-out에서 한 실행당 **최대 256개 Agent**까지 허용할 수 있습니다. 동시에 interrupted session과 auto-resume에서 prompt cache가 불필요하게 깨지는 문제, compaction 이후 `git status`가 session 시작 시점의 오래된 상태를 보여주던 문제, 설정 source가 다른 permission rule에 영향을 주던 문제도 수정됐습니다. 다음 날 나온 2.1.270은 2.1.269에서 발생한 read-only git command permission regression을 바로잡았습니다. :chatgpt-content-reference{index="2"}

이 조합이 흥미로운 이유는 Agent framework의 다음 경쟁 지점이 단순히 **“subagent를 몇 개 띄울 수 있는가”**가 아니라 **“skill과 orchestration policy를 어떻게 평가하고 회귀 테스트하는가”**로 이동하고 있기 때문입니다. 50개 Agent를 병렬로 띄우는 것보다 새 skill이 성공률을 실제로 올렸는지, token 비용은 얼마나 증가했는지, 특정 repository에서만 overfit했는지 측정하는 infrastructure가 더 중요해집니다.

실무에서는 skill마다 `task success`, `tool-call count`, `tokens/success`, `latency`, `failure category`를 고정 eval set에서 비교하고, skill version을 code처럼 regression gate에 통과시키는 구조가 좋습니다. 특히 256-Agent fan-out은 기술적 상한이지 권장값은 아닙니다. concurrency를 높일수록 rate limit, duplicated exploration, context storage, sandbox RAM이 먼저 병목이 될 가능성이 큽니다.

## 2. py-kvcache: 외부 KV cache는 “있으면 빠르다”가 아니라 `load vs recompute` 의사결정 문제 ★★★★★

9월 10일 제출된 **Building py-kvcache**는 vLLM의 external KV caching을 꽤 현실적으로 분석했습니다. 핵심 결과부터 말하면, 긴 prefix에서는 NVMe에 저장된 KV를 읽어오는 것이 유리할 수 있지만 **짧은 prefix나 빠른 GPU에서는 그냥 GPU가 prefill을 다시 계산하는 편이 더 빠를 수 있습니다.** 즉 cache hit가 존재한다는 사실만으로 cache load를 선택하면 오히려 TTFT가 악화될 수 있습니다. :chatgpt-content-reference{index="4"}

논문은 GPU·CPU·NVMe tier를 비교하면서 실제 성능을 결정하는 요소가 raw SSD bandwidth만이 아니라 **transfer granularity, staging memory, 요청이 scheduler의 어느 시점에서 cache load를 시작하는가**라고 분석합니다. 이를 바탕으로 만든 `py-kvcache`는 direct I/O와 `io_uring`, bounded pinned staging memory, scheduler-aware preloading을 사용합니다. 80K-token prefix에서는 disk load가 LMCache 대비 2.0배 빨랐고, preloading 자체가 1.34배 개선에 기여했습니다. GPU+CPU+disk 전체 구성에서는 LMCache보다 1.23배 빨랐고 vLLM native KV Offload와 약 4% 이내 성능까지 접근했다고 보고합니다. :chatgpt-content-reference{index="5"}

그런데 가장 중요한 결과는 H100에서 나왔습니다. production trace replay에서는 평균 요청 prefix가 **cache load의 break-even point보다 짧았고 GPU memory만으로 충분한 prefix를 유지할 수 있어서 external KV cache의 이점이 줄었습니다.** 연구진은 따라서 external cache 사용을 setup-specific **admission decision**으로 봐야 한다고 결론냅니다. :chatgpt-content-reference{index="6"}

공개 구현도 이 철학을 그대로 사용합니다. request가 기다리는 동안 KV를 미리 DRAM으로 읽어두고, measured break-even curve를 이용해 request마다 `지금 load / background로 defer / GPU에서 recompute` 중 하나를 선택합니다. 작은 요청이 거대한 cache load 뒤에서 기다리지 않도록 queue 순서를 사실상 조정할 수도 있습니다. 다만 현재 구현은 단일 모델만 지원하고, vLLM fork가 필요하며 file cache의 GC·eviction도 아직 없습니다. :chatgpt-content-reference{index="7"}

이 연구가 주는 메시지는 명확합니다.

`cache hit = reuse`

가 아니라

`cache hit → load cost와 recompute cost 비교 → 더 싼 쪽 선택`

이어야 합니다.

Long-context serving을 한다면 cache hit rate만 기록할 게 아니라 `prefix length`, `load latency`, `recompute latency`, `storage tier`, `queue delay`를 함께 측정해야 합니다.

원문: [논문 · Building py-kvcache: External KV Caching for vLLM with NVMe SSDs](https://arxiv.org/abs/2609.11744) · [GitHub · atlarge-research/py-kvcache](https://github.com/atlarge-research/py-kvcache)

## 3. AgentZip: 고동시성 Agent에서는 GPU보다 sandbox RAM이 먼저 바닥날 수 있다 ★★★★★

**Memory Compression for High-Fanout Agent Sandboxes**는 멀티에이전트 인프라에서 꽤 중요한 병목을 짚습니다. 한 task가 수십 개 sibling Agent를 동시에 띄우면 각 Agent가 독립 sandbox를 가지는데, 실제로는 이 sandbox들이 같은 base image에서 출발하고 유사한 trajectory를 실행하기 때문에 memory page 상당 부분이 중복됩니다. 연구진이 측정한 workload에서는 **76~96%의 page가 template-relative 또는 cross-sandbox redundancy**를 보였습니다. :chatgpt-content-reference{index="10"}

AgentZip은 일반적인 swap/compression과 다르게 세 가지를 이용합니다. base template 대비 delta로 memory를 저장하고, sibling sandbox 사이에 유사 page dictionary를 공유하며, 무엇보다 **LLM 응답을 기다리는 idle 구간에서 압축 작업을 수행**합니다. Tool execution이 활발할 때 compression CPU 비용을 넣는 대신 Agent가 model output을 기다리는 시간을 활용하는 것입니다. :chatgpt-content-reference{index="11"}

LLM training·inference workload에서 sandbox-owned memory를 최대 **8.7배 줄였고**, Linux 기본 compression 구성은 2.1배 수준이었습니다. 공격적인 압축은 원래 실행을 최대 3.1배 느리게 만들 수 있었지만 restore prefetch와 agent-phase-aware scheduling을 적용하자 slowdown을 **1.40배**까지 줄이면서 대부분의 memory saving을 유지했다고 보고합니다. :chatgpt-content-reference{index="12"}

이건 앞으로 고 fan-out Agent system에서 꽤 현실적인 문제입니다. Agent concurrency를 올릴 때 보통 API rate limit이나 GPU throughput부터 생각하지만, 각 sandbox가 Python environment, repository, browser, tool process를 띄우면 **host RAM이 먼저 concurrency ceiling을 결정**할 수 있습니다.

실제 시스템에서는 `agent_count`만 보지 말고 `RSS/sandbox`, `shared-template ratio`, `idle-to-tool-execution ratio`, `restore page-fault latency`를 함께 보는 편이 좋습니다. 특히 동일 repository에서 여러 coding agent가 작업한다면 copy-on-write filesystem뿐 아니라 **memory state까지 sibling-aware deduplication**하는 구조가 앞으로 중요해질 가능성이 있습니다.

다만 이건 prototype system 연구입니다. container runtime, VM isolation 수준, NUMA topology, swap configuration에 따라 효과가 크게 달라질 수 있으므로 8.7배를 일반적인 Agent workload 수치로 받아들이면 안 됩니다.

원문: [논문 · Memory Compression for High-Fanout Agent Sandboxes / AgentZip](https://arxiv.org/pdf/2609.11294)

## 4. GuardedAct: 운영 Agent에서 `LLM → shell` 사이에 digital twin과 blast-radius gate를 넣는다 ★★★★★

**GuardedAct**는 backend 장애를 LLM이 자동 복구할 때 가장 위험한 부분을 직접 다룹니다. 모델이 remediation command를 잘 생성하더라도 production에서 바로 실행하면 잘못된 restart, scaling, routing 변경이 cascading failure를 만들 수 있습니다. 연구진은 그래서 LLM과 production 사이에 **sandbox-first verification layer**를 넣었습니다. :chatgpt-content-reference{index="14"}

구조는 명확합니다.

`Diagnosis + live topology + telemetry`
→ `LLM candidate actions`
→ `digital-twin sandbox simulation`
→ `blast-radius / risk estimation`
→ `rollback-confidence gate`
→ `low-risk만 자동 실행, 나머지는 human escalation`

입니다. 즉 LLM이 action을 고르는 것과 **실제 시스템에서 실행해도 되는가**를 완전히 다른 단계로 분리합니다. :chatgpt-content-reference{index="15"}

DeathStarBench social-network application의 5개 fault scenario에서 overall recovery rate는 **87.4%**, direct LLM execution의 collateral damage 25.6%를 **5.2%로 낮춰 79.7% 감소**시켰습니다. 그 대가로 sandbox 검증 때문에 mean time to recovery가 약 8초 늘었습니다. :chatgpt-content-reference{index="16"}

Production infra Agent에서는 이 trade-off가 꽤 합리적입니다. 8초 더 빨리 recovery하는 것보다 잘못된 `kubectl delete`, scaling, traffic shift 때문에 blast radius가 커지는 비용이 훨씬 클 수 있기 때문입니다.

이 원리는 microservice에만 국한되지 않습니다. 데이터베이스 migration, CI/CD, GPU cluster operations, model deployment에도 적용할 수 있습니다. 예를 들어 `restart vLLM`이라는 action을 바로 실행하지 않고 현재 active request, replica 수, GPU memory, failover endpoint를 clone/simulation 환경에서 먼저 평가한 뒤 rollback path가 준비됐는지 확인할 수 있습니다.

다만 실험이 DeathStarBench의 5개 fault scenario에 한정되므로 복잡한 production topology에서도 87.4%가 유지된다고 볼 수는 없습니다. digital twin이 실제 environment를 얼마나 정확하게 반영하는지가 이 방식의 가장 큰 한계이자 관찰 포인트입니다.

원문: [논문 · GuardedAct: Blast-Radius-Aware Sandboxing for AI Remediation](https://arxiv.org/abs/2609.11264)

## 5. MoE의 숨은 약점: 데이터를 반복 학습하면 Dense보다 더 빨리 overfit할 수 있다 ★★★★★

**Data Scarcity and Model Sparsity**는 MoE scaling을 할 때 꽤 불편한 결과를 보여줍니다. 같은 데이터를 반복해서 학습하는 상황에서 MoE는 dense Transformer보다 **더 빠르게 degradation**했고, sparsity와 total parameter가 커질수록 이 현상이 강해졌습니다. 연구는 80M~1B active parameter, 최대 8.5B total parameter 범위를 조사했습니다. :chatgpt-content-reference{index="18"}

80M dense model은 데이터를 **8회 이상 반복해도** degradation이 작았지만 MoE는 약 **4회 반복부터 성능 저하**가 나타났습니다. 반복이 32회에 도달하면 all-unique-data 조건에서 갖던 MoE의 이점을 잃고 dense model보다도 떨어질 수 있었습니다. routing은 학습 초기에 빠르게 고정됐고 expert specialization이 강해지는 것이 반복 데이터 overfitting과 상관관계를 보였습니다. :chatgpt-content-reference{index="19"}

흥미롭게도 strong masking regularization을 사용하면 64회 이상 반복에서도 MoE가 dense보다 우위를 유지할 수 있었습니다. 하지만 **unique data로 학습한 성능까지 완전히 복구한 방법은 없었습니다.** :chatgpt-content-reference{index="20"}

이 결과는 앞으로 데이터 부족이 심해질수록 중요해질 수 있습니다. MoE는 FLOPs 관점에서 효율적이지만 전체 parameter capacity가 크기 때문에 동일한 training sample을 반복하면 expert들이 domain-specific pattern을 너무 빨리 memorization하는 방향으로 갈 가능성이 있습니다.

따라서 MoE pretraining에서는 `tokens / active parameter`뿐 아니라 **`unique tokens / total parameters`, repetition count, expert routing entropy**를 같이 기록하는 편이 더 적절할 수 있습니다. Synthetic data를 섞는 경우에도 동일 template나 generator-induced pattern이 과도하게 반복되지 않는지 봐야 합니다.

주의할 점은 최대 규모가 8.5B total parameter이므로 수백B급 frontier MoE에서도 동일 threshold인 “4×, 32×”가 유지된다고 볼 수는 없습니다. 이 논문의 가치는 특정 숫자보다 **sparsity와 data repetition 사이에 명확한 interaction이 있다**는 데 있습니다.

원문: [논문 · Data Scarcity and Model Sparsity: Mixtures-of-Experts Overfit More to Repeated Data](https://arxiv.org/abs/2609.11917)

## 6. “PTQ가 왜 이렇게 잘 버티는가?” — pretrained Transformer가 quantization error를 층별로 일부 상쇄한다 ★★★★★

**Why Does Post-Training Quantization Work?**는 매우 기본적이지만 지금까지 의외로 설명이 약했던 질문을 다룹니다. Weight를 low precision으로 바꾸면 매 layer마다 hidden-state error가 새로 들어가므로 직관적으로는 depth가 깊어질수록 오차가 계속 누적돼야 합니다. 실제로 random initialization model에서는 그렇게 됩니다. 그런데 pretrained model은 quantization 후에도 downstream 성능이 놀라울 정도로 유지됩니다. :chatgpt-content-reference{index="22"}

연구진은 두 가지 메커니즘을 제시합니다. 첫째, 어떤 layer가 새로 만드는 quantization error가 **이전 layer에서 들어온 error와 반대 방향을 가지는 경향**이 있어서 부분적으로 상쇄됩니다. 이 residual error-cancellation behavior는 pretraining 과정에서 형성됐고 random model에서는 나타나지 않았습니다. 둘째, 최종 LM head의 geometry가 모든 logit을 동일하게 보호하는 것이 아니라 **상위 rank token의 score와 probability를 더 안정적으로 유지**합니다. :chatgpt-content-reference{index="23"}

이 관점은 quantization benchmark를 조금 다르게 보게 합니다. Weight reconstruction error가 크더라도 실제 hidden-state error가 다음 layer에서 상쇄될 수 있고, logit 전체가 조금 움직여도 top-ranked token order가 유지된다면 generation 결과는 거의 변하지 않을 수 있습니다.

따라서 PTQ를 평가할 때 `MSE(weight)` 하나만 보는 것보다 `layerwise hidden-state error`, `error cosine`, `top-k logit rank stability`, 최종 task accuracy를 같이 측정하는 것이 더 설명력이 있을 수 있습니다.

다만 이것은 **“어떤 양자화든 안전하다”는 이론이 아닙니다.** 특정 layer나 gate가 outlier-sensitive하거나 FP4/W4A4에서 activation noise가 강해지면 이 상쇄 구조가 깨질 수 있습니다. 오히려 앞으로 quantization calibration에서는 “어떤 layer가 error를 스스로 흡수하고 어떤 layer가 error를 증폭하는가?”를 기준으로 precision을 비균일하게 배분하는 방향으로 연결될 가능성이 있습니다.

원문: [논문 · Why Does Post-Training Quantization Work?](https://arxiv.org/abs/2609.11716)

## 7. COBRA-Skills: Agent skill 최적화를 brute-force eval 대신 contextual bandit 문제로 바꾼다 ★★★★☆

Agent에게 reusable skill을 만들어주는 방식이 늘어나고 있지만 skill version 하나를 바꿀 때마다 전체 benchmark를 실행하면 비용이 금방 커집니다. **COBRA-Skills**는 이 문제를 skill candidate에 제한된 eval budget을 어떻게 배분할 것인가라는 **contextual-bandit optimization**으로 바꿉니다. :chatgpt-content-reference{index="25"}

Framework는 과거 execution evidence를 보고 성능이 좋아질 가능성이 있거나 아직 정보가 부족한 skill candidate를 우선 평가하고, 결과를 이용해 다시 skill population을 수정합니다. 모든 후보를 균등하게 benchmark하는 대신 **promising 또는 informative candidate에 계산 budget을 집중**하는 방식입니다. :chatgpt-content-reference{index="26"}

6개 heterogeneous Agent benchmark와 3개 target model에서 비교 방법 중 평균 성능이 가장 높았고, SkillOpt 대비 optimization cost를 **55~58% 감소**시켰다고 보고합니다. benchmark당 unique optimization example도 50개만 사용했습니다. Harness가 바뀌어도 비교적 robust했고 target model 자체가 skill generation과 refinement를 수행해도 효과가 유지됐습니다. :chatgpt-content-reference{index="27"}

이 아이디어는 prompt optimization에도 그대로 적용 가능합니다. 예를 들어 `Reviewer Skill v1~v20`을 전부 task 500개에서 평가하는 대신 초기 sample에서 candidate를 비교하고 uncertainty와 reward estimate가 높은 후보에 benchmark budget을 더 배분할 수 있습니다.

Agent skill library가 커지기 시작하면 skill authoring보다 **skill-selection / skill-evolution / eval-budget allocation**이 더 큰 문제가 될 가능성이 있습니다.

다만 55~58%라는 비용 절감은 SkillOpt 대비 특정 benchmark/optimization setting의 결과입니다. Production workload에서 benchmark noise가 크거나 task distribution이 자주 변하면 bandit이 잘못된 candidate에 budget을 몰아줄 수도 있으므로 independent holdout evaluation은 여전히 필요합니다.

원문: [논문 · COBRA-Skills: Contextual Bandit-Guided Evolution for Agent Skill Optimization](https://arxiv.org/abs/2609.11682)

## 8. RAG-Safety-Bench: 안전한 base model + 신뢰 문서 RAG라고 해서 안전성이 유지되는 것은 아니다 ★★★★★

EMNLP 2026 main conference에 채택된 **RAG-Safety-Bench**는 RAG 보안을 꽤 깔끔하게 분리해 평가합니다. 일반 RAG safety benchmark에서는 retriever가 잘못된 문서를 가져온 것인지, 올바른 문서를 가져왔는데 generation이 위험해진 것인지 구분하기 어렵습니다. 이 연구는 retrieval quality를 통제하기 위해 네 조건을 별도로 만듭니다. non-RAG, harmful answer를 직접 포함한 oracle document, 관련은 있지만 직접 답은 없는 document, 그리고 random safe document입니다. :chatgpt-content-reference{index="29"}

5개 open-source LLM에서 테스트한 결과 **base model의 safety guardrail이 RAG pipeline 전체의 safety를 보장하지 않았습니다.** 더 흥미로운 것은 일부 모델에서는 harmful information이 없는 benign retrieval document만 추가해도 unsafe generation 가능성이 올라갔다는 점입니다. :chatgpt-content-reference{index="30"}

이 결과가 중요한 이유는 기업 RAG에서 “우리 문서만 검색하니 신뢰할 수 있다”는 가정을 자주 하기 때문입니다. 신뢰된 PDF나 wiki도 질문과 함께 context에 들어갔을 때 모델의 refusal boundary를 움직일 수 있습니다. 즉 문서 자체가 악성 prompt injection을 포함하지 않아도 **retrieval context가 safety behavior를 변화시키는 변수**가 됩니다.

따라서 RAG 평가에서는 retrieval accuracy와 answer accuracy만 볼 게 아니라 `non-RAG refusal`, `retrieval-enabled refusal`, `unsafe completion rate`, `document provenance`, `retrieved-context class`를 같이 측정해야 합니다. High-risk domain이라면 generation 직전과 이후에 별도의 deterministic policy/safety classifier를 두는 편이 낫습니다.

다만 현재 연구는 5개 open-source 모델에 기반합니다. 상용 frontier model이나 production RAG stack에서 같은 정도의 degradation이 발생한다고 일반화할 수는 없습니다. 핵심은 **base-model safety certification을 RAG application safety certification으로 대신할 수 없다는 것**입니다.

원문: [논문 · RAG-Safety-Bench: Reliable Evaluation of Retrieval-Augmented LLM Safety](https://arxiv.org/abs/2609.11758)

# 오늘 직접 해볼 만한 실습 — `KV Load vs Recompute Break-even Curve` 만들기

오늘은 vLLM 환경에서 **prefix cache의 손익분기점을 직접 측정**하는 실험이 가장 좋습니다. 동일 모델로 prefix 길이를 `4K / 8K / 16K / 32K / 64K / 80K` 정도로 바꾸고, 각 길이에서 **① GPU recompute, ② CPU KV load, ③ NVMe KV load** 세 조건의 TTFT를 비교합니다.

각 run에서는 `prefix tokens`, `TTFT`, `prefill tok/s`, `cache load time`, `CPU→GPU DMA`, `NVMe read time`, `queue wait`, `GPU utilization`을 남기고, 세 곡선이 교차하는 지점을 찾으면 됩니다. 그 결과로 다음과 같은 policy를 만들 수 있습니다.

```text
prefix < X tokens      → RECOMPUTE
X ≤ prefix < Y tokens  → LOAD FROM DRAM
prefix ≥ Y tokens      → PRELOAD FROM NVMe
```

그다음 concurrency를 `1 / 8 / 32`로 바꿔 같은 곡선을 다시 그려보십시오. 중요한 점은 **break-even이 GPU 모델이나 storage bandwidth뿐 아니라 queue 상태에 따라서도 움직이는지** 확인하는 것입니다.

이 실험을 제대로 해두면 “prefix caching을 켰더니 빨라졌다” 수준이 아니라 **어떤 workload에서 어떤 cache tier를 선택해야 하는지 설명할 수 있는 serving policy**까지 만들 수 있습니다. :chatgpt-content-reference{index="35"}
