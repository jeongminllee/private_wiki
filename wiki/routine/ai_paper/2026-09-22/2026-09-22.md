## 1. AWS Strands Harness 공개 — Agent SDK 위에 `Context + Memory + Skills + Subagent + Verification`을 기본값으로 얹는다 ★★★★★

AWS Strands 팀이 **Strands Harness**를 공개했습니다. 기존 Strands Agents SDK가 Agent loop의 building block이었다면, 새 Harness는 처음부터 작동하는 **fully assembled agent**입니다. Python에서는 `create_harness()` 하나로 시작하며 Amazon Bedrock이 기본 provider지만 Anthropic, OpenAI, Google, Ollama 등으로 model backend를 바꿀 수 있습니다. :chatgpt-content-reference{index="0"}

기본 구성이 흥미롭습니다. shell·read/write/edit·web tool이 들어가고, system prompt는 `먼저 탐색 → 변경 → irreversible action 확인 → 완료 전 검증` 흐름을 기본으로 합니다. 긴 tool output은 active context에서 분리하고 재사용되는 request 부분은 prompt caching하며, session ID를 통해 이전 실행을 복원하고 장기 memory를 유지합니다. Open-ended 작업은 내장 generalist subagent에 넘기고 Agent Skills와 MCP도 사용할 수 있습니다. :chatgpt-content-reference{index="1"}

이 발표에서 가장 중요한 것은 AWS가 또 하나의 Agent framework를 만들었다는 사실보다 **“SDK와 Harness는 다른 제품”이라는 구분**입니다. Agent loop가 돌아간다고 production harness가 완성되는 것이 아닙니다.

`Agent SDK`
→ model 호출 / tool dispatch

`Agent Harness`
→ context policy / memory / verification / session / skill / subagent / observability

로 abstraction이 올라가고 있습니다.

또 Strands는 opinionated default를 주지만 반환값은 일반 Strands Agent라 모든 component를 교체할 수 있게 했습니다. Production에서는 이 방식이 black-box managed Agent보다 실험하기 좋습니다. 특정 context strategy나 verifier 하나만 바꿔 같은 model에서 A/B할 수 있기 때문입니다.

다만 AWS가 제시한 다른 harness 대비 비용·token 효율 수치는 자사 benchmark 결과이고 일부 비교 benchmark는 이미 newer version이 나온 상태라, 해당 수치를 그대로 일반화하기보다는 **같은 model·같은 task에서 harness만 고정 비교**하는 편이 맞습니다.

원문: [공식 문서 · Strands Harness](https://strandsagents.com/docs/user-guide/harness/?utm_source=chatgpt.com) · [GitHub · strands-agents/harness-sdk](https://github.com/strands-agents/harness-sdk)

## 2. “좋은 Agent Harness에서 실제로 돈값 하는 것은 무엇인가?” — Verifier가 거의 모든 false-pass 방어 효과를 가져갔다 ★★★★★

신규 논문 **How Do Agent Harnesses Create Value?**는 Agent harness를 planning과 verification으로 분해해 꽤 좋은 controlled experiment를 했습니다. Planning 문장이 많아서 좋아진 것인지, 실제 plan 정보가 있어서 좋아진 것인지 구분하기 위해 **task-specific plan과 길이를 동일하게 맞춘 shuffled policy text**를 비교했습니다. :chatgpt-content-reference{index="4"}

265개 matched condition에서 실제 plan은 oracle-verified success를 평균 **+7.17 percentage points** 개선했습니다. 효과는 복잡한 task에 집중됐습니다. 그런데 verifier 결과가 더 흥미롭습니다. Read-only terminal verifier는 잘못된 episode의 **61%를 reject**했지만 동시에 올바른 episode의 **17%도 보류**했습니다. 추가 비용은 episode당 1센트 미만이었습니다. :chatgpt-content-reference{index="5"}

연구진이 내린 중요한 결론은 **오류 비용이 높은 환경에서는 standalone verifier가 planning+verification stack의 false-pass 감소 효과 대부분을 훨씬 싼 비용으로 얻을 수 있다**는 것입니다. 즉 Agent architecture를 복잡하게 만든다고 항상 가치가 추가되는 것이 아닙니다.

실무에서는 다음과 같이 해석하는 편이 좋습니다.

`Planner → Agent → Reviewer → Critic → Manager`

처럼 Agent를 계속 추가하기 전에,

`Agent → deterministic/read-only verifier`

가 실패의 상당 부분을 막는지 먼저 측정해야 합니다.

특히 파일 변경, 코드 분석, 배포 같은 작업은 최종 산출물을 test/static analyzer/schema validator가 싸게 검증할 수 있습니다. 이 경우 verifier에 투자하는 편이 새로운 reasoning Agent 하나를 붙이는 것보다 ROI가 클 수 있습니다.

반대로 false reject 17%는 작지 않습니다. Chat assistant에서는 사용자 경험을 나쁘게 만들 수 있지만, 배포·금융·보안 분석처럼 **false positive보다 false acceptance 비용이 큰 작업**에서는 합리적인 trade-off일 수 있습니다.

원문: [논문 · How Do Agent Harnesses Create Value? Planning Information and Release Control in Stateful LLM Agents](https://arxiv.org/abs/2609.20474)

## 3. LLM Autoscaling을 `GPU util 80% 넘으면 replica 추가`에서 **TTFT·ITL SLO 기반 Queueing Model**로 바꾼다 ★★★★★

GPU 인프라 쪽에서 오늘 가장 볼 만한 연구는 **An Approximate Queueing Model of LLM Inference Serving for SLO-Driven Autoscaling**입니다.

연구진은 model-accelerator pair를 크게 세 parameter로 표현합니다.

`baseline iteration overhead`  
`per-token compute cost`  
`per-token KV-cache access cost`

그리고 continuous batching에서 batch occupancy가 변하는 과정을 state-dependent Markov chain으로 모델링해 **TTFT와 ITL을 직접 예측**합니다. :chatgpt-content-reference{index="7"}

H100에서 Llama-3.1-8B와 Qwen2.5-14B를 측정한 결과 평균 ITL prediction error는 각각 약 **5%, 8%**, TTFT는 약 **14%, 16%**였습니다. 이 모델을 autoscaling controller에 넣어 OpenShift H100 cluster에서 traffic을 4배까지 ramp시켰을 때 127번 control cycle 가운데 SLO를 놓친 것은 7회였고, controller 내부 TTFT·ITL prediction median error도 각각 최대 약 5%, 9%였습니다. 비교한 throughput-only analyzer는 128 cycle 중 27회를 놓쳤습니다. :chatgpt-content-reference{index="8"}

이 연구의 중요한 점은 replica 수를 결정할 때 **throughput capacity만 보면 안 된다는 것**입니다.

예를 들어 현재 1 GPU가 100 req/s를 처리하고 load가 80 req/s라고 해서 80% 여유가 있는 것이 아닙니다. Input length가 길어져 prefill queue가 쌓이면 TTFT SLO는 이미 깨질 수 있고, long-context request가 많으면 KV read 때문에 ITL이 먼저 악화될 수도 있습니다.

따라서 production autoscaler의 control variable은

`GPU utilization`

보다

`P95 TTFT ≤ SLO`
`P95 ITL ≤ SLO`

에 가까워져야 합니다.

주의할 점은 이 모델이 Markovian approximation이고 검증 범위가 light~moderate load 중심이라는 것입니다. Bursty Agent traffic, heterogeneous multimodal requests, very-long context에서는 오차가 더 커질 수 있습니다. 그래도 **model-specific calibration을 몇 개의 observable latency parameter로 압축해 autoscaler에 넣는다**는 방향은 상당히 실용적입니다.

원문: [논문 · An Approximate Queueing Model of LLM Inference Serving for SLO-Driven Autoscaling](https://arxiv.org/abs/2609.20957)

## 4. Qwen‑Image‑2.1 공개 — 7B DiT에 `Prefix KV Cache + Continuous Batching + TP`까지 들어온다 ★★★★★

Qwen 팀은 **9월 20일 Qwen‑Image‑2.1**을 공개했습니다. Visual generation component는 **7B parameter, 32-layer Single-Stream DiT**이며 text-to-image와 image editing을 하나의 model에 통합합니다. Native RGBA transparency를 지원하고 reference image를 최대 10개까지 받을 수 있습니다. :chatgpt-content-reference{index="10"}

아키텍처에서 재미있는 부분은 attention입니다. Text에는 token-level causal mask를, image block에는 chunk-level bidirectional mask를 사용하는 block-causal 구조이며, Qwen3-VL 8B가 text instruction과 condition image를 unified representation으로 encode합니다. VAE는 64-channel RGBA에 16× spatial compression을 사용합니다. :chatgpt-content-reference{index="11"}

엔지니어 입장에서는 모델 품질보다 **serving stack**이 더 흥미롭습니다. Editing에서는 condition image와 text prefix가 denoising step마다 동일하므로 첫 step에서 계산한 prefix KV를 재사용합니다. vLLM-Omni는 이를 cross-step prefix caching과 CUDA Graph, FP8, tensor parallelism, Ulysses parallelism, step-level continuous batching으로 가속합니다. SGLang-Diffusion도 day-one으로 multi-GPU parallelism과 offload를 지원합니다. :chatgpt-content-reference{index="12"}

즉 image generation serving도 점점 LLM serving과 비슷해지고 있습니다.

`Repeated static context`
→ KV reuse

`여러 동시 generation`
→ continuous batching

`큰 DiT`
→ TP / sequence parallel

`GPU memory 부족`
→ component offload

이 convergence는 향후 unified multimodal serving engine에서 꽤 중요합니다.

Qwen의 자체 benchmark에서는 강한 경쟁력을 주장하지만 그 수치는 vendor benchmark입니다. 오히려 지금 바로 검증 가능한 것은 **7B visual core, 2K generation, native RGBA, multi-reference editing, 그리고 vLLM/SGLang의 실제 serving support**입니다.

## 5. Plugin4Shell — “SHA로 pin했으니 안전하다”가 깨졌다: Coding Agent plugin supply chain의 첫 대형 경고 ★★★★★

AIR Security가 공개한 **Plugin4Shell**은 Claude Code, Codex, Copilot, Gemini CLI의 plugin loading에서 발견된 zero-click RCE 계열 취약점입니다. 핵심은 매우 단순하면서 위험합니다. Plugin marketplace가 특정 **commit SHA**를 pin해도 Agent가 checkout 이후 **실제로 그 commit에 도착했는지 다시 검증하지 않았습니다.** 공격자가 SHA처럼 보이는 이름의 branch를 만들 수 있는 Git host를 이용하면 reviewed commit 대신 attacker-controlled code가 실행될 수 있었습니다. :chatgpt-content-reference{index="15"}

문제가 더 큰 이유는 일부 coding Agent가 marketplace plugin을 background에서 자동 update하기 때문입니다. 사용자가 새 plugin을 직접 설치하지 않아도 update path를 통해 malicious version이 실행될 수 있으므로 연구진은 zero-click이라고 분류했습니다. :chatgpt-content-reference{index="16"}

공개 시점 기준 AIR에 따르면 Claude Code는 **2.1.179**, Codex는 **0.146.0**에서 수정됐습니다. GitHub는 GitHub-hosted repository에서는 SHA처럼 생긴 branch/tag 생성을 차단하기 때문에 해당 공격 경로가 성립하지 않는다고 설명했지만, AIR 측은 Bitbucket이나 self-hosted Git backend까지 지원하는 환경에서는 risk가 남을 수 있다고 반박했습니다. 따라서 제품별 상태는 vendor·hosting topology까지 같이 봐야 합니다. :chatgpt-content-reference{index="17"}

이 사건의 가장 중요한 교훈은 **“pinning value를 저장했다”와 “실제 실행 artifact를 검증했다”는 다르다**는 것입니다.

Plugin/Skill 설치 시 최소한

`requested SHA`
→ checkout
→ `git rev-parse HEAD`
→ exact equality verification
→ artifact hash/signature
→ 실행

순서가 필요합니다.

Agent Skills가 `README/Markdown`을 넘어 executable helper·script·plugin으로 커지면 package manager 수준의 supply-chain control이 필요합니다. 단순히 trusted marketplace에서 가져왔다는 사실만으로는 부족합니다.

원문: [보안 연구 · AIR Security — Plugin4Shell](https://www.air.security/blog-posts/plugin4shell?utm_source=chatgpt.com) · [보조 확인 · The Register — Vendor response and patch status](https://assets.theregister.com/2026/09/17/202619/?utm_source=chatgpt.com)

## 6. EvoSkill‑GUI — Agent Skill도 배포 후 실패를 보고 **스스로 수정되는 procedural memory**로 바뀐다 ★★★★☆

**Reflect, Revise, Reuse**는 GUI Agent의 Skill을 고정된 script가 아니라 **deployment 중 계속 진화하는 artifact**로 봅니다. GUI Agent의 실제 실패는 reasoning 자체보다 popup, delayed load, widget relocation 같은 environment drift 때문인 경우가 많습니다. Deployment 전에 작성한 skill은 이런 상황을 예측하기 어렵습니다. :chatgpt-content-reference{index="20"}

EvoSkill-GUI에서 하나의 skill은 executable plan뿐 아니라 retrieval metadata, backup localization, failure-recovery rule, accessibility utility, 과거 failure case를 여러 파일에 저장합니다. 실행이 실패하면 isolated critic이 trajectory를 분석하고, executor는 unrestricted source editing이 아니라 **제한된 skill-edit interface**로 문제가 난 파일만 수정합니다. :chatgpt-content-reference{index="21"}

Training 없이 MobileWorld·AndroidWorld·OSWorld에서 각각 최대 **+16.2%, +6.0%, +10.5%** 개선됐고, 수정된 skill은 동일 task에만 쓰이지 않고 관련 task에도 재사용됐습니다. :chatgpt-content-reference{index="22"}

이 패턴은 GUI에만 국한되지 않습니다.

예를 들어 deployment skill이

`vLLM 실행 → health check → benchmark → report`

를 담고 있는데 새로운 vLLM version에서 flag가 바뀌었다면, 매번 model을 fine-tune할 필요 없이 **skill artifact 자체를 수정하고 regression test를 거쳐 재사용**할 수 있습니다.

다만 self-modifying skill에는 governance가 필요합니다. 실패한 Agent가 자신이 실패를 평가하고 자기 지침까지 마음대로 바꾸게 하면 오류가 고착될 수 있습니다. EvoSkill이 critic isolation과 restricted edit surface를 사용한 이유가 바로 여기 있습니다.

원문: [논문 · Reflect, Revise, Reuse: Training-Free Skill Evolution for GUI Agents](https://arxiv.org/abs/2609.17653)

## 7. V7의 “Institutional Memory” 사례 — RAG에서 `문서 검색`보다 Entity/Relation Graph가 Agent 비용을 줄이는 이유 ★★★★★

OpenAI가 9월 21일 공개한 V7 사례는 enterprise Agent memory 관점에서 꽤 볼 만합니다. V7 Go는 GPT‑5.6 Luna를 이용해 수백만 파일에서 entity, relationship, fact, metric을 추출해 **Context Graph**를 만들고, 원문 citation을 연결합니다. Agent는 모든 질문마다 PDF를 처음부터 다시 검색하지 않고 구조화된 graph를 먼저 조회하고, 정보가 부족할 때만 원문 RAG로 내려갑니다. :chatgpt-content-reference{index="24"}

여기서 핵심은 memory를 `chat history`로 보지 않는 것입니다.

`Documents`
→ entity/fact extraction
→ graph
→ cited evidence
→ Agent query

형태로 **회사 자체의 semantic state를 외부화**합니다.

V7 설명에 따르면 최근 대화는 model context에 남기고 오래된 내용은 graph로 이동시켰다가 필요할 때 retrieve합니다. V7 내부 HERB 평가에서 retrieval-only system이 official baseline보다 69% 높은 결과를 기록했고 unanswerable query hallucination은 38% 감소했다고 합니다. 다만 이는 V7/OpenAI가 공개한 자체 평가입니다. :chatgpt-content-reference{index="25"}

Model routing도 흥미롭습니다. Structured extraction은 Luna, reasoning/tool-use는 Terra·Sol, 가장 어려운 Context Graph query는 Astra를 사용합니다. V7은 GPT‑5.6 Luna 사용으로 이전 GPT‑5.4 mini 대비 문서당 비용을 78% 줄였고, Responses API로 옮긴 일부 PDF-heavy workflow에서는 token 사용량이 약 5% 감소했다고 보고합니다. :chatgpt-content-reference{index="26"}

이런 architecture가 의미하는 것은 production Agent의 memory가 결국 세 층으로 나뉠 가능성이 높다는 점입니다.

`Active context` — 현재 trajectory  
`Structured institutional memory` — 장기 사실·관계  
`Raw source/RAG` — 검증용 원본

모든 것을 vector DB 하나에 던져 top-K retrieval하는 구조보다 훨씬 관리하기 쉽고 provenance도 명확합니다.

원문: [공식 사례 · OpenAI — How V7 gives AI agents institutional memory](https://openai.com/index/v7/)

# 오늘 직접 해볼 만한 실습 — B200 로그로 `SLO-Aware Autoscaler`의 3개 parameter 추정하기

오늘은 새로운 모델을 돌리기보다 기존 vLLM benchmark 데이터를 이용해 **간단한 serving performance model을 만들어보는 것**이 좋습니다.

TP1과 TP2 각각에서 input/output 길이와 concurrency를 몇 가지 바꾸면서 `TTFT`, `TPOT 또는 ITL`, `active sequences`, `input tokens`, `KV usage`를 저장합니다. 그다음 모델-accelerator configuration마다 다음 세 coefficient를 fitting합니다.

```text
C0      = iteration 고정 overhead
Ccomp   = token당 compute cost
Ckv     = active KV token당 memory-access cost
```

첫 번째 목표는 완벽한 queueing model 구현이 아니라 **이 세 parameter만으로 실제 TTFT/ITL의 방향을 얼마나 설명할 수 있는지** 보는 것입니다.
