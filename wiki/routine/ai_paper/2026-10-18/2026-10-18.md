## 1. Anthropic이 Git을 버리고 자체 Source Control을 만든 이유 ★★★★★

**이번 주 가장 중요한 인프라 사례입니다.**

Anthropic은 10월 13일, Claude 기반 개발량이 급증하면서 Git이 개발 인프라의 병목이 되었고, 자체 version-control system인 **Scion**으로 monorepo를 완전히 이전했다고 공개했습니다. 10월 15일 글을 업데이트하면서 세부 구현도 추가했습니다. [Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)

### 무엇이 바뀌었나

Anthropic의 하루 merge 규모가:

- 2026년 5월: 약 **2,500건/day**
- 2026년 9월: **30,000건/day 이상**

으로 10배 이상 증가했습니다. [Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)

문제는 단순한 commit 수가 아닙니다.

Anthropic monorepo의 main history만 거의 **100GB**, 압축 working copy가 25GB 이상이고, CI에서 하루 약 **2,500만 번의 checkout**이 발생합니다. 단순한 Git 방식으로 계산하면 하루 600PB가 넘는 Git traffic이 발생할 수 있다고 설명합니다. [Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)

그래서 Scion은 Git의 핵심 가정을 뒤집었습니다.

```text
기존 Git

Client
 ├─ full repository
 ├─ local history
 ├─ local commit
 └─ push
```

에서

```text
Scion

Agent / CI
    │
    ▼
Source Control Service
    │
 ┌──┼───────────────┐
 ▼  ▼               ▼
diff merge       history
API   API           API
```

방식으로 이동했습니다.

### 왜 중요한가

**AI coding agent가 많아지면 source control 자체가 distributed systems 문제가 됩니다.**

특히 agent는 인간과 달리:

- 거의 항상 online이고
- 매우 많은 checkpoint/commit을 만들고
- 동시에 수백~수천 개가 실행되며
- repository 전체를 로컬에 보유할 필요가 없고
- API로 diff/history만 조회해도 되는 경우가 많습니다.

따라서 Git의 **offline-first / fully replicated client**라는 설계 철학이 agent workload에는 반드시 최적은 아닙니다. [Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)

### 실제 적용

Coding Agent infrastructure를 직접 만든다면 source control을 단순한 `git clone → 작업 → push`로 설계하지 않는 것이 좋습니다.

다음과 같이 생각할 수 있습니다.

```text
Agent
 ↓
Ephemeral Workspace
 ↓
Sparse / Virtual Checkout
 ↓
Source Control API
 ↓
Patch / Diff
 ↓
CI
```

특히 agent가 repository 전체를 clone하지 않고 **필요한 파일만 materialize**하는 구조는 대규모 agent fleet에서 매우 중요해질 수 있습니다.

### 주의할 점

Anthropic의 workload는 일반적인 회사보다 훨씬 극단적입니다. 따라서 **“모든 기업이 지금 Git을 버려야 한다”는 결론은 아닙니다.**

오히려 지금 봐야 할 것은:

> “우리 조직에서 agent concurrency가 얼마까지 증가하면 Git/CI/checkout이 병목이 되는가?”

입니다.

**후속 관찰 포인트**

- Git worktree/sparse checkout으로 얼마나 버틸 수 있는가
- agent 수 증가에 따른 checkout latency
- CI clone/fetch traffic
- merge queue contention
- source-control API화의 효과

**원문**

[공식 기술 발표 · Anthropic Scion](https://www.anthropic.com/engineering/redesigning-source-control)

# 2. GitHub도 agent-scale Git 인프라를 다시 만들고 있다 ★★★★★

Anthropic 사례가 특정 회사의 극단적인 사례라면, GitHub의 자료는 **전체 Git 생태계에서 같은 문제가 발생하고 있음을 보여줍니다.**

GitHub는 10월 6일 agent-scale software development를 위한 Git infrastructure 재설계를 공개했습니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

### 숫자가 상당히 크다

2025년 9월 → 2026년 8월 사이 Git activity가:

**218.2B → 473.3B events/month**

으로 증가했습니다.

또 2026년 9월에는 개발자와 agent가 GitHub에서 만든 commit이:

**7.38B commits**

에 달했고, 전년 대비 5배 이상 증가했습니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/?utm_source=chatgpt.com)

Push는 약 **4.9× YoY**, PR merge는 거의 **4×**, GitHub Actions 실행은 약 **3.26B/month**까지 증가했습니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/?utm_source=chatgpt.com)

### 중요한 포인트

Git infrastructure의 문제는 단순 read scaling이 아닙니다.

```text
Read

Agent → clone
       ↓
     cache
       ↓
     replica

상대적으로 쉽다.
```

하지만 write는:

```text
Agent 1 ─┐
Agent 2 ─┤
Agent 3 ─┤
Agent N ─┘
     ↓
   Push
     ↓
  Ref update
     ↓
   Merge
     ↓
    CI
```

처럼 **동일 repository state에 대한 concurrent mutation**이 발생합니다.

GitHub가 특히 강조하는 것도 이 부분입니다. [The GitHub Blog](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/?utm_source=chatgpt.com)

### 엔지니어에게 중요한 의미

앞으로 coding-agent platform을 설계할 때는:

```text
LLM Serving
+
Sandbox
+
Repository
+
CI
+
Artifact Storage
+
Secrets
+
Observability
```

를 하나의 **Agent Infrastructure Stack**으로 봐야 합니다.

LLM latency를 20% 줄였는데 repository checkout 때문에 agent가 30초 기다린다면 시스템 전체 성능은 개선되지 않습니다.

### 실무 적용

현재 agent workload를 운영한다면 최소한 다음 metric을 분리해서 측정할 것을 권합니다.

| Metric | 의미 |
|---|---|
| model TTFT | LLM 병목 |
| tool latency | tool 병목 |
| checkout latency | source-control 병목 |
| CI queue time | execution 병목 |
| merge latency | coordination 병목 |
| sandbox startup | environment 병목 |

이렇게 해야 **“Agent가 느리다”**를 실제 병목으로 분해할 수 있습니다.

**원문**

[공식 기술 발표 · GitHub Agent-scale Git Infrastructure](https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/)

# 3. NVIDIA OpenShell 0.0.34 보안 업데이트 — Agent Sandbox도 공격면이다 ★★★★★

이건 **오늘 반드시 확인할 항목**입니다.

NVIDIA의 OpenShell은 autonomous agent를 sandbox 안에서 실행하고 파일·syscall·network access를 정책으로 통제하는 runtime입니다. 현재 프로젝트는 0.1.x 계열로 발전했고, kernel-level enforcement와 policy verification을 핵심 구조로 내세웁니다. [GitHub](https://github.com/NVIDIA/OpenShell/blob/main/README.md?utm_source=chatgpt.com)

그런데 8월에 공개된 보안 bulletin에서 OpenShell에 **Critical 9.9 CVSS 취약점**이 포함됐습니다. [GitHub](https://github.com/NVIDIA/product-security/blob/main/2026/5872/5872.md)

### 무엇이 있었나

OpenShell 0.0.33 이하에 대해 다음과 같은 문제가 공개됐습니다.

- CVE-2026-65093 — sandbox escape — **CVSS 9.9**
- CVE-2026-65083 — sandbox provisioning API — **CVSS 9.9**
- CVE-2026-65091 — malicious gateway에 의한 OS command injection
- CVE-2026-65086 — sandbox exec handler command injection

NVIDIA는 OpenShell의 수정 버전으로 **0.0.34**를 지정했습니다. [GitHub](https://github.com/NVIDIA/product-security/blob/main/2026/5872/5872.md)

### 왜 중요한가

여기서 중요한 건 취약점 자체보다 **아키텍처적 교훈**입니다.

Agent sandbox가:

```text
LLM
 ↓
Tool
 ↓
Sandbox
 ↓
Filesystem
Network
Credentials
```

를 보호한다면, sandbox 자체가 compromise될 경우 agent의 권한 경계가 무너집니다.

즉,

> “LLM에게 prompt injection 방어를 넣었다”

만으로는 충분하지 않습니다.

실제 보안 boundary는:

```text
Model policy
      ↓
Agent harness
      ↓
Tool authorization
      ↓
Sandbox
      ↓
Kernel
      ↓
Network / Credential boundary
```

전체에 걸쳐 있어야 합니다.

### 실제 적용

Agent infrastructure에서 다음 세 가지를 분리하세요.

**1. Model-level policy**

LLM에게 무엇을 하지 말라고 하는가.

**2. Tool-level authorization**

agent가 실제로 어떤 API를 호출할 수 있는가.

**3. OS-level enforcement**

agent가 prompt를 무시해도 실제로 무엇을 할 수 있는가.

가장 중요한 것은 **3번은 1번과 독립적으로 동작해야 한다는 것**입니다.

### 주의할 점

OpenShell을 평가하거나 도입한다면 최신 security bulletin과 release version을 먼저 확인해야 합니다.

특히 agent sandbox는 일반 application dependency보다 훨씬 높은 보안 민감도를 가져야 합니다.

**원문**

[공식 보안 bulletin · NVIDIA OpenShell/NemoClaw](https://github.com/NVIDIA/product-security/blob/main/2026/5872/5872.md)  
[GitHub · NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell/blob/main/README.md?utm_source=chatgpt.com)

# 4. ReviewBench — AI Code Review도 이제 “benchmark engineering” 단계로 들어간다 ★★★★★

GitHub가 10월 5일 공개한 ReviewBench는 AI code-review agent를 위한 공개 benchmark입니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

### 무엇이 바뀌었나

ReviewBench는 단순히 bug가 맞았는지를 평가하지 않습니다.

219개 public PR, 187개 repository, 19개 언어를 대상으로 하고, 1억 390만 개의 GitHub PR 분포를 분석해 benchmark corpus를 구성했습니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

Ground truth도 하나의 모델에서 만들지 않았습니다.

```text
Human Review
     +
Static Analysis
     +
Multiple Frontier LLMs
     +
Author Follow-up Changes
     ↓
Candidate Findings
     ↓
Deduplication
     ↓
Human / Calibrated Judge
     ↓
Golden Set
```

### 왜 중요한가

AI code review에서 가장 중요한 문제 중 하나는 **noise**입니다.

예를 들어:

```text
Agent A
Recall = 90%
Precision = 30%

Agent B
Recall = 65%
Precision = 90%
```

어느 쪽이 더 좋은지는 조직의 review philosophy에 따라 달라집니다.

ReviewBench는 그래서:

- grounded precision
- grounded recall
- augmented precision
- augmented recall
- F1 / Fβ

등으로 평가합니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

특히 **golden set에 없던 새로운 finding**도 별도로 평가하는 augmented metric이 중요합니다. 고정된 benchmark의 가장 큰 문제인 “모델이 benchmark보다 똑똑해지면 어떻게 평가할 것인가?”를 다루기 때문입니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

### 실무 적용

Coding Agent를 개발하고 있다면 benchmark를 다음 구조로 가져가는 것을 추천합니다.

```text
Prompt / Model / Tool 변경
            ↓
       Offline Eval
            ↓
 ┌──────────┼──────────┐
 ↓          ↓          ↓
Precision  Recall     Cost
            ↓
        Regression?
            ↓
        Production
```

즉 **agent system도 CI에서 regression testing해야 합니다.**

### 검증 결과도 흥미롭다

GitHub는 ReviewBench offline 결과와 production A/B test의 방향성이 일치했다고 보고했습니다.

한 ensemble review 실험에서:

- addressed rate: **+8.0%**
- recall: **+13.6%**
- comment volume: **+61%**
- cost/review: **−8.0%**

가 production에서 관찰됐다고 설명합니다. [The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

다만 이것은 **GitHub 내부의 자체 실험 결과**이므로 독립적인 재현과는 구분해야 합니다.

**원문**

[공식 발표 · ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

# 5. Claude Haiku 5.5 — Agent architecture에서 “작은 모델을 많이 쓰는 구조”가 더 현실적으로 변했다 ★★★★☆

Anthropic은 10월 7일 **Claude Haiku 5.5**를 공개했습니다. 핵심은 단순한 신형 모델 출시가 아니라 **agent workload의 cost architecture 변화**입니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com)

### 핵심 변화

Anthropic에 따르면 Haiku 5.5는 Haiku 4.5 대비:

- 요청당 가격 최대 **90% 낮음**
- 출력 token 기준도 크게 낮아짐
- 빠른 inference
- adjustable effort
- computer use / browser use 지원

을 제공합니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com)

동시에 Sonnet 5.5의 cache read 가격도 **50% 인하**해 agentic workload 비용을 약 20% 줄였다고 발표했습니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com)

### 왜 중요한가

Agent architecture가 다음처럼 바뀔 수 있습니다.

기존:

```text
User
 ↓
Large Model
 ↓
Tool
 ↓
Large Model
 ↓
Tool
 ↓
Large Model
```

보다:

```text
             ┌→ Haiku ─→ classify
             │
User → Router ┤→ Haiku ─→ retrieve
             │
             ├→ Haiku ─→ summarize
             │
             └→ Sonnet/Opus ─→ hard reasoning
```

즉 **heterogeneous model routing**이 더 경제적입니다.

특히 compaction, classification, routing, subagent 같은 workload를 frontier model에서 분리할 수 있습니다. Anthropic도 Haiku 5.5를 이런 용도로 강조합니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com)

### 실제 적용

Agent scheduler를 설계한다면:

```text
Task Complexity
      ↓
Router
 ┌────┼────┐
 ↓    ↓    ↓
Small Mid  Large
```

형태로 **model selection 자체를 scheduling problem**으로 취급하는 것이 좋습니다.

### 주의할 점

Haiku 5.5가 모든 agent task에서 큰 모델을 대체한다는 의미는 아닙니다.

Anthropic도 복잡한 agentic coding에서는 Sonnet/Opus 계열이 여전히 더 적합하다고 명시합니다. [Anthropic](https://www.anthropic.com/claude-haiku-5-5?utm_source=chatgpt.com)

따라서 모델 가격만 비교하면 안 되고:

\[
\text{Cost / successful task}
=
\frac{\text{Inference Cost}}
{\text{Task Success Rate}}
\]

를 봐야 합니다.

# 6. LFM2.5-24B-A2B — 2B active parameter로 로컬 Agent를 노리는 방향 ★★★★☆

10월 13일 Liquid AI가 공개한 **LFM2.5-24B-A2B**는 로컬/edge AI 관점에서 상당히 흥미롭습니다. [Hugging Face](https://huggingface.co/blog/LiquidAI/lfm25-24b-a2b?utm_source=chatgpt.com)

### 구조

총:

**24B parameters**

하지만 token당 active parameter는 약:

**2.45B**

입니다.

64 experts 중 top-4를 사용하는 MoE 구조이며 context window는 **131K**입니다. [Hugging Face](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B?utm_source=chatgpt.com)

즉:

```text
24B total
 ├─ Expert 1
 ├─ Expert 2
 ├─ ...
 └─ Expert 64

        ↓ routing

~2.45B active / token
```

### 성능보다 더 중요한 부분

이 모델은 agent harness에서 실제로 post-training됐습니다.

Liquid AI는 OpenClaw, Hermes Agent, Pi, OpenCode 등의 harness에서 agentic RL을 수행했다고 공개했습니다. [Hugging Face](https://huggingface.co/blog/LiquidAI/lfm25-24b-a2b?utm_source=chatgpt.com)

또한:

- vLLM
- SGLang
- Transformers
- llama.cpp 계열
- ONNX
- MLX

등 다양한 deployment target을 제공합니다. [Hugging Face](https://huggingface.co/LiquidAI/LFM2.5-24B-A2B?utm_source=chatgpt.com)

### 실제 하드웨어

Liquid AI가 공개한 수치에 따르면:

- Apple M5 Max: 최대 **184 tok/s**
- NVIDIA B300: 최대 **21K output tok/s**

를 제시합니다. [Hugging Face](https://huggingface.co/blog/LiquidAI/lfm25-24b-a2b?utm_source=chatgpt.com)

물론 이 숫자는 모델사 자체 측정치이므로 동일한 workload와 generation setting에서 직접 검증해야 합니다.

### 왜 중요한가

이건 **local agent architecture의 방향성**을 보여줍니다.

앞으로 모든 작업을 cloud frontier model에 보낼 필요가 없어질 수 있습니다.

```text
Local Small Agent
      ↓
Simple Task
      ↓
Local execution

        ↓ hard task

Cloud Frontier Agent
```

### 주의할 점

        +

# 오늘 새 연구 하나 더: Goal Drift를 감시하는 Agent

10월 15일 공개된 **Learning to Steer LLM Agents and Multi-Agent Systems**는 장기 agent execution에서 발생하는 **goal drift**를 다룹니다. [arXiv](https://arxiv.org/abs/2610.22316)

즉 agent가 처음에는:

```text
Goal A
```

를 수행하고 있었지만 여러 tool call 이후:

```text
A → B → C → D
```

로 이동하면서 원래 목표에서 벗어나는 현상입니다.

연구에서는 별도의 **steering agent**가 실행 중간에 개입해 목표 이탈 여부를 판단하고 intervention하도록 합니다. [arXiv](https://arxiv.org/abs/2610.22316)

이 구조는 실제 agent infrastructure에서도 상당히 실용적입니다.

```text
Executor Agent
      ↓
   Tool Call
      ↓
  State Update
      ↓
Steering Agent
      ↓
 Continue / Correct / Stop
```

앞으로 agent monitoring이 단순 log 수집이 아니라 **execution-time control loop**가 될 가능성을 보여줍니다.

[논문 · Learning to Steer LLM Agents](https://arxiv.org/abs/2610.22316)

# 오늘 직접 해볼 만한 실습

## `Agent Infrastructure Bottleneck Profiler` 만들기

오늘은 모델 자체를 학습하지 말고, **agent 전체 실행 시간을 어디에서 소비하는지 측정하는 작은 profiler**를 만드는 것을 추천합니다.

실행 trace를 다음처럼 정의합니다.

```text
agent_run
 ├── model_call
 │    ├── ttft
 │    └── generation_time
 │
 ├── tool_call
 │    └── latency
 │
 ├── repository
 │    ├── checkout
 │    ├── diff
 │    └── commit
 │
 ├── sandbox
 │    └── startup
 │
 └── evaluation
      └── test_time
```

그리고 각 run마다:

```text
total_latency
model_latency
tool_latency
repo_latency
sandbox_latency
evaluation_latency
token_in
token_out
estimated_cost
```

를 기록합니다.

그 다음 **동일한 agent를 1개 → 4개 → 16개 → 64개 concurrent execution**으로 증가시키세요.

측정해야 할 핵심 그래프는:

```text
Concurrency
     │
     ├── Model latency
     ├── Repository latency
     ├── CI latency
     └── Total task latency
```

입니다.

이 실험의 목적은 **“GPU를 더 많이 쓰면 agent가 선형적으로 빨라지는가?”**가 아닙니다.

오히려 오늘의 Anthropic/GitHub 사례를 검증하는 것입니다.

> **agent concurrency가 증가하면 GPU가 아닌 source control, sandbox, CI, synchronization이 새로운 bottleneck이 되는가?**

이 실험은 이후 사용자의 **B200/vLLM infrastructure benchmark**와도 자연스럽게 연결할 수 있습니다. GPU serving 성능을 측정할 때 단순 tokens/sec에서 끝내지 않고, **agent end-to-end throughput과 bottleneck decomposition**까지 확장할 수 있기 때문입니다.

## 오늘의 한 줄 결론

**2026년 10월의 AI 엔지니어링에서 중요한 변화는 “LLM이 코드를 더 잘 쓴다”가 아닙니다.**

이제 실제로는:

```text
              ┌─ LLM
              ├─ Agent Harness
              ├─ Tool Runtime
              ├─ Sandbox
Agent System ─┼─ Source Control
              ├─ CI / Evaluation
              ├─ GPU Scheduler
              ├─ KV Cache
              └─ Security Boundary
```

**전체 execution system이 하나의 새로운 컴퓨팅 플랫폼으로 변하고 있습니다.**

오늘 나온 Anthropic Scion, GitHub agent-scale Git, NVIDIA OpenShell, ReviewBench, Haiku 5.5, LFM2.5, Muse Spark Open을 한꺼번에 보면 이 방향이 상당히 명확합니다.
