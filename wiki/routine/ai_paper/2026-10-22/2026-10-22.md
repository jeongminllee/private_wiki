# AI 엔지니어 데일리 브리핑
### 2026년 10월 22일

오늘은 **“LLM inference engine → distributed inference platform”으로의 계층 상승**이 가장 중요한 흐름입니다.

특히 오늘은 **DeepSeek의 DeepInfer 공개**, **vLLM 0.32.0**, 그리고 **llm-d 1.0을 둘러싼 Kubernetes-native distributed inference**를 하나의 흐름으로 보는 것이 좋습니다. 이 세 가지는 각각 다른 프로젝트처럼 보이지만, 실제로는 **모델 실행·GPU 최적화·라우팅·KV cache·스케줄링을 어디까지 inference platform이 책임질 것인가**라는 같은 문제를 풀고 있습니다.

## 1. DeepSeek이 자체 production inference engine `DeepInfer`를 공개했다 ★★★★★

DeepSeek이 **DeepInfer**를 오픈소스로 공개했습니다. DeepSeek은 이를 자사 대규모 production serving을 구동하는 고성능 inference framework라고 설명하며 Apache-2.0으로 공개했습니다. 현재 공식 저장소에서 지원하는 모델은 **DeepSeek-V4.1-Flash**입니다. [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

핵심 기능은 꽤 공격적입니다.

- Attention DP / balanced CP
- MoE EP + EPLB
- DSpark + confidence-scheduled verification
- SWA bounded replay
- asynchronous scheduling
- batch-invariant inference
- deterministic sampling
- structured outputs
- FlashMLA
- DeepGEMM
- DeepEP
- TileKernels
- DeepSelect [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

특히 **CPU batch scheduling과 GPU execution을 overlap하는 asynchronous scheduler가 기본 활성화**되어 있다는 점이 중요합니다. [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

### 왜 중요한가

이제 DeepSeek의 inference stack을 단순히:

> “vLLM의 대체재”

라고 보면 안 됩니다.

DeepInfer의 README를 보면 오히려 **vLLM을 기반으로 출발해 SGLang, TensorRT-LLM 등의 아이디어를 흡수하면서 DeepSeek 모델에 특화된 전체 serving stack으로 발전한 형태**에 가깝습니다. [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

구조적으로 보면:

```text
Model
 ↓
Model Runtime
 ↓
Kernel
 ├─ FlashMLA
 ├─ DeepGEMM
 ├─ DeepEP
 └─ TileKernels
 ↓
Parallelism
 ├─ DP
 ├─ CP
 └─ EP
 ↓
Scheduler
 ├─ async scheduling
 └─ speculative verification
```

입니다.

### 특히 사용자의 B200 실험과 연결되는 부분

DeepInfer는 **NVIDIA SM100**을 공식 지원합니다. 즉 B200 계열에서 직접 비교 실험을 해볼 수 있는 구조입니다. 공식 prerequisite도 CUDA 13 + Python 3.12로 명시되어 있습니다. [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

따라서 기존 benchmark를:

```text
vLLM
vs
DeepInfer
```

로 확장하면 꽤 의미 있는 실험이 됩니다.

단, **동일 모델·동일 CUDA·동일 GPU topology·동일 parallelism·동일 sampling configuration**으로 맞추지 않으면 비교가 무의미합니다.

또 하나 중요한 점은 DeepInfer가 **완전한 production serving stack 전체를 포함하는 것은 아니라는 것**입니다. 공식 README에서도 KV cache system, prefill/decode disaggregation, replica-level load balancing 등이 별도로 필요하다고 명시합니다. [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

즉 DeepInfer 자체가 곧 Kubernetes-scale serving platform은 아닙니다.

### 후속 관찰

앞으로 가장 재미있는 비교는:

```text
vLLM
  ↕
DeepInfer
  ↕
SGLang
  ↕
TensorRT-LLM
```

의 **model-specific optimization과 general-purpose serving abstraction의 trade-off**입니다.

# 2. vLLM 0.32.0 — inference engine이 “structured decision engine”까지 확장된다 ★★★★★

현재 vLLM 공식 GitHub release의 최신 버전은 **v0.32.0**입니다. 10월 18일 공개됐고, **814 commits / 363 contributors**가 포함된 대규모 릴리스입니다. [GitHub](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

가장 눈에 띄는 변화 중 하나는 **structured decisions와 generic parsers**입니다.

새로운:

```text
POST /v1/systemone
```

endpoint가 structured state에 대해 `choice`, `noul`, `score` 등의 결정을 수행하도록 추가됐습니다. [GitHub](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

### 왜 중요한가

이것은 inference server의 역할이 조금씩 바뀌고 있다는 신호입니다.

기존:

```text
Request
 ↓
LLM
 ↓
Text
```

에서:

```text
Request
 ↓
Model
 ↓
Structured decision
 ↓
Router / Tool / Policy
```

로 이동합니다.

즉 LLM을 단순히 **text generator**로 사용하는 것이 아니라 **decision component**로 사용하는 구조입니다.

### Agent 시스템과 연결하면

예를 들어:

```text
User Request
      │
      ▼
 Decision Model
      │
 ┌────┼────┐
 ↓    ↓    ↓
small medium frontier
 │
 ▼
tool / agent
```

처럼 사용할 수 있습니다.

이 구조는 **모든 요청을 비싼 frontier model로 보내지 않고 작은 decision model을 먼저 사용해 routing/gating하는 architecture**와 잘 맞습니다.

### 실무적으로 중요한 이유

Agent serving cost를:

\[
C =
C_{\text{routing}}
+
C_{\text{reasoning}}
+
C_{\text{tool}}
\]

로 나누고, 앞단의 routing cost를 매우 작게 유지하면 전체 cost를 크게 낮출 수 있습니다.

예를 들어:

```text
100 requests
 ↓
decision model

70 → small model
20 → medium model
10 → frontier model
```

이라면 frontier GPU capacity를 훨씬 적게 확보해도 됩니다.

### 주의

v0.32.0 역시 대규모 릴리스입니다. 특히 structured-output, parser, model-specific optimization이 함께 들어가므로 **기존 0.31.x benchmark를 그대로 비교하면 안 됩니다.**

반드시 benchmark artifact에:

```text
vLLM version
commit
CUDA
driver
model revision
GPU topology
```

를 기록하세요.

**원문**

[릴리스 노트 · vLLM 0.32.0](https://github.com/vllm-project/vllm/releases?utm_source=chatgpt.com)

# 3. llm-d 1.0 — vLLM 위에 “Day-2 distributed inference layer”가 생긴다 ★★★★★

Google Cloud가 10월 20일 **llm-d 1.0**을 발표했습니다.

llm-d는 Kubernetes-native distributed inference stack으로, vLLM이나 SGLang 같은 model server **위에서 동작하는 orchestration/optimization layer**입니다. [Google Cloud](https://cloud.google.com/blog/topics/ai-infrastructure/llm-d-1-0-an-open-source-stack-for-distributed-inference?utm_source=chatgpt.com)

핵심 기능은:

- cache-aware routing
- load-aware routing
- multi-tenant traffic control
- tiered KV cache
- high availability
- prefill/decode disaggregation
- KV cache offloading
- expert parallelism
- batch/async inference [Google Cloud](https://cloud.google.com/blog/topics/ai-infrastructure/llm-d-1-0-an-open-source-stack-for-distributed-inference?utm_source=chatgpt.com)

입니다.

### 여기서 가장 중요한 개념

llm-d는 **vLLM을 대체하려는 프로젝트가 아닙니다.**

구조가:

```text
Kubernetes
   │
   ▼
 llm-d
   │
 ├── Router
 ├── Scheduler
 ├── KV management
 ├── Autoscaling
 └── HA
   │
   ▼
vLLM / SGLang
   │
   ▼
GPU
```

입니다.

즉:

> vLLM = **모델을 GPU에서 빠르게 실행**

> llm-d = **그 모델 서버들을 production cluster에서 효율적으로 운영**

이라는 계층 분리가 명확해지고 있습니다.

### 왜 중요한가

지금까지 LLM serving에서 많이 집중했던 것은:

```text
kernel
attention
KV cache
batching
TP
PP
EP
```

였습니다.

하지만 production에서는 결국:

```text
누가 어느 replica로 갈 것인가?
KV cache가 어디에 있는가?
어떤 tenant가 GPU를 얼마나 사용하는가?
업데이트 중에도 service를 유지할 수 있는가?
```

가 문제입니다.

즉 **Day-0 inference optimization → Day-2 infrastructure operation**으로 관심사가 이동합니다.

### 사용자의 B200 실험에 연결하면

현재 benchmark가:

```text
B200 × 2
      ↓
vLLM
      ↓
tokens/sec
```

라면 다음 단계는:

```text
B200 × N
      ↓
Kubernetes
      ↓
llm-d
      ↓
┌─────┼─────┐
vLLM  vLLM  vLLM
```

에서:

- cache-aware routing
- concurrency scaling
- replica scaling
- P/D disaggregation
- GPU utilization

을 측정하는 것입니다.

이 단계까지 가면 **단순 GPU benchmark가 아니라 distributed inference benchmark**가 됩니다.

### 주의

Google의 발표는 production-ready라는 방향성을 강하게 강조하지만, 실제 workload에서 vLLM/SGLang 단독 대비 어느 정도 개선되는지는 **모델, prefix locality, traffic pattern, cluster topology**에 따라 달라집니다.

따라서 `llm-d`를 도입할 때는 반드시 실제 traffic trace를 replay하는 것이 좋습니다.

**원문**

[공식 발표 · Google Cloud llm-d 1.0](https://cloud.google.com/blog/topics/ai-infrastructure/llm-d-1-0-an-open-source-stack-for-distributed-inference?utm_source=chatgpt.com)  
[GitHub · llm-d](https://github.com/llm-d/llm-d?utm_source=chatgpt.com)  
[GitHub · llm-d 1.0 Release Tracking](https://github.com/llm-d/llm-d/issues/2619?utm_source=chatgpt.com)

# 4. DeepSeek의 DeepInfer와 vLLM 0.32.0이 보여주는 것 — “generic engine vs model-specialized engine” 경쟁이 본격화 ★★★★★

오늘 가장 흥미로운 비교 포인트입니다.

DeepSeek은:

> **우리 모델을 가장 빠르게 실행하는 engine**

을 직접 공개했습니다.

반면 vLLM은:

> **많은 모델과 hardware를 하나의 API/serving abstraction으로 실행**

하는 방향을 유지합니다.

이를 단순화하면:

| | vLLM | DeepInfer |
|---|---|---|
| 목표 | General-purpose serving | DeepSeek 최적화 |
| 모델 | 광범위 | V4.1-Flash 중심 |
| API | OpenAI-compatible serving 중심 | offline inference 중심 |
| Kernel | 범용 + model-specific | DeepSeek 최적화 강함 |
| Parallelism | 광범위 | DeepSeek workload 특화 |
| Production orchestration | 외부 layer 가능 | 별도 필요 |
| 라이선스 | Apache-2.0 | Apache-2.0 |

DeepInfer는 현재 **offline inference 중심**이고, 완전한 serving service를 위해 KV cache, P/D disaggregation, replica load balancing 등이 별도로 필요하다고 공식 문서에서 밝히고 있습니다. [GitHub](https://github.com/deepseek-ai/DeepInfer?utm_source=chatgpt.com)

### 이게 왜 중요한가

앞으로 inference stack은 하나의 “최강 engine”으로 수렴하지 않을 가능성이 높습니다.

오히려:

```text
                 Router
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
    vLLM       DeepInfer    TensorRT-LLM
       │           │           │
    general     DeepSeek      NVIDIA
```

처럼 **model/hardware/workload별 specialized backend**를 router가 선택하는 구조가 더 현실적입니다.

이는 llm-d의 등장과도 정확히 맞물립니다.

# 5. GPU inference의 다음 병목은 “GPU 계산량”이 아니라 memory movement다 ★★★★☆

오늘 infrastructure 관점에서 놓치지 말아야 할 연구 흐름은 **host memory와 HBM을 동시에 활용하는 inference optimization**입니다.

최근 Georgia Tech, NVIDIA Research, Stanford 연구진의 BOOST 계열 연구는 LLM inference에서 **HBM과 host memory에 대한 concurrent access**를 활용해 memory wall을 완화하는 방향을 제시합니다. [세미엔지니어링](https://semiengineering.com/concurrent-hbm-and-host-memory-access-improves-llm-inference-throughput-georgia-tech-nvidia-stanford/?utm_source=chatgpt.com)

### 왜 중요한가

LLM decode에서는 연산량보다 memory access가 병목이 되는 구간이 많습니다.

특히:

```text
Decode
 ↓
weight access
 ↓
KV access
 ↓
memory bandwidth
 ↓
GPU compute
```

구조가 되기 때문에 FLOPS만 늘린다고 성능이 선형적으로 증가하지 않습니다.

이를 단순화하면:

\[
\text{Performance}
\approx
\min(
\text{Compute throughput},
\text{Memory bandwidth},
\text{Memory capacity}
)
\]

입니다.

### B200 benchmark에서 무엇을 봐야 하는가

GPU utilization이 90%라고 해서 반드시 compute-bound인 것은 아닙니다.

반드시:

```text
SM utilization
HBM bandwidth
HBM capacity
L2 hit rate
PCIe/NVLink traffic
CPU memory bandwidth
KV cache footprint
```

를 같이 봐야 합니다.

특히 long-context agent workload에서는 **KV cache capacity**가 GPU 수를 결정하는 요소가 될 가능성이 큽니다.

### 후속 관찰

앞으로는:

- KV cache offload
- tiered memory
- host memory
- CXL
- NVLink
- disaggregated memory

를 함께 보는 것이 좋습니다.

**원문**

[연구 기사 · BOOST memory optimization 연구](https://semiengineering.com/concurrent-hbm-and-host-memory-access-improves-llm-inference-throughput-georgia-tech-nvidia-stanford/?utm_source=chatgpt.com)

# 6. Agentic AI infrastructure — NVIDIA가 AI Factory를 “GPU cluster”가 아니라 heterogeneous distributed system으로 정의한다 ★★★★

NVIDIA의 최근 AI Factory 자료에서도 agentic workload는 기존 inference와 다르다고 명시적으로 설명합니다.

하나의 user request가:

```text
model call
 → tool call
 → memory lookup
 → another model call
 → code execution
 → another model call
```

처럼 여러 단계의 실행을 발생시킵니다. [NVIDIA Developer](https://developer.nvidia.com/blog/scaling-agentic-ai-factories-through-extreme-co-design-with-nvidia-bluefield/?utm_source=chatgpt.com)

그래서 NVIDIA는:

- GPU
- CPU
- DPU
- SuperNIC
- scheduler
- storage
- networking

을 하나의 시스템으로 최적화하는 방향을 강조하고 있습니다. [NVIDIA Developer](https://developer.nvidia.com/blog/validate-ai-factory-changes-with-digital-twins-and-ai-agents/?utm_source=chatgpt.com)

### 엔지니어 관점의 핵심

Agent throughput을:

\[
T_{agent}
=
f(
T_{GPU},
T_{CPU},
T_{network},
T_{storage},
T_{scheduler}
)
\]

로 봐야 합니다.

즉 GPU benchmark만 잘하는 것은 agent infrastructure 전체 성능의 일부만 측정하는 것입니다.

### 사용자의 현재 연구 방향에서 의미

이 때문에 **B200 vLLM benchmark → distributed inference → agent runtime**이라는 확장이 상당히 자연스럽습니다.

각 단계가:

```text
B200
 ↓
GPU performance

vLLM
 ↓
inference performance

llm-d
 ↓
distributed serving

Agent
 ↓
end-to-end execution
```

으로 연결됩니다.

# 7. 로컬 Agent + RTX Spark — inference가 다시 edge/developer machine으로 내려온다 ★★★★

NVIDIA가 IFA에서 공개한 RTX Spark 계열은 **local agent execution**을 강조하고 있습니다. NVIDIA는 개발자와 크리에이터가 로컬에서 agent를 실행할 수 있는 소형 시스템을 내세우고 있습니다. [NVIDIA Blog](https://blogs.nvidia.com/blog/local-ai-ifa-next-gen-agents-nv-pair-rtx-spark/?utm_source=chatgpt.com)

### 왜 중요한가

Agent가 항상 cloud frontier model을 호출할 필요는 없습니다.

예:

```text
Sensitive document
      ↓
Local small model
      ↓
classification / extraction

Complex task
      ↓
Cloud frontier model
```

이라는 hybrid architecture가 가능해집니다.

### 이것이 infrastructure에 미치는 영향

모델 routing이:

```text
request
 ↓
cloud
```

가 아니라:

```text
request
 ↓
policy
 ├── local
 ├── edge
 ├── private GPU
 └── cloud frontier
```

가 됩니다.

이는 privacy뿐 아니라 latency와 비용 최적화에도 직접 연결됩니다.

### 후속 관찰

- local model quality
- unified memory
- quantization
- local tool execution
- cloud/local model routing
- secure local sandbox

를 계속 볼 필요가 있습니다.

**원문**

[공식 발표 · NVIDIA RTX Spark와 local agents](https://blogs.nvidia.com/blog/local-ai-ifa-next-gen-agents-nv-pair-rtx-spark/?utm_source=chatgpt.com)

## 오늘의 핵심 결론

오늘의 자료를 하나로 묶으면 구조가 상당히 선명합니다.

```text
                  Agent / Application
                         │
                         ▼
                  Inference Router
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
            vLLM      DeepInfer   Other
              │          │
              └────┬─────┘
                   ▼
              Model Runtime
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      Kernel      KV        Scheduler
        │          │          │
        └──────────┼──────────┘
                   ▼
              GPU / CPU
                   │
                   ▼
             llm-d / K8s
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       Routing   Scaling    HA
```

**오늘 가장 중요한 변화는 inference stack의 계층화입니다.**

- **DeepInfer** → 모델 특화 inference engine
- **vLLM** → 범용 high-performance model server
- **llm-d** → distributed production inference layer
- **Kubernetes** → infrastructure orchestration
- **Agent runtime** → 실제 multi-step workload

그리고 이 구조에서는 **GPU 자체의 TFLOPS보다 memory movement, scheduling, routing, KV locality, CPU overhead가 점점 더 중요한 성능 변수**가 됩니다.

이 관점으로 보면 지금 하고 있는 **B200 × 2 vLLM Tensor Parallel benchmark를 `vLLM vs DeepInfer → llm-d distributed serving → agent workload`로 확장하는 것이 매우 자연스럽습니다.** 단순히 최신 기술을 따라가는 것이 아니라 하나의 일관된 **LLM inference infrastructure research story**가 됩니다.


다음 단계로 이어서 할 만한 작업은:

- vLLM 0.32.0 vs DeepInfer를 B200×2에서 비교하는 실험 설계표를 만들어줘
- DeepInfer 코드 구조를 vLLM과 비교해줘
- B200 benchmark를 llm-d까지 확장하는 로드맵을 만들어줘
