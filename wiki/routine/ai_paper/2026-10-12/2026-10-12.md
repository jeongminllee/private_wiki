## 1. Zepp — MoE Serving에서 완벽한 Load Balancing이 오히려 비효율적일 수 있다 ★★★★★

**논문 제출: 2026년 10월 8일 | 분야: LLM Architecture · Expert Parallelism · GPU Networking**

오늘 GPU·LLM 인프라 분야에서 가장 중요한 논문입니다.

**Zepp: Accelerating Distributed MoE Serving under Relaxed Balance Constraints**는 MoE 모델을 여러 GPU에 분산 실행할 때 발생하는 부하 불균형 문제를 새로운 관점에서 접근합니다.

### 무엇이 달라졌는가?

일반적인 Mixture of Experts 모델은 Router가 토큰마다 일부 Expert를 선택합니다.

Expert Parallelism을 이용하면 Expert가 여러 GPU에 분산되고, 선택된 Expert가 있는 GPU로 토큰을 전송해야 합니다.

```text
Input Tokens
      │
      ▼
Expert Router
      │
      ├── Expert 0 → GPU 0
      ├── Expert 1 → GPU 1
      ├── Expert 2 → GPU 2
      └── Expert 3 → GPU 3
             │
             ▼
      Dispatch / All-to-All
             │
             ▼
         Expert Compute
             │
             ▼
           Combine
```

문제는 모든 Expert가 동일한 빈도로 선택되지 않는다는 것입니다.

특정 Expert에 요청이 집중되면 해당 GPU가 병목이 됩니다.

기존 시스템은 이를 해결하기 위해 Expert를 복제하거나 GPU 사이에 재배치해 부하를 균등하게 만들었습니다.

하지만 Zepp 연구진은 여기서 중요한 문제를 발견했습니다.

**연산 부하를 균등하게 만드는 과정 자체가 추가적인 네트워크 통신을 발생시킬 수 있다는 것입니다.**

예를 들어 GPU A에 요청이 집중됐다고 가정하겠습니다.

이를 분산하기 위해 다른 노드의 GPU B로 일부 토큰을 전달하면 GPU A의 연산 부하는 감소합니다.

하지만 GPU B로 전달하는 데이터가 노드 간 통신을 요구한다면, 계산에서 절약한 시간보다 네트워크 통신에 더 많은 시간이 소요될 수 있습니다.

즉 다음 관계가 항상 성립하지는 않습니다.

\[
\text{Better Load Balance}
\not\Rightarrow
\text{Better End-to-End Performance}
\]

### Zepp의 접근

Zepp는 Load Balancing을 최종 목표로 두지 않습니다.

대신 **GPU와 NIC의 부하를 허용 가능한 범위로 제한하면서 노드 간 통신량을 최소화**합니다.

이를 위해 세 가지 기술을 결합합니다.

**Expert Placement와 Locality-aware Routing**

가능하다면 토큰이 생성된 노드 내부에서 Expert 연산을 완료하도록 배치합니다.

특정 Expert가 여러 GPU에 복제돼 있다면 완벽하게 균등한 요청 분배보다 통신 비용이 낮은 복제본을 우선 선택합니다.

**Split/Merge Communication**

여러 Expert가 동일한 입력 토큰을 필요로 한다면 토큰을 중복 전송하는 대신 통신을 병합합니다.

반대로 특정 NIC에 통신량이 집중된다면 데이터 흐름을 분할해 병목을 줄입니다.

**Communication-Computation Overlap**

토큰을 전송하는 동안 이미 준비된 다른 Expert 연산을 실행합니다.

또한 Expert 수요가 변할 때 노드 전체를 재배치하기보다 가능한 범위에서 노드 내부의 Expert 배치를 조정합니다. [arXiv](https://arxiv.org/html/2610.11158v1)

### 성능 결과

연구진은 7개의 기존 MoE Serving 시스템과 비교했습니다.

| 비교 기준 | Zepp 결과 |
|---|---:|
| 기존 구현 대비 최대 MoE Layer 속도 향상 | 6.68배 |
| 가장 빠른 경쟁 Baseline 대비 최대 개선 | 2.78배 |
| 가장 빠른 경쟁 Baseline 대비 기하평균 개선 | 1.86배 |

여기서 **중요한 것은 측정 단위가 MoE Layer 실행이라는 점**입니다.

6.68배가 전체 LLM 서비스의 요청 처리량이 6.68배 향상됐다는 의미는 아닙니다.

실제 모델에는 Attention, Normalization, Scheduling, KV Cache 관리 등 다른 연산도 존재합니다.

따라서 해당 결과를 End-to-End Serving 성능으로 일반화해서는 안 됩니다. [arXiv](https://arxiv.org/abs/2610.11158)

### 실제 시스템에 적용한다면

MoE 모델의 추론 시스템을 비교할 때 단순 GPU Utilization만 측정해서는 부족합니다.

다음 항목을 함께 확인해야 합니다.

```text
Expert Token Distribution
Expert Replica Placement
Inter-GPU Communication
Inter-Node Communication
NIC Utilization
Expert Compute Time
Communication Overlap
MoE Layer Latency
End-to-End TPOT
```

특히 Expert Parallelism에서 병목이 발생한다면 **Expert를 더 균등하게 분산하기 전에 실제 Critical Path가 연산인지 통신인지 확인하는 것**이 중요합니다.

### 주의할 점과 후속 관찰

Zepp의 주요 최적화 대상은 여러 노드에 분산된 Expert Parallelism입니다.

단일 노드에서 NVLink로 연결된 GPU 두 장을 사용하는 환경과는 통신 구조가 다릅니다.

따라서 소규모 멀티 GPU 환경에서는 논문의 알고리즘을 그대로 적용하기보다 Expert Placement, Token Locality, 통신·연산 중첩의 영향을 먼저 분석하는 편이 적절합니다.

**후속 관찰:** 실제 vLLM·SGLang 통합, 동적 Expert 분포에서의 안정성, GPU 메모리 사용량 증가, 전체 모델 Serving 성능입니다.

**원문:** [논문 · Zepp: Accelerating Distributed MoE Serving under Relaxed Balance Constraints](https://arxiv.org/abs/2610.11158) · [GitHub · Zepp 공식 구현](https://github.com/andronius-yang/zepp)

## 2. PageWeaver — Sparse Attention에서는 KV를 적게 읽는 것만큼 Query Grouping이 중요하다 ★★★★★

**논문 제출: 2026년 10월 8일 | 분야: LLM Architecture · Sparse Attention · GPU Kernel**

**PageWeaver: KV-Guided Query Unions for Sparse Attention**는 Sparse Attention을 실제 GPU에서 실행할 때 발생하는 비효율을 다룹니다.

전날 브리핑에서 다룬 TokenRouter가 여러 모델 사이의 실행 스케줄링을 최적화한다면, PageWeaver는 **하나의 Attention Kernel 내부에서 Query와 KV Page를 어떻게 배치할 것인가**를 연구합니다.

### 기존 Sparse Attention의 문제

Dynamic Sparse Attention은 각 Query가 참조할 KV Page를 선택합니다.

예를 들어 Query마다 16개의 KV Page만 읽는다고 가정하겠습니다.

```text
Query A → Page [1, 2, 3, 4]
Query B → Page [2, 3, 4, 5]
Query C → Page [1, 3, 4, 6]
Query D → Page [7, 8, 9, 10]
```

Query A와 B는 많은 Page를 공유합니다.

반면 Query A와 D는 공유하는 Page가 없습니다.

GPU에서 Query A와 B를 같은 그룹으로 처리하면 KV Page를 한 번 읽어 여러 Query에서 재사용할 수 있습니다.

하지만 A와 D를 같은 그룹에 넣으면 재사용 효과가 작습니다.

즉 **각 Query가 참조하는 Page 수가 동일하더라도 어떤 Query를 함께 실행하는지에 따라 메모리 접근 비용이 달라집니다.**

### PageWeaver의 해결 방법

PageWeaver는 Query가 선택한 KV Page의 유사도를 이용해 Query 그룹을 재구성합니다.

```text
Queries
   │
   ▼
Selected KV Pages
   │
   ▼
Page Affinity Analysis
   │
   ▼
Query Regrouping
   │
   ▼
KV Page Union
   │
   ▼
GPU Attention Kernel
```

다만 Query를 재배치하면 원래 Query의 위치와 출력 위치가 달라질 수 있습니다.

PageWeaver는 Query ID를 유지하는 방식으로 원래의 Attention 대상과 출력 위치를 보존합니다.

또한 GPU에서 실행할 수 있는 범위 내에서 Query Group을 탐색하고, FP8 KV Cache와 전용 Attention Kernel을 이용해 실행 효율을 개선합니다. [arXiv](https://arxiv.org/html/2610.11201v1)

### 성능 결과와 중요한 구분

연구진은 H200과 B300 환경에서 평가했습니다.

| 평가 항목 | 보고 결과 |
|---|---|
| H200의 Union8 구현 vs 측정된 FlashInfer 경로 | 기하평균 1.70배 |
| 선택된 64K Context에서 Online Regrouping | 연산 지연 3.26~7.66% 감소 |
| H200 Whole-model Prefill Throughput | 기존 Native 경로 대비 7.88~14.36% 증가 |
| Regrouping만의 추가 Median 개선 | 32K/64K에서 0.47~0.73% |

여기서 주의할 점이 있습니다.

**1.70배 개선은 Attention 연산 경로의 비교이며 전체 서비스 성능 개선이 아닙니다.**

또한 Whole-model Prefill의 7.88~14.36% 향상 대부분은 기본 Union8 구현에서 발생했습니다.

실제로 Query Regrouping만 추가했을 때의 개선량은 상대적으로 작았습니다.

8K Context에서는 오히려 성능이 저하되는 조건도 있었습니다.

B300에서는 기존 Native Kernel이 더 빨라서 PageWeaver의 재그룹화가 전체적으로 이기지 못하는 조건도 확인됐습니다. [arXiv](https://arxiv.org/html/2610.11201v1)

### 왜 중요한가?

이 논문은 Sparse Attention의 성능을 두 단계로 구분하도록 만듭니다.

**Algorithmic Sparsity**는 얼마나 적은 토큰이나 Page를 참조하는가의 문제입니다.

**Execution Efficiency**는 선택된 연산을 GPU에서 얼마나 효율적으로 실행하는가의 문제입니다.

첫 번째가 좋다고 두 번째가 자동으로 좋아지는 것은 아닙니다.

예를 들어 Attention 계산량을 절반으로 줄이더라도 불규칙한 메모리 접근과 작은 Kernel 실행이 증가하면 실제 지연시간은 줄어들지 않을 수 있습니다.

### 주의할 점과 후속 관찰

저자들은 FP8 계산의 수치적 차이와 실제 모델 출력 품질을 별도로 구분했습니다.

따라서 동일한 Sparse Support를 유지한다는 사실만으로 최종 생성 품질이 완전히 동일하다고 결론낼 수는 없습니다.

**후속 관찰:** Query Grouping Overhead, B200/Blackwell에서의 성능, Batch Size별 효율, 최종 생성 정확도, Attention Kernel과 전체 서비스 처리량의 차이입니다.

**원문:** [논문 · PageWeaver: KV-Guided Query Unions for Sparse Attention](https://arxiv.org/abs/2610.11201)

## 3. Plan-and-Patch — Diffusion LLM으로 에이전트 실행 계획의 일부만 수정한다 ★★★★★

**논문 제출: 2026년 10월 7일 · 10월 9일 공개 목록 확인 | 분야: Agent Planning · Diffusion Language Model**

**Plan-and-Patch: Diffusion Language Models for Agentic Planning**은 장기 에이전트의 계획 생성과 수정 문제를 다룹니다.

기존 에이전트는 계획이 실패하면 상당 부분을 처음부터 다시 생성하는 경우가 있습니다.

하지만 실제 작업에서는 전체 계획이 잘못된 것이 아니라 일부 단계만 수정해야 하는 경우가 많습니다.

### 무엇이 달라졌는가?

예를 들어 다음과 같은 계획이 있다고 가정하겠습니다.

```text
Step 1: Repository 분석
Step 2: 관련 함수 탐색
Step 3: 수정 방법 결정
Step 4: 코드 변경
Step 5: 테스트 실행
Step 6: 결과 검증
```

Step 4에서 예상하지 못한 오류가 발생했다고 해서 Step 1부터 모든 계획을 다시 작성할 필요는 없습니다.

Plan-and-Patch는 Diffusion Language Model을 이용해 **수정이 필요한 구간만 다시 생성**합니다.

```text
Original Plan
     │
     ▼
Execution Failure
     │
     ▼
Failure Localization
     │
     ▼
Affected Region Masking
     │
     ▼
Diffusion Infilling
     │
     ▼
Patched Plan
```

이때 변경하지 않는 앞부분과 뒷부분은 유지합니다.

Diffusion Model은 Masking된 구간을 반복적으로 복원하면서 수정된 계획을 생성합니다.

일반적인 Autoregressive 모델과 달리 일부 구간을 앞뒤 문맥에 맞춰 복원하는 구조를 활용한다는 점이 특징입니다. [arXiv](https://arxiv.org/abs/2610.10786)

### 실험 결과

연구진은 DreamReasoner-8B와 Qwen3-8B를 비교했습니다.

Task-specific Training 없이 Natural Plan에서 평가한 결과는 다음과 같습니다.

| 평가 항목 | Diffusion Planner | Autoregressive Planner |
|---|---:|---:|
| 계획 생성 성공률 | 33.0% | 48.6% |
| 계획 수정 성공률 | 53.7% | 27.0% |

여기서 상당히 중요한 결과가 있습니다.

**Diffusion Planner는 계획 생성 자체에서는 성능이 낮았지만, 이미 존재하는 계획의 일부를 수정하는 작업에서는 더 좋은 성능을 보였습니다.**

이는 생성과 수정이 서로 다른 문제라는 점을 보여줍니다.

ALFWorld와 TextCraft에서 Task-specific Training을 적용한 평가에서는 두 Planner의 작업 성공률이 유사했으며, Diffusion 방식의 평균 계획 생성 지연시간은 39~46% 낮았습니다.

다만 이 속도는 단일 A100에서 측정한 **계획 생성 단계의 지연시간**입니다. 환경 실행과 전체 에이전트 작업 시간은 포함하지 않습니다. [arXiv](https://arxiv.org/html/2610.10786v1)

### 에이전트 하네스에 적용한다면

현재 에이전트의 Plan을 단순 Markdown 문장으로만 관리한다면 특정 단계의 변경을 추적하기 어려울 수 있습니다.

반대로 계획을 구조화하면 다음과 같은 방식이 가능합니다.

```text
Plan
├── Step ID
├── Description
├── Dependencies
├── Preconditions
├── Expected Result
└── Verification
```

실패한 Step과 영향을 받는 Dependency만 수정하고 나머지는 유지하는 것입니다.

중요한 것은 Diffusion Model을 반드시 도입해야 한다는 의미가 아닙니다.

**전체 계획 재생성과 부분 수정의 효과를 독립적으로 비교할 수 있는 실험 구조**를 제공한다는 점이 핵심입니다.

### 주의할 점

논문에서는 어떤 부분을 수정할지 선택하는 단계도 중요한 병목으로 나타났습니다.

수정해야 할 범위를 잘못 선택하면 계획 복원 모델이 뛰어나더라도 전체 결과가 좋아지지 않습니다.

또한 실패 후 환경을 초기화하고 수정된 계획을 실행하는 평가가 포함돼 있으므로, 이미 외부 상태를 변경한 실제 에이전트에서는 별도의 Recovery Policy가 필요합니다.

**후속 관찰:** 실패 구간 자동 선택, 장기 계획의 Dependency 관리, 실제 Coding Agent에서의 부분 수정 성공률, Plan Repair 비용입니다.

**원문:** [논문 · Plan-and-Patch: Diffusion Language Models for Agentic Planning](https://arxiv.org/abs/2610.10786)

## 4. LLM Agents as Resilience Engineers — AI가 HPC 프로그램의 Checkpoint/Restart를 자동 구현할 수 있을까? ★★★★★

**논문 제출: 2026년 10월 8일 | 분야: HPC · Distributed Systems · Coding Agent**

미국 Argonne National Laboratory와 University of Chicago 연구진이 발표한 **LLM Agents as Resilience Engineers for Scientific Applications**는 상당히 실용적인 연구입니다.

이 논문은 에이전트가 단순히 코드를 생성하는 것을 넘어, **장시간 실행되는 과학 계산 프로그램에 장애 복구 기능을 직접 추가할 수 있는가**를 검증합니다.

### 무엇을 연구했는가?

HPC에서는 프로그램이 수 시간 또는 수일 동안 실행될 수 있습니다.

중간에 GPU나 서버에 장애가 발생하면 지금까지 수행한 계산을 잃을 수 있습니다.

이를 방지하기 위한 대표적인 방법이 Checkpoint/Restart입니다.

```text
Scientific Application
       │
       ▼
Checkpoint
       │
       ▼
Continue Computing
       │
       ├── 정상 실행
       │
       └── 장애 발생
                │
                ▼
         Restore Checkpoint
                │
                ▼
           Resume Computing
```

그러나 Checkpoint를 구현하려면 어떤 상태를 저장해야 하는지 정확히 알아야 합니다.

예를 들어 MPI 기반 프로그램에서는 각 프로세스의 상태가 서로 연결돼 있습니다.

어떤 프로세스는 이미 다음 계산으로 넘어갔는데 다른 프로세스는 이전 상태를 저장했다면 Restart 이후 일관성이 깨질 수 있습니다.

### AI Agent의 역할

연구진은 16개의 MPI 애플리케이션을 대상으로 Coding Agent가 다음 작업을 수행하도록 했습니다.

```text
Source Inspection
       │
       ▼
Critical State Identification
       │
       ▼
Checkpoint Code Generation
       │
       ▼
Failure Injection
       │
       ▼
Recovery Validation
       │
       ▼
Revision
```

저수준 Checkpoint 기능은 기존 VeloC 라이브러리를 사용했고, 에이전트는 프로그램에서 복구에 필요한 상태와 안전한 Checkpoint 위치를 찾아 코드를 작성했습니다.

평가는 3개의 모델을 사용한 총 48개 애플리케이션·모델 조합을 중심으로 수행됐습니다.

연구진은 **41개의 정상 작동하는 장애 복구 구현**을 얻었다고 보고했습니다. [arXiv](https://arxiv.org/html/2610.11260v1)

### 핵심 결과

성공한 실행은 평균적으로 한 시간 이내에 완료됐고, 약 1,500만 토큰을 사용했습니다.

생성된 구현은 정상 실행 상태에서 대체로 3% 이내의 추가 실행시간을 보였으며, 장애 후 복구 효율도 사람이 작성한 구현과 유사했습니다.

하지만 복구에 필요한 상태가 여러 모듈에 분산돼 있으면 에이전트의 성능이 크게 떨어졌습니다.

일부 실패 사례에서는 1억 토큰 이상과 300분 이상의 실행시간을 소비하고도 작업을 완료하지 못했습니다. [arXiv](https://arxiv.org/html/2610.11260v1)

### 엔지니어링 관점

이 연구의 중요한 발견은 **프로젝트 코드 크기보다 복구해야 할 상태의 구조가 작업 난이도에 더 큰 영향을 미쳤다는 점**입니다.

이는 Coding Agent의 성능이 모델 능력뿐 아니라 코드베이스의 구조와 상태 가시성에 영향을 받는다는 의미입니다.

특히 Distributed Training과 Agent Runtime에서도 같은 원칙을 적용할 수 있습니다.

복구 상태를 다음과 같이 분리해 관리한다면 장애 복구를 구현하기 쉬워집니다.

```text
Recoverable State
├── Model / Adapter Weights
├── Optimizer State
├── Scheduler State
├── RNG State
├── Dataset Cursor
├── Distributed Rank Metadata
└── Checkpoint Version
```

다만 이것은 일반적인 학습 시스템에 적용하기 위한 설계 예시이며, 논문이 이 모든 항목을 직접 검증했다는 의미는 아닙니다.

### 후속 관찰

이번 연구는 MPI 애플리케이션과 Fail-stop Failure 중심입니다.

GPU OOM, 통신 Deadlock, Checkpoint 손상, 노드 수 변경 후 복구 같은 문제까지 해결했다는 증거는 아닙니다.

**후속 관찰:** DeepSpeed/FSDP 학습 시스템으로의 확장, Distributed State 일관성, Agent가 생성한 Checkpoint 코드의 장기 안정성, 실패 사례에 대한 진단 정보 개선입니다.

**원문:** [논문 · LLM Agents as Resilience Engineers for Scientific Applications](https://arxiv.org/abs/2610.11260)

## 5. Agent-Controlled Forgetting — 장기 에이전트에서 기록을 삭제하지 않고 Context만 줄이는 방법 ★★★★★

**논문 제출: 2026년 10월 6일 · 최신 목록 확인: 10월 9일 | 분야: Agent Memory · Context Engineering**

**Agent-Controlled Forgetting for Tool-Using Agents**는 Context Window의 불필요한 데이터를 줄이는 실용적인 방법을 연구합니다.

전날 살펴본 REMORY가 학습 가능한 Soft Memory를 사용하는 방식이었다면, 이번 연구는 **별도의 모델 학습 없이 Tool Result를 보관하고 필요할 때 복원하는 방식**입니다.

### 무엇이 다른가?

장기 에이전트는 Tool을 실행하면서 매우 큰 결과를 받습니다.

예를 들어 검색 결과, 테스트 로그, 실행 추적, 브라우저 페이지 전체 내용 등을 Context에 보관합니다.

하지만 대부분의 결과는 현재 작업에 필요한 정보보다 훨씬 깁니다.

이번 논문은 에이전트가 더 이상 직접 참조할 필요가 없는 Tool Result를 선택해 짧은 메모로 대체합니다.

```text
Tool Result
    │
    ▼
Agent Decision
    │
    ├── Keep in Context
    │
    └── Archive
          │
          ├── Short Note → Active Context
          │
          └── Original Result → Recoverable Archive
```

필요한 경우 보관된 원본을 다시 가져올 수 있습니다.

중요한 것은 사용자의 지시와 에이전트의 메시지를 임의로 삭제하는 것이 아니라 **이미 수신한 Tool Observation을 대상으로 한다는 점**입니다.

### 실제 측정 결과

OpenTelemetry 관련 디버깅과 후속 구현 작업에서 다음 결과를 보고했습니다.

| 지표 | 전체 기록 유지 | 선택적 보관 |
|---|---:|---:|
| 최종 입력 Context | 912,492 tokens | 231,951 tokens |
| 누적 입력 토큰 | 약 45.77M | 약 22.99M |
| 모델 요청 횟수 | 121 | 185 |
| 전체 실행시간 | 1,730초 | 2,025초 |
| 추정 API 비용 | 약 $4.38 | $1.28~1.44 |

선택적 보관은 누적 입력 토큰을 약 50% 줄였습니다.

하지만 모델 요청 횟수가 증가하면서 **전체 작업 시간은 약 17% 길어졌습니다.**

다른 애플리케이션 작업에서는 비용이나 Context 절감 효과가 나타나지 않았습니다. [arXiv](https://arxiv.org/html/2610.10590v1)

### 왜 중요한가?

이 결과는 Agent Context Optimization에서 자주 놓치는 문제를 보여줍니다.

**토큰 비용 절감과 실행시간 단축은 서로 다른 목표입니다.**

또한 Archive를 자주 조회하면 Context가 작아지더라도 도구 호출과 모델 실행 횟수가 증가할 수 있습니다.

따라서 다음 지표를 따로 측정해야 합니다.

```text
Active Context Tokens
Archive Read Count
Model Requests
Tool Requests
Repeated Investigation
Task Success
Wall-clock Time
Total Cost
```

### 주의할 점

이번 연구는 소수의 탐색적 작업을 대상으로 수행됐습니다.

저자도 모든 에이전트에서 동일한 효과가 나타난다고 주장하지 않습니다.

공개 저장소에는 주요 실험 기록과 검증 스크립트가 포함되지만 일부 원본 Observation과 모든 실행 자료가 포함돼 있지는 않습니다.

따라서 엄격한 독립 재현에는 추가 자료가 필요합니다. [GitHub](https://github.com/boldprojekte/agent-forgetting-research)

**후속 관찰:** 실제 Coding Agent에서의 비용 절감, 반복 조사 증가 여부, Archive 검색 비용, 오래된 Tool Result의 유효성 관리입니다.

**원문:** [논문 · Agent-Controlled Forgetting for Tool-Using Agents](https://arxiv.org/abs/2610.10590) · [GitHub · Agent Forgetting Research Artifacts](https://github.com/boldprojekte/agent-forgetting-research)

## 6. CodeQL 2.27.2 — 정적분석 정확도 개선과 Go Control Flow Graph의 구조 변경 ★★★★☆

**릴리스: 2026년 10월 9일 | 분야: Security Engineering · Static Analysis · Open Source**

GitHub가 **CodeQL 2.27.2**를 공개했습니다.

이번 업데이트는 단순한 보안 규칙 추가보다 **프로그램의 실행 흐름과 라이브러리 동작을 더 정확하게 모델링하는 것**에 초점이 맞춰져 있습니다.

### 무엇이 달라졌는가?

C/C++에서는 ECMAScript 문법을 사용하는 `std::regex` 표현식 분석을 지원합니다.

Comdb2 C API의 SQL Injection Sink와 일부 직렬화·역직렬화 라이브러리의 Data Flow Summary도 추가됐습니다.

Rust에서는 `async`와 `await`가 포함된 코드의 Data Flow를 개선했습니다.

JavaScript/TypeScript에서는 Workflow SDK의 `"use workflow"`, `"use step"` 지시문을 인식하고 Hapi의 요청 처리 경로 추적을 보강했습니다. [The GitHub Blog](https://github.blog/changelog/2026-10-09-codeql-2-27-2-improves-c-go-rust-and-javascript-analysis/)

### 중요한 변경 — Go CFG

Go의 Control Flow Graph가 공통 CFG 라이브러리 기반으로 변경됐습니다.

이로 인해 CFG의 Node, Edge, Basic Block 경계 등이 달라질 수 있습니다.

기존 CodeQL Query가 특정 CFG 구조를 가정하고 있었다면 업데이트 후 Query를 수정해야 할 수 있습니다.

따라서 **정적분석 엔진 버전이 바뀌면 코드가 동일해도 탐지 결과가 바뀔 수 있습니다.**

### 보안 특화 LLM 평가에서의 의미

정적분석 결과를 LLM에 제공하는 시스템에서는 Analyzer Version이 중요한 실험 변수입니다.

예를 들어 다음 두 결과를 비교한다고 가정하겠습니다.

```text
Experiment A
    CodeQL 2.27.1
    + LLM Model X

Experiment B
    CodeQL 2.27.2
    + LLM Model X
```

LLM이 동일하더라도 CodeQL의 Data Flow 모델이 개선되면 입력되는 Finding이 달라질 수 있습니다.

이 경우 전체 탐지율이 높아졌다고 해서 LLM의 분석 능력이 개선됐다고 말할 수 없습니다.

따라서 평가할 때는 Analyzer 결과와 LLM 결과를 분리해야 합니다.

```text
Source Code
     │
     ▼
Static Analyzer
     │
     ▼
Analyzer Findings
     │
     ▼
LLM Assessment
     │
     ▼
Validated Findings
```

### 주의할 점

이번 릴리스에서는 macOS와 Xcode 버전 호환성 변경도 있습니다.

GitHub는 macOS 27/Xcode 27 환경에서 컴파일 언어의 일부 추적 기반 CodeQL Build Mode를 지원하지 않는다고 설명했습니다.

해당 환경을 사용하는 개발자는 분석 파이프라인을 업데이트하기 전에 공식 호환성 문서를 확인해야 합니다.

**후속 관찰:** C/C++ CWE 탐지율, Rust Async Flow 분석 품질, Go CFG 변경에 따른 기존 Query 호환성, False Positive 변화입니다.

**원문:** [릴리스 노트 · GitHub CodeQL 2.27.2](https://github.blog/changelog/2026-10-09-codeql-2-27-2-improves-c-go-rust-and-javascript-analysis/)

## 7. VS Code 1.141 — 여러 에이전트 작업을 동시에 확인하고 Worktree를 관리하는 기능 확대 ★★★★☆

**릴리스 안내: 2026년 10월 9일 | 분야: Coding Agent · Developer Tools · Multi-Agent Workflow**

GitHub가 10월 9일 공개한 Copilot 주간 업데이트에서 **VS Code 1.141의 에이전트 작업 관리 기능**을 소개했습니다.

이번 변경은 새로운 추론 모델보다 **여러 에이전트의 실행 결과와 작업 공간을 관리하는 개발자 경험**에 초점이 맞춰져 있습니다.

### 주요 변경

첫 번째는 **Agent Session을 나란히 배치하는 기능**입니다.

여러 세션을 Grid 형태로 정렬해 각각의 작업 진행 상황과 결과를 비교할 수 있습니다.

두 번째는 **Worktree Cleanup**입니다.

Agent Session이 생성한 Git Worktree 중 사용하지 않는 항목을 확인하고 정리할 수 있습니다.

Copilot App에서도 모델 이용 계정과 Repository에 접근하는 GitHub 계정을 분리해 사용할 수 있게 됐습니다. [The GitHub Blog](https://github.blog/changelog/2026-10-09-github-copilot-weekly-releases-october-5)

### 왜 중요한가?

여러 에이전트를 병렬 실행하면 모델 호출보다 다른 문제가 먼저 발생할 수 있습니다.

대표적으로 동일한 Repository 파일을 여러 에이전트가 동시에 수정하는 문제입니다.

```text
Main Repository
      │
      ├── Agent A Worktree
      │       └── Feature A
      │
      ├── Agent B Worktree
      │       └── Feature B
      │
      └── Agent C Worktree
              └── Tests
```

Worktree를 분리하면 각 에이전트가 독립된 작업 디렉터리에서 변경을 수행할 수 있습니다.

하지만 Worktree는 실행 격리나 보안 Sandbox를 자동으로 제공하는 것은 아닙니다.

또한 별도 Worktree에서 수정한 파일을 최종 Branch에 반영할 때 Merge Conflict가 발생할 수 있습니다.

따라서 병렬 에이전트 시스템에서는 다음 요소를 분리해야 합니다.

**Execution Isolation**은 에이전트가 다른 작업의 파일을 변경하지 못하도록 제한하는 문제입니다.

**State Isolation**은 작업별 Git 상태와 파일 변경을 분리하는 문제입니다.

**Integration**은 여러 결과를 하나의 Branch에 결합하는 문제입니다.

### 실제 적용과 후속 관찰

병렬 Coding Agent가 늘어날수록 Worktree의 디스크 사용량, 중복 Dependency 설치, 테스트 충돌, Merge Conflict 등이 운영 비용으로 나타납니다.

# 오늘 직접 해볼 만한 실습
## `KV Page Affinity` — Query를 어떻게 묶느냐에 따라 메모리 접근량이 달라질까?

오늘은 PageWeaver의 핵심 아이디어를 작은 실험으로 검증하는 것을 추천합니다.

논문에서 제시한 GPU Kernel 전체를 구현하는 것은 상당한 작업이 필요합니다.

대신 **Query Grouping에 따른 KV Page 재사용 가능성**을 먼저 확인할 수 있습니다.

### 1. 연구 질문

동일한 KV Page를 참조하는 Query를 같은 그룹에 배치하면 필요한 KV Page의 합집합 크기를 줄일 수 있을까요?

두 조건을 비교합니다.

**A. Sequential Grouping**은 Query의 기존 순서를 유지하면서 8개씩 묶습니다.

**B. Affinity Grouping**은 KV Page 집합이 유사한 Query를 우선 묶습니다.

두 조건에서 각 Query가 실제로 참조하는 KV Page 집합은 동일하게 유지합니다.

### 2. PyTorch 없이 재현 가능한 실험

다음 코드는 별도의 GPU 없이 실행할 수 있습니다.

```python
import random

random.seed(42)

N_QUERIES = 64
TOP_K = 16
GROUP_SIZE = 8
N_PAGES = 1024

# 공통 페이지를 공유하는 Query 생성
supports = []

for cluster in range(8):
    shared = set(random.sample(range(N_PAGES), 12))

    for _ in range(8):
        extra = set()

        while len(extra) < TOP_K - len(shared):
            extra.add(random.randrange(N_PAGES))

        supports.append(shared | extra)

# 기존 Query 순서 섞기
random.shuffle(supports)


def union_cost(groups):
    return sum(
        len(set().union(*group))
        for group in groups
    )


# A. Sequential Grouping
sequential = [
    supports[i:i + GROUP_SIZE]
    for i in range(0, N_QUERIES, GROUP_SIZE)
]


# B. Affinity-based Greedy Grouping
remaining = supports.copy()
affinity_groups = []

while remaining:
    group = [remaining.pop(0)]

    while len(group) < GROUP_SIZE and remaining:
        current = set().union(*group)

        best_idx = max(
            range(len(remaining)),
            key=lambda i: len(current & remaining[i])
        )

        group.append(remaining.pop(best_idx))

    affinity_groups.append(group)


cost_a = union_cost(sequential)
cost_b = union_cost(affinity_groups)

print(f"Sequential union pages: {cost_a}")
print(f"Affinity union pages:   {cost_b}")
print(f"Union reduction: {(1 - cost_b / cost_a) * 100:.2f}%")
```

### 3. 무엇을 관찰해야 하는가?

이 실험에서 중요한 지표는 세 가지입니다.

**첫 번째는 Union Page Count입니다.**

그룹 내 Query들이 선택한 Page의 합집합 크기입니다.

동일한 Page를 여러 Query가 사용한다면 한 번의 로드로 재사용할 기회가 생깁니다.

**두 번째는 Page Reuse Ratio입니다.**

Query별 Page 선택 수의 합계에 비해 그룹 단위에서 중복되는 Page가 얼마나 많은지를 나타냅니다.

**세 번째는 Grouping Overhead입니다.**

유사한 Query를 찾는 과정에도 계산 비용이 발생합니다.

따라서 Page 재사용이 증가하더라도 Query를 그룹화하는 데 너무 많은 시간이 소요되면 실제 성능은 저하될 수 있습니다.

### 4. 이후 GPU 실험으로 확장

실제 GPU에서는 다음 지표를 추가로 측정해야 합니다.

| 지표 | 측정 목적 |
|---|---|
| KV Pages per Query | Sparse Attention의 선택 범위 |
| Unique KV Pages per Group | KV 재사용 가능성 |
| Grouping Overhead | 그룹 탐색 비용 |
| HBM Read Bytes | 실제 메모리 트래픽 |
| Attention Kernel Latency | GPU 연산 효율 |
| End-to-End Prefill Time | 전체 추론 성능 |
| Output Numerical Error | 연산 결과 일치성 |

중요한 점은 오늘 작성한 코드가 **PageWeaver의 GPU Kernel을 재현한 것은 아니라는 사실**입니다.

이 실험은 KV Page 선택 집합과 Query Grouping의 관계를 확인하는 기초 실험입니다.

또한 Union Page 수가 감소했다고 실제 HBM Read Byte나 실행시간이 동일한 비율로 감소하는 것은 아닙니다.

GPU에서는 Tile Utilization, Memory Coalescing, Register Pressure, Kernel Launch, Grouping Overhead가 함께 작용하기 때문입니다.

실제 Attention Kernel로 확장할 때는 이러한 변수들을 따로 측정해야 합니다.

## 오늘의 종합 판단

오늘 조사한 자료는 크게 세 가지 방향으로 연결됩니다.

**첫째, 모델 내부 연산과 GPU 실행의 관계가 더욱 중요해지고 있습니다.** Zepp와 PageWeaver는 계산량을 줄이거나 Load Balancing을 개선하는 것만으로 전체 성능이 좋아지지 않는다는 점을 보여줍니다.

**둘째, 장기 에이전트에서는 상태를 어떻게 관리하느냐가 핵심입니다.** Plan-and-Patch는 계획의 일부만 수정하는 방법을 제안하고, Agent-Controlled Forgetting은 과거 Observation을 복구 가능한 형태로 보관하는 방법을 제시합니다.

**셋째, 실제 시스템의 신뢰성은 검증과 복구에 달려 있습니다.** HPC 장애 복구 연구와 CodeQL 업데이트는 정확한 상태 분석, 실행 흐름 추적, 재현 가능한 검증이 얼마나 중요한지 보여줍니다.

오늘 가장 중요한 연구 질문은 다음과 같습니다.

> **LLM 아키텍처와 실행 시스템을 최적화할 때, 이론적 연산량이 아니라 실제 병목을 형성하는 데이터 이동과 실행 상태를 기준으로 설계하면 얼마나 개선할 수 있는가?**

특히 Zepp와 PageWeaver는 이 질문을 서로 다른 계층에서 다루고 있습니다. 두 논문을 함께 읽으면 **모델 아키텍처의 효율성과 실제 GPU 시스템의 효율성이 왜 반드시 일치하지 않는지** 이해하는 데 도움이 됩니다.
