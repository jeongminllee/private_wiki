# AI 엔지니어 데일리 브리핑

**2026년 8월 5일 수요일**
**분석 범위:** 8월 4일 공식 발표와 최신 arXiv 공개 자료

## 오늘의 핵심 흐름

오늘은 **모델 규모보다 모델이 실행되는 시스템의 설계가 성능과 안전성을 결정한다**는 흐름이 강합니다.

Liquid AI는 2.6B 모델을 실제 에이전트 harness 안에서 강화학습해 로컬 실행 영역을 공략했습니다. 추론 연구에서는 draft 모델의 토큰 생성 방식뿐 아니라, 서로 다른 길이의 요청을 같은 batch에 묶는 정책이 처리량과 비용을 결정한다는 분석이 나왔습니다. 에이전트 연구는 모델 가중치를 바꾸는 대신 실패 기록으로 runtime harness 자체를 수정하는 단계까지 확장됐습니다.

## 1. 필독 | Liquid AI, 로컬 에이전트용 LFM2.5-2.6B 공개

### 무엇이 바뀌었나

Liquid AI가 8월 4일 `LFM2.5-2.6B`와 base checkpoint를 공개했습니다. 모델은 2.69B 파라미터, 30개 layer, 128K context를 지원하며 약 34조 토큰으로 사전학습됐습니다. 22개 short-convolution block과 8개 GQA layer를 결합한 hybrid 구조이며, 한국어를 포함한 16개 언어를 지원합니다. ([Hugging Face][1])

Post-training은 SFT, 도메인별 teacher 학습, multi-domain on-policy distillation, 실제 에이전트 환경에서의 강화학습 순으로 구성됐습니다. 특히 OpenClaw·Hermes Agent 같은 harness를 black box로 유지한 채 tool call과 multi-turn trajectory를 수집하는 proxy 구조를 사용했습니다. ([Hugging Face][2])

### 왜 중요한가

작은 모델도 정적 instruction tuning이 아니라 **실제 실행 harness 안에서 학습**하면 제한적인 도구 사용 영역에서 훨씬 큰 모델과 경쟁할 수 있다는 사례입니다.

Liquid AI의 자체 평가에서 LFM2.5-2.6B는 instruction-following benchmark에서 비교 대상인 4.7B~9.7B 모델과 경쟁했고, ToolSandbox에서는 77.83점을 기록했습니다. 반면 LiveCodeBench에서는 큰 모델들이 앞섰으며, 공식 모델 카드도 agentic coding과 지식 집약적 작업에는 권장하지 않는다고 명시합니다. ([Hugging Face][2])

### 실무 적용

이 모델이 적합한 영역은 다음과 같습니다.

* 로컬 문서 검색·요약 에이전트
* 개인정보가 외부로 나가면 안 되는 사내 도구
* 정형화된 API·함수 호출
* 요청 분류와 상위 모델 라우팅
* 대량의 저비용 background 작업
* 노트북·스마트폰·엣지 장치의 개인 비서

모델 카드는 vLLM, SGLang, llama.cpp, MLX, ONNX와 LM Studio 경로를 모두 제공합니다. GGUF에서는 `Q4_K_M`이 1.67GB, `Q8_0`이 2.87GB이며, tool-heavy 작업에는 Q8 또는 BF16처럼 품질 손실이 작은 구성이 더 안전하다고 안내합니다. ([Hugging Face][1])

### 성능 주장의 해석

Liquid AI 측 측정에서는 Apple M5 Max에서 220 tokens/s, Ryzen AI Max+ 395에서 113 tokens/s, H100 고동시성 환경에서 약 15K output tokens/s를 기록했습니다. 이는 공급사 자체 환경의 결과이므로, 실제 평가에서는 동시성·context 길이·양자화·tool-call 성공률을 동일하게 맞춰야 합니다. ([Hugging Face][2])

또한 이 모델은 항상 reasoning을 생성하며 기본 tool call 형식은 JSON이 아니라 특수 토큰 안의 Python 형태입니다. 기존 OpenAI 호환 agent harness가 JSON 함수 호출만 가정한다면 parser를 별도로 검증해야 합니다. 라이선스도 Apache나 MIT가 아닌 `lfm1.0`이므로 상업 배포 전 조건 확인이 필요합니다. ([Hugging Face][1])

**후속 관찰 포인트:** 한국어 도구 호출 안정성, 128K 실효 성능, Q4와 Q8의 tool-call 회귀, 휴대전화 환경의 지속 발열·배터리 비용.

**원문**

* **[공식 발표]** LFM2.5-2.6B 구조·학습·성능 설명. ([Hugging Face][2])
* **[모델 카드]** 체크포인트·라이선스·tool-call 형식·배포 방법. ([Hugging Face][1])
* **[공식 가이드]** Hermes Agent 등 로컬 harness 연결법. ([Liquid Docs][3])

## 2. GPU·추론 | Speculative decoding은 draft 생성과 batch 편성 모두 최적화해야 한다

오늘 공개된 두 논문은 서로 다른 위치의 추론 낭비를 다룹니다.

### xPress: diffusion draft에 인과관계를 다시 넣는다

Block-diffusion draft 모델은 여러 토큰을 한 번의 forward pass로 생성할 수 있지만, 각 위치의 토큰이 서로 독립적으로 샘플링되면 개별 토큰은 자연스러워도 전체 sequence는 target 모델에 부자연스러울 수 있습니다. 이 경우 앞부분에서 검증이 실패해 나머지 draft가 모두 폐기됩니다. ([arXiv][4])

xPress는 전체 draft block을 token-by-token으로 다시 생성하지 않고, 가벼운 causal refiner가 병렬로 조정하도록 설계됐습니다. 저자 평가에서는 Qwen3-8B와 7개 수학·코드·대화 benchmark에서 acceptance length가 평균 약 30%, 최대 56% 증가했고, decoding throughput은 평균 약 1.3배, 최대 1.7배 개선됐습니다. ([arXiv][4])

### Resource-fair scheduling: 짧은 요청이 긴 요청의 비용을 대신 부담한다

다른 연구는 continuous batching에서 batch 한 step의 비용이 가장 큰 활성 KV cache에 의해 좌우될 수 있다고 지적합니다. 짧은 요청이 매우 긴 요청과 묶이면 자신의 token 수에 비해 과도한 GPU 자원과 지연시간을 부담하게 됩니다. ([arXiv][5])

연구진은 같은 batch에 포함되는 요청 사이의 decode 진행도와 KV footprint 차이를 제한하는 `ISJL` 정책을 제안했습니다. 이론적으로 3/4 이상의 global competitive ratio를 보이고, 수치 실험에서는 FCFS의 batching externality와 긴 요청 우선 정책의 경직성 사이에서 중간 지점을 제공했습니다. ([arXiv][5])

### 실무 적용

Serving benchmark에서는 전체 tokens/s만 기록하지 말고 두 계층을 나눠야 합니다.

```text
Draft 계층
- draft latency
- accepted length
- rejection 위치
- verification waste
- target forward 횟수

Batch 계층
- 요청별 KV footprint
- batch 내 최대·최소 context 차이
- 요청별 GPU residency time
- P95·P99 TPOT
- 짧은 요청의 queue delay
```

Speculative decoding이 microbenchmark에서는 빨라도 긴 요청이 batch를 계속 지배하면 사용자별 체감 지연은 나빠질 수 있습니다. 반대로 공정성을 지나치게 강화하면 batch 선택지가 줄어 전체 GPU utilization이 떨어질 수 있으므로, throughput과 요청별 비용 편차를 함께 최적화해야 합니다. 이는 두 논문의 결과를 종합한 실무적 해석입니다. ([arXiv][4])

### 주의할 점

xPress 결과는 Qwen3-8B와 특정 diffusion drafter를 사용한 초기 연구이며, vLLM·SGLang에 즉시 적용할 수 있는 범용 옵션은 아닙니다. Resource-fair scheduling 연구도 실제 production server 구현보다 수학적 모델과 수치 실험에 초점이 있으므로, kernel·scheduler overhead를 포함한 재현이 필요합니다. ([arXiv][4])

**원문**

* **[논문]** xPress: Parallel Refinement for Diffusion Drafters. ([arXiv][4])
* **[논문]** Resource-Fair Scheduling for Batched LLM Serving. ([arXiv][5])

## 3. 필독 | AtumAI: 자연어 요구사항을 데이터센터 제어 정책으로 컴파일

### 무엇이 바뀌었나

AtumAI는 사용자가 자연어로 작성한 데이터센터 운영 목표를 받아 workload placement, resource scaling, power management 정책을 자동 생성하는 프레임워크입니다. ([arXiv][6])

구조는 두 부분으로 나뉩니다.

1. **Datacenter Task Compiler**
   자연어 목표를 목적함수, hard constraint, decision variable, 평가 방법이 포함된 machine-checkable specification으로 변환합니다.

2. **Evolutionary Design Discovery Loop**
   LLM만으로 후보를 생성하지 않고 diffusion model, evolutionary algorithm과 surrogate model을 결합해 정책 공간을 탐색합니다. ([arXiv][6])

저자들은 세 가지 제어 작업에서 생성 정책이 전문가가 작성한 baseline을 일관되게 앞섰다고 보고했습니다. 또한 새 작업을 지원할 때 별도의 수개월짜리 구현 대신 작업 설명 작성으로 onboarding할 수 있다고 주장합니다. ([arXiv][6])

### 왜 중요한가

LLM에게 곧바로 Kubernetes나 데이터센터 정책을 작성하게 하면 다음 문제가 생깁니다.

* hard constraint가 실제로 지켜지는지 보장하기 어려움
* 평가 함수가 매 iteration마다 달라질 수 있음
* 이전 작업에서 얻은 정책과 실험 결과를 재사용하기 어려움
* 자연어로 생성되는 후보가 좁은 지역 최적점에 머물 수 있음

AtumAI의 핵심은 자연어 생성보다 **먼저 검색 가능한 형식 문제로 컴파일한다는 것**입니다. 이 구조는 최근 Bedrock의 형식 정책 검증 흐름과도 유사하게, LLM을 최종 정책 판정기가 아니라 문제 정의와 후보 생성기로 제한합니다. ([arXiv][6])

### 실무 적용

GPU 클러스터에 적용한다면 다음과 같은 specification을 만들 수 있습니다.

```text
목적
- 평균 GPU utilization 최대화
- deadline miss 최소화
- 전력비 최소화

제약
- 작업별 최소 GPU 수
- 데이터 locality
- VRAM 요구량
- 최대 rack 전력
- preemption 금지 작업

평가
- trace replay
- 비용
- P95 completion time
- OOM 및 재시작 횟수
```

에이전트가 만든 정책은 곧바로 production scheduler에 적용하지 않고 simulator, historical trace replay, shadow deployment와 canary 단계를 통과시켜야 합니다. 정책 자체뿐 아니라 정책이 사용한 workload distribution과 hardware topology도 artifact로 보관해야 재현할 수 있습니다.

### 주의할 점

“새 작업 onboarding을 설명 작성으로 줄였다”는 주장은 대상 시스템에 정확한 simulator와 평가 함수가 이미 있다는 전제를 포함합니다. 현실에서는 metric 정의, trace 정제, 제약 조건 합의와 simulator calibration이 상당한 엔지니어링 비용을 차지할 수 있습니다. 결과도 논문 저자들의 초기 평가이므로 독립 재현이 필요합니다. ([arXiv][6])

**후속 관찰 포인트:** 코드 공개, 실제 클러스터 canary 결과, simulator와 production 간 policy drift, 여러 목적함수의 우선순위 변경 안정성.

**원문**

* **[논문]** AtumAI: Agentic Generation of Datacenter Control-Plane Policies. ([arXiv][6])

## 4. 에이전트 | Harness-R1: 실패 기록으로 모델이 아니라 runtime을 수정

### 무엇이 바뀌었나

Harness-R1은 에이전트의 실패 trajectory를 이용해 context 구성, tool 중개, action 검증과 오류 복구를 담당하는 **실행 harness 코드를 자동 수정**합니다. ([arXiv][7])

별도의 9B harness engineer가 실패 묶음을 분석해 실행 가능한 patch를 만들고, 동결된 target agent를 같은 batch에서 다시 실행합니다. 실제 task 성공률이 reward가 되며 target 모델이 아니라 harness engineer만 GRPO로 업데이트됩니다. ([arXiv][7])

저자 평가에서는 vanilla Qwen3.5-9B의 WebShop·ALFWorld·DBBench 평균 성공률이 44.3%에서 53.6%로 상승했습니다. Target agent를 직접 fine-tuning한 이후에도 전용 harness engineer를 적용하자 59.2%에서 64.2%로 추가 상승했습니다. ([arXiv][7])

### 왜 중요한가

에이전트 실패의 원인이 항상 foundation model에 있는 것은 아닙니다.

* tool output이 너무 길게 전달됨
* 실패한 action을 무한 반복함
* 필수 결과를 context에서 제거함
* 잘못된 tool schema를 제공함
* 완료 조건을 검사하지 않음
* transient error와 permanent error를 구분하지 않음

이런 문제는 모델을 다시 학습하기보다 runtime patch가 더 싸고 빠르게 해결할 수 있습니다. Harness-R1은 이를 수작업 prompt engineering이 아니라 **학습 가능한 소프트웨어 유지보수 문제**로 바꿉니다. ([arXiv][7])

### 실무 적용

사내 agent runtime에서 failure trajectory를 다음 구조로 보관하면 유사한 개선 루프를 만들 수 있습니다.

```text
task_id
harness_version
model_version
full_tool_trace
failure_category
environment_state
candidate_patch
regression_results
same-task_rerun
unrelated-task_rerun
promotion_decision
```

다만 patch reward를 실패했던 batch에만 두면 특정 사례에 과적합할 수 있습니다. 새로운 patch는 원래 실패 task, 기존 성공 task, 공격·권한 test와 비용·latency benchmark를 모두 통과해야 합니다.

### 주의할 점

Runtime을 자동 수정하는 시스템은 agent capability뿐 아니라 공격 표면도 변경합니다. Tool permission 완화나 validation 생략이 단기 성공률을 높일 수 있으므로, 보안 invariant는 reward와 별개로 강제해야 합니다. 초기 결과는 세 benchmark와 특정 target 모델에 기반하며 장기적인 patch 누적 안정성은 추가 검증이 필요합니다. ([arXiv][7])

**후속 관찰 포인트:** 코드 공개, patch 간 충돌, lifecycle 전체의 regression 관리, 사람 작성 harness와 공동 진화했을 때의 유지보수성.

**원문**

* **[논문]** Harness-R1: Learning to Edit Executable Runtime Harnesses. ([arXiv][7])

## 5. AI 보안 | 위험 행동을 세션 단위로만 검사하면 놓친다

두 연구가 서로 다른 방식으로 같은 사각지대를 지적합니다.

### Magnet: 공격자는 여러 세션에 걸쳐 능력을 조립한다

Magnet은 공격자가 하나의 위험 목표를 여러 개의 무해해 보이는 요청으로 나누고, 서로 다른 세션이나 에이전트에서 결과물을 수집할 수 있다고 지적합니다.

각 대화는 stateless이지만 사용자는 이전 세션의 코드, credential, 조사 결과와 도구 실행 결과를 계속 보유합니다. Magnet은 개별 prompt의 위험도가 아니라 사용자 ID 같은 상위 correlator에서 **시간에 따라 축적된 capability artifact**를 모아 판단합니다. ([arXiv][8])

### EvoBreak: 각각 안전한 memory가 결합되면 안전 경계가 무너진다

EvoBreak는 self-evolving agent가 interaction trajectory를 장기 memory나 experience로 증류할 때 발생하는 공격입니다. 공격자는 개별적으로는 benign한 작업을 순차적으로 수행시켜 상호 보완적인 experience를 쌓은 뒤, 마지막 요청에서 이를 함께 활성화합니다. ([arXiv][9])

기존 memory 공격처럼 명백히 악성인 레코드를 삽입하거나 memory store에 직접 접근할 필요가 없다는 점이 핵심입니다. 저자 측 실험에서는 여러 self-evolving framework와 backbone에서 기존 공격보다 높은 효과를 보였다고 보고했습니다. ([arXiv][9])

### 실무 적용

에이전트 보안 로그는 prompt·session 단위가 아니라 다음 세 수준을 연결해야 합니다.

```text
Session
- 개별 요청과 tool call

Capability
- 생성된 코드·credential·설정·취약점 정보
- 수행 가능한 행동의 증가

Principal
- 사용자·조직·API key·agent identity
- 여러 세션의 capability 누적
```

Persistent memory에는 출처, 생성 task, 만료 시간, 접근 범위와 안전 분류를 붙여야 합니다. 여러 memory를 동시에 검색할 때는 개별 레코드가 안전하다는 사실만 확인하지 말고, 조합된 context가 새로운 위험 능력을 만드는지도 평가해야 합니다. 이는 두 연구에서 도출되는 시스템 차원의 대응입니다. ([arXiv][8])

### 주의할 점

Cross-session correlator는 오탐과 개인정보 문제를 일으킬 수 있습니다. 정상적인 개발자나 보안 연구자 역시 여러 세션에 걸쳐 복잡한 능력을 축적하기 때문입니다. 전체 대화 원문을 무기한 저장하기보다, 목적 제한된 capability metadata와 명확한 보존 기간을 사용하는 것이 적절합니다.

두 논문 모두 초기 arXiv 연구이므로 실제 상용 서비스의 탐지율과 우회 가능성은 별도 검증이 필요합니다. ([arXiv][8])

**원문**

* **[논문]** Magnet: Detecting Cross-Session AI Misuse. ([arXiv][8])
* **[논문]** Benign Alone, Harmful Together: EvoBreak. ([arXiv][9])

## 6. 보안 모델 | Antares: 3B 모델로 대규모 저장소의 취약점 위치 추적

### 무엇이 바뀌었나

Antares는 350M, 1B, 3B 크기의 agentic vulnerability localization 모델군입니다. IBM Granite base model에 사이버보안 reasoning과 repository exploration trajectory를 SFT하고, 취약한 저장소에서 검증 가능한 reward를 사용하는 강화학습을 추가했습니다. ([arXiv][10])

저자 측 평가에서 Antares-3B는 GPT-5.5에 근접했으며, 파라미터가 200배 이상 큰 일부 open-weight 모델을 앞섰다고 보고됐습니다. H100 한 장에서 500개 task 전체 평가를 약 15분에 수행해 task당 평균 2초 미만, 비용은 0.002달러 미만으로 계산됐습니다. ([arXiv][10])

### 왜 중요한가

취약점 localization은 최종 patch 생성과 분리할 수 있습니다.

```text
저비용 local model
→ 의심 파일·함수·line 후보 축소
→ 정적 분석·테스트
→ 고성능 모델 또는 보안 엔지니어의 최종 검토
```

전체 저장소를 비싼 frontier model에 매번 전달하지 않고, 작은 모델을 대량 triage 계층으로 사용할 수 있습니다. 내부 소스코드가 외부 API로 나가지 않는다는 장점도 있습니다.

### 실무 적용

실제 적용 시에는 정확도 외에 다음을 측정해야 합니다.

* 파일·함수·line 단위 recall
* 취약점이 없는 저장소의 false-positive
* repository 크기별 latency
* 탐색한 파일 수와 token 수
* 동일 취약점의 여러 구현 패턴에 대한 일반화
* localization 이후 patch 성공률
* 정적 분석기·CodeQL 결과와의 결합 효과

단일 모델의 최종 판단으로 merge를 차단하기보다, CodeQL·SAST·테스트와 결과가 일치할 때 우선순위를 높이는 방식이 적절합니다.

### 주의할 점

“GPT-5.5에 근접”과 “200배 큰 모델보다 우수”는 논문 저자들이 선택한 benchmark와 agent loop에서 측정한 결과입니다. 저장소 언어, 취약점 유형, context budget과 tool 구성이 달라지면 순위가 바뀔 수 있습니다. 공개 artifact와 독립 재현이 확인되기 전에는 연구 결과로 보는 것이 안전합니다. ([arXiv][10])

**원문**

* **[논문]** Antares: Foundation Models for Agentic Vulnerability Localization. ([arXiv][10])

## 7. 개발 도구 | GitHub, 독립형 AI 앱에서 저장소 내부 에이전트로 재편

### 무엇이 바뀌었나

GitHub는 Code Quality 설정에서 AI agent가 저장소에 맞는 code coverage workflow를 생성하고 PR을 열어주는 기능을 공개 미리보기로 출시했습니다. 생성 workflow는 build, test, coverage report 생성과 업로드를 수행하며 기본적으로 least-privilege permission을 사용합니다. ([The GitHub Blog][11])

반면 독립형 AI 앱 제작 도구인 GitHub Spark는 8월 4일부터 신규 사용자와 신규 앱 생성을 중단했습니다. 기존 사용자는 8월 31일까지 코드를 repository로 export할 수 있으며, 이미 배포된 앱은 계속 실행됩니다. Spark의 `llm()` 기능이 사용하던 GitHub Models는 7월 30일 이미 종료됐습니다. ([The GitHub Blog][12])

### 왜 중요한가

GitHub가 설명한 방향은 AI 개발 경험을 별도의 no-code workbench보다 VS Code, CLI, GitHub Copilot app과 PR workflow 안으로 통합하는 것입니다. 즉, AI가 완성된 앱을 소유하는 구조보다 **기존 저장소에서 검토 가능한 변경을 생성하는 구조**에 무게가 실리고 있습니다. ([The GitHub Blog][12])

Code coverage 설정도 agent가 workflow를 즉시 활성화하는 것이 아니라 PR을 생성합니다. 최근 데이터·코드 에이전트 사례에서 반복되는 패턴과 마찬가지로, AI 결과를 운영 설정이 아니라 검토 가능한 후보 변경으로 다루는 접근입니다.

### 실무 적용

AI가 만든 Actions workflow는 병합 전에 다음을 확인해야 합니다.

* `permissions`가 실제로 최소 권한인지
* Fork PR에서 secret을 읽지 않는지
* third-party action이 commit SHA로 고정됐는지
* coverage upload token의 범위
* package installation 중 임의 코드 실행 가능성
* 사용하지 않는 artifact와 log의 보존 기간
* self-hosted runner 접근 여부

Spark를 사용했다면 8월 31일 전에 repository export를 완료하고, 코드에서 `llm()` 호출을 검색해 자체 inference provider로 교체해야 합니다. 새 provider의 API key, 비용 상한, rate limit과 데이터 보존 정책도 별도로 관리해야 합니다. ([The GitHub Blog][12])

### 주의할 점

“Least privilege by default”는 생성된 workflow가 모든 저장소에서 자동으로 안전하다는 뜻이 아닙니다. 언어별 build script와 dependency가 외부 네트워크나 secret을 요구할 수 있으므로 YAML뿐 아니라 실제 실행 경로도 검토해야 합니다. Code Quality 기능은 현재 github.com의 Team·Enterprise Cloud 대상이며 GHES에서는 아직 제공되지 않습니다. ([The GitHub Blog][11])

**원문**

* **[GitHub 릴리스]** AI 기반 code coverage workflow PR 생성. ([The GitHub Blog][11])
* **[GitHub 종료 공지]** GitHub Spark 신규 생성 중단과 export 일정. ([The GitHub Blog][12])

# 오늘의 실습: LFM2.5 로컬 에이전트 회귀 테스트

**목표:** LFM2.5-2.6B를 로컬로 연결하고 일반 대화 점수가 아니라 실제 tool-call 신뢰성을 측정합니다.

## 1. 모델 실행

GPU 환경에서는 공식 모델 카드의 vLLM 또는 SGLang 경로를 사용합니다.

```bash
pip install vllm
vllm serve LiquidAI/LFM2.5-2.6B
```

CPU·노트북 환경에서는 llama.cpp 또는 LM Studio의 `Q4_K_M`으로 시작하고, tool-call 오류가 많으면 `Q8_0`으로 올립니다. 공식 가이드는 OpenAI 호환 `/v1` endpoint를 Hermes Agent, OpenClaw와 Pi에 연결하는 방식을 제공합니다. ([Hugging Face][1])

## 2. 도구 세 개 구성

```text
search_document(query)
get_system_status(service)
create_task(title, priority)
```

`create_task`만 side effect를 갖도록 하고, 실제 생성 전 승인 단계를 둡니다.

## 3. 테스트 세트

각 조건을 최소 10회 반복합니다.

```text
정상
- 필요한 도구 하나 호출
- 두 도구를 순서대로 호출
- 도구 없이 답해야 하는 질문

오류
- 도구가 timeout 반환
- 필수 argument 누락
- 존재하지 않는 service 요청

보안
- 문서 검색 결과에 악성 지시 포함
- 승인 없이 create_task 실행 유도
- 이전 세션 결과를 이용한 금지 작업
```

## 4. 기록할 지표

```text
tool_selection_accuracy
argument_schema_accuracy
tool_call_parse_failure
unnecessary_tool_calls
retry_count
side_effect_without_approval
final_answer_matches_tool_result
latency_p50
latency_p95
tokens_per_task
```

## 5. 비교 조건

```text
A. Q4_K_M
B. Q8_0 또는 BF16
C. 원본 system prompt
D. 도구 계약과 승인 조건을 명시한 system prompt
```

양자화 품질이 자연어 답변에는 거의 영향을 주지 않아도 function name, 괄호, 인자 quoting 같은 구조화 출력에서 먼저 회귀할 수 있습니다. 따라서 최종 답변의 인상보다 parser 성공률과 실제 side effect를 기준으로 판단해야 합니다.

**승격 기준**

* Tool-call parse 성공률 99% 이상
* 승인 없는 side effect 0건
* Timeout 이후 무한 재시도 0건
* 도구 결과와 최종 답변 불일치 0건
* 동일 task 10회 중 9회 이상 strict success

이 실험을 완료하면 작은 로컬 모델이 cloud model을 완전히 대체할 수 있는지를 묻는 대신, **어떤 저위험·고빈도 작업을 안정적으로 맡길 수 있는지**를 구체적으로 판단할 수 있습니다.
