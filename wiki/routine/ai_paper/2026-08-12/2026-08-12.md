## 1. 필독 | NVIDIA Nemotron 3.5 Lightning + NeMo Switchyard: “계획은 큰 모델, 실행은 작은 모델”

### 무엇이 바뀌었나

NVIDIA가 8월 11일 **Nemotron 3.5 Lightning**을 공개했습니다. 총 30B 파라미터지만 토큰당 약 3B만 활성화되는 MoE이며, Mamba-2·MoE·Attention을 결합한 hybrid 구조입니다. 공식 NVFP4 모델 카드 기준 context는 최대 1M token이고 BF16·NVFP4 checkpoint를 제공합니다. 모델 학습 단계부터 MTP를 포함했으며 DSpark·DFlash speculative drafter도 함께 제공합니다. vLLM, SGLang, TensorRT-LLM뿐 아니라 llama.cpp·Ollama·LM Studio 같은 로컬 경로도 지원합니다. ([NVIDIA Developer][1])

이 모델의 목표가 일반적인 “작은 frontier model”은 아닙니다. NVIDIA는 장기 에이전트의 `git pull`, tool-result validation, formatting, subagent delegation 같은 **고빈도 실행 단계**를 Lightning에 맡기고, 복잡한 계획과 문제 해결만 더 큰 frontier model로 보내는 구조를 명시적으로 제안합니다. NVIDIA 측 PinchBench 평가에서는 86% 정확도를 기록하면서 비슷한 정확도의 Qwen3.6 35B보다 10,000개 작업 완료 시간이 30% 짧았다고 보고했습니다. 이는 공급사 측 결과이므로 동일 harness에서 재검증해야 합니다. ([NVIDIA Developer][1])

같은 날 공개된 **NeMo Switchyard**가 이 구조를 실제 시스템으로 연결합니다. Switchyard는 provider-neutral SDK로 model endpoint와 routing logic을 분리하고, LLM classifier·stage router·escalation router 같은 training-free 방식과 residual-stream을 사용하는 tunable prefill router를 제공합니다. Stage router는 최근 tool activity를 보고 반복 오류·탐색이 길어지면 강한 모델로, 테스트가 통과하고 수정 작업이 안정되면 작은 모델로 내리는 방식입니다. ([NVIDIA Developer][2])

LangChain의 145개 multi-turn agent 평가에서 Lightning과 Claude Opus 4.8 사이에 escalation routing을 적용했을 때 frontier 호출은 전체의 7%였고, frontier-only 대비 비용이 74% 줄어든 대신 정확도는 약 6점 낮아졌습니다. Cognition의 별도 coding 평가에서는 Opus 5와 Kimi K2.7 routing이 Opus-only보다 평균 비용을 약 28% 낮추면서 정확도 차이를 2.8%p 안쪽으로 유지했다고 NVIDIA가 보고했습니다. 이 결과들도 partner/vendor 환경의 결과입니다. ([NVIDIA Developer][2])

### 왜 중요한가

이제 agent 비용 최적화의 단위가 **request routing**보다 더 작아지고 있습니다.

```text
Planner           → frontier reasoning model
Repository search → small execution model
Edit / formatting → small execution model
Repeated failure  → frontier escalation
Validation        → small / verifier model
```

특히 여러 번 tool call을 하는 coding·research agent에서는 최종 답을 만드는 한 번의 호출보다 중간 실행 호출의 총 token이 더 클 수 있습니다. 그러므로 작은 모델의 raw benchmark보다 **task당 frontier-call 비율과 strict-success당 총비용**이 더 중요한 지표가 됩니다. 이는 Switchyard의 stage/escalation routing 설계가 직접 겨냥하는 문제입니다. ([NVIDIA Developer][2])

### 주의할 점과 관찰 포인트

Router 자체가 새로운 failure point입니다. 작은 모델로 잘못 내리는 `missed escalation`과 불필요하게 큰 모델을 쓰는 `unnecessary escalation`을 모두 측정해야 합니다. 특히 모델이 변경되거나 API 가격·latency가 달라지면 과거에 학습한 routing boundary도 다시 검증해야 합니다. Nemotron의 최대 1M context도 실제 1M workload에서 품질·KV memory·TTFT가 모두 실용적이라는 의미는 아닙니다. ([NVIDIA Developer][2])

## 2. GPU·ML 인프라 | vLLM 0.27.0 → 0.27.1: Kimi K3부터 Rubin까지 한 번에

vLLM은 8월 10일 `v0.27.0`, 8월 11일 patch release인 `v0.27.1`을 공개했습니다. 0.27.1은 quantized DSpark Markov head 지원을 추가했고, 큰 변화는 561개 commit이 포함된 0.27.0에 집중돼 있습니다. ([GitHub][4])

가장 큰 변화는 **Kimi K3의 full-stack 지원**입니다. 모델·kernel뿐 아니라 Python/Rust frontend, AttnRes, DeepGEMM, compressed-tensors checkpoint, DSpark AR fusion과 shared-expert sharding까지 한 릴리스에 들어왔습니다. Qwen3.5 dense/MoE와 EVS video-token pruning, K-EXAONE-2.0-750B-A37B 등도 추가됐습니다. ([GitHub][4])

Blackwell 사용자에게는 FlashAttention 4 통합이 더 직접적입니다. SM100에서 FP8 KV cache와 head-dim 256 지원이 들어갔고, JIT·Triton kernel을 첫 요청 전에 warmup하는 인프라가 추가되어 **첫 production request가 kernel compilation 비용을 대신 지불하는 문제**를 줄입니다. DeepSeek-V4 경로에서는 sequence parallelism, workspace reuse, router/top-k 생략 등의 최적화가 추가됐으며 vLLM이 보고한 개별 변경 중 일부는 kernel 약 2배 또는 E2E TTFT 3~4% 수준의 개선을 냈습니다. ([GitHub][4])

분산 serving도 상당히 바뀌었습니다. DP+EP 외부 load balancer용 간소화된 fault-tolerance framework, elastic EP 준비, hybrid MLA+SSM 모델을 위한 NIXL prefill/decode disaggregation과 heterogeneous block size, TP↔DP 간 prefill/decode routing이 추가됐습니다. Rust frontend에는 health reporting, abort, model discovery와 KV-event discovery를 포함하는 gRPC control plane이 확장됐습니다. Rubin용 `sm_107` target과 NVLink all-reduce 경로도 이미 들어가기 시작했습니다. ([GitHub][4])

### 실무에서 특히 주의할 점

vLLM 0.27.0은 **PyTorch 2.13.0, torchvision 0.28.0, Triton 3.7.1로 올라가는 breaking environment change**입니다. 기존 container에서 vLLM wheel만 올리는 식의 업그레이드는 권하지 않습니다. PyTorch 2.13 자체도 새로운 torchcomms backend와 distributed stack 변화를 포함한 릴리스이므로 CUDA·FlashInfer·FlashAttention·custom extension을 포함해 별도의 immutable image로 regression test하는 편이 안전합니다. ([GitHub][4])

승격 시에는 평균 throughput보다 `cold-start TTFT`, `warm TTFT`, `KV capacity`, `speculative acceptance`, `EP imbalance`, `restart recovery`, `numerical delta`를 함께 기록해야 합니다. 이번 버전처럼 warmup·disaggregation·fault tolerance가 동시에 변하면 raw tok/s만으로 regression 원인을 구분하기 어렵습니다. ([GitHub][4])

## 3. 개발 도구 | GitHub Copilot: persistent memory + Ollama + air-gap + 모델별 token 회계

8월 11일 GitHub의 여러 변경을 묶어서 보면 coding agent가 단순한 SaaS IDE assistant를 넘어 **상태·로컬 모델·폐쇄망·FinOps를 갖춘 enterprise runtime**으로 가고 있다는 흐름이 보입니다. ([The GitHub Blog][6])

JetBrains용 Copilot은 이제 대화 session을 넘어 project 정보나 preference를 기억하는 **Copilot Memory**를 지원합니다. 동시에 Ollama를 BYOK model provider로 사용할 수 있어 JetBrains 안에서 local model을 선택할 수 있습니다. Enterprise managed setting에는 MCP server access, permission-bypass behavior와 OpenTelemetry 설정도 포함됐습니다. Codex session 역시 agent debug log에서 관측할 수 있게 됐습니다. ([The GitHub Blog][6])

더 흥미로운 것은 GHES 3.22 RC입니다. GitHub Cloud 연결이 없는 **disconnected/air-gapped 환경에서도 Copilot CLI**를 사용할 수 있도록, 관리자가 GHES에 모델 provider를 설정하고 사용자는 GHES credential로 접근하는 기술 미리보기가 추가됐습니다. 폐쇄망에서 코딩 에이전트를 사용하려는 조직에 상당히 중요한 architecture 변화입니다. ([The GitHub Blog][7])

FinOps 쪽에서는 AI usage report가 모델별로 `input`, `output`, `cache read`, `cache write` token과 소비된 AI credit을 같이 보여주기 시작했습니다. 이제 “이번 달 Copilot 비용이 왜 늘었나?”를 모델 선택뿐 아니라 **cache가 실제로 재사용됐는지, 긴 prompt가 반복됐는지**까지 내려가 분석할 수 있습니다. ([The GitHub Blog][8])

### 실무 적용과 주의점

Persistent memory는 편리하지만 새로운 state boundary입니다. 잘못된 repository assumption이나 오래된 API 정보를 memory가 여러 session에 걸쳐 재사용할 수 있으므로 memory를 단순 context cache가 아니라 **versioned persistent data**로 다뤄야 합니다. Ollama도 로컬 inference를 제공한다고 해서 agent가 접근하는 repository·MCP·shell의 권한 문제가 사라지는 것은 아닙니다. ([The GitHub Blog][6])

Copilot 운영 지표는 이제 `model`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `agent`, `task_result`, `PR_merged`를 연결할 수 있습니다. 가장 가치 있는 지표는 token 사용량 자체보다 `tokens_per_success`와 `credits_per_merged_PR`입니다. 전자는 GitHub가 제공하는 token accounting 위에 조직이 task outcome을 결합해 만드는 실무 지표입니다. ([The GitHub Blog][8])

## 4. AI 보안·산업 | OpenAI Daybreak Cyber가 Amazon Bedrock으로

OpenAI는 Daybreak의 사이버보안 모델을 AWS 환경에서 사용할 수 있도록 확대했습니다. **Daybreak Blue**는 GPT‑5.6 Sol을 포함한 frontier general-purpose model에 방어적 보안 workflow용 safeguards를 적용하고, **Daybreak Red**는 vulnerability research, exploit validation, security testing 같은 더 민감한 작업용 purpose-trained cyber model을 제공합니다. eligible customer는 Amazon Bedrock 환경 안에서 이를 사용할 수 있습니다. ([OpenAI][9])

동시에 OpenAI는 Accenture, IBM, Palo Alto Networks, CrowdStrike, Cisco, Sophos, EY, PwC 등 승인된 파트너가 Daybreak 모델을 managed security service와 고객 engagement에 활용하는 Cyber Partner Program을 발표했습니다. Red 모델 같은 민감한 capability는 customer에게 직접 weight나 unrestricted access를 넘기는 대신 승인 파트너가 identity verification, scope definition, logging, monitoring, human oversight를 포함하는 controlled engagement 안에서 사용하는 구조입니다. ([OpenAI][10])

### 왜 중요한가

frontier cyber capability의 enterprise 도입 모델이 보입니다.

```text
강한 cyber model
→ 일반 API 공개

가 아니라

강한 cyber model
→ verified principal
→ 명시적 testing scope
→ monitored execution
→ security expert
→ 고객 환경
```

즉 model alignment만으로 위험을 제어하기보다 **배포·신원·권한·감사 계층으로 capability access 자체를 관리**하는 방식입니다. 특히 exploit validation처럼 정상적 방어 연구와 공격 행동의 기술적 형태가 거의 동일한 영역에서는 이 방식이 중요합니다. OpenAI도 Daybreak Red를 더 closely governed work로 설명합니다. ([OpenAI][10])

### 주의할 점

현재 공개 자료에는 Red 모델의 상세 architecture·benchmark나 false-positive/false-negative 수준의 안전성 지표가 충분히 제시돼 있지 않습니다. 따라서 “frontier cyber model이 AWS에 들어왔으니 일반 기업이 즉시 자율 penetration agent를 만들 수 있다”는 해석은 잘못입니다. access 자체가 controlled이며, 실제 운영 품질·scope enforcement·audit granularity는 후속 자료를 봐야 합니다. ([OpenAI][9])

## 5. 머신러닝·서빙 연구 | 모델이 토큰마다 “몇 층까지 생각할지” 달라지면 batching도 다시 만들어야 한다

8월 10일 공개된 **Continuous Depth Batching(CDB)** 연구는 looped language model의 depth-adaptive inference를 실제 serving 문제로 다룹니다. Looped LM은 동일한 recurrent block을 여러 번 돌리되 쉬운 token은 일찍 종료하고 어려운 token은 더 많이 반복할 수 있습니다. 문제는 같은 batch 안에서도 token마다 필요한 loop 수가 달라지면서 일반적인 continuous batching의 “한 번의 통일된 forward pass” 가정이 깨진다는 것입니다. ([arXiv][11])

CDB는 scheduling 단위를 token이 아니라 **개별 loop iteration**으로 낮춥니다. Prefill, prelude, recurrent core, coda를 각각 queue로 분리하고, recurrent core에서 token 하나가 조기 종료하면 비어진 batch slot에 다른 token을 바로 refill합니다. Exit decision 때문에 CPU scheduler가 GPU를 기다리지 않도록 한 loop 앞에서 결정을 준비하는 lookahead gate를 사용하며, depth-aware KV-cache layout도 새로 도입했습니다. ([arXiv][11])

Ouro 1.4B와 Huginn 3.5B를 단일 80GB H100에서 평가한 결과, 논문 저자들은 이론상 adaptive-depth speedup의 최대 99%를 구현했고, fixed-depth continuous batching 대비 offline throughput 1.5~1.9배, dynamic serving의 normalized latency 45~90% 감소를 보고했습니다. ([arXiv][11])

### 왜 중요한가

최근 모델 연구에서 compute budget이 “출력 token 몇 개를 생성했는가”뿐 아니라 **한 token 내부에서 얼마만큼 latent computation을 했는가**로 이동하고 있습니다. 하지만 모델만 adaptive하게 만들어서는 실제 GPU latency가 줄지 않습니다. 쉬운 token이 일찍 종료해 FLOP은 줄었더라도 batch가 작아져 GPU가 memory-bound 상태라면 wall-clock은 거의 줄지 않을 수 있습니다. CDB의 refill은 이 빈 compute capacity를 다른 token으로 채우는 방식입니다. ([arXiv][11])

이 연구는 아직 1.4B·3.5B looped model과 단일 H100 실험입니다. 현재 대형 dense/MoE production LLM의 drop-in 최적화가 아니며, adaptive-depth architecture가 실제 frontier model로 확장될지부터 지켜봐야 합니다. 다만 **모델 구조를 바꾸면 scheduler와 KV-cache 구조도 함께 바꿔야 한다**는 co-design 원칙은 상당히 중요합니다. ([arXiv][11])

**원문:** **[논문] Depth-adaptive Inference via Continuous Depth Batching** ([arXiv][11])

## 6. AI 보안·평가 | ActBench: “답변이 안전한가?”가 아니라 “실제로 무엇을 했는가?”

8월 10일 공개된 **ActBench**는 cowork agent의 안전성을 최종 응답 대신 **execution trajectory와 실제 state transition**으로 평가합니다. 213개 operational scenario에서 benign/attack을 짝지은 600개 case를 만들고, context·reasoning·policy·action·persistent memory·environment라는 여섯 execution space와 48개 web-service API에 걸쳐 15종의 risk behavior를 평가합니다. ([arXiv][12])

Risk에는 prompt injection뿐 아니라 credential exposure, memory poisoning, state tampering, deceptive tool invocation, unauthorized command/API invocation, tool-scope escalation, resource exhaustion, false reporting, permission chaining 등이 포함됩니다. Attack 성공 판정도 단순 LLM judge가 아니라 trusted log에서 금지된 side effect가 실제 발생했는지를 확인하고 trajectory evidence를 함께 사용합니다. ([arXiv][12])

15개 LLM과 OpenClaw·Hermes·Claude Code 등을 포함한 6개 open-source cowork agent에서 총 24,000 trajectory를 실행했습니다. 동일 harness에서 model만 바꾸면 attack success rate가 10.1~94.4%까지 벌어졌고, 동일 base model에서 agent framework를 바꿔도 73.7~94.4%가 나왔습니다. 저자들의 환경에서는 model 차이가 더 컸지만 **어떤 harness도 공격을 충분히 제거하지 못했다**는 점이 더 중요합니다. ([arXiv][12])

### 실무 적용

Agent safety test를 다음 네 개의 결과로 나누는 것이 좋습니다.

```text
task_complete
forbidden_effect_occurred
policy_blocked
final_report_matches_state
```

예컨대 agent가 “비밀정보를 보내지 않았습니다”라고 대답해도 API audit log에 전송이 남았다면 safety failure입니다. 반대로 공격 prompt에 동의하는 문장을 만들었더라도 runtime policy가 실제 action을 완전히 차단했다면 side-effect safety 측면에서는 다른 결과입니다. ActBench가 바로 이 차이를 평가하려는 benchmark입니다. ([arXiv][12])

**주의:** 이는 새 arXiv benchmark이고 94.4%라는 수치를 실제 모든 cowork-agent 배포 환경의 compromise 확률로 해석하면 안 됩니다. 중요한 것은 절대 수치보다 **response-level 평가에서 trajectory/state-level 평가로 옮겨가는 방법론**입니다. ([arXiv][12])

**원문:** **[논문] ActBench** ([arXiv][12])

## 7. 연구 검증 | Agent가 “취약점을 재현했다”는 로그만으로는 취약점 검증이 아니다

8월 10일 공개된 독립 reproducibility 연구는 2023~2026년 LLM/agent 기반 vulnerability-validation 연구를 감사했습니다. 104개 논문 중 공개 artifact를 찾을 수 있었던 것은 59개(56.7%)였고, 선정한 18개 artifact 가운데 선언된 workflow를 수정 없이 끝까지 실행할 수 있었던 것은 10개(55.6%)였습니다. 환경 수준 수정만 허용한 뒤에도 11/18까지밖에 늘지 않았습니다. ([arXiv][13])

더 심각한 문제는 **oracle**이었습니다. Anchor benchmark의 102개 사례 중 58개에서 directory가 주장하는 CVE와 script 내부 CVE identifier가 달랐습니다. Signal이 발생한 30개 사례를 patched build에서도 실행했더니 20개가 여전히 같은 “취약점 성공” 신호를 냈고, benign negative control 19개 중 7개도 trigger됐습니다. 연구진이 계산한 artifact oracle의 sensitivity는 60%, specificity는 45%였습니다. ([arXiv][13])

### 왜 중요한가

보안 에이전트는 흔히 다음을 성공으로 간주합니다.

```text
PoC 실행
→ crash / 특정 문자열 / status code
→ "취약점 재현 성공"
```

하지만 patched binary에서도 같은 signal이 나온다면 그것은 **CVE-specific evidence가 아닙니다.**

더 강한 검증은 다음 형태입니다.

```text
vulnerable build → exploit signal
patched build    → signal 없음
benign control   → signal 없음
```

즉 agentic vulnerability research의 verifier는 모델과 독립된 **patched-counterfactual + negative-control oracle**이어야 합니다. 최근 cyber model의 capability가 강해질수록 더 많은 PoC가 자동 생성될 것이기 때문에 “생성 능력”보다 이 검증 계층이 오히려 병목이 될 수 있습니다. 이는 이번 연구와 Daybreak 같은 cyber-agent 확장을 함께 보면 특히 중요한 운영 포인트입니다. ([arXiv][13])

**주의:** 18개 paper-level artifact는 전체 분야를 완전히 대표하는 표본은 아니며, 저자들도 결과를 exploratory라고 표현합니다. 그러나 reproducibility protocol 자체—R0/R1 repair ladder, semantic evidence level, patched counterfactual—는 내부 보안 agent 평가에도 바로 차용할 가치가 있습니다. ([arXiv][13])

**원문:** **[논문] From Runnable to Verifiable** ([arXiv][14])

**1. Nemotron 3.5 Lightning + Switchyard.** 오늘 가장 중요한 시스템 설계 변화입니다. “최강 모델 하나”보다 **planner와 executor를 분리하고 오류·tool 상태에 따라 모델을 동적으로 올렸다 내리는 구조**가 실제 open-source stack으로 나왔습니다. ([NVIDIA Developer][1])

# 오늘의 실습 | “Planner는 큰 모델, Executor는 Lightning” 2단 라우터 만들기

오늘은 Switchyard 전체를 바로 도입하기보다 핵심 아이디어를 작은 benchmark로 재현하는 것이 좋습니다. Nemotron 3.5 Lightning NVFP4를 vLLM 0.27.1로 띄우고, 비교 대상으로 평소 사용하는 더 강한 reasoning model 하나를 둡니다. NVIDIA 모델 카드는 vLLM과 SGLang의 직접 serving 경로를 제공합니다. ([Hugging Face][3])

20~30개의 coding/tool task를 준비해 세 정책을 비교합니다.

```text
A. Frontier Only
모든 turn → 강한 모델

B. Lightning Only
모든 turn → Nemotron 3.5 Lightning

C. Stage Router
계획 / 반복 실패       → Frontier
파일 읽기 / tool 확인
edit / formatting
테스트 성공 후 정리    → Lightning
```

Stage Router의 첫 버전은 LLM router를 쓰지 말고 deterministic rule로 만드는 것이 좋습니다. 예를 들어 `consecutive_failures >= 2`, `tool_error`, `new_plan_required`이면 frontier로 올리고, 최근 3개 action이 안정적인 read/edit/test라면 Lightning으로 내립니다. NVIDIA의 Switchyard stage router도 최근 tool activity와 repeated error·exploration을 routing signal로 사용하는 구조입니다. ([NVIDIA Developer][2])

측정 지표는 `strict_success`, `frontier_calls`, `lightning_calls`, `input/output tokens`, `wall_clock`, `cost_per_success`, `unnecessary_escalation`, `missed_escalation` 정도면 충분합니다. 가능하면 speculative decoding도 끈 상태와 DSpark/DFlash를 켠 상태를 따로 측정해 **“executor 모델 자체의 decode 가속”과 “router가 줄여준 frontier 비용”을 분리**하십시오. Nemotron은 MTP·DSpark·DFlash 세 계열의 speculative path를 제공하므로 이 비교가 가능합니다. ([NVIDIA Developer][1])

성공 기준은 단순히 C가 가장 싸다는 것이 아닙니다. **Frontier-only의 strict success에서 2~3%p 이상 잃지 않으면서 frontier call 비율과 성공당 총비용을 의미 있게 줄이는 것**을 목표로 잡는 편이 좋습니다. 그렇게 하면 오늘 발표의 핵심인 “큰 모델을 덜 쓰는 것”이 아니라 **필요한 순간에만 큰 모델을 쓰는 agent architecture**를 직접 검증할 수 있습니다. ([NVIDIA Developer][2])
