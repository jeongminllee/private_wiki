# AI 엔지니어 데일리 브리핑

**2026년 8월 28일 금요일**
오늘은 **8월 27일 공개 자료를 최우선**으로 확인했습니다. 오늘의 핵심 흐름은 세 가지입니다. **에이전트가 소프트웨어를 넘어 실제 물리 장비를 조작하기 시작하면서 하드웨어 인터페이스와 safety boundary가 표준화되기 시작했고, 장기 reasoning·multi-agent serving의 병목은 모델 FLOPs보다 context·KV cache·workflow scheduling으로 이동하고 있습니다. 동시에 agent 평가와 multi-tenant serving에서는 OpenTelemetry와 GPU-level information-flow tracking처럼 모델 밖의 검증·보안 계층이 빠르게 중요해지고 있습니다.**

## 1. 필독 | Anthropic Model Hardware Standard — MCP 다음은 “AI가 실험실·공장 장비를 안전하게 조작하는 표준”

### 무엇이 바뀌었나

Anthropic이 **8월 27일 Model Hardware Standard(MHS)** 연구 프리뷰를 공개했습니다. MHS는 현미경, liquid handler, robotic arm, sensor 같은 물리 장비를 AI agent가 공통 방식으로 제어하기 위한 specification입니다. 초기 개발은 HHMI Janelia Research Campus와 시작됐으며, 현재 과학 연구소·로보틱스·제조 분야 파트너에게 제한적으로 공개되고 있습니다. 아직 오픈소스 표준은 아니며, 파트너 평가 후 공개할 계획입니다. ([Anthropic][1])

핵심 abstraction은 **device driver + 단순 primitive**입니다.

```text
Device-specific API
        ↓
MHS Driver
        ↓
read / write 등 공통 primitive
        ↓
MCP / CLI / API
        ↓
AI Agent
```

Driver에는 장비의 측정 가능 항목, 조정 가능한 parameter, 물리적 특성, safety limit 등을 자연어 tag로 기술할 수 있고 이를 바탕으로 agent용 reference file을 생성합니다. Agent는 MCP·CLI·code API를 통해 여러 장비를 하나의 workflow로 orchestration할 수 있습니다. ([Anthropic][1])

### 왜 중요한가

MCP가 **소프트웨어 tool의 공통 interface**를 만들었다면 MHS는 같은 개념을 physical world까지 확장합니다.

Physical agent에서 가장 위험한 구조는:

```text
LLM 판단
→ 바로 robot command
```

입니다.

MHS가 지향하는 구조는:

```text
LLM proposal
→ MHS driver
→ device capability
→ safety constraint
→ physical action
```

입니다. 즉 자연어 reasoning과 실제 actuator 사이에 **deterministic hardware contract**를 넣습니다.

Anthropic이 소개한 CMU 실험에서는 서로 다른 liquid handler, plate reader, robot arm, camera를 약 8시간 안에 통합했고 기존 vendor integration은 수주가 걸릴 수 있다고 설명합니다. 해당 serial-dilution workflow는 기존보다 약 3배 빨랐습니다. 이는 파트너의 특정 실험 결과이며 범용 성능 수치는 아닙니다. ([Anthropic][1])

Safety demo도 흥미롭습니다. 연구진은 missing plate, rotated plate, busy reader, disconnected camera, unreachable device, active emergency stop 등 여섯 오류 상태를 의도적으로 만들었고 **장비가 움직이기 전에 여섯 경우 모두 차단됐다고 보고했습니다.** 이것 역시 제한된 시험이지 전체 physical-agent safety 보장은 아닙니다. ([Anthropic][1])

### 실무 적용

로봇·실험 장비용 agent를 만든다면 tool schema에 command만 넣지 말고 다음을 device contract로 분리할 가치가 있습니다.

```text
device_capabilities
physical_limits
safe_operating_range
preconditions
interlocks
emergency_stop
expected_postcondition
```

특히 high-frequency motor control까지 LLM에게 맡기기보다 agent는 고수준 계획만 만들고, 실제 빠른 control loop는 장비 controller나 deterministic code가 담당하는 구조가 좋습니다. MHS도 긴 작업이나 agent reasoning보다 빠른 동작이 필요할 때 driver command를 code로 묶어 장비 측에서 수행하도록 설계합니다. ([Anthropic][1])

**후속 관찰 포인트:** 실제 open-source spec 공개, permission/capability model, 장비 vendor adoption, MCP와 MHS의 identity delegation, physical safety benchmark.

**원문:** [공식 발표 — Anthropic Model Hardware Standard](https://www.anthropic.com/news/model-hardware-standard-research-preview)

## 2. Gemini 3.5 Transcribe — STT가 “음성을 글자로 바꾸는 모델”에서 Voice Agent 전처리 계층으로

Google은 **Gemini 3.5 Transcribe**를 개발자용 public preview로 공개했습니다. 실시간용 `gemini-3.5-transcribe-live`와 녹음 파일용 `gemini-3.5-transcribe`를 분리하며, Live API에서는 **sub-second latency**, 녹음 API에서는 speaker attribution과 word-level timestamp를 제공합니다. 85개 이상의 언어를 자동 감지하고 custom vocabulary를 받을 수 있습니다. ([Google DeepMind][2])

Google이 인용한 Artificial Analysis 측정에서는 평균 WER가 streaming **4.0%**, non-streaming **2.6%**였고 time-to-final-transcription은 이전 Chirp 3 대비 70% 개선됐습니다. Google 자체 FLEURS 결과는 streaming 5.50%, non-streaming 5.04% WER입니다. ([Google DeepMind][2])

### 왜 중요한가

전통 STT pipeline은:

```text
Audio
→ 문자 그대로 transcription
→ LLM이 cleanup
→ LLM이 intent 추론
```

에 가깝습니다.

3.5 Transcribe는 self-correction, filler word 제거, formatting, custom vocabulary를 transcription 단계에서 처리합니다.

예를 들어 사용자가:

> “화요일… 아니 수요일 오후 세 시로 잡아줘.”

라고 말하면 단순 acoustic transcript보다 **의도에 가까운 clean text**를 반환하는 방향입니다. Voice agent에서는 후단 LLM이 처리해야 할 noise가 줄어듭니다.

Google Antigravity에서는 화면 context와 chat history를 함께 활용해 filename이나 active document 같은 domain vocabulary transcription을 개선하기도 합니다. ([Google DeepMind][2])

### 실무에서 주의할 부분

“더 깔끔한 transcript”가 항상 좋은 것은 아닙니다.

법률·의료·회의 기록처럼 **원문 보존이 중요한 환경**에서는 filler 제거·self-correction 정규화가 evidence를 바꿀 수 있습니다. 따라서 다음 두 출력을 분리하는 편이 안전합니다.

```text
verbatim_transcript
normalized_transcript
```

또 speaker attribution은 현재 녹음 audio에서 최대 세 화자를 공식 지원하고, 3명 초과는 experimental입니다. ([Google DeepMind][2])

Voice agent를 평가할 때 WER만 보지 말고 `entity accuracy`, `speaker error`, `finalization latency`, `tool-intent accuracy`도 같이 봐야 합니다. 주문번호나 파일명 한 글자를 틀리는 것은 일반 단어 하나를 틀리는 것보다 실제 task failure에 훨씬 큰 영향을 줍니다.

**후속 관찰 포인트:** 한국어 WER 세부 결과, streaming partial-result stability, 3+ speaker diarization, voice→tool-call end-to-end reliability.

**원문:** [공식 발표 — Gemini 3.5 Transcribe](https://deepmind.google/blog/intelligent-transcription-with-gemini-3-5-transcribe/) · [모델 카드 — Gemini 3.5 Audio](https://deepmind.google/models/model-cards/gemini-3-5-audio/?utm_source=chatgpt.com)

## 3. Agent MLOps | AgentCore Evaluations — Agent Framework가 달라도 OpenTelemetry만 맞으면 같은 평가기로

AWS는 8월 26일 **Amazon Bedrock AgentCore Evaluations의 framework-agnostic 구조**를 공개했습니다. LangGraph, LlamaIndex, OpenAI Agents SDK, Google ADK, Claude Agent SDK, Strands Agents가 모두 같은 evaluation pipeline을 사용할 수 있습니다. 공통 계약은 framework API가 아니라 **OpenTelemetry/OpenInference trace**입니다. ([Amazon Web Services][3])

Agent 실행은 다음 span들로 분해됩니다.

```text
invoke_agent
├─ chat
├─ execute_tool
├─ retrieval
├─ embedding
├─ memory read/write
└─ guardrail
```

AgentCore는 `session.id`와 `trace_id`를 이용해 session→turn→tool trajectory를 다시 구성하고 GoalSuccessRate, Correctness, Helpfulness, custom LLM judge 등으로 평가합니다. On-demand evaluation은 CI regression용, online evaluation은 production traffic sampling용입니다. ([Amazon Web Services][3])

### 왜 중요한가

지금 agent benchmark의 큰 문제는:

```text
Model A + Harness A + Evaluator A
vs
Model B + Harness B + Evaluator B
```

를 비교한다는 것입니다.

평가 layer를 telemetry contract로 분리하면 최소한:

```text
Harness A ─┐
Harness B ─┼→ 동일 OTel schema → 동일 evaluator
Harness C ─┘
```

가 가능합니다.

특히 여러 sub-agent 체계를 직접 만들고 있다면 **모델 교체와 harness 교체의 효과를 분리**하기 쉬워집니다.

### 실무 적용

지금부터 agent telemetry field를 다음 정도로 통일해두면 AWS를 사용하지 않더라도 가치가 있습니다.

```text
session_id
trace_id
agent_id

gen_ai.operation.name
gen_ai.request.model

tool.name
tool.arguments
tool.result

input_tokens
output_tokens

task_success
```

모델 provider나 harness를 바꿔도 동일 schema로 저장하면 이후 Langfuse·CloudWatch·자체 evaluator 등 backend를 바꾸기 쉽습니다.

### 주의할 점

평가가 trace에 의존하므로 **instrumentation이 틀리면 평가도 틀립니다.**

AWS도 span만 있고 message event가 없으면 Correctness 같은 response evaluator가 실행되지 않는다고 설명합니다. 또 prompt·tool result를 OTel backend에 그대로 보내면 source code, PII, credential이 telemetry에 저장될 수 있습니다. ([Amazon Web Services][3])

따라서:

```text
metadata     → 항상 수집
token counts → 항상 수집
prompt/body  → redaction / sampling
secret       → 절대 기록 금지
```

정도로 계층화하는 것이 좋습니다.

**후속 관찰 포인트:** GenAI OTel semantic convention의 안정화, evaluation result portability, multimodal/tool side-effect evaluator, LLM judge 비용.

**원문:** [AWS 공식 발표 — Framework-Agnostic AgentCore Evaluations](https://aws.amazon.com/blogs/machine-learning/evaluate-any-agent-framework-with-amazon-bedrock-agentcore-evaluations/?utm_source=chatgpt.com)

## 4. 필독 | Prefix Sliding — reasoning이 10만 token을 넘어가도 전체 사고 기록을 계속 들고 있을 필요가 있는가?

8월 27일 신규 논문 **Prefix Sliding**은 test-time scaling의 매우 단순하지만 강한 아이디어를 제안합니다.

기존 reasoning model은:

```text
Prompt
+ token 1
+ token 2
+ ...
+ token 100,000
```

전체 reasoning trace를 attention context에 계속 유지합니다. 따라서 reasoning이 길수록 다음 token 한 개의 attention 비용과 KV memory가 계속 증가합니다. ([arXiv][4])

Prefix Sliding은 다음 두 부분만 유지합니다.

```text
[고정 Prefix]
system prompt
task
tool descriptions

+

[Sliding Window]
가장 최근 reasoning 몇천 token
```

그 사이의 오래된 intermediate reasoning은 버립니다.

논문 예시처럼 prefix가 100 token, sliding window가 4,096이면 모델이 백만 token을 reasoning해도 **attention에서 유지하는 상태는 약 4,196 token으로 일정**해집니다. ([arXiv][4])

### 결과

저자 실험에서는 별도 학습 없이 기존 model을 **최대 약 3배 빠르게 하면서 성능을 유지**했고, RL과 결합하면 100K token 이상의 reasoning trajectory도 학습할 수 있었습니다. 주 실험은 Qwen3-1.7B와 math reasoning benchmark를 사용했으며 custom Hopper FlashAttention kernel을 구현했습니다. ([arXiv][4])

### 왜 중요한가

Long-horizon agent context 관리에도 상당히 직접적인 아이디어입니다.

현재 많은 harness는:

```text
전체 reasoning
→ summary
→ 다시 context
```

를 사용합니다.

그런데 summary 자체에도 token과 LLM inference가 필요하고, 잘못 요약하면 중요한 state를 잃습니다.

Prefix Sliding의 관점은 더 공격적입니다.

> **오래된 사고 과정 자체가 필요한가, 아니면 system/task state와 최근 작업만 있으면 되는가?**

즉 intermediate reasoning과 durable state를 분리합니다.

Agent에서는 다음 정보를 prefix/structured state에 남기고:

```text
requirements
tool contracts
confirmed facts
experiment results
current plan
```

버려도 되는 exploratory reasoning은 sliding history로 처리할 수 있습니다.

### 주의할 점

모든 reasoning task가 오래된 intermediate state를 잊어도 되는 것은 아닙니다. 수십 단계 전의 증명 lemma, 긴 코드 분석에서 발견한 dependency, 여러 도구 결과를 다시 참조해야 하는 작업에서는 regression이 발생할 수 있습니다.

또 3배 결과는 주로 작은 Qwen 모델·reasoning benchmark의 연구 결과이며 production frontier model의 3배 speedup으로 일반화할 수 없습니다. ([arXiv][4])

**후속 관찰 포인트:** 7B~70B 규모, coding agent, vLLM/SGLang upstream, structured memory와 Prefix Sliding의 결합.

**원문:** [논문 — Prefix Sliding for Efficient Test-Time Scaling](https://arxiv.org/abs/2608.26070?utm_source=chatgpt.com) · [GitHub — Prefix Sliding 구현](https://github.com/Muennighoff/prefix-sliding?utm_source=chatgpt.com)

## 5. GPU·Multi-Agent Serving | TOPAS — 어떤 Agent의 KV Cache를 남길지 “현재 요청”이 아니라 전체 Workflow로 결정

TOPAS는 multi-agent serving에서 꽤 실용적인 문제를 다룹니다.

긴 system prompt의 KV cache를 GPU에 계속 보존하면 해당 agent의 다음 요청은 빨라집니다. 하지만 KV가 HBM을 점유해 다른 request의 batch size는 줄어듭니다.

```text
Agent A prefix 보존
→ A 다음 호출 빠름
→ GPU memory 감소
→ B/C batching 악화
```

기존 scheduler는 보통 cache locality 또는 현재 queue latency 중 하나를 우선합니다. TOPAS는 **workflow DAG 전체의 남은 critical path**까지 함께 고려해 어떤 prefix를 보존하고 어떤 request를 먼저 실행할지 공동 결정합니다. ([arXiv][5])

SGLang에 구현한 평가에서 synthetic DAG workload의 mean/p99 job completion time은 best baseline 대비 최대 **39.8% / 49.4% 감소**했습니다. MetaGPT software-development workflow에서는 MetaGPT-SOP mean JCT -9.8%, MetaGPT-TL mean/p99 -22.0%/-26.6%를 보고했습니다. ([arXiv][5])

### 왜 중요한가

Multi-agent serving의 최적화 목표가:

```text
request latency
```

에서:

```text
whole-task completion time
```

으로 이동한다는 의미입니다.

예를 들어:

```text
Planner
   ↓
Retriever
   ↓
Coder
   ↓
Reviewer
```

에서 Retriever 요청을 100ms 빨리 처리해도 Coder prefix를 eviction해서 5초가 늘면 전체 task에는 손해입니다.

따라서 앞으로 scheduler에는 `agent_id`만 아니라:

```text
workflow_id
stage
dependencies
critical_path
future_prefix_reuse
```

같은 정보가 들어갈 가능성이 큽니다.

### 실무 적용

현재 SGLang/vLLM 환경에서도 먼저 trace를 이용해 다음을 계산해볼 수 있습니다.

```text
prefix_size
prefix_reuse_interval
cache_hit
stage_wait_time
task_completion_time
```

그 뒤 LRU cache와 “다음 stage가 곧 실행될 prefix를 pin하는 정책” 정도만 비교해도 workflow-aware cache의 효과를 확인할 수 있습니다.

### 주의할 점

TOPAS는 세 synthetic DAG와 두 MetaGPT workflow의 초기 연구입니다. 실제 production에서는 다음 stage의 실행 시간과 future prefix reuse 확률을 정확하게 알기 어렵습니다.

잘못 예측하면 오히려 large prefix를 오래 pin해 전체 throughput을 낮출 수 있습니다. Scheduler 계산 자체의 overhead도 커질 수 있습니다. ([arXiv][5])

**후속 관찰 포인트:** 실제 coding-agent trace, dynamic workflow, LMCache와 결합, workflow hint를 MCP/agent harness에서 inference server로 전달하는 표준.

**원문:** [논문 — TOPAS: Workflow-Aware Prefix-State Scheduling](https://arxiv.org/abs/2608.25523)

## 6. AI 보안·GPU | GIFT — Multi-Tenant LLM에서 User Isolation을 CPU Sandbox가 아니라 GPU Data Flow까지 추적

공유 GPU LLM server에는 조금 불편한 보안 문제가 있습니다.

```text
User A prompt
User B prompt
        ↓
같은 CPU serving process
        ↓
같은 GPU
        ↓
shared kernels / buffers / cache
```

Application layer에서 tenant를 분리해도 GPU 내부 data movement가 제대로 격리되는지를 증명하기는 어렵습니다.

8월 26일 공개된 **GIFT(GPU Information Flow Tracking)**는 이를 GPU information-flow 문제로 다룹니다. ([arXiv][6])

### 구조

첫 번째 아이디어는 **encryption-as-isolation**입니다.

CPU serving framework는 주로 data를 orchestration할 뿐 내용 자체를 계산하지 않는다는 관찰을 이용해 user별 데이터를 암호화된 상태로 CPU 측에서 이동시킵니다.

GPU에서는 kernel별 정보 흐름이 비교적 제한적이고 예측 가능하다는 점을 이용해 **각 kernel의 static information-flow rule을 미리 계산**하고 별도의 tracker가 데이터 provenance를 따라갑니다.

```text
User A encrypted input
       ↓
GPU kernel
       ↓
A-tainted buffer
       ↓
A만 접근 가능
```

Kernel 자체를 instrument하지 않기 때문에 GPU stall을 피하는 것이 핵심입니다. ([arXiv][6])

OS·hypervisor까지 신뢰하지 않는 환경을 위해 confidential computing을 결합한 **GIFT-CC**도 제안합니다.

vLLM과 DistServe 구현에서는 throughput overhead가 **4~10.7%**, latency는 동일 수준으로 유지됐다고 저자들은 보고했습니다. ([arXiv][6])

### 왜 중요한가

LLM privacy를:

```text
container isolation
```

만으로 해결하는 것이 아니라:

```text
request → CPU → DMA → GPU buffer → kernel → output
```

전체 정보 흐름으로 보는 접근입니다.

특히 여러 tenant를 동일 GPU에서 batch하는 enterprise inference에서는 좋은 보안 모델입니다.

### 주의할 점

GIFT는 모든 임의 GPU program에 magic처럼 적용되는 것이 아닙니다. **Kernel의 정보 흐름을 사전 분석할 수 있다는 가정**이 중요합니다.

Runtime-generated kernel, custom Triton/CUDA extension, 새로운 fused kernel이 계속 추가되는 inference stack에서는 flow rule 유지·검증이 별도의 supply-chain 문제가 될 수 있습니다.

암호화 key lifecycle도 실서비스에서는 중요한 운영 부담입니다.

그리고 4~10.7%는 연구 구현의 throughput overhead이지 범용 production SLA는 아닙니다.

**후속 관찰 포인트:** Triton/JIT kernel 지원, KV-cache isolation, continuous batching, Blackwell confidential computing, malicious custom kernels.

**원문:** [논문 — GIFT: GPU Information Flow Tracking for LLM Serving](https://arxiv.org/abs/2608.25431)

## 7. Agentic Inference | AsymSpec — 작은 Draft Model에는 전체 Context, 큰 Model에는 압축 Context만 준다

AsymSpec은 speculative decoding의 전제를 뒤집습니다.

일반 speculative decoding:

```text
Draft model    → Full context
Target model   → Full context
```

이어야 target이 draft token을 정확하게 verify할 수 있습니다.

문제는 장기 agent context가 커질수록 **큰 verifier가 매 turn 거대한 context를 읽는 비용**이 커진다는 점입니다.

AsymSpec은 다음처럼 비대칭으로 구성합니다.

```text
Small Drafter → Full context
Large Verifier → Compressed context
```

그리고 drafter의 full-context logits 정보를 large verifier에 보정 신호로 사용합니다. ([arXiv][7])

저자 평가에서는 네 agent capability와 두 end-to-end agent benchmark에서 full-context 성능의 평균 약 **90%**를 유지했고, isolated text capability에서는 **1.3~1.7배 throughput**, full-context 대비 **0.2~0.3배 compute cost**를 보고했습니다. ([arXiv][7])

### 왜 중요한가

대부분의 context compression은:

```text
전체 context
→ 요약
→ 모든 모델이 요약본만 봄
```

입니다.

AsymSpec은 작은 모델에는 상세 context를 남겨두고 **비싼 모델에게만 context tax를 줄이는 것**입니다.

Agent router 관점에서는 꽤 흥미로운 구조입니다.

```text
Cheap model
→ full repository/tool history 보유

Expensive model
→ compressed state만 처리

Cheap model이
→ 누락된 context signal 보완
```

### 가장 중요한 주의사항

이건 **고전적 의미의 lossless speculative decoding이 아닙니다.**

Verifier가 원본 full context가 아니라 compressed context를 보기 때문에 결과 distribution 자체가 달라지고, 논문도 성능을 “full-context accuracy의 약 90%”라고 보고합니다.

즉 목표는:

```text
동일 출력 더 빠르게
```

가 아니라:

```text
일부 품질 손실을 허용해
context compute를 크게 줄이기
```

입니다.

Production에서는 `accuracy × cost × latency`의 Pareto problem으로 봐야 합니다.

**후속 관찰 포인트:** coding agent의 long tool history, compression strategy별 결과, drafter context memory 비용, Prefix Sliding과의 결합.

**원문:** [논문 — AsymSpec: Context-Asymmetric Speculative Decoding for Agentic LLMs](https://arxiv.org/abs/2608.26004)

# 오늘 꼭 볼 것 3개

**1. Anthropic Model Hardware Standard.** 오늘 가장 큰 방향 변화입니다. MCP가 software tool을 표준화했다면 MHS는 **AI agent와 physical machine 사이의 hardware contract**를 만들려는 시도입니다. 특히 natural-language hardware metadata와 deterministic safety limit을 분리한 구조를 보세요. ([Anthropic][1])

**2. Prefix Sliding.** LLM reasoning cost가 “얼마나 오래 생각하느냐”에 따라 무한히 커질 필요가 없다는 간단하지만 강한 아이디어입니다. 장기 agent의 context management에도 직접적으로 연결됩니다. ([arXiv][4])

**3. GIFT.** Multi-tenant inference security를 container/IAM에서 끝내지 않고 **GPU kernel과 buffer까지 information-flow tracking 대상으로 본다**는 점이 중요합니다. 자체 inference infrastructure를 운영한다면 꽤 생각할 거리가 많은 논문입니다. ([arXiv][6])

# 오늘의 실습 | Agent Framework가 달라도 비교 가능한 “공통 Evaluation Trace” 만들기

오늘은 AWS AgentCore Evaluations의 핵심 아이디어를 AWS 없이 작은 규모로 재현해보는 것을 추천합니다. 목표는 **모델·harness를 교체해도 같은 평가 코드를 재사용하는 것**입니다. ([Amazon Web Services][3])

먼저 agent 내부 구현과 무관하게 아래 event schema만 고정합니다.

```text
session_start

llm_call
  model
  input_tokens
  output_tokens
  latency_ms

tool_call
  tool_name
  arguments

tool_result
  success
  latency_ms

session_end
  final_answer
  task_success
```

가능하면 OpenTelemetry naming에 맞춰 다음 attribute를 사용합니다.

```text
session.id
trace_id

gen_ai.operation.name
gen_ai.request.model
gen_ai.tool.name
```

그 다음 **동일한 10개 task**를 서로 다른 두 agent 구성에 실행합니다.

예를 들어:

```text
A. 현재 사용하는 Agent Harness

B. 동일 모델 + 다른 Harness
```

또는:

```text
A. Same Harness + Local Model
B. Same Harness + Frontier Model
```

각 run을 같은 evaluator 하나로 처리합니다.

```text
strict_success
tool_selection_accuracy
retry_count

tokens_per_success
tool_calls_per_success
wall_clock_per_success
```

결과 표는 다음 정도면 충분합니다.

| Configuration | Success | Tokens / Success | Tool calls | Wall-clock |
| ------------- | ------: | ---------------: | ---------: | ---------: |
| A             |         |                  |            |            |
| B             |         |                  |            |            |

여기서 한 단계 더 중요한 실험을 추가하십시오. **모델을 바꾸지 않고 Harness만 변경합니다.**

예를 들어 B에:

```text
retry limit
context compaction
persistent memory
Skill
```

중 하나만 추가합니다.

그러면 성능 차이가:

```text
Model capability
```

때문인지,

```text
Harness architecture
```

때문인지 분리해서 볼 수 있습니다.

마지막으로 telemetry payload에는 source code나 credential을 그대로 넣지 말고 다음처럼 분리하십시오.

```text
항상 기록
→ model, timing, token count, tool name

선택적 기록
→ prompt, arguments, tool result

절대 기록 금지
→ API key, password, private credential
```

이 작은 harness를 만들어두면 이후 vLLM 모델, Claude/Codex, Qwen, Gemini 등을 바꿀 때도 **항상 같은 `success × cost × latency` 기준으로 비교**할 수 있습니다. 최신 Agent 시스템에서 모델보다 먼저 만들어둘 가치가 있는 자산 중 하나입니다. ([Amazon Web Services][3])
