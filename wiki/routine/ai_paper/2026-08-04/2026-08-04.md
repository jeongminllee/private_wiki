**2026년 8월 4일 화요일**
**분석 범위:** 8월 3일 공식 발표와 7월 말 공개·개정된 주요 논문 및 릴리스

## 오늘의 핵심 흐름

오늘의 공통 주제는 **생성 자동화에서 검증 자동화로 중심이 이동하고 있다는 것**입니다.

Amazon Bedrock은 자연어 정책을 형식 논리로 바꾸는 과정의 오류를 자동 진단하기 시작했고, Formula 1은 에이전트가 데이터 파이프라인을 직접 생성하되 변경 사항은 기존 PR·리뷰 절차를 통과하도록 설계했습니다. 동시에 음성 입력과 학습 공급망에서는 기존 텍스트 프롬프트 필터만으로 막기 어려운 새로운 공격 표면이 확인되고 있습니다. ([Amazon Web Services, Inc.][1])

## 1. 필독 | Amazon Bedrock, 형식 논리 정책의 자동 수정 제안 기능 공개

### 무엇이 바뀌었나

AWS는 8월 3일 Amazon Bedrock Automated Reasoning의 **자동 정책 개선 기능**을 발표했습니다. 기존에는 테스트 실패 원인을 사람이 분석하고 규칙을 직접 수정한 뒤 재시험해야 했지만, 이제 refinement engine이 실패를 진단하고 형식 논리 변경안을 제안합니다. 변경 사항은 자동 적용되지 않으며 사용자가 승인해야 효력이 생깁니다. ([Amazon Web Services, Inc.][2])

새 기능은 실패 원인을 두 종류로 나눕니다.

* **Iterative Refinement:** 형식 규칙 자체가 잘못되거나 빠진 경우
* **Ambiguous Variable Refinement:** 자연어를 변수 값으로 변환하는 설명이 모호한 경우

Bedrock의 검증 파이프라인은 먼저 자연어 입력과 출력을 변수 할당으로 변환하고, 그다음 형식 규칙을 적용합니다. 따라서 같은 테스트 실패라도 번역 단계의 문제인지 논리 규칙의 문제인지에 따라 수정 대상이 달라집니다. 결과는 `VALID`, `INVALID`, `SATISFIABLE`, `IMPOSSIBLE`, `TRANSLATION_AMBIGUOUS` 등의 상태로 반환됩니다. ([Amazon Web Services, Inc.][1])

### 왜 중요한가

LLM 기반 정책 시스템의 오류는 흔히 “모델이 규칙을 지키지 않았다”로 뭉뚱그려지지만 실제로는 세 계층으로 나뉩니다.

```text
자연어 정책
   ↓
변수·사실 추출
   ↓
형식 규칙 적용
   ↓
허용·차단 판정
```

예를 들어 “계약직은 100만 원 이상의 비용을 지출할 수 없다”는 정책에서 `temporary employee`를 계약직으로 분류하지 못했다면 규칙이 아니라 자연어→변수 변환 문제입니다. 반대로 분류는 정확하지만 승인 예외 조건이 빠졌다면 형식 규칙의 문제입니다.

이 구분이 중요한 이유는 잘못된 규칙을 계속 추가하면 특정 테스트는 통과하면서 전체 정책은 더 복잡하고 취약해질 수 있기 때문입니다.

### 실무 적용

자동 수정안을 곧바로 운영 정책에 반영하기보다 코드 변경과 동일하게 다루는 것이 좋습니다.

```text
실패 테스트
→ 원인 분류
→ 정책 변경안 생성
→ 변경 diff 검토
→ 전체 회귀 테스트
→ 반례 생성
→ 사람 승인
→ 버전 승격
```

다음 정보를 변경 artifact로 남겨야 합니다.

```text
policy_version
failed_test_id
failure_stage
proposed_rule_diff
affected_variables
regression_result
counterexample
approver
deployment_time
```

특히 하나의 실패 사례를 고치면서 기존 허용 사례가 차단되거나 금지 사례가 허용되는지 반드시 전체 테스트로 확인해야 합니다.

### 주의할 점

AWS가 언급한 최대 99% 검증 정확도는 **자연어가 형식 논리로 모호하지 않게 변환됐다는 전제**에서의 수치입니다. 자연어 정책 문서 자체가 불완전하거나 변수 정의가 모호하면 형식 검증기는 잘못 표현된 정책을 매우 정확하게 검증할 수 있습니다. ([Amazon Web Services, Inc.][2])

**후속 관찰 포인트:** 수정안의 최소성 보장, 기존 테스트에 대한 과적합, 정책 간 충돌 탐지, Cedar·OPA 및 MCP gateway와의 연동.

**원문**

* **[공식 발표]** Amazon Bedrock Automated Reasoning policy refinement. ([Amazon Web Services, Inc.][2])
* **[기술 설명]** Automated Reasoning의 정책 생성·테스트 구조. ([Amazon Web Services, Inc.][3])

## 2. 필독 | Formula 1: 데이터 소스 온보딩을 6~8주에서 약 40분의 코드 생성으로

### 무엇이 바뀌었나

Formula 1과 AWS는 MarTech 데이터 플랫폼을 위한 **Data Accelerator** 운영 사례를 공개했습니다. 기존에는 새 데이터 소스 하나를 연결하는 데 6~8주가 걸렸고 12개 소스에 대해 18개월의 backlog가 쌓여 있었습니다. 새 시스템에서는 코드 생성 자체를 약 40분 안에 수행하고, 이후 배포와 검토에 수 시간이 사용된다고 설명합니다. ([Amazon Web Services, Inc.][4])

작업 흐름은 다음과 같습니다.

1. 담당자가 데이터 소스의 Business Requirements Document를 S3에 업로드
2. AgentCore에서 실행되는 에이전트가 설정 파일 생성
3. GitHub App을 통해 PR 생성
4. Jira ticket과 PR 연결
5. 사람이 설정을 검토하고 승인
6. 승인 후 인프라·DBT 변환·GDPR 거버넌스용 PR을 별도로 생성
7. 각 저장소 담당자가 다시 검토 후 배포

모든 대화와 동작은 추적되며, 운영 측은 데이터 lineage와 root-cause analysis를 함께 구축했습니다. ([Amazon Web Services, Inc.][5])

### 왜 중요한가

여기서 중요한 부분은 에이전트가 데이터 파이프라인 코드를 생성했다는 사실이 아닙니다. **기존 엔지니어링 workflow를 우회하지 않았다는 것**입니다.

```text
에이전트 출력
≠ 운영 환경 직접 변경

에이전트 출력
= 리뷰 가능한 PR 후보
```

Infrastructure, transformation, governance를 서로 다른 PR로 나눈 것도 의미가 있습니다. 하나의 대형 변경으로 만들면 데이터 변환 오류와 IAM·GDPR 정책 오류를 독립적으로 검토하기 어렵습니다.

### 실무 적용

유사한 데이터 온보딩 에이전트를 만들려면 먼저 파이프라인을 표준화해야 합니다.

* 입력 요구사항을 위한 BRD schema
* source별 configuration contract
* ingestion·transformation template
* 데이터 품질 검사 규칙
* PII·GDPR classification
* lineage metadata
* deployment·rollback procedure

에이전트가 자유롭게 전체 코드를 작성하게 하기보다, 정해진 template의 빈칸을 채우고 필요한 경우에만 확장 코드를 생성하게 하는 편이 안정적입니다.

운영 지표도 코드 생성 시간만 보면 안 됩니다.

```text
PR 승인 전 수정 횟수
배포 후 schema 오류
데이터 품질 실패율
rollback 횟수
GDPR 분류 오탐·미탐
사람의 검토 시간
장애당 평균 복구 시간
```

### 주의할 점

AWS와 F1은 에이전트가 온보딩 작업의 95%를 사람 개입 없이 처리하고 총 소요 시간을 약 99% 줄였다고 설명합니다. 다만 코드 생성 이후에도 사람의 검토·승인과 수 시간의 배포 작업이 남으며, 공개 수치는 공급자와 고객이 공동 발표한 내부 운영 결과입니다. 독립 벤치마크로 해석해서는 안 됩니다. ([Amazon Web Services, Inc.][5])

**후속 관찰 포인트:** 운영 이후 오류율, 에이전트가 만든 schema migration의 rollback 성공률, 새로운 형태의 데이터 소스에 대한 일반화, 사람 검토 시간이 실제로 얼마나 감소했는지.

**원문**

* **[AWS·F1 기술 사례]** Agentic Data Accelerator의 아키텍처와 운영 결과. ([Amazon Web Services, Inc.][4])

## 3. GPU 인프라 | FlashInfer 0.6.16.post1과 0.6.17rc1: 안정 버전과 실험 버전을 분리해야 한다

### 무엇이 바뀌었나

FlashInfer는 8월 2일 `0.6.16.post1`을 최신 안정 릴리스로 올렸습니다. 기능 추가가 아니라 `tvm-ffi 0.1.13-post0`의 ABI 호환성 hotfix를 반영한 버전입니다. `0.6.16`을 설치했다면 Python package, cubin package, JIT cache package와 TVM-FFI의 버전 정합성을 확인할 필요가 있습니다. ([GitHub][6])

별도로 공개된 `0.6.17rc1`에는 다음과 같은 후속 기능이 들어갔습니다.

* per-tensor routed FP8 fused-MoE
* SM100의 GDN 성능 개선
* high-expert·high-top-k용 TensorRT-LLM routing 최적화
* speculative decode를 위한 ragged query와 행별 sliding-window mask
* Ulysses P2P all-to-all
* XQA decode kernel 사전 컴파일을 통한 테스트 시간 단축 ([GitHub][6])

### 왜 중요한가

FlashInfer 같은 kernel library는 Python 패키지만 업그레이드해도 실제 실행 경로에는 여러 artifact가 관여합니다.

```text
flashinfer Python package
+ cubin package
+ JIT cache
+ TVM-FFI
+ PyTorch
+ CUDA runtime
+ GPU architecture
```

이 중 일부가 다른 버전이면 import 단계에서는 정상처럼 보여도 특정 MoE·FP8 경로에서 ABI 오류, backend fallback 또는 잘못된 kernel dispatch가 발생할 수 있습니다.

특히 B200 환경에서는 `SM100` 최적화와 FP8 fused-MoE가 직접적인 관심 대상입니다. 다만 `0.6.17rc1`은 release candidate이므로 운영 기본값이 아니라 실험 대상에 가깝습니다.

### 실무 적용

서버 시작 시 다음 정보를 강제로 출력하고 기록하는 것이 좋습니다.

```text
flashinfer_version
cubin_version
jit_cache_version
tvm_ffi_version
torch_version
cuda_runtime
gpu_compute_capability
selected_attention_backend
selected_moe_backend
```

업그레이드는 세 단계로 나누는 편이 안전합니다.

1. `0.6.16 → 0.6.16.post1`: ABI hotfix 검증
2. `0.6.16.post1 → 0.6.17rc1`: canary 성능 실험
3. `0.6.17` 정식 출시 후 전체 회귀 테스트

RC 비교에서는 평균 처리량뿐 아니라 numerical delta, P95 TTFT·TPOT, expert routing 분포, CUDA Graph capture 성공 여부를 확인해야 합니다.

### 주의할 점

릴리스 노트에 언급된 개선은 개별 kernel 또는 test workload 기준입니다. 실제 vLLM·SGLang 서비스에서 end-to-end 처리량이 같은 비율로 오르는 것은 아닙니다. 또한 RC에서는 추가 수정이나 API 변경이 발생할 수 있습니다. ([GitHub][6])

**후속 관찰 포인트:** `0.6.17` 정식 릴리스, B200에서 GDN·routed FP8 실측, vLLM·SGLang 기본 backend 채택 시점, JIT cache와 cubin package의 배포 표준화.

**원문**

* **[GitHub 릴리스]** FlashInfer 릴리스 목록과 `0.6.16.post1` ABI hotfix. ([GitHub][6])
* **[GitHub 릴리스]** FlashInfer `0.6.17rc1` 변경 내역. ([GitHub][6])

## 4. AI 보안 | 사용자 음성 위에 공격 명령을 겹쳐 넣는 prompt injection

### 무엇이 바뀌었나

새 연구는 음성 에이전트가 사용자의 발화를 듣는 동안 다른 음원에 포함된 악성 명령을 함께 처리하도록 유도하는 **concurrent audio prompt injection**을 분석했습니다.

연구진은 8개 실제 작업 시나리오와 10개 공격 유형으로 구성된 AudioAgentSecurity benchmark를 만들고 11개 에이전트를 평가했습니다. 저자 측 실험에서는 Gemini 3 Pro를 대상으로 평균 공격 성공률 69.1%를 기록했습니다. 방어 방식인 CADV는 음원 분리와 cross-modal consistency 검사를 결합해 여러 공격 조건에서 90% 이상의 탐지율을 보고했습니다. ([arXiv][7])

### 왜 중요한가

텍스트 에이전트에서는 사용자 입력과 외부 문서의 출처를 어느 정도 분리할 수 있습니다. 그러나 연속 음성 입력은 다음 신호가 하나의 waveform에 섞입니다.

```text
사용자 발화
+ TV·스피커 음성
+ 주변 사람의 발화
+ 배경음
+ 의도적으로 삽입된 공격 명령
```

STT 결과만 모델에 전달하면 어떤 문장이 실제 사용자의 명령이고 어떤 문장이 환경에서 유입됐는지 구분하기 어렵습니다. “프롬프트 안에서 외부 명령을 무시하라”고 지시하는 텍스트 수준 방어만으로는 음원 자체의 출처 문제를 해결하지 못합니다.

### 실무 적용

음성 에이전트의 도구 실행 경로를 다음처럼 분리해야 합니다.

```text
오디오 입력
→ 화자·음원 분리
→ 사용자 음성 인증
→ 명령 후보 추출
→ 현재 대화 의도와 일관성 검사
→ 고위험 action 재확인
→ 도구 실행
```

결제, 메시지 발송, 문 잠금 해제, 계정 설정 변경 같은 작업은 음성 명령 하나만으로 실행하지 않고 화면이나 별도 기기에서 구체적인 내용을 확인받는 것이 좋습니다.

평가 지표도 공격 탐지율만으로 부족합니다.

* Attack Success Rate
* 정상 음성 task 성공률
* false-positive rate
* source separation latency
* 화자 중첩 시 성능
* 재생 스피커 거리·소음별 성능
* 공격 이후 발생한 실제 side effect

### 주의할 점

69.1% 공격 성공률과 90% 이상 탐지율은 연구진이 구성한 모델·음원·환경에서 얻은 초기 결과입니다. 음원 분리는 정상 사용자 발화의 일부를 제거하거나 응답 지연을 늘릴 수 있습니다. 따라서 CADV 같은 방어를 적용할 때는 공격 탐지와 정상 업무 성공률을 함께 측정해야 합니다. ([arXiv][7])

**후속 관찰 포인트:** 스마트폰·차량·회의실에서의 재현성, 사용자 음성 인증 우회, 실시간 환경에서의 지연시간, 여러 공격 음원이 동시에 존재하는 경우.

**원문**

* **[논문]** Piggybacking on Perception: Concurrent Audio Prompt Injection. ([arXiv][7])

## 5. 필독 | GradLock: 학습된 모델 파일 자체를 개인정보 유출 저장소로 사용

### 무엇이 바뀌었나

GradLock은 침해된 오픈소스 학습 구성 요소가 민감한 학습 데이터를 모델 파라미터 내부에 의도적으로 저장하도록 만드는 training-time injection 공격입니다.

공격자는 결정론적인 인덱싱으로 특정 파라미터 영역을 데이터 저장 공간처럼 사용하고, 학습 과정에서 payload가 손상되지 않도록 gradient를 동적으로 제어합니다. 저자 측 MNIST·Imagenette·CelebA 실험에서는 SSIM 약 1.0 수준의 거의 무손실 복원과 1초 미만의 추출 시간을 보고했습니다. 양자화, pruning, 추가 fine-tuning 이후에도 공격이 유지됐으며 사용자 연구에서는 참가자의 93.3%가 악성 로직을 발견하지 못했습니다. ([arXiv][9])

### 왜 중요한가

기존 ML supply-chain 검사는 주로 다음을 확인합니다.

* 모델 정확도가 정상인가
* 악성 pickle이나 임의 코드 실행이 있는가
* 알려진 backdoor trigger가 있는가
* 모델 출력으로 개인정보가 직접 노출되는가

GradLock의 위협에서는 모델이 정상 정확도를 유지하면서도 **weight artifact 자체가 데이터 vault** 역할을 할 수 있습니다. 추출자는 학습 환경이나 inference query 없이 모델 파일만 확보해도 데이터를 복구할 수 있습니다.

### 실무 적용

최종 checkpoint만 검사해서는 부족합니다. 학습 전체에 provenance가 필요합니다.

* trainer·optimizer source commit 고정
* container image와 wheel hash 기록
* dependency SBOM 생성
* custom autograd function·gradient hook 검사
* 외부 callback·plugin allowlist
* hermetic build와 네트워크 차단
* 학습 코드 재현 빌드
* synthetic secret을 이용한 leakage canary

특히 다음과 같은 코드는 별도 보안 검토 대상으로 두는 것이 좋습니다.

```text
register_hook
custom backward
optimizer step override
parameter-specific gradient masking
고정 parameter index에 대한 직접 쓰기
checkpoint 저장 직전 변환
```

학습 전후 weight 통계만 비교하는 방식은 의도적으로 분산된 payload를 놓칠 수 있으므로, 알려진 canary 데이터를 실제로 복원할 수 있는지 red-team extraction test도 고려해야 합니다.

### 주의할 점

현재 결과는 이미지 분류 데이터셋을 중심으로 한 공격 연구이며, 위협 모델은 학습 도구나 dependency가 이미 침해됐다고 가정합니다. 모든 공개 모델이 이러한 공격에 노출돼 있다는 뜻은 아닙니다. 다만 서명된 가중치만으로는 해당 가중치가 **어떤 학습 코드로 생성됐는지**까지 증명할 수 없다는 문제를 명확히 보여줍니다. ([arXiv][9])

**후속 관찰 포인트:** LLM·embedding 모델에서의 확장성, 공격 탐지기 공개, reproducible training provenance 표준, model registry의 학습 코드 attestations.

**원문**

* **[논문 HTML]** 공격 구조와 공급망 위협 분석. ([arXiv][10])

## 6. 멀티모달·로보틱스 | Mirror Learning: 3인칭 영상을 로봇 학습 데이터로 변환

### 무엇이 바뀌었나

Mirror Learning은 사람이 수행하는 작업을 제3자 시점에서 촬영한 영상으로부터 로봇 정책을 학습하는 방식을 제안합니다.

시스템은 두 단계를 조합합니다.

1. Fine-tuned video diffusion model로 관찰 영상을 로봇의 1인칭 시점처럼 변환
2. Inverse dynamics model로 변환된 영상에서 로봇 제어 공간의 action trajectory 추정

이렇게 생성된 pseudo first-person 데이터를 저자들은 `mirror data`라고 부릅니다. 논문은 mirror data만으로도 정책 학습이 가능했으며 기존 first-person behavior-cloning 데이터에 추가했을 때 downstream 성능이 개선됐다고 보고합니다. ([arXiv][11])

### 왜 중요한가

로봇 학습 데이터는 일반적으로 사람이 직접 원격 조종하거나 로봇 관점에서 시범을 수집해야 합니다. 비용이 높고 수집 가능한 행동과 환경도 제한됩니다.

Mirror Learning의 방향이 재현된다면 다음과 같은 기존 영상도 학습 자원으로 사용할 가능성이 생깁니다.

* 사람이 조립하는 영상
* 공장 작업 기록
* 요리·청소 시연
* 수술·의료 작업 영상
* 다른 형태의 로봇이 수행한 작업

핵심은 영상 생성 모델을 최종 콘텐츠 생성기가 아니라 **관점과 embodiment를 변환하는 데이터 엔진**으로 사용한다는 점입니다.

### 실무 적용

바로 실제 로봇 정책에 투입하기보다 데이터 augmentation 경로로 평가하는 것이 안전합니다.

```text
3인칭 시연
→ 관점 변환
→ action 추정
→ 물리·기하 검증
→ 낮은 confidence 데이터 제거
→ simulation rollout
→ 실제 로봇 제한 테스트
```

검증 항목은 다음과 같습니다.

* 손·도구·객체 위치의 기하학적 일관성
* 접촉 발생 시점
* 생성 영상과 추정 action의 일치
* 관절 한계·충돌 여부
* 장기 rollout drift
* 실제 first-person 데이터 대비 성능
* simulation에서 실제 환경으로의 전이

### 주의할 점

Video diffusion model이 그럴듯하지만 물리적으로 잘못된 장면을 생성하면 inverse dynamics가 존재하지 않는 행동을 학습할 수 있습니다. 따라서 생성 영상의 시각 품질보다 **action feasibility와 causal consistency**를 우선 검증해야 합니다. 이 논문은 초기 연구 결과이며 대규모 실제 로봇 환경에서의 독립 재현이 필요합니다. ([arXiv][11])

**후속 관찰 포인트:** 코드·데이터 공개, 다양한 embodiment 간 전이, 불확실성 추정, 실제 teleoperation 데이터를 얼마나 줄일 수 있는지.

**원문**

* **[논문]** Mirror Learning. ([arXiv][11])

## 7. 평가 | FinIndices: 32K 재무제표를 읽어도 구조적 계산은 쉽게 무너진다

### 무엇이 바뀌었나

FinIndices는 잘린 표나 객관식 문제가 아니라 최대 32K 토큰의 원본 재무제표를 이용해 재무 지표 계산과 다기간 표 생성을 평가하는 benchmark입니다.

연구진은 공식 힌트를 제거했을 때 Gemini 3.1 Pro의 table task 성능이 70.70%에서 38.22%로 떨어졌다고 보고했습니다. 모델이 공식 자체를 기억하더라도 누적값을 분기값으로 바꾸는 temporal de-cumulation, stock·flow 지표 구분, 인접 열 선택과 복수 기간 계산에서 오류가 발생했습니다. SFT 후에는 zero-hint 조건에서 Single task가 8.54%포인트, Table task가 3.82%포인트 개선됐습니다. ([arXiv][12])

### 왜 중요한가

긴 문서를 context window에 넣었다고 해서 구조적 추론 문제가 해결되는 것은 아닙니다.

특히 여러 지표와 기간을 한꺼번에 표로 작성하게 하면 모델은 다음 오류를 만들기 쉽습니다.

* 바로 옆의 잘못된 열 선택
* 분기·누적 수치 혼동
* 단위 변환 누락
* 서로 다른 회계 범위의 수치 결합
* 복잡한 조정을 단순 사칙연산으로 대체
* 일부 셀 오류가 이후 계산으로 전파

즉, 긴 context를 처리하는 능력과 올바른 데이터 lineage를 유지하는 능력은 별도입니다.

### 실무 적용

재무·데이터 분석 에이전트는 한 번에 최종 표를 만들게 하지 말고 작업을 분리해야 합니다.

```text
문서·표 추출
→ 셀 위치와 단위 정규화
→ 공식 선택
→ 기간·지표별 계산
→ 결정론적 계산기로 재계산
→ source cell lineage 검증
→ 최종 표 생성
```

각 결과 셀에 다음 정보를 붙이면 검증하기 쉽습니다.

```text
value
unit
formula
source_document
source_table
source_row
source_column
period
intermediate_values
```

공식 힌트를 제공해 성능이 올라가는 것은 실용적으로 유용할 수 있지만, 모델이 구조를 이해했다는 증거는 아닙니다. 힌트 유무와 source cell 교란 조건을 나눠 평가해야 합니다.

### 주의할 점

FinIndices는 재무 분야에 특화된 연구진 측 benchmark이며 합성 pipeline과 adversarial trap 설계에 결과가 영향을 받을 수 있습니다. 공개 수치를 모든 문서 추론으로 일반화하기보다, 장문 테이블 작업에서 **셀 lineage와 결정론적 계산기를 반드시 분리해야 한다는 증거**로 보는 것이 적절합니다. ([arXiv][12])

**후속 관찰 포인트:** dataset·evaluation harness 공개 범위, 실제 기업 보고서에서의 재현, tool-augmented agent 성능, 표 크기와 오류율의 관계.

**원문**

# 오늘의 실습: 정책 자동 수정용 Regression Harness 만들기

**목표:** 정책 테스트가 실패했을 때 규칙을 무조건 덧붙이지 않고, 자연어 해석 오류와 논리 오류를 구분한 뒤 전체 회귀 테스트를 수행합니다.

## 1단계: 정책 정의

간단한 비용 승인 정책을 작성합니다.

```yaml
rules:
  - 정규직은 100만 원 이하 비용을 승인 없이 지출할 수 있다.
  - 계약직은 모든 지출에 관리자 승인이 필요하다.
  - 고객 개인정보가 포함된 구매는 금액과 관계없이 보안 승인이 필요하다.
```

## 2단계: 구조화 변수

```text
employee_type
amount
has_manager_approval
contains_customer_data
has_security_approval
```

## 3단계: 테스트 구성

최소 다음 사례를 포함합니다.

* 정규직, 80만 원, 승인 없음 → 허용
* 정규직, 150만 원, 승인 없음 → 차단
* 계약직, 10만 원, 관리자 승인 없음 → 차단
* `temporary worker`, 10만 원, 승인 없음 → 번역 모호성
* 정규직, 5만 원, 고객정보 포함, 보안 승인 없음 → 차단
* 정규직, 5만 원, 고객정보 포함, 보안 승인 있음 → 허용

## 4단계: 실패 원인 분리

```text
Translation failure
- employee_type을 잘못 매핑
- 금액·승인 여부 추출 실패
- 동의어가 변수 정의에 없음

Rule failure
- 변수 매핑은 정확함
- 예외·우선순위 규칙이 누락
- 두 규칙이 서로 모순됨
```

## 5단계: 수정안 승격 조건

자동 생성된 변경안은 다음을 모두 통과해야 합니다.

* 최초 실패 테스트 통과
* 기존 테스트의 regression 0건
* 새로 생성한 경계값 반례 통과
* 변경된 규칙 수가 사전 설정한 한도 이하
* 허용 범위가 의도하지 않게 확대되지 않음
* 사람이 diff를 승인함

## 기록할 지표

```text
translation_ambiguity_rate
false_allow
false_deny
regression_failures
changed_rule_count
counterexamples_found
approval_time
policy_version
```

핵심은 테스트 하나를 통과시키는 것이 아니라, **정책의 전체 의미를 유지하면서 가장 작은 변경으로 오류를 수정하는 것**입니다. 이를 Git 저장소에 넣어 정책 원문, 구조화 규칙, 테스트와 승인 기록을 함께 versioning하면 F1 사례처럼 에이전트의 출력도 기존 엔지니어링 절차 안에서 관리할 수 있습니다.
