> 누락분 사후 보완판 · 작성일: 2026-10-06 · 월요일판은 주말 직전 arXiv v1 공개 연구를 중심으로 구성했습니다. 아래 논문들의 v1 제출일은 10월 2일이며, 모두 10월 5일에 처음 제출된 것으로 서술하지 않습니다. 수치는 저자 보고이며 별도 실행 재현은 하지 않았습니다.

## 오늘의 흐름

**에이전트 시스템의 scheduling 단위가 요청 하나에서 workflow·rollout group·메모리 상태로 확장되고 있다.** Coda와 VenusRL은 어떤 작업을 언제 실행 자원에 들여보낼지 다룬다. MRVQ는 검색 인덱스의 메모리를, DepGPO는 실행 로그를 이용한 학습 신호 배분을 다룬다. 아키텍처 관점에서는 생성모델의 layer depth와 반복 시간의 관계를 조사하는 연구도 함께 볼 만하다.

## 1. Coda — 준비된 에이전트 요청과 지금 실행하기 좋은 요청은 다르다

**공개:** arXiv v1 2026-10-02 · **분야:** 에이전트 서빙·KV·admission control · **확인:** 논문 초록·HTML 본문

**무엇이 바뀌었나.** Coda는 요청의 논리적 준비 상태뿐 아니라 KV residency, 상태 준비 비용, 문맥 호환성을 고려해 admission과 batching을 조정한다. 대기 시간이 긴 요청을 계속 미루지 않도록 aging과 진행 보장을 결합한다. 논문의 30B 구성에서 강한 비교 시스템 대비 output throughput 개선은 4.2~12.1%, SLO throughput 개선은 15.9~44.3%로 보고된다.

**왜 중요한가.** 에이전트는 도구가 끝난 뒤 긴 이전 문맥을 가진 채 다시 추론에 들어온다. 모델 서버에 모든 요청을 즉시 넣으면 캐시 준비와 서로 다른 context 길이가 queue를 비효율적으로 만들 수 있다. 반면 캐시가 있는 요청만 우대하면 일부 사용자가 계속 기다리는 공정성 문제가 생긴다.

**실무 적용.** serving 실험에 `ready_at`, `admitted_at`, `first_token_at`, KV hit 상태와 context 길이를 함께 기록하자. 외부 admission에서 기다린 시간을 TTFT에서 빼면 성능이 좋아 보이는 착시가 생긴다. 처리량과 함께 대기시간 최댓값, 긴 문맥 요청의 성공률, SLO를 만족한 요청 수를 평가해야 한다.

**주의·후속 확인.** 전체 headline 최대값과 강한 baseline 대비 결과는 같지 않다. 일부 기준선은 round-robin·FIFO를 사용하며, trace-driven replay에서는 원래 trace에 없는 물리 KV 배치를 재구성한다. A100 중심 결과가 B200의 더 큰 메모리·다른 통신 조건에서도 유지되는지는 별도 측정이 필요하다.

원문: [논문 · Coda: Exploiting Admission Flexibility for Coding-Agent Serving](https://arxiv.org/abs/2610.03088v1)

## 2. VenusRL — RL 학습에서는 개별 요청보다 업데이트를 막는 rollout group을 본다

**공개:** arXiv v1 2026-10-02 · **분야:** 에이전트 RL·분산 인프라 · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** VenusRL은 분리형 agentic RL에서 거의 완료된 rollout group을 우선 처리하도록 admission, KV residency, worker 배치를 연결한다. 환경 메모리는 선언된 최대치만큼 계속 확보하기보다 실제 활용과 template page 공유를 활용한다. 저자는 조건에 따라 E2E 학습 4.24배 가속과 환경 비용 최대 89% 절감을 보고한다.

**왜 중요한가.** 개별 generation이 빨라도 하나의 group에서 마지막 rollout이 늦게 끝나면 policy update가 기다릴 수 있다. 단순 GPU 사용률이나 초당 token만으로 학습 효율을 설명하기 어려운 이유다. tool environment의 RAM과 컨테이너 비용도 전체 RL 자원의 일부다.

**실무 적용.** GRPO 계열 실험에서는 `group_id`, group 완료 시간, 가장 늦은 rollout, policy version, update 시작 지연을 기록하자. 환경 실행 시간과 모델 생성 시간을 분리하면 어느 계층의 straggler가 실제 학습을 막는지 알 수 있다. 전체 모델 재학습 전에 작은 workload에서 timeline을 만드는 것으로 시작할 수 있다.

**주의·후속 확인.** 최대 가속 배율을 모든 RL 작업의 평균으로 사용할 수 없다. 비동기 실행이 늘면 policy staleness와 표본 분포가 바뀔 수 있으며, 환경 page 공유는 격리와 쓰기 보호를 확인해야 한다. 특히 서로 다른 사용자의 민감 데이터를 공유 메모리 최적화에 섞지 않도록 설계해야 한다.

원문: [논문 · VenusRL](https://arxiv.org/abs/2610.03286v1)

## 3. MRVQ — 하나의 검색 인덱스 표현에서 여러 저장 예산을 지원한다

**공개:** arXiv v1 2026-10-02 · **분야:** RAG·벡터 인덱스·양자화 · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** MRVQ는 frozen embedding에 Matryoshka residual vector quantization을 적용해 residual stage 또는 좌표 차원을 잘라 여러 rate와 dimension을 지원한다. FiQA·NFCorpus에서 4·8·16바이트 code 등을 비교한다. RAM 절감은 공유 모델 기준선 대비 약 1.89~2.02배이며, 17.8~22배 수치는 세 개의 별도 QINCo2 인덱스와의 비교다.

**왜 중요한가.** 서로 다른 latency·메모리 요구에 맞춰 별도 인덱스를 여러 개 유지하면 벡터뿐 아니라 codebook·모델·메타데이터도 중복된다. 하나의 표현을 다양한 예산에서 읽는 방식은 데이터 인프라의 운영 복잡도를 줄일 가능성이 있다. 그러나 인덱스가 작아져도 검색 품질이 충분한지는 별도 문제다.

**실무 적용.** 보안 문서 RAG에서 원문은 보존하고 인덱스 표현만 바꾸는 실험을 설계하자. 총 RAM에 codebook과 부가 metadata를 포함하고, recall·nDCG·검색 P95·reranking 비용을 함께 기록한다. 최종 답변의 근거 회수율까지 내려가야 인덱스 압축이 실제 보고서 품질에 미치는 영향을 알 수 있다.

**주의·후속 확인.** 개별 rate에 특화한 QINCo2 대비 FiQA nDCG@10은 0.026~0.107 낮아지는 조건이 보고된다. “메모리를 줄이면서 모든 baseline보다 우수하다”는 결과가 아니다. 압축률·공유 비용·품질 손실을 각각 제시하고 다른 도메인의 긴 코드·다국어 문서에서 검증할 필요가 있다.

원문: [논문 · MRVQ 연구](https://arxiv.org/abs/2610.03651v1)

## 4. DepGPO — 최종 점수를 모든 도구 행동에 똑같이 나누지 않는다

**공개:** arXiv v1 2026-10-02 · **분야:** 에이전트 학습·credit assignment · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** DepGPO는 명령의 read/write 관계로 실행 의존 그래프를 만들고, verifier가 확인한 자원에서 역방향으로 추적해 관련 write와 이를 뒷받침한 read에 학습 신호를 배분한다. 최종 성공·실패라는 하나의 결과를 전체 trajectory에 균일하게 전파하는 대신 실제 실행 구조를 이용한다.

**왜 중요한가.** 코드 수정 전의 핵심 조사와 관계없는 반복 명령을 같은 정도로 보상하면 학습 신호가 희석될 수 있다. 자연어 reasoning의 자기 설명보다 실제 읽고 쓴 자원의 연결을 활용한다는 점이 장점이다. 관측성을 모델 평가뿐 아니라 후학습 데이터로 재사용하는 흐름이기도 하다.

**실무 적용.** 실험 하네스에서 명령, 작업 디렉터리, 파일 해시, read/write 대상, verifier가 읽은 산출물을 기록하자. 초기에는 RL을 돌리지 않고 성공한 patch까지 이어지는 의존 경로를 분석해 불필요한 도구 호출을 찾는 용도로 사용할 수 있다. 로그의 누락률을 함께 측정해야 한다.

**주의·후속 확인.** 데이터 의존성은 인과적 중요도의 완전한 증명이 아니다. 네트워크 응답, 환경변수, 간접 파일 접근과 숨은 상태가 빠지면 그래프가 불완전해진다. verifier를 에이전트가 수정할 수 있으면 reward 경로도 오염되므로 평가기와 학습 대상의 권한을 분리해야 한다.

원문: [논문 · DepGPO의 실행 의존성 기반 credit assignment 연구](https://arxiv.org/abs/2610.03634v1)

## 5. HyperBrowseComp — 영어 텍스트 검색만 잘해도 실제 조사 에이전트가 되는가

**공개:** arXiv v1 2026-10-02 · **분야:** 웹 에이전트·멀티모달·다국어 평가 · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** HyperBrowseComp는 13개 언어의 423개 문제를 사람 작성·검증으로 구성한다. 여러 단서, 영상, 스캔 문서, 이미지·지도 등에서 간결하고 검증 가능한 사실을 찾도록 설계하며, native search 환경과 공통 하네스 평가를 함께 다룬다.

**왜 중요한가.** 검색 모델이 영어 웹문서의 잘 정리된 답을 찾는 능력과, 여러 언어·매체에 흩어진 근거를 조사하는 능력은 다르다. 문헌·산업 조사에서 실제 실패는 정답 생성 이전의 자료 접근과 증거 추출 단계에서 자주 발생할 수 있다. 평가도 그 단계를 구분해야 한다.

**실무 적용.** 기술 브리핑이나 리뷰 하네스에 한국어·영어 자료, 표가 포함된 PDF, GitHub 릴리스와 영상 설명을 섞은 소규모 검증셋을 만들자. 최종 답뿐 아니라 원문 도달 여부, 필요한 구간 발견, 증거 추출, 출처 날짜의 정확성을 각각 기록한다.

**주의·후속 확인.** 검색 인덱스와 웹페이지는 시간이 지나며 바뀐다. source snapshot과 조사 날짜를 남기지 않으면 모델 변화와 웹 변화가 섞인다. 각 회사의 native tool 결과를 공통 하네스 결과와 같은 조건으로 비교해서도 안 된다. 다국어·멀티모달별 세부 성능과 비용이 후속 관찰 대상이다.

원문: [논문 · HyperBrowseComp](https://arxiv.org/abs/2610.03574v1)

## 6. Depth as Time — 한 번의 생성 안에서 layer depth가 시간처럼 작동할 수 있다

**공개:** arXiv v1 2026-10-02 · **분야:** 생성모델·아키텍처·반복 계산 · **확인:** 논문 원문 초록

**무엇이 바뀌었나.** 이 연구는 일부 one-step 생성모델의 중간 layer를 해석하면 denoising에 대응하는 과정이 depth 방향으로 나타난다고 분석한다. MeanFlow 계열의 짧은 transport·denoise·renoise 동작 등을 조사하고, SiT-L/2를 하나의 시간 조건부 block으로 압축해 parameter 수를 16.6배 줄인 결과를 제시한다.

**왜 중요한가.** 모델의 깊이를 단순히 서로 다른 parameter를 가진 layer 수로만 볼 필요가 없다는 문제 제기다. 같은 block의 반복, time conditioning, 내부 표현의 진행을 결합하면 가중치 저장과 연산 시간을 다른 방식으로 배분할 수 있다. LLM의 tied-layer·looped 구조를 공부할 때도 연결해 볼 개념이다.

**실무 적용.** 자신의 아키텍처 연구에서는 중간 표현의 변화량, output head로 본 예측, 반복 횟수에 따른 품질을 함께 측정하는 관점을 가져올 수 있다. 다만 이미지 생성에서 발견된 depth–time 관계를 언어모델에 바로 적용하지 말고, 별도의 가설과 작은 통제 실험으로 다뤄야 한다.

**주의·후속 확인.** 16.6배 parameter 압축은 16.6배 latency 또는 FLOPs 감소가 아니다. 같은 block을 여러 번 계산하면 실행 비용이 남으며 품질·다양성도 확인해야 한다. 모든 one-step 생성기에서 같은 현상이 관측된 것도 아니므로 모델군별 차이가 중요하다.

원문: [논문 · Depth as Time 연구](https://arxiv.org/abs/2610.03626v1)

## 오늘 꼭 볼 것 3개

1. **Coda:** ready와 admitted 사이의 정책이 실제 사용자 지연과 캐시 효율을 바꾼다.
2. **DepGPO:** 실행 의존 로그를 학습 신호로 바꾸려면 관측 범위와 verifier 무결성이 먼저 필요하다.
3. **Depth as Time:** layer depth·parameter 공유·반복 시간의 관계를 아키텍처 가설로 확장할 수 있다.

## 오늘 직접 해볼 만한 실습 — 캐시 친화적 admission과 공정성을 함께 측정하기

먼저 측정 가능한 작은 요청 trace를 만든다. 각 요청에는 도착 시각, session ID, 입력 길이, prefix 식별자, deadline을 넣는다. 고정된 trace를 `FIFO`, `동일 prefix 우선`, `동일 prefix 우선 + 최대 대기시간 aging` 세 정책으로 replay한다. 아래는 Coda에서 착안한 단순 실험이며 공식 구현 재현은 아니다.

실제 서버로 실행한다면 요청의 최초 도착부터 첫 token까지 측정하고, 외부 admission 대기도 전체 지연에 포함한다. GPU가 없으면 명시적인 가상 처리시간 모델로 시뮬레이션할 수 있지만 결과에 반드시 “시뮬레이션”이라고 표시해야 한다.

```text
request_id | arrived_at | admitted_at | first_token_at | finished_at
session_id | prefix_id | input_tokens | cache_hit
admission_wait | total_TTFT | E2E | deadline_met
```

**핵심 질문:** prefix를 우대해 평균 성능이 좋아져도 긴 문맥·낮은 재사용 요청이 계속 밀리지는 않는가? 평균 처리량, SLO goodput, 최장 대기, 요청군별 P95를 같이 비교한다. 다른 곳으로 기다림을 옮긴 것을 성능 향상으로 보고하지 않는 것이 가장 중요한 판정 기준이다.
