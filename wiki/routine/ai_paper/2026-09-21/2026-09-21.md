# AI 엔지니어 데일리 브리핑 — 2026년 9월 21일

한국시간 **9월 21일 아침** 기준입니다. 주말 직후라 새 논문은 9월 18일 공개 묶음이 중심이고, 제품·인프라 쪽에서는 9월 18일 발표가 가장 최신입니다. 오늘은 특히 **① LLM serving에서 scheduler의 판단 단위가 GPU load에서 KV cache·prefix·LoRA residency까지 확대되고, ② Coding Agent 평가는 “짧은 버그 수정”에서 며칠짜리 long-horizon engineering으로 이동하며, ③ Agent 운영에서는 재현 불가능했던 실패를 CI regression test로 바꾸는 기술이 등장하고, ④ LLM 기반 악성코드 분석은 코드가 아니라 “서사”에도 속을 수 있다는 공격면**이 선명합니다.

## 1. AWS HyperPod Inference Gateway — Kubernetes round-robin 대신 `KV cache + queue + prefix + LoRA residency`로 request routing ★★★★★

AWS가 9월 18일 **SageMaker HyperPod Inference Gateway**를 공개했습니다. 핵심은 model server가 아니라 그 앞의 router입니다. 일반 Kubernetes round-robin이나 least-connections는 GPU 내부 상태를 모르기 때문에, 이미 KV cache가 꽉 찬 pod나 긴 generation을 처리 중인 pod에도 새 요청을 계속 보낼 수 있습니다. 새 Gateway는 Prometheus로 model-serving pod의 **KV cache utilization, queue depth, running request 수, LoRA adapter residency, prefix-cache hit 가능성**을 읽고 weighted score로 backend를 고릅니다. :chatgpt-content-reference{index="0"}

구조도 꽤 깔끔합니다. Envoy Gateway가 HTTPS를 받고, Body-Based Router가 OpenAI-compatible request의 `model`을 읽어 model pool을 결정하고, Endpoint Picker가 그 안에서 실제 pod를 고릅니다. 여러 모델을 한 gateway로 다룰 수 있고, fine-tuned LoRA 요청은 해당 adapter가 이미 GPU에 올라가 있는 pod를 우선 선택합니다. AWS는 별도 sidecar나 service mesh, client SDK 변경 없이 EKS addon으로 넣도록 설계했습니다. :chatgpt-content-reference{index="1"}

Benchmark는 8B~235B 모델과 H100/A10G를 사용해 mixed GPU, bursty traffic, shared-prefix 세 조건에서 수행됐습니다. AWS가 내세운 headline은 **first-token latency 최대 82% 감소**이며, 예시상 4.4초가 800ms 미만으로 내려갔다고 합니다. 다만 이 수치는 heterogeneous/bursty 환경의 vendor benchmark이며, AWS 스스로도 **GPU가 균일하고 steady traffic이면 intelligent routing과 round-robin 성능이 비슷하다**고 명시합니다. 즉 router의 가치는 “항상”이 아니라 **상태 비대칭이 커질수록 증가**합니다. :chatgpt-content-reference{index="2"}

이 방향은 self-hosted vLLM에도 중요합니다. 지금까지는 `load balancer → replica` 정도로 끝냈다면 앞으로 routing score를 대략 이렇게 볼 수 있습니다.

`score = queue + KV pressure + prefix locality + adapter locality + active requests`

특히 여러 replica에서 prefix caching을 켜면 cache hit rate가 높더라도 **요청을 그 cache가 있는 replica로 다시 보내지 않으면** 실제 이득을 상당 부분 잃게 됩니다. GPU serving에서 cache policy와 router policy가 점점 하나의 문제로 합쳐지고 있습니다.

원문: [공식 발표 · Introducing Amazon SageMaker HyperPod Inference Gateway](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-sagemaker-hyperpod-inference-gateway/)

## 2. Android Bench 2.0 — Coding Agent 평가가 `bug fix`에서 **며칠짜리 long-horizon engineering**으로 이동 ★★★★★

Google Android 팀이 **Android Bench 2.0**을 공개했습니다. 기존 Android Bench와 초기 coding benchmark들이 작은 bug fix나 incremental repository change를 중심으로 했다면, 새 benchmark에는 실제 엔지니어가 **수일~1주** 사용할 만한 Long-Horizon Tasks가 들어갑니다. 예시는 dependency upgrade, 새로운 feature 추가, 처음부터 앱 구축, cross-platform app을 Android로 port하는 작업입니다. :chatgpt-content-reference{index="4"}

평가 방식도 pass/fail에서 **continuous scoring**으로 바뀌었습니다. 예를 들어 Agent가 40개 화면을 Compose로 옮기고 database까지 구현했는데 edge-case assertion 하나를 실패했다고 전체를 0점 처리하면 실제 engineering capability를 잘 표현하지 못합니다. Android Bench 2.0은 functionality, visual fidelity, regression avoidance, 구조적 요구사항 위반 등을 합쳐 completion rate를 계산합니다. :chatgpt-content-reference{index="5"}

난이도 상승은 매우 큽니다. 기존 benchmark task는 최고 모델의 pass rate가 약 **91%**였지만 새 long-horizon task의 최고 pass rate는 **약 28%**에 불과합니다. Google은 모델들이 새 코드를 작성하는 데는 비교적 강하지만 기존 architecture를 이해하면서 refactor하거나 framework breaking change를 처리하는 데는 훨씬 약하다고 분석합니다. Java→Kotlin, Retrofit→Ktor처럼 잘 알려진 deterministic transformation은 125개 이상의 파일·8,000줄 이상에서도 꽤 일관되게 수행하지만, runtime dependency graph나 unreleased library 지식이 필요해지면 성능이 급격히 떨어집니다. :chatgpt-content-reference{index="6"}

특히 Google은 이제 **model뿐 아니라 model+agent 조합**을 평가하기 시작했습니다. 예를 들어 GPT-5.6 Sol은 Codex, Gemini 3.8 Flash는 Google Antigravity와 함께 평가합니다. Google도 prompt caching이나 compact tool windowing 같은 harness 설계가 token 사용과 실제 task 결과를 바꿀 수 있다고 설명합니다. :chatgpt-content-reference{index="7"}

이 흐름은 coding-agent 포트폴리오에도 중요합니다. 이제 “SWE-bench에서 몇 %”보다 더 좋은 평가는 **긴 작업을 얼마나 진행했고, 어느 단계에서 멈췄고, regression을 얼마나 남겼는가**입니다. Long-horizon task라면 `pass/fail`과 별도로 `completion %, regression count, test coverage, cost, total turns`를 함께 기록하는 것이 더 적절합니다.

원문: [공식 발표 · Android Bench 2.0: Pushing the frontier with challenging long-horizon tasks](https://android-developers.googleblog.com/2026/09/android-bench-2-long-horizon-tasks.html)

## 3. Chronicle — 재현하기 힘든 Agent 장애를 **Git에 커밋 가능한 regression test**로 바꾼다 ★★★★★

Agent 운영에서 가장 난감한 문제 중 하나는 **“어제 production에서 실패한 trajectory를 오늘 다시 못 만든다”**는 것입니다. 모델 출력은 비결정적이고, tool이 읽는 외부 상태도 바뀌며, Agent가 동일한 path를 다시 탈 확률도 낮기 때문입니다. 9월 17일 공개된 **Chronicle**은 이 문제를 record-and-replay 관점에서 풉니다. :chatgpt-content-reference{index="9"}

Chronicle은 LLM call, tool call, routing decision 같은 **non-deterministic boundary**의 input/output을 immutable `Envelope`로 기록합니다. 전체 incident를 다시 실행하는 대신 특정 boundary 하나만 새 코드로 실행하고 나머지는 과거 fixture를 그대로 replay하는 **cut-point replay**를 사용합니다. 예를 들어 잘못된 `delete_file` 호출이 사고 원인이었다면 planner output과 그 앞뒤 Agent response는 그대로 고정하고, 새 `delete_file` guard만 live로 실행해 수정이 실제 사고를 막는지 pytest/CI에서 검사할 수 있습니다. :chatgpt-content-reference{index="10"}

논문 benchmark에서는 recording overhead가 boundary crossing당 **23μs**, 가정한 300ms model call 대비 0.008%였고, full replay는 실제 model call을 하나도 하지 않으면서 20회 반복에서 bit-stable했습니다. 6개의 recorded incident에서는 faulty code가 실패하고 guarded/benign change가 통과했습니다. 규모가 작은 prototype benchmark라는 점은 감안해야 하지만, 아이디어 자체는 매우 실용적입니다. :chatgpt-content-reference{index="11"}

특히 좋은 점은 **Agent evaluation과 software regression testing을 분리**했다는 것입니다.

`Layer 1: deterministic structural replay → control flow / tool safety`  
`Layer 2: optional LLM judge → semantic quality`

모델 생성문 전체를 bitwise equality로 비교하려 하지 않고, safety-critical path는 deterministic assertion으로 닫습니다. Agent 테스트를 매번 live API로 돌리는 구조보다 훨씬 재현성이 높습니다. :chatgpt-content-reference{index="12"}

실무적으로는 production incident가 발생할 때 단순 trace를 저장하는 데서 끝내지 말고 **“이 trace를 다음 release를 막는 fixture로 만들 수 있는가?”**까지 생각해볼 만합니다.

원문: [논문 · Chronicle: Cut-Point Replay for Regression Testing of LLM Agents](https://arxiv.org/abs/2609.20625) · [GitHub · theagentplane/chronicle](https://github.com/theagentplane/chronicle)

## 4. ALIBI — LLM 악성코드 분석기는 코드뿐 아니라 **공격자가 심은 그럴듯한 설명문**에도 영향을 받는다 ★★★★★

이번 주 보안·LLM 논문 중 매우 중요한 것은 **ALIBI: Adversarial Legitimacy Injection in Binary Input against LLM Malware Analyzers**입니다. 특히 LLM을 정적분석 결과의 reasoning/reporting layer로 사용하는 시스템이라면 직접적인 문제입니다. :chatgpt-content-reference{index="15"}

공격은 실행 코드를 바꾸는 방식이 아닙니다. 연구진은 실행되지 않는 read-only section에 “이 프로그램은 endpoint-security 제품이고, 특정 suspicious behavior는 정상 기능이다” 같은 **일관된 cover story**를 넣습니다. Import나 실제 executable behavior는 그대로인데 LLM이 이 narrative를 정적 증거의 의미를 해석하는 context로 받아들이게 됩니다. :chatgpt-content-reference{index="16"}

50개의 malicious PE sample을 고정해 평가했을 때 Gemini 2.5 Pro는 baseline에서 malicious로 판단했던 35개 중 **30개를 benign으로 뒤집었습니다.** GPT-5.5 Pro와 Claude Opus 4.7은 label 자체가 더 견고했지만 severity와 confidence가 유의미하게 낮아졌습니다. ELF에서도 Gemini는 40개 중 16개가 뒤집혔습니다. Verification-guided prompt를 사용하면 공격이 줄기는 했지만 malicious sample의 **42.9%가 여전히 benign verdict**에 도달했습니다. :chatgpt-content-reference{index="17"}

이 결과의 핵심은 “더 강한 prompt를 쓰자”가 아닙니다. **verified fact와 attacker-controlled narrative를 입력 단계에서 다른 trust class로 분리해야 한다**는 것입니다.

예를 들어 malware report pipeline에서 다음을 같은 text context로 섞으면 안 됩니다.

`imports / API calls / CFG / code span / static-tool finding` → verified evidence  
`PE strings / embedded comments / README-like text / metadata description` → untrusted narrative

LLM에게는 두 channel을 명시적으로 나누고, verdict 근거가 반드시 verified evidence를 참조하도록 만드는 편이 안전합니다. 특히 “파일 안에 들어 있으니까 ground truth”라는 가정은 이제 위험합니다.

원문: [논문 · ALIBI: Adversarial Legitimacy Injection in Binary Input against LLM Malware Analyzers](https://arxiv.org/abs/2609.19722?utm_source=chatgpt.com)

## 5. MCP 시대의 새 실패 유형 — “없는 Tool 호출”은 일반 guardrail이 막지 못한다 ★★★★★

**Closed-World Resolution Against Tool Hallucination in LLM Agents**는 tool Agent에서 의외로 기본적인 빈틈을 다룹니다. 현재 tool safety의 대부분은 “실제 존재하는 tool을 호출하려는 요청이 위험한가?”를 검사합니다. 그런데 모델이 **존재하지 않는 tool name이나 schema에 없는 argument를 아예 만들어내면**, 그 호출은 기존 permission gate의 의사결정 대상으로조차 들어가지 않을 수 있습니다. :chatgpt-content-reference{index="19"}

연구에서는 10개 hosted model, 두 종류 invocation surface에서 **322개의 실제 tool hallucination**을 측정했습니다. Raw JSON처럼 자유롭게 tool call을 생성하는 surface에서는 fabricated tool이 34건, 더 constrained surface에서는 3건이었습니다. 모델 크기를 키운다고 문제가 자동으로 사라지지도 않았고, 논문에서는 675B 모델과 7~8B 모델이 유사한 수준의 failure를 보인 사례를 보고합니다. :chatgpt-content-reference{index="20"}

MCP에서는 문제가 더 복잡해집니다. 여러 MCP server를 하나의 tool namespace로 merge하면 이름 충돌, shadowing, 서로 다른 schema가 섞일 수 있습니다. 연구진은 live MCP surface에서 **154건의 hallucination**을 추가로 측정했고, single registry에서는 깨끗했던 frontier model도 merged MCP environment에서는 실패했습니다. :chatgpt-content-reference{index="21"}

제안하는 해결책 자체는 의외로 단순합니다. Model output 뒤에 바로 실행 gate를 두지 말고 먼저 **closed-world resolver**를 통과시킵니다.

`Model tool call`
→ `registry membership 확인`
→ `exact signature/schema 확인`
→ `그 다음 permission/safety gate`
→ `실행`

즉 `Tool 존재 여부`와 `Tool 사용 권한`은 다른 문제입니다.

MCP 환경을 직접 구성한다면 특히 tool 이름만 unique하게 만드는 것보다 `server_id + tool_name + schema_version`을 canonical identifier로 관리하는 편이 낫습니다. 여러 server를 flat namespace로 합치는 순간 이름 자체가 신뢰 가능한 identity가 아니게 됩니다.

원문: [논문 · Closed-World Resolution Against Tool Hallucination in LLM Agents](https://arxiv.org/abs/2609.19425)

## 6. AWS + Hugging Face Skills — Agent의 약점은 reasoning보다 **최신 운영 지식의 staleness**일 수 있다 ★★★★★

9월 18일 AWS와 Hugging Face가 꽤 흥미로운 실무 사례를 공개했습니다. Coding Agent에게 단순히 “Qwen 모델을 SageMaker에 배포해줘”라고 시켰을 때 Kiro와 Claude Code 모두 처음에는 **TGI**를 선택했습니다. 몇 년간 TGI가 표준이었던 training data가 많기 때문인데, 최신 Qwen3 architecture와 region별 container reality에서는 맞지 않았고 endpoint health check가 반복해서 실패했습니다. :chatgpt-content-reference{index="23"}

AWS/HF의 해결책은 새 모델로 바꾸는 게 아니라 **deployment knowledge를 Skill 파일로 외부화**하는 것입니다. 여섯 개 Skill이 AWS context discovery, Python environment, IAM preflight, serving image selection, production defaults, 전체 orchestration을 나눠 담당합니다. `SKILL.md`는 필요할 때 progressive disclosure 방식으로 로드됩니다. :chatgpt-content-reference{index="24"}

Skill을 사용하면 Qwen3은 resource를 만들기 전에 vLLM을 선택하고, AWS DLC catalog에서 현재 region에 맞는 image URI를 조회하며, autoscaling과 CloudWatch alarm을 같이 구성합니다. Smoke test가 HTTP 200을 반환하더라도 실제 generation이 `max_tokens` 때문에 reasoning block 안에서 잘려 answer가 없는 경우를 Agent가 “성공”으로 처리하지 않고 configuration issue로 남긴 사례도 소개됐습니다. :chatgpt-content-reference{index="25"}

여기서 중요한 교훈은 상당히 일반적입니다.

**모델의 parametric knowledge보다 빨리 변하는 운영 지식은 모델 안에 기억시키지 말고 versioned Skill로 관리하는 편이 낫습니다.**

예를 들어

`현재 vLLM 실행 옵션`  
`NVIDIA driver/CUDA compatibility`  
`프로젝트 directory convention`  
`배포 port`  
`정적 분석 command`

같은 정보는 모델에 fine-tune할 대상이 아니라 repository 안의 versioned documentation/skill로 두는 것이 훨씬 관리하기 쉽습니다.

또 AWS는 특정 HF Skills commit SHA를 pin해 사용했습니다. Agent Skill도 dependency와 똑같이 **version pinning**이 필요하다는 좋은 예입니다.

원문: [공식 기술 가이드 · Deploy Hugging Face models on Amazon SageMaker AI with coding agents](https://aws.amazon.com/blogs/machine-learning/deploy-hugging-face-models-on-amazon-sagemaker-ai-with-coding-agents/)

## 7. GitHub Copilot — Code Review가 `읽고 코멘트`에서 **Shell validation + Multi-Agent findings + Production error→PR**로 확대 ★★★★☆

9월 18일 GitHub Copilot 주간 업데이트에서는 code review와 Agent runtime이 꽤 의미 있게 바뀌었습니다. Copilot code review는 이제 **shell tool을 사용해 변경사항을 실제 검증**할 수 있고, Lite review에서는 여러 Agent의 finding을 합칩니다. 이후 commit에서 수정된 finding은 자동으로 resolved 처리하며 여전히 남아 있는 issue만 유지합니다. :chatgpt-content-reference{index="27"}

이건 review Agent가 단순 static text reviewer에서 **execution-backed reviewer**로 이동하는 흐름입니다. 예를 들어 diff를 보고 “test가 깨질 것 같다”고 추측하는 대신 shell에서 실제 test/static analysis command를 돌릴 수 있습니다. Review의 신뢰성은 model reasoning만으로 결정되지 않고 **tool-backed verification 비중**이 커지게 됩니다. :chatgpt-content-reference{index="28"}

Copilot App에는 **Sentry Canvas**도 추가됐습니다. Production crash report, stack trace, 관련 context를 읽고 원인을 조사한 뒤 fix validation과 PR 준비까지 연결합니다. VS Code Agent window에서는 **local Dev Container** 안에서 Agent를 실행할 수 있어 프로젝트의 실제 dependency/toolchain을 유지하면서 작업할 수 있습니다. :chatgpt-content-reference{index="29"}

전체 흐름을 보면 coding-agent 제품의 abstraction이 상당히 바뀌고 있습니다.

`Prompt → code`

에서

`Production signal → isolated runtime → investigate → execute tests → review → PR`

로 확장되고 있습니다.

앞으로 coding-agent capability를 평가할 때 단순 코드 생성률보다 **“실제 runtime evidence를 얼마나 잘 수집하고 검증 loop를 닫는가”**가 점점 중요해질 가능성이 큽니다.

원문: [릴리스 노트 · GitHub Copilot weekly releases — September 14](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14/)

## 8. RL Post-Training 연구 — “개별 Skill을 잘 학습시키면 자동으로 조합할 수 있다”는 가정이 깨진다 ★★★★☆

기초 ML 쪽에서는 **Compositional Reasoning in Language Models under Reinforcement Learning Post-Training**이 주목할 만합니다. 연구진은 reasoning task를 dependency graph로 표현하고, 개별 skill을 따로 학습한 뒤 그 skill들을 조합해야 하는 task에서 얼마나 generalize하는지 조사했습니다. :chatgpt-content-reference{index="31"}

결과는 꽤 비대칭적입니다. **Decomposed skill을 각각 잘 학습시켜도 composed task로 안정적으로 전이되지 않았습니다.** 반대로 여러 skill을 함께 써야 하는 composed task에서 RL을 수행한 모델은 개별 decomposed task로 비교적 잘 역전이됐습니다. 연구진은 length extrapolation, structural distribution shift, unseen skill transfer에서도 이 현상을 조사했습니다. :chatgpt-content-reference{index="32"}

아직 핵심 실험은 data-structure 기반 synthetic task이고 실제 tool-calling에 대해서는 **pilot study 수준**입니다. 따라서 “Agent 학습은 무조건 복합 task로 해야 한다”까지 일반화하면 이릅니다. 다만 training data 구성 측면의 시사점은 큽니다. :chatgpt-content-reference{index="33"}

예를 들어 Agent가 각각

`검색할 수 있음`  
`코드를 수정할 수 있음`  
`테스트할 수 있음`

을 잘 수행한다고 해서 자동으로

`문제 분석 → 검색 → 수정 → test → 실패 원인 추적 → 재수정`

을 잘 수행한다고 보장할 수 없습니다.

Fine-tuning/post-training dataset에서도 개별 tool-use example만 채우는 것보다 **여러 skill이 의존 관계를 이루는 trajectory**를 별도 category로 확보할 필요가 있습니다.

원문: [논문 · Compositional Reasoning in Language Models under Reinforcement Learning Post-Training](https://arxiv.org/abs/2609.19465?utm_source=chatgpt.com)

# 오늘 꼭 볼 것 3개

**1순위는 ALIBI입니다.** LLM 기반 악성코드/정적분석 시스템을 만들 때 “모델이 코드 분석 결과를 잘 설명하는가?”보다 더 근본적인 질문인 **어떤 입력을 사실로 믿게 할 것인가**를 다룹니다. LLM report layer 앞에 evidence provenance를 두어야 하는 이유가 매우 강합니다. :chatgpt-content-reference{index="35"}

**2순위는 HyperPod Inference Gateway입니다.** LLM serving이 이제 model server 내부 optimization만의 문제가 아니라 **prefix/KV/adapter locality를 이해하는 request router**까지 포함하는 문제로 가고 있습니다. 여러 replica를 운영하기 시작하면 거의 반드시 만나게 되는 문제입니다. :chatgpt-content-reference{index="36"}

**3순위는 Chronicle입니다.** Agent failure가 비결정적이라 regression test를 만들기 어렵다는 문제를 **recorded trajectory → deterministic fixture**로 바꾸는 아이디어가 매우 실용적입니다. Multi-agent/harness를 실제 프로젝트에 넣는다면 좋은 참고 구현입니다. :chatgpt-content-reference{index="37"}

# 오늘 직접 해볼 만한 실습 — `Verified Evidence vs Untrusted Narrative` 악성코드 분석 A/B 테스트

오늘은 ALIBI 논문의 문제를 **공격 payload를 만들지 않고도** 안전하게 재현해볼 수 있습니다.

현재 정적분석 pipeline에서 LLM에 전달하는 입력을 두 채널로 나눠보십시오.

```text
VERIFIED_EVIDENCE
- static analyzer finding
- suspicious API/import
- exact code span
- CFG/data-flow result
- Ruff/mypy/other tool output
- file/hash/section metadata

UNTRUSTED_CONTEXT
- strings extracted from file
- comments
- embedded description
- package/app metadata
- human-readable claims
```

그다음 동일 sample에 대해 세 조건을 비교합니다.

```text
A. 모든 정보를 하나의 context로 그대로 전달
B. VERIFIED / UNTRUSTED를 명시적으로 분리
C. B + 최종 verdict의 모든 근거가 VERIFIED_EVIDENCE를 참조하도록 강제
```

기록할 값은 `malicious/benign verdict`, `risk score`, `confidence`, `사용된 evidence ID`, `untrusted-context 인용 횟수`, `static analyzer와 LLM verdict disagreement` 정도면 충분합니다.

특히 **정답 label은 그대로인데 confidence나 severity가 내려가는 경우**도 별도로 기록하는 것이 중요합니다. ALIBI 연구에서도 강한 모델은 label을 완전히 뒤집지 않더라도 severity와 confidence가 흔들렸습니다. :chatgpt-content-reference{index="38"}

이렇게 하면 단순히 “LLM이 취약점을 설명한다”에서 한 단계 올라가 **`evidence provenance → trust separation → LLM reasoning → verdict` 전체를 검증하는 보안 평가**가 됩니다. 정적 분석 + Local LLM 보고서 구조에 바로 붙이기 좋은 실험입니다.
