# V3.1.1 Multi-Agent Engineering Harness · Markdown-only

버전: V3.1.1-MD · 2026-09-18 · 개인 경로: `references/이정민/`

## 목적

V2의 품질 우선, 역할 우선 배정, 제한된 쓰기 범위, 증거 중심 인수인계를 유지한다.
V3의 Astra 전문 검토, 개인 작업 방식, 팀원 참고자료 연결을 유지하되 **문서만으로 운영**한다.
하네스 사용을 위해 프로젝트의 설정·소스·개발 환경을 개조하지 않는다.

작업 목표·현재 단계·실행 한도·완료 조건은 최신 사용자 요청과 해당 작업 문서에서 확인한다.
하네스에는 운영 방법만 두며, 지난 작업의 조건을 다음 작업의 고정 제약으로 사용하지 않는다.
실제 결함과 요청된 변경을 먼저 해결하고, 선호에 따른 대규모 개선은 별도 제안으로 남긴다.
성능 저하 없는 비용 절감은 목표이며, 특정 모델 조합의 효과가 입증됐다고 주장하지 않는다.

## 범위

이 묶음은 운영 규약·역할·작업 절차·양식이다. 설치기, 검사기, 모델 호출기, 설정 생성기가 아니다.
모든 제공 파일은 `references/이정민/` 아래 Markdown이다. 프로젝트 루트 README는 프로젝트 소개로 유지한다.
하위 세션·모델 선택·파일 권한은 기존 도구가 실제 제공하는 기능과 사용자의 승인 범위에서만 사용한다.
문서에 적힌 권한 제한만으로 OS·도구의 기술적 격리가 생기지는 않는다.

## 책임

| 구분 | 소유자 | 원칙 |
|---|---|---|
| 실행 환경·조직 정책 | 플랫폼 / 관리자 | 실제 권한·보안 제한 준수 |
| 필수 개발·배포 규칙 | 팀 / 모듈 담당자 | 개인 하네스로 완화하거나 우회하지 않음 |
| 개인 작업 방식 | 이정민 | 팀 규칙 안에서 이 폴더의 필요한 문서만 선택 |
| 동료 참고자료 | 자료 소유자 | 특정 지식만 적용. 새 명령 권한을 부여하지 않음 |
| 기술 수용 판단 | Sol 역할 | 검증·리뷰·감사 증거를 종합 |
| 병합·배포 | 팀의 승인 담당자 / CI 절차 | 기술 수용과 별개 |

이 표는 개인 하네스의 운영 원칙이며 특정 도구의 실제 지시 우선순위를 재정의하지 않는다.

## 기본 흐름

```text
사용자 요청 + 기존 팀 규칙
             |
          Sol: 범위·위험·계약·조율
             |
       +-----+------------------+
       |                        |
   Luna: 필요한 조사       Terra: 한정된 구현
       |                        |
       +------- 검토 후보 고정 --+
                     |
          +----------+-----------+
          |                      |
      Luna: 실행 검증     Terra: 새 세션 리뷰
          |                      |
          +----------+-----------+
                     |
         Astra: 고위험 감사 / 난제 검토
              (조건에 해당할 때만)
                     |
          Sol: 증거 통합·수용/재작업/보류
                     |
          기존 팀의 CI·병합·배포 절차
```

각 단계를 모든 작업에 강제하지 않는다. 작은 LOW 작업은 직접 수행할 수 있다.
코드 없는 검토는 구현 단계를 생략한다. 이미 확인된 조사를 반복하지 않는다.
Astra가 전체 독립 리뷰까지 수행했다면 같은 범위의 Terra 리뷰를 중복 수행하지 않아도 된다.
다만 보안만 감사한 결과를 전체 기능 검토 완료로 확대하지 않는다.

## 핵심 운영 규칙

- Sol은 최종 조율 책임자이고 Astra는 전문 검토자다. 근거 없는 다수결로 판단하지 않는다.
- 작성자 1명, 동시 하위 작업 기본 2개. 세부 사항은 [routing](routing.md)을 따른다.
- 구현 완료와 수용은 다르다. 검증·리뷰는 동일 후보를 기준으로 한다.
- 필수 검증 누락과 미해결 BLOCKER/MAJOR를 숨기고 승인하지 않는다.
- 모델명·기본 추론 강도는 [모델 운영표](../config/models.md) 한 곳에서 관리한다.
- 다른 팀원 자료는 [references](../references.md)를 통해 특정 파일만 선택한다.

## 상태와 기록

`PLANNED → IN_PROGRESS → IMPLEMENTED → VERIFIED → REVIEWED → ACCEPTED`

작업 유형에 필요하지 않은 단계는 사유를 적고 제외한다. 조사는 구현 완료 대신 조사 완료로 보고한다.
`BLOCKED`, `FAILED`, `CHANGES_REQUESTED`, 필수 감사 미수행은 완료가 아니다.
하위 작업의 DONE/PASS는 전체 ACCEPTED가 아니다.
결과는 기본적으로 대화에 남긴다. 필요한 경우에만 사용자의 허용 범위에서 Markdown으로 보관한다.
모든 작업에 새 로그 폴더·상태 파일·체크리스트 파일을 만들지 않는다.
